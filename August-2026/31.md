### Question: House Robber (Dynamic Programming — Medium)

You are a professional robber planning to rob houses along a street. Each house has a non-negative amount of money stashed, given as an integer array `nums`, where `nums[i]` is the money in house `i`. The only constraint is that adjacent houses have connected security systems, so **you cannot rob two adjacent houses on the same night** (robbing them would trigger the alarm).

Given `nums`, return the maximum amount of money you can rob without robbing two adjacent houses.

**Input format:**
- An integer array `nums` of length `n`.

**Output format:**
- An integer: the maximum amount of money that can be robbed.

**Worked Examples:**

1. `nums = [1, 2, 3, 1]` → `4` (rob house 0 and house 2: `1 + 3 = 4`; robbing house 1 and house 3 only gives `2 + 1 = 3`).
2. `nums = [2, 7, 9, 3, 1]` → `12` (rob houses 0, 2, and 4: `2 + 9 + 1 = 12`; robbing house 1 alone gives 7, worse overall).
3. `nums = [2, 1, 1, 2]` → `4` (rob house 0 and house 3: `2 + 2 = 4`; they are not adjacent, so both are allowed).

**Constraints:**
- `1 <= n <= 100`
- `0 <= nums[i] <= 400`

---

### Step-by-Step Walkthrough

**Approach — Dynamic Programming (space-optimized)**

Define `dp[i]` as the maximum money that can be robbed considering only the first `i` houses (indices `0..i-1`), where the robber is free to choose any valid (non-adjacent) subset among those `i` houses. For each house `i` (0-indexed), there are exactly two choices:

- **Skip house `i`:** the best total is whatever was achievable using the first `i` houses, i.e. `dp[i]`.
- **Rob house `i`:** house `i-1` must NOT have been robbed, so the best total is `nums[i]` plus the best achievable using the first `i-1` houses, i.e. `dp[i-1] + nums[i]`.

This gives the recurrence (using 1-indexed `dp` for clarity, `dp[i]` = best using first `i` houses):

```
dp[0] = 0                                   // no houses
dp[1] = nums[0]                             // only one house, must take it
dp[i] = max(dp[i-1], dp[i-2] + nums[i-1])   // for i >= 2
```

The answer is `dp[n]`.

**Why it works:** the recurrence considers every house exactly once and, for each, correctly accounts for the adjacency constraint by only combining "rob this house" with the best solution that explicitly excludes the immediately preceding house (`dp[i-2]`, not `dp[i-1]`). Since `dp[i-2]` already represents the optimal answer for the first `i-2` houses (which may or may not include house `i-2` itself, but never conflicts with the constraint relative to house `i-1`), no invalid adjacent pair is ever counted, and no valid combination is missed because both choices (skip/rob) are considered at every step.

**Space optimization:** `dp[i]` only ever depends on `dp[i-1]` and `dp[i-2]`, so the full array is unnecessary — two rolling variables (`prev1` for `dp[i-1]`, `prev2` for `dp[i-2]`) are enough, dropping space from `O(n)` to `O(1)`.

**Complexity Analysis:**
- **Time complexity:** `O(n)` — a single pass over the array, constant work per house.
- **Space complexity:** `O(1)` — only two rolling variables are kept, regardless of `n`.

### C++ Code

```cpp
#include <iostream>
#include <vector>
#include <algorithm>
using namespace std;

class Solution {
public:
    // Returns the maximum money robbable with no two adjacent houses chosen.
    int rob(vector<int>& nums) {
        int prev2 = 0; // dp[i-2]: best using houses before the previous one
        int prev1 = 0; // dp[i-1]: best using houses up to (not including) i

        for (int i = 0; i < static_cast<int>(nums.size()); i++) {
            int cur = max(prev1, prev2 + nums[i]); // skip house i vs rob house i
            prev2 = prev1;
            prev1 = cur;
        }

        return prev1;
    }
};

int main() {
    Solution sol;

    // Example 1
    vector<int> a1 = {1, 2, 3, 1};
    cout << sol.rob(a1) << " (expected 4)" << endl;

    // Example 2
    vector<int> a2 = {2, 7, 9, 3, 1};
    cout << sol.rob(a2) << " (expected 12)" << endl;

    // Example 3
    vector<int> a3 = {2, 1, 1, 2};
    cout << sol.rob(a3) << " (expected 4)" << endl;

    return 0;
}
```

**Trace against the examples:**
- `nums = [1, 2, 3, 1]`: `i=0`: `cur=max(0,0+1)=1` → `prev2=0,prev1=1`. `i=1`: `cur=max(1,0+2)=2` → `prev2=1,prev1=2`. `i=2`: `cur=max(2,1+3)=4` → `prev2=2,prev1=4`. `i=3`: `cur=max(4,2+1)=4` → `prev2=4,prev1=4`. Final: `4`. ✓
- `nums = [2, 7, 9, 3, 1]`: `i=0`: `cur=2` → `prev2=0,prev1=2`. `i=1`: `cur=max(2,0+7)=7` → `prev2=2,prev1=7`. `i=2`: `cur=max(7,2+9)=11` → `prev2=7,prev1=11`. `i=3`: `cur=max(11,7+3)=11` → `prev2=11,prev1=11`. `i=4`: `cur=max(11,11+1)=12` → `prev2=11,prev1=12`. Final: `12`. ✓
- `nums = [2, 1, 1, 2]`: `i=0`: `cur=2` → `prev2=0,prev1=2`. `i=1`: `cur=max(2,0+1)=2` → `prev2=2,prev1=2`. `i=2`: `cur=max(2,2+1)=3` → `prev2=2,prev1=3`. `i=3`: `cur=max(3,2+2)=4` → `prev2=3,prev1=4`. Final: `4`. ✓

## CS Fundamentals

### 1. Operating Systems (Conceptual/Definition)

What is a deadlock, and what are the four Coffman conditions that must all hold simultaneously for one to occur? Briefly explain how breaking just one of the four is enough to prevent deadlock.

**Answer:**

A **deadlock** is a state in which two or more processes (or threads) are each waiting indefinitely for a resource held by another process in the same waiting cycle, so none of them can ever proceed. Deadlock is a permanent standstill, not a temporary slowdown — without external intervention (like killing a process), the involved processes never make progress again.

The **four Coffman conditions** are the necessary conditions that must **all** hold at once for a deadlock to be possible:

1. **Mutual exclusion:** at least one resource must be held in a non-shareable mode — only one process can use it at a time (e.g., a printer, or a lock on a data structure).
2. **Hold and wait:** a process is currently holding at least one resource while simultaneously waiting to acquire additional resources that are held by other processes.
3. **No preemption:** resources cannot be forcibly taken away from a process holding them — they can only be released voluntarily by the process holding them, once it finishes using them.
4. **Circular wait:** there exists a cycle of two or more processes, where each process is waiting for a resource held by the next process in the cycle (e.g., process A waits for a resource held by B, and B waits for a resource held by A).

**Why breaking one condition is enough:** all four conditions are individually *necessary* — deadlock cannot occur if any single one is absent — so prevention strategies target eliminating just one:
- Breaking **mutual exclusion** (using resources that support shared/concurrent access, e.g., read-only files) removes the possibility entirely, though it's often infeasible for inherently exclusive resources.
- Breaking **hold and wait** (requiring a process to request all resources it will ever need up front, atomically, or to release everything before requesting more) prevents a process from holding one resource while blocking on another.
- Breaking **no preemption** (allowing a resource to be forcibly reclaimed from a waiting process, which then must reacquire everything later) is used in some database systems (transaction rollback and retry).
- Breaking **circular wait** (imposing a strict global ordering on resource acquisition, so every process must always request resources in the same relative order, e.g., always lock connection A before connection B) is the most common practical fix, since it directly prevents cycles from forming.

**Why this matters:** the Coffman conditions turn "avoid deadlock" from a vague goal into a concrete engineering checklist — in practice, most real-world deadlock prevention (like the "always acquire locks in a fixed global order" rule taught for multi-lock code) is really just an application of breaking the circular-wait condition, and recognizing which condition a given system design violates is the fastest way to reason about whether a set of concurrent operations can deadlock.

### 2. Computer Networks (Comparison)

Compare HTTP/1.1, HTTP/2, and HTTP/3 in terms of how they handle multiple in-flight requests over a connection, and explain what specific problem each version was introduced to solve.

**Answer:**

| Aspect | HTTP/1.1 | HTTP/2 | HTTP/3 |
|---|---|---|---|
| Transport protocol | TCP | TCP | QUIC (built on UDP) |
| Multiple requests per connection | One request in flight per TCP connection at a time (without pipelining); browsers work around this by opening several parallel TCP connections to the same host. | **Multiplexing**: many requests/responses interleaved as independent streams over a **single** TCP connection. | Multiplexing carried over independent QUIC streams, but now each stream also has its own independent loss-recovery. |
| Head-of-line (HOL) blocking | Severe — a slow response blocks everything queued behind it on that connection. | Solved at the HTTP layer (streams are independent), but **still exists at the TCP layer**: if one TCP packet is lost, TCP holds up delivery of all bytes behind it (across all streams) until it's retransmitted. | Solved at **both** layers — QUIC's per-stream loss recovery means a lost packet only stalls the one stream it belongs to; other streams keep flowing. |
| Connection setup | TCP handshake (1 round-trip) then, for HTTPS, a separate TLS handshake (1-2 more round-trips). | Same as HTTP/1.1 (TCP + TLS handshakes are separate, unless TLS session resumption is used). | QUIC **combines** the transport and TLS 1.3 handshake into a single combined handshake (often 1 round-trip, or 0-RTT on a resumed connection), reducing connection setup latency. |
| Header overhead | Headers sent as plain text on every request, fully repeated. | **HPACK** header compression — repeated header fields (like cookies, user-agent) across requests are compressed/referenced instead of resent in full. | **QPACK** — a variant of header compression adapted to work correctly even when QUIC streams can arrive out of order. |

**What problem each version solves:**
- **HTTP/1.1 → HTTP/2:** solves the "too many parallel TCP connections" and "no multiplexing" problems of HTTP/1.1, by multiplexing many logical requests over one TCP connection with header compression, cutting overhead and improving throughput on a single connection.
- **HTTP/2 → HTTP/3:** solves the **TCP-layer head-of-line blocking** that HTTP/2 still suffered from — since HTTP/2 multiplexes over a single TCP connection, one lost packet stalls every stream, which is especially painful on lossy networks (e.g., mobile/WiFi). By moving to QUIC (over UDP, with its own reliability and congestion control built at the transport layer per-stream), a lost packet only affects the one stream it belongs to, and connection setup is faster because transport and encryption handshakes are combined.

**Why this matters:** each version's design directly follows from a real, measured bottleneck in the previous one — HTTP/2's multiplexing was a response to the connection-limit workarounds browsers needed under HTTP/1.1, and QUIC's redesign of the transport layer itself was necessary because TCP's in-order-delivery guarantee, not anything in the HTTP protocol itself, was the remaining source of head-of-line blocking that HTTP/2 alone couldn't fix.

### 3. DBMS (Scenario/Applied)

A `users` table has 50 million rows and a query `SELECT * FROM users WHERE email = 'someone@example.com'` is used constantly for login lookups, but it currently takes several seconds per query. There is no index on the `email` column, only the default primary key index on `id`. Explain why the query is slow, what type of index you'd add, and any trade-off that comes with adding it.

**Answer:**

**Why it's slow:** without an index on `email`, the database has no way to jump directly to matching rows — it must perform a **full table scan**, reading all 50 million rows sequentially and checking each one's `email` value against the target, discarding the vast majority as non-matches. This is `O(n)` work per query, and at 50 million rows, even fast per-row comparisons add up to seconds of I/O and CPU time. The existing primary key index on `id` doesn't help at all here because it's organized by `id`, not `email` — an index can only accelerate lookups on the column(s) it's built on.

**Fix — add a (non-clustered / secondary) B-tree index on `email`:**
```sql
CREATE UNIQUE INDEX idx_users_email ON users(email);
```
A B-tree index keeps `email` values in sorted order alongside a pointer back to the corresponding row (or, in a clustered-index-organized engine like InnoDB, back to the primary key). This turns the lookup from a linear scan into a `O(log n)` tree traversal — for 50 million rows, that's roughly 26 comparisons instead of up to 50 million, which is why the same query then returns in milliseconds instead of seconds. Marking it `UNIQUE` is appropriate here since login emails should be unique per account, and it lets the database also enforce that constraint for free.

**Clustered vs. non-clustered distinction:** the primary key index is typically the **clustered** index — the table's actual rows are physically stored in that order, so a primary-key lookup requires no extra pointer-following. A new index on `email` is a **non-clustered (secondary)** index — it stores `email` values sorted with a reference to the primary key (or row location), so a lookup does: (1) traverse the `email` B-tree to find the matching entry, then (2) follow the reference to fetch the full row. This is still vastly faster than a full scan, but technically one extra hop compared to a clustered lookup.

**Trade-offs of adding the index:**
- **Write cost:** every `INSERT`, `UPDATE` (of the `email` column), or `DELETE` must now also update the index's B-tree structure, which adds overhead to write operations — usually a good trade for a login table, since reads (logins) vastly outnumber writes (account creation/email changes).
- **Storage cost:** the index itself consumes additional disk space (roughly proportional to the size of the indexed column times the row count, plus B-tree overhead).
- **Maintenance:** indexes can become fragmented over time under heavy write load and may need periodic rebuilding/reorganizing depending on the database engine.

**Why this matters:** "the query is slow" almost always traces back to either a missing index or an index the query planner can't use (e.g., applying a function to the indexed column in the `WHERE` clause, like `WHERE LOWER(email) = ...`, which prevents a plain index on `email` from being used) — recognizing which columns are hit by high-frequency `WHERE`/`JOIN` clauses and indexing those deliberately, while accepting the write/storage cost, is one of the highest-leverage and most common tuning steps in real database administration.
