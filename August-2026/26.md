### Question: Linked List Cycle Detection (Linked Lists — Easy)

**Problem Statement**

Given the `head` of a singly linked list, determine whether the list contains a cycle. A cycle exists if some node in the list can be reached again by continuously following the `next` pointer.

As a follow-up, return the node where the cycle *begins* (or `nullptr` if there is no cycle).

**Input/Output Format**

- Input: a pointer to the head node of a singly linked list (possibly `nullptr`).
- Output: a boolean for the main problem; a node pointer for the follow-up.

**Examples**

1. `3 → 2 → 0 → -4 → (back to node 2)` → Output: `true`, cycle starts at the node with value `2`.
2. `1 → 2 → (back to node 1)` → Output: `true`, cycle starts at the node with value `1`.
3. `1 → 2 → 3 → nullptr` → Output: `false`.

**Constraints**

- Number of nodes in range `[0, 10^4]`.
- Node values are arbitrary integers and may repeat, so you cannot identify a node by its value.
- Aim for O(n) time and O(1) extra space.

### Step-by-Step Walkthrough

**The obvious approach first.** Walk the list, storing every node pointer you've seen in a hash set. If you ever reach a node already in the set, that's a cycle; if you reach `nullptr`, there isn't one. It's O(n) time and correct — and it's genuinely a fine answer — but it costs O(n) extra space. Note that you must store node **addresses**, not values: values can repeat in a perfectly acyclic list.

**Key insight (Floyd's tortoise and hare).** Think about two runners on a track. If the track is a straight line, the faster runner reaches the end and the race is over. If the track is a **loop**, the faster runner must eventually lap the slower one — they cannot pass each other without at some point occupying the same position.

So run two pointers at different speeds:

1. `slow` advances one node per step; `fast` advances two.
2. If `fast` (or `fast->next`) reaches `nullptr`, the list ends — **no cycle**.
3. If `slow == fast` at any point, they've met — **cycle**.

**Why they must meet, and why they can't skip past each other.** Once both pointers are inside the cycle, consider the gap from `fast` to `slow` measured *forward around the loop*. Each step, `fast` gains exactly one position on `slow`, so that gap shrinks by exactly 1 per step. A quantity that decreases by exactly 1 each step and lives in the range `[0, cycleLength)` must hit 0 — it cannot jump over it. That's the whole proof, and it's also why a step size of 2 specifically is convenient: a gap closing by 1 at a time can never overshoot.

**Follow-up: finding where the cycle starts.** This is the part worth memorising, because it looks like magic. Let:
- `L` = distance from head to the cycle's entry point,
- `C` = length of the cycle,
- `k` = distance from the entry point to the meeting point (measured forward around the cycle).

When they meet, `slow` has travelled `L + k` and `fast` has travelled `L + k + nC` for some whole number of extra laps `n`. Since `fast` moves exactly twice as far:

```
2(L + k) = L + k + nC
    L + k = nC
        L = nC - k
```

Read that last line as a statement about distances: starting at the **meeting point** and walking `L` steps forward lands you exactly at the cycle entry (you complete the remaining `C - k` of the current lap, then `n-1` full laps). And starting at the **head** and walking `L` steps also lands you at the entry, by definition of `L`.

So: put one pointer back at `head`, leave the other at the meeting point, and advance **both one step at a time**. They meet precisely at the cycle's entry node.

**Complexity.**
- Time: O(n) — the pointers reach the cycle in O(L) and meet within O(C) more.
- Space: O(1) — two pointers, regardless of list length.

### C++ Code

```cpp
struct ListNode {
    int val;
    ListNode* next;
    explicit ListNode(int x) : val(x), next(nullptr) {}
};

bool hasCycle(ListNode* head) {
    ListNode* slow = head;
    ListNode* fast = head;

    // Checking both `fast` and `fast->next` is what makes the two-step
    // advance safe on a list with an odd number of remaining nodes.
    while (fast != nullptr && fast->next != nullptr) {
        slow = slow->next;
        fast = fast->next->next;

        if (slow == fast) {
            return true;   // The fast pointer lapped the slow one.
        }
    }

    return false;          // Reached the end, so the list is acyclic.
}

ListNode* detectCycleStart(ListNode* head) {
    ListNode* slow = head;
    ListNode* fast = head;

    // Phase 1: find a meeting point inside the cycle, if one exists.
    while (fast != nullptr && fast->next != nullptr) {
        slow = slow->next;
        fast = fast->next->next;
        if (slow == fast) break;
    }

    if (fast == nullptr || fast->next == nullptr) {
        return nullptr;    // No cycle.
    }

    // Phase 2: L = nC - k means head and the meeting point are both
    // exactly L single steps away from the cycle entry.
    slow = head;
    while (slow != fast) {
        slow = slow->next;
        fast = fast->next;
    }

    return slow;
}
```

## CS Fundamentals

### 1. Operating Systems (Comparison)

**Question:** What is the difference between a mutex and a semaphore? Both can protect a critical section — so why does the distinction matter, and when is using a binary semaphore as a lock actually a bug?

**Answer:**

The mechanical difference is small; the difference in *intent* is what matters.

**A mutex** (mutual exclusion lock) enforces that at most one thread is inside a critical section at a time. Its defining property is **ownership**: the thread that locks a mutex is the only thread allowed to unlock it. That ownership is what makes several important features possible:
- **Priority inheritance** — if a low-priority thread holds a lock a high-priority thread wants, the OS can temporarily raise the holder's priority. It can only do this because it knows *who* holds the lock.
- **Recursive locking** and **error checking** — the runtime can detect "this thread already holds this" or "you're unlocking something you don't own".

**A semaphore** is a counter with two atomic operations, `wait`/`P` (decrement, block if it would go below zero) and `signal`/`V` (increment, wake a waiter). It has **no ownership** — any thread may signal, including a thread that never waited. It is fundamentally a mechanism for **counting available resources** or for **signalling between threads**.

| | Mutex | Semaphore |
| --- | --- | --- |
| Value | Locked / unlocked | Integer count ≥ 0 |
| Ownership | Yes — locker must unlock | No — anyone can signal |
| Purpose | Mutual exclusion | Resource counting, signalling |
| Priority inheritance | Possible | Not possible |
| Classic use | Guard shared state | Connection pool of N; producer/consumer |

**Where the distinction bites.** A **counting semaphore** initialised to N models "there are N of this resource" — N database connections, N slots in a bounded buffer. A mutex simply cannot express that.

Conversely, a semaphore is the right tool for **signalling across threads**, which a mutex cannot do correctly. In producer/consumer, the producer signals "an item is available" and the consumer waits on it. Here the signaller is deliberately *not* the waiter — exactly the pattern a mutex forbids.

**When a binary semaphore as a lock is a bug.** A semaphore initialised to 1 looks like a mutex and is often used as one, but:

1. **No ownership means no priority inheritance**, which exposes you to **unbounded priority inversion**: a low-priority thread holds the lock, a medium-priority thread preempts it and runs indefinitely, and a high-priority thread waiting on the lock is blocked the whole time. With a real mutex the OS boosts the holder and the inversion is bounded. This is not hypothetical — it is the documented cause of the 1997 Mars Pathfinder mission's repeated system resets.
2. **Any thread can `signal`**, so a bug elsewhere can "unlock" a critical section a different thread is inside, with no error raised. A mutex would reject that.
3. **Double-signal breaks the invariant permanently** — signalling twice pushes the count to 2, and now two threads can be in the critical section simultaneously. A mutex unlock is idempotent in the sense that it cannot raise the limit.

**Rule of thumb:** if you are protecting shared data, use a mutex. If you are counting resources or signalling between threads, use a semaphore.

### 2. DBMS (Scenario/Applied)

**Question:** A ticket booking service checks `SELECT seats_available FROM shows WHERE id = ?`, and if it's greater than zero, runs `UPDATE shows SET seats_available = seats_available - 1 WHERE id = ?`. Both statements are inside a transaction. Under load, the service occasionally sells more tickets than exist. Why does wrapping it in a transaction not prevent this, and how would you fix it?

**Answer:**

**Why the transaction doesn't save you.** The common misreading of ACID is that "transaction" means "nothing else can interfere". It doesn't. Isolation is a *level*, and every engine's default level permits this specific anomaly.

Under `READ COMMITTED` (the PostgreSQL/Oracle default), the sequence is:

1. Transaction A reads `seats_available = 1`. Passes the check.
2. Transaction B reads `seats_available = 1`. Also passes the check — A hasn't committed, and even after it does, B already has its snapshot of the read.
3. A decrements to 0 and commits.
4. B decrements — and because `seats_available = seats_available - 1` is evaluated against the *current* row at write time, it goes to **-1**.

Both transactions committed successfully. Neither did anything the database considers illegal. This is the **lost update** / **read-modify-write race**, and the root cause is that the *decision* (the read and the `if`) was made outside any lock, while only the *action* was transactional. Even MySQL's stricter `REPEATABLE READ` default doesn't help here, because it gives A and B a consistent snapshot for reads — which is precisely what lets them both see 1.

**Fixes**, roughly in order of what production systems actually do:

**1. Make the database enforce it — a `CHECK` constraint (do this regardless).**
```sql
ALTER TABLE shows ADD CONSTRAINT seats_non_negative CHECK (seats_available >= 0);
```
This doesn't prevent the race, but it converts a silent data-corruption bug into a loud failed transaction. It's the safety net you want even after fixing the logic.

**2. Do the check and the write in one atomic statement — usually the best fix.**
```sql
UPDATE shows
   SET seats_available = seats_available - 1
 WHERE id = ? AND seats_available > 0;
```
Then inspect the **affected row count**: 1 means the booking succeeded, 0 means it was already sold out. There is no window between the check and the decrement because they are the same statement, and the engine takes a row lock for the duration. This is cheap, requires no extra round trips, and needs no special isolation level.

**3. Pessimistic locking — `SELECT ... FOR UPDATE`.**
```sql
SELECT seats_available FROM shows WHERE id = ? FOR UPDATE;
```
This takes an exclusive row lock at read time, so B blocks until A commits and then re-reads the true value of 0. Correct, and necessary when the decision genuinely requires application logic between the read and the write. The cost is serialised access to that row and real deadlock risk if different code paths lock rows in different orders.

**4. Optimistic locking — a version column.** Read `(seats_available, version)`, then `UPDATE ... WHERE id = ? AND version = ?`, incrementing the version. If zero rows are affected, someone else won; retry. Better than pessimistic locking under low contention, worse under high contention because of retry churn — which is exactly the wrong shape for a hot ticket release.

**5. Raise the isolation level to `SERIALIZABLE`.** Correct, but the bluntest instrument: it forces the engine to detect and abort conflicting transactions, so your application must be prepared to retry on serialisation failures, and throughput on the hot row drops.

**The general lesson:** a transaction guarantees your writes are *atomic and durable*; it does **not** guarantee that what you read is still true when you write. Any read-decide-write sequence needs the decision and the write fused into one atomic operation, or an explicit lock held across both.

### 3. Computer Networks (Conceptual/Definition)

**Question:** What happens during a TLS handshake when you connect to an HTTPS site? Explain the role of asymmetric and symmetric cryptography, and what the certificate actually proves.

**Answer:**

TLS gives three guarantees: **confidentiality** (nobody can read the traffic), **integrity** (nobody can alter it undetected), and **authentication** (you're talking to the server you think you are). The handshake's job is to establish all three before any application data flows.

**Why two kinds of cryptography.** Asymmetric (public-key) crypto solves the key-distribution problem — you can encrypt to a stranger's public key without a prior shared secret — but it is computationally expensive, orders of magnitude slower than symmetric crypto. Symmetric crypto (AES) is fast, but both sides must already share a key. So TLS uses **asymmetric crypto briefly, to agree on a symmetric key**, then switches to symmetric crypto for the actual data. This is the single most important structural idea in the protocol.

**The handshake (TLS 1.3, which collapsed the older four-step exchange into one round trip):**

1. **ClientHello.** The client sends the TLS versions and cipher suites it supports, a random nonce, the target hostname via **SNI** (so one IP can host many HTTPS sites), and — the 1.3 optimisation — a **key share**: its public half of a Diffie-Hellman exchange, guessed optimistically before knowing the server's preference.
2. **ServerHello.** The server picks the cipher suite, sends its own random nonce and its own DH key share. At this point **both sides can independently compute the same shared secret** via Diffie-Hellman, without that secret ever crossing the wire.
3. **Certificate + CertificateVerify.** The server sends its certificate chain, and signs a transcript of the handshake so far with the private key corresponding to the certificate's public key.
4. **Finished.** Both sides send a MAC over the entire handshake transcript, proving neither side's messages were tampered with. Application data flows, encrypted with keys derived from the shared secret.

**What the certificate actually proves — and what it doesn't.** A certificate binds a **hostname** to a **public key**, signed by a Certificate Authority the client already trusts (CA root certificates ship with your OS/browser). The client validates the chain up to a trusted root, checks the hostname matches, checks the validity dates, and checks revocation.

Crucially, step 3's signature is what makes the certificate meaningful. Anyone can copy a public certificate — it's public. What an attacker *cannot* do is produce a valid signature over the handshake transcript, because that requires the matching **private key**. So the certificate proves "whoever I'm talking to holds the private key that a trusted CA vouched belongs to `example.com`."

What it does **not** prove: that the site is honest, safe, or reputable. A phishing site can obtain a perfectly valid certificate for its own domain in minutes. The padlock means "encrypted and correctly identified", not "trustworthy".

**Two properties worth naming:**
- **Forward secrecy.** Because the session key comes from an ephemeral Diffie–Hellman exchange rather than being encrypted with the server's long-term key, recording today's traffic and stealing the server's private key next year does not decrypt it. TLS 1.3 makes this mandatory — older RSA key-transport suites, which lacked it, were removed.
- **Downgrade protection.** The Finished MAC covers the whole transcript, including the version and cipher negotiation, so an attacker cannot silently strip the negotiation down to a weak cipher without breaking the MAC.
