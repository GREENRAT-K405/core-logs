## DSA

### Question: Valid Palindrome (Strings — Easy)

**Problem Statement**

Given a string `s`, return `true` if it is a palindrome after converting all uppercase letters to lowercase and removing all non-alphanumeric characters, and `false` otherwise. An empty string counts as a palindrome.

**Input/Output Format**

- Input: a string `s` that may contain letters, digits, spaces, and punctuation.
- Output: a boolean (`true` or `false`).

**Examples**

1. Input: `"A man, a plan, a canal: Panama"` → Output: `true` (cleans to `"amanaplanacanalpanama"`)
2. Input: `"race a car"` → Output: `false` (cleans to `"raceacar"`)
3. Input: `" "` → Output: `true` (cleans to `""`)

**Constraints**

- `1 <= s.length <= 2 * 10^5`
- `s` consists of printable ASCII characters.
- Aim for O(n) time and O(1) extra space.

### Step-by-Step Walkthrough

**The obvious approach first.** Build a cleaned copy of the string — walk `s`, keep only alphanumeric characters, lowercase them — then compare that copy with its reverse. This is correct and easy to write, and it's O(n) time. But it allocates a second string of up to n characters, so it costs O(n) extra space. The constraint asks for O(1), so we can do better.

**Key insight.** We never actually needed the cleaned string as a *thing*. A palindrome check only ever compares one character from the front with one from the back. So instead of materializing the cleaned string, we can walk the original string from both ends at once and simply *skip over* the characters that cleaning would have removed.

That gives the two-pointer method:

1. Put `left` at index 0 and `right` at the last index.
2. While `left < right`:
   - Advance `left` rightward while it points at a non-alphanumeric character.
   - Move `right` leftward while it points at a non-alphanumeric character.
   - Now both pointers sit on characters that survive cleaning. Compare them case-insensitively. If they differ, the string is not a palindrome — return `false` immediately.
   - Otherwise step both pointers inward and continue.
3. If the loop finishes without a mismatch, every meaningful pair matched, so return `true`.

**Why it's correct.** After the skip loops, `left` and `right` point at the *i*-th character from the start and the *i*-th from the end of the cleaned string — exactly the pair a naive check would compare at that step. The pointers only ever move inward, so every such pair is examined exactly once, in order, until they meet. When they meet or cross, all pairs have matched.

**The one detail worth getting right.** The inner skip loops must also test `left < right`, not just the character class. Without that guard, a string of only punctuation (`",,,"`) would let `left` run past `right` and off the end of the string.

**Complexity.**
- Time: O(n) — each pointer only ever moves toward the other, so together they traverse the string at most once.
- Space: O(1) — two indices, no matter how long the input is.

### C++ Code

```cpp
#include <string>
#include <cctype>
using namespace std;

bool isPalindrome(const string& s) {
    int left = 0;
    int right = (int)s.size() - 1;

    while (left < right) {
        // Skip anything that cleaning would have stripped out.
        // The `left < right` guard stops the pointers crossing on
        // inputs that are entirely punctuation.
        while (left < right && !isalnum((unsigned char)s[left])) {
            left++;
        }
        while (left < right && !isalnum((unsigned char)s[right])) {
            right--;
        }

        // Both pointers now sit on characters that survive cleaning.
        if (tolower((unsigned char)s[left]) != tolower((unsigned char)s[right])) {
            return false;
        }

        left++;
        right--;
    }

    return true;
}
```

Note the `(unsigned char)` casts: `isalnum` and `tolower` take an `int` whose value must be representable as `unsigned char` (or be `EOF`). Passing a plain `char` that happens to be negative is undefined behaviour — a classic latent bug on inputs with bytes above 127.

## CS Fundamentals

### 1. OOP (Comparison)

**Question:** What is the difference between abstraction and encapsulation? They are often described as "hiding" — what exactly does each one hide, and why do both exist?

**Answer:**

Both are about hiding, but they hide *different things for different reasons*, which is why a language gives you separate tools for them.

**Encapsulation** hides *state*. It bundles data together with the methods that operate on that data, and restricts direct outside access to that data — typically via access modifiers (`private`, `protected`). The goal is **protecting invariants**. If a `BankAccount` exposes `balance` as a public field, any code anywhere can set it to `-5000`, and the class can no longer guarantee anything about itself. Make it private and force changes through `deposit()` and `withdraw()`, and the class can enforce "balance never goes negative" in exactly one place.

**Abstraction** hides *implementation*. It exposes a simplified, essential interface and suppresses the details of how the work is actually done — via abstract classes, interfaces, or just a well-chosen public API. The goal is **managing complexity and decoupling**. When you call `list.sort()`, you don't know or care whether it's merge sort or introsort; you're programming against the idea "this can be sorted," not against a particular algorithm.

The clearest way to hold them apart:

| | Encapsulation | Abstraction |
| --- | --- | --- |
| Hides | Internal data/state | Implementation details |
| Answers | "Who is allowed to touch this?" | "What does this thing do?" |
| Purpose | Protect invariants, control mutation | Reduce complexity, decouple callers |
| Typical tool | `private` fields + accessor methods | Interfaces, abstract base classes |

**How they relate:** encapsulation is largely a *mechanism*; abstraction is largely a *design outcome*. You commonly use encapsulation to achieve abstraction — making fields private is part of how you keep callers from depending on your internals. But they're independent: a class can be well-encapsulated (all fields private) yet a leaky abstraction (its public methods are named after implementation details like `rehashBuckets()`), and you can have a clean abstract interface whose implementing class carelessly exposes public mutable state.

### 2. Computer Networks (Scenario/Applied)

**Question:** You type `www.example.com` into a browser and press Enter. Walk through how the browser turns that name into an IP address it can actually connect to. Where can the answer come from, and what does each step cache?

**Answer:**

The name means nothing to the network — routing works on IP addresses — so the first job is **DNS resolution**. The lookup is answered by the first layer that already knows, and only falls through when nobody does:

1. **Browser cache.** Browsers keep their own short-lived DNS cache. A hit here ends the process with no network traffic at all.
2. **OS cache / hosts file.** The OS resolver checks its own cache, and consults `/etc/hosts` (or the Windows equivalent), which can override DNS entirely — this is why a stale hosts entry can make one machine behave differently from every other machine on the same network.
3. **Recursive resolver.** Otherwise the OS sends the query to a configured recursive resolver (your ISP's, or something like `8.8.8.8`), usually over UDP port 53. This resolver does the real work on the client's behalf, and has its own large cache.
4. **The authoritative hierarchy**, if the resolver has nothing cached. It walks down the tree:
   - a **root** server, which doesn't know `example.com` but knows who handles `.com`,
   - the **`.com` TLD** servers, which return the nameservers delegated for `example.com`,
   - the **authoritative nameserver** for `example.com`, which finally returns the actual `A` record (IPv4) or `AAAA` record (IPv6).
5. The resolver caches the answer for its **TTL** and returns it to the OS, which caches it and hands it to the browser.

Only now does the browser open a TCP connection to that IP (then a TLS handshake for HTTPS, then the HTTP request).

**Why the caching layers matter in practice:** TTL is the reason DNS changes aren't instant. When you repoint a domain to a new server, clients and resolvers that cached the old record keep using it until their TTL expires — which is exactly why the standard playbook before a migration is to *lower the TTL in advance*, so the cached copies are short-lived when the switch actually happens.

Two related details worth knowing: a **CNAME** record returns another *name* rather than an address, so the resolver has to resolve again (this is how most CDN setups work), and a single name commonly maps to **multiple A records**, which the resolver may return in rotating order — a crude but very widely used form of load distribution.

### 3. DBMS (Conceptual/Definition)

**Question:** What are the ACID properties of a database transaction? Explain what each one guarantees, and give a concrete example of what breaks without it.

**Answer:**

A **transaction** is a unit of work that must be treated as a single indivisible operation. ACID is the set of four guarantees a transactional database makes about it.

**A — Atomicity.** A transaction either happens completely or not at all; there is no partial application. If any statement fails, everything already done in that transaction is rolled back.
*Without it:* transferring ₹1000 between accounts debits the sender, then crashes before crediting the receiver. The money has simply vanished. Atomicity guarantees the debit is undone.

**C — Consistency.** A transaction moves the database from one valid state to another, respecting all defined rules — constraints, foreign keys, cascades, triggers. A transaction that would violate a constraint is rejected outright.
*Without it:* you could insert an `orders` row referencing a `customer_id` that doesn't exist, leaving orphaned rows that every later join silently mishandles.
(Note this is the property most dependent on *you*: the database enforces the constraints you declare. Business rules you never expressed as constraints aren't protected by consistency.)

**I — Isolation.** Concurrent transactions don't observe each other's uncommitted intermediate states. The result of running transactions concurrently should match some valid serial ordering of them.
*Without it:* two transactions both read `seats_available = 1`, both conclude a seat is free, and both book it. This is the classic lost-update / double-booking bug.

**D — Durability.** Once a transaction is committed, it survives crashes, power loss, and restarts. Typically implemented by writing changes to a **write-ahead log** on durable storage *before* acknowledging the commit, so the log can replay after a crash.
*Without it:* the database confirms your payment, the server loses power a second later, and the payment is gone despite the confirmation.

**The practical nuance:** atomicity, consistency, and durability are close to absolute in a real database, but **isolation is a dial, not a switch**. Full isolation (`SERIALIZABLE`) is expensive, so engines default to weaker levels — `READ COMMITTED` in PostgreSQL and Oracle, `REPEATABLE READ` in MySQL/InnoDB. Each weaker level permits specific anomalies (dirty reads, non-repeatable reads, phantom reads) in exchange for concurrency. So "my database is ACID" does *not* mean "I cannot have race conditions" — it means the tools to prevent them exist, and choosing the right isolation level (or explicit locking) is still your job.
