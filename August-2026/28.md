## DSA

### Question: Course Schedule (Graphs — Medium)

There are `numCourses` courses labeled `0` to `numCourses - 1`. You are given an array `prerequisites` where `prerequisites[i] = [a, b]` means you must take course `b` before course `a`.

Return `true` if it is possible to finish all courses, or `false` if there is no way to do so (i.e. the prerequisites form a cycle).

**Input format:**
- An integer `numCourses`.
- A 2D array `prerequisites`, where each entry `[a, b]` means "`b` is a prerequisite of `a`".

**Output format:**
- A boolean: `true` if all courses can be finished, `false` otherwise.

**Worked Examples:**

1. `numCourses = 2`, `prerequisites = [[1, 0]]` → `true` (take course 0, then course 1).
2. `numCourses = 2`, `prerequisites = [[1, 0], [0, 1]]` → `false` (course 0 needs course 1, and course 1 needs course 0 — a cycle, so neither can ever be taken first).
3. `numCourses = 4`, `prerequisites = [[1, 0], [2, 0], [3, 1], [3, 2]]` → `true` (a valid order is `0, 1, 2, 3` — or `0, 2, 1, 3`).

**Constraints:**
- `1 <= numCourses <= 10^5`
- `0 <= prerequisites.length <= 5000`
- `prerequisites[i].length == 2`
- `0 <= a, b < numCourses`
- All pairs `[a, b]` are distinct.

---

### Step-by-Step Walkthrough

**Approach — Topological Sort via Kahn's Algorithm (BFS)**

This problem is really asking: "does the directed graph of course dependencies contain a cycle?" If it's acyclic, a valid course order (a topological sort) exists and all courses can be finished; if there's a cycle, no course in the cycle can ever be scheduled first, so it's impossible.

Model the problem as a directed graph: for each pair `[a, b]`, draw an edge `b -> a` (take `b` before `a`). Then:

1. **Build the graph and in-degree count.** For every edge `b -> a`, add `a` to `b`'s adjacency list, and increment `indegree[a]` by 1 (the number of prerequisites `a` still has outstanding).
2. **Seed the queue.** Push every course whose `indegree` is `0` — these have no unmet prerequisites, so they can be taken immediately.
3. **Process in BFS order.** Repeatedly pop a course from the queue, mark it as "completed" (increment a `visited` counter), and for each course that depends on it, decrement that course's `indegree`. Whenever a course's `indegree` drops to `0`, it means all of its prerequisites are now satisfied, so push it onto the queue.
4. **Decide the answer.** If, at the end, `visited == numCourses`, every course was eventually reachable with all prerequisites satisfied — no cycle exists, so return `true`. If `visited < numCourses`, some courses were never freed up (they remain stuck waiting on each other in a cycle), so return `false`.

**Why it works:** A node can only enter the queue once all of its prerequisites have already been fully processed. If a genuine cycle exists among a set of courses, every course in that cycle permanently depends on another course in the same cycle, so none of their in-degrees can ever reach `0` — they simply never get pushed, and `visited` falls short of `numCourses`. This is exactly Kahn's algorithm for topological sorting, and its termination condition doubles as a cycle detector.

**Complexity Analysis:**
- **Time complexity:** `O(V + E)` where `V = numCourses` and `E = prerequisites.length` — building the adjacency list and in-degree array is `O(V + E)`, and each node/edge is processed exactly once during the BFS.
- **Space complexity:** `O(V + E)` for the adjacency list, in-degree array, and the queue.

### C++ Code

```cpp
#include <iostream>
#include <vector>
#include <queue>
using namespace std;

class Solution {
public:
    // Returns true if all numCourses can be completed given the prerequisites.
    bool canFinish(int numCourses, vector<vector<int>>& prerequisites) {
        vector<vector<int>> adj(numCourses);
        vector<int> indegree(numCourses, 0);

        // Build graph: edge b -> a for each [a, b] ("b before a").
        for (auto& p : prerequisites) {
            int a = p[0], b = p[1];
            adj[b].push_back(a);
            indegree[a]++;
        }

        // Seed the queue with every course that has no prerequisites.
        queue<int> q;
        for (int i = 0; i < numCourses; i++) {
            if (indegree[i] == 0) q.push(i);
        }

        int visited = 0;
        while (!q.empty()) {
            int course = q.front();
            q.pop();
            visited++;

            // Freeing up 'course' may satisfy the last prerequisite
            // of its dependents -- push them once their indegree hits 0.
            for (int next : adj[course]) {
                if (--indegree[next] == 0) {
                    q.push(next);
                }
            }
        }

        // If we visited every course, there was no cycle blocking any of them.
        return visited == numCourses;
    }
};

int main() {
    Solution sol;

    // Example 1
    vector<vector<int>> pre1 = {{1, 0}};
    cout << boolalpha << sol.canFinish(2, pre1) << " (expected true)" << endl;

    // Example 2
    vector<vector<int>> pre2 = {{1, 0}, {0, 1}};
    cout << boolalpha << sol.canFinish(2, pre2) << " (expected false)" << endl;

    // Example 3
    vector<vector<int>> pre3 = {{1, 0}, {2, 0}, {3, 1}, {3, 2}};
    cout << boolalpha << sol.canFinish(4, pre3) << " (expected true)" << endl;

    return 0;
}
```

**Trace against the examples:**
- `numCourses = 2`, `prerequisites = [[1, 0]]`: `adj[0] = [1]`, `indegree = [0, 1]`. Queue starts with `[0]`. Pop `0` → `visited = 1`, decrement `indegree[1]` to `0`, push `1`. Pop `1` → `visited = 2`. `visited == numCourses` → `true`. ✓
- `numCourses = 2`, `prerequisites = [[1, 0], [0, 1]]`: `adj[0] = [1]`, `adj[1] = [0]`, `indegree = [1, 1]`. No course starts at indegree `0`, so the queue is empty and `visited` stays `0`. `0 != 2` → `false`. ✓
- `numCourses = 4`, `prerequisites = [[1, 0], [2, 0], [3, 1], [3, 2]]`: `indegree = [0, 1, 1, 2]`. Queue starts with `[0]`. Pop `0` → `visited = 1`, decrement `1` and `2` to `0`, push both. Pop `1` → `visited = 2`, decrement `3` to `1` (not yet `0`). Pop `2` → `visited = 3`, decrement `3` to `0`, push it. Pop `3` → `visited = 4`. `4 == 4` → `true`. ✓

## CS Fundamentals

### 1. DBMS (Conceptual/Definition)

What is database normalization, and what specific anomalies does it prevent? Walk through 1NF, 2NF, and 3NF with a short example showing the kind of problem each one resolves.

**Answer:**

Normalization is the process of organizing a relational database's tables and columns to reduce data redundancy and prevent update anomalies, by progressively enforcing stricter design rules called **normal forms**.

Without normalization, a single flat table (e.g., `Orders(OrderID, CustomerName, CustomerAddress, ProductID, ProductName, Price, Quantity)`) can suffer from three classic anomalies:
- **Update anomaly:** if a customer's address changes, it has to be updated in every row containing an order from that customer — miss one row, and the data becomes inconsistent.
- **Insertion anomaly:** you can't record a new product until someone orders it, because `ProductName`/`Price` only exist attached to an `OrderID`.
- **Deletion anomaly:** deleting the last order for a customer accidentally erases their address entirely, since it wasn't stored anywhere else.

**1NF (First Normal Form):** Every column must hold a single, atomic value (no repeating groups or comma-separated lists in one cell), and each row must be uniquely identifiable (e.g., via a primary key).
*Fixes:* a table where one row stores `Products = "Pen, Notebook, Eraser"` in a single cell — you can't easily query "which orders contain a Notebook" without parsing a string. 1NF splits this into one row per product per order.

**2NF (Second Normal Form):** Must already be in 1NF, and every non-key column must depend on the **whole** primary key, not just part of it (this only matters for tables with a composite primary key).
*Fixes:* a table keyed on `(OrderID, ProductID)` that also stores `ProductName` — `ProductName` depends only on `ProductID`, not on the full `(OrderID, ProductID)` pair, so it's a **partial dependency**. 2NF moves `ProductName` into a separate `Products` table.

**3NF (Third Normal Form):** Must already be in 2NF, and no non-key column may depend on another non-key column (no **transitive dependencies**).
*Fixes:* an `Orders` table storing both `CustomerID` and `CustomerAddress` — `CustomerAddress` depends on `CustomerID`, not directly on `OrderID` (the primary key). 3NF moves customer details into their own `Customers` table, referenced by a foreign key.

**Why this matters:** normalization trades some query convenience (you now need `JOIN`s to reassemble the full picture) for correctness and maintainability — a value is stored in exactly one place, so it can only ever be updated in one place. In practice, real systems sometimes deliberately **denormalize** parts of a heavily-read schema afterward for performance, but that's a conscious tradeoff made on top of an already-normalized design, not a substitute for understanding it.

### 2. OOP (Comparison)

Compare composition and inheritance as two ways to reuse code between classes. What is the "diamond problem," and why do many modern languages/style guides favor "composition over inheritance"?

**Answer:**

| Aspect | Inheritance ("is-a") | Composition ("has-a") |
|---|---|---|
| Relationship | A subclass **is a** specialized version of its base class (`Car` is a `Vehicle`). | An object **contains** another object it delegates work to (`Car` has an `Engine`). |
| Coupling | Tight — the subclass is bound to the base class's implementation details; changes to the base class can silently break subclasses ("fragile base class" problem). | Loose — the containing class only depends on the contained object's interface, which can be swapped out (e.g., a different `Engine` implementation) without touching the containing class. |
| Flexibility | Fixed at compile time — a class can't easily change its parent at runtime. | Flexible — the composed object can be injected, replaced, or reconfigured at runtime (e.g., dependency injection). |
| Multiple reuse | Multiple inheritance (inheriting from more than one class) is allowed in some languages (C++) but not others (Java, C#), because of ambiguity problems. | An object can freely compose as many other objects as needed with no such restriction. |

**The diamond problem:** occurs with multiple inheritance when class `D` inherits from both `B` and `C`, and both `B` and `C` inherit from a common base class `A`. If `A` has a method or field, `D` ends up with two separate paths to it, causing ambiguity — which copy does `D` actually get, and which version of an overridden method should run? C++ allows multiple inheritance and has to resolve this explicitly (e.g., via `virtual` inheritance, so `A` is only included once); Java and C# sidestep the issue entirely by disallowing multiple inheritance of classes, permitting only single inheritance plus multiple **interfaces** (which don't carry field state, only method contracts).

**Why "composition over inheritance":** inheritance hierarchies tend to become rigid and awkward as requirements evolve — forcing a strict "is-a" taxonomy onto behavior that's really more of a "has this capability" relationship. For instance, if `FlyingBird` and `SwimmingBird` are both subclasses of `Bird`, where does a `Duck` (which does both) go, and what about a `Penguin` (which swims but doesn't fly)? Composition solves this cleanly: give `Bird` a `flyBehavior` and a `swimBehavior` object, and configure each concrete bird with whichever behaviors apply — no combinatorial explosion of subclasses, and behaviors can even be swapped at runtime. This is why many modern style guides (e.g., Effective Java's "favor composition over inheritance") recommend defaulting to composition and reaching for inheritance only when a true, stable "is-a" relationship exists and the base class was explicitly designed to be extended.

### 3. System Design (Scenario/Applied)

You're designing a URL-shortening service (like bit.ly) that must handle roughly 100 million new short links created per day, with about 10x that many redirect (read) requests. Walk through your high-level design: how you'd generate short IDs, how you'd store the mapping, and how you'd keep redirects fast at that read volume.

**Answer:**

**Step 1 — Clarify the core operation.** Two endpoints: `POST /shorten` (takes a long URL, returns a short code) and `GET /{shortCode}` (redirects to the original URL). At 100M writes/day (~1,150 writes/sec average, higher at peak) and ~10x reads (~11,500 reads/sec average), this is an extremely **read-heavy** workload, so the design should optimize aggressively for fast reads.

**Step 2 — Short ID generation.** Two common approaches:
- **Base62 encoding of an auto-incrementing counter:** maintain a global counter (e.g., via a dedicated ID-generation service, or a database sequence), and encode each new integer ID in base62 (`[a-zA-Z0-9]`) to produce a compact code like `aZ3kP1`. Simple, guarantees uniqueness with no collision checks needed, and a 7-character base62 code already covers `62^7 ≈ 3.5 trillion` possible codes — far more than needed.
- **Hash-based (e.g., MD5/SHA-256 of the long URL, truncated):** deterministic (the same URL always maps to the same code), but requires collision handling (two different URLs producing the same truncated hash) and doesn't naturally support wanting *different* short codes for the same URL requested by different users.

I'd pick the **counter + base62** approach for guaranteed uniqueness and simplicity, using a distributed ID generator (e.g., pre-allocating blocks of IDs to each application server, so servers don't need to coordinate on every single request — similar to how Twitter's Snowflake or a database's `AUTO_INCREMENT` with reserved ranges works).

**Step 3 — Storage.** Store the mapping `shortCode -> longURL` (plus metadata like creation time and optional expiry) in a key-value or simple relational store. Given the access pattern is a pure key lookup with no complex queries or relationships, a **key-value store** (e.g., DynamoDB, Cassandra) fits well and scales horizontally by partitioning on `shortCode`.

**Step 4 — Make reads fast.** This is the crux of the design given the read-heavy ratio:
- Put a **cache** (e.g., Redis) in front of the database, keyed by `shortCode -> longURL`. Since short-link access tends to follow a power-law distribution (a small fraction of links get most of the traffic), a cache with a reasonable eviction policy (LRU) will absorb the large majority of read traffic, leaving only cold/rare links to hit the database.
- Serve the redirect as an **HTTP 301 (permanent redirect)** where appropriate, which lets browsers cache the redirect themselves after the first visit, further reducing repeat load on the service — though a 302 might be preferred instead if you need to keep counting each click for analytics.
- Scale the read path horizontally: stateless application servers behind a load balancer, each capable of hitting the cache/database, so read capacity scales by adding more instances.

**Step 5 — Handle scale/failure considerations.** Partition the key-value store by `shortCode` (or by ID ranges, matching how codes were generated) to distribute load; replicate for availability; and consider a CDN or edge cache for redirect responses if latency to a global user base matters.

**Why this matters:** this scenario tests the ability to reason about read/write asymmetry (design for the dominant access pattern), pick an ID strategy that avoids coordination bottlenecks, and layer caching correctly — all recurring themes across many real-world system design problems (not just URL shorteners).
