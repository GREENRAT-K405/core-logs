## DSA

### Question: Two Sum (Hashing/Maps — Easy)

Given an array of integers `nums` and an integer `target`, return the indices of the two numbers such that they add up to `target`.

You may assume that each input has **exactly one solution**, and you may not use the same element twice. You can return the answer in any order.

**Input format:**
- An array of integers `nums`.
- An integer `target`.

**Output format:**
- A pair (or array) of two indices `[i, j]` such that `nums[i] + nums[j] == target`.

**Worked Examples:**

1. `nums = [2, 7, 11, 15]`, `target = 9` → `[0, 1]` (because `nums[0] + nums[1] == 2 + 7 == 9`)
2. `nums = [3, 2, 4]`, `target = 6` → `[1, 2]` (because `nums[1] + nums[2] == 2 + 4 == 6`)
3. `nums = [3, 3]`, `target = 6` → `[0, 1]` (two distinct elements with the same value can still be a valid pair, since they occupy different indices)

**Constraints:**
- `2 <= nums.length <= 10^4`
- `-10^9 <= nums[i] <= 10^9`
- `-10^9 <= target <= 10^9`
- Exactly one valid answer exists.
- The same element may not be used twice (but the same *value* at two different indices is fine).

---

### Step-by-Step Walkthrough

**Approach — Single-pass hash map**

The brute-force approach checks every pair `(i, j)` with nested loops, which is `O(n^2)` — for each `nums[i]`, scan the rest of the array for a `nums[j]` such that `nums[i] + nums[j] == target`. This works but is wasteful because we repeatedly re-scan the array from scratch.

The key insight: for a fixed `nums[i]`, the value we need to find is exactly `target - nums[i]` (the "complement"). Instead of searching for it linearly, we can look it up in `O(1)` average time using a hash map, if we've already recorded which values we've seen and at what index.

Algorithm:
1. Create an empty hash map `seen` that maps `value -> index`.
2. Iterate through `nums` with index `i`:
   - Compute `complement = target - nums[i]`.
   - If `complement` already exists as a key in `seen`, we've found our pair: return `[seen[complement], i]`.
   - Otherwise, insert `nums[i] -> i` into `seen` and continue.
3. Because the problem guarantees exactly one solution, we're guaranteed to return before the loop ends.

**Why it works:** By the time we reach index `i`, `seen` contains every index `j < i` we've already visited. If the required partner for `nums[i]` was any earlier element, it's already in the map, so the lookup succeeds. This only needs a **single pass** because every pair `(j, i)` with `j < i` is checked exactly once, from the "later" index's perspective, which is sufficient to cover all unordered pairs in the array.

**Complexity Analysis:**
- **Time complexity:** `O(n)` — one pass through the array, and each hash map insert/lookup is `O(1)` on average.
- **Space complexity:** `O(n)` — in the worst case (no match until the very last element), the map holds up to `n - 1` entries.

---

### C++ Code

```cpp
#include <iostream>
#include <vector>
#include <unordered_map>
using namespace std;

class Solution {
public:
    // Returns the indices of the two numbers in nums that add up to target.
    vector<int> twoSum(vector<int>& nums, int target) {
        unordered_map<int, int> seen; // value -> index

        for (int i = 0; i < (int)nums.size(); i++) {
            int complement = target - nums[i];

            // If we've already seen the number that completes the pair,
            // we're done -- return both indices immediately.
            auto it = seen.find(complement);
            if (it != seen.end()) {
                return {it->second, i};
            }

            // Otherwise, record this value's index for future lookups.
            seen[nums[i]] = i;
        }

        // Problem guarantees a solution exists, so this line is unreachable
        // for valid inputs; returned only to satisfy the compiler.
        return {};
    }
};

int main() {
    Solution sol;

    // Example 1
    vector<int> nums1 = {2, 7, 11, 15};
    vector<int> res1 = sol.twoSum(nums1, 9);
    cout << "[" << res1[0] << ", " << res1[1] << "] (expected [0, 1])" << endl;

    // Example 2
    vector<int> nums2 = {3, 2, 4};
    vector<int> res2 = sol.twoSum(nums2, 6);
    cout << "[" << res2[0] << ", " << res2[1] << "] (expected [1, 2])" << endl;

    // Example 3
    vector<int> nums3 = {3, 3};
    vector<int> res3 = sol.twoSum(nums3, 6);
    cout << "[" << res3[0] << ", " << res3[1] << "] (expected [0, 1])" << endl;

    return 0;
}
```

**Trace against the examples:**
- `nums = [2, 7, 11, 15]`, `target = 9`: at `i=0`, complement is `7`, not seen yet, insert `2 -> 0`. At `i=1`, complement is `9 - 7 = 2`, which **is** in `seen` (at index 0) → return `[0, 1]`. ✓
- `nums = [3, 2, 4]`, `target = 6`: at `i=0`, complement `3`, not seen, insert `3 -> 0`. At `i=1`, complement `4`, not seen, insert `2 -> 1`. At `i=2`, complement `6 - 4 = 2`, which **is** in `seen` (at index 1) → return `[1, 2]`. ✓
- `nums = [3, 3]`, `target = 6`: at `i=0`, complement `3`, not seen, insert `3 -> 0`. At `i=1`, complement `6 - 3 = 3`, which **is** in `seen` (at index 0, a *different* index than the current one) → return `[0, 1]`. ✓

## CS Fundamentals

### 1. Computer Architecture (Conceptual/Definition)

What is cache memory, and why does a CPU typically have multiple cache levels (L1, L2, L3)? Explain the principle of locality of reference that makes caching effective in the first place, and describe what happens on a cache miss.

**Answer:**

Cache memory is a small amount of very fast SRAM (static RAM) sitting between the CPU core and main memory (DRAM). It exists purely to bridge a huge speed gap: a modern CPU can execute an instruction in under a nanosecond, while a round trip to main memory can take on the order of 100 nanoseconds. Without caching, the CPU would spend almost all of its time stalled waiting on memory.

Caching only works because of **locality of reference**, which comes in two forms:
- **Temporal locality:** if a memory location was accessed recently, it's likely to be accessed again soon (e.g., a loop counter, or a variable reused across iterations).
- **Spatial locality:** if a memory location was accessed, nearby locations are likely to be accessed soon too (e.g., iterating over an array). This is why caches fetch data in fixed-size blocks called **cache lines** (typically 64 bytes), not single bytes — pulling in the whole line front-loads the neighboring data that's likely to be needed next.

CPUs use a **multi-level hierarchy** rather than one big cache because there's a direct tradeoff between a cache's size and its speed/cost: a cache small enough to be extremely fast (a handful of cycles) can only hold a few tens of kilobytes, while a cache large enough to hold a few megabytes is inherently slower to search and more expensive to build.
- **L1** — smallest (tens of KB), fastest (~1-4 cycles), private per core, often split into separate instruction and data caches.
- **L2** — larger (hundreds of KB to a few MB), a bit slower (~10 cycles), usually private per core.
- **L3** — largest (several MB to tens of MB), slowest of the three (~30-50 cycles), but still far faster than DRAM, and typically **shared across all cores** on the chip (useful for data shared between cores).

**Cache miss:** when the CPU requests an address not currently held in a given cache level, that's a miss, and the request falls through to the next level (L1 → L2 → L3 → main memory), incurring progressively higher latency at each step. Misses are commonly classified as:
- **Compulsory** — the very first access to a block that's never been cached before (unavoidable).
- **Capacity** — the cache is too small to hold the entire working set, so useful blocks get evicted and later re-requested.
- **Conflict** — in caches that aren't fully associative, multiple addresses map to the same cache line/set and evict each other even though the cache overall isn't full.

**Why this matters:** understanding cache behavior explains real, measurable performance effects — e.g., why iterating a 2D array in row-major order can be several times faster than column-major order (spatial locality), or why a "smaller, simpler" data structure sometimes outperforms an asymptotically better one purely because it fits in cache.

### 2. Computer Networks (Comparison)

Compare TCP and UDP. What guarantees does TCP provide that UDP does not, and why would an application like video calling deliberately choose UDP despite giving up those guarantees?

**Answer:**

| Aspect | TCP | UDP |
|---|---|---|
| Connection | Connection-oriented — requires a handshake (SYN, SYN-ACK, ACK) before data flows. | Connectionless — a sender just fires packets ("datagrams") with no setup. |
| Reliability | Guaranteed delivery: lost packets are detected (via sequence numbers/ACKs) and retransmitted. | No delivery guarantee — a dropped packet is simply gone. |
| Ordering | Guarantees in-order delivery to the receiving application, buffering/reordering packets that arrive out of sequence. | No ordering guarantee — packets can arrive in any order, and the application must handle that itself if it cares. |
| Flow/Congestion control | Built in — dynamically adjusts sending rate based on receiver buffer space and detected network congestion (e.g., via the congestion window). | None — the sender pushes data at whatever rate the application requests. |
| Overhead | Larger header (20+ bytes), plus the cost of handshakes, ACKs, and retransmission logic. | Minimal header (8 bytes), no handshake, no retransmission bookkeeping. |
| Typical use cases | Web browsing (HTTP/HTTPS), file transfer, email — anything where correctness of every byte matters more than raw latency. | DNS lookups, live video/audio calls, online gaming, streaming — anything where low latency matters more than perfect delivery. |

**Why an app like video calling chooses UDP:** TCP's reliability comes at a direct cost to latency and timeliness. If a packet is lost, TCP will pause delivery of everything *after* it to the application until the lost packet is retransmitted and received — this is called **head-of-line blocking**. For a live video/voice call, a frame or audio sample that arrives 300ms late (because TCP is busy retransmitting an old, now-useless packet) is worse than useless — the moment has already passed, and the call would rather skip that frame and move on to the current one, producing a brief glitch instead of a growing lag. UDP lets the application (or a protocol built on top of it, like RTP/WebRTC) make that tradeoff explicitly: send continuously, tolerate occasional loss, and never block waiting for a retransmission that would arrive too late to be useful anyway.

**Why this matters:** this comparison is really about a fundamental systems tradeoff — reliability/ordering vs. latency — that shows up far beyond networking (e.g., "at-least-once" vs. "at-most-once" delivery semantics in distributed messaging systems). Picking the right one depends entirely on which failure mode the application can tolerate.

### 3. Operating Systems (Scenario/Applied)

Two processes deadlock: Process A holds Resource 1 and is waiting for Resource 2; Process B holds Resource 2 and is waiting for Resource 1. Neither can proceed. What are the four necessary conditions for a deadlock like this to occur, and name two practical strategies used in production systems to prevent it?

**Answer:**

For a deadlock to occur, all four of the following conditions (known as the **Coffman conditions**) must hold **simultaneously**. Breaking any single one is enough to make deadlock impossible.

1. **Mutual exclusion** — at least one resource is held in a non-shareable mode (only one process can use it at a time). In the example, Resource 1 and Resource 2 are each exclusively held.
2. **Hold and wait** — a process is holding at least one resource while simultaneously waiting to acquire additional resources held by others. Process A holds Resource 1 *and* waits for Resource 2 at the same time, rather than releasing Resource 1 first.
3. **No preemption** — resources cannot be forcibly taken away from a process; they can only be released voluntarily by the process holding them. The OS can't just grab Resource 1 back from Process A to hand to Process B.
4. **Circular wait** — there's a cycle of processes, each waiting for a resource held by the next one in the cycle. Here: A waits on B (for Resource 2), and B waits on A (for Resource 1) — a cycle of length two.

**Two practical prevention strategies:**

1. **Lock/resource ordering (breaks circular wait):** impose a fixed global order on all lockable resources (e.g., always acquire Resource 1 before Resource 2, system-wide, regardless of which process or which order the logic would "naturally" want them in). If every process is required to acquire resources in that same order, a cycle can never form — some process in any potential cycle would have had to acquire a "later" resource before an "earlier" one, which the ordering rule forbids. This is the standard fix for multi-lock deadlocks in real codebases.

2. **Timeout with back-off and retry (breaks hold-and-wait, in effect):** instead of blocking indefinitely while holding a resource and waiting for another, a process attempts to acquire the second resource with a timeout (e.g., `try_lock` with a deadline). If it fails, it releases everything it's currently holding, waits a randomized backoff interval, and retries the entire acquisition from scratch. This guarantees no process can indefinitely hold one resource while blocking forever on another, which breaks the condition that makes deadlock possible.

(Other valid approaches include preemption — allowing the OS/runtime to forcibly reclaim a resource and roll back the process holding it — and deadlock avoidance algorithms like the **Banker's algorithm**, which only grants a resource request if doing so keeps the system in a "safe state" where all processes can still eventually complete.)

**Why this matters:** deadlock isn't just an OS-textbook concept — it's a real, recurring bug class in any system with multiple locks (databases doing row-level locking, multi-threaded applications, distributed systems acquiring locks across services). Lock ordering in particular is one of the most common real-world deadlock-prevention conventions, and violating it is one of the most common root causes of production deadlocks.
