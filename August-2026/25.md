## DSA

### Question: Valid Parentheses (Stacks/Queues — Easy)

**Problem Statement**

Given a string `s` containing only the characters `(`, `)`, `{`, `}`, `[` and `]`, determine whether the string is valid. A string is valid when every open bracket is closed by a bracket of the **same type**, brackets are closed in the **correct order**, and every closing bracket has a matching open bracket.

**Input/Output Format**

- Input: a string `s` of bracket characters.
- Output: a boolean (`true` or `false`).

**Examples**

1. Input: `"()[]{}"` → Output: `true`
2. Input: `"([)]"` → Output: `false` (correct types, wrong order)
3. Input: `"{[]}"` → Output: `true` (properly nested)

**Constraints**

- `1 <= s.length <= 10^4`
- `s` consists only of the six bracket characters listed above.

### Step-by-Step Walkthrough

**Spotting the structure.** A tempting first idea is to just count brackets — if the number of `(` equals the number of `)`, surely it's balanced? Example 2 kills that immediately: `"([)]"` has perfectly matched counts of every type and is still invalid. Counting throws away the information that actually matters, which is **order**.

**Key insight.** Look at what "correctly nested" really means: when a closing bracket appears, it must match the **most recently opened bracket that is still unclosed**. That phrase — *most recent, still outstanding* — is the definition of last-in-first-out. So the data structure picks itself: a **stack**.

The algorithm follows directly:

1. Walk the string one character at a time.
2. If the character is an **opening** bracket, push it. We don't yet know what will close it, so we record that it's outstanding.
3. If the character is a **closing** bracket, it must be matched right now by the top of the stack:
   - If the stack is **empty**, there is no outstanding open bracket for it — invalid (e.g. `")("`).
   - If the top is an opening bracket of a **different type**, the nesting is crossed — invalid (this is what catches `"([)]"`).
   - Otherwise it matches: pop the top and continue.
4. After the whole string, the stack must be **empty**. Anything left is an open bracket that was never closed (e.g. `"(("`).

**Walking example 2 to see it fail.** For `"([)]"`: push `(`, push `[`, then hit `)`. The top of the stack is `[`, which is not the partner of `)`, so we return `false` right there — exactly the crossed nesting a counting approach missed.

**Why the final emptiness check is not optional.** Every step above only rejects *closing* brackets that go wrong. A string like `"([{"` never triggers any of those checks — it just pushes three times and ends. Without step 4 it would be wrongly accepted.

**Complexity.**
- Time: O(n) — one pass, and each character is pushed and popped at most once.
- Space: O(n) — worst case is a fully nested string like `"((((("`, where every character sits on the stack at once.

### C++ Code

```cpp
#include <string>
#include <stack>
#include <unordered_map>
using namespace std;

bool isValid(const string& s) {
    // Maps each closing bracket to the opening bracket it must match.
    const unordered_map<char, char> partner{
        {')', '('},
        {']', '['},
        {'}', '{'},
    };

    stack<char> open;

    for (char c : s) {
        auto it = partner.find(c);

        if (it == partner.end()) {
            // Not a closing bracket, so it's an opening one: record it
            // as outstanding.
            open.push(c);
            continue;
        }

        // A closing bracket must be matched by the most recent
        // still-unclosed opening bracket.
        if (open.empty() || open.top() != it->second) {
            return false;
        }
        open.pop();
    }

    // Anything still outstanding was opened and never closed.
    return open.empty();
}
```

## CS Fundamentals

### 1. Operating Systems (Conceptual/Definition)

**Question:** What is virtual memory, and what happens on a page fault? What is thrashing, and why does adding more processes sometimes make total system throughput collapse rather than merely slow down?

**Answer:**

**Virtual memory** is the abstraction that gives every process its own private, contiguous address space, decoupled from actual physical RAM. The process works with *virtual addresses*; the MMU translates them to *physical addresses* using per-process **page tables**, with the **TLB** caching recent translations. Memory is managed in fixed-size **pages** (commonly 4 KB), and only the pages a process is actively using need to be resident in RAM — the rest can live on disk in a swap area or backing file.

This buys three things at once: **isolation** (a process cannot name, let alone touch, another's memory), **the illusion of more memory than physically exists**, and **freedom from contiguity** (a process's pages can sit anywhere in physical RAM, so there's no external fragmentation problem to solve).

**A page fault** is what happens when a process touches a virtual address whose page isn't currently in RAM. The MMU raises a trap, and the OS takes over:

1. Verify the access is legal (a reference to an unmapped or protection-violating address isn't a recoverable fault — that's a segmentation fault).
2. Find a free physical frame. If none is free, choose a **victim** page to evict using a replacement policy (LRU approximations like the clock algorithm are typical).
3. If the victim is **dirty** (modified since being loaded), write it out to disk first.
4. Read the needed page in from disk, update the page table and TLB.
5. Restart the faulting instruction — which now succeeds.

The critical fact is the cost asymmetry: a RAM access is tens of nanoseconds; a fault that touches disk is milliseconds. That's a gap of roughly **10⁵–10⁶×**. Even a very low fault rate dominates average access time.

**Thrashing** is what happens when the sum of the processes' active working sets exceeds physical memory. Each process is now faulting constantly, and — critically — the pages being evicted are pages some *other* process is about to need. Every process spends its time waiting on disk rather than computing.

**Why throughput collapses rather than degrades gracefully:** this is a feedback loop, and historically the OS made it worse. The CPU sits idle because everyone is blocked on I/O. A scheduler that reads "low CPU utilization" as "I have spare capacity" responds by admitting *more* processes — which increases total working-set demand, which increases faulting, which drops CPU utilization further. The system spirals down. This is why modern kernels track working-set size and use **admission control / load shedding** (and why Linux's OOM killer exists) rather than naively treating idle CPU as an invitation to add load.

### 2. System Design (Comparison)

**Question:** Compare write-through, write-back, and cache-aside caching strategies. What does each guarantee about consistency and durability, and when would you pick each?

**Answer:**

All three sit between your application and a slower store (usually a database), but they differ in **who writes, when, and in what order** — which determines exactly what you lose when something crashes.

**Write-through.** Every write goes to the cache *and* the database synchronously, and only then is the write acknowledged.
- **Consistency:** cache and DB never disagree.
- **Durability:** full — the DB has the data before the client is told "done".
- **Cost:** every write pays the DB's latency; the cache gives you nothing on the write path.
- **Use when:** reads dominate writes and you can't tolerate stale or lost data. Also pairs badly with write-heavy workloads that rarely re-read — you fill the cache with entries nobody asks for.

**Write-back (write-behind).** Writes go to the cache only, acknowledged immediately, and are flushed to the database asynchronously — batched, or after a delay.
- **Consistency:** the cache is ahead of the DB for a window; anything reading the DB directly sees stale data.
- **Durability:** **this is the one that can lose committed writes.** If the cache node dies before flushing, acknowledged data is gone.
- **Cost:** by far the fastest writes, and it absorbs bursts and coalesces repeated writes to the same key into one DB write.
- **Use when:** write volume is high and some loss is genuinely acceptable — view counts, metrics, presence/"last seen", analytics events. Not for payments.

**Cache-aside (lazy loading).** The application owns the cache explicitly. On read: check cache; on miss, read the DB, populate the cache, return. On write: write the DB, then **invalidate** (or update) the cache entry.
- **Consistency:** eventually consistent, with a real race window (see below).
- **Durability:** full — the DB is always the source of truth.
- **Cost:** every miss costs an extra round trip, and the first read of any key is always a miss.
- **Use when:** this is the sensible default for most read-heavy web applications, and it's what Redis/Memcached in front of a relational DB usually means. Its big practical advantage is that the cache can go down entirely and the system still works, just slower.

| | Write-through | Write-back | Cache-aside |
| --- | --- | --- | --- |
| Write latency | Slow (DB-bound) | Fast | DB-bound |
| Can lose acked writes | No | **Yes** | No |
| Cache down ⇒ | Writes fail | Data loss risk | Degraded, still correct |
| Typical use | Read-heavy, correctness-critical | Counters, metrics | General web caching |

**The trap to know:** cache-aside's classic race is *invalidate-then-repopulate*. Reader A misses and reads value `v1` from the DB. Writer B updates the DB to `v2` and invalidates the (already empty) cache. Reader A then writes its stale `v1` into the cache — where it now sits indefinitely. Mitigations are to **delete rather than update** on write, set a TTL as a backstop so any inconsistency self-heals, or use versioned/compare-and-set writes.

### 3. Computer Architecture (Conceptual/Applied)

**Question:** What is instruction pipelining, and what are pipeline hazards? Why can an unpredictable `if` inside a hot loop be dramatically slower than a predictable one, even when both execute the same number of instructions?

**Answer:**

**Pipelining** overlaps the execution of instructions the way an assembly line overlaps building cars. A classic 5-stage RISC pipeline splits each instruction into Fetch, Decode, Execute, Memory, Write-back. Rather than finishing one instruction before starting the next, the CPU keeps five instructions in flight, each in a different stage. Latency per instruction is unchanged, but **throughput** approaches one instruction per cycle instead of one per five. Real cores go much further — deeper pipelines (15–20+ stages) and superscalar issue of several instructions per cycle.

This only works if the pipeline stays full. **Hazards** are the situations that stall it:

- **Structural hazards** — two instructions need the same hardware unit in the same cycle. Solved by duplicating units or separating instruction and data caches.
- **Data hazards** — an instruction needs a result that an earlier, still-in-flight instruction hasn't produced yet. Largely solved by **forwarding/bypassing** (routing the result straight from one stage to another rather than waiting for write-back), with a stall only when unavoidable, as after a load.
- **Control hazards** — a branch. The CPU doesn't know which instruction to fetch next until the branch condition resolves, several stages later.

Control hazards are the expensive ones, and the fix is **speculation**: the branch predictor guesses the outcome and the CPU speculatively fetches and executes down the predicted path. A correct guess costs essentially nothing. A **misprediction** means every speculatively executed instruction must be discarded and the pipeline refilled from the correct target — a penalty of roughly **15–20 cycles** on a modern core.

**Which is exactly why branch predictability dominates branch count.** Consider summing only the elements above a threshold in a large array:

- If the array is **sorted**, the branch is taken for a long run and then not taken for a long run. The predictor learns this almost immediately and is right ~100% of the time. Near-zero misprediction cost.
- If the array is **randomly ordered**, the branch is a coin flip. No predictor can beat ~50%, so roughly *half* of all iterations pay the full flush penalty.

Same instruction count, same memory access pattern, same total work — and the random version can run **several times slower**. This is the single most famous demonstration of why "count the operations" is an inadequate performance model for modern CPUs.

**What to do about it:** make the branch predictable (sorting first can pay for itself), or **remove the branch entirely** — replace it with branchless arithmetic, a conditional-move (`cmov`), or a bitmask, so there's nothing to mispredict. This is also why `std::sort` uses insertion sort for small partitions, why binary search can lose to linear scan on small arrays, and why data-oriented design favours layouts that let you process elements uniformly.
