## DSA

### Question: Container With Most Water (Arrays — Medium)

You are given an integer array `height` of length `n`, where `height[i]` represents the height of a vertical line drawn at position `i` on the x-axis. Two lines, together with the x-axis, form a container. Find two lines that, together with the x-axis, form a container that holds the **most water**, and return the maximum amount of water it can store.

Note: the container cannot be slanted — the amount of water held is determined by the **shorter** of the two chosen lines, times the horizontal distance between them.

**Input format:**
- An integer array `height` of length `n`.

**Output format:**
- An integer: the maximum area of water that can be contained.

**Worked Examples:**

1. `height = [1, 8, 6, 2, 5, 4, 8, 3, 7]` → `49` (lines at index 1, value 8, and index 8, value 7: `min(8, 7) * (8 - 1) = 7 * 7 = 49`).
2. `height = [1, 1]` → `1` (only one pair possible: `min(1, 1) * (1 - 0) = 1`).
3. `height = [4, 3, 2, 1, 4]` → `16` (lines at index 0 and index 4, both height 4: `min(4, 4) * (4 - 0) = 16`).

**Constraints:**
- `2 <= n <= 10^5`
- `0 <= height[i] <= 10^4`

---

### Step-by-Step Walkthrough

**Approach — Two Pointers**

The brute-force approach checks every pair `(i, j)` and computes `min(height[i], height[j]) * (j - i)`, which is `O(n^2)` and too slow for `n` up to `10^5`. To get to `O(n)`, notice a key property: for a fixed pair of lines, the area is capped by the **shorter** line, no matter how tall the other one is.

Start with the widest possible container: two pointers, `left` at index `0` and `right` at index `n - 1`. This gives the maximum possible width, so the only way to ever increase the area from here is if a later pair has enough extra height to compensate for a smaller width.

1. **Initialize** `left = 0`, `right = n - 1`, `best = 0`.
2. **Loop while `left < right`:**
   - Compute the current area: `min(height[left], height[right]) * (right - left)`. Update `best` if this is larger.
   - **Move the pointer at the shorter line inward.** This is the crux of the algorithm: if `height[left] < height[right]`, the current area is bottlenecked by `height[left]`. Keeping `right` fixed and moving `left` inward can only ever produce a width that's smaller-or-equal *and* a limiting height that's smaller-or-equal-or-possibly-larger — but crucially, moving `right` inward instead would strictly decrease width while the limiting height (still `height[left]`, since `right` was already larger) stays the same or gets worse. So moving the shorter side is the only choice that could possibly find a *larger* area; moving the taller side can never help, because width only shrinks and the bottleneck was already the other side.
   - Symmetric case if `height[right] <= height[left]`: move `right` inward.
3. **Return `best`** once `left` meets `right`.

**Why it works:** at every step we discard exactly one line — the shorter one at the current boundary — from ever being paired with anything better than what we've already tried with it, because pairing it with any line strictly between `left` and `right` would only reduce the width without possibly raising the limiting height above the discarded line's own height (since the other boundary at that moment is already `>=` the discarded line). This lets us safely shrink the search space by one index per iteration without missing the true optimum, giving a full scan in linear time.

**Complexity Analysis:**
- **Time complexity:** `O(n)` — each of the two pointers moves inward at most `n` times total, so the loop runs at most `n` iterations.
- **Space complexity:** `O(1)` — only a constant number of extra variables are used.

---

### C++ Code

```cpp
#include <iostream>
#include <vector>
#include <algorithm>
using namespace std;

class Solution {
public:
    // Returns the maximum water area formed by any two lines in height.
    int maxArea(vector<int>& height) {
        int left = 0;
        int right = static_cast<int>(height.size()) - 1;
        int best = 0;

        while (left < right) {
            int width = right - left;
            int limitingHeight = min(height[left], height[right]);
            best = max(best, limitingHeight * width);

            // Always move the pointer at the shorter line inward --
            // moving the taller one can never yield a larger area.
            if (height[left] < height[right]) {
                left++;
            } else {
                right--;
            }
        }

        return best;
    }
};

int main() {
    Solution sol;

    // Example 1
    vector<int> h1 = {1, 8, 6, 2, 5, 4, 8, 3, 7};
    cout << sol.maxArea(h1) << " (expected 49)" << endl;

    // Example 2
    vector<int> h2 = {1, 1};
    cout << sol.maxArea(h2) << " (expected 1)" << endl;

    // Example 3
    vector<int> h3 = {4, 3, 2, 1, 4};
    cout << sol.maxArea(h3) << " (expected 16)" << endl;

    return 0;
}
```

**Trace against the examples:**
- `height = [1, 8, 6, 2, 5, 4, 8, 3, 7]`: `left=0,right=8`: area `min(1,7)*8=8`, best=8; `height[0]=1<7` so `left++`. `left=1,right=8`: area `min(8,7)*7=49`, best=49; `height[1]=8>=7` so `right--`. Continuing the scan never beats 49 (later widths shrink faster than the height ceiling of 8 can compensate). Final: `49`. ✓
- `height = [1, 1]`: `left=0,right=1`: area `min(1,1)*1=1`, best=1; pointers meet. Final: `1`. ✓
- `height = [4, 3, 2, 1, 4]`: `left=0,right=4`: area `min(4,4)*4=16`, best=16; equal heights so `right--`. `left=0,right=3`: area `min(4,1)*3=3`, best stays 16; `height[0]=4>=1` so `right--`. Remaining pairs only shrink width further with no taller line available. Final: `16`. ✓

## CS Fundamentals

### 1. Computer Architecture (Conceptual/Definition)

What is cache locality, and what are the two forms of locality (temporal and spatial) that CPU cache design exploits? Explain how each form influences whether a program runs fast or slow on real hardware.

**Answer:**

**Cache locality** refers to the tendency of programs to access a small, predictable subset of memory addresses repeatedly or in nearby clusters over short periods of time, rather than jumping randomly across the entire address space. CPU caches are built on the assumption that this pattern holds, and their entire performance benefit depends on it.

- **Temporal locality:** if a memory location is accessed once, it is likely to be accessed again soon. Example: a loop counter or an accumulator variable is read and written on every iteration of a loop — it stays "hot" in the cache the whole time, so after the first access it's served from a fast cache line instead of slow main memory on every subsequent access.
- **Spatial locality:** if a memory location is accessed, nearby memory locations are likely to be accessed soon too. Example: iterating over an array sequentially (`for i in 0..n: sum += arr[i]`) touches consecutive addresses. Caches exploit this by fetching an entire **cache line** (typically 64 bytes, i.e. several array elements at once) on a miss, not just the single requested byte/word — so the next few accesses become cheap "hits" for free.

**Impact on real performance:** a program that respects locality (e.g., iterating a 2D array row-major when it's stored row-major in memory) keeps hitting data already sitting in L1/L2 cache, running orders of magnitude faster than one that jumps around unpredictably (e.g., iterating the same array column-major, or chasing pointers through a scattered linked list) and constantly triggers cache misses that stall the CPU waiting on DRAM, which is roughly 100x slower than an L1 cache hit. This is why, in practice, two algorithms with identical Big-O complexity can have wildly different real-world runtimes — cache-friendly memory access patterns (also called "mechanical sympathy") often matter as much as algorithmic complexity for performance-critical code.

**Why this matters:** locality is the reason data-structure and loop-ordering choices (array-of-structs vs. struct-of-arrays, row-major vs. column-major traversal, blocking/tiling in matrix multiplication) show up as real, measurable performance levers in systems and competitive programming, not just theoretical trivia.

### 2. Object-Oriented Programming (Comparison)

Compare method overloading and method overriding in object-oriented programming. Cover when each is resolved (compile-time vs. run-time), what relationship between classes each requires, and give a short example of each.

**Answer:**

| Aspect | Overloading | Overriding |
|---|---|---|
| Definition | Multiple methods in the **same class** (or scope) share a name but differ in parameter list (number, type, or order of parameters). | A subclass provides its own implementation of a method already defined (with the same signature) in its superclass. |
| Class relationship | No inheritance required — can happen within a single class. | Requires an inheritance (or interface-implementation) relationship between two classes. |
| Resolution time | **Compile-time** (a.k.a. static/early binding) — the compiler picks the matching overload based on the argument types visible at the call site. | **Run-time** (a.k.a. dynamic/late binding) — the actual method invoked depends on the real object type behind a base-class pointer/reference, determined via the virtual dispatch mechanism (e.g., a vtable in C++). |
| Return type | Can differ between overloads (though parameters must differ; return type alone isn't enough to distinguish overloads in most languages). | Must match (or be a covariant subtype of) the overridden method's return type. |
| Purpose | Provide multiple convenient ways to call conceptually the same operation with different inputs. | Let a subclass customize/specialize inherited behavior while keeping a uniform interface for callers. |

**Overloading example:**
```cpp
class Calculator {
public:
    int add(int a, int b) { return a + b; }
    double add(double a, double b) { return a + b; }
};
```
The compiler picks which `add` to call based on whether the arguments are `int` or `double` — decided at compile time.

**Overriding example:**
```cpp
class Shape {
public:
    virtual double area() { return 0.0; }
};
class Circle : public Shape {
public:
    double radius;
    double area() override { return 3.14159 * radius * radius; }
};

Shape* s = new Circle{5.0};
s->area(); // calls Circle::area() at run time, even though s is typed as Shape*
```
Even though `s` is a `Shape*`, calling `s->area()` invokes `Circle::area()` because the actual object is a `Circle` — resolved at run time via virtual dispatch, not based on the pointer's declared type.

**Why this matters:** this distinction is the basis of **polymorphism** in OOP — overriding (dynamic binding) is what lets a single interface (like `Shape*`) behave differently depending on the concrete object behind it, which is the mechanism that makes extensible, plugin-style designs (new shapes, new payment methods, new file formats) possible without modifying the code that consumes the base interface.

### 3. System Design Basics (Scenario/Applied)

You're designing a URL shortener service (like bit.ly) that needs to handle a very high ratio of reads (redirects) to writes (new short URLs created) — say, 100:1. A teammate suggests putting a cache in front of the database that maps short codes to long URLs. Explain what caching strategy (read-through, cache-aside, write-through) fits best here, and describe what happens on a cache miss and how you'd handle cache invalidation if a URL mapping is ever deleted.

**Answer:**

**Best-fit strategy: cache-aside (a.k.a. lazy loading), read-heavy optimized.**

In cache-aside, the application code (not the cache or database itself) is responsible for checking the cache first and populating it on a miss:

1. **On a read (redirect request) — cache hit:** the application looks up the short code in the cache (e.g., Redis). If found, it immediately returns the long URL and issues the redirect — no database hit at all. Given the 100:1 read:write ratio, this is the overwhelmingly common path, and it's fast (in-memory lookup, no disk I/O, no query planning).
2. **On a read — cache miss:** the application queries the database for the short code, gets the long URL, **writes that result into the cache** (so the next read for the same code is a hit), and then returns the redirect. This is why it's called "lazy" — the cache is only populated on demand, not proactively for every row in the database.
3. **On a write (new short URL created):** the application writes the new mapping directly to the database. It can optionally also write it into the cache immediately (a small write-through step layered on top of cache-aside) so the very first redirect for a brand-new link is already a cache hit instead of forcing one guaranteed miss.

**Why cache-aside over write-through/read-through here:** a pure write-through cache updates the cache on every write path automatically, which is great when reads and writes are more balanced, but here writes are rare (1 in 101 requests) — paying cache-population cost on every write is fine, but the real win is that cache-aside keeps the cache lean, populated only with codes that are actually being read (naturally matching real-world traffic, where a small fraction of short URLs account for most redirects — a classic power-law/Zipfian access pattern). A read-through cache (where the cache itself, not the app, fetches from the DB on a miss) behaves similarly to cache-aside from a strategy standpoint but pushes the DB-fetch logic into the caching layer instead of the app — a reasonable alternative, but cache-aside keeps that logic in application code, which is simpler to reason about and debug for most teams.

**Cache invalidation on delete:** when a short URL mapping is deleted (or expires), the application must explicitly **delete the corresponding key from the cache** at the same time it deletes the row from the database (rather than leaving it to expire naturally via TTL, which could serve a dead link for minutes or hours). A safe pattern: delete from the database first, then delete from the cache — if the cache-delete step fails or is delayed, worst case a stale cache entry serves one more redirect to a URL that should now be gone (a rare, low-severity read of soon-to-be-evicted data), which is a much safer failure mode than deleting the cache first and having a concurrent read repopulate it with now-stale data from the database before the database delete completes.

**Why this matters:** cache-aside is the default caching pattern for read-heavy services precisely because it self-selects for "hot" data without needing to predict access patterns in advance, and the delete-DB-then-cache ordering is a small but easy-to-get-backwards detail that determines whether your system ever serves incorrect data after a deletion, versus merely serving slightly-stale-but-still-correct data for a short window.
