### Question: Subarray Sum Equals K (Hashing/Maps — Medium)

Given an integer array `nums` and an integer `k`, return the total number of **contiguous subarrays** whose elements sum to exactly `k`.

**Input format:**
- An integer array `nums`.
- An integer `k`.

**Output format:**
- An integer: the count of contiguous subarrays whose sum equals `k`.

**Worked Examples:**

1. `nums = [1, 1, 1]`, `k = 2` → `2` (the subarrays `[1, 1]` starting at index 0 and `[1, 1]` starting at index 1 both sum to 2).
2. `nums = [1, 2, 3]`, `k = 3` → `2` (`[1, 2]` and `[3]`).
3. `nums = [1, -1, 0]`, `k = 0` → `3` (`[1, -1]`, `[0]`, and `[1, -1, 0]` all sum to 0).

**Constraints:**
- `1 <= nums.length <= 2 * 10^4`
- `-1000 <= nums[i] <= 1000`
- `-10^7 <= k <= 10^7`
- `nums[i]` may be negative, so a sliding window alone does not work.

---

### Step-by-Step Walkthrough

**Approach — Prefix Sums + Hash Map**

The brute-force approach checks every pair of start/end indices and sums each subarray, which is `O(n^2)`. Since `nums` can contain negative numbers, a two-pointer sliding window (which relies on the window sum growing monotonically as you extend it) doesn't apply here. Instead, reduce the problem to prefix sums.

Define `prefix[i]` as the sum of `nums[0..i-1]` (with `prefix[0] = 0`). The sum of any subarray `nums[i..j]` (inclusive) equals `prefix[j+1] - prefix[i]`. We want to count pairs `(i, j+1)` where:

```
prefix[j+1] - prefix[i] = k
=> prefix[i] = prefix[j+1] - k
```

So, as we scan through the array computing a running prefix sum, at each position we just need to know **how many earlier prefix sums equal `current_prefix - k`**. That's a lookup, not a search — perfect for a hash map that tracks the frequency of every prefix sum seen so far.

1. **Initialize.** Create `freq`, a hash map from prefix-sum value to how many times it has occurred. Seed it with `freq[0] = 1` — this accounts for a subarray starting at index 0 (an empty prefix sums to 0, so if the running sum itself ever equals `k`, that lookup must match this seeded entry).
2. **Scan once.** Maintain a running `prefix` sum. For each element:
   - Add it to `prefix`.
   - Look up `freq[prefix - k]`. If present, add its count to the answer — every earlier index with that prefix sum marks the start of a subarray ending here that sums to `k`.
   - Increment `freq[prefix]` by 1 (this prefix sum is now itself a candidate for future lookups).
3. **Return the accumulated count.**

**Why it works:** every pair of positions `(i, j+1)` with `prefix[i] = prefix[j+1] - k` corresponds to exactly one contiguous subarray summing to `k`. Because the hash map stores *counts* of prefix sums rather than just their presence, duplicate prefix sums (which happen naturally, especially with negative numbers or zeros in the array) are all counted, not just the first occurrence.

**Complexity Analysis:**
- **Time complexity:** `O(n)` — a single pass through `nums`, with `O(1)` average-case hash map lookups and insertions.
- **Space complexity:** `O(n)` in the worst case, for the hash map storing up to `n + 1` distinct prefix sums.

---

### C++ Code

```cpp
#include <iostream>
#include <vector>
#include <unordered_map>
using namespace std;

class Solution {
public:
    // Returns the count of contiguous subarrays of nums summing to k.
    int subarraySum(vector<int>& nums, int k) {
        unordered_map<int, int> freq;
        freq[0] = 1;  // empty prefix, needed so a subarray starting at index 0 is counted

        int prefix = 0;
        int count = 0;

        for (int num : nums) {
            prefix += num;

            // If some earlier prefix sum equals (prefix - k), every subarray
            // from just after that earlier index up to here sums to k.
            auto it = freq.find(prefix - k);
            if (it != freq.end()) {
                count += it->second;
            }

            freq[prefix]++;
        }

        return count;
    }
};

int main() {
    Solution sol;

    // Example 1
    vector<int> nums1 = {1, 1, 1};
    cout << sol.subarraySum(nums1, 2) << " (expected 2)" << endl;

    // Example 2
    vector<int> nums2 = {1, 2, 3};
    cout << sol.subarraySum(nums2, 3) << " (expected 2)" << endl;

    // Example 3
    vector<int> nums3 = {1, -1, 0};
    cout << sol.subarraySum(nums3, 0) << " (expected 3)" << endl;

    return 0;
}
```

**Trace against the examples:**
- `nums = [1, 1, 1]`, `k = 2`: `freq = {0:1}`. `prefix=1`: look up `-1`, not found; `freq={0:1,1:1}`. `prefix=2`: look up `0`, found (count 1) → `count=1`; `freq={0:1,1:1,2:1}`. `prefix=3`: look up `1`, found (count 1) → `count=2`. Final: `2`. ✓
- `nums = [1, 2, 3]`, `k = 3`: `freq={0:1}`. `prefix=1`: look up `-2`, not found; `freq={0:1,1:1}`. `prefix=3`: look up `0`, found → `count=1`; `freq={0:1,1:1,3:1}`. `prefix=6`: look up `3`, found → `count=2`. Final: `2`. ✓
- `nums = [1, -1, 0]`, `k = 0`: `freq={0:1}`. `prefix=1`: look up `1`, not found; `freq={0:1,1:1}`. `prefix=0`: look up `0`, found (count 1) → `count=1`; `freq={0:2,1:1}`. `prefix=0`: look up `0`, found (count 2) → `count=3`; `freq={0:3,1:1}`. Final: `3`. ✓

## CS Fundamentals

### 1. Computer Architecture (Conceptual/Definition)

What is instruction pipelining in CPU architecture, and why does it improve throughput? Describe the three classic types of pipeline hazards — structural, data, and control — and one common technique used to mitigate each.

**Answer:**

**Instruction pipelining** overlaps the execution of multiple instructions by splitting the CPU's instruction-processing cycle into discrete stages (a common textbook version: Fetch, Decode, Execute, Memory access, Write-back), where each stage is handled by dedicated hardware. Instead of waiting for one instruction to fully complete all five stages before starting the next, a new instruction enters the Fetch stage every clock cycle, so at any given moment up to five instructions are in flight simultaneously, each at a different stage.

This doesn't reduce the *latency* of any single instruction (it may even increase it slightly due to pipeline register overhead), but it dramatically improves **throughput** — in the ideal case, a 5-stage pipeline can complete close to one instruction per clock cycle once the pipeline is full, instead of one instruction every five cycles.

This overlap introduces **hazards** — situations where the next instruction can't safely execute in its expected clock cycle:

- **Structural hazard:** two instructions in the pipeline need the same hardware resource at the same time (e.g., both want to access memory in the same cycle, but there's only one memory port). *Mitigation:* duplicate the resource (e.g., separate instruction and data caches/memory ports, the classic Harvard-architecture-inspired fix used even in otherwise von-Neumann designs).
- **Data hazard:** an instruction depends on the result of a previous instruction that hasn't finished the pipeline yet (e.g., `ADD R1, R2, R3` immediately followed by `SUB R4, R1, R5`, where `R1` isn't written back yet when `SUB` needs to read it). *Mitigation:* **forwarding/bypassing** — route the computed result directly from the Execute stage's output back into a later instruction's input, without waiting for the Write-back stage; when forwarding isn't possible, insert a **pipeline stall (bubble)**.
- **Control hazard:** caused by branch instructions — the pipeline doesn't know which instruction to fetch next until the branch is resolved, which may not happen until several stages later. *Mitigation:* **branch prediction** (guess the branch direction based on history and speculatively fetch/execute down that path, rolling back on a misprediction) — modern CPUs achieve high prediction accuracy (95%+), making this far more effective than simply stalling until every branch resolves.

**Why this matters:** pipelining is the foundational technique behind why modern CPUs are fast despite each individual instruction taking multiple clock cycles to fully execute, and hazard-handling logic (forwarding units, branch predictors) occupies a significant fraction of a modern CPU's transistor budget.

### 2. Computer Networks (Comparison)

Compare TCP and UDP in terms of the guarantees each protocol provides at the transport layer. Give one real-world application best suited to each, and explain why.

**Answer:**

| Aspect | TCP | UDP |
|---|---|---|
| Connection | Connection-oriented — requires a handshake (SYN, SYN-ACK, ACK) before data flows. | Connectionless — a sender just fires datagrams with no setup. |
| Reliability | Guarantees delivery via acknowledgments and retransmission of lost packets. | No delivery guarantee — a lost packet is simply gone. |
| Ordering | Guarantees in-order delivery to the application (reorders/buffers packets that arrive out of sequence). | No ordering guarantee — packets can arrive in any order, and the application must handle that itself if it matters. |
| Flow/congestion control | Built in — uses a sliding window and algorithms like slow start / congestion avoidance to adapt sending rate to network and receiver capacity. | None — UDP will happily send as fast as the application asks, with no backoff on congestion. |
| Overhead | Higher — larger header (20 bytes minimum), handshake latency, and retransmission bookkeeping. | Lower — 8-byte header, no handshake, minimal per-packet overhead. |
| Header/packet unit | Stream-oriented — the application sees a continuous byte stream, not discrete message boundaries. | Message-oriented — each `send()` call corresponds to one discrete datagram the receiver gets (or doesn't) as a whole. |

**TCP fits:** file transfer / web browsing (HTTP over TCP). Loading a web page or downloading a file is worthless if bytes are missing, duplicated, or scrambled out of order — correctness of the full byte stream matters far more than shaving off milliseconds of handshake latency, so TCP's reliability and ordering guarantees are exactly what's needed.

**UDP fits:** live video/voice calls (e.g., VoIP, video conferencing) or real-time multiplayer games. If one audio frame's packet is lost, retransmitting it is pointless by the time it would arrive — the call has already moved past that moment in time. It's far better to drop that frame and keep playing forward in real time than to stall the whole stream waiting for a TCP-style retransmission and reordering. Similarly, a slightly stale position update in a fast-paced game is more useful than an up-to-date one that arrives late because it was queued behind a retransmission.

**Why this matters:** the TCP-vs-UDP choice is really a proxy for a broader systems-design question — "does this application need correctness/completeness, or does it need timeliness/low latency more?" — and that same tradeoff (reliable-but-slower vs. best-effort-but-fast) recurs constantly in distributed systems design beyond just networking.

### 3. Operating Systems (Scenario/Applied)

You're building a system where multiple threads need coordinated access to a pool of 3 identical database connections (any thread can use any connection, but no more than 3 threads may hold one at a time). Would you use a mutex or a semaphore here, and why? Then describe a scenario in which improper semaphore use could cause a deadlock, and how you'd prevent it.

**Answer:**

**Mutex vs. semaphore for this scenario:** a **mutex** is a binary lock meant to protect a single critical section — it has an owner (the thread that locked it must be the one to unlock it) and only ever allows one thread through at a time. That doesn't fit here, because we need **up to 3** threads to hold a connection simultaneously, not just 1.

A **counting semaphore** is the right tool: initialize it to `3` (matching the pool size). Each thread calls `wait()`/`acquire()` on the semaphore before taking a connection from the pool (which decrements the internal counter; if the counter is already `0`, the thread blocks until a slot frees up) and calls `signal()`/`release()` when it returns the connection (incrementing the counter and waking a waiting thread, if any). This naturally caps concurrent connection usage at exactly 3, and unlike a mutex, a semaphore has no single "owner" — any thread can signal it, which fits a resource-pool pattern where the thread returning a connection need not be the one that most recently acquired it.

**A deadlock scenario:** suppose each database operation actually needs *two* connections at once (e.g., to run a cross-shard query touching two different databases), and a thread acquires them one at a time: `wait(pool)` twice in a row. With a pool size of 3, imagine three threads each successfully acquire one connection (semaphore count drops to 0), and each then blocks on `wait(pool)` trying to acquire its *second* connection — but no connections remain, and none of the three threads holding one will ever release it, because each is stuck waiting for a second one before it can finish and give the first one back. This is a classic **circular wait**, one of the four necessary conditions for deadlock (along with mutual exclusion, hold-and-wait, and no preemption).

**Prevention:** the simplest fix here is breaking the **hold-and-wait** condition — require each thread to acquire *all* the connections it needs for an operation in a single atomic step (e.g., wrap acquisition of both slots behind one higher-level lock, or use `try_wait()` on the second connection and release the first and retry from scratch if it's unavailable, rather than blocking while still holding the first). More generally, standard deadlock-prevention strategies include: enforcing a global acquisition order for all resources (so every thread requests connections in the same fixed order, eliminating circular wait), using timeouts on `wait()` calls with rollback on failure, or redesigning the operation so it genuinely only ever needs one resource at a time.

**Why this matters:** this distinction — mutex for exclusive single-resource access vs. semaphore for bounded pools of interchangeable resources — comes up constantly in real backend systems (database connection pools, thread pools, rate limiters), and the hold-and-wait deadlock pattern shown here is exactly what happens in production when connection-pool code acquires multiple resources without care for ordering.
