## DSA

### Question: Two Sum (Arrays — Easy)

**Problem Statement**

Given an array of integers `nums` and an integer `target`, return the indices of the two numbers such that they add up to `target`. You may assume that each input has exactly one solution, and you may not use the same element twice. You can return the answer in any order.

**Input/Output Format**

- Input: an array of integers `nums`, and an integer `target`.
- Output: a pair (array of two indices) `[i, j]` such that `nums[i] + nums[j] == target`.

**Examples**

1. `nums = [2, 7, 11, 15]`, `target = 9` → Output: `[0, 1]` (because `nums[0] + nums[1] = 2 + 7 = 9`)
2. `nums = [3, 2, 4]`, `target = 6` → Output: `[1, 2]` (because `nums[1] + nums[2] = 2 + 4 = 6`)
3. `nums = [3, 3]`, `target = 6` → Output: `[0, 1]` (duplicate values are allowed, but not reusing the same index twice)

**Constraints**

- `2 <= nums.length <= 10^4`
- `-10^9 <= nums[i] <= 10^9`
- `-10^9 <= target <= 10^9`
- Exactly one valid answer exists.

### Step-by-Step Walkthrough

**Brute force first.** The most obvious approach is to check every pair `(i, j)` and see if `nums[i] + nums[j] == target`. That's two nested loops, giving O(n²) time and O(1) extra space. It works, but for n = 10⁴ that's up to ~10⁸ comparisons — noticeably slow, and there's a much better way.

**Key insight.** For each element `nums[i]`, the value we *need* to complete the pair is `complement = target - nums[i]`. The brute force wastes time re-scanning the array to look for that complement every time. Instead, we can remember every value we've already seen, along with its index, in a hash map (`unordered_map<int,int>` mapping value → index). Then, as we scan the array once:

1. Compute `complement = target - nums[i]`.
2. Check if `complement` is already a key in the map (i.e., we've seen it earlier in the array).
   - If yes, we've found our pair: the earlier index (stored in the map) and the current index `i`.
   - If no, insert `nums[i] → i` into the map and continue.

This works because by the time we reach index `i`, the map contains every element that came *before* it. If the complement of `nums[i]` was seen earlier, the map already holds it — we don't need to look ahead, since the problem guarantees exactly one solution and we only need to find each pair once (in whichever order the two elements occur).

**Why it's correct.** Every pair `(i, j)` with `i < j` gets checked exactly once: when we're processing index `j`, we ask "have I seen `target - nums[j]` before?" — and if `nums[i]` was that earlier value, we catch it there. We never revisit the same index twice, and we never need a nested loop.

**Complexity.**
- Time: O(n) — a single pass through the array; each hash map lookup/insert is O(1) on average.
- Space: O(n) — in the worst case, we store almost every element in the hash map before finding the match.

### C++ Code

```cpp
#include <vector>
#include <unordered_map>
using namespace std;

vector<int> twoSum(vector<int>& nums, int target) {
    // Maps a value we've already seen to the index where it occurred.
    unordered_map<int, int> seen;

    for (int i = 0; i < (int)nums.size(); i++) {
        int complement = target - nums[i];

        // If the complement was seen earlier, we've found our pair.
        auto it = seen.find(complement);
        if (it != seen.end()) {
            return {it->second, i};
        }

        // Otherwise, remember this value and its index for future lookups.
        seen[nums[i]] = i;
    }

    // Problem guarantees a solution exists, so this line is unreachable.
    return {};
}
```

## CS Fundamentals

### 1. Operating Systems (Conceptual/Definition)

**Question:** What is the difference between a process and a thread? Why is context switching between two threads of the same process generally faster than context switching between two separate processes?

**Answer:**

A **process** is an independent, running instance of a program. It owns its own private address space (code, heap, stack, data segments), its own set of file descriptors, and its own OS-level resources. Processes are isolated from each other by the OS — one process cannot directly read or write another process's memory.

A **thread** is a unit of execution *within* a process. A single process can have multiple threads, and all threads within that process share the same address space (the same heap, global/static data, and open file descriptors), but each thread has its own stack, its own program counter, and its own set of registers (i.e., its own execution context).

**Why thread switches are cheaper:** A context switch has to save and restore whatever state distinguishes one execution context from another, and reload the CPU/MMU state needed to run it. When switching between two threads of the *same* process:
- The address space (page tables) stays the same, so there's typically no need to flush the TLB (translation lookaside buffer) or change the memory-mapping hardware state.
- Only the thread-specific state (registers, program counter, stack pointer) needs to be saved/restored.

When switching between two *different processes*, the OS additionally has to swap out the entire address space — change page table pointers, and in many architectures flush (or tag-invalidate) the TLB, since the old cached virtual→physical mappings are no longer valid for the new process. This extra work (and the subsequent cache/TLB misses as the new process "warms up" its mappings) is what makes process context switches meaningfully more expensive than thread context switches. This is also the underlying reason multi-threaded designs are often preferred over multi-process designs when frequent, fine-grained concurrency and shared state are needed.

### 2. Computer Networks (Comparison)

**Question:** Compare HTTP/1.1 and HTTP/2. What specific problem in HTTP/1.1 does HTTP/2 solve, and how does it solve it?

**Answer:**

**HTTP/1.1** is a text-based, request-response protocol. Its major performance problem is **head-of-line (HOL) blocking at the application layer**: although HTTP/1.1 supports "keep-alive" (reusing one TCP connection for multiple requests), it processes requests on that connection strictly in order — the client can't get response #2 until response #1 has been fully sent. Browsers work around this by opening multiple parallel TCP connections to the same host (commonly 6 per domain), but this has costs: each TCP connection needs its own handshake (and TLS handshake, if HTTPS), consumes a separate congestion-control window, and there's a hard cap on how many you can realistically open.

**HTTP/2** solves this with **multiplexing**: it introduces the concept of "streams" within a *single* TCP connection. Each request/response pair is broken into small binary-framed messages tagged with a stream ID, and frames from different streams can be interleaved on the same connection. The receiving end reassembles frames by stream ID. This means many requests and responses can be in flight concurrently over one connection, with no request needing to wait for an unrelated one to finish — eliminating application-layer HOL blocking and removing the need for multiple parallel connections to the same host.

Other related HTTP/2 improvements: header compression (HPACK, to reduce the overhead of repetitive headers like cookies/user-agent on every request) and server push (allowing the server to proactively send resources it knows the client will need).

**Important nuance:** HTTP/2 removes HOL blocking at the *application* layer, but because it still runs over a single TCP connection, a single lost packet still blocks *all* streams at the *transport* layer (TCP guarantees in-order delivery of the whole byte stream). This TCP-level HOL blocking is what HTTP/3 (built on QUIC/UDP) further addresses, by giving each stream independent loss recovery.

### 3. DBMS (Scenario/Applied)

**Question:** A `users` table has a unique `email` column. You add a standard B-tree index on `email` to speed up lookups, but queries of the form `SELECT * FROM users WHERE LOWER(email) = 'someone@example.com'` are still doing a full table scan and are just as slow as before. Why doesn't the index help here, and how would you fix it?

**Answer:**

A standard B-tree index stores entries keyed on the **exact, literal value** of the indexed column (in this case, the raw `email` string as stored), sorted in that order. The database's query planner can only use an index to satisfy a `WHERE` condition if the condition is expressed directly (or can be provably simplified to) that indexed expression.

The query `WHERE LOWER(email) = '...'` applies a function, `LOWER(...)`, to the column *before* comparing it. The index was built on `email` itself, not on `LOWER(email)` — so there is no way for the planner to use the index to jump directly to matching rows for that particular expression. It has no choice but to evaluate `LOWER(email)` for every row and check the condition, i.e., a full table scan.

This is a common and easy mistake: wrapping an indexed column in a function (`LOWER()`, `UPPER()`, `DATE()`, string concatenation, arithmetic, etc.) in the `WHERE` clause silently defeats the index, even though the index still exists and is otherwise healthy.

**Fixes** (in order of how most production systems actually solve it):

1. **Functional / expression index:** Most modern databases (PostgreSQL, Oracle, MySQL 8+) support creating an index directly on the expression: `CREATE INDEX idx_users_email_lower ON users (LOWER(email));`. The planner can then match `WHERE LOWER(email) = '...'` to this index directly.
2. **Normalize the data at write time:** Store emails already lowercased (e.g., in a dedicated `email_lower` column, or just always lowercase before insert/update), and index that column directly. Then queries filter on the normalized column with a plain equality, using the plain index — this also avoids paying the `LOWER()` cost on every read.
3. **Application-level normalization:** Lowercase the email in application code before it ever reaches the query, so the query becomes `WHERE email = 'someone@example.com'` (assuming email was stored lowercase to begin with), which uses the existing plain index.

The general lesson: an index only helps a query if the query's predicate is written in a form the planner can match to how the index is built — case-insensitive or function-wrapped lookups need either a matching expression index or normalized storage.
