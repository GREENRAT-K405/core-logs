**Problem: Lowest Common Ancestor of a Binary Tree**

Given the root of a binary tree, and two nodes `p` and `q` that exist in the tree, find their lowest common ancestor (LCA).

The LCA of two nodes `p` and `q` in a binary tree is defined as the lowest (i.e. deepest) node that has both `p` and `q` as descendants (a node can be a descendant of itself).

**Input format:**
- The root of a binary tree (each node has a unique integer value).
- Two node references/values `p` and `q`, both guaranteed to exist in the tree.

**Output format:**
- The value of the node that is the LCA of `p` and `q`.

**Worked Examples:**

Consider the tree:

```
              3
            /   \
           5     1
          / \   / \
         6   2 0   8
            / \
           7   4
```

1. `p = 5`, `q = 1` → LCA = `3` (5 and 1 are in different subtrees of the root, so the root itself is the LCA).
2. `p = 5`, `q = 4` → LCA = `5` (4 is a descendant of 5, and a node is allowed to be its own ancestor).
3. `p = 6`, `q = 4` → LCA = `5` (both 6 and 4 live under node 5 — 6 directly, 4 through node 2).

**Constraints:**
- The number of nodes in the tree is in the range `[2, 10^5]`.
- `-10^9 <= Node.val <= 10^9`
- All `Node.val` are unique.
- `p != q`
- `p` and `q` will both exist in the tree.

---

### Step-by-Step Walkthrough

**Approach — Recursive Post-Order DFS**

The key insight: if we search a subtree and find that `p` is in one branch and `q` is in the other branch (relative to some node `X`), then `X` must be the LCA — because `X` is the deepest node from which both `p` and `q` are still reachable.

We do a recursive DFS from the root:

1. **Base case:** If the current node is `null`, or it *is* `p` or `q`, return the current node itself. Returning early on hitting `p` or `q` is valid because no node below `p` (or `q`) needs to be searched further — we already know `p`/`q` is present at this point, so this node is a candidate answer to propagate upward.
2. **Recurse left and right:** Call the same function on `root->left` and `root->right`. Each call returns either `null` (neither `p` nor `q` found in that subtree) or a non-null node (either `p`, `q`, or their LCA, found somewhere in that subtree).
3. **Combine results:**
   - If **both** left and right recursive calls return non-null, it means `p` was found in one subtree and `q` in the other (or one of them is the current root itself, discovered via the base case at a higher call). In that case, the **current node** is the LCA — return it.
   - If **only one side** is non-null, that means both `p` and `q` (or whichever one has been found so far) live entirely within that one subtree, so we simply propagate that result upward unchanged.
   - If both are `null`, neither node is in this subtree, so return `null`.

**Why it works:** Because this is a post-order traversal (we process children before making a decision at the parent), by the time we decide at any node, we already know the complete answer for both of its subtrees. The first node (from the bottom up) where both `p` and `q` are confirmed to be present in different branches is necessarily the deepest common ancestor — exactly the LCA definition.

**Complexity Analysis:**
- **Time complexity:** `O(n)` — in the worst case we visit every node exactly once, since there's no early termination across sibling subtrees once we start the DFS (until we find both nodes, which could be anywhere).
- **Space complexity:** `O(h)` where `h` is the height of the tree, due to the recursion call stack. Worst case `O(n)` for a completely skewed (linked-list-like) tree; `O(log n)` for a balanced tree.

---

### C++ Solution

```cpp
#include <iostream>
using namespace std;

// Definition for a binary tree node.
struct TreeNode {
    int val;
    TreeNode *left;
    TreeNode *right;
    TreeNode(int x) : val(x), left(nullptr), right(nullptr) {}
};

class Solution {
public:
    // Returns the LCA of p and q in the tree rooted at 'root'.
    TreeNode* lowestCommonAncestor(TreeNode* root, TreeNode* p, TreeNode* q) {
        // Base case: empty node, or we've found one of our targets.
        // Returning here lets the found node propagate up as a candidate.
        if (root == nullptr || root == p || root == q) {
            return root;
        }

        // Search both subtrees.
        TreeNode* leftResult = lowestCommonAncestor(root->left, p, q);
        TreeNode* rightResult = lowestCommonAncestor(root->right, p, q);

        // If both sides returned a non-null node, p and q were found
        // in different subtrees -> current node is the LCA.
        if (leftResult != nullptr && rightResult != nullptr) {
            return root;
        }

        // Otherwise, propagate whichever side found something
        // (or null if neither side found anything).
        return (leftResult != nullptr) ? leftResult : rightResult;
    }
};

// Helper to build the example tree and locate node pointers by value.
TreeNode* findNode(TreeNode* root, int val) {
    if (root == nullptr) return nullptr;
    if (root->val == val) return root;
    TreeNode* leftFound = findNode(root->left, val);
    if (leftFound != nullptr) return leftFound;
    return findNode(root->right, val);
}

int main() {
    // Build the example tree:
    //               3
    //             /   \
    //            5     1
    //           / \   / \
    //          6   2 0   8
    //             / \
    //            7   4
    TreeNode* n3 = new TreeNode(3);
    TreeNode* n5 = new TreeNode(5);
    TreeNode* n1 = new TreeNode(1);
    TreeNode* n6 = new TreeNode(6);
    TreeNode* n2 = new TreeNode(2);
    TreeNode* n0 = new TreeNode(0);
    TreeNode* n8 = new TreeNode(8);
    TreeNode* n7 = new TreeNode(7);
    TreeNode* n4 = new TreeNode(4);

    n3->left = n5;  n3->right = n1;
    n5->left = n6;  n5->right = n2;
    n1->left = n0;  n1->right = n8;
    n2->left = n7;  n2->right = n4;

    Solution sol;

    // Example 1: LCA(5, 1) = 3
    TreeNode* res1 = sol.lowestCommonAncestor(n3, findNode(n3, 5), findNode(n3, 1));
    cout << "LCA(5, 1) = " << res1->val << " (expected 3)" << endl;

    // Example 2: LCA(5, 4) = 5
    TreeNode* res2 = sol.lowestCommonAncestor(n3, findNode(n3, 5), findNode(n3, 4));
    cout << "LCA(5, 4) = " << res2->val << " (expected 5)" << endl;

    // Example 3: LCA(6, 4) = 5
    TreeNode* res3 = sol.lowestCommonAncestor(n3, findNode(n3, 6), findNode(n3, 4));
    cout << "LCA(6, 4) = " << res3->val << " (expected 5)" << endl;

    return 0;
}
```

**Trace against the examples:**
- `LCA(5, 1)`: DFS from 3 finds 5 down the left branch and 1 down the right branch → both sides non-null at node 3 → returns `3`. ✓
- `LCA(5, 4)`: DFS from 3 goes left; at node 5 itself, `root == p`, so it returns `5` immediately without needing to search further; the right branch (containing 1) returns `null`; so node 3 propagates the left result `5` upward. ✓
- `LCA(6, 4)`: At node 5, left subtree (rooted at 6) returns `6` since `root == p`; right subtree (rooted at 2) recurses down and finds `4`, returning `4`. Both sides at node 5 are non-null → node 5 is the LCA. ✓

### 1. OOP — Comparison

**Q: Compare Method Overloading and Method Overriding in Object-Oriented Programming. Give a short code example of each and state which type of polymorphism each represents.**

**A:**

| Aspect | Method Overloading | Method Overriding |
|---|---|---|
| Definition | Multiple methods in the **same class** (or scope) share a name but differ in parameter list (number/type/order of arguments). | A subclass provides a **new implementation** of a method already defined in its superclass, with the **same signature**. |
| Binding | Resolved at **compile time** (static/early binding) — the compiler picks the right version based on argument types. | Resolved at **runtime** (dynamic/late binding) — the actual object type determines which version runs, via the virtual function table (vtable) in C++/Java. |
| Relationship | Occurs within one class; no inheritance required. | Requires an inheritance relationship (base and derived class). |
| Polymorphism type | Compile-time / static polymorphism. | Runtime / dynamic polymorphism. |
| Return type | Can differ, as long as parameter lists differ. | Must be the same (or covariant) — signature must match exactly. |

**Example (C++):**

```cpp
// Overloading — same class, different parameter lists
class Calculator {
public:
    int add(int a, int b) { return a + b; }
    double add(double a, double b) { return a + b; }
};

// Overriding — subclass redefines a base class virtual method
class Shape {
public:
    virtual double area() { return 0.0; }
};
class Circle : public Shape {
    double radius;
public:
    Circle(double r) : radius(r) {}
    double area() override { return 3.14159 * radius * radius; }
};
```

**Why this matters:** Overloading gives you a convenient, readable API (one method name, many usages) resolved purely by the compiler with no runtime cost. Overriding is what makes polymorphism useful in practice: a `Shape*` pointer can point to a `Circle` or a `Square`, and calling `area()` through the base pointer correctly dispatches to the derived class's implementation at runtime — this is the mechanism behind extensible, interface-driven designs (e.g., plugging in new shape types without changing code that consumes `Shape`).

### 2. System Design Basics — Scenario / Applied

**Q: You're asked to design a rate limiter for an API gateway that must support roughly 10,000 requests/second across many clients, each with their own per-minute quota. Walk through your high-level approach, including which algorithm you'd pick and why.**

**A:**

**Step 1 — Clarify the requirement:** Each client (identified by API key or user ID) should be limited to, say, N requests per rolling time window (e.g., 100 requests/minute). The system must make an allow/deny decision in microseconds per request, since it sits in the hot path of every API call, and must work correctly even when the gateway is horizontally scaled across multiple machines.

**Step 2 — Pick an algorithm.** Common choices:
- **Fixed Window Counter:** Simplest — increment a counter per client per fixed time window (e.g., per calendar minute), reset it when the window rolls over. Downside: allows up to 2x the limit in bursts right at window boundaries (e.g., 100 requests at 0:59 and another 100 at 1:00).
- **Sliding Window Log:** Store a timestamp for every request per client, count how many fall within the last N seconds. Very accurate, but memory-heavy (one entry per request).
- **Sliding Window Counter:** A weighted average between the current and previous fixed window counts — approximates a true sliding window with much less memory than a full log. Good accuracy/cost tradeoff.
- **Token Bucket:** Each client has a bucket that refills at a fixed rate (tokens/sec) up to a max capacity; each request consumes a token, and is rejected if the bucket is empty. This naturally allows short bursts (up to bucket capacity) while enforcing a long-term average rate — a good fit for typical API traffic patterns.

For this scenario I'd choose **Token Bucket** (or Sliding Window Counter as a close second) because it tolerates natural burstiness in client traffic without being unfair like the fixed window, and it's cheap: O(1) state per client (just "tokens remaining" and "last refill timestamp").

**Step 3 — Where to store the state.** At 10,000 req/sec, per-request database writes are too slow. Use an **in-memory store like Redis**, since it's fast, supports atomic operations (`INCR`, or a Lua script combining check-and-decrement into one atomic step), and can be shared across multiple gateway instances so the rate limit is enforced consistently cluster-wide rather than per-instance.

**Step 4 — Handle scale/failure:**
- Shard clients across multiple Redis instances (e.g., by hashing client ID) to avoid a single Redis node becoming a bottleneck.
- Set a TTL on each client's rate-limit key so idle clients don't leak memory forever.
- Decide a fail-open vs fail-closed policy if Redis is unreachable — typically fail-open (allow the request) for availability, since a broken rate limiter is a lesser evil than an outage of the whole API.

**Step 5 — Respond to the client:** On rejection, return HTTP 429 (Too Many Requests) with a `Retry-After` header so well-behaved clients back off correctly.

**Why this matters:** Rate limiting is a recurring building block in system design interviews because it touches several core themes at once — algorithm choice under memory/accuracy tradeoffs, distributed shared state, atomicity of check-and-update operations, and graceful degradation under failure.

### 3. DBMS — Conceptual / Definition

**Q: What are the ACID properties of a database transaction? Define each and give a concrete example of what would go wrong if that property were violated.**

**A:** ACID is an acronym for the four guarantees a database transaction system provides to ensure reliable processing even in the presence of errors, power failures, or concurrent access.

1. **Atomicity** — A transaction is treated as a single indivisible unit: either *all* of its operations succeed, or *none* of them take effect (it's rolled back entirely). 
   *Example of violation:* A bank transfer debits $100 from Account A but the system crashes before crediting Account B. Without atomicity, the $100 simply vanishes — money is lost because only part of the transaction completed.

2. **Consistency** — A transaction takes the database from one valid state to another valid state, never violating defined rules, constraints, or invariants (e.g., foreign keys, unique constraints, custom business rules like "balance can't go negative").
   *Example of violation:* A transfer moves money out of Account A (now negative, violating a "no overdraft" constraint) but the constraint isn't checked — the database ends up in a state that shouldn't be possible according to its own rules.

3. **Isolation** — Concurrently executing transactions should not interfere with each other; the end result should be as if the transactions ran one after another (serially), even though they may actually execute in parallel for performance. Isolation levels (Read Uncommitted, Read Committed, Repeatable Read, Serializable) control how strictly this is enforced, trading off consistency guarantees against concurrency/performance.
   *Example of violation:* Two transactions both read Account A's balance ($100) at the same time, each deduct $50 independently, and both write back $50 — instead of the correct final balance of $0. This is a classic "lost update" caused by insufficient isolation.

4. **Durability** — Once a transaction is committed, its changes are permanent, even if the system crashes immediately afterward (typically achieved via write-ahead logging (WAL) or similar persistence mechanisms).
   *Example of violation:* A user's transaction is confirmed as "successful," but the server crashes before the write-ahead log is flushed to disk — after restart, the committed change has silently disappeared.

**Why this matters:** ACID is the foundation that lets application developers reason about data correctness without manually handling every possible interleaving of failures and concurrent transactions themselves — the database engine handles it. It's also the key contrast point when discussing NoSQL/distributed systems, many of which relax some ACID guarantees (favoring "eventual consistency" or BASE) in exchange for higher availability and horizontal scalability (as formalized by the CAP theorem).
