### Question: Validate Binary Search Tree (Trees — Medium)

**Problem Statement**

Given the root of a binary tree, determine if it is a valid Binary Search Tree (BST).

A valid BST is defined as follows:
- The left subtree of a node contains only nodes with values **strictly less than** the node's value.
- The right subtree of a node contains only nodes with values **strictly greater than** the node's value.
- Both the left and right subtrees must also be valid BSTs.

**Input/Output Format**

- Input: the root of a binary tree (nodes hold integer values; the tree may be given level-order with `null` markers for missing children).
- Output: a boolean — `true` if the tree is a valid BST, `false` otherwise.

**Examples**

1. Input: `[2,1,3]` (root 2, left 1, right 3) → Output: `true`
   Every left value is smaller and every right value is larger than its ancestor.
2. Input: `[5,1,4,null,null,3,6]` (root 5, left 1, right 4; 4's children are 3 and 6) → Output: `false`
   Node `4` is in the right subtree of `5`, so every value under it must be `> 5`. But `4` itself is `< 5`, so the tree is invalid (it doesn't matter that `4 > 3` locally).
3. Input: `[1]` (single node) → Output: `true`
   A single node trivially satisfies the BST property.

**Constraints**

- The number of nodes is in the range `[0, 10^4]`.
- `-2^31 <= Node.val <= 2^31 - 1` (values fit in a 32-bit signed integer, so we must be careful with strict bound comparisons at the extremes).

---

**Step-by-Step Walkthrough**

A common mistake is to only compare each node to its immediate children (i.e., check `left->val < node->val < right->val` locally). That is **not sufficient** — Example 2 above is exactly the trap: node `3` is a valid left child of `4` locally, but `3` also sits in the right subtree of `5`, where it's fine (3 < 5 is false — wait, actually the real violation is `4 < 5`). The point stands: a node's value must respect the constraints imposed by **every ancestor** on the path from the root, not just its parent.

The clean way to enforce this is to carry a valid **range `(low, high)`** down the recursion:

1. Start at the root with an unbounded range `(-infinity, +infinity)`.
2. At each node, check that `low < node->val < high`. If not, the tree is invalid — return `false` immediately.
3. Recurse into the left subtree with the range narrowed to `(low, node->val)` — everything in the left subtree must be less than the current node.
4. Recurse into the right subtree with the range narrowed to `(node->val, high)` — everything in the right subtree must be greater than the current node.
5. An empty subtree (`null`) is always valid — base case returns `true`.
6. The tree is valid overall only if the current node's check passes **and** both subtrees are valid (`&&`, which also gives us short-circuiting — we stop as soon as one side fails).

**Why it works:** by construction, the range passed to any node is the intersection of all constraints imposed by its ancestors so far. So checking against that single range is equivalent to checking against every ancestor individually, but done incrementally in O(1) work per node instead of walking back up on every call.

**Handling the value range edge case:** since node values can be as small as `INT_MIN` or as large as `INT_MAX`, using `int` for the `low`/`high` sentinels would overflow or collide with a real node value. Using `long long` for the bounds (with `LLONG_MIN`/`LLONG_MAX` as the initial unbounded range) avoids this cleanly.

*(An alternative approach: an in-order traversal of a valid BST visits nodes in strictly increasing order, so you could do an in-order traversal and check that each visited value is strictly greater than the previous one. Both approaches are O(n) time; the bounds-passing recursion avoids storing the whole traversal and is what's implemented below.)*

**Complexity Analysis**

- **Time:** O(n) — every node is visited exactly once, and the work done per node (two comparisons) is O(1).
- **Space:** O(h) — where `h` is the height of the tree, due to the recursion call stack. Worst case O(n) for a completely skewed (linked-list-shaped) tree; O(log n) for a balanced tree.

**C++ Code**

```cpp
#include <bits/stdc++.h>
using namespace std;

struct TreeNode {
    int val;
    TreeNode *left;
    TreeNode *right;
    TreeNode(int x) : val(x), left(nullptr), right(nullptr) {}
};

class Solution {
public:
    bool isValidBST(TreeNode* root) {
        // Start with an unbounded open range using long long so that
        // INT_MIN / INT_MAX node values never collide with the sentinels.
        return validate(root, LLONG_MIN, LLONG_MAX);
    }

private:
    // Returns true if every node in this subtree lies strictly within (low, high)
    // AND both its children satisfy the same property with a narrowed range.
    bool validate(TreeNode* node, long long low, long long high) {
        if (node == nullptr) {
            return true; // an empty subtree is trivially a valid BST
        }

        if (node->val <= low || node->val >= high) {
            return false; // violates an ancestor's constraint
        }

        // Left subtree: all values must stay below node->val.
        // Right subtree: all values must stay above node->val.
        return validate(node->left, low, node->val) &&
               validate(node->right, node->val, high);
    }
};

// --- Simple manual test harness against the worked examples ---
int main() {
    Solution sol;

    // Example 1: [2,1,3] -> true
    TreeNode* t1 = new TreeNode(2);
    t1->left = new TreeNode(1);
    t1->right = new TreeNode(3);
    cout << boolalpha << sol.isValidBST(t1) << "\n"; // true

    // Example 2: [5,1,4,null,null,3,6] -> false
    TreeNode* t2 = new TreeNode(5);
    t2->left = new TreeNode(1);
    t2->right = new TreeNode(4);
    t2->right->left = new TreeNode(3);
    t2->right->right = new TreeNode(6);
    cout << boolalpha << sol.isValidBST(t2) << "\n"; // false

    // Example 3: [1] -> true
    TreeNode* t3 = new TreeNode(1);
    cout << boolalpha << sol.isValidBST(t3) << "\n"; // true

    return 0;
}
```

### 1. Object-Oriented Programming (Conceptual/Definition)

**Question:** What is the difference between **compile-time polymorphism** and **run-time polymorphism** in OOP? Give an example of each.

**Answer:**

Polymorphism means "many forms" — the ability of the same interface (function/operator name) to behave differently depending on context. It comes in two flavors:

- **Compile-time polymorphism (static binding):** The compiler decides which function/operator implementation to call *at compile time*, based on the number/types of arguments. Achieved via:
  - **Function overloading** — multiple functions with the same name but different parameter lists (e.g., `int add(int, int)` vs `double add(double, double)`).
  - **Operator overloading** — redefining how an operator behaves for a user-defined type (e.g., overloading `+` for a `Complex` number class).

- **Run-time polymorphism (dynamic binding):** The specific function to call is decided *at run time*, based on the actual (derived) type of the object, not its static (declared) type. Achieved via:
  - **Virtual functions** in a base class, overridden in derived classes, accessed through a base class pointer/reference. The compiler generates a lookup through a **vtable** (virtual function table) so the correct override is invoked based on the object's real type.

  ```cpp
  class Shape {
  public:
      virtual double area() const { return 0; }
  };
  class Circle : public Shape {
      double r;
  public:
      Circle(double r) : r(r) {}
      double area() const override { return 3.14159 * r * r; }
  };

  Shape* s = new Circle(2.0);
  s->area(); // resolved at run time -> Circle::area() is called, not Shape::area()
  ```

**Why this distinction matters:** compile-time polymorphism is faster (no indirection, resolved once at compile time) but rigid — the behavior can't change based on the actual object at run time. Run-time polymorphism is what makes abstractions like "process a list of `Shape*` without knowing their concrete types" possible — it's the mechanism behind interfaces/abstract classes and is central to designing extensible, decoupled systems.

### 2. System Design Basics (Comparison)

**Question:** Compare **horizontal scaling** and **vertical scaling**. What are the trade-offs, and why do most large-scale distributed systems favor one over the other?

**Answer:**

- **Vertical scaling ("scale up"):** Increase the capacity of a single machine — more CPU, RAM, faster disk. 
  - *Pros:* Simple — no change to application architecture; no distributed-systems complexity (no need for data partitioning, consensus, network calls between nodes).
  - *Cons:* Has a hard physical/cost ceiling — you eventually run out of bigger hardware to buy, and cost grows super-linearly as you approach top-tier hardware. Also a **single point of failure**: if that one machine goes down, the whole system is down.

- **Horizontal scaling ("scale out"):** Add more machines and distribute load/data across them (via a load balancer, sharding, replication, etc.).
  - *Pros:* Near-unbounded scaling (in principle, just add more commodity machines); better fault tolerance (one node failing doesn't take down the whole system, assuming proper replication/failover); cost scales roughly linearly with commodity hardware instead of exponentially.
  - *Cons:* Introduces real distributed-systems complexity — network latency between nodes, the need for load balancing, data consistency across replicas/shards (CAP theorem trade-offs), and harder debugging/observability across many machines.

**Why large-scale systems favor horizontal scaling:** at large scale, no single machine — no matter how powerful — can handle the required throughput or storage, and relying on one machine means one failure takes everything down. Horizontal scaling trades implementation complexity (which is a one-time, amortized engineering cost) for elasticity, fault tolerance, and a scaling ceiling that's effectively "add more boxes." Most systems in practice use a hybrid: scale vertically first (it's cheap and simple) up to a comfortable point, then move to horizontal scaling once vertical scaling's cost/complexity curve stops being worth it or a single-point-of-failure risk becomes unacceptable.

### 3. Computer Architecture (Scenario/Applied)

**Question:** A program has a loop that accesses a large 2D array **column-by-column** in a language that stores arrays in **row-major order** (like C/C++). A colleague suggests rewriting the loop to access the array **row-by-row** instead. Explain why this change would likely make the program run significantly faster, referencing how CPU caches work.

**Answer:**

In row-major order, elements of a 2D array are laid out in memory row after row — i.e., `arr[i][j]` and `arr[i][j+1]` are adjacent in memory, but `arr[i][j]` and `arr[i+1][j]` are `(number of columns)` elements apart.

CPUs don't fetch memory one variable at a time — they fetch it in fixed-size chunks called **cache lines** (commonly 64 bytes) into the **L1/L2/L3 cache**. This exploits **spatial locality**: the assumption that if you access one memory address, you'll likely access nearby addresses soon after.

- **Column-by-column access** (`arr[0][j], arr[1][j], arr[2][j], ...` for fixed `j`) jumps across memory by a full row's width on every single access. Each access is likely to land in a *different* cache line than the previous one (unless the row is tiny), so almost every access is a **cache miss**, forcing a slow trip to main memory (DRAM), which can be 100+ times slower than an L1 cache hit. Worse, when you fetch a full cache line for `arr[i][j]`, the other useful values loaded alongside it (`arr[i][j+1]`, `arr[i][j+2]`, ...) get evicted before they're ever used, since the loop won't touch them until much later (if the array is large enough that its rows don't fit entirely in cache).

- **Row-by-row access** (`arr[i][0], arr[i][1], arr[i][2], ...` for fixed `i`) accesses consecutive memory addresses. The first access to a cache line pulls in, say, 16 consecutive `int`s (64 bytes / 4 bytes per int) in one memory fetch; the next 15 accesses are then **cache hits** served directly from L1, no trip to main memory needed.

**Result:** row-by-row traversal turns what would be mostly cache misses into mostly cache hits, which can easily produce a 10-100x speedup for large arrays, purely from changing the *access pattern* — no change to the algorithm's time complexity (both are still O(rows × cols)) or the amount of data processed. This is a classic illustration that **Big-O complexity doesn't capture real-world performance** — memory access patterns and hardware cache behavior often dominate actual wall-clock time.
