### Question: Minimum Window Substring (Strings — Hard)

**Problem Statement**

Given two strings `s` and `t`, return the minimum-length substring of `s` that contains every character of `t` (including repeated characters, at least as many times as they occur in `t`). If no such substring exists, return an empty string `""`. If there are multiple minimum-length windows, return any one of them.

**Input/Output Format**

- Input: two strings `s` and `t` of English letters (mixed case).
- Output: a string — the smallest window of `s` satisfying the coverage condition, or `""` if none exists.

**Examples**

1. Input: `s = "ADOBECODEBANC"`, `t = "ABC"` → Output: `"BANC"` — the shortest window of `s` containing one `'A'`, one `'B'`, and one `'C'`.
2. Input: `s = "a"`, `t = "a"` → Output: `"a"`.
3. Input: `s = "a"`, `t = "aa"` → Output: `""` — `t` needs two `'a'`s, but `s` only has one.

**Constraints**

- `1 <= s.length, t.length <= 10^5`
- `s` and `t` consist of uppercase and lowercase English letters.
- Aim for O(|s| + |t|) time.

### Step-by-Step Walkthrough

**Why brute force is too slow.** The naive idea — try every `(left, right)` pair as a candidate window and check whether it covers `t` — is O(n²) pairs times O(n) (or O(26)) to verify coverage, which is far too slow for `n = 10^5`. The real insight we need: as `right` moves forward, the window only ever *gains* characters, so "does this window cover `t`" is monotonic in `right` for a fixed `left`. That monotonicity is exactly what a sliding window exploits.

**Setting up the counts.** Build a frequency map `need` of every character in `t` (so `need['A'] = 1, need['B'] = 1, need['C'] = 1` for `t = "ABC"`, or `need['a'] = 2` for `t = "aa"`). Let `required = need.size()` — the number of *distinct* characters that must be satisfied, not the total character count.

**Expand, then contract.** Maintain a second map `window` counting characters currently inside `[left, right]`, and a counter `formed` = how many distinct characters in `need` are currently satisfied *exactly or more* (`window[c] >= need[c]`).

1. Advance `right` one step at a time, adding `s[right]` to `window`. If this character is one `t` needs and `window[c]` has just reached `need[c]` (not exceeded — exactly matched), increment `formed`.
2. Whenever `formed == required`, the current window is *valid* (it covers `t`). This is the moment to try shrinking from the left: while the window stays valid, repeatedly record the window length if it's the best seen so far, then remove `s[left]` from `window` and advance `left`. Stop shrinking the instant removing a character would drop `window[c]` below `need[c]` for a needed character (that's when `formed` decrements).
3. Continue advancing `right` until it exhausts `s`.

**Why this is correct.** For each position of `right`, the smallest valid window ending anywhere near it has already been found by the inner contraction loop, because we always shrink as far as validity allows before moving `right` again — we never leave a shrinkable valid window un-shrunk. And we never need to reconsider a `left` position once we've moved past it: if the window `[left, right]` was invalid without `s[left]`, no window starting further right can recover characters we already have, so `left` only ever moves forward. That's what keeps the whole scan linear.

**Why it's efficient.** Both `left` and `right` traverse `s` once, moving only forward — each index enters and leaves the window at most once. Map operations are O(1) amortized (bounded alphabet).

**Complexity.**
- Time: O(|s| + |t|) — building `need` is O(|t|); the two-pointer scan is O(|s|).
- Space: O(|Σ|) — at most 52 entries (upper + lower case letters) in each map, so effectively O(1).

### C++ Code

```cpp
#include <string>
#include <unordered_map>
#include <climits>
using namespace std;

string minWindow(const string& s, const string& t) {
    if (s.empty() || t.empty() || s.size() < t.size()) return "";

    unordered_map<char, int> need, window;
    for (char c : t) need[c]++;

    int required = (int)need.size();   // distinct characters that must be covered
    int formed = 0;                    // how many of those are currently satisfied

    int left = 0, bestLen = INT_MAX, bestStart = 0;

    for (int right = 0; right < (int)s.size(); right++) {
        char c = s[right];
        window[c]++;
        // Count this character as "satisfied" only at the moment it first
        // reaches the required amount, so formed never over-counts.
        if (need.count(c) && window[c] == need[c]) {
            formed++;
        }

        // Window covers t: shrink from the left as far as coverage allows.
        while (formed == required) {
            if (right - left + 1 < bestLen) {
                bestLen = right - left + 1;
                bestStart = left;
            }

            char lc = s[left];
            window[lc]--;
            if (need.count(lc) && window[lc] < need[lc]) {
                formed--;
            }
            left++;
        }
    }

    return bestLen == INT_MAX ? "" : s.substr(bestStart, bestLen);
}
```

Two details that make or break correctness: `formed` increments only when `window[c] == need[c]` (the exact moment of satisfaction — using `>=` on every insert would over-count and let `formed` reach `required` too early or stay stuck), and the initial `s.size() < t.size()` guard avoids ever entering the loop for an input that can't possibly be covered.

### 1. Operating Systems (Comparison)

What is the difference between a process and a thread? Specifically, what do threads of the same process share, what stays private to each thread, and why is switching between threads generally cheaper than switching between processes?

**Answer:**

A **process** is an independent execution unit with its own private address space: its own code segment, heap, and virtual memory mapping, managed by the OS as a self-contained sandbox. A **thread** is a unit of execution *within* a process — a process can have many threads, and by default they all run inside that one process's address space.

**What threads share:** the same virtual address space (so the same global/static variables and heap-allocated objects), the same open file descriptors and sockets, and the same code segment. This is precisely why threads can communicate by just reading and writing shared variables directly — no IPC mechanism is needed.

**What stays private per thread:** its own stack (so local variables and the call chain are thread-specific), its own program counter and register set, and its own thread-local storage if the language provides it. This is why two threads can be at completely different points in the same function at the same time without stepping on each other's local variables — but *can* corrupt shared heap state if they touch it without synchronization (the root cause of race conditions).

**Why context-switching threads is cheaper:** switching between two processes requires the OS to swap the entire memory mapping (page tables, TLB flush) in addition to saving/restoring registers, because the two processes have completely different address spaces. Switching between two threads of the *same* process reuses the same page table — only registers, the stack pointer, and the program counter need to be saved and restored. Fewer things to swap means a measurably cheaper switch, which is exactly why highly concurrent servers favor a thread-per-connection or thread-pool model over spinning up a new process per connection.

The tradeoff mirrors the savings: because threads share memory, one misbehaving or crashing thread (e.g., writing through a bad pointer) can corrupt or bring down the whole process, whereas a crashing process is isolated and only affects itself — the OS reclaims its memory and the rest of the system is unaffected.

### 2. Computer Networks (Scenario/Applied)

You're designing a live video-calling feature. A teammate suggests using TCP "since it's reliable and guarantees delivery." Would you agree, and what protocol would you actually pick — and why does the same reasoning *not* apply to a file-download feature in the same app?

**Answer:**

I would push back — for a live call, TCP's reliability is actually a liability, and I'd pick **UDP** (typically wrapped in something like RTP for media framing, with the application handling loss itself).

**Why TCP hurts here.** TCP guarantees reliable, in-order delivery via acknowledgments and retransmission: if packet 5 is lost, TCP will not deliver packet 6 to the application until packet 5 is successfully retransmitted and arrives — this is "head-of-line blocking." For a live call, a video frame that arrives 400ms late because it was queued behind a retransmission is *useless* — the moment has passed, the caller is already speaking the next sentence. Late data in real-time media is worse than *missing* data: a dropped frame just causes a brief glitch that the codec can conceal or interpolate around, but a delayed-then-delivered frame stalls everything behind it and the receiver has to catch up, making the lag worse.

**Why UDP fits.** UDP has no ordering guarantee, no retransmission, and no handshake overhead — the application (or the RTP layer on top of it) just sends packets and moves on. If a packet is lost, it's simply gone; the receiver keeps playing the next frame it has. Real-time codecs are specifically designed to tolerate this: audio codecs interpolate across a missing packet, video codecs lean on periodic keyframes to bound how far a dropped frame's effect can propagate. The application trades perfect delivery for low, *predictable* latency, which is the actual requirement for a call feeling "live."

**Why file download is the opposite case.** A downloaded file that's missing bytes 4000–4500 is a corrupted file — there is no acceptable "glitch and move on" for a ZIP archive or a PDF. Here, correctness (every byte, in order) matters far more than latency; an extra 200ms of retransmission delay is invisible to the user, but one missing chunk ruins the whole deliverable. That's exactly TCP's guarantee, so it's the right tool.

The general principle: **TCP when correctness of every byte matters more than timeliness; UDP (with an application-level tolerance for loss) when timeliness matters more than completeness.** The protocol choice should follow from what a "late but complete" versus "on-time but lossy" delivery actually costs the user, not from a blanket preference for "reliable" transport.

### 3. OOP (Definition)

What is polymorphism, and what is the difference between compile-time (static) polymorphism and runtime (dynamic) polymorphism? Give a concrete mechanism for each.

**Answer:**

**Polymorphism** ("many forms") is the ability for the same interface — a function name, an operator, a method call — to behave differently depending on the type or number of arguments it's invoked with, or the actual runtime type of the object it's invoked on. It lets calling code stay generic ("call `draw()` on this shape") without needing to know which concrete variant it's dealing with.

**Compile-time (static) polymorphism** is resolved by the compiler *before* the program runs, purely from the information visible at the call site — no runtime dispatch mechanism is involved. The two common mechanisms:
- **Function/method overloading** — multiple functions share a name but differ in parameter types or count (`area(int side)` vs `area(int base, int height)`); the compiler picks the matching one based on the arguments at the call site.
- **Operator overloading** — giving `+`, `==`, etc. custom meaning for a user-defined type (e.g., `Complex operator+(Complex a, Complex b)`); again resolved at compile time from the operand types.
Because resolution happens at compile time, this is also called **early binding** — the generated machine code already contains a direct call to the specific overload.

**Runtime (dynamic) polymorphism** is resolved *while the program is running*, based on the actual object behind a reference or pointer, not its declared/static type. The mechanism is **method overriding** through inheritance plus **virtual dispatch**: a base class declares a `virtual` method (or an abstract/interface method), and derived classes override it. A call through a base-class pointer or reference is resolved via a vtable lookup at the moment of the call, using the object's real (dynamic) type. This is **late binding**. Example: a `vector<Shape*>` holding a mix of `Circle*` and `Square*` objects — calling `shape->draw()` in a loop invokes each object's own override, even though every element is accessed through the same `Shape*` type.

**Why the distinction matters in practice:** static polymorphism has zero runtime dispatch cost (the compiler already knows exactly which function to call) but requires the set of types to be known at compile time. Dynamic polymorphism costs one indirection (a vtable lookup) per call but is what makes extensibility possible — new `Shape` subclasses can be added later, and existing code that loops over `Shape*` and calls `draw()` keeps working without modification. This is precisely the mechanism behind the **open/closed principle**: code is open to extension (new subclasses) but closed to modification (the calling loop never changes).
