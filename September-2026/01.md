## DSA

### Question: Jump Game (Greedy — Medium)

You are given an integer array `nums`. You start at index `0`. Each element `nums[i]` represents the **maximum** number of steps you can jump forward from index `i` (you may jump anywhere from `1` up to `nums[i]` steps, or not jump at all if you're already at the last index).

Return `true` if you can reach the last index of the array, or `false` otherwise.

**Input format:**
- An integer array `nums` of length `n`.

**Output format:**
- A boolean: `true` if the last index is reachable from index `0`, `false` otherwise.

**Worked Examples:**

1. `nums = [2, 3, 1, 1, 4]` → `true` (jump `1` step from index `0` to `1`, then `3` steps from index `1` to index `4`, the last index).
2. `nums = [3, 2, 1, 0, 4]` → `false` (no matter how you jump from index `0`, `1`, or `2`, you always land on index `3`, which has `nums[3] = 0` — you get stuck there and can never reach index `4`).
3. `nums = [0]` → `true` (you start at index `0`, which is already the last index, so no jump is needed).

**Constraints:**
- `1 <= n <= 10^4`
- `0 <= nums[i] <= 10^5`

---

### Step-by-Step Walkthrough

**Approach — Greedy (track the farthest reachable index)**

The key insight is that we don't need to try every possible sequence of jumps (which would be exponential). Instead, as we scan the array left to right, we maintain a single running value: `maxReach`, the farthest index reachable so far using any combination of jumps from indices we've already visited.

Walk through the array with index `i` from `0` to `n-1`:

1. **Check reachability first:** if `i > maxReach`, it means even the farthest jump from any earlier index cannot get us to index `i` — we're stuck, so return `false` immediately.
2. **Update the frontier:** otherwise, index `i` is reachable, so update `maxReach = max(maxReach, i + nums[i])` — from here we could jump as far as `i + nums[i]`.
3. **Early exit:** if at any point `maxReach >= n - 1`, the last index is already reachable, so return `true` without scanning further.

If the loop finishes without ever failing the reachability check, `maxReach` must have reached at least `n - 1` by the last index, so return `true`.

**Why it works:** this is a classic greedy argument — at every index we only care about the *single best* (farthest) jump achievable so far, never about which specific path of jumps got us there. This is valid because reachability is monotonic: if the farthest point reachable using indices `0..i` is `maxReach`, then every index up to `maxReach` is also reachable (since jump lengths are between `0` and `nums[i]`, meaning any smaller jump is always a legal choice too). So tracking only the maximum, rather than branching over every possible jump length, loses no information relevant to the yes/no reachability question, while avoiding the exponential blow-up of trying every path.

**Complexity Analysis:**
- **Time complexity:** `O(n)` — a single left-to-right pass over the array, constant work per index.
- **Space complexity:** `O(1)` — only the `maxReach` variable is kept, regardless of `n`.

---

### C++ Code

```cpp
#include <iostream>
#include <vector>
#include <algorithm>
using namespace std;

class Solution {
public:
    // Returns true if the last index is reachable from index 0.
    bool canJump(vector<int>& nums) {
        int n = static_cast<int>(nums.size());
        int maxReach = 0; // farthest index reachable so far

        for (int i = 0; i < n; i++) {
            if (i > maxReach) {
                // Can't even get to index i using any jump from an earlier index.
                return false;
            }
            maxReach = max(maxReach, i + nums[i]);
            if (maxReach >= n - 1) {
                // Last index is already within reach; no need to scan further.
                return true;
            }
        }

        return true; // loop completed without ever getting stuck
    }
};

int main() {
    Solution sol;

    // Example 1
    vector<int> a1 = {2, 3, 1, 1, 4};
    cout << boolalpha << sol.canJump(a1) << " (expected true)" << endl;

    // Example 2
    vector<int> a2 = {3, 2, 1, 0, 4};
    cout << boolalpha << sol.canJump(a2) << " (expected false)" << endl;

    // Example 3
    vector<int> a3 = {0};
    cout << boolalpha << sol.canJump(a3) << " (expected true)" << endl;

    return 0;
}
```

**Trace against the examples:**
- `nums = [2, 3, 1, 1, 4]`: `i=0`: `0<=0`, `maxReach=max(0,0+2)=2`. `i=1`: `1<=2`, `maxReach=max(2,1+3)=4`. `4>=n-1(=4)` → return `true`. ✓
- `nums = [3, 2, 1, 0, 4]`: `i=0`: `maxReach=max(0,3)=3`. `i=1`: `1<=3`, `maxReach=max(3,1+2)=3`. `i=2`: `2<=3`, `maxReach=max(3,2+1)=3`. `i=3`: `3<=3`, `maxReach=max(3,3+0)=3`. `i=4`: `4>3` → return `false`. ✓
- `nums = [0]`: `n=1`. `i=0`: `0<=0`, `maxReach=max(0,0+0)=0`. `maxReach>=n-1(=0)` → return `true`. ✓

## CS Fundamentals

### 1. DBMS (Conceptual/Definition)

What are the ACID properties of a database transaction? Define each one and explain what specifically could go wrong if that property were dropped.

**Answer:**

**ACID** is an acronym describing four guarantees a database management system makes about how transactions behave, so that applications can rely on the database even under concurrency and failures:

- **Atomicity:** a transaction's operations either **all** succeed and are committed, or **none** of them are applied at all — there is no partial execution. *Without it:* if a transaction transferring money debited one account but crashed before crediting the other, money would simply vanish from the system with no way to recover consistently.
- **Consistency:** a transaction moves the database from one valid state to another, respecting all defined constraints (foreign keys, unique constraints, application-level invariants like "balance can't go negative"). *Without it:* a transaction could commit and leave the database violating its own schema/business rules, e.g. a row referencing a foreign key that no longer exists.
- **Isolation:** concurrently executing transactions must not see each other's intermediate, uncommitted state — the end result must look as if the transactions ran one after another (serially), even though they may actually run in parallel for performance. *Without it:* classic anomalies appear, such as a **dirty read** (transaction B reads a value transaction A wrote but hasn't committed yet, and A later rolls back, so B acted on data that never really existed).
- **Durability:** once a transaction is committed, its effects survive permanently, even if the system crashes or loses power immediately afterward (typically guaranteed via write-ahead logging to non-volatile storage). *Without it:* a user could receive a "payment successful" confirmation, then lose that payment entirely on a server crash a moment later.

**Why this matters:** ACID is the contract that lets an application developer reason about correctness without personally re-implementing crash recovery or concurrency control — in practice, most real-world database bugs trace back to a mistaken assumption about one of these four guarantees, most commonly assuming a stronger isolation level than the database is actually configured to provide (e.g., assuming serializable isolation while running under read-committed, which can still allow non-repeatable reads and phantom reads).

### 2. Computer Networks (Comparison)

Compare TCP and UDP as transport-layer protocols. For each, describe how it handles reliability, ordering, and connection setup, and give one real-world use case where each protocol's trade-offs make it the better choice.

**Answer:**

| Aspect | TCP | UDP |
|---|---|---|
| Connection model | **Connection-oriented** — requires a three-way handshake (`SYN`, `SYN-ACK`, `ACK`) before any data is sent. | **Connectionless** — a sender just fires datagrams; no handshake, no persistent connection state. |
| Reliability | **Reliable** — every segment is acknowledged; lost segments are automatically retransmitted using sequence numbers and timeouts. | **Unreliable** — no acknowledgments, no retransmission; a lost datagram is simply gone unless the application handles it. |
| Ordering | **Guaranteed in-order delivery** — segments are buffered and reassembled in the correct sequence before being handed to the application, even if they arrive out of order over IP. | **No ordering guarantee** — datagrams can arrive in a different order than they were sent, and the application must handle that itself if it matters. |
| Flow/congestion control | Built-in flow control (sliding window, so a fast sender can't overwhelm a slow receiver) and congestion control (backs off sending rate when packet loss suggests network congestion). | None built in — a UDP sender can keep blasting datagrams regardless of receiver or network state; the application layer must implement any pacing itself. |
| Overhead / latency | Higher — handshake adds round-trip latency before data flows, and per-segment acknowledgment/retransmission bookkeeping adds ongoing overhead. | Lower — data can be sent immediately with a minimal (8-byte) header and no handshake, minimizing latency. |

**Real-world use cases:**
- **TCP** is the right choice for **file transfer / HTTP web page loading**: a corrupted or missing byte in a downloaded file or an HTML page is unacceptable, so guaranteed, ordered, complete delivery is worth the extra latency and overhead.
- **UDP** is the right choice for **live video/voice calls (e.g., VoIP) or real-time multiplayer gaming**: if a single audio packet or a stale position update is lost, retransmitting it later is actually *worse* than just dropping it and moving on — by the time a retransmission would arrive, that moment has already passed, so low latency matters more than perfect delivery. These applications instead build their own lightweight, latency-tolerant handling on top of UDP (e.g., interpolating a missing video frame) rather than paying TCP's retransmission delay.

**Why this matters:** the TCP-vs-UDP choice is really a proxy for a more general system design question — "is stale-but-fast data more useful to this application than complete-but-slow data?" — and recognizing which side of that trade-off a given feature falls on (checkout payment vs. live game state) is a recurring theme across networking and distributed systems design.

### 3. System Design Basics (Scenario/Applied)

You're asked to design a URL shortener (like bit.ly): given a long URL, it returns a short unique code (e.g. `short.ly/aZ9kQ`), and visiting that short URL redirects to the original long URL. Walk through the high-level design: how would you generate the short code, what does the data model look like, and how would you handle the redirect at scale?

**Answer:**

**Core requirements:** (1) given a long URL, generate a short, unique code and store the mapping; (2) given a short code, redirect the client to the original long URL, with very low latency since redirects are on the read-heavy hot path; (3) reads vastly outnumber writes (a link is shortened once but clicked many times).

**Short code generation — two common approaches:**
1. **Counter + base62 encoding:** maintain a globally unique, monotonically increasing integer ID (e.g., from an auto-increment column or a distributed ID generator like Snowflake), then encode that integer in base62 (`[a-zA-Z0-9]`, 62 symbols) to produce a compact string. E.g., ID `125` (base 10) → some short string like `"cb"` in base62. This guarantees uniqueness by construction (no collision checking needed) and a 7-character base62 code supports `62^7 ≈ 3.5 trillion` unique codes, which is more than enough headroom.
2. **Hashing:** hash the long URL (e.g., with MD5) and take the first few characters of the hash, base62-encoded. This is simpler but requires a **collision check** (query if that code is already taken; if so, re-hash with a salt or take a different substring) since a partial hash isn't guaranteed unique — the counter approach is generally preferred for its collision-free guarantee.

**Data model:** a simple key-value-shaped table is enough —

```sql
CREATE TABLE url_mappings (
    short_code   VARCHAR(10) PRIMARY KEY,
    long_url     TEXT NOT NULL,
    created_at   TIMESTAMP NOT NULL DEFAULT NOW(),
    expires_at   TIMESTAMP NULL,
    click_count  BIGINT NOT NULL DEFAULT 0
);
```
`short_code` as the primary key makes redirect lookups a direct indexed point-query. This table doesn't need complex relational joins, so it's also a natural fit for a key-value store (e.g., DynamoDB or Redis-backed) instead of a relational database, if the scale demands it.

**Handling the redirect at scale:**
- **Caching is critical:** since reads (redirects) dominate writes by orders of magnitude, and link popularity typically follows a power-law distribution (a small number of links get most of the clicks), put a **cache** (e.g., Redis) in front of the database, keyed by `short_code`. Most redirect requests are served straight from cache, never touching the database.
- **Redirect type:** use an **HTTP 301 (permanent redirect)** if click analytics per-visit aren't needed (browsers cache it, reducing future load on the service entirely) — but if you need to count every click (as the `click_count` column suggests), use a **302 (temporary redirect)** instead, so the browser always asks the server again, letting you log/increment the click count on each visit; the count is then usually incremented asynchronously (e.g., via a message queue) rather than synchronously blocking the redirect response.
- **Horizontal scaling:** the redirect service itself is stateless (given `short_code`, look up `long_url` and respond), so it scales horizontally behind a load balancer with no special coordination needed between instances — all shared state lives in the cache/database layer.

**Why this matters:** this exercise is a good stand-in for a whole class of "read-heavy lookup service" system design questions — the interesting design decisions are rarely the write path (which is simple and low-volume) but rather how aggressively and correctly you exploit caching and read-optimized data access on the hot path, plus the subtle trade-off (301 vs 302) between browser-side caching efficiency and the ability to keep accurate analytics.
