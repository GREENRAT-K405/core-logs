### Question: Search in Rotated Sorted Array (Sorting/Searching — Medium)

You are given an integer array `nums` sorted in ascending order (with **distinct** values), which has been **rotated** at some unknown pivot index `k` (`0 <= k < nums.length`). For example, `[0,1,2,4,5,6,7]` might become `[4,5,6,7,0,1,2]` after rotating at index 3.

Given the rotated array `nums` and an integer `target`, return the index of `target` in `nums`, or `-1` if it is not present. Your algorithm must run in `O(log n)` time.

**Input format:**
- An array of distinct integers `nums`, sorted ascending then rotated at some pivot.
- An integer `target` to search for.

**Output format:**
- The index of `target` in `nums`, or `-1` if `target` is not found.

**Worked Examples:**

1. `nums = [4,5,6,7,0,1,2]`, `target = 0` → output `4` (0 sits at index 4).
2. `nums = [4,5,6,7,0,1,2]`, `target = 3` → output `-1` (3 is not in the array at all).
3. `nums = [1]`, `target = 0` → output `-1` (single-element array, target absent).

**Constraints:**
- `1 <= nums.length <= 5000`
- `-10^4 <= nums[i] <= 10^4`
- All values in `nums` are **unique**.
- `nums` is guaranteed to be an ascending array, possibly rotated at some pivot.
- `-10^4 <= target <= 10^4`

---

### Step-by-Step Walkthrough

**Approach — Modified Binary Search**

A plain binary search relies on the whole array being sorted, which is no longer true here — but a rotated sorted array has a useful property: **at any midpoint, at least one of the two halves (left-to-mid, or mid-to-right) is still normally sorted.** We can always tell which half is sorted by comparing `nums[low]` with `nums[mid]`, and use that to decide which half to keep searching in.

1. Maintain two pointers, `low = 0` and `high = n - 1`.
2. While `low <= high`:
   - Compute `mid = low + (high - low) / 2`.
   - If `nums[mid] == target`, return `mid` immediately.
   - **Determine which half is sorted:**
     - If `nums[low] <= nums[mid]`, the **left half** (`low` to `mid`) is sorted normally (no rotation point inside it).
       - Check if `target` falls within that sorted range: `nums[low] <= target < nums[mid]`. If yes, search left (`high = mid - 1`); otherwise search right (`low = mid + 1`).
     - Otherwise, the **right half** (`mid` to `high`) must be the sorted one.
       - Check if `target` falls within that range: `nums[mid] < target <= nums[high]`. If yes, search right (`low = mid + 1`); otherwise search left (`high = mid - 1`).
3. If the loop exits without returning, `target` is not present — return `-1`.

**Why it works:** Rotating a sorted array creates exactly one "break point" where the sequence drops. Whichever half of the current search window doesn't contain that break point is, by definition, still fully ascending, so a normal sorted-range check (`low <= target < mid` or similar) is valid on that half. The other half might still contain the rotation, but we don't need to know exactly where — we just narrow into it and repeat the same test recursively. Each iteration halves the search space exactly like standard binary search, so correctness carries over from the classic proof, just with an extra branch to pick the right comparison.

**Complexity Analysis:**
- **Time complexity:** `O(log n)` — every iteration discards half of the remaining search window, identical to standard binary search.
- **Space complexity:** `O(1)` — only a constant number of index variables are used, no extra data structures.

### C++ Code

```cpp
#include <iostream>
#include <vector>
using namespace std;

class Solution {
public:
    int search(vector<int>& nums, int target) {
        int low = 0, high = static_cast<int>(nums.size()) - 1;

        while (low <= high) {
            int mid = low + (high - low) / 2;

            if (nums[mid] == target) {
                return mid;
            }

            // Left half [low..mid] is sorted normally.
            if (nums[low] <= nums[mid]) {
                if (nums[low] <= target && target < nums[mid]) {
                    // target lies within the sorted left half.
                    high = mid - 1;
                } else {
                    // target must be in the (possibly rotated) right half.
                    low = mid + 1;
                }
            } else {
                // Otherwise the right half [mid..high] is the sorted one.
                if (nums[mid] < target && target <= nums[high]) {
                    // target lies within the sorted right half.
                    low = mid + 1;
                } else {
                    // target must be in the (possibly rotated) left half.
                    high = mid - 1;
                }
            }
        }

        return -1; // target not found
    }
};

int main() {
    Solution sol;

    vector<int> nums1 = {4, 5, 6, 7, 0, 1, 2};
    cout << "search([4,5,6,7,0,1,2], 0) = " << sol.search(nums1, 0) << " (expected 4)" << endl;

    vector<int> nums2 = {4, 5, 6, 7, 0, 1, 2};
    cout << "search([4,5,6,7,0,1,2], 3) = " << sol.search(nums2, 3) << " (expected -1)" << endl;

    vector<int> nums3 = {1};
    cout << "search([1], 0) = " << sol.search(nums3, 0) << " (expected -1)" << endl;

    return 0;
}
```

**Trace against the examples:**
- `[4,5,6,7,0,1,2]`, target `0`: `low=0,high=6,mid=3` (`nums[mid]=7`). `nums[low]=4 <= nums[mid]=7`, left sorted; is `4 <= 0 < 7`? No → search right, `low=4`. Now `mid=5` (`nums[mid]=1`). `nums[low]=0 <= nums[mid]=1`, left sorted; is `0 <= 0 < 1`? Yes → search left, `high=4`. Now `low=high=4`, `mid=4`, `nums[4]=0 == target` → return `4`. ✓
- `[4,5,6,7,0,1,2]`, target `3`: the search narrows repeatedly (similar branching) and every window excludes index positions holding `3`, since `3` isn't present; loop ends with `low > high` → returns `-1`. ✓
- `[1]`, target `0`: `low=high=0`, `mid=0`, `nums[0]=1 != 0`; `nums[low]=1 <= nums[mid]=1` so left considered sorted; is `1 <= 0 < 1`? No → `low = mid+1 = 1`; now `low > high`, loop ends → returns `-1`. ✓

### 1. Operating Systems (Comparison)

Compare a process and a thread. Cover how each is scheduled, what memory/resources they share versus own privately, and the relative cost of context-switching between two processes versus two threads of the same process.

**Answer:**

| Aspect | Process | Thread |
|---|---|---|
| Definition | An independent program in execution, with its own isolated address space. | A unit of execution *within* a process; a process can have one or many threads. |
| Memory | Owns its own private virtual address space (code, data, heap) — isolated from other processes. | Shares the parent process's address space (code, global/heap data) with all sibling threads. |
| Private resources | Own memory, own file descriptor table, own set of OS resources. | Its own stack, program counter, and register set/CPU state — but shares everything else with sibling threads. |
| Communication | Requires explicit IPC (pipes, sockets, shared memory, message queues) since memory is isolated. | Can communicate directly by reading/writing shared memory (variables, heap objects) — no IPC needed, but requires synchronization (locks) to avoid races. |
| Creation cost | Expensive — the OS must set up a new address space, page tables, and duplicate/allocate resources. | Cheap — only a new stack and register context need to be created within an existing address space. |
| Context-switch cost | Expensive — switching processes typically means switching page tables (flushing/reloading the TLB), which stalls memory access until it's repopulated. | Cheap — switching threads within the same process keeps the same page tables and TLB entries valid, so only register/stack state needs to change. |
| Fault isolation | A crash in one process does not directly bring down another (separate address spaces). | A bug in one thread (e.g. writing through a bad pointer) can corrupt memory shared by all threads in the same process, potentially crashing the whole process. |

**Why this matters:** This distinction drives real architecture decisions — e.g., a web server using a thread pool per request is far cheaper to scale than forking a full process per request, but it also means one misbehaving thread can take down every other request being served by that process, whereas a multi-process design trades some performance for strong fault isolation between requests. Understanding the address-space/TLB cost difference is also the concrete reason "threads are lightweight, processes are heavyweight" is true at the hardware level, not just a slogan.

### 2. Computer Networks (Conceptual/Definition)

What is the OSI (Open Systems Interconnection) model? Name its seven layers in order, state the core responsibility of each, and give one real-world protocol or device example that operates at that layer.

**Answer:**

The OSI model is a conceptual, seven-layer framework that standardizes how network communication is broken into independent responsibilities, so that each layer can be designed, implemented, and swapped out without needing to know the internals of the others. Data passed down from an application is progressively wrapped (encapsulated) with headers as it descends through the layers on the sending side, and unwrapped in reverse order on the receiving side.

From top (closest to the user) to bottom (closest to the physical wire):

1. **Application** — Provides network services directly to end-user applications (the interface a program actually talks to). *Example:* HTTP, DNS, SMTP.
2. **Presentation** — Translates, encrypts/decrypts, and compresses data so the application layer gets it in a usable format, independent of how it was transmitted. *Example:* TLS/SSL encryption, JPEG/ASCII encoding.
3. **Session** — Establishes, manages, and terminates the connection ("session") between two communicating applications, including synchronization checkpoints for long transfers. *Example:* session tokens/APIs in RPC frameworks; NetBIOS.
4. **Transport** — Provides end-to-end delivery between hosts, handling segmentation, flow control, and (optionally) reliability/ordering guarantees. *Example:* TCP (reliable, ordered) and UDP (best-effort) at the port level.
5. **Network** — Handles logical addressing and routing of packets across multiple networks to get them from source host to destination host. *Example:* IP (IPv4/IPv6), routers.
6. **Data Link** — Handles node-to-node delivery across a single physical link, including framing, MAC addressing, and error detection on that link. *Example:* Ethernet, Wi-Fi (802.11), switches.
7. **Physical** — Transmits raw bits over an actual physical medium (electrical signals, light pulses, radio waves). *Example:* copper cabling, fiber optics, radio transceivers.

**Why this matters:** The OSI model is primarily a *teaching and diagnostic* tool rather than something literally implemented layer-for-layer in real stacks (which mostly follow the simpler four-layer TCP/IP model) — but it's invaluable for debugging: "is this a Layer 1 issue (unplugged cable), a Layer 3 issue (bad routing/no connectivity), or a Layer 7 issue (the app returned a 500)?" gives you a structured way to isolate where in the stack a networking problem actually lives, rather than guessing at the whole system as one opaque unit.

### 3. System Design Basics (Scenario/Applied)

You're asked to design a distributed unique ID generator for a system with many application servers that must each independently generate IDs for new database rows — no central counter is allowed, IDs must be roughly sortable by creation time, and the system must handle tens of thousands of ID generations per second across all servers combined. Walk through your approach.

**Answer:**

**Step 1 — Rule out the naive options.** A single auto-increment counter in one database is a single point of contention and failure at this scale (every server would have to round-trip to it for every ID), and plain random UUIDs (v4) solve uniqueness but aren't time-sortable, which hurts database index locality (inserts land at random points in a B+ tree index instead of appending at the end) and makes "give me the newest N rows" queries awkward.

**Step 2 — Adopt a Snowflake-style ID scheme.** Twitter's Snowflake approach (and similar schemes used by Instagram, Discord, etc.) packs a 64-bit integer ID out of three parts, generated **locally on each server with zero coordination**:
- **Timestamp bits** (e.g., 41 bits) — milliseconds since a custom epoch, placed in the most-significant bits so IDs are naturally roughly increasing over time and sort chronologically.
- **Machine/worker ID bits** (e.g., 10 bits) — a unique ID assigned to each generating server/process (up to 1024 machines), so two machines never collide even if they generate an ID in the same millisecond.
- **Sequence bits** (e.g., 12 bits) — a per-machine counter that increments for multiple IDs generated within the same millisecond on that machine (up to 4096 per ms per machine), resetting to 0 when the clock ticks forward.

**Step 3 — Machine ID assignment.** Each server needs a unique, stable machine ID. This can be assigned via a lightweight coordination service at startup (e.g., a row claimed in a config table, or a value handed out by ZooKeeper/etcd), or statically configured per deployment (e.g., derived from a Kubernetes pod ordinal). This is the only coordination needed, and it happens once at startup — not per ID.

**Step 4 — Handle clock issues.** Since correctness depends on the local clock moving forward, guard against clock drift/rollback (e.g., NTP adjusting the clock backward): if a server detects `current_time < last_used_time`, it should either wait until the clock catches up or refuse to generate IDs briefly rather than risk emitting a duplicate or out-of-order ID.

**Step 5 — Throughput check.** With 12 sequence bits, a single machine can emit 4096 IDs per millisecond = ~4 million IDs/sec, so far more than enough headroom per machine; scaling to tens of thousands of IDs/sec across the whole fleet is trivially covered even with only a handful of machines, entirely without any cross-server coordination on the hot path.

**Why this matters:** This pattern shows up whenever a system needs "give me a unique value, fast, with no shared bottleneck" — the core trick generalizes beyond IDs: partition the value space so each independent actor (here, machine ID) owns a disjoint slice it can generate from locally, trading a tiny bit of coordination at setup time for zero coordination on the critical path.
