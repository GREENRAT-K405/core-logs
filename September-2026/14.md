### Question: Rotting Oranges (Graphs — Medium)

You are given an `m x n` grid where each cell can have one of three values:

- `0` — an empty cell
- `1` — a fresh orange
- `2` — a rotten orange

Every minute, any fresh orange that is **4-directionally adjacent** (up/down/left/right, not diagonal) to a rotten orange becomes rotten.

Return the minimum number of minutes that must elapse until **no cell has a fresh orange**. If this is impossible (some fresh orange can never be reached), return `-1`.

**Input format:**
- An `m x n` grid of integers, each `0`, `1`, or `2`.

**Output format:**
- A single integer: the minimum number of minutes until no fresh orange remains, or `-1` if some fresh orange is unreachable.

**Worked Examples:**

1.
```
Input:
[[2,1,1],
 [1,1,0],
 [0,1,1]]
Output: 4
```
Minute 0: rotten at (0,0). Minute 1: (0,1) and (1,0) rot. Minute 2: (0,2) and (1,1) rot. Minute 3: (2,1) rots (via (1,1)). Minute 4: (2,2) rots (via (2,1)). All fresh oranges are gone by minute 4.

2.
```
Input:
[[2,1,1],
 [0,1,1],
 [1,0,1]]
Output: -1
```
The orange at `(2,0)` is isolated by zeros on both 4-directional sides that connect to the rest of the grid — it can never be reached, so the answer is `-1`.

3.
```
Input:
[[0,2]]
Output: 0
```
There are no fresh oranges at all, so 0 minutes are needed.

**Constraints:**
- `1 <= m, n <= 10^4`
- `1 <= m * n <= 10^5`
- `grid[i][j]` is `0`, `1`, or `2`.

---

### Step-by-Step Walkthrough

**Approach — Multi-source Breadth-First Search (BFS)**

This is a classic "simultaneous spreading" problem, which is exactly what BFS models well when there are multiple starting points that all begin spreading at the same time.

1. **Scan the grid once** to:
   - Push the coordinates of every initially rotten orange (`2`) into a queue — these are all "level 0" of the BFS, since they all start rotting at minute 0 simultaneously.
   - Count the total number of fresh oranges (`1`). This count lets us later check whether every fresh orange was actually reached, without needing a second scan.

2. **Run BFS level by level** (minute by minute):
   - Process the queue **in whole layers**: for each layer, pop every node currently in the queue (this represents "everything that is rotten at the start of this minute"), and for each one, look at its four neighbors.
   - If a neighbor is a fresh orange (`1`), turn it into rotten (`2`), decrement the fresh-orange counter, and push it into the queue (it will spread further next minute).
   - After finishing a full layer, if we pushed at least one new rotten orange in that layer, increment the minute counter.

   Processing strictly by layers (rather than one node at a time) is what correctly models "all currently-rotten oranges infect their neighbors at the same time" — it guarantees the minute counter reflects true simultaneous spread instead of an arbitrary per-node order.

3. **Termination check:** After the BFS completes (queue empties), check the fresh-orange counter:
   - If it is `0`, every fresh orange was eventually rotted — return the minute counter.
   - If it is still `> 0`, some fresh oranges were never reached (isolated by empty cells or grid boundaries) — return `-1`.

**Why it works:** BFS naturally explores the grid in increasing order of distance (in minutes) from the nearest rotten orange, since all rotten oranges are enqueued together as the starting frontier. Processing the queue in discrete layers means the number of layers processed is exactly the number of minutes elapsed, so we get the correct answer for "all oranges rot simultaneously" without needing to simulate time explicitly.

Edge cases handled naturally by this approach:
- No fresh oranges at all → fresh count starts at 0 → loop never increments minutes → returns 0 immediately.
- Fresh oranges present but no rotten oranges at all → queue starts empty → BFS never runs → fresh count stays > 0 → returns -1.

**Complexity Analysis:**
- **Time:** `O(m * n)` — every cell is enqueued and dequeued at most once, and each dequeue does O(1) work per neighbor (4 neighbors).
- **Space:** `O(m * n)` — for the BFS queue in the worst case (e.g., all oranges start rotten).

### C++ Code

```cpp
#include <vector>
#include <queue>
using namespace std;

class Solution {
public:
    int orangesRotting(vector<vector<int>>& grid) {
        int rows = grid.size();
        if (rows == 0) return 0;
        int cols = grid[0].size();

        queue<pair<int,int>> rotten;   // BFS frontier: coordinates of rotten oranges
        int freshCount = 0;

        // Step 1: initial scan -- seed the queue with all rotten oranges,
        // and count how many fresh oranges need to be reached.
        for (int r = 0; r < rows; r++) {
            for (int c = 0; c < cols; c++) {
                if (grid[r][c] == 2) {
                    rotten.push({r, c});
                } else if (grid[r][c] == 1) {
                    freshCount++;
                }
            }
        }

        // No fresh oranges to begin with -- nothing to wait for.
        if (freshCount == 0) return 0;

        int minutes = 0;
        int dr[4] = {-1, 1, 0, 0};
        int dc[4] = {0, 0, -1, 1};

        // Step 2: BFS, processed strictly layer-by-layer so each layer
        // corresponds to exactly one minute of simultaneous spreading.
        while (!rotten.empty()) {
            int layerSize = rotten.size();
            bool rottedAnyThisLayer = false;

            for (int i = 0; i < layerSize; i++) {
                auto [r, c] = rotten.front();
                rotten.pop();

                for (int d = 0; d < 4; d++) {
                    int nr = r + dr[d];
                    int nc = c + dc[d];
                    if (nr < 0 || nr >= rows || nc < 0 || nc >= cols) continue;
                    if (grid[nr][nc] != 1) continue; // only spread onto fresh oranges

                    grid[nr][nc] = 2;       // mark rotten
                    freshCount--;
                    rotten.push({nr, nc});
                    rottedAnyThisLayer = true;
                }
            }

            if (rottedAnyThisLayer) minutes++;
        }

        // Step 3: if any fresh orange never got reached, it's impossible.
        return freshCount == 0 ? minutes : -1;
    }
};
```

### 1. Computer Networks (Conceptual)

Explain the TCP three-way handshake: what are the three messages exchanged, and why can't a connection be established with just one or two messages?

**Answer:**

The TCP three-way handshake is the process by which two hosts establish a reliable, bidirectional connection before exchanging application data. It consists of three messages:

1. **SYN** — The client sends a segment with the `SYN` flag set and an initial sequence number, `client_isn`. This says: "I want to start a connection, and my byte stream will start counting from `client_isn`."
2. **SYN-ACK** — The server responds with both the `SYN` and `ACK` flags set. The `ACK` part acknowledges the client's sequence number (`client_isn + 1`), and the `SYN` part carries the server's own initial sequence number, `server_isn`, saying: "I acknowledge your start, and here is where my byte stream starts counting from."
3. **ACK** — The client replies with just the `ACK` flag set, acknowledging the server's sequence number (`server_isn + 1`). At this point both sides have confirmed they can send and receive, and the connection moves to the `ESTABLISHED` state.

**Why not fewer messages?**

TCP is a **full-duplex** protocol — both sides can independently send data — so each direction of the connection needs its own agreed-upon starting sequence number, and each side needs proof that the other side actually received its proposed sequence number (not just sent it).

- With only **one message** (just a SYN), the client would tell the server its starting sequence number, but the server would have no way to communicate its own starting sequence number back, and the client would have no confirmation the server even received the SYN. The server also can't safely allocate resources for the connection without knowing the client can respond.
- With only **two messages** (SYN, then SYN-ACK), the server sends its sequence number in the SYN-ACK, but has no confirmation the client actually received it. If the client's reply is lost, the server would sit there believing a connection is established (having possibly allocated buffers/resources) while the client never got that far — this is exactly the vulnerability behind SYN-flood-style resource exhaustion, and why the third `ACK` is required to confirm the server's sequence number was received before either side commits fully.

The third message is what lets **both directions** be mutually confirmed: the client confirms the server's sequence number is acknowledged, closing the loop that two messages alone would leave open. This is also why the handshake is sometimes summarized as "SYN, SYN+ACK, ACK" rather than two independent one-way handshakes — combining the server's SYN and ACK into a single second message is an optimization that still requires the third message to fully close both directions.

### 2. DBMS (Comparison)

Compare a clustered index with a non-clustered (secondary) index in a relational database. How is data physically stored differently under each, and what does that imply for read and write performance?

**Answer:**

Both are data structures (almost always B-trees or B+trees in practice) that let the database engine avoid scanning the whole table to find rows matching a condition, but they differ fundamentally in what lives at the leaf level.

| Aspect | Clustered Index | Non-Clustered (Secondary) Index |
|---|---|---|
| Leaf node contents | The actual table row data itself | A pointer/reference to the row (a row ID, or the clustering key in engines like InnoDB) |
| Physical row order | Table rows are physically stored on disk sorted by the clustered index key | Table rows keep whatever order the clustered index (or heap) dictates; the secondary index is a separate structure |
| Count per table | Exactly one (the table's rows can only be sorted one way physically) | Many — a table can have several secondary indexes, one per frequently-filtered column |
| Lookup cost for indexed column | Single index traversal reaches the row directly | Index traversal finds a pointer, then a second lookup ("bookmark lookup") fetches the actual row — unless the query is "covered" by the index alone |
| Range query performance | Excellent for ranges on the key, since matching rows are physically adjacent on disk | Good for finding matching rows quickly, but if many rows match, the bookmark lookups to fetch full rows can involve scattered disk I/O |
| Write cost | Inserting/updating in the middle of the key range may require physically shifting rows (e.g., page splits) | Cheaper per index — only pointer entries need updating — but every additional secondary index adds its own write overhead on insert/update/delete |

**What this implies in practice:**

- Choose the clustered index key to match the column(s) most queried by range or by primary lookup (often the primary key), because it directly controls physical row layout — this is a one-time, table-wide decision.
- Secondary indexes are cheap to add for query flexibility (e.g., indexing a `email` or `created_at` column), but each one adds write-path overhead: every `INSERT`/`UPDATE`/`DELETE` must also update every secondary index on the table, so tables with heavy write traffic should avoid indexing columns that aren't actually queried.
- A query that only needs columns present in a secondary index (a "covering index") avoids the extra bookmark lookup entirely and can be nearly as fast as a clustered index hit — this is a common performance tuning technique.

### 3. OOP (Scenario)

You are designing a payment-processing module that must support multiple payment providers (credit card, PayPal, bank transfer), and new providers will be added over time. A junior developer proposes a single `PaymentProcessor` class with a `type` field and a large `if/else` (or `switch`) block inside `processPayment()` that branches on `type` to decide what logic to run. What OOP principle does this design violate, and how would you redesign it?

**Answer:**

This design violates the **Open/Closed Principle** (the "O" in SOLID): a class should be open for extension but closed for modification. Every time a new payment provider is added, the existing `PaymentProcessor` class must be edited — a new branch added to the `if/else`/`switch` — which risks breaking existing, already-tested logic for other providers and requires re-testing the whole class rather than just the new addition. It also tends to violate the **Single Responsibility Principle**, since one class ends up owning the logic for every provider instead of having one clear reason to change.

**Redesign using polymorphism:**

1. Define a common interface (or abstract base class), e.g.:
   ```cpp
   class PaymentMethod {
   public:
       virtual bool processPayment(double amount) = 0;
       virtual ~PaymentMethod() = default;
   };
   ```
2. Implement one concrete class per provider, each encapsulating only its own logic:
   ```cpp
   class CreditCardPayment : public PaymentMethod {
   public:
       bool processPayment(double amount) override { /* credit card specific logic */ }
   };
   class PayPalPayment : public PaymentMethod {
   public:
       bool processPayment(double amount) override { /* PayPal specific logic */ }
   };
   class BankTransferPayment : public PaymentMethod {
   public:
       bool processPayment(double amount) override { /* bank transfer specific logic */ }
   };
   ```
3. The calling code depends only on the `PaymentMethod` interface, not on any concrete type:
   ```cpp
   void checkout(PaymentMethod& method, double amount) {
       method.processPayment(amount);
   }
   ```
4. Adding a new provider (e.g., `CryptoPayment`) means **adding a new class** that implements `PaymentMethod` — no existing class is touched at all. This is typically paired with a **factory** (another OOP pattern) that maps a provider identifier (e.g., from a config or request) to the correct concrete instance, so the "branching" is isolated to one small, well-tested piece of construction logic instead of being smeared across the business logic.

**Why this matters:** beyond satisfying a principle for its own sake, this design means each provider's logic can be unit-tested in isolation, new providers ship without risking regressions in unrelated ones, and the code stays readable as the number of providers grows — a 3-branch `if/else` is manageable, but a 15-branch one spanning hundreds of lines becomes a maintenance and testing liability.
