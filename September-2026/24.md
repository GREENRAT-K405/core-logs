## DSA

### Question: Substring with Concatenation of All Words (Hashing/Maps — Hard)

You are given a string `s` and an array of strings `words`. All strings in `words` are of the **same length**. Return the starting indices of all substrings in `s` that are a concatenation of **each word in `words` exactly once**, in **any order**, and **without any intervening characters**.

You can return the answer in any order.

**Input format:**
- A string `s`.
- An array of strings `words`, where every element has the same length. `words` may contain duplicate words.

**Output format:**
- A list of integers: every starting index in `s` where a valid concatenated substring begins.

**Worked Examples:**

Example 1:
```
s = "barfoothefoobarman"
words = ["foo", "bar"]
```
Output: `[0, 9]`
Explanation: The substring starting at index `0` is `"barfoo"`, which is `"bar"` + `"foo"` (both words, each used once). The substring starting at index `9` is `"foobar"`, which is `"foo"` + `"bar"`. Both are valid concatenations of `words` in some order.

Example 2:
```
s = "wordgoodgoodgoodbestword"
words = ["word", "good", "best", "word"]
```
Output: `[]`
Explanation: `words` requires **two** occurrences of `"word"` (it appears twice in the array) plus one `"good"` and one `"best"` all concatenated back-to-back with no gaps. No 16-character window of `s` satisfies that exact multiset, so there is no match.

Example 3:
```
s = "barfoofoobarthefoobarman"
words = ["bar", "foo", "the"]
```
Output: `[6, 9, 12]`
Explanation: Starting at `6`: `"foobarthe"` = `"foo"+"bar"+"the"`. Starting at `9`: `"barthefoo"` = `"bar"+"the"+"foo"`. Starting at `12`: `"thefoobar"` = `"the"+"foo"+"bar"`. Each is a permutation of `words`.

**Constraints:**
- `1 <= s.length <= 10^4`
- `1 <= words.length <= 5000`
- `1 <= words[i].length <= 30`
- `s` and `words[i]` consist of lowercase English letters.
- All strings in `words` have the same length.

### Step-by-Step Walkthrough

**Approach — Fixed-Length Sliding Window per Starting Offset, with a Word-Count Hash Map**

The key observation is that every valid match is a concatenation of `numWords` words, each of length `wordLen`, so every valid window has a **fixed total length** `totalLen = numWords * wordLen`, and within that window we only ever need to look at it in `wordLen`-sized chunks — we never need to inspect an individual character in isolation.

1. **Precompute a frequency map of the target words.** Build `need[word] = count` from `words`, so we know exactly how many times each distinct word must appear in a valid window (this is what correctly handles duplicate words like the two `"word"`s in Example 2).
2. **Handle the alignment problem.** A valid window's word-chunks always start at positions that are `wordLen` apart from each other, but the window itself could start at `s[0]`, `s[1]`, `s[2]`, ... — any starting character. However, once we fix *where the first chunk boundary falls* (i.e., the starting offset modulo `wordLen`), all chunk boundaries for windows beginning at or after that offset are `wordLen` apart. So it's enough to run a sliding window starting at each offset `0, 1, ..., wordLen - 1` — any valid match must be caught by exactly one of these `wordLen` passes, since its own starting index has some remainder mod `wordLen`.
3. **For each offset, run a sliding window over chunk-sized steps:**
   - Maintain `left` (window start), a `have` hash map of chunk counts currently inside the window, and `matched` (how many chunks currently in the window are valid, counting toward but not exceeding `need`).
   - Move `right` forward one chunk (`wordLen` characters) at a time:
     - Extract the chunk `word = s[right..right+wordLen)`.
     - If `word` isn't in `need` at all, the window can't extend through it — reset: clear `have`, `matched = 0`, and jump `left` to right after this chunk.
     - Otherwise increment `have[word]` and `matched`. If `have[word]` now exceeds `need[word]` (too many copies of that word), shrink the window from the left — repeatedly drop the leftmost chunk (decrementing `have` and `matched`, advancing `left` by `wordLen`) until the excess is gone. This correctly handles duplicate words: we never allow more copies of a word in the window than `words` actually contains.
     - If `matched == numWords`, the window `[left, right + wordLen)` is an exact concatenation of all of `words` — record `left` as a valid answer. Then slide the window forward by one chunk (drop the leftmost chunk from `have`/`matched` and advance `left`) so the search can continue for further overlapping matches.
4. **Return all recorded starting indices** across all `wordLen` offset passes.

**Why it works:** By fixing the offset mod `wordLen`, every chunk boundary the sliding window ever looks at is one that a real match starting at that offset would also use — so we never mis-split a word across a chunk boundary. The `have`-vs-`need` count check with active shrinking guarantees we only ever accept a window whose multiset of chunks exactly equals the multiset of `words` (not a superset), which correctly rejects windows with too many copies of a repeated word.

**Complexity Analysis:**
- Let `n = s.length()`, `L = wordLen`, `k = numWords` (so `n` chunks of size `L` are examined per full pass over the string).
- **Time complexity:** `O(n * L)` overall. There are `L` offset passes; each pass slides across roughly `n / L` chunk positions, and each chunk comparison/hash operation costs `O(L)` (for hashing/substring extraction of an `L`-length string) — so each pass costs `O((n/L) * L) = O(n)`, and `L` passes give `O(n * L)` total. Since `L <= 30` by the constraints, this is comfortably efficient for `n <= 10^4`.
- **Space complexity:** `O(k * L)` for the `need` and `have` hash maps, which together hold at most `k` distinct word entries of length `L` each (plus `O(1)` extra for the sliding window pointers).

### C++ Code

```cpp
#include <iostream>
#include <vector>
#include <string>
#include <unordered_map>
using namespace std;

class Solution {
public:
    vector<int> findSubstring(string s, vector<string>& words) {
        vector<int> result;
        if (s.empty() || words.empty()) return result;

        int wordLen = words[0].size();
        int numWords = words.size();
        int totalLen = wordLen * numWords;
        int n = s.size();
        if (n < totalLen) return result;

        // Frequency map of the required words.
        unordered_map<string, int> need;
        for (const string& w : words) {
            need[w]++;
        }

        // One sliding-window pass per starting offset (0..wordLen-1).
        for (int offset = 0; offset < wordLen; ++offset) {
            unordered_map<string, int> have;
            int matched = 0;
            int left = offset;

            for (int right = offset; right + wordLen <= n; right += wordLen) {
                string word = s.substr(right, wordLen);

                auto it = need.find(word);
                if (it == need.end()) {
                    // Chunk isn't part of words at all: window can't span it.
                    have.clear();
                    matched = 0;
                    left = right + wordLen;
                    continue;
                }

                have[word]++;
                matched++;

                // Too many copies of this word: shrink from the left.
                while (have[word] > it->second) {
                    string leftWord = s.substr(left, wordLen);
                    have[leftWord]--;
                    matched--;
                    left += wordLen;
                }

                // Found a full valid concatenation window.
                if (matched == numWords) {
                    result.push_back(left);
                    // Slide window forward by one chunk to look for more matches.
                    string leftWord = s.substr(left, wordLen);
                    have[leftWord]--;
                    matched--;
                    left += wordLen;
                }
            }
        }

        return result;
    }
};

int main() {
    Solution sol;

    // Example 1
    {
        string s = "barfoothefoobarman";
        vector<string> words = {"foo", "bar"};
        vector<int> res = sol.findSubstring(s, words);
        cout << "Example 1: ";
        for (int v : res) cout << v << " ";
        cout << "(expected 0 9)" << endl;
    }

    // Example 2
    {
        string s = "wordgoodgoodgoodbestword";
        vector<string> words = {"word", "good", "best", "word"};
        vector<int> res = sol.findSubstring(s, words);
        cout << "Example 2: size=" << res.size() << " (expected 0)" << endl;
    }

    // Example 3
    {
        string s = "barfoofoobarthefoobarman";
        vector<string> words = {"bar", "foo", "the"};
        vector<int> res = sol.findSubstring(s, words);
        cout << "Example 3: ";
        for (int v : res) cout << v << " ";
        cout << "(expected 6 9 12)" << endl;
    }

    return 0;
}
```

- Example 1: `wordLen=3`, `numWords=2`, `need={"foo":1,"bar":1}`. Offset 0: at `right=0` chunk `"bar"` (matched=1); at `right=3` chunk `"foo"` (matched=2) → record `left=0`, slide to `left=3`. Chunk `"the"` at `right=6` isn't in `need` → reset, `left=9`. Chunk `"foo"` at `right=9` (matched=1), chunk `"bar"` at `right=12` (matched=2) → record `left=9`, slide to `left=12`. Chunk `"man"` not in `need` → reset. Final: `[0, 9]`. ✓

## CS Fundamentals

### 1. Operating Systems (Conceptual/Definition)

Explain the difference between a process and a thread, and why switching between two threads of the same process is cheaper than switching between two separate processes.

**Answer:**

A **process** is an independent, isolated unit of execution: it owns its own virtual address space (code, data, heap, stack), its own set of open file descriptors, and its own OS-level resources (signal handlers, security context, etc.). Two processes cannot directly see or corrupt each other's memory — the OS enforces isolation between them via separate page tables.

A **thread** is a unit of execution *within* a process. A process can have multiple threads, and all threads belonging to the same process **share** that process's address space, open files, and most other resources — but each thread has its own **stack**, its own **program counter/registers**, and its own **execution state** (running, ready, blocked), since each thread executes independently.

**Why context switching between threads (of the same process) is cheaper:**

A context switch — whether between threads or processes — requires the CPU to save the current execution context (registers, program counter, stack pointer) and load the next one. The extra cost specific to switching *processes* comes from:

1. **Address space / page table switch:** Switching processes means switching to a different virtual memory mapping (a different page table), which requires reloading the CPU's page-table base register (e.g., `CR3` on x86) and, critically, **flushing the TLB (Translation Lookaside Buffer)** — the cache of recent virtual-to-physical address translations — since the old TLB entries are meaningless under the new page table. This TLB flush means the next several memory accesses in the new process all suffer cache-miss-like penalties as the TLB refills, which is a real, measurable slowdown.
2. **Cache effects:** Switching processes also tends to cause more L1/L2 cache pollution since the new process's code/data working set is entirely different from the old one's, whereas threads of the same process are often (though not always) working on related data.

Because threads of the same process **share the same address space**, switching between them does **not** require a page table switch or a TLB flush — the OS only needs to save/restore the per-thread register state and stack pointer, which is a much smaller and cheaper operation.

**Why this matters:** This cost difference is the core reason multithreading is favored over multiprocessing for tasks that need frequent, fine-grained context switching or tight communication between concurrent units of work (e.g., a web server handling many simultaneous connections) — threads let you get concurrency with much lower switching overhead, at the cost of needing explicit synchronization (locks, etc.) since shared memory is both the benefit and the hazard.

### 2. OOP (Comparison)

Compare **inheritance** and **composition** as two ways to reuse code across classes. Give one concrete scenario where composition is clearly the better choice and explain why.

**Answer:**

| Aspect | Inheritance ("is-a") | Composition ("has-a") |
|---|---|---|
| Relationship modeled | A subclass **is a** specialized kind of its base class (e.g., `Dog` **is an** `Animal`). | A class **has a** reference to another object and delegates work to it (e.g., `Car` **has an** `Engine`). |
| Coupling | Tight — the subclass is coupled to the base class's implementation details; changes to the base class can silently break subclasses ("fragile base class problem"). | Loose — the containing class only depends on the composed object's interface, not its internals; the composed object can be swapped out freely. |
| Flexibility at runtime | Fixed at compile time — a class's parent(s) cannot change after the class is defined. | Flexible at runtime — you can swap in a different implementation of the composed dependency (even via dependency injection) without changing the containing class's code. |
| Reuse across unrelated hierarchies | Limited — reuse only flows down a single hierarchy (or via multiple inheritance, which brings its own complications like the diamond problem). | Unlimited — any class can compose any other class regardless of hierarchy, since it's just holding a reference/object. |
| Encapsulation | Weaker — a subclass typically has access to protected members of its parent, exposing more internal detail than necessary. | Stronger — the containing class only sees the composed object's public interface, nothing more. |

**Scenario where composition wins — a `Car` class needing an engine:**

Suppose you're modeling a `Car` class that needs an engine. It's tempting to write `class Car : public Engine` (inheritance), but a car **is not** an engine — it **has** one. Using inheritance here would be semantically wrong (a `Car` object shouldn't expose engine-internal methods like `igniteSparkPlug()` directly as if they were car behaviors) and would also lock you into one engine implementation baked into the class hierarchy.

With composition — `class Car { Engine* engine; ... }` — the `Car` simply holds a reference to an `Engine` (or better, an abstract `Engine` interface) and delegates to it (`engine->start()` inside `Car::start()`). This means:
- You can swap in a `PetrolEngine`, `DieselEngine`, or `ElectricMotor` at construction time (or even at runtime) without touching `Car`'s code at all, as long as they all implement the same `Engine` interface — a textbook application of the Strategy pattern and the "favor composition over inheritance" design principle.
- `Car` doesn't leak engine-internal details to its own callers, preserving encapsulation.

**Why this matters:** The general design guidance "favor composition over inheritance" (popularized by the Gang of Four) exists because inheritance hierarchies tend to become rigid and fragile as a codebase grows — deep hierarchies are hard to refactor, and forcing an "is-a" relationship where the real relationship is "has-a" or "uses-a" leads to awkward, leaky abstractions. Inheritance is still the right tool when there's a genuine, stable "is-a" relationship with shared behavior (e.g., a UI framework's `Button`, `Checkbox`, and `Slider` all genuinely **are** `Widget`s) — but composition should be the default choice when in doubt, since it keeps classes more loosely coupled and easier to change independently.

### 3. System Design Basics (Scenario/Applied)

You're designing a read-heavy public API (e.g., a product-catalog endpoint) that currently hits the primary database on every request and is starting to struggle under load. You decide to add a cache in front of it. Describe a caching strategy for this endpoint, including how you'd keep the cache from serving badly stale data after the underlying product data changes.

**Answer:**

**Choosing a caching strategy — cache-aside (lazy loading):**

For a read-heavy endpoint like a product catalog, the standard approach is **cache-aside** (also called lazy loading): on a read request, the application first checks the cache (e.g., Redis or Memcached); on a **cache hit**, it returns the cached value directly, skipping the database entirely; on a **cache miss**, it reads from the database, stores the result in the cache with a TTL (time-to-live), and then returns it. This is preferred over "cache-through" designs for read-heavy, infrequently-updated data because it only caches what's actually being requested (avoiding wasted memory on cold data) and is simple to reason about.

**Keeping the cache from serving badly stale data — a layered defense:**

1. **TTL (time-to-live) as a safety net:** Every cached entry gets an expiration time (e.g., 5–10 minutes for a product catalog). Even if nothing else invalidates the cache correctly, no entry can be stale for longer than the TTL — this bounds the worst-case staleness and guards against bugs in explicit invalidation.
2. **Active invalidation on writes:** Whenever the product data is updated (price change, stock update, etc.), the write path should explicitly **invalidate** (delete) the corresponding cache key(s) rather than waiting for the TTL to expire. This is far more precise than TTL alone — a customer sees a price change within milliseconds of the update instead of waiting up to the full TTL window. The write path becomes: update the database, then delete (not update) the cache key for that product — deleting rather than writing the new value into the cache avoids race conditions where a slow read that started before the write could overwrite the cache with stale data after the delete.
3. **Handling the race condition (write-then-read race):** Between "update DB" and "delete cache key," a concurrent read could still fetch stale data from the cache and even re-populate it after the delete, briefly reintroducing staleness. Mitigations include: a short TTL as a backstop (bounds how long that stale re-population can persist), or using a versioned/keyed cache invalidation approach (e.g., embedding a version number in the cache key that's bumped on writes, so old cache entries are simply never looked up again rather than needing active deletion).
4. **Cache stampede protection:** If a popular key expires and thousands of concurrent requests all miss the cache simultaneously, they could all hammer the database at once ("thundering herd"). This is mitigated with techniques like request coalescing (only one request per key is allowed to query the DB while others wait for that result) or jittering TTLs slightly per-key so mass-expiration is less likely.

**Why this matters:** No caching strategy eliminates staleness entirely — the real design question is always "how stale is acceptable, and for how long, given the product's tolerance for it?" A product catalog can usually tolerate a few seconds to a few minutes of staleness (a price update doesn't need to propagate instantly to every viewer), which is why TTL + explicit invalidation is a good fit here; a system with a much stricter consistency requirement (e.g., an account balance) would need a fundamentally different approach, such as skipping the cache for writes-then-immediate-reads or using write-through caching with strong consistency guarantees instead.
