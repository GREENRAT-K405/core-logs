### Question: Gas Station (Greedy — Medium)

**Problem Statement**

There are `n` gas stations arranged in a circle, numbered `0` to `n - 1`. You have a car with an unlimited gas tank. `gas[i]` is the amount of fuel available at station `i`, and `cost[i]` is the fuel needed to travel from station `i` to station `i + 1` (the last station connects back to station `0`).

You begin the journey with an empty tank at whichever station you choose. Return the index of the starting gas station from which you can travel around the entire circuit once in the clockwise direction, without running out of fuel. If no such starting station exists, return `-1`. It is guaranteed that if a solution exists, it is unique.

**Input/Output Format**

- Input: two integer arrays `gas` and `cost`, both of length `n`.
- Output: a single integer — the starting index, or `-1`.

**Examples**

1. `gas = [1,2,3,4,5]`, `cost = [3,4,5,1,2]` → Output: `3`.
   Starting at station 3: tank = 4 − 1 = 3 → station 4: 3 + 5 − 2 = 6 → station 0: 6 + 1 − 3 = 4 → station 1: 4 + 2 − 4 = 2 → station 2: 2 + 3 − 5 = 0. Tank never goes negative, and we're back at station 3.
2. `gas = [2,3,4]`, `cost = [3,4,3]` → Output: `-1`.
   Total gas = 9, total cost = 10. There isn't enough fuel in the system to complete the loop from any start, so no answer exists.
3. `gas = [3,3,4]`, `cost = [3,4,3]` → Output: `2`.
   Starting at station 2: tank = 4 − 3 = 1 → station 0: 1 + 3 − 3 = 1 → station 1: 1 + 3 − 4 = 0. Completes the circuit with the tank never dropping below zero.

**Constraints**

- `n == gas.length == cost.length`
- `1 <= n <= 10^5`
- `0 <= gas[i], cost[i] <= 10^4`
- Aim for O(n) time and O(1) extra space (an O(n²) brute force that tries every start is easy but too slow at this size).

### Step-by-Step Walkthrough

**Reframe the problem as a running balance.** Define `diff[i] = gas[i] - cost[i]`, the net fuel gained or lost by leaving station `i`. A start at station `s` succeeds exactly when every prefix sum of `diff`, taken cyclically starting at `s`, stays non-negative. So the question becomes: starting the partial-sum walk at which index does it never dip below zero?

**Necessary condition: total supply must cover total demand.** If `sum(diff) < 0` across all stations, then no matter where you start, you traverse every station exactly once over the full loop, so your tank's net change over the whole circuit is `sum(diff)`. If that total is negative, the tank is negative at the end of any full lap — impossible for *every* starting point simultaneously, so the answer is `-1`. This gives an easy first check, but it isn't yet a way to find the start.

**Key insight: if a total solution exists, greedily resetting on failure finds it in one pass.** Walk `i` from `0` to `n - 1`, keeping a running `currTank` that accumulates `diff[i]`, and a separate `totalTank` that accumulates the same values but is never reset (used only for the final feasibility check). Whenever `currTank` goes negative, it means: no station between the current tentative `start` and `i` (inclusive) can be a valid starting point either.

*Why the whole stretch is disqualified, not just `start` itself.* Suppose starting at `start` gets you to station `i` with a negative running tank, and consider any candidate `start' `strictly between `start` and `i`. Arriving at `start'` from `start`, the tank was some value `T ≥ 0` (otherwise we'd have reset earlier). Starting instead at `start'` means beginning with an empty tank, i.e. *less* fuel than you actually had at that point on the `start`-run (0 ≤ T). Since the run from `start'` to `i` is the same sequence of `diff` values either way, and it drove the tank negative even with the extra `T` fuel from starting earlier, it will *certainly* drive it negative starting from 0 at `start'`. So every index in `(start, i]` can be safely skipped, and we jump the candidate start straight to `i + 1`, resetting `currTank` to 0.

**Putting it together.** After the single pass, if `totalTank >= 0`, a solution exists — and because of the elimination argument above, the last surviving `start` value is the only candidate left standing, hence *the* answer (the problem guarantees uniqueness when a solution exists). If `totalTank < 0`, no start works, so return `-1`.

**Complexity.**
- Time: O(n) — one linear pass, no nested loops or backtracking.
- Space: O(1) — only a handful of running counters.

### C++ Code

```cpp
#include <vector>
using namespace std;

int canCompleteCircuit(vector<int>& gas, vector<int>& cost) {
    int n = gas.size();
    long long totalTank = 0;  // net fuel over the whole circuit (feasibility check)
    long long currTank = 0;   // net fuel since the current candidate start
    int start = 0;

    for (int i = 0; i < n; i++) {
        int diff = gas[i] - cost[i];
        totalTank += diff;
        currTank += diff;

        if (currTank < 0) {
            // Every index from `start` through `i` is eliminated: none of them
            // could reach here without already going negative, or going
            // negative here rules them out too. Try the very next station.
            start = i + 1;
            currTank = 0;
        }
    }

    return (totalTank >= 0) ? start : -1;
}
```

## CS Fundamentals

### 1. Operating Systems (Conceptual/Definition)

What are the four necessary conditions for deadlock, and for each one, name a concrete OS or application-level mechanism that prevents it from holding?

**Answer:**

A deadlock is a cycle of processes each waiting on a resource the next one in the cycle holds, with nobody able to proceed. Coffman (1971) showed all four of the following must hold **simultaneously** for deadlock to occur — breaking any single one makes deadlock structurally impossible, which is why prevention strategies target one condition rather than trying to detect cycles at runtime.

**1. Mutual exclusion** — at least one resource is held in a non-shareable mode (only one process can use it at a time).
*Prevention:* Make the resource shareable where the semantics allow it. A read-only file can be opened by many readers simultaneously with a shared (reader) lock instead of an exclusive one; spooling (as with printers) turns an exclusive device into a shareable queue. This isn't always possible — you can't make a write lock on a bank account "shareable" without breaking correctness — so this condition is the hardest to eliminate in general.

**2. Hold and wait** — a process holds at least one resource while blocked waiting to acquire another.
*Prevention:* Require processes to request **all** the resources they will need atomically, up front, before running (or release everything before requesting more). Some database engines and job schedulers do exactly this — a transaction declares its lock set, and the lock manager grants it all-or-nothing. The downside is reduced concurrency: you may hold resources far longer than you're actively using them, and it requires knowing all resource needs in advance, which isn't always practical.

**3. No preemption** — a resource can only be released voluntarily by the process holding it; it cannot be forcibly taken away.
*Prevention:* Allow the OS (or runtime) to preempt a resource from a waiting process and give it to another. Modern OS schedulers preempt CPU time this way (that's why CPU deadlock via this condition essentially never happens); optimistic concurrency control in databases does the analogous thing by aborting and rolling back a transaction instead of leaving it holding locks indefinitely. This is workable for state that can be checkpointed and restored (CPU registers, transaction state) but not for resources like a half-written file or a physical device mid-operation.

**4. Circular wait** — there exists a cycle of processes `P1 → P2 → ... → Pn → P1` where each `Pi` is waiting on a resource held by `P(i+1)`.
*Prevention:* Impose a **global total ordering** on all resource types, and require every process to request resources in strictly increasing order. If every process acquires resource type `A` before `B` before `C`, a cycle becomes mathematically impossible — a cycle would require some process to request a lower-ordered resource while holding a higher-ordered one, violating the ordering rule. This is the most commonly used prevention technique in real systems, e.g. always locking database rows in primary-key order, or the classic "always pick up the lower-numbered fork first" solution to the dining philosophers problem.

**Why this matters in practice:** detection-and-recovery (letting deadlocks happen, then finding and breaking cycles, as some database engines do via a wait-for graph) trades prevention overhead for occasional abort/retry cost. Prevention trades some concurrency or flexibility for the guarantee that deadlock simply cannot occur — the right choice depends on how costly a rollback is versus how much the ordering constraint restricts useful concurrency.

### 2. Computer Networks (Comparison)

Compare TCP and UDP, and explain why a modern protocol like QUIC (used for HTTP/3) is built on top of UDP instead of TCP, despite UDP offering none of TCP's reliability guarantees.

**Answer:**

**The core trade-off.** TCP is connection-oriented and provides reliable, ordered, flow-controlled, congestion-controlled byte-stream delivery: it retransmits lost segments, reorders out-of-sequence ones, and slows down under network congestion. UDP is connectionless and provides none of that — it's a best-effort, fire-and-forget datagram service. The cost of TCP's guarantees is *latency and head-of-line blocking*; the cost of UDP's simplicity is that *the application* must handle loss, ordering, and congestion itself if it needs them.

| | TCP | UDP |
| --- | --- | --- |
| Connection | Handshake required (3-way SYN/SYN-ACK/ACK) | None — send immediately |
| Reliability | Guaranteed delivery via ACKs + retransmission | None — packets can be lost silently |
| Ordering | Guaranteed (sequence numbers) | Not guaranteed |
| Congestion control | Built in (slow start, AIMD, etc.) | None (application must implement if needed) |
| Header overhead | 20+ bytes | 8 bytes |
| Typical use | HTTP/1.1, HTTP/2, file transfer, email | DNS, video/voice calls, gaming, HTTP/3 (via QUIC) |

**Why QUIC chose UDP as its foundation.** This looks backwards at first — QUIC re-implements reliability, ordering, and congestion control, all of which TCP already provides for free. The reason is **head-of-line blocking at the transport layer**, and the fact that TCP is baked into kernels and middleboxes in ways that are effectively frozen in place.

TCP delivers one ordered byte stream. If a single packet is lost, the kernel withholds *every* later byte — even bytes belonging to logically independent HTTP requests multiplexed over the same connection — until the lost packet is retransmitted and arrives. HTTP/2 multiplexes many streams over one TCP connection specifically to avoid opening many connections, but that means one lost packet stalls all of those streams simultaneously, even though most of them had nothing to do with the lost data.

QUIC solves this by implementing its own reliability **per stream** rather than per connection, entirely in user space on top of UDP's raw, unordered datagrams. A packet loss affecting stream A's data no longer blocks delivery of already-arrived data for streams B and C — each stream's ordering and retransmission is tracked independently. This is impossible to retrofit onto TCP because TCP's ordering guarantee is a single global sequence number space enforced inside the OS kernel, not something an application can partially opt out of.

**A second, more practical reason: deployability.** TCP's congestion control, flow control, and handshake behavior live inside OS kernels, which upgrade slowly, and are frequently "optimized" or filtered by middleboxes (NAT devices, firewalls, load balancers) that assume TCP semantics. Changing TCP's behavior at internet scale is a multi-year, multi-vendor effort. UDP, by contrast, is mostly left alone by middleboxes as an opaque datagram carrier — QUIC can innovate entirely in user-space library code (shipped inside the browser and server binaries) and iterate as fast as an application, not as slow as an OS kernel. QUIC also folds the TCP handshake and the TLS handshake into a single combined round trip (0-RTT on repeat connections), something that's straightforward to design from scratch on UDP but very hard to retrofit onto TCP's fixed wire format.

**The general lesson:** UDP isn't "the unreliable one to avoid" — it's the primitive that lets you build exactly the reliability semantics you need (or none at all), whereas TCP hands you one fixed, kernel-enforced bundle of guarantees that isn't always the right shape for the application.

### 3. System Design Basics (Scenario/Applied)

You're scaling a distributed cache from 4 servers to 5 by adding one more machine. With plain `hash(key) % N` routing, almost every key remaps to a different server the moment `N` changes, causing a massive wave of cache misses. Explain why this happens and how consistent hashing avoids it.

**Answer:**

**Why `% N` routing collapses on resize.** With modulo hashing, a key's server assignment is `hash(key) % N`. Changing `N` from 4 to 5 changes the divisor in that formula for *every single key*, not just a fraction of them — a key that mapped to server `hash(key) % 4 = 2` might now map to `hash(key) % 5 = 4`, a completely unrelated server, with no relationship to its old assignment. There's no structural reason nearby hash values keep the same owner after resize; the mapping is essentially re-randomized. In the worst case, only keys where `hash(key) % 20` (the LCM-ish overlap) happens to coincide keep their server — roughly only `1/N` of keys stay put, and `(N-1)/N` of them move. At scale, that's a synchronized flood of cache misses hitting the database all at once, exactly the kind of thundering-herd event caching exists to prevent.

**Consistent hashing's core idea: hash servers onto the same ring as keys.** Instead of hashing a key into a bucket index `[0, N)`, both servers and keys are hashed into the same large fixed circular space (e.g. `[0, 2^32)`, visualized as a ring). A key belongs to the **first server encountered walking clockwise** from the key's position on the ring. This decouples the assignment rule from `N` entirely — it depends only on relative positions on a ring that doesn't change shape when a server is added or removed.

**Why this bounds the remapping.** Adding a new server `S_new` at some point on the ring only affects the *arc* of key-space between `S_new` and the next server counter-clockwise from it (its predecessor's territory). Every key that previously belonged to that one predecessor and falls between the predecessor and `S_new` now belongs to `S_new` instead; every other key on the ring — the vast majority — is completely untouched, because its nearest clockwise server hasn't changed. With `N` roughly-evenly-spaced servers, adding one more remaps only about `1/N` of keys (the ones stolen from its immediate predecessor), instead of `(N-1)/N` of them. Removing a server is symmetric: only the keys it owned move, to its clockwise successor.

**The uneven-load wrinkle, and the fix.** A single hash point per physical server means the arcs between servers are randomly sized — some servers can end up owning a much larger slice of the ring than others just by the luck of where their hash landed, and losing one server dumps its *entire* arc onto exactly one neighbor. The standard fix is **virtual nodes**: each physical server is hashed onto the ring at many points (e.g. 100–200 virtual replicas), each independently placed. This (a) averages out load more evenly since each server now owns many small, scattered arcs rather than one large contiguous one, and (b) means that when a server leaves, its load is spread across many different neighbors instead of piling entirely onto one — smoothing both the steady-state load distribution and the impact of scaling events.

**Why this matters for the scenario:** going from 4 to 5 servers with virtual-node consistent hashing remaps roughly 20% of keys — exactly the keys logically owned by the new server's arcs — instead of the ~80% churn plain modulo hashing would cause, so the database sees a proportional, bounded increase in load rather than a stampede.
