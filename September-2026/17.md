### Question: Kth Largest Element in an Array (Sorting/Searching — Medium)

Given an integer array `nums` and an integer `k`, return the `k`th largest element in the array.

Note that it is the `k`th largest element **in sorted order**, not the `k`th distinct element. In other words, if you sorted `nums` in descending order, the answer is the element at index `k - 1`.

**Input format:**
- An integer array `nums`.
- An integer `k` (1-indexed rank from the largest element).

**Output format:**
- A single integer: the `k`th largest value in `nums`.

**Worked Examples:**

1. `nums = [3,2,1,5,6,4]`, `k = 2` → sorted descending: `[6,5,4,3,2,1]` → 2nd largest = `5`.
2. `nums = [3,2,3,1,2,4,5,5,6]`, `k = 4` → sorted descending: `[6,5,5,4,3,3,2,2,1]` → 4th largest = `4`.
3. `nums = [1]`, `k = 1` → only one element → `1`.

**Constraints:**
- `1 <= k <= nums.length <= 10^5`
- `-10^4 <= nums[i] <= 10^4`

---

### Step-by-Step Walkthrough

**Naive approach:** Sort `nums` in descending order and return `nums[k-1]`. This works and is `O(n log n)` time — correct, but does more work than necessary since we don't actually need the *entire* array sorted, only to know which element lands at rank `k`.

**Better approach — Quickselect (a variant of Quicksort's partitioning):**

The key insight is that we don't need to fully sort the array to find one specific rank — we only need to correctly place *one* element (the one at the target rank) and can discard the half of the array we don't care about at each step, similar to binary search.

Converting "`k`th largest" to a 0-indexed position from the *smallest* end makes the partitioning code simpler: the `k`th largest element is the element that ends up at index `n - k` once the array is fully sorted in **ascending** order (e.g. for `n=6, k=2`, index `6-2=4`, which holds the 2nd largest value once sorted ascending).

1. **Partition step (Lomuto scheme):** Pick a pivot value (we pick it at a **random** index and swap it to the end first — this avoids the classic `O(n^2)` worst case that a fixed pivot choice triggers on already-sorted or adversarially crafted input). Walk through the subarray, moving every element smaller than the pivot to the front, and finally place the pivot itself right after them. The pivot's final resting index, `pivotIndex`, is now exactly where it would sit if the whole array were sorted.
2. **Compare `pivotIndex` to the target index `n - k`:**
   - If `pivotIndex == target`, we're done — that's our answer.
   - If `pivotIndex < target`, the answer lies to the right, so recurse (or loop) only on the right subarray `[pivotIndex + 1, right]`.
   - If `pivotIndex > target`, the answer lies to the left, so recurse only on `[left, pivotIndex - 1]`.
3. Repeat until `pivotIndex == target`, then return `nums[target]`.

Because we only ever recurse into **one side** of the partition (unlike Quicksort, which recurses into both), the work shrinks geometrically on average, giving a much better expected running time than full sorting.

**Why it works:** A partition step guarantees that after it runs, the pivot is in its correct sorted position relative to everything else — every element to its left is `<=` pivot and everything to its right is `>=` pivot. That is precisely the definition of "this element's rank is fixed," so once `pivotIndex` equals our target rank, no further work is needed — we've found the exact element that would occupy that slot in the fully sorted array, without sorting the rest.

**Complexity Analysis:**
- **Time complexity:** `O(n)` average case (each partition pass roughly halves the remaining search space: `n + n/2 + n/4 + ... ≈ 2n`). Worst case `O(n^2)` if partitioning happens to be maximally unbalanced on every step, but random pivot selection makes this exponentially unlikely in practice.
- **Space complexity:** `O(1)` extra space for the iterative version (partitioning is done in-place); `O(log n)` average / `O(n)` worst case if implemented recursively, due to the call stack.
- **Alternative:** A min-heap of size `k` gives a guaranteed `O(n log k)` with no worst-case blowup, which is preferable when a hard time guarantee matters more than average-case speed.

### C++ Code

```cpp
#include <iostream>
#include <vector>
#include <cstdlib>
#include <ctime>
using namespace std;

class Solution {
public:
    int findKthLargest(vector<int>& nums, int k) {
        int n = nums.size();
        // Kth largest == element at index (n - k) once sorted ascending.
        int target = n - k;
        int left = 0, right = n - 1;

        while (left <= right) {
            int pivotIndex = partition(nums, left, right);
            if (pivotIndex == target) {
                return nums[pivotIndex];
            } else if (pivotIndex < target) {
                left = pivotIndex + 1;  // answer is in the right half
            } else {
                right = pivotIndex - 1; // answer is in the left half
            }
        }
        return -1; // unreachable given valid input constraints
    }

private:
    // Lomuto partition scheme with a randomly chosen pivot to avoid
    // worst-case O(n^2) behavior on sorted/adversarial input.
    int partition(vector<int>& nums, int left, int right) {
        int randomIndex = left + rand() % (right - left + 1);
        swap(nums[randomIndex], nums[right]); // move pivot to the end
        int pivot = nums[right];

        int storeIndex = left; // boundary of "elements < pivot"
        for (int i = left; i < right; ++i) {
            if (nums[i] < pivot) {
                swap(nums[i], nums[storeIndex]);
                storeIndex++;
            }
        }
        swap(nums[storeIndex], nums[right]); // place pivot in its final spot
        return storeIndex;
    }
};

int main() {
    srand(static_cast<unsigned>(time(nullptr)));
    Solution sol;

    vector<int> nums1 = {3, 2, 1, 5, 6, 4};
    cout << "Example 1: " << sol.findKthLargest(nums1, 2) << " (expected 5)" << endl;

    vector<int> nums2 = {3, 2, 3, 1, 2, 4, 5, 5, 6};
    cout << "Example 2: " << sol.findKthLargest(nums2, 4) << " (expected 4)" << endl;

    vector<int> nums3 = {1};
    cout << "Example 3: " << sol.findKthLargest(nums3, 1) << " (expected 1)" << endl;

    return 0;
}
```

**Trace against the examples:**
- Example 1: `n=6, k=2` → `target = 4`. Partitioning repeatedly narrows the search until index 4 holds `5`, matching the expected 2nd largest value. ✓
- Example 2: `n=9, k=4` → `target = 5`. After partitioning converges, index 5 in the ascending-sorted arrangement holds `4`, the 4th largest value (duplicates of `5` and `2`/`3` are handled correctly since Lomuto partitioning only compares against the pivot value, not distinctness). ✓
- Example 3: `n=1, k=1` → `target = 0`, and the single-element array trivially returns `1`. ✓

## CS Fundamentals

### 1. Operating Systems (Conceptual/Definition)

What is virtual memory, and what problem does it solve? Explain the role of paging and a page table in implementing it.

**Answer:**

Virtual memory is an abstraction provided by the operating system (with hardware support from the Memory Management Unit, MMU) that gives each process the illusion of having its own large, contiguous, private address space, independent of how much physical RAM is actually installed and independent of what other processes are doing.

**The problem it solves:**
- **Isolation:** Without virtual memory, processes would need to reference physical RAM addresses directly, meaning one buggy or malicious process could read or overwrite another process's memory. Virtual memory gives each process its own address space, so one process cannot accidentally (or deliberately) touch another's memory.
- **Overcommitment / running programs larger than physical RAM:** A process's total virtual address space can exceed the amount of physical RAM installed, because not all of it needs to be resident in RAM at once.
- **Simplifying programming and linking:** Every process can assume it starts at the same base address and has a full, contiguous address range, so compilers and linkers don't need to know how much physical memory is available or where other processes are loaded.

**How paging implements it:**
- Both virtual and physical memory are divided into fixed-size chunks: **pages** (virtual side) and **frames** (physical side), typically 4 KB each.
- A per-process **page table** maps virtual page numbers to physical frame numbers. When a program accesses a virtual address, the MMU splits it into a page number and an offset, looks up the page number in the page table to get the corresponding physical frame, and combines that frame with the offset to get the real physical address — all transparently to the running program.
- Not every virtual page needs a physical frame at all times. A page table entry has a **valid/present bit**; if a process accesses a page marked "not present," a **page fault** occurs, trapping into the OS, which loads the required page from disk (the swap space/page file) into a free physical frame, updates the page table, and resumes the process. This is called **demand paging** — pages are only brought into RAM when actually needed, rather than loading an entire program up front.
- When RAM is full and a new page must be brought in, the OS evicts an existing page using a replacement policy (e.g., Least Recently Used) — writing it back to disk first if it was modified ("dirty").

**Why this matters:** Virtual memory with paging is what allows modern multitasking operating systems to run many processes concurrently, each believing it has the whole machine to itself, safely isolated from each other, while still letting the OS overcommit RAM and swap less-used pages to disk. It's also the mechanism underlying features like memory-mapped files and copy-on-write (used to make `fork()` cheap).

### 2. Computer Networks (Comparison)

Compare TCP and UDP as transport-layer protocols. For each, describe how it works at a high level and give a real-world example of an application that would prefer it, explaining why.

**Answer:**

| Aspect | TCP (Transmission Control Protocol) | UDP (User Datagram Protocol) |
|---|---|---|
| Connection model | Connection-oriented — requires a handshake (the 3-way SYN / SYN-ACK / ACK handshake) before data transfer, and an explicit teardown afterward. | Connectionless — a sender just fires datagrams at a destination with no setup or teardown. |
| Reliability | Reliable — every segment is acknowledged; lost segments are automatically retransmitted; data is guaranteed to arrive (as long as the connection stays up) exactly once and in order. | Unreliable — no acknowledgments, no retransmission, no ordering guarantee. Packets can be lost, duplicated, or arrive out of order, and the application must handle that itself if it cares. |
| Ordering | Guaranteed — the receiver's TCP stack reorders segments using sequence numbers before handing data to the application. | Not guaranteed — datagrams may arrive in a different order than sent. |
| Flow/congestion control | Built in — uses a sliding window for flow control (so a fast sender doesn't overwhelm a slow receiver) and algorithms like slow start / congestion avoidance to back off when the network is congested. | None — UDP just sends as fast as the application asks; any congestion control has to be implemented by the application itself, if at all. |
| Overhead | Higher — larger header (20+ bytes), handshake latency, acknowledgment traffic. | Lower — minimal 8-byte header, no handshake, no acknowledgments. |
| Typical use cases | Web browsing (HTTP/HTTPS), file transfer (FTP), email (SMTP) — anything where correctness and completeness of the data matter more than raw speed. | DNS lookups, live video/audio streaming, online gaming, VoIP — anything where low latency matters more than occasionally losing a packet. |

**Example — why an application prefers one over the other:**
- A **file download** (e.g., downloading a PDF over HTTPS) needs **TCP**: if even one byte is missing or out of order, the file is corrupted. The extra latency from acknowledgments and retransmission is an acceptable price for guaranteed, correct, in-order delivery.
- A **live video call** prefers **UDP**: if one video frame's packet is lost, retransmitting it would arrive too late to be useful anyway (the call has already moved on to the next frame) — it's better to just drop that frame and keep playing forward smoothly than to stall the whole stream waiting for a retransmission. Low, consistent latency matters more than perfect completeness.

**Why this matters:** Understanding the TCP/UDP tradeoff is fundamental to designing networked systems — it's the first decision point when choosing a transport layer, and it directly reflects a classic systems tradeoff between reliability/ordering guarantees and latency/overhead. Some protocols even build a reliability layer on top of UDP when they want to customize the tradeoff themselves (e.g., QUIC, which HTTP/3 is built on).

### 3. DBMS (Scenario/Applied)

You have a `users` table with 50 million rows and a query `SELECT * FROM users WHERE email = ?` that's running slowly, doing a full table scan on every call. Walk through how you'd diagnose and fix this, and explain any tradeoffs of your fix.

**Answer:**

**Step 1 — Confirm the diagnosis.** Run `EXPLAIN` (or `EXPLAIN ANALYZE`) on the query. If the query plan shows a "Seq Scan" / "Full Table Scan" on `users` instead of an index lookup, that confirms the database has no efficient way to jump straight to matching rows — it's reading and checking all 50 million rows on every call.

**Step 2 — Fix: add an index on `email`.**
```sql
CREATE INDEX idx_users_email ON users(email);
```
Most relational databases implement this as a **B-tree index** by default. A B-tree keeps entries sorted and balanced, so looking up a value takes `O(log n)` disk/page reads instead of `O(n)` — for 50 million rows, that's the difference between scanning tens of millions of rows and a handful of index page lookups (roughly 3-4 levels deep for a table this size). After creating the index, `EXPLAIN` should now show an "Index Scan" (or "Index Only Scan" if the query only needs indexed columns) instead of a sequential scan.

**Step 3 — Consider a uniqueness constraint.** If `email` is meant to be unique per user (which it almost always is for a `users` table), use `CREATE UNIQUE INDEX` instead of a plain index. This both speeds up the lookup and enforces a business rule at the database level (no two users can register with the same email), rather than relying solely on application-level checks that could race under concurrent inserts.

**Tradeoffs of adding the index:**
- **Write cost:** Every `INSERT`, `UPDATE` (of the `email` column), or `DELETE` now also has to update the index's B-tree structure, not just the table's heap storage. For a write-heavy table this can meaningfully slow down writes, though for a `users` table (read far more often than written) this is almost always a good trade.
- **Storage cost:** An index is a separate on-disk structure that duplicates the indexed column's data (plus row pointers), so it consumes additional disk space — typically a small fraction of the table's size for a single-column index, but it adds up if many indexes are added carelessly.
- **Index maintenance:** Indexes can become fragmented over time with heavy write/delete churn, and periodically need to be rebuilt/reorganized (`REINDEX` in Postgres, `OPTIMIZE TABLE` in MySQL) to stay efficient.
- **`SELECT *` specifically:** Since the query selects all columns, not just `email`, the database still needs to do a lookup in the index followed by a "heap fetch" to retrieve the rest of the row's columns (unless a covering index is used). This is still vastly faster than a full scan, but worth noting — if the query only needed a couple of columns, a **covering index** (`CREATE INDEX ... ON users(email) INCLUDE (name, created_at)`) could let the database satisfy the query straight from the index without touching the table at all.

**Why this matters:** Indexing is the single highest-leverage tool for query performance in a relational database, but it isn't free — every index added is a tradeoff between read speed and write speed/storage, so production systems index deliberately (based on actual query patterns, e.g. from a slow-query log) rather than indexing every column defensively.
