### Question: Single Number II (Bit Manipulation — Medium)

Given an integer array `nums` where every element appears **exactly three times**, except for one element which appears **exactly once**, find and return that single element.

Your solution must run in **linear time** and use only **constant extra space** (no hash maps or sorting).

**Input format:**
- An integer array `nums` of length `n`, where `n >= 1`.

**Output format:**
- The single integer that appears exactly once.

**Worked Examples:**

1. `nums = [2,2,3,2]` → `3` (2 appears three times, 3 appears once).
2. `nums = [0,1,0,1,0,1,99]` → `99` (0 and 1 each appear three times, 99 appears once).
3. `nums = [-2,-2,1,1,-3,1,-3,-3,-4,-2]` → `-4` (both -2 and -3 appear three times, 1 appears three times, -4 appears once — negative numbers must be handled correctly).

**Constraints:**
- `1 <= nums.length <= 3 * 10^4`
- `-2^31 <= nums[i] <= 2^31 - 1`
- Each element in `nums` appears exactly three times except for one element which appears exactly once.

---

### Step-by-Step Walkthrough

**Why XOR alone (the "Single Number I" trick) doesn't work here**

For the classic variant where every element appears *twice* except one, XOR-ing everything together works because `x ^ x = 0`, so all paired elements cancel out and only the lone element survives. Here elements appear **three** times, and XOR-ing a value with itself three times just leaves the value itself (`x ^ x ^ x = x`), so plain XOR does **not** cancel the triples — we need a mechanism that tracks counts modulo 3, not modulo 2.

**Approach — track "seen count mod 3" per bit using two accumulator variables**

The key idea: look at each of the 32 bit positions independently. For any bit position, across the whole array, the number of `1`s at that position contributed by the tripled numbers is always a multiple of 3. So if we count (per bit) how many `1`s appear at that position and take that count `mod 3`, whatever remains must come from the single unique number's bit at that position.

Rather than literally keeping 32 counters, we can simulate "count mod 3" for *all* bit positions in parallel using two integers, `ones` and `twos`, treated as a tiny finite-state machine per bit:
- `ones` holds the bits that have been seen `1 time mod 3` so far.
- `twos` holds the bits that have been seen `2 times mod 3` so far.
- Implicitly, a bit seen `0 times mod 3` is absent from both.

For each incoming number `num`, we update both accumulators:
```
ones = (ones ^ num) & ~twos
twos = (twos ^ num) & ~ones   // uses the just-updated ones
```

Reading this as a per-bit state transition (state = 0, 1, or 2 counts mod 3, encoded as `(twos_bit, ones_bit)`):
- State `(0,0)`, bit arrives → new count is 1 → goes to `(0,1)`. `ones` picks it up via XOR; `twos` stays clear because `~ones` after the update masks it out.
- State `(0,1)`, bit arrives → new count is 2 → goes to `(1,0)`. `ones` XORs back to 0 (since it was already 1), and `twos` picks it up via its own XOR, masked by the *new* `~ones` (which is now 0 there, so the mask allows it).
- State `(1,0)`, bit arrives → new count is 3 ≡ 0 → goes to `(0,0)`. `ones` XORs 0→1 momentarily is prevented by `& ~twos` (twos is still 1 at that point, so the mask zeroes it), then `twos` XORs 1→0.
- If no bit arrives at a position, both `ones` and `twos` are left untouched at that bit (XOR-ing with 0 does nothing).

After processing all `n` numbers, every bit belonging to a number that appeared exactly 3 times has cycled `(0,0) → (0,1) → (1,0) → (0,0)` and lands back at 0 in both `ones` and `twos`. The single unique number appeared once, so its bits are wherever they'd be after **one** step from `(0,0)`, i.e. exactly in `ones`. So **`ones` at the end is the answer.**

**Complexity Analysis:**
- **Time complexity:** `O(n)` — one constant-time bitwise update per array element, no nested loops over bit widths needed (the two-variable trick handles all 32 bits simultaneously in each step).
- **Space complexity:** `O(1)` — only the two accumulator integers `ones` and `twos` are used, regardless of `n`.

Two's-complement negative numbers work correctly with this trick automatically: in C++, `int` is a fixed-width two's-complement type, so bitwise `^`, `&`, and `~` operate uniformly across the sign bit exactly like any other bit position — no special-casing is needed for negative inputs.

---

### C++ Code

```cpp
#include <iostream>
#include <vector>
using namespace std;

class Solution {
public:
    // Returns the element that appears exactly once, given every other
    // element appears exactly three times. O(n) time, O(1) space.
    int singleNumber(vector<int>& nums) {
        int ones = 0, twos = 0;

        for (int num : nums) {
            // Bit goes into 'ones' only if it wasn't already pending in 'twos'.
            ones = (ones ^ num) & ~twos;
            // Bit goes into 'twos' only if it wasn't just placed into 'ones'.
            twos = (twos ^ num) & ~ones;
        }

        // Bits that cycled through all three occurrences cancel back to 0
        // in both accumulators; only the once-seen number's bits survive in 'ones'.
        return ones;
    }
};

int main() {
    Solution sol;

    // Example 1
    vector<int> n1 = {2, 2, 3, 2};
    cout << sol.singleNumber(n1) << " (expected 3)" << endl;

    // Example 2
    vector<int> n2 = {0, 1, 0, 1, 0, 1, 99};
    cout << sol.singleNumber(n2) << " (expected 99)" << endl;

    // Example 3 (negative numbers)
    vector<int> n3 = {-2, -2, 1, 1, -3, 1, -3, -3, -4, -2};
    cout << sol.singleNumber(n3) << " (expected -4)" << endl;

    return 0;
}
```

**Trace against Example 1 (`[2,2,3,2]`):**
- Start: `ones=0, twos=0`.
- `num=2` (`010`): `ones=(0^2)&~0=2`; `twos=(0^2)&~2=0`. → `ones=2, twos=0`.
- `num=2`: `ones=(2^2)&~0=0`; `twos=(0^2)&~0=2`. → `ones=0, twos=2`.
- `num=3` (`011`): `ones=(0^3)&~2 = 3 & ~2 = 001 = 1`; `twos=(2^3)&~1 = 1 & ~1 = 0`. → `ones=1, twos=0`.
- `num=2`: `ones=(1^2)&~0 = 3`; `twos=(0^2)&~3 = 2 & ~3 = 0`. → `ones=3, twos=0`.
- Final `ones = 3`. ✓ Matches expected output.

### 1. DBMS (Conceptual/Definition)

What is a database index, and specifically why does a **B+ tree** (rather than a plain binary search tree or a hash table) make such a good default structure for a general-purpose index? Mention what you give up in exchange for faster reads.

**Answer:**

A **database index** is an auxiliary data structure, stored alongside a table, that maps values of one or more columns to the physical location(s) of the matching rows — its purpose is to let the query engine find matching rows without scanning every row in the table (a "full table scan"), trading extra storage and write overhead for much faster reads on the indexed columns.

**Why a B+ tree specifically:**
- **Matches disk/page-based I/O:** a B+ tree is a wide, shallow, balanced tree where each node corresponds to one disk page (typically 4–16 KB) and holds many keys (often hundreds). Because disk (and even SSD) access is dominated by the cost of each I/O operation rather than raw comparisons, minimizing the *number of page reads* matters far more than minimizing comparisons — and a B+ tree's high fan-out keeps the tree only 3–4 levels deep even for millions of rows, versus `O(log2 n)` *levels* (and thus disk reads) for a plain binary search tree, which is far too deep and would need one disk read per level.
- **All data lives in the leaves, and leaves are linked:** unlike a plain B-tree (which can store data in internal nodes too), a B+ tree keeps all actual row pointers/values only in leaf nodes, and the leaves are linked together in a sorted doubly-linked list. This makes **range queries** (`WHERE age BETWEEN 20 AND 30`, `ORDER BY`) very efficient: once you descend to the first matching leaf, you can just walk the leaf-level linked list forward instead of re-traversing the tree.
- **Stays balanced under insertion/deletion:** like other balanced trees, B+ trees rebalance (via node splits/merges) on insert/delete, so worst-case lookup, insert, and delete all stay `O(log n)` — unlike a plain (unbalanced) BST, which can degrade to `O(n)` on sorted/adversarial insert order.

**Why not a hash table instead:** a hash index gives `O(1)` average lookup for exact-match equality (`WHERE id = 5`), which can beat a B+ tree's `O(log n)`, but hash tables destroy ordering — they can't efficiently answer range queries, prefix (`LIKE 'abc%'`) queries, or `ORDER BY` on the indexed column, all of which a B+ tree handles naturally by walking its sorted leaf chain.

**What you give up:** every index speeds up reads but slows down writes (`INSERT`/`UPDATE`/`DELETE`) because the index itself must be kept up to date and rebalanced, and it consumes additional disk space. This is why indexes are added selectively — on columns that are actually queried/filtered/joined/sorted on frequently — rather than on every column, and it's the reasoning behind the general read/write trade-off that shows up throughout database and systems design.

### 2. Computer Architecture (Comparison)

Compare **direct-mapped**, **set-associative**, and **fully-associative** cache placement policies in terms of where a given memory block can be placed, hit-rate behavior (especially conflict misses), and lookup hardware cost.

**Answer:**

| Aspect | Direct-Mapped | Set-Associative (N-way) | Fully-Associative |
|---|---|---|---|
| Where a block can go | Exactly **one** specific cache line, determined by `(block address) mod (number of lines)`. | Any of **N** lines within one specific *set*, determined by `(block address) mod (number of sets)`. | **Any** line in the entire cache — no fixed mapping at all. |
| Conflict misses | **Highest** — if two frequently-used blocks happen to map to the same line, they repeatedly evict each other even if the rest of the cache is empty (classic "thrashing" pattern). | **Reduced** — two blocks only conflict if more than N of them map to the same set at once, so a higher associativity (larger N) lowers conflict misses. | **None** — since a block can go anywhere, conflict misses are eliminated entirely; the only misses left are compulsory (cold) and capacity misses. |
| Lookup hardware cost | **Cheapest/fastest** — only one tag comparator needed per access, since there's only one possible location to check. | **Moderate** — needs N parallel tag comparators (one per way in the set), plus replacement-policy logic (e.g. LRU) to choose which of the N ways to evict. | **Most expensive** — needs a comparator for *every* line in the cache, checked in parallel, which becomes impractically expensive/slow (in silicon area and power) as cache size grows. |
| Typical use | Rare in modern general-purpose CPU caches (too many conflict misses) — sometimes used for very large, latency-tolerant caches. | The dominant real-world choice — e.g. modern L1/L2 caches are commonly 4-way, 8-way, or 16-way set-associative, balancing hit rate against hardware cost. | Used only for small, highly latency-critical structures like a **TLB** (translation lookaside buffer) or very small caches, where the number of entries is small enough that full comparator hardware is affordable. |

**Why this matters:** this is a direct illustration of a recurring hardware trade-off between **hit rate** and **hardware cost/latency** — direct-mapped is fast and cheap per access but wastes performance on avoidable conflicts, fully-associative gets the best possible hit rate for a given cache size but doesn't scale in hardware, and set-associative is the practical middle ground almost every real CPU cache actually uses, tuning the associativity (N) as one of the key cache-design knobs alongside cache size and line size.

### 3. System Design Basics (Scenario/Applied)

You're asked to design a **URL-shortening service** (like a `bit.ly`) that takes a long URL and returns a short one, then redirects visitors from the short URL to the original. Describe the key components of the system and explain specifically how you would generate short codes so that concurrent requests don't collide.

**Answer:**

**Core components:**
1. **Write path (shorten):** a client submits a long URL via an API (`POST /shorten`); the service generates a unique short code, stores the mapping `{short_code -> long_url}` in a datastore, and returns the full short URL (e.g. `https://short.ly/abc123`).
2. **Read path (redirect):** a client hits `GET /{short_code}`; the service looks up `short_code` in the datastore, and if found, issues an HTTP redirect (301/302) to the original long URL. This path is read-heavy and latency-sensitive (users expect instant redirects), so it should be backed by a **cache** (e.g. Redis) in front of the primary datastore, since a small fraction of URLs (viral links) tend to receive a disproportionate share of traffic.
3. **Datastore:** a key-value or simple relational store mapping short codes to long URLs (plus metadata like creation time, expiry, click count). Given the access pattern is essentially key-based lookups, a key-value store (or a simple indexed table keyed on `short_code`) scales well and is easy to reason about; click-count analytics can be handled asynchronously (e.g. via a message queue) so they don't slow down the redirect's hot path.
4. **Short-code generator:** the component responsible for producing the actual short string — this is the part most prone to collisions under concurrency, addressed below.

**Avoiding collisions on short-code generation under concurrent requests:**

The naive approach — hash the long URL (e.g. MD5) and take the first few characters — is dangerous under concurrency and at scale: two different long URLs can produce colliding prefixes, and you'd need a read-check-then-write (check if the code already exists, retry if so) which is racy under concurrent writes and adds extra round trips.

A more robust approach is to **decouple ID generation from encoding**, using a centralized, monotonically-increasing unique ID source instead of hashing content:
- Use a **distributed ID generator** — e.g., a dedicated auto-increment counter service, database sequence, or a scheme like Twitter's Snowflake (timestamp + machine ID + per-machine sequence number) — to hand out a globally unique 64-bit integer ID to each shorten request. Because the ID source itself guarantees uniqueness (via atomic increments or structurally distinct machine/sequence components), **no two concurrent requests can ever be handed the same ID**, which eliminates the collision problem at its root rather than detecting and retrying after the fact.
- **Base62-encode** that unique integer ID (using `[a-zA-Z0-9]`, 62 symbols) into a short alphanumeric string — a 6-character Base62 string already covers `62^6 ≈ 56.8` billion distinct codes, which is why short URLs typically look like `abc123` rather than being pure random strings.
- Store `{short_code -> long_url}` using this generated code as the key. Because the ID (and therefore the code) was already guaranteed unique before the write, the write itself is a simple insert with no collision-checking or retry loop needed.

**Why this matters:** the key design insight is recognizing that "no two requests get the same short code" is fundamentally a **uniqueness/coordination problem**, not an encoding problem — solving it by picking a strong, centrally-coordinated (or structurally collision-free, as in Snowflake) ID source up front is far simpler and more scalable than trying to detect and resolve collisions after generating codes independently on multiple servers, which is a pattern that generalizes to many distributed-systems problems beyond URL shorteners (e.g., generating unique order IDs, database primary keys in a sharded system, etc.).
