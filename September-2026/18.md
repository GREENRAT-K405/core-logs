## DSA

### Question: Burst Balloons (Dynamic Programming — Hard)

You are given `n` balloons, indexed `0` to `n - 1`. Each balloon has a number painted on it, given by an integer array `nums`. You are asked to burst all the balloons.

If you burst balloon `i`, you get `nums[left] * nums[i] * nums[right]` coins, where `left` and `right` are the indices of the balloons adjacent to `i` **at the moment it is burst**. After bursting, `left` and `right` become adjacent to each other.

If `i` is at the boundary of the (currently remaining) balloons, treat the missing neighbor as if it were a balloon with the value `1` (i.e., out-of-bounds neighbors count as `1`, not `0`).

Return the maximum number of coins you can collect by bursting all the balloons, in the best possible order.

**Input format:**
- An integer array `nums` of length `n`, the values painted on each balloon.

**Output format:**
- A single integer: the maximum total coins obtainable.

**Worked Examples:**

1. `nums = [3,1,5,8]` → burst `1` first, then `5`, then `3`, then `8`: `3*1*5 + 3*5*8 + 1*3*8 + 1*8*1 = 15 + 120 + 24 + 8 = 167` → output `167`.
2. `nums = [1,5]` → burst `1` first (`1*1*5 = 5`), then `5` alone (`1*5*1 = 5`): total `10`. Bursting `5` first only yields `6` total, so `10` is the max → output `10`.
3. `nums = [7]` → only one balloon, boundaries on both sides count as `1`: `1*7*1 = 7` → output `7`.

**Constraints:**
- `1 <= n <= 300`
- `0 <= nums[i] <= 100`

---

### Step-by-Step Walkthrough

**Why a greedy or brute-force order doesn't work:** The coins earned for bursting a balloon depend on its *current* neighbors, which change as other balloons are removed. Trying every possible burst order directly is `O(n!)`, hopelessly slow, and there's no obvious greedy rule (e.g., "always burst the smallest first") that provably maximizes the total — the interactions between values are too entangled.

**The key reframe — think about the *last* balloon burst in a range, not the first:**

Instead of asking "which balloon do I burst first?", ask the reverse question: "for a contiguous range of balloons, which one is burst **last**?" This turns out to be far more tractable, because once we fix which balloon `k` is burst last within a range `(l, r)` (exclusive boundaries `l` and `r`, which are *not* burst as part of this subproblem), we know:
- Every other balloon strictly between `l` and `r` must have already been burst *before* `k`.
- Therefore, at the moment `k` is burst, its immediate neighbors are exactly `nums[l]` and `nums[r]` — the two fixed boundary balloons — regardless of the order in which the other balloons in between were removed.
- This means the subproblem cleanly splits into two **independent** subranges, `(l, k)` and `(k, r)`, whose optimal solutions can be computed and combined without worrying about interactions crossing between them.

**Padding trick:** Add a virtual balloon of value `1` at both ends of `nums` (so out-of-bounds neighbors are handled uniformly, matching the problem's rule). If `nums` has length `n`, the padded array `balloons` has length `n + 2`, with `balloons[0] = balloons[n+1] = 1`.

**DP definition:** Let `dp[l][r]` = the maximum coins obtainable by bursting **all balloons strictly between** indices `l` and `r` in the padded array (i.e., balloons `l+1 .. r-1`), leaving `l` and `r` themselves un-burst as the fixed boundary for this subrange.

**Base case:** `dp[l][r] = 0` whenever `r <= l + 1` (no balloons strictly between them to burst).

**Transition:** For each range `(l, r)` with at least one balloon between them, try every possible choice of `k` (`l < k < r`) as the *last* balloon burst in that range:

```
dp[l][r] = max over l < k < r of:
    dp[l][k] + dp[k][r] + balloons[l] * balloons[k] * balloons[r]
```

- `dp[l][k]`: best result for bursting everything strictly between `l` and `k` first.
- `dp[k][r]`: best result for bursting everything strictly between `k` and `r` first.
- `balloons[l] * balloons[k] * balloons[r]`: the coins earned when `k` itself is finally burst, with `l` and `r` as its neighbors (since everything else in `(l, r)` is already gone).

Ranges are computed in increasing order of width (`r - l`) so that `dp[l][k]` and `dp[k][r]` — both narrower ranges — are already known when `dp[l][r]` is computed.

**Final result:** `dp[0][n+1]`, the best result for bursting everything strictly between the two padding balloons — i.e., all of the original balloons.

**Complexity Analysis:**
- **Time complexity:** `O(n^3)` — `O(n^2)` distinct `(l, r)` ranges, each trying up to `O(n)` choices of `k`.
- **Space complexity:** `O(n^2)` for the `dp` table.

---

### C++ Code

```cpp
#include <iostream>
#include <vector>
#include <algorithm>
using namespace std;

class Solution {
public:
    int maxCoins(vector<int>& nums) {
        int n = nums.size();

        // Pad with virtual balloons of value 1 at both ends so
        // out-of-bounds neighbors are handled uniformly.
        vector<int> balloons(n + 2, 1);
        for (int i = 0; i < n; ++i) {
            balloons[i + 1] = nums[i];
        }

        // dp[l][r] = max coins from bursting everything strictly between
        // indices l and r (exclusive), leaving l and r themselves intact.
        vector<vector<int>> dp(n + 2, vector<int>(n + 2, 0));

        // Iterate by increasing range width so smaller subranges are
        // already solved when we need them.
        for (int width = 2; width <= n + 1; ++width) {
            for (int l = 0; l + width <= n + 1; ++l) {
                int r = l + width;
                int best = 0;
                // Try every balloon k as the LAST one burst in (l, r).
                for (int k = l + 1; k < r; ++k) {
                    int coins = dp[l][k] + dp[k][r]
                              + balloons[l] * balloons[k] * balloons[r];
                    best = max(best, coins);
                }
                dp[l][r] = best;
            }
        }

        return dp[0][n + 1];
    }
};

int main() {
    Solution sol;

    vector<int> nums1 = {3, 1, 5, 8};
    cout << "Example 1: " << sol.maxCoins(nums1) << " (expected 167)" << endl;

    vector<int> nums2 = {1, 5};
    cout << "Example 2: " << sol.maxCoins(nums2) << " (expected 10)" << endl;

    vector<int> nums3 = {7};
    cout << "Example 3: " << sol.maxCoins(nums3) << " (expected 7)" << endl;

    return 0;
}
```

**Trace against the examples:**
- Example 1: `nums = [3,1,5,8]` → padded `[1,3,1,5,8,1]`. Filling `dp` by increasing width eventually yields `dp[0][5] = 167`, matching the burst order `1 → 5 → 3 → 8` worked out by hand above. ✓
- Example 2: `nums = [1,5]` → padded `[1,1,5,1]`. `dp[0][2] = 5` (burst the `1`), `dp[1][3] = 5` (burst the `5`), and `dp[0][3] = max(dp[0][1]+dp[1][3]+1*1*1, dp[0][2]+dp[2][3]+1*5*1) = max(6, 10) = 10`. ✓
- Example 3: `nums = [7]` → padded `[1,7,1]`. `dp[0][2] = balloons[0]*balloons[1]*balloons[2] = 1*7*1 = 7`. ✓

## CS Fundamentals

### 1. Operating Systems (Conceptual/Definition)

What is a race condition, and what are the necessary conditions for one to occur? Describe two different mechanisms an OS or programmer can use to prevent it.

**Answer:**

A **race condition** occurs when two or more threads or processes access shared data concurrently, and the final outcome of that access depends on the unpredictable timing/interleaving of their execution — i.e., the program's correctness "races" against scheduling, rather than being determined purely by its logic. The classic example is two threads both executing `counter++` on a shared variable: this is not an atomic operation at the hardware level (it decomposes into read `counter`, add `1`, write back), so if both threads read the same old value before either writes back, one increment is silently lost.

**Necessary conditions for a race condition to matter (Bernstein's conditions, informally):**
1. **Shared resource:** At least one piece of data (a variable, file, data structure) is accessible by more than one thread/process.
2. **Concurrent access:** At least one of the accesses is a write, and it can happen concurrently with another access (read or write) to the same resource.
3. **No synchronization:** There is no mechanism enforcing a specific safe order between those accesses — the interleaving is left to the scheduler, which is not guaranteed to behave any particular way.

If all three hold, the code contains a **critical section** (the piece of code touching the shared resource) that is not properly protected, and different runs of the program can produce different, sometimes-incorrect results even with identical input.

**Prevention mechanisms:**
1. **Mutex locks (mutual exclusion):** Wrap the critical section with `lock()`/`unlock()` calls. Only one thread can hold the lock at a time; any other thread trying to enter the critical section blocks until the lock is released. This directly removes condition 3 above by forcing a serialized order on the conflicting accesses. The tradeoff is potential contention (threads waiting) and the risk of deadlock if multiple locks are acquired in inconsistent orders across different code paths.
2. **Atomic instructions / lock-free operations:** Many CPUs provide hardware-level atomic instructions such as `compare-and-swap` (CAS) or `fetch-and-add`, which the OS/compiler exposes as atomic types (e.g., `std::atomic<int>` in C++). These let an operation like `counter++` complete as a single indivisible step relative to other cores, with no separate lock needed. This avoids lock overhead and deadlock risk but is harder to use correctly for anything beyond simple counters/flags, and can still suffer from subtler issues like the ABA problem in lock-free data structures.

**Why this matters:** Race conditions are notoriously hard to debug because they are non-deterministic — a bug might appear once in a thousand runs, especially under specific timing/load conditions, and can be nearly impossible to reproduce in a debugger that itself changes timing. Understanding the precise conditions that cause them is what lets an engineer recognize risky shared-state patterns in code review, before they ship as an intermittent production bug.

### 2. OOP (Comparison)

Compare composition and inheritance as ways to reuse code between classes. Give an example scenario where each is the better choice, and explain the "favor composition over inheritance" guideline.

**Answer:**

| Aspect | Inheritance ("is-a") | Composition ("has-a") |
|---|---|---|
| Relationship modeled | A subclass **is a** specialized kind of its parent class (e.g., `Car` is a `Vehicle`). | A class **has/contains/uses** an instance of another class as a member, delegating to it (e.g., `Car` has an `Engine`). |
| Coupling | Tight — a subclass depends on the internal implementation details of its parent, not just its public interface (the "fragile base class" problem: changing the parent can silently break subclasses). | Loose — the containing class only depends on the contained object's public interface, and can swap it out for a different implementation without changing its own class definition. |
| Flexibility at runtime | Fixed at compile time — an object's class (and thus its inherited behavior) can't change after construction. | Flexible — the contained object can often be swapped or reconfigured at runtime (e.g., injecting a different `Engine` implementation). |
| Code reuse mechanism | Reuses behavior by inheriting methods/fields directly from the parent class. | Reuses behavior by delegating calls to a member object, which does the actual work. |
| Risk with deep hierarchies | Deep or wide hierarchies become hard to reason about; multiple inheritance (where supported) introduces ambiguity (the "diamond problem"). | No such hierarchy depth issue — composed objects form a flat, explicit graph of dependencies. |

**Example where inheritance is the better choice:** A UI framework with a base `Widget` class defining common behavior (`render()`, `handleClick()`, layout properties), and subclasses `Button`, `Checkbox`, `Slider` that are genuinely specialized *kinds* of widget, sharing a true "is-a" relationship and meant to be used polymorphically (e.g., stored in a `vector<Widget*>` and rendered uniformly). Here the hierarchy is shallow, stable, and the "is-a" relationship is semantically real.

**Example where composition is the better choice:** A `Car` class that needs `Engine`, `Transmission`, and `GPS` behavior. A car is **not** an engine — it *has* one. Modeling this with inheritance (e.g., `Car extends Engine`) would be semantically wrong and would also lock the car into exactly one engine implementation forever. With composition, `Car` holds an `Engine` member (possibly injected via constructor as an interface/abstract type), so a `HybridEngine` or `ElectricEngine` can be substituted without touching `Car`'s class definition at all.

**"Favor composition over inheritance":** This widely cited OOP guideline says that when reuse is the goal (rather than genuine polymorphic "is-a" substitutability), composition is usually safer and more flexible than inheritance: it avoids the fragile base class problem, keeps coupling to a public interface rather than internal details, and allows runtime flexibility inheritance can't offer. Inheritance is still the right tool when there's a real "is-a" relationship intended to be used polymorphically — the guideline isn't "never use inheritance," it's "don't reach for inheritance just to reuse a few methods when what you actually want is delegation."

**Why this matters:** Overusing inheritance for convenience (rather than genuine is-a relationships) is one of the most common sources of brittle, hard-to-refactor object-oriented codebases — it's a design smell interviewers frequently probe for, because recognizing it signals whether a candidate designs for long-term maintainability or just for getting something working today.

### 3. System Design Basics (Scenario/Applied)

You're designing a URL shortener (like bit.ly): given a long URL, it returns a short code (e.g., `abc123`); visiting `short.ly/abc123` redirects to the original URL. Walk through the high-level design: how you'd generate short codes, what the read/write path looks like, and how you'd scale it for a system with far more reads than writes.

**Answer:**

**Core requirements:** `POST /shorten` takes a long URL and returns a short code; `GET /{code}` redirects (HTTP 301/302) to the original long URL. Reads (redirects) vastly outnumber writes (shortenings) in a typical bit.ly-style system — most short links get clicked many times after being created once.

**Short code generation — two common approaches:**
1. **Base62 encoding of an auto-incrementing ID:** Use a counter (from a database sequence or a dedicated ID-generation service) to assign each new URL a unique monotonically increasing integer, then encode that integer in base62 (`[a-zA-Z0-9]`, 62 symbols) to get a short, URL-safe string. E.g., ID `125` → some 3-4 character code. This guarantees uniqueness by construction (no collision checking needed) and produces the shortest possible codes for the current ID range, but requires a centralized (or carefully partitioned, e.g. per-shard ID ranges) counter to avoid collisions across multiple servers.
2. **Random string + collision check:** Generate a random 6-7 character base62 string, check if it already exists in the database, and regenerate on collision. Simpler to distribute (no centralized counter needed), but requires a uniqueness check (a fast indexed lookup) on every write, and collision probability needs monitoring as the keyspace fills up.

Either approach typically also supports **custom aliases** (user-chosen codes) as an alternate write path, checked for availability the same way.

**Write path (`POST /shorten`):**
1. Client sends the long URL to an API server.
2. Server generates a short code (via one of the methods above).
3. Server writes a `{short_code → long_url}` mapping to the primary database (a simple key-value or relational store; a relational table `(short_code PRIMARY KEY, long_url, created_at, ...)` works fine at moderate scale).
4. Server returns the full short URL (`short.ly/abc123`) to the client.

**Read path (`GET /{code}`):**
1. Client requests `short.ly/abc123`.
2. Server looks up `abc123` → `long_url`.
3. Server responds with an HTTP redirect to `long_url`.

**Scaling for read-heavy traffic:**
- **Caching layer (e.g., Redis) in front of the database:** Since a small fraction of links tend to receive the majority of clicks (a long-tail/Zipfian access pattern), a cache holding hot `short_code → long_url` mappings can serve the overwhelming majority of redirect requests without touching the database at all. Cache lookups are `O(1)` in-memory and far faster than a database round trip.
- **Read replicas:** For lookups that miss the cache, route reads to one or more read-replica databases (asynchronously replicated from the primary) rather than the single primary, so read load is horizontally distributed and doesn't compete with write traffic on the primary.
- **CDN/edge redirect caching:** Since redirects are simple and (mostly) static per short code, a CDN or edge layer can cache the redirect response itself for a TTL, serving repeat requests for popular links without the request even reaching the origin servers.
- **Horizontal scaling of stateless API servers:** Because the read/write logic itself holds no server-side session state, API servers can be scaled out behind a load balancer independently of the database layer.
- **Database choice/partitioning at very large scale:** A single relational database with a cache in front is often enough for a long time; at very large scale, the mapping table can be sharded by short code (e.g., hash-based sharding) across multiple database nodes, since lookups are always by exact short code (no cross-shard queries needed).

**Why this matters:** This is a textbook "read-heavy, simple-data-model" system design question, and the interesting engineering is almost entirely about caching and read scaling rather than the write path or the data model, which are both intentionally simple. It's a good test of whether a candidate reaches for caching/replication appropriately rather than over-engineering the write path or under-thinking the read path.
