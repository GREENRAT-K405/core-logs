### Question: Binary Tree Zigzag Level Order Traversal (Trees — Medium)

Given the root of a binary tree, return the *zigzag level order traversal* of its node values. That is, traverse level 0 left-to-right, level 1 right-to-left, level 2 left-to-right again, and so on, alternating direction at each depth.

**Input format:**
- The root of a binary tree (each node has an integer value; the tree may be empty).

**Output format:**
- A list of lists of integers — one inner list per level, in the zigzag order described above.

**Worked Examples:**

Example 1:

```
        3
       / \
      9  20
        /  \
       15   7
```

- Level 0 (left→right): `[3]`
- Level 1 (right→left): `[20, 9]`
- Level 2 (left→right): `[15, 7]`

Output: `[[3], [20, 9], [15, 7]]`

Example 2:

```
    1
```

Output: `[[1]]` (single level, trivially left-to-right).

Example 3:

```
(empty tree)
```

Output: `[]` (no nodes to traverse).

**Constraints:**
- The number of nodes is in the range `[0, 2000]`.
- `-100 <= Node.val <= 100`

---

### Step-by-Step Walkthrough

**Approach — BFS level order traversal with a direction flag**

The core of the problem is an ordinary breadth-first (level order) traversal — the only twist is that every other level needs to come out reversed. Rather than reasoning about zigzag order directly, it's easier to:

1. Do a completely standard BFS, level by level, using a queue. For each level, collect that level's values into a temporary list of the correct size (`queue.size()` at the start of the level, since children pushed during this level must not be mixed into it).
2. Track a boolean `leftToRight` that starts `true` and flips after every level.
3. If `leftToRight` is `true` for the current level, append the values in the natural (left-to-right) order collected by BFS. If it's `false`, reverse that level's list before adding it to the result — BFS still visits children left-to-right internally (so the tree structure and child ordering stay correct for the next level), we only reverse the *output* for that level.
4. Push `nullptr`-safe children (`left` then `right`) of every node onto the queue as usual, and stop when the queue is empty.

**Why it works:** BFS naturally groups nodes by depth if we process the queue in fixed-size batches (snapshotting `queue.size()` before draining a level). Reversing only the *presentation* of alternate levels — rather than trying to push/pop in reverse order — keeps the traversal logic identical to a normal level-order BFS, so correctness follows directly from BFS correctness: every node is visited exactly once, in depth order, and each level's children are still discovered left-to-right, which is required for level `d+1` to itself be enumerated correctly before any needed reversal.

**Complexity Analysis:**
- **Time complexity:** `O(n)` — every node is enqueued and dequeued exactly once; reversing a level of size `k` costs `O(k)`, and the sum of all `k` across levels is `n`.
- **Space complexity:** `O(n)` — the queue holds at most one full level, which in the worst case (a complete binary tree's last level) is `O(n/2) = O(n)`; the output itself also stores all `n` values.

### C++ Code

```cpp
#include <iostream>
#include <vector>
#include <queue>
using namespace std;

// Definition for a binary tree node.
struct TreeNode {
    int val;
    TreeNode *left;
    TreeNode *right;
    TreeNode(int x) : val(x), left(nullptr), right(nullptr) {}
};

class Solution {
public:
    vector<vector<int>> zigzagLevelOrder(TreeNode* root) {
        vector<vector<int>> result;
        if (root == nullptr) {
            return result; // empty tree -> empty result
        }

        queue<TreeNode*> q;
        q.push(root);
        bool leftToRight = true;

        while (!q.empty()) {
            int levelSize = q.size(); // snapshot: only nodes of THIS level
            vector<int> level(levelSize);

            for (int i = 0; i < levelSize; ++i) {
                TreeNode* node = q.front();
                q.pop();

                // Place value according to current direction without a
                // separate reverse pass: index from the front or the back.
                int idx = leftToRight ? i : (levelSize - 1 - i);
                level[idx] = node->val;

                if (node->left != nullptr) q.push(node->left);
                if (node->right != nullptr) q.push(node->right);
            }

            result.push_back(level);
            leftToRight = !leftToRight; // flip direction for next level
        }

        return result;
    }
};

int main() {
    // Build the example tree:
    //         3
    //        / \
    //       9  20
    //         /  \
    //        15   7
    TreeNode* n3 = new TreeNode(3);
    TreeNode* n9 = new TreeNode(9);
    TreeNode* n20 = new TreeNode(20);
    TreeNode* n15 = new TreeNode(15);
    TreeNode* n7 = new TreeNode(7);

    n3->left = n9;
    n3->right = n20;
    n20->left = n15;
    n20->right = n7;

    Solution sol;
    vector<vector<int>> result = sol.zigzagLevelOrder(n3);

    for (const auto& level : result) {
        cout << "[";
        for (size_t i = 0; i < level.size(); ++i) {
            cout << level[i] << (i + 1 < level.size() ? ", " : "");
        }
        cout << "]\n";
    }
    // Expected output:
    // [3]
    // [20, 9]
    // [15, 7]

    return 0;
}
```

**Trace against the examples:**
- Example 1: Level 0 `{3}` with `leftToRight = true` → `[3]`. Level 1 `{9, 20}` dequeued in that order, but `leftToRight = false` now, so index `0` (value 9) is placed at `level[1]` and index `1` (value 20) at `level[0]` → `[20, 9]`. Level 2 `{15, 7}` with `leftToRight = true` → `[15, 7]`. Final: `[[3], [20, 9], [15, 7]]`. ✓
- Example 2: Single node, one level, `leftToRight = true` → `[[1]]`. ✓
- Example 3: `root == nullptr`, the function returns immediately with an empty vector → `[]`. ✓

## CS Fundamentals

### 1. Computer Networks (Scenario/Applied)

A user reports that your website takes about 2 extra seconds to load, but only on their very first visit of the day — every reload after that is fast. Walk through what's likely happening at the network level and how you'd confirm your diagnosis.

**Answer:**

The symptom — a one-time cost that disappears on repeat visits within the same session/day — points strongly at something being **cached** on the first request and **reused** afterward. There are three usual suspects, roughly in the order a browser hits them:

1. **DNS resolution.** The very first request for a hostname requires resolving it to an IP address, which can involve several hops (browser cache → OS resolver cache → recursive resolver → root/TLD/authoritative name servers) if nothing is cached yet. Once resolved, the OS and browser cache the result for the record's **TTL** (Time To Live) — if that TTL is, say, 24 hours, the first visit of a new day pays the full resolution cost again while later visits that day hit the cache and skip it almost entirely.
2. **TCP handshake + TLS handshake.** Establishing a new TCP connection costs one round trip (SYN, SYN-ACK, ACK), and if the site is HTTPS, the TLS handshake adds one or two more round trips to negotiate the session keys (fewer with TLS 1.3's 1-RTT, or 0-RTT session resumption). Browsers keep connections alive and may resume TLS sessions for a while, so a same-day reload can skip a fresh handshake entirely; a first visit generally cannot.
3. **HTTP resource caching.** Static assets (JS, CSS, images, fonts) sent with cache headers (`Cache-Control`, `ETag`, `Expires`) are stored by the browser after the first load. A first visit downloads everything from the server; subsequent visits validate or reuse from the local cache, which is much faster and may involve zero network round trips at all (for a `max-age` that hasn't expired) or a cheap `304 Not Modified` exchange.

**How to confirm it:** Open the browser's DevTools **Network** tab, clear the cache, and reload — this reproduces the "first visit" condition. Look at the timing breakdown for the initial document request: a large "DNS Lookup" segment confirms cause 1, a large "Initial Connection"/"SSL" segment confirms cause 2, and a large number of full-size (non-304) resource downloads confirms cause 3. Then reload without clearing the cache and compare — most of those segments should shrink to near zero, matching the user's report of fast repeat loads.

**Why this matters:** Distinguishing between these three layers matters because the fix differs for each — you'd lower DNS TTL or use a faster resolver for cause 1, enable connection keep-alive/HTTP-2 multiplexing or OCSP stapling for cause 2, and tune `Cache-Control` headers for cause 3. Diagnosing "slow" by which network phase is actually slow, rather than guessing, is a core skill for any backend or full-stack engineer.

### 2. OOP (Conceptual/Definition)

What is the Single Responsibility Principle (the "S" in SOLID)? Define it and give a short example of a class that violates it, followed by a corrected version.

**Answer:**

The **Single Responsibility Principle (SRP)** states that a class (or module) should have **only one reason to change** — in other words, it should be responsible for exactly one piece of functionality, and that responsibility should be entirely encapsulated by the class. If a class bundles two or more unrelated responsibilities, a change driven by one of them risks breaking or requiring a re-test of code related to the other, even though the two are logically unrelated.

**Example — violation:**

```cpp
class Invoice {
public:
    double calculateTotal(const vector<double>& items) {
        double total = 0;
        for (double price : items) total += price;
        return total;
    }

    void printInvoice(const vector<double>& items) {
        // formatting/printing logic mixed into the same class
        cout << "Invoice total: $" << calculateTotal(items) << endl;
    }

    void saveToDatabase(const vector<double>& items) {
        // persistence logic also mixed in
        cout << "Saving invoice to DB..." << endl;
    }
};
```

Here, `Invoice` has at least three reasons to change: a change in how totals are calculated (business logic), a change in how invoices are formatted/displayed (presentation), and a change in how/where invoices are persisted (storage — e.g., switching from a SQL database to a document store). These are unrelated concerns bundled into one class.

**Example — corrected (responsibilities split):**

```cpp
class Invoice {
public:
    double calculateTotal(const vector<double>& items) {
        double total = 0;
        for (double price : items) total += price;
        return total;
    }
};

class InvoicePrinter {
public:
    void print(const Invoice& invoice, const vector<double>& items) {
        cout << "Invoice total: $" << invoice.calculateTotal(items) << endl;
    }
};

class InvoiceRepository {
public:
    void save(const Invoice& invoice, const vector<double>& items) {
        cout << "Saving invoice to DB..." << endl;
    }
};
```

Now each class has exactly one reason to change: `Invoice` only if the total-calculation rules change, `InvoicePrinter` only if the display format changes, and `InvoiceRepository` only if the storage mechanism changes.

**Why this matters:** SRP keeps classes small, focused, and easy to test in isolation (you can unit-test `calculateTotal` without touching a database or console output). It also reduces coupling — a team working on invoice formatting can change `InvoicePrinter` without any risk of breaking persistence code, and vice versa. This is the same reasoning that later shows up in microservice boundaries and layered architectures at a larger scale: separate the things that change for different reasons.

### 3. Computer Architecture (Comparison)

Compare the L1, L2, and L3 cache levels in a modern CPU: their typical size, latency, and scope (per-core vs shared), and explain why a multi-level hierarchy is used instead of one large cache.

**Answer:**

| Aspect | L1 Cache | L2 Cache | L3 Cache |
|---|---|---|---|
| Typical size | 32–64 KB (often split into separate instruction and data caches) | 256 KB – 1 MB | A few MB to tens of MB |
| Typical latency | ~1–4 CPU cycles | ~10–20 cycles | ~30–70 cycles |
| Scope | Private to a single core | Usually private to a single core (sometimes shared by a pair) | Shared across all cores on the chip |
| Speed vs. capacity | Fastest, smallest | Slower, larger | Slowest of the three, largest |

**Why a hierarchy instead of one big cache:** There is a fundamental physical trade-off between a memory's **size**, its **speed**, and its **cost per bit** — larger memories require more transistors and longer signal paths to address, which directly increases access latency, and fast SRAM cells (used for caches) are far more expensive per bit than DRAM (used for main memory). A single cache big enough to hold a useful working set (multiple MB) built entirely out of the fastest possible SRAM would be both prohibitively expensive and, more importantly, too slow to access in 1–2 cycles because of its sheer physical size (longer wires, more decoding logic).

The multi-level design exploits the **principle of locality** (temporal and spatial): most memory accesses cluster around a small, frequently reused set of addresses at any given moment. So:
- **L1** is kept tiny and extremely fast to serve the hottest, most frequently accessed data/instructions with almost no latency, sitting directly next to the core's execution units.
- **L2** is larger and a bit slower, catching most of what L1 misses, still private to the core so it doesn't contend with other cores.
- **L3** is much larger and shared, acting as a last line of defense before a far more expensive trip to main memory (DRAM, ~200+ cycles), and its shared nature also lets cores exchange data efficiently (useful for cache coherence between cores working on related data).

This graduated structure means the *average* memory access latency stays close to L1 speed for the common case (cache hits at L1), while still providing enough total capacity (via L2 and L3) to avoid constantly paying the very high cost of a main-memory access — a compromise no single cache size/speed point could achieve on its own.

**Why this matters:** Understanding the cache hierarchy explains why algorithms with good data locality (e.g., iterating an array sequentially) run dramatically faster than those with poor locality (e.g., pointer-chasing through a random-access linked structure) even with identical Big-O complexity — the difference is how often each pattern causes cache misses that fall through to slower levels or to main memory.
