### Question: Product of Array Except Self (Arrays — Medium)

**Problem Statement**

Given an integer array `nums` of length `n`, return an array `answer` such that `answer[i]` is equal to the product of all the elements of `nums` except `nums[i]`.

You must write an algorithm that runs in `O(n)` time and without using the division operation (so you can't just compute the total product and divide by `nums[i]`, which also breaks when `nums[i] == 0`).

**Input/Output Format**

- Input: an integer array `nums`.
- Output: an integer array `answer` of the same length, where `answer[i] = product of all nums[j] for j != i`.

**Examples**

1. Input: `nums = [1, 2, 3, 4]` → Output: `[24, 12, 8, 6]`
   (`answer[0] = 2*3*4 = 24`, `answer[1] = 1*3*4 = 12`, `answer[2] = 1*2*4 = 8`, `answer[3] = 1*2*3 = 6`)
2. Input: `nums = [-1, 1, 0, -3, 3]` → Output: `[0, 0, 9, 0, 0]`
   (any index paired with the single `0` elsewhere in the array becomes `0`, except the `0`'s own index, which is the product of everything else)
3. Input: `nums = [2, 5]` → Output: `[5, 2]`

**Constraints**

- `2 <= nums.length <= 10^5`
- `-30 <= nums[i] <= 30`
- The product of any prefix or suffix of `nums` is guaranteed to fit in a 32-bit integer.

### Step-by-Step Walkthrough

**Why the obvious approach is blocked.** The natural idea — compute `total = product of all elements`, then set `answer[i] = total / nums[i]` — is explicitly disallowed, and for good reason beyond the rules of the problem: it breaks the moment any `nums[i] == 0`, since you can't divide by zero, and it silently gives wrong answers if *two or more* elements are zero (every `answer[i]` should be `0` in that case, but `total` is already `0` and dividing `0/0` is undefined). So the real problem is "compute this without division," which means each `answer[i]` has to be built directly out of a product of the *other* elements.

**Splitting the product into two halves.** Notice that `answer[i] = (product of everything to the left of i) * (product of everything to the right of i)`. Call these `prefix[i]` (product of `nums[0..i-1]`) and `suffix[i]` (product of `nums[i+1..n-1]`). If we had both arrays, `answer[i] = prefix[i] * suffix[i]` for every `i`.

**Building prefix products in one left-to-right pass.** `prefix[0] = 1` (there's nothing to the left of index 0, and an empty product is `1` by convention). Then `prefix[i] = prefix[i-1] * nums[i-1]` — the product of everything before `i` is the product of everything before `i-1`, times the element that was just added (`nums[i-1]`).

**Building suffix products in one right-to-left pass**, symmetrically: `suffix[n-1] = 1`, and `suffix[i] = suffix[i+1] * nums[i+1]`.

**Saving the extra array.** A direct implementation would use three arrays of size `n` (`prefix`, `suffix`, `answer`), which is `O(n)` extra space beyond the output. This can be tightened to `O(1)` extra space (not counting the output array itself, which the problem requires you to return): first fill `answer[i]` with the prefix products directly (reusing the output array as the "prefix" array), then do a second pass from the right, keeping a *running* suffix product in a single variable instead of a whole array, multiplying it into `answer[i]` as you go.

**Why this is correct.** Every element of `answer[i]` is decomposed into exactly two disjoint pieces — "everything strictly before `i`" and "everything strictly after `i`" — which together cover every index except `i` itself, exactly once each. Since multiplication is associative, computing those two pieces independently (one pass forward, one pass backward) and multiplying them together at the end gives exactly the same result as multiplying all `n-1` other elements directly, just reorganized to avoid recomputation and avoid division.

**Complexity.**
- Time: `O(n)` — two linear passes over the array.
- Space: `O(1)` extra space beyond the required output array (the running suffix product is a single variable, not a second array).

### C++ Code

```cpp
#include <vector>
using namespace std;

vector<int> productExceptSelf(vector<int>& nums) {
    int n = (int)nums.size();
    vector<int> answer(n, 1);

    // Pass 1 (left to right): answer[i] ends up holding the product of
    // every element strictly to the left of i.
    // answer[0] stays 1, since there is nothing to the left of index 0.
    for (int i = 1; i < n; i++) {
        answer[i] = answer[i - 1] * nums[i - 1];
    }

    // Pass 2 (right to left): multiply in the product of every element
    // strictly to the right of i, tracked in a single running variable
    // instead of a second array, to keep extra space O(1).
    int suffix = 1;
    for (int i = n - 1; i >= 0; i--) {
        answer[i] *= suffix;      // combine left-product (already stored) with right-product
        suffix *= nums[i];        // extend the running suffix product to include nums[i]
    }

    return answer;
}
```

### 1. Operating Systems (Conceptual)

What are the four necessary conditions for a deadlock to occur in an operating system? Explain each one briefly, and note why all four must hold simultaneously.

**Answer:**

A deadlock is a state where a set of processes are each waiting for a resource held by another process in the same set, so none of them can ever proceed. Four conditions, first formalized by Coffman et al., must **all** hold at once for a deadlock to be possible:

1. **Mutual Exclusion.** At least one resource must be held in a non-shareable mode — only one process can use it at a time (e.g. a printer, or a lock on a data structure). If every resource could be freely shared, no process would ever need to wait for another to release one.
2. **Hold and Wait.** A process currently holding at least one resource is waiting to acquire additional resources that are currently held by other processes. The process doesn't release what it already has while it waits.
3. **No Preemption.** Resources cannot be forcibly taken away from a process; they can only be released voluntarily by the process holding them once it finishes using them. If the OS could preempt a resource, it could break a stuck cycle by seizing one and handing it to a waiting process.
4. **Circular Wait.** There exists a cycle of processes `P1, P2, ..., Pn` where `P1` is waiting for a resource held by `P2`, `P2` is waiting for a resource held by `P3`, ..., and `Pn` is waiting for a resource held by `P1`.

**Why all four are necessary simultaneously:** each condition individually blocks a way out of the standoff, so removing any single one breaks the deadlock. For example, if preemption were allowed (breaking condition 3), the OS could forcibly reclaim a resource from one process in the cycle and hand it to another, unwinding the wait chain. If circular wait couldn't occur (breaking condition 4, e.g. by imposing a global resource-acquisition ordering so every process must request resources in the same fixed order), the "chain" of waiting processes could never close into a loop. This is exactly why real deadlock-*prevention* strategies work by deliberately denying one of these four conditions (e.g. requesting all needed resources upfront denies hold-and-wait; a strict lock-ordering protocol denies circular wait) rather than trying to detect and recover from deadlocks after the fact.

### 2. Computer Networks (Comparison)

Compare TCP and UDP across reliability, ordering, connection setup, and typical use cases. Why would an application ever choose UDP given that it's "less reliable"?

**Answer:**

| | TCP | UDP |
|---|---|---|
| Connection | Connection-oriented (three-way handshake: SYN, SYN-ACK, ACK) | Connectionless — just send the datagram |
| Reliability | Guaranteed delivery via acknowledgments and retransmission | No delivery guarantee — a lost packet is simply gone |
| Ordering | Guarantees in-order delivery to the application (reorders/buffers at the receiver) | No ordering guarantee — packets can arrive out of sequence |
| Flow/congestion control | Built in (sliding window, congestion avoidance algorithms) | None — the application must handle it if needed |
| Overhead | Higher (handshake, ACKs, retransmission bookkeeping, larger header) | Lower (minimal 8-byte header, no handshake) |
| Typical use cases | Web (HTTP/HTTPS), file transfer, email — anything where correctness of every byte matters | Live video/audio calls, online gaming, DNS lookups, streaming |

**Why choose UDP despite being "less reliable":** for a large class of applications, a late or reordered packet is actively *worse* than a dropped one. In a live video call, if a frame's data arrives 200ms late because TCP is busy retransmitting a lost packet and holding up everything queued behind it (head-of-line blocking), that data is useless by the time it arrives — you'd rather skip that frame and move on to the current one than stall the whole stream waiting for a guaranteed, in-order delivery of stale data. TCP's reliability comes from mechanisms (handshakes, ACKs, retransmission, in-order buffering) that all add latency; UDP strips those away to minimize delay and lets the *application* decide what to do about loss — which is exactly what real-time media, gaming, and DNS (where a client simply retries a query itself if no reply comes) all do. In short: TCP optimizes for "every byte arrives, correctly ordered, eventually"; UDP optimizes for "get this to the receiver as fast as possible, and I'll deal with what's missing at the application layer."

### 3. OOP (Scenario)

You're designing a payment-processing module that must support multiple payment methods — credit card, PayPal, and cryptocurrency — with the ability to add new methods later without modifying existing checkout code. Which OOP design pattern fits this, and how would you structure the classes?

**Answer:**

This is a textbook case for the **Strategy pattern**: define a common interface for "how to pay," implement one concrete class per payment method, and have the checkout code depend only on the interface rather than on any specific payment method. This satisfies the **Open/Closed Principle** — the checkout flow is closed for modification (you never touch it again) but open for extension (adding a new payment method is just adding a new class).

**Structure:**

```cpp
// The strategy interface: every payment method must implement this.
class PaymentStrategy {
public:
    virtual bool pay(double amount) = 0;   // returns success/failure
    virtual ~PaymentStrategy() = default;
};

// Concrete strategies — one per payment method.
class CreditCardPayment : public PaymentStrategy {
public:
    bool pay(double amount) override {
        // talk to the card network / gateway...
        return true;
    }
};

class PayPalPayment : public PaymentStrategy {
public:
    bool pay(double amount) override {
        // talk to PayPal's API...
        return true;
    }
};

class CryptoPayment : public PaymentStrategy {
public:
    bool pay(double amount) override {
        // submit a blockchain transaction...
        return true;
    }
};

// The checkout code depends only on the abstract PaymentStrategy —
// it never knows or cares which concrete method is plugged in.
class Checkout {
    PaymentStrategy* strategy;
public:
    explicit Checkout(PaymentStrategy* s) : strategy(s) {}
    bool completeOrder(double amount) {
        // ... validate cart, compute totals, etc ...
        return strategy->pay(amount);
    }
};
```

**Why this is the right fit (and not, say, a big `switch` statement):** a `switch (paymentType) { case CREDIT_CARD: ... case PAYPAL: ... }` embedded directly in the checkout function works at first, but every new payment method means editing that function again — violating Open/Closed, and risking a regression in a piece of code that already works for existing methods every time you touch it. With Strategy, adding "Apple Pay" next quarter means writing one new class implementing `PaymentStrategy`; `Checkout` is never touched, recompiled logic-wise, or re-tested for methods it already handled. It also makes each payment method independently unit-testable in isolation, and allows the concrete strategy to be chosen at runtime (e.g. based on what the user picks at checkout, or via dependency injection/a factory), rather than being hard-coded.

**Why it matters beyond this scenario:** Strategy is the general pattern for "a family of interchangeable algorithms/behaviors, selected at runtime, behind one interface" — the same shape shows up for sorting comparators, compression algorithms, authentication methods, and pricing rules. Recognizing "multiple ways to do the same conceptual thing, need to add more later without touching callers" as the Strategy pattern is one of the most transferable OOP design instincts for real interview scenario questions.
