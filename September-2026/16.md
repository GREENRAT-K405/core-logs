### Question: Largest Rectangle in Histogram (Stacks/Queues — Hard)

Given an array of integers `heights` representing the heights of bars in a histogram, where each bar has width `1` and the bars are placed adjacent to one another, find the area of the **largest rectangle** that can be formed entirely within the histogram (the rectangle's height is limited by the shortest bar it spans).

**Input format:**
- An integer `n`, the number of bars.
- An array `heights[0..n-1]` of non-negative integers, the height of each bar.

**Output format:**
- A single integer: the maximum rectangular area achievable.

**Worked Examples:**

1. `heights = [2, 1, 5, 6, 2, 3]` → output `10`
   The bars at indices 2 and 3 have heights 5 and 6. Taking both together, the limiting height is `min(5, 6) = 5` over a width of 2, giving area `5 * 2 = 10`. No other combination beats this.

2. `heights = [2, 4]` → output `4`
   Either take just the bar of height 4 alone (`4 * 1 = 4`), or both bars together limited by `min(2, 4) = 2` over width 2 (`2 * 2 = 4`). Both give `4`, so the answer is `4`.

3. `heights = [6, 2, 5, 4, 5, 1, 6]` → output `12`
   Bars at indices 2, 3, 4 have heights 5, 4, 5. Taking all three, the limiting height is `min(5, 4, 5) = 4` over width 3, giving area `4 * 3 = 12`, which is the maximum.

**Constraints:**
- `1 <= n <= 10^5`
- `0 <= heights[i] <= 10^4`

---

### Step-by-Step Walkthrough

**Why brute force is too slow:**
The naive approach checks, for every bar `i`, how far the rectangle of height `heights[i]` can extend left and right before hitting a shorter bar, then takes `height * width` as a candidate. Done directly, this is `O(n^2)` in the worst case (e.g. a strictly increasing array), which is too slow for `n` up to `10^5`.

**Key insight:** For every bar `i`, the largest rectangle that uses `heights[i]` as its limiting (shortest) height extends from just after the **previous strictly-smaller bar** on the left to just before the **next strictly-smaller-or-equal bar** on the right. If we can find those two boundaries for every bar in linear time, the rest is a single pass taking the maximum `height[i] * width[i]`.

**Monotonic stack approach:**
Maintain a stack of bar *indices* whose heights are in strictly increasing order from bottom to top. Push a sentinel index `-1` at the bottom to represent "no bar to the left."

Walk through indices `i = 0 .. n` (note: one past the end, using a virtual height of `0` at `i == n` to force the stack to fully drain by the end):

1. While the stack (excluding the sentinel) is non-empty and `heights[stack.top()] >= currentHeight`, it means the bar at `stack.top()` can no longer extend to the right — its next-smaller-or-equal bar is at index `i`. Pop it.
2. When popped, its height is the limiting height of a candidate rectangle. Its left boundary is whatever is now at the top of the stack (the previous smaller bar), and its right boundary is `i`. So the width is `i - stack.top() - 1` (after the pop).
3. Compute `area = poppedHeight * width` and update the running maximum.
4. Once no more pops are possible (or the current bar is taller than the stack top), push the current index `i` onto the stack.

Because every index is pushed exactly once and popped at most once, the total work across the whole run is `O(n)`.

**Why it's correct:** Each bar is only popped once we've confirmed a shorter bar to its right exists (or we've reached the virtual end with height 0, which guarantees every remaining bar eventually gets popped). At the moment a bar is popped, the current stack top is guaranteed to be the nearest bar to its left that is strictly shorter (everything taller in between was already popped earlier), so both boundaries used for the width are correct and tight — meaning we never overcount the width of the rectangle for that bar's height.

**Complexity Analysis:**
- **Time complexity:** `O(n)` — each index is pushed once and popped at most once onto/off the stack.
- **Space complexity:** `O(n)` — for the stack in the worst case (e.g. a strictly increasing sequence of heights, where nothing gets popped until the very end).

---

### C++ Code

```cpp
#include <bits/stdc++.h>
using namespace std;

int largestRectangleArea(vector<int>& heights) {
    int n = heights.size();
    stack<int> st;   // holds indices; heights at these indices are strictly increasing
    st.push(-1);     // sentinel: "no bar" to the left of index 0
    int maxArea = 0;

    for (int i = 0; i <= n; i++) {
        // Use height 0 at the virtual index n to flush every remaining bar off the stack.
        int currentHeight = (i == n) ? 0 : heights[i];

        while (st.top() != -1 && heights[st.top()] >= currentHeight) {
            int poppedHeight = heights[st.top()];
            st.pop();
            // Width spans from just after the new top (previous smaller bar)
            // to just before the current index (next smaller-or-equal bar).
            int width = i - st.top() - 1;
            maxArea = max(maxArea, poppedHeight * width);
        }
        st.push(i);
    }

    return maxArea;
}

int main() {
    vector<int> h1 = {2, 1, 5, 6, 2, 3};
    cout << "Example 1: " << largestRectangleArea(h1) << " (expected 10)" << endl;

    vector<int> h2 = {2, 4};
    cout << "Example 2: " << largestRectangleArea(h2) << " (expected 4)" << endl;

    vector<int> h3 = {6, 2, 5, 4, 5, 1, 6};
    cout << "Example 3: " << largestRectangleArea(h3) << " (expected 12)" << endl;

    return 0;
}
```

**Trace against the examples:**
- `[2, 1, 5, 6, 2, 3]`: bar `1` (height 6) pops when `2` (index 4) arrives, since `2 < 6`, giving width `4 - 2 - 1 = 1`, area `6`. Bar at index 2 (height 5) then pops against the same `2`, with the stack top now at index 1 (height 1), giving width `4 - 1 - 1 = 2`, area `5 * 2 = 10` — the maximum. ✓
- `[2, 4]`: at the virtual end (`i = 2`, height 0), index 1 (height 4) pops first: top is now index 0, width `2 - 0 - 1 = 1`, area `4`. Then index 0 (height 2) pops: top is sentinel `-1`, width `2 - (-1) - 1 = 2`, area `4`. Max stays `4`. ✓
- `[6, 2, 5, 4, 5, 1, 6]`: bar at index 4 (height 5) pops when index 5 (height 1) arrives: top is index 3 (height 4), width `5 - 3 - 1 = 1`, area `5`. Then index 3 (height 4) pops: top is index 1 (height 2), width `5 - 1 - 1 = 3`, area `4 * 3 = 12` — the maximum. ✓

## CS Fundamentals

### 1. Computer Architecture (Conceptual/Definition)

What is cache memory in a computer system, and what are the principles of **temporal locality** and **spatial locality** that justify its effectiveness? Explain with a brief example of how a CPU cache exploits both principles when a program loops over an array.

**Answer:**

**Cache memory** is a small, very fast memory (built from SRAM) sitting physically close to the CPU core, between the registers and main memory (DRAM). Its purpose is to bridge the huge speed gap between the CPU (which can execute billions of instructions per second) and main memory (which is an order of magnitude or more slower to access). Modern systems use a hierarchy of caches (L1, closest and smallest/fastest; L2; often a shared L3) with increasing size and decreasing speed as you move away from the core.

Caching only helps because real programs exhibit **locality of reference**:

- **Temporal locality** — if a memory location is accessed once, it is likely to be accessed again soon. Example: a loop counter, an accumulator variable, or a frequently-called function's instructions are reused over and over in a short time window, so keeping them in cache after the first access avoids repeated slow trips to main memory.
- **Spatial locality** — if a memory location is accessed, nearby memory locations are likely to be accessed soon after. This is why caches don't fetch a single byte/word on a miss — they fetch an entire **cache line** (typically 64 bytes) containing the requested address plus its neighbors.

**Example — summing an array:**
```cpp
long sum = 0;
for (int i = 0; i < n; i++) {
    sum += a[i];
}
```
- *Temporal locality*: `sum` and `i` are accessed on every single iteration. They are kept in registers/L1 cache the entire time rather than being re-fetched from main memory each iteration.
- *Spatial locality*: when `a[0]` is first accessed, it's a cache miss, but the hardware pulls in the whole cache line — which, since the array is stored contiguously, also contains `a[1], a[2], ...` up to the line size (e.g. 16 consecutive `int`s for a 64-byte line). The next 15 iterations then hit the cache instead of going to main memory, even though only one memory-level fetch actually happened.

**Why this matters:** Average memory access time is modeled as `hit_time + miss_rate * miss_penalty`. Because of locality, real programs achieve cache hit rates well above 90% even with a cache that's a tiny fraction of main memory's size — which is *the* reason the entire cache hierarchy works at all, and why data structure layout (e.g. array-of-structs vs struct-of-arrays, row-major vs column-major traversal) has a measurable, sometimes 10x+, impact on real-world performance despite doing the exact same amount of "work" in Big-O terms.

### 2. DBMS (Scenario/Applied)

You inherit an `Orders` table where every row stores the order's product/quantity/price **and**, inline, the customer's name, email, and shipping address. The team complains that (a) updating a customer's email means updating hundreds of order rows, and (b) placing a new order means re-typing the customer's full address every time, and a typo produces two "different" addresses for the same customer. What problem is this table suffering from, and how would you redesign the schema to fix it (up to 3NF)?

**Answer:**

This table is suffering from **data redundancy caused by insufficient normalization**, which manifests as classic **update, insertion, and deletion anomalies**:
- **Update anomaly**: the customer's email is duplicated across every order row, so changing it requires updating all of them (and missing even one leaves the data inconsistent).
- **Insertion anomaly**: you can't easily add a new customer without also placing an order (since customer data only exists attached to orders), and re-entering the address by hand invites typos/duplication.
- **Deletion anomaly**: deleting a customer's last remaining order would silently delete all record of that customer too.

The root cause: non-key attributes (`customer_name`, `customer_email`, `customer_address`) depend on the **customer**, not on the **order** itself — this is a **transitive dependency** through the customer, which violates **Third Normal Form (3NF)** (every non-key attribute must depend on the key, the whole key, and nothing but the key).

**Normalizing step by step:**

- **1NF** (atomic values, no repeating groups): assume this already holds — each field holds a single value, no comma-separated lists of products in one cell.
- **2NF** (no partial dependency on part of a composite key): if `Orders` had a composite key like `(order_id, product_id)`, an attribute like `order_date` would depend only on `order_id`, not on `product_id` — so it must be pulled into its own table keyed by `order_id` alone. This motivates splitting order-level data from line-item-level data.
- **3NF** (no transitive dependency): customer attributes depend on `customer_id`, not directly on `order_id` — so they must be extracted into their own `Customers` table.

**Resulting schema:**

```sql
Customers(customer_id PK, name, email, address)
Orders(order_id PK, customer_id FK -> Customers, order_date)
Products(product_id PK, name, unit_price)
OrderItems(order_item_id PK, order_id FK -> Orders, product_id FK -> Products, quantity, price_at_purchase)
```

Now updating an email is a single-row update in `Customers`; placing a new order just references an existing `customer_id` (or creates one row in `Customers` if it's a new customer); and deleting an order never touches customer data at all.

**Trade-off worth mentioning:** normalization removes redundancy and anomalies but requires **joins** to reconstruct a full order view (`Orders` ⋈ `Customers` ⋈ `OrderItems` ⋈ `Products`), which costs more at read time. For read-heavy analytical workloads, teams sometimes deliberately **denormalize** (e.g. a reporting table or materialized view that flattens this back out) as a performance optimization — but that's a conscious trade-off made on top of a normalized source of truth, not a substitute for having one.

### 3. OOP (Comparison)

Compare **composition** and **inheritance** as two ways to reuse code and model relationships between classes in object-oriented design. What does the principle "favor composition over inheritance" mean, and why is it generally considered good practice? Illustrate with a short example.

**Answer:**

| Aspect | Inheritance ("is-a") | Composition ("has-a") |
|---|---|---|
| Relationship | Subclass *is a* specialized kind of its superclass. | An object *has a* reference to another object and delegates work to it. |
| Coupling | Tight — subclass depends on the base class's internal implementation details, not just its public interface (the "fragile base class" problem: a seemingly safe change to the base can silently break subclasses). | Loose — the containing object only depends on the contained object's public interface. |
| Binding time | Fixed at compile time; the class hierarchy can't be rearranged once the program is running. | Flexible at runtime — you can swap in a different implementation object (e.g. inject a different strategy/dependency) while the program runs. |
| Code reuse mechanism | Reuse by extending a base class. | Reuse by delegating calls to a held object. |
| Risk of misuse | Easy to build deep, rigid hierarchies, or to force an "is-a" relationship that doesn't really hold (e.g. `Square extends Rectangle` breaks if `Rectangle` allows independently setting width and height, violating the Liskov Substitution Principle). | Requires a bit more boilerplate (explicit delegation) but avoids hierarchy misuse entirely. |

**"Favor composition over inheritance"** means: when you want to reuse behavior, prefer giving a class a reference to another object that provides that behavior, rather than extending a base class to inherit it — unless a true, stable "is-a" relationship exists and you specifically need polymorphic substitution.

**Example — the classic "flying duck" problem:**

*Inheritance version (problematic):*
```cpp
class Bird {
public:
    virtual void fly() { cout << "Flap flap, flying!\n"; }
};
class Duck : public Bird {};          // fine, ducks fly
class RubberDuck : public Bird {};    // broken: inherits fly() but shouldn't fly!
```
Here, every `Bird` subclass is forced to inherit `fly()`, even ones that shouldn't (a rubber duck). Fixing it by overriding `fly()` to do nothing in `RubberDuck` is a code smell, and the hierarchy only gets messier as more flightless/non-standard birds are added.

*Composition version (Strategy pattern):*
```cpp
class FlyBehavior {
public:
    virtual void fly() = 0;
};
class FlyWithWings : public FlyBehavior {
public:
    void fly() override { cout << "Flap flap, flying!\n"; }
};
class CannotFly : public FlyBehavior {
public:
    void fly() override { cout << "I can't fly.\n"; }
};

class Duck {
    FlyBehavior* flyBehavior;   // Duck HAS-A FlyBehavior, doesn't inherit one
public:
    Duck(FlyBehavior* fb) : flyBehavior(fb) {}
    void performFly() { flyBehavior->fly(); }
};
```
Now flying behavior is an independent, swappable object. A `RubberDuck` is simply constructed with a `CannotFly` behavior instead of `FlyWithWings` — no broken inheritance, and behavior can even be changed at runtime by assigning a different `FlyBehavior*`.

**Why this matters:** Composition keeps classes small, testable in isolation (you can mock the composed dependency), and flexible to changing requirements without rewriting a class hierarchy — which is why most modern design patterns (Strategy, Decorator, Dependency Injection) are built around composition rather than deep inheritance trees. Inheritance still has its place (true "is-a" relationships with stable contracts, e.g. `Circle`/`Square` both genuinely *are* `Shape`s for the purpose of computing `area()`), but it should be the exception reached for deliberately, not the default tool for code reuse.
