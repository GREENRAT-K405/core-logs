### Question: Construct Binary Tree from Preorder and Inorder Traversal (Trees — Medium)

**Problem Statement**

Given two integer arrays `preorder` and `inorder`, where `preorder` is the preorder traversal of a binary tree and `inorder` is the inorder traversal of the *same* tree, construct and return the binary tree. All node values in the tree are unique.

**Input/Output Format**

- Input: `preorder` (vector of ints), `inorder` (vector of ints), both of the same length, describing one valid binary tree.
- Output: the root pointer of the reconstructed binary tree.

**Examples**

1. Input: `preorder = [3,9,20,15,7]`, `inorder = [9,3,15,20,7]` → Output: the tree `3(left=9, right=20(left=15, right=7))`.
2. Input: `preorder = [-1]`, `inorder = [-1]` → Output: a single node with value `-1`.
3. Input: `preorder = [1,2,3]`, `inorder = [3,2,1]` → Output: a left-skewed chain `1 -> left 2 -> left 3`.

**Constraints**

- `1 <= preorder.length <= 3000`
- `inorder.length == preorder.length`
- `-3000 <= Node.val <= 3000`
- All values in `preorder` and `inorder` are unique.
- `inorder` is guaranteed to be the inorder traversal of the tree; `preorder` is guaranteed to be the preorder traversal of the same tree.

### Step-by-Step Walkthrough

**What each traversal tells you.** Preorder visits `root, left subtree, right subtree` — so `preorder[0]` is *always* the root of whatever subtree we're currently building. Inorder visits `left subtree, root, right subtree` — so once we know which value is the root, its position in the inorder array splits that array cleanly into "everything in the left subtree" (before it) and "everything in the right subtree" (after it).

**The recursive idea.** That gives a direct recursion:
1. The next unused value in `preorder` is the root of the current subtree.
2. Look up that value's index in `inorder`. Everything to its left (within the current inorder range) belongs to the left subtree; everything to its right belongs to the right subtree.
3. Recurse to build the left subtree first (because preorder visits left before right), then the right subtree, consuming `preorder` values left-to-right as we go.

**Avoiding the naive O(n²) trap.** A straightforward implementation slices `inorder` into new sub-vectors at every call and does a linear scan to find the root's index each time — that's O(n) work per node, O(n²) overall, and it also copies memory unnecessarily. Two fixes:
- **Hashmap for index lookup.** Precompute `value -> index in inorder` once, up front, turning "find the root in inorder" into O(1).
- **Index range instead of sub-vectors.** Never copy `preorder`/`inorder`. Instead pass `(inStart, inEnd)` bounds into the *original* `inorder` array, and track a single shared "next preorder index to consume" (passed by reference) instead of slicing `preorder`. The size of the left subtree is simply `rootIdx - inStart`, so we know exactly how many preorder entries belong to the left recursive call before we even make it — we don't need to pass that count explicitly, because the preorder pointer naturally consumes the right number of entries as the left recursion runs to completion before the right one starts.

**Why it's correct.** At every recursive call, `(inStart, inEnd)` exactly identifies the inorder slice of some subtree, and the next unconsumed `preorder` value is guaranteed (by the definition of preorder traversal) to be that subtree's root. Splitting on the root's inorder index correctly partitions the remaining nodes into left/right children, and consuming `preorder` left-to-right while recursing left-before-right keeps the shared pointer synchronized with which subtree is currently being built.

**Complexity.**
- Time: O(n) — building the hashmap is O(n), and each of the n nodes is created and processed exactly once in O(1) work (map lookup + pointer increment).
- Space: O(n) — O(n) for the hashmap, plus O(h) recursion stack (worst case O(n) for a skewed tree), plus O(n) for the output tree itself.

### C++ Code

```cpp
#include <vector>
#include <unordered_map>
using namespace std;

struct TreeNode {
    int val;
    TreeNode *left;
    TreeNode *right;
    TreeNode(int x) : val(x), left(nullptr), right(nullptr) {}
};

class Solution {
public:
    TreeNode* buildTree(vector<int>& preorder, vector<int>& inorder) {
        // Map each value to its index in inorder for O(1) root-split lookups.
        unordered_map<int, int> inIndex;
        for (int i = 0; i < (int)inorder.size(); i++) {
            inIndex[inorder[i]] = i;
        }

        int preIdx = 0; // next unused index into preorder, shared across the whole recursion
        return build(preorder, preIdx, 0, (int)inorder.size() - 1, inIndex);
    }

private:
    // Builds the subtree whose inorder values occupy inorder[inStart..inEnd].
    TreeNode* build(vector<int>& preorder, int& preIdx, int inStart, int inEnd,
                     unordered_map<int, int>& inIndex) {
        if (inStart > inEnd) return nullptr; // empty subtree

        int rootVal = preorder[preIdx++];       // next preorder value is this subtree's root
        TreeNode* root = new TreeNode(rootVal);
        int rootIdx = inIndex[rootVal];          // split point within inorder

        // Preorder processes left before right, so recurse left first: this keeps
        // preIdx correctly synchronized with which subtree is currently being built.
        root->left = build(preorder, preIdx, inStart, rootIdx - 1, inIndex);
        root->right = build(preorder, preIdx, rootIdx + 1, inEnd, inIndex);
        return root;
    }
};
```

## CS Fundamentals

### 1. Computer Architecture (Conceptual/Definition)

**Question:** What is cache coherence, and why do multi-core systems need a protocol like MESI to maintain it?

**Answer:**

**Cache coherence** is the guarantee that all cores in a multi-core system see a *consistent* view of memory, even though each core has its own private cache holding copies of the same underlying data. Without it, one core could update a value in its own cache while another core keeps reading a stale copy from its own cache — the two cores would silently disagree about the current value of the same memory location.

**Why this happens at all.** Modern CPUs give each core an L1 (and often private L2) cache purely for speed — going to main memory on every access would be far too slow. But once multiple caches can each hold a copy of the same cache line, a write by one core has to somehow be reflected (or at least accounted for) in every other core's copy, or correctness breaks.

**Concrete failure without coherence:** Core A and Core B both cache the line holding a shared counter `x = 5`. Core A increments it to `6` in its own cache but the write never propagates. Core B, still holding its cached `5`, reads `5` again — and if B also increments and writes back `6`, A's increment is silently lost. This is a real, observable bug class in naive shared-memory systems.

**How MESI solves it.** MESI is a protocol that tags every cache line in every core's cache with one of four states:
- **Modified (M)** — this cache holds the only copy, and it has been written; it differs from main memory and must eventually write back.
- **Exclusive (E)** — this cache holds the only copy, and it matches main memory (not yet written).
- **Shared (S)** — multiple caches may hold this line, all matching main memory.
- **Invalid (I)** — this cache's copy is stale/unusable and must be re-fetched.

Cores communicate over a shared bus (or interconnect) using coherence messages: before a core writes to a line, it broadcasts an invalidation so every other cached copy transitions to Invalid; before a core reads a line another core has Modified, that other core must supply the up-to-date value (write it back or forward it) rather than let the reader see stale memory. This turns "who has the latest copy" into an explicit, enforced state machine instead of an accident of timing.

**Why it matters in practice:** cache coherence protocols are the hardware-level reason higher-level concurrency primitives (mutexes, atomics, memory fences) behave predictably across cores — but coherence alone only guarantees *a* consistent view of individual memory locations, not the *ordering* of operations across multiple locations. That ordering problem is what memory models and explicit synchronization (locks, atomics with the right memory order) exist to solve on top of a coherent cache system.

### 2. OOP (Comparison)

**Question:** What is the difference between composition and inheritance as ways to reuse code, and why is "favor composition over inheritance" such common advice?

**Answer:**

Both let one class reuse behavior defined elsewhere, but they create a very different kind of relationship between the classes involved.

**Inheritance** models an **is-a** relationship. A subclass extends a base class, automatically acquiring its fields and methods, and can override behavior. `class Car extends Vehicle` says "a Car *is a* Vehicle." The coupling is tight and fixed at compile time: the subclass is bound to exactly one base class's implementation (in single-inheritance languages), inherits *everything* whether it wants it or not, and any change to the base class's internals can silently change subclass behavior — the classic "fragile base class" problem.

**Composition** models a **has-a** relationship. A class holds a reference to another object and delegates work to it, rather than inheriting from it. `class Car { private Engine engine; }` says "a Car *has an* Engine." The coupling is through a chosen interface only — the `Car` only depends on whatever methods of `Engine` it actually calls — and the relationship can be assembled or swapped at runtime (pass in a `PetrolEngine` or an `ElectricEngine`), not locked in at compile time.

| | Inheritance | Composition |
| --- | --- | --- |
| Relationship | is-a | has-a |
| Binding | Compile-time, fixed | Runtime, swappable |
| Coupling | Tight — exposes base internals | Loose — only the used interface |
| Reuse granularity | All-or-nothing (whole base class) | Pick exactly what's needed |
| Common failure mode | Fragile base class, deep rigid hierarchies | Slightly more boilerplate (delegation) |

**Why composition is generally favored:** deep inheritance hierarchies tend to become rigid over time — a change three levels up can ripple unpredictably down to every descendant, and forcing real-world relationships into strict single-parent trees often doesn't fit (a `Duck` is a `Bird` and can `Fly`, but a `Penguin` is also a `Bird` and *cannot* — inheritance pushes you toward awkward overrides or exceptions to model this, whereas composing in a `FlyBehavior` object lets each duck-like class simply plug in the behavior it actually has). Composition keeps components independently testable and swappable, at the modest cost of writing explicit delegation methods.

**Where inheritance still earns its place:** genuine is-a hierarchies with a stable, narrow shared contract (e.g., implementing a common interface, or a small class hierarchy that truly won't grow more special cases) — and, practically, wherever a framework requires subclassing to hook into its lifecycle. The advice isn't "inheritance is wrong," it's "don't reach for it by default when a has-a relationship would be looser and more flexible."

### 3. Computer Networks (Scenario/Applied)

**Question:** You're designing two features for the same app: (1) a live video call, and (2) downloading a large file attachment. Which transport protocol — TCP or UDP — would you choose for each, and why?

**Answer:**

The right choice depends on what each feature actually needs to guarantee, because TCP and UDP make opposite trade-offs between **reliability** and **latency**.

**TCP (Transmission Control Protocol)** is connection-oriented and guarantees reliable, ordered, complete delivery: it establishes a connection (three-way handshake), acknowledges every segment, retransmits anything lost, and reorders segments that arrive out of sequence — all invisibly to the application. The cost is overhead and latency: handshake setup time, acknowledgment round-trips, and — critically — **head-of-line blocking**, where a single lost packet stalls delivery of every packet after it until the lost one is retransmitted and arrives.

**UDP (User Datagram Protocol)** is connectionless and delivers datagrams on a best-effort basis: no handshake, no acknowledgments, no retransmission, no guaranteed ordering. A lost packet is just lost — the application finds out only if it's built to notice. In exchange, there's minimal overhead and no head-of-line blocking: later packets are never held hostage by an earlier lost one.

**File download → TCP.** Every byte of the file matters, and the file is useless if even one chunk is silently missing or corrupted — you cannot "skip" a missing piece of a `.zip` or `.pdf` and still get a usable file. There's no strict real-time deadline (a few extra hundred milliseconds from a retransmission is completely acceptable), so TCP's reliability guarantees are exactly what's needed and its latency cost is irrelevant to the use case.

**Live video call → UDP** (typically carrying RTP on top of it). Here, *timeliness* matters more than *completeness*: a frame that arrives late is worse than useless, since by the time it's retransmitted and arrives, the call has moved on and the audio/video would visibly stutter waiting for it. It's far better to drop one video frame or a few milliseconds of audio (perceived as a brief glitch) than to freeze the entire stream waiting for TCP to retransmit and re-order one lost packet. Real-time video/voice stacks handle the residual unreliability themselves at the application layer — packet loss concealment, forward error correction, adaptive bitrate — rather than paying TCP's ordering/retransmission cost for every packet.

**The general principle:** choose TCP when correctness and completeness of the data itself is the requirement (files, web pages, API calls, database traffic); choose UDP when timeliness matters more than perfect delivery and the application can tolerate or compensate for loss (live media, real-time gaming state, DNS's quick single-round-trip queries).
