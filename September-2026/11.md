## DSA

### Question: Edit Distance (Dynamic Programming — Hard)

**Problem Statement**

Given two strings `word1` and `word2`, return the minimum number of operations required to convert `word1` into `word2`. You may perform any of the following three operations on `word1`, any number of times:

1. Insert a character
2. Delete a character
3. Replace a character

**Input/Output Format**

- Input: two strings `word1` and `word2`.
- Output: an integer — the minimum number of operations.

**Examples**

1. Input: `word1 = "horse"`, `word2 = "ros"` → Output: `3`
   (`horse` → `rorse` (replace `h` with `r`) → `rose` (delete `r`) → `ros` (delete `e`))
2. Input: `word1 = "intention"`, `word2 = "execution"` → Output: `5`
3. Input: `word1 = ""`, `word2 = "abc"` → Output: `3` (three inserts, since the source is empty)

**Constraints**

- `0 <= word1.length, word2.length <= 500`
- `word1` and `word2` consist of lowercase English letters.

### Step-by-Step Walkthrough

**Why brute force fails.** Trying every sequence of inserts/deletes/replaces is a branching recursion — at each pair of positions you could take three different actions, and the recursion tree is exponential in the string lengths. But the recursion has a huge amount of overlapping structure: the sub-problem "minimum edits to turn the first `i` characters of `word1` into the first `j` characters of `word2`" gets recomputed over and over from different paths. That's the signature of a dynamic programming problem.

**Defining the state.** Let `dp[i][j]` = the minimum number of operations to convert the first `i` characters of `word1` into the first `j` characters of `word2`. The answer we want is `dp[m][n]` where `m = word1.length()`, `n = word2.length()`.

**Base cases.** Converting an empty prefix into a `j`-length prefix takes exactly `j` insertions, so `dp[0][j] = j`. Symmetrically, converting an `i`-length prefix into an empty string takes `i` deletions, so `dp[i][0] = i`.

**The recurrence.** To compute `dp[i][j]`, look at the last characters of the two prefixes, `word1[i-1]` and `word2[j-1]`:

- **If they match**, no edit is needed at this position — the cost is whatever it took to convert the strings *without* these last characters: `dp[i][j] = dp[i-1][j-1]`.
- **If they don't match**, we must spend exactly one operation here, and we pick whichever of the three options leaves the smallest remaining sub-problem:
  - **Replace** `word1[i-1]` with `word2[j-1]`: now both last characters "match" by construction, so what remains is `dp[i-1][j-1]`.
  - **Delete** `word1[i-1]`: what remains is converting the first `i-1` characters of `word1` into all `j` characters of `word2`, i.e. `dp[i-1][j]`.
  - **Insert** `word2[j-1]` at the end of `word1`'s current prefix: what remains is converting all `i` characters of `word1` into the first `j-1` characters of `word2`, i.e. `dp[i][j-1]`.

  So `dp[i][j] = 1 + min(dp[i-1][j-1], dp[i-1][j], dp[i][j-1])`.

**Why this is correct.** Any optimal sequence of edits transforming one prefix into another must end with *some* last decision about the final characters — either they already agreed, or the last edit applied was a replace, delete, or insert touching the tail. Those are exactly the three cases enumerated above, and by the optimal-substructure property, the best total cost is the best combination of "cost of that last step" plus "optimal cost of the resulting sub-problem." Building the table bottom-up (increasing `i`, then `j`) guarantees every `dp[i-1][*]` and `dp[*][j-1]` value is already finalized before it's needed.

**Complexity.**
- Time: O(m·n) — one constant-time computation per cell of an (m+1)×(n+1) table.
- Space: O(m·n) for the full table as written below. This can be reduced to O(min(m,n)) by only keeping the previous and current rows, since `dp[i][*]` only ever depends on row `i-1` and the current row — not shown here for clarity, but worth knowing for a follow-up "optimize the space" question.

### C++ Code

```cpp
#include <vector>
#include <string>
#include <algorithm>
using namespace std;

int minDistance(const string& word1, const string& word2) {
    int m = (int)word1.size();
    int n = (int)word2.size();

    // dp[i][j] = min operations to convert word1[0..i) into word2[0..j)
    vector<vector<int>> dp(m + 1, vector<int>(n + 1, 0));

    // Base cases: converting to/from an empty prefix costs that many
    // inserts (dp[0][j] = j) or deletes (dp[i][0] = i).
    for (int i = 0; i <= m; i++) dp[i][0] = i;
    for (int j = 0; j <= n; j++) dp[0][j] = j;

    for (int i = 1; i <= m; i++) {
        for (int j = 1; j <= n; j++) {
            if (word1[i - 1] == word2[j - 1]) {
                // Last characters already agree; no operation spent here.
                dp[i][j] = dp[i - 1][j - 1];
            } else {
                dp[i][j] = 1 + min({
                    dp[i - 1][j - 1], // replace word1[i-1] with word2[j-1]
                    dp[i - 1][j],     // delete word1[i-1]
                    dp[i][j - 1]      // insert word2[j-1] after word1's prefix
                });
            }
        }
    }

    return dp[m][n];
}
```

The `min({...})` form uses the three-argument `std::initializer_list` overload of `std::min` from `<algorithm>`, which reads more clearly than nesting two binary `min` calls.

## CS Fundamentals

### 1. DBMS (Conceptual)

What are the first three normal forms (1NF, 2NF, 3NF) in relational database design? Explain what each one rules out, and give an example of a table that violates each.

**Answer:**

Normalization is the process of structuring tables so that each fact is stored in exactly one place, which eliminates specific classes of update/insert/delete anomalies. Each normal form fixes a stronger version of the same underlying problem: redundant, dependent data.

**1NF — First Normal Form.** Every column must hold a single, atomic value (no repeating groups or lists inside a cell), and every row must be uniquely identifiable.
*Violation example:* a `Students` table with a column `Phones = "9998887777, 8887776666"`. You can't easily query "students with a given phone number" or update one number without parsing a string. The fix is a separate `StudentPhones` table with one row per (student, phone).

**2NF — Second Normal Form.** Must already be in 1NF, and additionally every non-key column must depend on the *whole* primary key, not just part of it. This only matters when the primary key is composite (more than one column).
*Violation example:* an `OrderItems` table keyed on `(OrderID, ProductID)` that also stores `ProductName`. `ProductName` depends only on `ProductID`, not on the full key — so the same product name is duplicated across every order that includes it, and if the product is renamed you must update every row. The fix is to move `ProductName` into a `Products` table keyed by `ProductID` alone.

**3NF — Third Normal Form.** Must already be in 2NF, and additionally no non-key column may depend on another *non-key* column (no "transitive dependency").
*Violation example:* an `Employees` table with columns `EmployeeID (key), DepartmentID, DepartmentName`. `DepartmentName` depends on `DepartmentID`, not directly on `EmployeeID` — it's a fact about the department, riding along on the employee row. If a department is renamed, every employee row referencing it must be updated, and if a department temporarily has zero employees, its name isn't stored anywhere. The fix is a separate `Departments` table.

**Why it matters in practice:** each higher normal form removes a specific category of anomaly, but at the cost of more joins at query time. Real systems often normalize to 3NF (or Boyce-Codd Normal Form) for correctness, then deliberately *denormalize* specific hot paths — pre-joining or caching data — once the redundancy problem is understood well enough to accept the trade-off consciously rather than by accident.

### 2. System Design Basics (Scenario)

You're asked to design a URL shortener like bit.ly: given a long URL, produce a short code that redirects to it. Walk through the core components, how you'd generate the short codes so they don't collide at scale, and how redirects stay fast.

**Answer:**

**Core components:**
1. **Write path (shorten):** client sends a long URL → service generates a short code → stores the mapping `{short_code → long_url}` → returns `https://short.ly/{short_code}`.
2. **Read path (redirect):** client requests `https://short.ly/{short_code}` → service looks up the long URL → responds with an HTTP `301`/`302` redirect.
3. **Storage:** a key-value store (or a simple relational table with `short_code` as the primary key) mapping codes to URLs, plus metadata like creation time and click count.

**Generating the short code without collisions at scale** is the crux of the design, and there are two main strategies:

- **Counter + base62 encoding.** Maintain a globally unique, monotonically increasing ID (e.g. from a database auto-increment, or a dedicated ID-generation service like Twitter's Snowflake so a single DB isn't a bottleneck). Encode that integer in base62 (`[a-zA-Z0-9]`) to get a short, dense string — a 62^6 ≈ 56 billion keyspace at 6 characters. This guarantees uniqueness by construction (no collision check needed) since IDs never repeat, and IDs can be handed out in pre-allocated blocks to multiple servers to avoid a single point of contention.
- **Hash-based (e.g. MD5/SHA of the long URL, truncated).** Simpler conceptually, but truncating a hash to a short length reintroduces collisions, so you need a check-and-retry (or append a salt/counter) loop against the datastore before accepting a code. This trades a guarantee for simplicity and can degrade under high write throughput due to retries.

The counter approach is generally preferred at scale precisely because it avoids collision-detection round-trips on the write path.

**Keeping redirects fast:** the read path is read-heavy and latency-sensitive (every redirect is on a user's critical path), so:
- Put a **cache** (e.g. Redis) in front of the datastore for hot short codes — most traffic concentrates on a small fraction of links (a classic power-law/Zipfian access pattern).
- Use a `301` (permanent) redirect if you want browsers/CDNs to cache the redirect themselves and skip your service on repeat visits, or a `302` (temporary) if you need every click to hit your service — e.g. to count analytics accurately. This is a genuine trade-off between server load and click-tracking accuracy.
- Shard the datastore by short code (e.g. consistent hashing) once a single node can't hold the keyspace or the request volume, since lookups are always by exact key and need no cross-shard joins.

**Why this decomposition matters:** the interviewer is really testing whether you can separate "guarantee uniqueness cheaply" (counter+encode) from "serve reads fast at scale" (cache + CDN-friendly redirect codes) — conflating the two into "just hash it and check the database" is the most common weak answer.

### 3. Computer Architecture (Comparison)

Compare RISC and CISC instruction set architectures. What design trade-off separates them, and why do modern CPUs (e.g. x86) blur the line between the two?

**Answer:**

**RISC (Reduced Instruction Set Computer)** and **CISC (Complex Instruction Set Computer)** represent two different answers to the question "where should complexity live — in hardware or in software (the compiler)?"

| | RISC | CISC |
|---|---|---|
| Instruction count | Small, simple instruction set | Large, includes complex multi-step instructions |
| Instruction size | Fixed-length (easy to decode/pipeline) | Variable-length |
| Execution model | One instruction ≈ one cycle (roughly) | A single instruction can take many cycles |
| Memory access | Only via explicit `load`/`store`; ALU ops work on registers | Instructions can operate directly on memory operands |
| Compiler's job | Does more work — breaks complex operations into sequences of simple ones | Does less work — can emit one instruction for a complex operation |
| Design goal | Simpler, faster hardware; easier to pipeline | Fewer instructions per program; denser code |
| Examples | ARM, MIPS, RISC-V | x86 (classic), VAX |

**The core trade-off:** CISC tries to reduce the *number of instructions* a program needs by making each instruction do more (e.g. a single `x86` instruction can load from memory, add, and store the result back). RISC instead makes every instruction uniform and minimal, accepting that a program will need *more* instructions, in exchange for hardware that is dramatically simpler to design, verify, and — critically — pipeline. Fixed-length, single-cycle-ish instructions are far easier to fetch, decode, and overlap across pipeline stages than variable-length instructions whose decoded length you don't know until you've partially decoded them.

**Why modern x86 blurs the line:** since the Pentium Pro era, x86 CPUs internally translate incoming CISC instructions into simpler, fixed-format **micro-operations (µops)** at decode time, and it's the µops — not the raw x86 instructions — that actually flow through the pipeline, get scheduled out of order, and execute. In other words, modern x86 chips have a CISC *instruction set* (for backward compatibility with decades of software) sitting on top of a RISC-*style* execution core internally. This is why the RISC-vs-CISC debate, while historically real (it drove genuine architecture wars in the 1980s–90s), matters less at the hardware-implementation level today — it's now more about the external contract a chip presents to compilers than a fundamental limit on how fast that chip's internals can run.
