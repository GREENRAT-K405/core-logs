### Question: Candy (Greedy — Hard)

There are `n` children standing in a line. Each child is assigned a rating value given in the integer array `ratings`.

You are giving candies to these children subject to the following requirements:
- Each child must have **at least one** candy.
- Children with a **higher rating** get **more candies** than their immediate neighbors (both left and right neighbors, independently).

Return the **minimum** total number of candies needed to satisfy all children.

**Input format:**
- An integer array `ratings` of length `n`, where `ratings[i]` is the rating of the `i`-th child.

**Output format:**
- A single integer: the minimum total number of candies required.

**Worked Examples:**

1. `ratings = [1, 0, 2]` → output `5`.
   One valid distribution: `candies = [2, 1, 2]`. Child 0 (rating 1) > child 1 (rating 0), so child 0 needs more than child 1. Child 2 (rating 2) > child 1 (rating 0), so child 2 needs more than child 1. Total = `2 + 1 + 2 = 5`.

2. `ratings = [1, 2, 2]` → output `4`.
   One valid distribution: `candies = [1, 2, 1]`. Child 1 (rating 2) > child 0 (rating 1), so child 1 gets more. Child 2 has the *same* rating as child 1 (not higher), so it does **not** need more candy than child 1 — it can safely drop back to 1. Total = `1 + 2 + 1 = 4`.

3. `ratings = [1, 3, 4, 5, 2]` → output `11`.
   One valid distribution: `candies = [1, 2, 3, 4, 1]`. The strictly increasing run `1 < 3 < 4 < 5` forces strictly increasing candies `1, 2, 3, 4`; the final child (rating 2) only needs to beat its own neighbor constraints, which are already satisfied by `candies[3] = 4 > 1`. Total = `1 + 2 + 3 + 4 + 1 = 11`.

**Constraints:**
- `1 <= n <= 2 * 10^4`
- `0 <= ratings[i] <= 2 * 10^4`

---

### Step-by-Step Walkthrough

**Approach — Two-Pass Greedy**

The rule "a higher-rated child must get more candy than a neighbor" is really **two separate local constraints** per child: one relative to the left neighbor, and one relative to the right neighbor. A single left-to-right (or right-to-left) sweep can only enforce one of these at a time, so the trick is to run **two passes** and combine them.

1. **Initialize:** Create a `candies` array of length `n`, all set to `1` (everyone gets the mandatory minimum).

2. **Left-to-right pass (enforces the "left neighbor" rule):**
   For `i` from `1` to `n-1`:
   - If `ratings[i] > ratings[i-1]`, then child `i` must have more candy than child `i-1`, so set `candies[i] = candies[i-1] + 1`.
   - Otherwise, leave `candies[i]` as is for now (it will be fixed, if needed, by the second pass).
   After this pass, every strictly increasing run (left to right) has strictly increasing candy counts.

3. **Right-to-left pass (enforces the "right neighbor" rule):**
   For `i` from `n-2` down to `0`:
   - If `ratings[i] > ratings[i+1]`, then child `i` must have more candy than child `i+1`. But child `i` might already have a large value from the first pass (to satisfy its left neighbor), so we must not overwrite that — we take `candies[i] = max(candies[i], candies[i+1] + 1)`.
   - Otherwise, leave `candies[i]` unchanged.

4. **Sum up** the final `candies` array — that's the answer.

**Why this works:** The first pass guarantees the "increasing from the left" constraint holds everywhere, and never violates the "increasing from the right" constraint because it never *decreases* any value. The second pass then patches in whatever additional candy is needed to satisfy the "increasing from the right" constraint, using `max` specifically so it never undoes what the first pass already established. Since each child's final candy count is the max of what each direction independently requires, and each of those two per-direction requirements is itself correct and minimal (proved by induction along each pass: a run of length `k` needs candies `1, 2, ..., k`, which is the fewest values satisfying a strictly increasing chain of constraints), the combined value is the true minimum that satisfies both directions simultaneously.

**Complexity Analysis:**
- **Time complexity:** `O(n)` — exactly two linear passes over the array, plus a linear sum at the end.
- **Space complexity:** `O(n)` for the `candies` array. (This can't easily be reduced below `O(n)` with the two-pass approach, though an `O(1)`-extra-space single-pass slope-counting variant exists as a further optimization.)

---

### C++ Code

```cpp
#include <iostream>
#include <vector>
#include <algorithm>
using namespace std;

class Solution {
public:
    int candy(vector<int>& ratings) {
        int n = ratings.size();
        if (n == 0) return 0;

        // Step 1: everyone starts with the mandatory minimum of 1 candy.
        vector<int> candies(n, 1);

        // Step 2: left-to-right pass -- enforce "beat your left neighbor" rule.
        for (int i = 1; i < n; ++i) {
            if (ratings[i] > ratings[i - 1]) {
                candies[i] = candies[i - 1] + 1;
            }
        }

        // Step 3: right-to-left pass -- enforce "beat your right neighbor" rule,
        // using max() so we never undo progress made by the left-to-right pass.
        for (int i = n - 2; i >= 0; --i) {
            if (ratings[i] > ratings[i + 1]) {
                candies[i] = max(candies[i], candies[i + 1] + 1);
            }
        }

        // Step 4: total candies needed is just the sum of the final array.
        int total = 0;
        for (int c : candies) total += c;
        return total;
    }
};

int main() {
    Solution sol;

    vector<int> r1 = {1, 0, 2};
    cout << "candy([1,0,2]) = " << sol.candy(r1) << " (expected 5)" << endl;

    vector<int> r2 = {1, 2, 2};
    cout << "candy([1,2,2]) = " << sol.candy(r2) << " (expected 4)" << endl;

    vector<int> r3 = {1, 3, 4, 5, 2};
    cout << "candy([1,3,4,5,2]) = " << sol.candy(r3) << " (expected 11)" << endl;

    return 0;
}
```

**Trace against the examples:**
- `[1,0,2]`: left pass → `[1,1,1]` (nothing increases left-to-right since ratings go down then up but 2>0 not 2>previous-left which is index1's rating 0 -- wait 2>0 is comparing index2 to index1, so candies[2]=candies[1]+1=2) → `[1,1,2]`. Right pass: `i=1`: `ratings[1]=0 < ratings[2]=2`, skip. `i=0`: `ratings[0]=1 > ratings[1]=0` → `candies[0] = max(1, candies[1]+1) = max(1, 2) = 2`. Final `[2,1,2]`, sum `5`. ✓
- `[1,2,2]`: left pass → `[1,2,1]` (`ratings[2]=2` is not `> ratings[1]=2`, so stays 1). Right pass: `i=1`: `ratings[1]=2` not `> ratings[2]=2`, skip. `i=0`: `ratings[0]=1 < ratings[1]=2`, skip. Final `[1,2,1]`, sum `4`. ✓
- `[1,3,4,5,2]`: left pass → `[1,2,3,4,1]`. Right pass only triggers at `i=3` (`5 > 2`) → `candies[3] = max(4, 1+1) = 4` (no change). Final `[1,2,3,4,1]`, sum `11`. ✓

## CS Fundamentals

### 1. Operating Systems (Conceptual/Definition)

What is a deadlock? State the four necessary conditions (the Coffman conditions) that must all hold simultaneously for a deadlock to occur, and briefly explain how breaking just one of them prevents deadlock.

**Answer:**

A **deadlock** is a state in which a set of processes are each waiting for a resource that another process in the same set holds, so none of them can ever proceed — they are stuck waiting forever in a circular chain of dependencies.

The **four Coffman conditions** must **all** hold simultaneously for a deadlock to be possible:

1. **Mutual Exclusion** — At least one resource must be held in a non-shareable mode; only one process can use a given resource at a time (e.g., a printer, or a lock on a data structure).
2. **Hold and Wait** — A process currently holding at least one resource is simultaneously waiting to acquire additional resources that are held by other processes.
3. **No Preemption** — A resource can only be released voluntarily by the process holding it; the operating system (or another process) cannot forcibly take it away.
4. **Circular Wait** — There exists a cycle of two or more processes, each waiting for a resource held by the next process in the cycle (P1 waits on a resource held by P2, P2 waits on one held by P3, ..., Pn waits on one held by P1).

**Why breaking one condition prevents deadlock:** Since all four conditions are *necessary* (deadlock cannot occur if even one is absent), operating systems use this to design prevention strategies targeting a single condition:
- Break **Hold and Wait** by requiring processes to request all resources they will ever need up front, before execution starts (eliminates waiting while holding).
- Break **No Preemption** by allowing the OS to forcibly reclaim resources from a waiting process (used in some real-time schedulers).
- Break **Circular Wait** by imposing a global ordering on resource acquisition (every process must request resources in the same fixed order, e.g., always lock resource A before resource B), which makes a cycle structurally impossible.

**Why this matters:** Deadlock analysis is a recurring theme in OS design (and in application-level concurrency bugs, like a database transaction deadlock or two threads each locking mutexes in opposite order). Recognizing the four conditions gives a systematic way to reason about *why* a system can deadlock and lets you pick a targeted fix instead of guessing — e.g., "always acquire locks in a consistent global order" is a direct, practical application of breaking the circular-wait condition.

### 2. DBMS (Comparison)

Compare a **Clustered Index** and a **Non-Clustered Index** in a relational database. How many of each can a table have, and how does that affect lookup performance?

**Answer:**

| Aspect | Clustered Index | Non-Clustered Index |
|---|---|---|
| Physical data order | The table's actual rows are **physically stored on disk** in the order of the indexed column(s) — the index *is* the data. | A **separate structure** from the table data; it stores the indexed column's values plus a pointer (row locator / row ID, or the clustering key in databases like InnoDB) back to the actual row. |
| Count per table | Only **one** per table (since data can only be physically sorted one way). | **Multiple** allowed per table (you can have many non-clustered indexes on different columns). |
| Lookup for indexed column | Very fast — once you find the entry, the row's data is right there (no extra fetch). | Requires an extra step: find the entry in the index, then follow the pointer to fetch the actual row (called a "bookmark lookup" or "key lookup"), which is an extra I/O compared to a clustered index. |
| Storage overhead | No separate storage for the index structure itself (aside from the B-tree/B+-tree internal pages) since it *is* the table. | Additional storage required, since it duplicates the indexed column's values plus a row pointer in a separate structure. |
| Typical default | Primary key columns are often (implicitly) the clustered index in many RDBMSs (e.g., InnoDB in MySQL always clusters on the primary key). | Any other frequently-queried column (e.g., a foreign key or a column used often in `WHERE` clauses) is a good non-clustered index candidate. |
| Write cost | Inserts/updates that change the indexed column's value can be expensive since rows may need to be physically moved to maintain sort order. | Cheaper to maintain relative to physical row movement, but every additional non-clustered index still adds write overhead (the index must be updated on every insert/update/delete). |

**Why this matters:** Choosing the right column for a clustered index has an outsized performance impact because it dictates the physical layout of the entire table — e.g., clustering on a monotonically increasing key (like an auto-increment ID) keeps inserts efficient (always appending at the end), while clustering on a column with random insert patterns (like a UUID) can cause expensive page splits and fragmentation. Meanwhile, non-clustered indexes are the workhorse for speeding up arbitrary `WHERE`/`JOIN`/`ORDER BY` queries on columns other than the clustering key, at the cost of extra storage and slower writes — so index design is fundamentally a read/write performance trade-off that a DBA or backend engineer has to tune deliberately per workload.

### 3. Computer Architecture (Scenario/Applied)

You have two implementations of the same operation on a large 2D array `int arr[1000][1000]`, differing only in loop order:

```cpp
// Version A
for (int i = 0; i < 1000; i++)
    for (int j = 0; j < 1000; j++)
        arr[i][j] = arr[i][j] * 2;

// Version B
for (int j = 0; j < 1000; j++)
    for (int i = 0; i < 1000; i++)
        arr[i][j] = arr[i][j] * 2;
```

Both versions touch every element exactly once and do the same amount of arithmetic. Which one will run faster in practice, and why?

**Answer:**

**Version A will run significantly faster**, because of how CPU **cache locality** interacts with how a 2D array is actually laid out in memory.

**Why:** In C++, a 2D array like `arr[1000][1000]` is stored in **row-major order** — meaning the entire first row is laid out contiguously in memory, immediately followed by the entire second row, and so on. So `arr[i][j]` and `arr[i][j+1]` are adjacent in memory (4 bytes apart for an `int`), while `arr[i][j]` and `arr[i+1][j]` are 1000 `int`s (4000 bytes) apart.

- **Version A** iterates `j` in the inner loop while holding `i` fixed — it walks through memory **sequentially**, address by address. When the CPU fetches `arr[i][j]`, it doesn't just fetch that one integer; it pulls an entire **cache line** (typically 64 bytes = 16 `int`s) into the L1 cache. Because Version A's very next accesses (`arr[i][j+1]`, `arr[i][j+2]`, ...) are already sitting in that same cache line, most accesses become fast cache hits, with a cache miss only roughly once every 16 elements.
- **Version B** iterates `i` in the inner loop while holding `j` fixed — each successive access (`arr[i][j]`, `arr[i+1][j]`, ...) jumps 4000 bytes ahead in memory, landing in a completely different cache line almost every single time. This causes a cache miss on nearly every access, forcing the CPU to repeatedly fetch from slower L2/L3 cache or main memory (DRAM), which can be **10-100x slower** than an L1 cache hit.

Both versions execute the exact same number of multiply operations and touch the exact same set of memory addresses overall — the *only* difference is the **order** of access, but that order determines whether the memory system can exploit **spatial locality** (nearby data is fetched together and reused while it's "hot" in cache) or not.

**Why this matters:** This is a classic, easily-reproducible demonstration that "same asymptotic complexity" (both are `O(n²)` here) does not mean "same real-world performance" — cache-aware loop ordering, tiling/blocking for matrix operations, and structuring data layouts (array-of-structs vs. struct-of-arrays) are practical techniques that can yield multi-x real speedups in performance-critical code (numerical computing, game engines, databases) purely from respecting how the memory hierarchy actually works, without changing the algorithm's big-O complexity at all.
