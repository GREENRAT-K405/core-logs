### Question: Daily Temperatures (Stacks/Queues — Medium)

Given an array of integers `temperatures` representing the daily temperatures, return an array `answer` such that `answer[i]` is the number of days you have to wait after day `i` to get a **warmer** temperature. If there is no future day for which this is possible, `answer[i]` should be `0`.

**Input format:**
- An integer array `temperatures` of length `n`.

**Output format:**
- An integer array `answer` of length `n`, where `answer[i]` is the number of days until a strictly warmer temperature, or `0` if none exists.

**Worked Examples:**

1. `temperatures = [73,74,75,71,69,72,76,73]` → `[1,1,4,2,1,1,0,0]` (e.g. day `0` is `73`; the next warmer day is day `1` at `74`, so wait `1` day. Day `6` is `76`, the max in the array, so there's no warmer day after it → `0`.)
2. `temperatures = [30,40,50,60]` → `[1,1,1,0]` (strictly increasing, so each day waits exactly `1` day for the next one, and the last day has nothing after it).
3. `temperatures = [30,60,90]` → `[1,1,0]` (same idea — the last, hottest day has no future warmer day).

**Constraints:**
- `1 <= temperatures.length <= 10^5`
- `30 <= temperatures[i] <= 100`

---

### Step-by-Step Walkthrough

**Approach — Monotonic (decreasing) stack of indices**

A brute-force solution would, for each day `i`, scan forward until it finds a warmer day — that's `O(n^2)` in the worst case (e.g. strictly decreasing temperatures, where every day scans almost to the end). We can do better by noticing that once we know the answer for a *later* day, we can reuse that information instead of re-scanning.

Maintain a stack that holds **indices** of days whose "waiting for a warmer day" question is still unresolved. The key invariant is that the temperatures at the indices in the stack are always in **decreasing order from bottom to top** — as soon as that invariant would be violated by the current day, we know we've found the answer for whichever earlier days are smaller than today.

Walk through the array left to right with index `i`:

1. **Resolve everything the current day beats:** while the stack is non-empty and `temperatures[i]` is strictly greater than `temperatures[stack.top()]`, pop the top index `idx` off the stack and set `answer[idx] = i - idx` (today is the first warmer day after `idx`, and since we process left to right and only ever push/pop in order, it is guaranteed to be the *first* such day).
2. **Push the current day:** after resolving everything smaller than it, push `i` onto the stack — its own "next warmer day" is still unknown and will be resolved by some future iteration (or never, if it stays `0`).
3. After the loop finishes, any indices still left on the stack never found a warmer day, so their `answer` values correctly remain `0` (the array is initialized to all zeros up front).

**Why it works:** each index is pushed onto the stack exactly once and popped at most once, so even though there's a `while` loop nested inside the `for` loop, the *total* number of pop operations across the entire run is bounded by `n` (you can never pop more elements than you pushed). This is the standard amortized-analysis argument for monotonic stack techniques. The decreasing-order invariant guarantees correctness: whenever we pop index `idx` at step `i`, no index between `idx` and `i` could have resolved it first, because any such index would have already been popped (if it had a smaller temperature than `idx` doesn't matter — what matters is that the stack only ever holds indices not yet resolved by anything after them, so `i` is the very first one that beats `idx`).

**Complexity Analysis:**
- **Time complexity:** `O(n)` — each index is pushed once and popped at most once, so the total work across all iterations is linear, not quadratic.
- **Space complexity:** `O(n)` — for the `answer` array and, in the worst case (a strictly decreasing sequence of temperatures), the stack can hold all `n` indices at once.

### C++ Code

```cpp
#include <iostream>
#include <vector>
#include <stack>
using namespace std;

class Solution {
public:
    // Returns, for each day, how many days until a strictly warmer day (0 if none).
    vector<int> dailyTemperatures(vector<int>& temperatures) {
        int n = static_cast<int>(temperatures.size());
        vector<int> answer(n, 0);
        stack<int> st; // indices with temps in decreasing order from bottom to top, still unresolved

        for (int i = 0; i < n; i++) {
            // Pop and resolve every earlier day that today is warmer than.
            while (!st.empty() && temperatures[st.top()] < temperatures[i]) {
                int idx = st.top();
                st.pop();
                answer[idx] = i - idx;
            }
            st.push(i);
        }

        // Any indices left on the stack never found a warmer day; answer[] is already 0 there.
        return answer;
    }
};

int main() {
    Solution sol;

    // Example 1
    vector<int> t1 = {73, 74, 75, 71, 69, 72, 76, 73};
    vector<int> r1 = sol.dailyTemperatures(t1);
    cout << "[";
    for (size_t i = 0; i < r1.size(); i++) cout << r1[i] << (i + 1 < r1.size() ? "," : "");
    cout << "] (expected [1,1,4,2,1,1,0,0])" << endl;

    // Example 2
    vector<int> t2 = {30, 40, 50, 60};
    vector<int> r2 = sol.dailyTemperatures(t2);
    cout << "[";
    for (size_t i = 0; i < r2.size(); i++) cout << r2[i] << (i + 1 < r2.size() ? "," : "");
    cout << "] (expected [1,1,1,0])" << endl;

    // Example 3
    vector<int> t3 = {30, 60, 90};
    vector<int> r3 = sol.dailyTemperatures(t3);
    cout << "[";
    for (size_t i = 0; i < r3.size(); i++) cout << r3[i] << (i + 1 < r3.size() ? "," : "");
    cout << "] (expected [1,1,0])" << endl;

    return 0;
}
```

**Trace against the examples:**
- `[73,74,75,71,69,72,76,73]`: `i=0` push `0`. `i=1`: `74>73` → pop `0`, `answer[0]=1`; push `1`. `i=2`: `75>74` → pop `1`, `answer[1]=1`; push `2`. `i=3`: `71<75`, push `3` (stack: `2,3`). `i=4`: `69<71`, push `4` (stack: `2,3,4`). `i=5`: `72>69` → pop `4`, `answer[4]=1`; `72>71` → pop `3`, `answer[3]=2`; `72<75`, push `5` (stack: `2,5`). `i=6`: `76>72` → pop `5`, `answer[5]=1`; `76>75` → pop `2`, `answer[2]=4`; push `6`. `i=7`: `73<76`, push `7`. Loop ends; indices `6,7` stay `0`. Final: `[1,1,4,2,1,1,0,0]`. ✓
- `[30,40,50,60]`: each day pops the previous index immediately (`40>30`, `50>40`, `60>50`), giving `answer=[1,1,1,-]`, and index `3` is never popped, so `answer[3]=0`. Final: `[1,1,1,0]`. ✓
- `[30,60,90]`: `60>30` pops `0` → `answer[0]=1`; `90>60` pops `1` → `answer[1]=1`; index `2` never popped → `0`. Final: `[1,1,0]`. ✓

### 1. Operating Systems (Conceptual/Definition)

What is a deadlock in an operating system? State the four necessary conditions that must all hold simultaneously for a deadlock to occur, and describe one concrete strategy each for deadlock *prevention* and deadlock *avoidance*.

**Answer:**

A **deadlock** is a state in which a set of processes are each waiting for a resource that is held by another process in the same set, so that none of them can ever make progress — every process in the cycle is permanently blocked waiting on another member of that same cycle.

**The four necessary (Coffman) conditions — all four must hold at once for deadlock to be possible:**
1. **Mutual exclusion:** at least one resource must be held in a non-shareable mode — only one process can use it at a time (e.g., a printer, or a mutex-protected data structure).
2. **Hold and wait:** a process is currently holding at least one resource while simultaneously waiting to acquire additional resources that are held by other processes.
3. **No preemption:** a resource can only be released voluntarily by the process holding it — the OS cannot forcibly take it away to break the standoff.
4. **Circular wait:** there exists a cycle of processes `P1, P2, ..., Pn` where `P1` waits for a resource held by `P2`, `P2` waits for one held by `P3`, ..., and `Pn` waits for one held by `P1`.

**Deadlock prevention** (guarantee at least one of the four conditions can *never* hold, so deadlock is structurally impossible): one common technique attacks **circular wait** by imposing a global total ordering on all resource types and requiring every process to request resources only in strictly increasing order. If process `A` holds resource `1` and wants resource `2`, and process `B` holds resource `2`, then `B` is *forbidden* from ever requesting resource `1` afterward (it would be requesting "backward"), which makes a circular chain of waits impossible to form in the first place.

**Deadlock avoidance** (allow all four conditions to potentially hold, but dynamically deny any resource request that *could* lead to an unsafe state): the classic example is the **Banker's Algorithm**. Before granting a resource request, the OS simulates granting it and checks whether the system would remain in a "safe state" — meaning there still exists *some* order in which all processes could finish given their declared maximum resource needs. If granting the request would leave no such safe ordering (i.e., it risks an eventual deadlock), the OS makes the requesting process wait instead, even though the resource is currently available.

**Why this matters:** prevention is simpler to reason about but often wastes resources (e.g., forcing processes to request everything up front, or in an inconvenient order) and can hurt concurrency/throughput, while avoidance is more resource-efficient but requires the OS to know processes' maximum future resource needs in advance, which is often impractical — this is exactly the kind of correctness-vs-efficiency trade-off that shows up throughout systems design, not just in deadlock handling.

### 2. Computer Architecture (Comparison)

Compare RISC and CISC instruction set architectures across instruction complexity, cycles per instruction, and compiler/code-density trade-offs. Give one real-world CPU family that exemplifies each.

**Answer:**

| Aspect | RISC (Reduced Instruction Set Computer) | CISC (Complex Instruction Set Computer) |
|---|---|---|
| Instruction complexity | Small set of **simple**, fixed-format instructions, each doing one basic operation (e.g., a single load, store, or arithmetic op). | Larger set of instructions, some of which are **complex**, multi-step operations (e.g., a single instruction that loads from memory, does arithmetic, and stores the result back). |
| Instruction length/format | **Fixed-length** instructions (e.g., always 32 bits), which simplifies instruction decoding and pipelining. | **Variable-length** instructions, which makes decoding more complex but allows denser encoding of common operations. |
| Cycles per instruction | Designed so most instructions execute in a **single clock cycle**, favoring a deep, simple pipeline. | Instructions can take **multiple clock cycles**, since a single instruction may internally perform several micro-operations. |
| Memory access | **Load/store architecture** — only dedicated `load`/`store` instructions touch memory; all arithmetic operates on registers. | Arithmetic instructions can **operate directly on memory operands**, not just registers. |
| Code density vs. compiler complexity | Programs need **more instructions** to accomplish the same task (lower code density), but the compiler's job is simpler since each instruction does one predictable thing. | Programs can be **more compact** (higher code density) since one instruction does more work, but the compiler (or the hardware's internal micro-op translation) has a harder job exploiting that complexity efficiently. |
| Real-world example | **ARM** (used in almost all smartphones, and Apple Silicon like the M-series chips) and **RISC-V** (open ISA gaining traction in embedded and server chips). | **x86 / x86-64** (Intel and AMD desktop and server CPUs) — though modern x86 chips internally translate CISC instructions into simpler RISC-like micro-ops before execution. |

**Why this matters:** the RISC vs. CISC distinction shaped decades of CPU design, but it also illustrates a recurring architecture trade-off — pushing complexity into hardware (CISC) vs. pushing it into the compiler and software (RISC). Modern high-performance x86 chips have actually converged toward RISC-style execution internally (decoding CISC instructions into simpler micro-ops that a RISC-like pipeline executes), showing that the "purest" version of either philosophy tends to yield to whatever gets the best real-world performance and power efficiency.

### 3. OOP (Scenario/Applied)

You have a base class `Shape` with a method `area()`, and derived classes `Circle` and `Square` that each override it. You store a `Shape*` pointing to a `Circle` object and call `shapePtr->area()`. Explain what happens at runtime for this call to correctly resolve to `Circle::area()`, why this would silently break if `area()` were **not** declared `virtual`, and briefly describe the vtable/vptr mechanism that makes it work.

**Answer:**

If `area()` is declared `virtual` in `Shape`, then calling `shapePtr->area()` uses **dynamic dispatch (runtime polymorphism)**: even though `shapePtr` is declared as a `Shape*`, the actual method that runs is determined by the **real, dynamic type of the object it points to** (`Circle`), not by the pointer's compile-time (`static`) type. This is what lets code written generically against `Shape*` correctly call the right derived-class behavior without knowing at compile time exactly which subclass it's dealing with — the core mechanism behind polymorphism.

**If `area()` were NOT `virtual`:** the compiler would instead perform **static (compile-time) binding**. It would look at the *declared type* of the pointer (`Shape*`) and hard-code a direct call to `Shape::area()` at compile time, completely ignoring the fact that the object is actually a `Circle` at runtime. The call would silently compile and run — it just would silently give the *wrong* answer (the base class's area formula, or worse, undefined/nonsensical behavior if `Shape::area()` isn't even meaningful on its own), which is a notoriously hard class of bug to spot because there's no compiler error or crash — just wrong output.

**The vtable/vptr mechanism:** when a class declares (or inherits) at least one `virtual` function, the compiler generates a **virtual table (vtable)** for that class — essentially a static array of function pointers, one entry per virtual function, pointing to the correct override for that class. Every *object* of such a class then carries a hidden pointer, the **vptr**, as an extra member, set by the constructor to point to its class's vtable (a `Circle` object's vptr points to `Circle`'s vtable; a `Square` object's vptr points to `Square`'s vtable). At the call site, `shapePtr->area()` compiles down to: follow `shapePtr`'s vptr to find the object's *actual* vtable, look up the `area` slot in that table, and call whatever function pointer is stored there — which resolves to `Circle::area` because that's the vtable the `Circle` object's vptr actually points to, regardless of what static type the pointer holding it was declared as.

**Why this matters:** this is the concrete mechanism underlying nearly all object-oriented polymorphism in C++ (and conceptually similar mechanisms — often called "method tables" — exist in most OOP languages, even ones without explicit pointers). It also explains real costs: virtual calls have a small runtime overhead (an extra pointer dereference vs. a direct call) and prevent some compiler optimizations like inlining, which is why performance-critical code sometimes deliberately avoids virtual dispatch (e.g., using `final`, templates/CRTP, or non-virtual designs) when the call target is known at compile time.
