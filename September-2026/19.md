## DSA

### Question: Maximum XOR of Two Numbers in an Array (Bit Manipulation — Medium)

**Problem Statement**

Given an integer array `nums`, find the maximum possible value of `nums[i] XOR nums[j]` over all pairs `0 <= i, j < nums.length` (a number may be paired with itself, though the maximum never actually needs that).

**Input/Output Format**

- Input: an array of non-negative integers `nums`.
- Output: a single integer — the maximum XOR value achievable from any pair in the array.

**Examples**

1. Input: `nums = [3,10,5,25,2,8]` → Output: `28` (`5 XOR 25 = 28`, since `00101 ^ 11001 = 11100 = 28`)
2. Input: `nums = [14,70,53,83,49,91,36,80,92,51,66,70]` → Output: `127` (`80 XOR 92 = 127`)
3. Input: `nums = [0,0]` → Output: `0` (only one distinct value, so no pair can XOR to anything but 0)

**Constraints**

- `1 <= nums.length <= 2 * 10^5`
- `0 <= nums[i] <= 2^31 - 1`
- Aim for better than the O(n^2) brute force — O(n) or O(n log(max value)) is expected.

### Step-by-Step Walkthrough

**The obvious approach first.** Compare every pair with two nested loops and track the best XOR seen. That's O(n^2), which is far too slow for `n` up to `2 * 10^5` (4 * 10^10 comparisons). We need to avoid ever comparing most pairs directly.

**Key insight — build the answer one bit at a time, from the most significant bit down.** XOR maximization is naturally greedy on bits: getting the highest bit of the result to be `1` is worth more than getting *every* lower bit to be `1`, because a `1` at bit `k` contributes `2^k`, which is larger than the sum of all bits below it combined (`2^k - 1`). So the strategy is: decide the answer's top bit, then its next bit, and so on, always preferring a `1` when it's achievable, and never revisiting a decision once made.

**How do we check "is a 1 achievable at this bit, given the bits already fixed"?** Maintain a running `mask` that keeps only the bits decided so far (from the top down), and look only at each number's *prefix* under that mask — `num & mask`. If we've tentatively fixed the answer's top bits as `result` and are now asking "can we also set bit `k`?", the candidate value is `candidate = result | (1 << k)`. Two prefixes `p1` and `p2` XOR to exactly `candidate` if and only if `p1 ^ candidate == p2` (XOR is its own inverse). So the check becomes: does the *set* of prefixes seen so far contain, for some prefix `p`, the value `p ^ candidate`? If yes, some real pair of numbers achieves `candidate` on the bits decided so far, so we lock in `result = candidate`. If no such pair exists, we leave that bit as `0` and move to the next bit.

**Why restricting to prefixes is valid.** Once bit `k+1` and above are fixed, only the bits from `k` upward have been "spoken for" in `result`; the lower, undecided bits don't affect whether the higher bits of some pair's XOR can match `candidate`, because `p1 & mask XOR p2 & mask` depends only on bits inside `mask`. Masking off the undecided lower bits before comparing is exactly what makes the prefix comparison correct at each step — it isolates the question "can the bits I've committed to so far actually be realized by some pair" from bits I haven't decided yet.

**Algorithm.**
1. Let `mask = 0` and `result = 0`.
2. For `bit` from the highest relevant bit (30, since `nums[i] < 2^31`) down to `0`:
   - Set `mask |= (1 << bit)`.
   - Build the set `prefixes` = `{ num & mask : num in nums }`.
   - Let `candidate = result | (1 << bit)`.
   - If `candidate ^ p` is in `prefixes` for some `p` in `prefixes`, set `result = candidate` (this bit is achievable).
   - Otherwise leave `result` unchanged (this bit stays 0).
3. Return `result`.

**Complexity.**
- Time: O(32n) ≈ O(n) — 31 bit positions, and at each we do one O(n) pass to build the prefix set and check candidates (using a hash set, each lookup is O(1) expected).
- Space: O(n) — the hash set of prefixes at each bit level (rebuilt each iteration, so only one level's worth is alive at a time).

**Trace on Example 1 (`[3,10,5,25,2,8]`, binary on 5 bits: `00011, 01010, 00101, 11001, 00010, 01000`).** Working from bit 4 down: bit 4 is achievable (`25` has it, others don't — pairing `25` with any 0-prefix gives a 1 there), so `result` gains `10000`. Continuing down, the greedy process eventually locks in `11100 = 28`, matching `5 XOR 25`.

### C++ Code

```cpp
#include <vector>
#include <unordered_set>
using namespace std;

int findMaximumXOR(vector<int>& nums) {
    int result = 0;
    int mask = 0;

    // Numbers fit in 31 bits (0 <= nums[i] <= 2^31 - 1), so start at bit 30.
    for (int bit = 30; bit >= 0; --bit) {
        mask |= (1 << bit);

        // Collect the prefix (bits decided so far) of every number.
        unordered_set<int> prefixes;
        prefixes.reserve(nums.size() * 2);
        for (int num : nums) {
            prefixes.insert(num & mask);
        }

        // Try to achieve a 1 at this bit on top of the bits already fixed.
        int candidate = result | (1 << bit);

        bool achievable = false;
        for (int p : prefixes) {
            // p1 ^ p2 == candidate  <=>  p1 ^ candidate == p2
            if (prefixes.count(p ^ candidate)) {
                achievable = true;
                break;
            }
        }

        if (achievable) {
            result = candidate;
        }
        // Otherwise this bit stays 0 in result; move to the next lower bit.
    }

    return result;
}
```

Edge case sanity check: with `nums = [0, 0]`, every prefix at every bit level is `0`, so `candidate ^ p` is always `candidate` itself, which is never `0` for `candidate > 0` while only `{0}` is in the set — so no bit is ever set, and the function correctly returns `0`.

## CS Fundamentals

### 1. Computer Architecture (Conceptual/Definition)

Explain the memory hierarchy (registers, L1/L2/L3 cache, main memory, disk) and the principle of locality that makes it work. Why can a program that iterates a large 2D array in the "wrong" order run several times slower than the same program iterating it in the "right" order, even though both touch exactly the same number of elements?

**Answer:**

The memory hierarchy exists because of a hard trade-off: memory that is fast to access is expensive and physically small, while memory that is large and cheap is slow. Registers sit closest to the CPU (sub-nanosecond access, but only a handful of them); then L1 cache (~1KB–64KB, a few cycles); L2 (hundreds of KB, ~10 cycles); L3 (several MB, shared across cores, tens of cycles); then main memory / DRAM (gigabytes, ~100+ cycles — roughly 100x slower than L1); then disk/SSD (terabytes, but access measured in microseconds to milliseconds — another factor of 1000x+ slower). Each level acts as a cache for the level below it.

This hierarchy only helps because real programs exhibit **locality of reference**:

- **Temporal locality** — if a memory location was accessed recently, it's likely to be accessed again soon (e.g., a loop counter, or a variable reused across iterations).
- **Spatial locality** — if a memory location was accessed, nearby locations are likely to be accessed soon too (e.g., the next element of an array).

Caches exploit spatial locality directly: they don't fetch a single byte from main memory, they fetch an entire **cache line** (typically 64 bytes) around the requested address, betting that the surrounding bytes will be needed next.

**Why row-major vs. column-major matters.** In C++, a 2D array `int a[N][N]` is stored in **row-major order** — an entire row is contiguous in memory, and moving to the next column within a row moves to the adjacent memory address, while moving to the next row jumps forward by `N * sizeof(int)` bytes.

- Iterating `for (row) for (col) a[row][col]` walks memory sequentially. Each cache line fetch (64 bytes = 16 ints) covers 16 consecutive accesses before the next fetch is needed. This is excellent spatial locality — few cache misses.
- Iterating `for (col) for (row) a[row][col]` jumps `N * 4` bytes on every single access. If `N` is large enough that a full row doesn't fit in cache, essentially *every* access misses the cache and has to go to main memory, because the previously fetched cache line is long evicted or never reused before its neighbor would have been touched.

The two loops perform the exact same number of arithmetic operations and touch the exact same set of elements — the *only* difference is the memory access pattern — yet the column-major traversal can be 5–10x slower in practice for large matrices, purely from cache-miss latency dominating the runtime. This is the practical reason "algorithmic complexity" alone (both are O(N^2)) doesn't fully predict real-world performance: constant factors from memory access patterns can dwarf differences that Big-O notation hides.

### 2. DBMS (Comparison)

What is the difference between a clustered index and a non-clustered index? A table can have at most one clustered index but many non-clustered ones — why is that restriction inherent to what a clustered index actually is?

**Answer:**

Both are index structures (almost always B-trees) that let the database find rows without scanning the whole table, but they differ in what the leaf level of the tree actually holds.

**Clustered index.** The table's rows are physically stored on disk in the order of the indexed column(s) — the leaf nodes of the B-tree *are* the actual data rows, not just pointers to them. This means the data is only ever "in order" with respect to one key at a time. If you cluster on `id`, rows are physically laid out sorted by `id`; a range scan like `WHERE id BETWEEN 100 AND 200` reads a contiguous block of disk pages very efficiently. Most engines create a clustered index automatically on the primary key (e.g., InnoDB in MySQL always does this — if you don't declare one, it manufactures a hidden row ID to cluster on).

**Non-clustered index.** A separate structure whose leaf nodes hold the indexed column's value plus a *pointer* back to the actual row (either the physical row location, or, in InnoDB's case, the clustered index key). The table's physical row order is untouched. Looking up a value in a non-clustered index means: traverse the index B-tree to find the pointer, then follow that pointer to fetch the actual row — an extra "lookup" step (sometimes called a "bookmark lookup" or, in InnoDB, requiring a second traversal of the clustered index).

**Why only one clustered index is possible.** "Clustered" describes the *physical* storage order of the table's rows — the rows can only be sorted on disk in one order at a time, the same way a phone book's paper pages can only be sorted by last name *or* by phone number, not both simultaneously. A non-clustered index doesn't have this restriction because it's a separate structure that merely references rows wherever they physically live, so a table can carry as many non-clustered indexes as its write-performance budget allows (each one must be updated on every insert/update/delete, which is the usual reason to *not* over-index a write-heavy table).

**When to use which.** Cluster on the column most frequently used for range scans or that defines the natural physical grouping of the data (often the primary key, or a `(tenant_id, created_at)` pair in multi-tenant systems). Add non-clustered indexes for other frequently-filtered or joined columns where you need fast lookup but don't need the physical ordering.

### 3. System Design Basics (Scenario/Applied)

You're asked to add rate limiting to a public API endpoint that's getting hammered by a few abusive clients. Compare the fixed-window counter and token bucket algorithms. What specific failure mode does the fixed-window approach have, and how does token bucket avoid it?

**Answer:**

**Fixed-window counter.** Divide time into fixed windows (e.g., one-minute buckets aligned to the clock). Keep a counter per client per window; increment on each request, and reject once the counter exceeds the limit (e.g., 100 requests/minute). Reset the counter to zero when the window rolls over. This is trivial to implement (often a single key with a TTL in Redis: `INCR` + `EXPIRE`) and cheap to reason about.

**The failure mode — the boundary burst problem.** Because windows are fixed and reset abruptly, a client can send its full quota in the last instant of one window and its full quota again in the first instant of the next window. With a 100 req/min limit, a client sending 100 requests at `0:00:59.9` and another 100 at `0:01:00.1` has sent 200 requests in a 200-millisecond span — double the intended rate — yet the fixed-window counter sees two perfectly compliant windows and rejects nothing. The limiter is checking "requests since the window started," not "requests in the last 60 seconds," and those are not the same question near a boundary.

**Token bucket.** Model a bucket that holds up to `capacity` tokens, refilling at a steady rate `r` tokens/second (rather than resetting in a lump at fixed instants). Each incoming request must remove one token to proceed; if the bucket is empty, the request is rejected (or queued/delayed, depending on the design). Because refill is continuous rather than a step function at window boundaries, there is no instant at which the bucket is simultaneously "freshly full" for two different windows — the total tokens available in *any* sliding 60-second span is bounded by `min(capacity, r * 60)` regardless of where you place the window. This directly closes the boundary-burst gap: a client that drained the bucket has to wait for it to refill at the steady rate, no matter how it times its requests relative to clock boundaries.

**The trade-off token bucket buys you.** The `capacity` parameter also gives you an explicit, tunable notion of "burst allowance" — a bucket with capacity 100 and refill rate 10/sec allows a client to legitimately burst up to 100 requests instantly (useful for bursty-but-legitimate traffic, like a page load firing several API calls at once) while still capping the long-run *average* rate at 10/sec. A fixed-window counter can't express "allow bursts, but bound the sustained rate" as cleanly — its only knobs are window size and count, which conflate burst allowance and sustained rate into one number.

**In practice:** token bucket (or its close sibling, the sliding-window log/counter hybrid) is the standard choice for public-facing API rate limits precisely because it eliminates the boundary artifact; fixed-window counters remain popular only where implementation simplicity matters more than precise rate enforcement, or as a cheap first line of defense in front of a more precise limiter.
