## DSA

### Question: Binary Tree Right Side View (Trees — Medium)

Given the root of a binary tree, imagine yourself standing on the right side of it. Return the values of the nodes you can see, ordered from top to bottom.

In other words, for every level of the tree, you should return the value of the **rightmost** node at that level (the last node visible from the right side).

**Input format:**
- The root of a binary tree (nodes may have `0`, `1`, or `2` children).

**Output format:**
- A list of integers, one per level, representing the rightmost node's value at each level, ordered from the top level (root) down to the deepest level.

**Worked Examples:**

Example 1:
```
      1
    /   \
   2     3
    \     \
     5     4
```
Input: `root = [1,2,3,null,5,null,4]`
Output: `[1, 3, 4]`
Explanation: Level 0 → only `1` is visible → `1`. Level 1 → `2` and `3` exist, but `3` is rightmost → `3`. Level 2 → `5` and `4` exist, but `4` is rightmost → `4`.

Example 2:
```
   1
    \
     3
```
Input: `root = [1,null,3]`
Output: `[1, 3]`

Example 3:
```
(empty tree)
```
Input: `root = []`
Output: `[]`

**Constraints:**
- The number of nodes in the tree is in the range `[0, 100]`.
- `-100 <= Node.val <= 100`

---

### Step-by-Step Walkthrough

**Approach — Level-Order BFS, Take the Last Node of Each Level**

The "right side view" is exactly the last node visited at each level when we scan a level left-to-right. So the cleanest approach is a standard breadth-first traversal (BFS) using a queue, processing the tree one level at a time, and recording the value of the *last* node dequeued from each level.

1. If the root is `null`, return an empty result immediately — there is nothing to see.
2. Initialize a queue with the root node.
3. While the queue is not empty:
   a. Record `levelSize = queue.size()` — this tells us exactly how many nodes belong to the current level, so we can process one full level before moving to the next.
   b. Loop `levelSize` times, popping a node each time:
      - If this is the **last** iteration of the inner loop (i.e., the last node of this level), append its value to the result — it is the rightmost node visible at this depth.
      - Push its left child (if any) and then its right child (if any) onto the queue, so the next level is built up in left-to-right order.
   c. After the inner loop finishes, the queue now holds exactly the next level's nodes.
4. Return the accumulated result list.

**Why it works:** Because we always enqueue children left-before-right, the queue at any point in time contains one level's nodes in strict left-to-right order. Tracking `levelSize` at the start of each level lets us know precisely when we've reached the last (rightmost) node of that level without needing any extra bookkeeping like depth counters compared against a max-depth map.

**Alternative approach (mentioned for completeness):** A DFS that visits **right child before left child**, and records the first node it sees at each new depth, achieves the same result recursively in `O(h)` extra space (call stack) instead of `O(w)` (widest level) for BFS — but BFS is more intuitive to reason about and equally efficient asymptotically, so it's the version implemented below.

**Complexity Analysis:**
- **Time complexity:** `O(n)` — every node is enqueued and dequeued exactly once.
- **Space complexity:** `O(w)` where `w` is the maximum width (number of nodes) of any single level, since that's the maximum size the queue ever reaches. In the worst case (a perfectly balanced tree), `w = O(n)`.

### C++ Code

```cpp
#include <iostream>
#include <vector>
#include <queue>
using namespace std;

// Definition for a binary tree node.
struct TreeNode {
    int val;
    TreeNode *left;
    TreeNode *right;
    TreeNode(int x) : val(x), left(nullptr), right(nullptr) {}
};

class Solution {
public:
    vector<int> rightSideView(TreeNode* root) {
        vector<int> result;
        if (root == nullptr) {
            return result; // empty tree -> nothing visible
        }

        queue<TreeNode*> q;
        q.push(root);

        while (!q.empty()) {
            int levelSize = q.size(); // number of nodes at the current level

            for (int i = 0; i < levelSize; ++i) {
                TreeNode* node = q.front();
                q.pop();

                // The last node processed in this level is the rightmost one.
                if (i == levelSize - 1) {
                    result.push_back(node->val);
                }

                // Enqueue children left-to-right so the next level stays ordered.
                if (node->left != nullptr) q.push(node->left);
                if (node->right != nullptr) q.push(node->right);
            }
        }

        return result;
    }
};

int main() {
    // Example 1:
    //       1
    //     /   \
    //    2     3
    //     \     \
    //      5     4
    TreeNode* n1 = new TreeNode(1);
    TreeNode* n2 = new TreeNode(2);
    TreeNode* n3 = new TreeNode(3);
    TreeNode* n5 = new TreeNode(5);
    TreeNode* n4 = new TreeNode(4);
    n1->left = n2; n1->right = n3;
    n2->right = n5;
    n3->right = n4;

    Solution sol;
    vector<int> res1 = sol.rightSideView(n1);
    cout << "Example 1: ";
    for (int v : res1) cout << v << " ";
    cout << "(expected 1 3 4)" << endl;

    // Example 2:
    //    1
    //     \
    //      3
    TreeNode* m1 = new TreeNode(1);
    TreeNode* m3 = new TreeNode(3);
    m1->right = m3;
    vector<int> res2 = sol.rightSideView(m1);
    cout << "Example 2: ";
    for (int v : res2) cout << v << " ";
    cout << "(expected 1 3)" << endl;

    // Example 3: empty tree
    vector<int> res3 = sol.rightSideView(nullptr);
    cout << "Example 3: size=" << res3.size() << " (expected 0)" << endl;

    return 0;
}
```

**Trace against the examples:**
- Example 1: Level 0 → queue has `[1]`, `levelSize=1`, last (and only) node is `1` → append `1`; push `2`, `3`. Level 1 → queue has `[2,3]`, `levelSize=2`, last node is `3` → append `3`; push `5` (from 2's right) and `4` (from 3's right). Level 2 → queue has `[5,4]`, `levelSize=2`, last node is `4` → append `4`. Result: `[1, 3, 4]`. ✓
- Example 2: Level 0 → `[1]` → append `1`, push `3`. Level 1 → `[3]` → append `3`. Result: `[1, 3]`. ✓
- Example 3: root is `nullptr`, function returns immediately with an empty vector. ✓

## CS Fundamentals

### 1. DBMS (Conceptual/Definition)

Explain how a B-Tree (or B+Tree) index works in a relational database, and why B-Trees are the standard choice for on-disk indexes rather than a plain binary search tree or a hash table.

**Answer:**

A B-Tree (and its common variant, the B+Tree, which most production databases like MySQL's InnoDB and PostgreSQL actually use) is a self-balancing tree structure designed around one key constraint: **minimizing disk I/O**, since reading from disk is orders of magnitude slower than reading from RAM.

**Structure:**
- Unlike a binary search tree where each node has at most 2 children, a B-Tree node holds many keys (often hundreds) and has a correspondingly high **fanout** (many children per node) — typically sized so that one node fits exactly in one disk page/block (commonly 4KB–16KB).
- Keys within a node are kept sorted, and each node has one more child pointer than it has keys, with each child subtree containing keys within the range defined by its neighboring keys in the parent.
- In a B+Tree specifically, all actual data (or row pointers) lives only in the **leaf nodes**, which are additionally linked together in a sorted doubly-linked list. Internal nodes only store keys used for navigation, not data — this maximizes fanout per internal node and makes range scans fast (just walk the leaf-level linked list).

**Why B-Trees over a plain BST:** A binary search tree has height `O(log₂ n)`, but because each node holds only one key, looking up a value among a billion rows would require ~30 disk reads (one per level) in the worst case if the tree doesn't fit in memory — and each disk read might cost milliseconds. A B-Tree with a fanout of, say, 500, has height `O(log₅₀₀ n)` — for the same billion rows, that's only about 3-4 levels, meaning 3-4 disk reads instead of 30. Matching node size to the disk block size also means each disk read pulls in a maximally useful chunk of the index in one I/O operation, rather than wasting most of a 4KB block to store just one key and two pointers.

**Why B-Trees over a hash index:** A hash index gives `O(1)` average-case lookups for **exact-match equality** (`WHERE id = 5`), which sounds better than a B-Tree's `O(log n)`. But hash indexes destroy ordering — keys are scattered pseudo-randomly across buckets — so they cannot efficiently answer range queries (`WHERE id BETWEEN 10 AND 100`), prefix queries (`WHERE name LIKE 'Sam%'`), or `ORDER BY`/`MIN`/`MAX` queries, all of which are extremely common in real applications. A B-Tree/B+Tree preserves sort order, so all of these operations are efficient by simply walking a contiguous range of the tree (or the leaf-level linked list in a B+Tree).

**Why this matters:** This tradeoff — accepting slightly slower exact-match lookups in exchange for ordered, range-friendly access and disk-I/O efficiency — is exactly why B+Trees are the default index type in virtually every relational database, while hash indexes are offered only as a specialized option for workloads that are purely equality-lookup-heavy and never need ordering.

### 2. Computer Networks (Comparison)

Compare TCP and UDP across reliability, connection model, and overhead. Give one real application that would choose each protocol and explain why that choice makes sense.

**Answer:**

| Aspect | TCP (Transmission Control Protocol) | UDP (User Datagram Protocol) |
|---|---|---|
| Connection model | **Connection-oriented** — requires a handshake (3-way SYN/SYN-ACK/ACK) before data transfer, and a teardown (FIN) afterward. | **Connectionless** — packets ("datagrams") are simply fired off with no setup or teardown. |
| Reliability | Guarantees delivery via acknowledgments and automatic retransmission of lost packets. | No delivery guarantee — a lost packet is simply gone unless the application handles retransmission itself. |
| Ordering | Guarantees in-order delivery to the application, using sequence numbers to reorder/reassemble out-of-order packets. | No ordering guarantee — packets can arrive out of order, and it's up to the application to handle that if it matters. |
| Flow/congestion control | Built-in (sliding window flow control, congestion control algorithms like slow-start/CUBIC) to avoid overwhelming the receiver or the network. | None — the application sends at whatever rate it wants; no automatic backoff under congestion. |
| Overhead | Higher — larger header (20+ bytes), handshake round-trips add latency, and retransmissions consume extra bandwidth. | Lower — minimal header (8 bytes), no handshake, so lower latency and less bandwidth overhead per packet. |
| Typical use cases | Web browsing (HTTP/HTTPS), file transfer (FTP), email (SMTP) — anywhere correctness matters more than raw speed. | DNS lookups, live video/audio streaming, online gaming, VoIP — anywhere low latency matters more than occasional data loss. |

**Application 1 — File download over HTTP/HTTPS uses TCP:** When downloading a file, every single byte must arrive, and it must arrive in the correct order, or the file is corrupted. A dropped packet that silently corrupted part of the file would be unacceptable, so the reliability and ordering guarantees TCP provides (at the cost of some latency and overhead) are exactly what's needed — the alternative (the application re-implementing acknowledgment and retransmission logic itself) would just be reinventing TCP badly.

**Application 2 — Live video calls (VoIP) use UDP:** In a live call, a single dropped audio/video frame from a second ago is worthless even if retransmitted — by the time it arrives, the conversation has moved on, and a brief glitch or dropout is far less disruptive to the user than the stuttering, buffering delay that TCP's retransmission and in-order delivery would introduce while waiting for a lost packet to be resent. UDP's "best effort, low latency, no waiting" model is a better fit: the application (e.g., via RTP on top of UDP) can simply skip a lost frame and keep playing in near real-time.

**Why this matters:** The TCP-vs-UDP choice is the canonical example of a fundamental networking tradeoff — reliability and ordering versus latency and overhead — and understanding which one your application's failure mode tolerates (stale/incomplete data is fine, vs. any data loss is unacceptable) is the deciding factor in protocol selection, which is why it's such a common building block in networking and system design interviews.

### 3. Computer Architecture (Scenario/Applied)

You're profiling a program that processes a large 2D array stored in row-major order (as C/C++ arrays are). You notice that iterating over the array column-by-column is roughly 10x slower than iterating row-by-row, even though both versions perform the exact same number of arithmetic operations. Explain why this happens, referencing the memory hierarchy, and describe how you would fix it.

**Answer:**

**Why this happens — spatial locality and cache lines:**

In row-major storage, a 2D array `A[rows][cols]` is laid out in memory as one long contiguous block, with each row placed immediately after the previous one: `A[0][0], A[0][1], ..., A[0][cols-1], A[1][0], A[1][1], ...`. So elements in the *same row* are adjacent in memory, while elements in the *same column* are `cols` elements (i.e., a full row's width) apart.

The CPU doesn't fetch memory one byte or one `int` at a time from RAM — it fetches memory in fixed-size chunks called **cache lines** (typically 64 bytes, e.g., 16 consecutive `int`s). When you access `A[0][0]`, the hardware pulls in the entire 64-byte cache line containing it, which — because of row-major layout — also happens to contain `A[0][1]`, `A[0][2]`, etc. (assuming they fit in 64 bytes).

- **Row-major iteration** (`for row: for col: use A[row][col]`) accesses memory in exactly the order it's laid out. After the first access to a row pulls in a cache line, the next several accesses are **cache hits** — the data is already sitting in L1 cache, extremely fast to access.
- **Column-major iteration** (`for col: for row: use A[row][col]`) jumps `cols` elements ahead on every single access. Each jump very likely lands outside the cache line(s) already loaded, causing a **cache miss** on nearly every access — forcing the CPU to go all the way out to a slower cache level (L2/L3) or, worst case, main memory (RAM), which can be 100x+ slower than an L1 cache hit. At a large enough stride, this can also cause **TLB (Translation Lookaside Buffer) misses**, adding page-table-walk overhead on top of the cache miss, and even touch more memory pages than necessary, worsening the effect further.

Both loops do the same number of arithmetic operations, but the column-major version spends the overwhelming majority of its time stalled waiting on memory rather than computing — which is exactly why the wall-clock slowdown (10x here) can be so much larger than the operation count would suggest; modern CPUs are so much faster than memory that being "memory-bound" rather than "compute-bound" dominates runtime.

**How to fix it:**
1. **Loop interchange:** Simply reorder the loops so the innermost loop walks memory in the same order it's physically laid out (i.e., iterate over `col` in the inner loop, matching row-major storage) whenever the algorithm allows it. This is the fix in this exact scenario and typically requires no algorithmic change, just reordering `for` statements.
2. **Loop tiling/blocking (for cases where you genuinely need to touch data in more than one order, e.g., matrix transpose or matrix multiply):** Process the array in small sub-blocks (tiles) that are sized to fit entirely within cache (e.g., a 32x32 tile), so that all accesses to a given tile stay cache-resident before moving to the next tile, instead of repeatedly evicting and re-fetching the same cache lines.
3. **Change the storage layout itself** if the access pattern is fixed and column-wise access is unavoidable (e.g., switch to column-major/Fortran-style storage, or use a "structure of arrays" layout instead of "array of structures" when the hot-path access pattern justifies it).

**Why this matters:** This is a foundational example of why **algorithmic complexity alone doesn't determine real-world performance** — two versions of the same loop with identical `O(rows × cols)` complexity can differ by an order of magnitude in wall-clock time purely due to memory access patterns. Understanding the cache hierarchy (L1/L2/L3, cache line size, spatial vs. temporal locality) is essential for writing genuinely fast low-level code, and "make hot loops access memory sequentially" is one of the highest-leverage, most broadly applicable optimizations in systems programming.
