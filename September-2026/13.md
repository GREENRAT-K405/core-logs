## DSA

### Question: Diameter of Binary Tree (Trees — Medium)

Given the root of a binary tree, return the length of the **diameter** of the tree.

The diameter of a binary tree is the length of the longest path between any two nodes in the tree. This path may or may not pass through the root. The length of a path between two nodes is represented by the number of **edges** between them.

**Input format:** The root node of a binary tree (each node has an integer value, and optional `left`/`right` children).

**Output format:** An integer — the length (in edges) of the longest path between any two nodes.

**Example 1:**
```
Input:
        1
       / \
      2   3
     / \
    4   5

Output: 3
Explanation: The longest path is [4, 2, 1, 3] or [5, 2, 1, 3], which has 3 edges.
```

**Example 2:**
```
Input:
    1
   /
  2

Output: 1
Explanation: The longest path is [2, 1], which has 1 edge.
```

**Example 3:**
```
Input: root = null (empty tree)
Output: 0
```

**Constraints:**
- The number of nodes in the tree is in the range `[0, 10^4]`.
- `-100 <= Node.val <= 100`
- The tree height can be up to `10^4` (so an implementation should avoid unnecessary re-traversal to stay efficient).

### Step-by-Step Walkthrough

**Key observation:** For any node `n`, the longest path that passes *through* `n` is `height(n.left) + height(n.right)`, where `height(x)` is the number of edges on the longest downward path from `x` to a leaf (height of an empty subtree is `-1`, or equivalently we can define `height` in terms of node count and subtract 1 at the end — here we use "number of nodes on longest downward path" and combine child heights as `1 + max(leftHeight, rightHeight)`, with the diameter at that node measured in edges as `leftHeight + rightHeight`).

The overall diameter of the tree is the **maximum**, over all nodes, of the path length through that node. It does not have to pass through the root, which is why we cannot just compute `height(root.left) + height(root.right)` once — we need the best answer at every node.

**Naive approach:** For every node, compute the height of its left and right subtree independently (a separate recursive call each time), and take `leftHeight + rightHeight`. This is correct but recomputes heights repeatedly — for a skewed tree this becomes O(N^2) time, since computing height at each of the N nodes costs O(N) in the worst case.

**Efficient approach (single DFS):** Do one post-order depth-first traversal. Write a helper function `height(node)` that:
1. Returns `0` for a `null` node (base case — height of empty subtree in "edges from this point" terms).
2. Recursively computes `leftHeight = height(node.left)` and `rightHeight = height(node.right)`.
3. Updates a global/shared `maxDiameter` with `leftHeight + rightHeight` (the longest path through `node`, in edges).
4. Returns `1 + max(leftHeight, rightHeight)` to its parent — the height of the subtree rooted at `node`, so the parent can use it in the same formula.

Because each node's height is computed exactly once and reused by its parent, the whole tree is visited only once.

**Why it works:** Every path in the tree has a unique highest point (the node closest to the root that lies on that path) — call it the path's "peak." For a path through peak `p`, its length is exactly `heightOfLeftChild(p) + heightOfRightChild(p)` edges (one branch going down-left, one going down-right, meeting at `p`). Since every possible path has some peak, and we compute `leftHeight + rightHeight` at every single node during the traversal, we are guaranteed to consider every path's length exactly when we visit its peak. Taking the max over all nodes therefore gives the true global diameter.

**Complexity analysis:**
- **Time:** O(N) — each node is visited exactly once, and O(1) work is done per node besides the recursive calls.
- **Space:** O(H) for the recursion call stack, where H is the height of the tree — O(log N) for a balanced tree, O(N) in the worst case (a completely skewed/linked-list-shaped tree).

### C++ Code

```cpp
#include <bits/stdc++.h>
using namespace std;

struct TreeNode {
    int val;
    TreeNode *left;
    TreeNode *right;
    TreeNode(int x) : val(x), left(nullptr), right(nullptr) {}
};

class Solution {
public:
    int diameterOfBinaryTree(TreeNode* root) {
        int maxDiameter = 0;
        height(root, maxDiameter);
        return maxDiameter;
    }

private:
    // Returns the height (in edges, i.e. number of nodes on longest downward
    // path counted starting from 1 for this node) of the subtree rooted at
    // `node`, while updating maxDiameter with the best path seen so far that
    // passes through `node`.
    int height(TreeNode* node, int& maxDiameter) {
        if (node == nullptr) {
            return 0; // empty subtree contributes 0 edges going further down
        }

        int leftHeight = height(node->left, maxDiameter);
        int rightHeight = height(node->right, maxDiameter);

        // Longest path that has `node` as its peak: one edge count going
        // down the left branch plus one going down the right branch.
        maxDiameter = max(maxDiameter, leftHeight + rightHeight);

        // Height contributed upward to the parent: pick the taller branch
        // and add 1 for the edge connecting node to that branch's root.
        return 1 + max(leftHeight, rightHeight);
    }
};

// Example driver for manual verification against the worked examples above.
int main() {
    // Example 1:  1 -> (2 -> (4, 5)), (3)   expected diameter = 3
    TreeNode* root1 = new TreeNode(1);
    root1->left = new TreeNode(2);
    root1->right = new TreeNode(3);
    root1->left->left = new TreeNode(4);
    root1->left->right = new TreeNode(5);

    Solution sol;
    cout << "Example 1 diameter: " << sol.diameterOfBinaryTree(root1) << endl; // 3

    // Example 2: 1 -> 2   expected diameter = 1
    TreeNode* root2 = new TreeNode(1);
    root2->left = new TreeNode(2);
    cout << "Example 2 diameter: " << sol.diameterOfBinaryTree(root2) << endl; // 1

    // Example 3: empty tree, expected diameter = 0
    TreeNode* root3 = nullptr;
    cout << "Example 3 diameter: " << sol.diameterOfBinaryTree(root3) << endl; // 0

    return 0;
}
```

## CS Fundamentals

### 1. DBMS (Comparison)

What is the difference between a `clustered index` and a `non-clustered index` in a relational database? When would you choose one over the other?

**Answer:**

A **clustered index** determines the *physical storage order* of the actual table rows. The table's data rows are stored on disk sorted according to the clustered index key, which means a table can have **at most one** clustered index (data can only be physically sorted one way). In many databases (e.g., SQL Server, MySQL/InnoDB), if you don't explicitly define one, the primary key is used as the clustered index by default.

A **non-clustered index** is a separate structure (typically a B-tree) that stores the indexed column's values along with a pointer (a row locator — either the physical row address or the clustered index key) back to the actual row in the table. The table data itself is not reordered. A table can have **many** non-clustered indexes.

**Practical implications:**
- **Lookups on the clustered key** are very fast because once you find the key in the index, you're already at the data — no extra hop needed.
- **Lookups via a non-clustered index** require an extra step ("bookmark lookup"): first find the entry in the index, then follow the pointer to fetch the actual row, unless the query is a "covering query" (all needed columns are already present in the index itself, avoiding the extra hop).
- **Range queries** (e.g., `WHERE order_date BETWEEN X AND Y`) benefit enormously from a clustered index on that column, since matching rows are physically adjacent on disk, minimizing I/O.
- **Write cost:** Because a clustered index dictates physical order, inserting a row with a key in the middle of the range can be more expensive (may require page splits), whereas non-clustered indexes add overhead per insert/update/delete but don't reorganize the table itself.

**When to choose which:** Use the clustered index on the column(s) most frequently used for range scans, sorting, or as the primary access path (often the primary key, or a column like a timestamp for time-series data). Use non-clustered indexes on columns frequently used in `WHERE`, `JOIN`, or `ORDER BY` clauses that aren't the clustered key, especially where selectivity is high — but avoid over-indexing, since each additional non-clustered index adds write overhead and storage.

### 2. Computer Architecture (Conceptual)

What is `pipelining` in CPU design, and what are `pipeline hazards`? Name the three main types of hazards.

**Answer:**

**Pipelining** is a CPU design technique that overlaps the execution of multiple instructions by splitting instruction processing into discrete stages (a classic example is the 5-stage RISC pipeline: **Fetch, Decode, Execute, Memory access, Write-back** — often abbreviated IF, ID, EX, MEM, WB). Each stage is handled by dedicated hardware, and at any given clock cycle, different instructions can occupy different stages simultaneously — much like an assembly line. This doesn't reduce the *latency* of any single instruction, but it dramatically increases *throughput* (instructions completed per unit time), since a new instruction can enter the pipeline every clock cycle once it's full, instead of waiting for the previous instruction to fully finish.

A **pipeline hazard** is a situation where the next instruction cannot execute in its designated clock cycle because of a conflict introduced by pipelining, which would produce incorrect results (or stalls) if not handled. The three main types are:

1. **Structural hazards** — occur when two or more instructions need the same hardware resource at the same time (e.g., a single shared memory unit needed simultaneously for an instruction fetch and a data access). Resolved by duplicating hardware resources (e.g., separate instruction and data caches/memories) or by stalling one instruction.

2. **Data hazards** — occur when an instruction depends on the result of a previous instruction that hasn't completed yet (e.g., `ADD R1, R2, R3` followed immediately by `SUB R4, R1, R5`, where `R1` isn't written back yet when `SUB` needs it). Resolved via **forwarding/bypassing** (routing the result directly from one pipeline stage to another before it's officially written back) or by stalling the pipeline until the value is available.

3. **Control hazards** (branch hazards) — occur due to branch instructions, where the CPU doesn't know which instruction to fetch next until the branch is resolved (condition evaluated) several stages later. Resolved via techniques like **branch prediction** (guessing the outcome and speculatively executing, rolling back on misprediction), **delayed branching**, or simply stalling until the branch outcome is known.

Understanding hazards matters because they are the main reason real-world pipelined CPUs don't achieve the theoretical "N times speedup for an N-stage pipeline" — stalls and flushes introduced by hazards eat into that ideal throughput gain.

### 3. System Design Basics (Scenario)

You're designing a URL shortener service (like bit.ly) that must handle very high read traffic (users clicking shortened links) compared to write traffic (users creating new short links). What caching strategy would you use, and why?

**Answer:**

Given the read-heavy access pattern — clicks (reads) vastly outnumber link creations (writes) — the goal is to minimize load on the primary database for the redirect path, since that's the hot path serving the vast majority of requests.

**Strategy: Cache-aside (lazy loading) with an in-memory cache like Redis or Memcached, sitting in front of the database, specifically for the short-code → long-URL mapping.**

How it works:
1. When a redirect request comes in for a short code, the application first checks the cache.
2. **Cache hit:** Return the long URL directly from cache — fast, and the database is never touched for this request.
3. **Cache miss:** Query the database for the mapping, return the result to the user, and populate the cache with that mapping for next time.
4. On **write** (a new short link is created), the application writes to the database as the source of truth. It can optionally also write through to the cache immediately (write-through) so the very first read is already a cache hit, which is useful here since a newly created link is often clicked soon after creation ("recency bias" in access patterns).

**Why this fits the scenario:**
- **Skewed/hot-key access pattern:** Real-world link click distributions tend to follow a power law — a small fraction of short links (viral links, marketing campaigns) receive a disproportionate share of clicks. An LRU (Least Recently Used) eviction policy on the cache naturally keeps these hot links resident in memory while letting cold, rarely-accessed links fall out, keeping the cache size manageable while still absorbing the majority of read traffic.
- **Read/write ratio:** Since writes are comparatively rare, the extra complexity of keeping cache and database consistent on write is a small price to pay for the large reduction in database read load — a great trade-off specifically because reads dominate.
- **Low latency requirement:** Redirects are latency-sensitive (users expect an instant redirect), and in-memory cache lookups (sub-millisecond) beat a database round-trip, especially at scale with many concurrent users.
- **Scalability:** The cache layer can be scaled horizontally (e.g., a Redis cluster with sharding by short code) independently of the database, and it absorbs the bulk of traffic so the database can be sized for the much smaller write volume plus the cache-miss trickle, rather than for full read+write load.

Additional considerations for a complete design: set a reasonable TTL (or none, if links rarely change) on cache entries, use consistent hashing to distribute keys evenly across cache nodes, and consider a CDN or edge-cache layer in front of the application for even lower latency on the most popular redirects.
