### Question: Basic Calculator (Stacks/Queues — Hard)

**Problem Statement**

Given a string `s` representing a valid mathematical expression, implement a basic calculator to evaluate it and return the result.

The expression contains non-negative integers, the operators `+` and `-`, parentheses `(` and `)`, and spaces. You are **not** allowed to use any built-in function that evaluates strings as expressions (e.g. `eval`).

**Input/Output Format**

- Input: a string `s` containing digits, `'+'`, `'-'`, `'('`, `')'`, and `' '`.
- Output: an integer, the evaluated result of the expression.

**Examples**

1. Input: `"1 + 1"` → Output: `2`
2. Input: `" 2-1 + 2 "` → Output: `3`
3. Input: `"(1+(4+5+2)-3)+(6+8)"` → Output: `23`

**Constraints**

- `1 <= s.length <= 3 * 10^5`
- `s` consists of digits, `'+'`, `'-'`, `'('`, `')'`, and `' '`.
- `s` represents a valid expression.
- `'+'` is not used as a unary operator (i.e. `"+1"` and `"+(2 + 3)"` are invalid), but `'-'` may be used as a unary operator (i.e. `"-1"` and `"-(2 + 3)"` are valid).
- There will be no two consecutive operators in the input.
- Every number and running sum will fit in a 32-bit signed integer.

### Step-by-Step Walkthrough

**Why a simple left-to-right scan isn't enough.** With only `+` and `-` (no `*`/`/`), operator precedence isn't the hard part — parentheses are. A naive scan that just accumulates a running total breaks the moment it hits a `(` : it needs to remember "what sign applies to everything inside this parenthesis" and "what was the total *before* this parenthesis started," then resume from there once the matching `)` closes. That's a **stack of contexts**, one pushed per open paren.

**State we track while scanning.**
- `result` — the running total for the *current* nesting level.
- `num` — the digits of the number currently being built.
- `sign` — `+1` or `-1`, the sign to apply to `num` once it's complete (defaults to `+1`).
- `st` — a stack holding `(previous result, sign that applied to this whole sub-expression)` pairs, pushed on `(` and popped on `)`.

**The scan, character by character.**
1. **Digit** → fold it into `num` (`num = num * 10 + digit`), since a number can be multiple digits long.
2. **`+` or `-`** → the number we were building (if any) is finished. Apply it: `result += sign * num`. Reset `num = 0`, and set `sign` to `+1` or `-1` for the *next* number.
3. **`(`** → we're about to start a fresh sub-expression. Push the current `(result, sign)` onto the stack so we can restore the outer context later, then reset `result = 0` and `sign = 1` — the parenthesized part starts clean, as if it were its own mini-expression.
4. **`)`** → first finish any pending number the same way as step 2 (`result += sign * num`, reset `num`). Now `result` holds the fully-evaluated value of everything inside the parenthesis. Pop `(prevResult, prevSign)` from the stack and fold the parenthesis's value back into the outer context: `result = prevResult + prevSign * result`. This is the key step — it's what lets `-(4+5+2)` correctly negate the *entire* sub-expression, because `prevSign` was captured at the `(` and applied to the sub-expression's total as a single unit.
5. **Space** → ignore.
6. **End of string** → there may be one last pending number that was never followed by an operator; fold it in the same way: `result += sign * num`.

**Why it's correct.** Each stack frame represents exactly one enclosing pair of parentheses along with the sign that was pending *before* that parenthesis was entered. Because parentheses are properly nested (guaranteed by the problem), a stack (LIFO) is exactly the right structure: the most recently opened paren is always the next one to close, so `push` on `(` / `pop` on `)` always restores the correct enclosing context, however deep the nesting.

**Complexity.**
- Time: O(n) — each character is processed once, and each stack push/pop happens once per parenthesis.
- Space: O(n) in the worst case — a string of all nested parens like `"(((((1)))))"` pushes one frame per `(`.

### C++ Code

```cpp
#include <string>
#include <stack>
using namespace std;

int calculate(const string& s) {
    stack<pair<long long, int>> st; // (result-so-far, sign) for each enclosing '('
    long long result = 0;
    long long num = 0;
    int sign = 1; // sign to apply to the number currently being read

    for (size_t i = 0; i < s.size(); i++) {
        char c = s[i];

        if (isdigit((unsigned char)c)) {
            num = num * 10 + (c - '0');
        } else if (c == '+' || c == '-') {
            // Finish the number built so far, then set up the next sign.
            result += sign * num;
            num = 0;
            sign = (c == '+') ? 1 : -1;
        } else if (c == '(') {
            // Save the context we're leaving; start the sub-expression clean.
            st.push({result, sign});
            result = 0;
            sign = 1;
        } else if (c == ')') {
            // Close out any pending number for this sub-expression.
            result += sign * num;
            num = 0;

            // Fold the sub-expression's total back into the enclosing context.
            auto [prevResult, prevSign] = st.top();
            st.pop();
            result = prevResult + prevSign * result;
        }
        // Spaces: nothing to do.
    }

    // One last number may still be pending (no trailing operator/paren).
    result += sign * num;

    return (int)result;
}
```

Trace `"(1+(4+5+2)-3)+(6+8)"`: on the inner `(4+5+2)` we push `(0, +1)` for the outer paren, evaluate the inner group to `11`, pop back `(0, +1)` and get `result = 0 + 1*11 = 11` inside the outer paren; continuing gives `1 + 11 - 3 = 9` for the outer group; popping the outermost frame `(0, +1)` folds that in as `9`; then `+ (6+8) = +14` gives the final `23` — matching the example.

## CS Fundamentals

### 1. DBMS (Comparison)

Clustered and non-clustered indexes both speed up lookups, but they organize data differently and that difference has real performance consequences. What exactly distinguishes them, and how would you decide which columns get which kind?

**Answer:**

A **clustered index** determines the *physical order* in which rows are actually stored on disk. Because the table's rows can only be physically sorted one way, a table can have **at most one** clustered index — it isn't a separate structure sitting next to the data, it *is* the data, stored as the leaf level of a B+ tree keyed on the indexed column(s). (In MySQL/InnoDB, if you don't declare a primary key, the engine creates a hidden clustered index anyway — the table is always clustered on something.)

A **non-clustered index** is a *separate* structure: its own B+ tree, sorted by the indexed column, where each leaf entry holds the indexed value plus a **pointer back to the actual row** (a row ID, or the clustering key on InnoDB). The table's own storage order is untouched. A table can have **many** non-clustered indexes.

The performance consequence follows directly from that structural difference:

| | Clustered | Non-Clustered |
| --- | --- | --- |
| Physical row order | Determined by this index | Independent structure |
| Count per table | At most 1 | Many |
| Lookup by indexed column | Direct — the leaf *is* the row | Leaf gives a pointer, then a second lookup ("bookmark lookup") fetches the row |
| Range scans (`BETWEEN`, `ORDER BY` on the key) | Very fast — rows are physically adjacent | Slower — matching rows are scattered across the table |
| Insert cost | Can be expensive — inserting mid-range may require physically relocating rows (page splits) | Cheaper — only the index structure updates, table storage is undisturbed |

**How to choose:** put the clustered index on the column(s) most queried by **range** and by primary access pattern — commonly the primary key, or a column like `order_date` in a time-series table where "give me last week's orders" benefits from those rows being physically contiguous. Reserve non-clustered indexes for columns frequently used in `WHERE`/`JOIN` filters that aren't the main access pattern (e.g. `customer_email` for point lookups), accepting the extra bookmark-lookup hop in exchange for not disturbing the table's primary physical order.

### 2. OOP (Conceptual)

What does "runtime polymorphism" mean in C++, and mechanically, how do virtual functions and the vtable make it happen? Why does forgetting a virtual destructor in a base class cause real bugs?

**Answer:**

**Runtime polymorphism** means the specific function that executes for a call is decided while the program is *running*, based on the actual (dynamic) type of the object being pointed to — not the type written in the source code (the static type of the pointer/reference). This is what lets code write `Shape* s = ...; s->area();` once and have it correctly call `Circle::area()`, `Square::area()`, or any other override, without knowing which at compile time.

**Mechanically, via the vtable:**
- When a class declares a function `virtual`, the compiler gives every object of that class (and its derived classes) a hidden pointer, the **vptr**, installed by the constructor, pointing to a per-class table of function pointers — the **vtable**.
- Each class that overrides a virtual function gets its own vtable entry pointing to *its* version of that function; a class that doesn't override inherits the base's entry.
- A call like `s->area()` compiles not to "jump to `Shape::area`" but to "read `s`'s vptr, index into the vtable at the slot for `area`, jump to whatever address is stored there." That indirection — one extra pointer dereference — is the entire mechanism, and it's why virtual calls are only slightly slower than direct calls, not a real bottleneck in practice.
- Non-virtual functions, by contrast, are resolved entirely at compile time based on the static type — this is why calling a non-virtual function through a base pointer always runs the base's version, even if the object is actually derived. That's the concrete difference between **compile-time binding** (non-virtual, decided by declared type) and **dynamic binding** (virtual, decided by the vptr at the call site).

**Why a missing virtual destructor is a real bug, not a style nitpick:**

```cpp
Shape* s = new Circle();
delete s; // if ~Shape() is NOT virtual: undefined behavior
```

`delete` on a base pointer calls the destructor that the *static* type resolves to, unless that destructor is virtual. With a non-virtual `~Shape()`, only `~Shape()` runs — `~Circle()` (and any member/resource cleanup it does, e.g. freeing a buffer `Circle` allocated) is skipped entirely. That's a silent resource leak or worse, and it only shows up for objects actually constructed as the derived type and destroyed through a base pointer — exactly the polymorphic use case the class was designed for. The fix is mechanical: **any class intended to be a polymorphic base (i.e., it has at least one virtual function, or is ever deleted through a base pointer) should declare its destructor `virtual`.** This one line costs one vtable slot and prevents an entire category of undefined behavior.

### 3. System Design Basics (Scenario/Applied)

Your read-heavy API (a product catalog, say) is suddenly getting 10x its normal traffic and the database is struggling to keep up. Walk through how you'd relieve the load, and what tradeoffs each option brings.

**Answer:**

The core diagnosis first: read-heavy means the same data is being fetched repeatedly, so the fix is to **stop asking the database the same question over and over** — every layer below adds a place to answer from cache instead of from the source of truth.

**1. Caching (the first lever, usually the biggest win).** Put a cache (Redis/Memcached) in front of the database for the hot read paths. A request checks the cache first; on a miss it reads the database and populates the cache (cache-aside pattern). This turns most reads into cheap in-memory lookups.
- *Tradeoff:* introduces **staleness** — the cache can serve outdated data until it expires or is invalidated. Requires deciding a TTL (shorter = fresher but less load relief) and an invalidation strategy (e.g. explicitly clear the cache entry when the underlying row is updated). For a product catalog specifically, moderate staleness (prices/descriptions a few minutes old) is usually an acceptable tradeoff for the load relief — but "current inventory count" might not be, since overselling is a real cost.

**2. CDN / edge caching.** If responses are largely the same for all users (e.g. product pages, images, category listings), cache them at the CDN edge, close to users. This offloads traffic before it even reaches your servers.
- *Tradeoff:* only works well for content that doesn't vary per-user; personalized responses (e.g. "recommended for you") can't be cached this way without extra work (edge-side includes, splitting personalized fragments out).

**3. Read replicas.** Add one or more read-only database replicas and route reads to them, keeping the primary for writes. This horizontally scales read capacity directly at the database layer.
- *Tradeoff:* replication is typically **asynchronous**, so replicas lag the primary slightly — a read immediately after a write can return stale data (replication lag). Also adds operational complexity (routing logic, replica health checks, promotion on primary failure).

**4. Rate limiting / load shedding, as a stopgap.** If the spike includes abusive or non-critical traffic, apply rate limits per client/IP, or shed low-priority requests, to protect the system from falling over entirely while the above measures take effect.
- *Tradeoff:* directly rejects some legitimate requests — it's damage control, not a real capacity increase, and should be a temporary safety valve, not the long-term answer.

**How they compose in practice:** caching (app-level and CDN) absorbs the bulk of repeat reads cheaply and should be reached for first since it requires no new infrastructure tier; read replicas are the right call when the *variety* of queries is too high for caching alone to help (e.g. many different filter/sort combinations that rarely repeat); rate limiting is the emergency brake while the others are being rolled out. A mature system typically ends up using all three together: CDN for static/shared content, an app-side cache for personalized-but-repeatable reads, and replicas for the long tail of queries caching can't cover.
