### Question: N-Queens (Recursion/Backtracking — Hard)

The n-queens puzzle is the problem of placing `n` chess queens on an `n × n` chessboard such that no two queens attack each other. Two queens attack each other if they share the same row, the same column, or the same diagonal.

Given an integer `n`, return **all distinct board configurations** in which the `n` queens can be placed on the `n × n` chessboard. Each solution should be represented as a vector of strings, where `'Q'` marks a queen and `'.'` marks an empty space.

**Input format:**
- A single integer `n`.

**Output format:**
- A list of solutions. Each solution is a list of `n` strings, each of length `n`, representing one valid board.
- If no solution exists, return an empty list.

**Worked Examples:**

1. `n = 4` → 2 solutions:
   ```
   Solution 1:        Solution 2:
   . Q . .             . . Q .
   . . . Q             Q . . .
   Q . . .             . . . Q
   . . Q .             . Q . .
   ```
   As strings: `[".Q..", "...Q", "Q...", "..Q."]` and `["..Q.", "Q...", "...Q", ".Q.."]`

2. `n = 1` → 1 solution: `["Q"]` (a single queen trivially doesn't attack anything).

3. `n = 2` (or `n = 3`) → 0 solutions. It is a well-known fact that no valid placement exists for `n = 2` or `n = 3` — the board is too small to keep every pair of queens out of each other's row, column, and diagonal simultaneously.

**Constraints:**
- `1 <= n <= 9`

---

### Step-by-Step Walkthrough

**Key observation:** Since no two queens may share a row, a valid solution places **exactly one queen per row**. That immediately turns the problem into: for each row `0` to `n-1`, choose a column for that row's queen, such that no column, and no diagonal, is reused.

**Approach — Backtracking, one row at a time**

1. Process rows in order, `row = 0, 1, ..., n-1`. At each row, try placing the queen in every column `col = 0` to `n-1`.
2. Before placing, check whether `col` is safe:
   - **Column check:** is this column already occupied by a queen from an earlier row?
   - **Diagonal check (↘):** cells on the same "positive" diagonal satisfy `row - col = constant`. Track occupied diagonals by the value `row - col + (n - 1)` (the `+ (n-1)` shift just keeps the index non-negative so it can index into an array).
   - **Diagonal check (↙):** cells on the same "negative" diagonal satisfy `row + col = constant`. Track occupied diagonals by `row + col`.
   - All three checks are `O(1)` if we maintain three boolean arrays (`usedCols`, `usedDiag1`, `usedDiag2`) instead of re-scanning the board.
3. If `col` is safe: place the queen (mark the column/diagonals used, write `'Q'` into the row string), then **recurse** to `row + 1`.
4. When `row == n`, every row has a queen placed consistently — record a copy of the current board as one valid solution.
5. **Backtrack:** after the recursive call returns (whether or not it found solutions further down), undo the placement — unmark the column/diagonals and reset the cell to `'.'` — before trying the next column in the same row. This is what lets the same row's later column choices be explored cleanly.

**Why it works:** By construction, only one queen is ever placed per row, so row conflicts are impossible by design. The three tracking arrays make column/diagonal conflicts detectable in constant time, so backtracking only recurses into states that are still consistent so far — invalid placements are pruned immediately rather than being discovered later by scanning the whole board. Because every recursive call fully undoes its own board mutation before returning, the same arrays and board buffer can be reused across the entire search without extra allocation.

**Complexity Analysis:**
- **Time complexity:** Worst case is bounded by `O(N!)` — the first queen has `N` column choices, the second has at most `N-1` remaining safe choices, and so on, with the constant-time safety checks pruning many branches early in practice. This is standard for the N-Queens backtracking search and is fine for the given constraint `n <= 9`.
- **Space complexity:** `O(N^2)` to store all found solutions (each solution is an `N x N` board), plus `O(N)` for the three tracking arrays and the recursion call stack depth (one frame per row).

### C++ Code

```cpp
#include <iostream>
#include <vector>
#include <string>
using namespace std;

class Solution {
public:
    vector<vector<string>> solveNQueens(int n) {
        vector<vector<string>> results;

        // board[row] holds the string representation of that row, built incrementally.
        vector<string> board(n, string(n, '.'));

        // O(1) conflict checks, indexed by column and by the two diagonal families.
        vector<bool> usedCols(n, false);
        vector<bool> usedDiag1(2 * n - 1, false); // index: row - col + (n - 1)
        vector<bool> usedDiag2(2 * n - 1, false); // index: row + col

        backtrack(0, n, board, usedCols, usedDiag1, usedDiag2, results);
        return results;
    }

private:
    void backtrack(int row, int n, vector<string>& board,
                   vector<bool>& usedCols, vector<bool>& usedDiag1, vector<bool>& usedDiag2,
                   vector<vector<string>>& results) {
        // Base case: every row has a validly placed queen -> record this board.
        if (row == n) {
            results.push_back(board);
            return;
        }

        for (int col = 0; col < n; ++col) {
            int diag1 = row - col + (n - 1);
            int diag2 = row + col;

            // Skip columns/diagonals already occupied by an earlier queen.
            if (usedCols[col] || usedDiag1[diag1] || usedDiag2[diag2]) {
                continue;
            }

            // Place the queen.
            board[row][col] = 'Q';
            usedCols[col] = usedDiag1[diag1] = usedDiag2[diag2] = true;

            // Recurse to the next row.
            backtrack(row + 1, n, board, usedCols, usedDiag1, usedDiag2, results);

            // Backtrack: undo the placement so the next column choice starts clean.
            board[row][col] = '.';
            usedCols[col] = usedDiag1[diag1] = usedDiag2[diag2] = false;
        }
    }
};

int main() {
    Solution sol;

    // Example 1: n = 4 -> expect 2 solutions
    auto res4 = sol.solveNQueens(4);
    cout << "n = 4 -> " << res4.size() << " solutions (expected 2)" << endl;
    for (auto& solution : res4) {
        for (auto& rowStr : solution) cout << rowStr << "\n";
        cout << "---\n";
    }

    // Example 2: n = 1 -> expect 1 solution ("Q")
    auto res1 = sol.solveNQueens(1);
    cout << "n = 1 -> " << res1.size() << " solutions (expected 1)" << endl;

    // Example 3: n = 2 -> expect 0 solutions
    auto res2 = sol.solveNQueens(2);
    cout << "n = 2 -> " << res2.size() << " solutions (expected 0)" << endl;

    return 0;
}
```

**Trace against the examples:**
- `n = 4`: row 0 tries columns 0..3; placing at column 1 eventually leads down a consistent chain (`row1=col3, row2=col0, row3=col2`), giving `.Q..`, `...Q`, `Q...`, `..Q.`; placing at column 2 first mirrors it, giving the second solution. Total: 2, matching the expected output.
- `n = 1`: the single row has one column choice, no conflicts possible, so the loop places the queen and immediately hits `row == n`, recording `["Q"]`. Total: 1.
- `n = 2`: row 0 places at column 0; row 1 has both columns blocked (column 0 is used, column 1 is on the diagonal `row+col=1` relative to `row0,col0`... concretely both remaining cells conflict), so no full placement completes; symmetric result when row 0 starts at column 1. Total: 0, matching the known result.

## CS Fundamentals

### 1. Operating Systems (Conceptual/Definition)

What is the difference between a process and a thread? Explain specifically why switching between two threads of the *same* process is typically much cheaper than switching between two separate processes.

**Answer:**

A **process** is an independent instance of a running program: it owns its own private virtual address space (code, heap, stack segments), its own set of open file descriptors, and its own OS-level resources (memory mappings, security context, etc.). Processes are isolated from each other by the operating system — one process cannot directly read or write another process's memory without going through an explicit inter-process communication (IPC) mechanism (pipes, shared memory, sockets, etc.).

A **thread** is a unit of execution *within* a process. A single process can contain multiple threads, and all threads belonging to that process **share** the same address space, heap, global variables, and open file descriptors. Each thread only gets its own private **stack** and its own set of CPU register values (including the program counter), since those are what's needed to track an independent execution path.

**Why thread switches are cheaper:**

1. **No address space change.** Switching between threads of the same process does not require changing the page table / memory mappings, because both threads already share the same virtual address space. Switching between processes, however, requires the OS to swap in a different page table (updating the CR3 register on x86, or the equivalent MMU state), which invalidates the CPU's Translation Lookaside Buffer (TLB) — a hardware cache that maps virtual to physical addresses. A TLB flush means the next several memory accesses are slow until the cache warms back up.
2. **Less state to save/restore.** A context switch between threads only needs to save/restore CPU registers, the program counter, and the stack pointer. A process switch additionally involves switching memory management state, and typically more OS bookkeeping (updating which process owns which file descriptors, security/permission context, etc.).
3. **Shared caches stay warmer.** Since threads of the same process typically operate on overlapping data and share the same address space, CPU cache lines (L1/L2) are more likely to still be relevant after a thread switch than after a full process switch, where the new process's working set is usually entirely different data.

**Why this matters:** This cost difference is exactly why highly concurrent server software (web servers, database engines) is usually built with a thread pool (or async/event-loop model) rather than spawning a new OS process per request — the overhead of process creation and process-level context switching would dominate at high request rates, whereas threads let concurrent work share memory and switch between each other cheaply.

### 2. DBMS (Comparison)

Compare SQL (relational) databases and NoSQL databases along three dimensions: data model/schema, consistency guarantees, and horizontal scalability. When would you choose one over the other?

**Answer:**

| Dimension | SQL (Relational) | NoSQL |
|---|---|---|
| Data model / schema | Data is stored in tables with a fixed, predefined schema (columns and types declared up front); relationships between tables are expressed via foreign keys, enforced by the database. | Schema-less or flexible-schema models: document stores (JSON-like documents, e.g. MongoDB), key-value stores (e.g. Redis), wide-column stores (e.g. Cassandra), or graph databases (e.g. Neo4j). Structure can vary per record and evolve without a migration. |
| Consistency guarantees | Strong consistency by default, backed by ACID transactions (Atomicity, Consistency, Isolation, Durability) — a committed write is immediately visible to all subsequent reads, and multi-row/multi-table transactions are all-or-nothing. | Many NoSQL systems favor **BASE** (Basically Available, Soft state, Eventually consistent) instead of strict ACID, especially in distributed deployments — a write may take some time to propagate to all replicas, trading immediate consistency for higher availability, as formalized by the CAP theorem (a distributed system can't simultaneously guarantee Consistency, Availability, and Partition tolerance — you pick at most two under a network partition). Some NoSQL databases do offer tunable or even strong consistency options, but it's not the universal default the way it is in SQL. |
| Horizontal scalability | Traditionally scales **vertically** (bigger machine) more easily than horizontally, because enforcing joins, foreign keys, and multi-row ACID transactions across many machines is complex; horizontal scaling (sharding) is possible but often requires significant application-level work or specialized clustering solutions. | Designed from the ground up for **horizontal** scaling — data is naturally partitioned (sharded) across many commodity nodes, since the flexible/denormalized data model avoids needing cross-node joins or distributed transactions for most operations. |

**When to choose which:**
- Choose **SQL** when data is naturally relational (e.g., orders referencing customers and products), when you need strong transactional guarantees (e.g., financial ledgers, inventory counts where overselling is unacceptable), or when the schema is stable and complex ad-hoc queries/joins are common.
- Choose **NoSQL** when you need to scale reads/writes horizontally across many nodes for very high throughput, when the data is naturally document-like or highly variable in shape (e.g., user activity logs, product catalogs with wildly different attributes per category), or when eventual consistency is an acceptable trade-off for availability (e.g., a social media "like" counter that can lag by a second or two).

**Why this matters:** This is one of the most common system-design and interview questions because the "right" choice is rarely universal — it depends on the actual access patterns (read/write ratio, need for joins, tolerance for stale reads) and consistency requirements of the specific application, not on one technology being unconditionally "better."

### 3. Computer Architecture (Scenario/Applied)

A CPU has the following memory hierarchy behavior:
- L1 cache hit time: 1 cycle, with a 95% hit rate.
- On an L1 miss, the request goes to L2, which has a hit time of 20 cycles (from the point of the L1 miss) and a 90% hit rate.
- On an L2 miss, an additional 100 cycles are needed to fetch the data from main memory.

Compute the **Average Memory Access Time (AMAT)**, in cycles, and explain how you arrived at it.

**Answer:**

**Formula:** AMAT is computed recursively through the levels of the memory hierarchy:

```
AMAT = HitTime_L1 + MissRate_L1 × MissPenalty_L1
MissPenalty_L1 = HitTime_L2 + MissRate_L2 × MissPenalty_L2
MissPenalty_L2 = AdditionalMainMemoryTime
```

**Step-by-step substitution:**

1. `MissRate_L1 = 1 - 0.95 = 0.05` (5%)
2. `MissRate_L2 = 1 - 0.90 = 0.10` (10%)
3. `MissPenalty_L2 = 100 cycles` (the extra time to reach main memory once L2 also misses)
4. `MissPenalty_L1 = HitTime_L2 + MissRate_L2 × MissPenalty_L2 = 20 + 0.10 × 100 = 20 + 10 = 30 cycles`
5. `AMAT = HitTime_L1 + MissRate_L1 × MissPenalty_L1 = 1 + 0.05 × 30 = 1 + 1.5 = 2.5 cycles`

**So AMAT = 2.5 cycles.**

**Interpretation:** On average, every memory access costs the equivalent of 2.5 CPU cycles, even though a pure L1 hit only costs 1 cycle. The extra 1.5 cycles is the "amortized tax" paid because 5% of accesses have to pay the L2 lookup cost (20 cycles), and a smaller fraction of *those* (10% of the 5%, i.e. 0.5% of all accesses overall) additionally pay the 100-cycle trip to main memory.

**Why this matters:** AMAT is the standard way architects quantify the real-world cost of a memory hierarchy design, because it lets you reason about trade-offs numerically — e.g., is it worth adding an L3 cache, or making L1 slightly bigger (which usually increases its hit time but improves its hit rate)? Small changes in hit rate at the *outer* levels of the hierarchy (L1 in this case) matter far more to AMAT than large changes deep inside the hierarchy (main memory latency), simply because most accesses never get there — which is exactly why cache design tends to focus so much engineering effort on maximizing the L1 hit rate.
