### Question: Trapping Rain Water (Arrays — Hard)

**Problem Statement**

Given `n` non-negative integers `height[0..n-1]` representing an elevation map where the width of each bar is `1`, compute how much water it can trap after raining.

**Input/Output Format**

- Input: an array `height` of non-negative integers.
- Output: a single integer — the total units of water trapped.

**Examples**

1. Input: `height = [0,1,0,2,1,0,1,3,2,1,2,1]` → Output: `6`
   (Water pools above the low points between the taller bars — e.g. index 2 holds 1 unit because it's flanked by height 1 on the left and height 2 on the right.)
2. Input: `height = [4,2,0,3,2,5]` → Output: `9`
3. Input: `height = [1,2]` (or any strictly non-decreasing/monotonic array) → Output: `0` (nothing to trap without a dip between two higher walls)

**Constraints**

- `0 <= n <= 2 * 10^4`
- `0 <= height[i] <= 10^5`
- Aim for O(n) time and O(1) extra space.

### Step-by-Step Walkthrough

**Reframe the problem per-column.** Instead of thinking about "pools" of water, think about how much water sits *on top of* each individual bar. At index `i`, water can only accumulate up to the height of the shorter of the two walls bounding it on the left and right — anything above that just spills off one side. So:

```
water[i] = min(maxHeightToLeftOf(i), maxHeightToRightOf(i)) - height[i]
```

(and only counts if that value is positive). Summing `water[i]` over all `i` gives the answer.

**Brute force.** For every index `i`, scan left to find the tallest bar in `height[0..i]`, scan right to find the tallest bar in `height[i..n-1]`, then apply the formula. That's correct but O(n) work per index, so O(n²) overall — too slow for `n` up to `2×10^4`.

**First improvement: precompute the bounds.** The left-max and right-max at each index don't need to be recomputed from scratch — they're prefix/suffix maximums. Build `leftMax[i] = max(height[0..i])` with one left-to-right pass, and `rightMax[i] = max(height[i..n-1])` with one right-to-left pass. Then a single pass applies the formula. This is O(n) time but O(n) extra space for the two arrays.

**Getting to O(1) space: two pointers.** The key realization is that we don't need the *full* `leftMax`/`rightMax` arrays simultaneously — we only ever need, at each step, the smaller of the two current bounds, and we can decide which side is "safe" to resolve without knowing the other side's exact final value.

Maintain `left = 0`, `right = n - 1`, and running maximums `leftMax = 0`, `rightMax = 0`. At each step, compare `height[left]` and `height[right]`:

- If `height[left] <= height[right]`: the wall at `right` (or something at least as tall, further right) guarantees the right boundary for position `left` is at least `height[right] >= height[left]`. That means the *left* side is the binding constraint at position `left` — whatever water sits there is capped by `leftMax`, not by anything on the right. So update `leftMax = max(leftMax, height[left])`, add `leftMax - height[left]` to the total, and advance `left` inward.
- Otherwise (`height[right] < height[left]`), symmetric logic applies on the right: update `rightMax`, add `rightMax - height[right]`, and pull `right` inward.

Each step resolves exactly one index's water contribution using only the *currently known* running maximum on its own side — which is guaranteed to be the limiting bound precisely because the pointer on the *other* side is standing on something at least as tall. Repeat until `left` meets `right`.

**Why it's correct.** `leftMax` at any point in the scan is the exact true maximum of `height[0..left]` (nothing to the right of `left` has been skipped over on that side). The comparison `height[left] <= height[right]` guarantees that the true maximum on the right side, from `left+1` to `n-1`, is at least `height[right]`, which is at least `height[left]`, which is at least the water level we'd compute from `leftMax` alone — so the right side can never be the binding (smaller) bound when we choose to resolve `left`. Symmetric reasoning holds when we resolve `right` instead.

**Complexity.**
- Time: O(n) — `left` and `right` each move strictly inward every iteration, so together they cover the array once.
- Space: O(1) — just a handful of scalars, no auxiliary arrays.

### C++ Code

```cpp
#include <vector>
#include <algorithm>
using namespace std;

int trap(vector<int>& height) {
    int n = (int)height.size();
    if (n < 2) return 0; // need at least two bars to trap anything

    int left = 0, right = n - 1;
    int leftMax = 0, rightMax = 0;
    int water = 0;

    while (left < right) {
        if (height[left] <= height[right]) {
            // The right side is at least as tall as height[left],
            // so leftMax is the binding bound for this column.
            leftMax = max(leftMax, height[left]);
            water += leftMax - height[left];
            left++;
        } else {
            // Symmetric case: the left side is taller, so rightMax
            // is the binding bound for this column.
            rightMax = max(rightMax, height[right]);
            water += rightMax - height[right];
            right--;
        }
    }

    return water;
}
```

## CS Fundamentals

### 1. DBMS (Conceptual/Definition)

What is Multi-Version Concurrency Control (MVCC), and how does it allow readers and writers to operate on a database without blocking each other?

**Answer:**

MVCC is a concurrency-control strategy where the database never overwrites a row in place when it's updated. Instead, it keeps multiple *versions* of a row, each tagged with the transaction (or timestamp) that created it and, once superseded, the transaction that expired it. A transaction reads the version of each row that was current as of some fixed point in time — usually the moment its transaction (or statement) began — rather than whatever the very latest committed value happens to be.

**Why this removes the need for read locks.** Under a purely lock-based scheme (two-phase locking, 2PL), a reader must take a shared lock on a row, and a writer must take an exclusive lock, so a long-running read can stall writers and vice versa. Under MVCC, a reader simply ignores row versions created *after* its snapshot was taken — it doesn't need to lock anything, because it's not contending with the writer for the *same* version of the data. The writer creates a brand-new version rather than mutating the one the reader is looking at. This is the origin of the common description: "readers don't block writers, and writers don't block readers."

**Mechanics, concretely (PostgreSQL-style):**
1. Every row carries hidden metadata — roughly, the transaction ID that inserted it (`xmin`) and the transaction ID that deleted/superseded it (`xmax`), if any.
2. An `UPDATE` doesn't modify the row; it marks the old row version as expired (sets `xmax`) and inserts a new row version with a new `xmin`.
3. Each transaction computes a *visibility snapshot* — a set of transaction IDs considered "already committed as of now" — and when scanning a table, it only considers row versions whose `xmin` is in that committed set and whose `xmax` is not (or is a transaction not yet committed at snapshot time).
4. Old, no-longer-visible-to-anyone row versions accumulate as dead space and are later reclaimed by a garbage-collection process (`VACUUM` in Postgres; a background purge thread in InnoDB, which instead keeps old versions in the undo log rather than in the table itself).

**The tradeoff.** MVCC isn't free: it costs storage and cleanup overhead (bloated tables until vacuumed, undo-log growth), and different engines still need *some* locking for genuine write-write conflicts (two transactions updating the same row) — MVCC solves read/write contention, not write/write contention. It also interacts with isolation levels: the snapshot a transaction sees, and how often it's refreshed (once per transaction vs. once per statement), is exactly what distinguishes `REPEATABLE READ` from `READ COMMITTED` in an MVCC engine like PostgreSQL or MySQL/InnoDB.

### 2. System Design (Comparison)

Compare batch processing and stream processing as approaches to handling data. What does each optimize for, and what kind of problem would make you pick one over the other?

**Answer:**

Both are strategies for turning raw data into useful output, but they differ in *when* they process it and what they're willing to trade off to do so.

**Batch processing** collects data over a window of time (an hour, a day) and then processes the whole accumulated set in one pass. It optimizes for **throughput and efficiency over a large, bounded dataset**: because the whole input is available up front, the system can sort, join, and aggregate in ways that are hard or impossible with a partial, still-arriving stream, and it can pack work efficiently across a cluster. The cost is **latency** — results are only as fresh as the last batch run finished. Classic tools: Hadoop MapReduce, Spark (batch mode), traditional nightly ETL jobs into a data warehouse.

**Stream processing** processes each event (or small micro-batch of events) as it arrives, continuously, with no fixed end to the input. It optimizes for **low latency and freshness** — results reflect data that's seconds or milliseconds old — at the cost of working with incomplete information at any given instant (it can't "see the whole dataset" the way a batch job can) and generally needing more careful handling of out-of-order or late-arriving events (windowing, watermarks). Classic tools: Kafka Streams, Apache Flink, Spark Structured Streaming.

| | Batch | Stream |
|---|---|---|
| Input | Bounded, known dataset | Unbounded, continuous |
| Optimizes for | Throughput, efficiency | Latency, freshness |
| Result freshness | Minutes to hours old | Sub-second to seconds old |
| Handles late/out-of-order data | Trivially (all data is in hand) | Requires explicit windowing/watermarking |
| Typical use case | Monthly billing reports, large-scale log analytics, model training on historical data | Fraud detection, real-time dashboards, live recommendation updates |

**How to choose.** The deciding question is usually: *does the business decision this data feeds need to happen within seconds, or can it wait?* Fraud detection has to flag a suspicious transaction before it clears — that demands streaming. A monthly revenue report has no such deadline, so batch is simpler, cheaper, and easier to reason about (and easier to re-run if something goes wrong, since the whole bounded input is still sitting there). In practice, many real systems run both side by side — a "lambda architecture" or similar setup, where streaming gives an approximate, immediate view and a nightly batch job later recomputes the authoritative, fully-corrected numbers over the same data.

### 3. Computer Architecture (Scenario/Applied)

A program spends 40% of its execution time in a section that can be perfectly parallelized across any number of cores; the remaining 60% is inherently sequential and cannot be parallelized at all. Using Amdahl's Law, what is the maximum speedup this program could ever achieve, no matter how many cores you throw at it? Why does the sequential portion dominate so heavily?

**Answer:**

**Amdahl's Law** gives the theoretical speedup of a program when a fraction `P` of its work is parallelized across `n` processors, while the remaining `(1 - P)` fraction stays strictly sequential:

```
Speedup(n) = 1 / ( (1 - P) + P/n )
```

Here `P = 0.4` (the parallelizable 40%), so `(1 - P) = 0.6` (the sequential 60%).

**Plugging in the numbers.** As `n → ∞`, the term `P/n` shrinks toward `0`, so the formula collapses to its limiting case:

```
Speedup(∞) = 1 / (1 - P) = 1 / 0.6 ≈ 1.67×
```

So even with an infinite number of cores instantly finishing the parallel 40% of the work, the program can never run more than about **1.67 times faster** than the single-core baseline. Adding a 4th, 16th, or 1000th core buys diminishing, and eventually negligible, additional speedup — most of the theoretical gain is already captured with a fairly small number of cores.

**Why the sequential fraction dominates.** Total runtime is the sum of the sequential part (fixed, doesn't shrink no matter what) and the parallel part (shrinks toward zero as cores increase). Once the parallel part has shrunk close to zero, the sequential 60% — unaffected by parallelism entirely — becomes essentially the *entire* remaining runtime. You're now trying to speed up a program whose floor is fixed at 60% of the original time, so the best possible speedup is capped at `1 / 0.6`, full stop, independent of hardware.

**Why this matters practically.** Amdahl's Law is the reason engineering effort on parallelizing hot loops has a hard ceiling: it's often far more valuable to *reduce the sequential fraction itself* (e.g., eliminate a serialized lock, remove an unavoidable I/O wait, restructure an algorithm to expose more parallelism) than to keep adding cores to an already highly parallel section. It's also the classic counterpoint to naively assuming "N cores means N× speedup" — that only holds in the idealized limit where `P = 1`, i.e., the workload is embarrassingly parallel with no sequential part at all.
