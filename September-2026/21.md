### Question: Reorder List (Linked Lists — Medium)

You are given the head of a singly linked list containing `n` nodes, numbered `L0, L1, ..., Ln-1`.

Reorder the list to be on the following form, **in place** (without creating a new list and without modifying the node values, only the pointers):

```
L0 → Ln → L1 → Ln-1 → L2 → Ln-2 → ...
```

**Input format:**
- The head of a singly linked list.

**Output format:**
- No return value — the list must be reordered in place, and the function receives the head reference.

**Worked Examples:**

1. Input: `[1, 2, 3, 4]` → Output: `[1, 4, 2, 3]`
   (`L0=1, L1=2, L2=3, L3=4` → `L0, L3, L1, L2` = `1, 4, 2, 3`)
2. Input: `[1, 2, 3, 4, 5]` → Output: `[1, 5, 2, 4, 3]`
   (`L0=1, L1=2, L2=3, L3=4, L4=5` → `L0, L4, L1, L3, L2` = `1, 5, 2, 4, 3`)
3. Input: `[1, 2]` → Output: `[1, 2]`
   (Only two nodes — `L0, L1` reordered is just `L0, L1` itself, nothing changes.)

**Constraints:**
- The number of nodes in the list is in the range `[1, 5 * 10^4]`.
- `1 <= Node.val <= 1000`
- You must solve it **without** using `O(n)` extra space for a second data structure (e.g. no array/vector of node pointers), and without altering node values (only pointers may change).

---

### Step-by-Step Walkthrough

**Approach — Find Middle, Reverse Second Half, Merge Alternately**

Reordering `L0 → L1 → ... → Ln-1 → Ln` into `L0 → Ln → L1 → Ln-1 → ...` is really "zip together the first half of the list with the *reversed* second half." That observation splits the problem into three clean, independent steps, each of which is a classic linked-list technique on its own:

1. **Find the middle of the list** using the slow/fast pointer technique: `slow` moves one step at a time, `fast` moves two steps at a time. When `fast` reaches the end, `slow` sits at the middle node. This splits the list into a first half `[L0 ... Lm]` and a second half `[Lm+1 ... Ln]` (for even-length lists) or gives the first half one extra node (for odd-length lists) — either split works for the merge step that follows.

2. **Reverse the second half** in place using the standard iterative pointer-reversal (`prev`, `curr`, `next`). After this step we have two singly linked lists both starting from position 0 of their respective halves: the original first half `L0 → L1 → ... → Lm`, and the reversed second half `Ln → Ln-1 → ... → Lm+1`.

3. **Merge the two halves alternately**: take one node from the first list, then one from the second, then one from the first, and so on, splicing `next` pointers as we go. Since the reversed second half is now walked from `Ln` down to `Lm+1`, alternating first-half/second-half nodes produces exactly `L0, Ln, L1, Ln-1, L2, Ln-2, ...` — the required order. The first half is always the same length or one node longer than the second half, so the loop naturally terminates when the second list is exhausted, and the last remaining node of the first list (if any, in the odd-length case) is simply left as the tail with `next = nullptr`.

**Why it works:** Each of the three steps preserves exactly the information needed by the next step — finding the middle only needs pointer traversal (no value comparison), reversing a singly linked list is a well-known `O(n)` in-place operation, and merging two equal-or-near-equal-length lists alternately is a direct pointer-splicing operation. Chaining them avoids any need for extra storage like an array of node pointers, satisfying the `O(1)` extra space constraint.

**Complexity Analysis:**
- **Time complexity:** `O(n)` — each of the three steps (find middle, reverse, merge) does a single linear pass over (half of) the list.
- **Space complexity:** `O(1)` — only a constant number of pointers (`slow`, `fast`, `prev`, `curr`, `next`, etc.) are used; no auxiliary array or recursion stack.

### C++ Code

```cpp
#include <iostream>
using namespace std;

// Definition for singly-linked list.
struct ListNode {
    int val;
    ListNode *next;
    ListNode(int x) : val(x), next(nullptr) {}
};

class Solution {
public:
    void reorderList(ListNode* head) {
        if (head == nullptr || head->next == nullptr) return;

        // Step 1: find the middle using slow/fast pointers.
        // When fast hits the end, slow is at (or just before) the middle.
        ListNode* slow = head;
        ListNode* fast = head;
        while (fast->next != nullptr && fast->next->next != nullptr) {
            slow = slow->next;
            fast = fast->next->next;
        }

        // Step 2: reverse the second half (everything after 'slow').
        ListNode* secondHead = slow->next;
        slow->next = nullptr; // cut the first half off from the second half
        ListNode* prev = nullptr;
        ListNode* curr = secondHead;
        while (curr != nullptr) {
            ListNode* nextNode = curr->next;
            curr->next = prev;
            prev = curr;
            curr = nextNode;
        }
        ListNode* secondList = prev; // head of the reversed second half

        // Step 3: merge the first half and reversed second half alternately.
        ListNode* firstList = head;
        while (secondList != nullptr) {
            ListNode* firstNext = firstList->next;
            ListNode* secondNext = secondList->next;

            firstList->next = secondList;
            secondList->next = firstNext;

            firstList = firstNext;
            secondList = secondNext;
        }
        // If the original list had odd length, the last node of firstList
        // is already correctly terminated with next == nullptr from Step 2's cut.
    }
};

// Helper to build a linked list from an array of values.
ListNode* buildList(const int* vals, int n) {
    if (n == 0) return nullptr;
    ListNode* head = new ListNode(vals[0]);
    ListNode* tail = head;
    for (int i = 1; i < n; ++i) {
        tail->next = new ListNode(vals[i]);
        tail = tail->next;
    }
    return head;
}

// Helper to print a linked list.
void printList(ListNode* head) {
    while (head != nullptr) {
        cout << head->val;
        if (head->next != nullptr) cout << " -> ";
        head = head->next;
    }
    cout << endl;
}

int main() {
    Solution sol;

    // Example 1: [1,2,3,4] -> [1,4,2,3]
    int a1[] = {1, 2, 3, 4};
    ListNode* l1 = buildList(a1, 4);
    sol.reorderList(l1);
    cout << "Example 1: ";
    printList(l1); // expected: 1 -> 4 -> 2 -> 3

    // Example 2: [1,2,3,4,5] -> [1,5,2,4,3]
    int a2[] = {1, 2, 3, 4, 5};
    ListNode* l2 = buildList(a2, 5);
    sol.reorderList(l2);
    cout << "Example 2: ";
    printList(l2); // expected: 1 -> 5 -> 2 -> 4 -> 3

    // Example 3: [1,2] -> [1,2]
    int a3[] = {1, 2};
    ListNode* l3 = buildList(a3, 2);
    sol.reorderList(l3);
    cout << "Example 3: ";
    printList(l3); // expected: 1 -> 2

    return 0;
}
```

**Trace against the examples:**
- `[1,2,3,4]`: slow/fast find `slow = 2` (node with val 2) as the middle split point after the loop (fast reaches near the end). Second half `[3,4]` reversed becomes `[4,3]`. Merging `[1,2]` with `[4,3]` alternately gives `1 -> 4 -> 2 -> 3`. ✓
- `[1,2,3,4,5]`: split into first half `[1,2,3]` and second half `[4,5]`, reversed to `[5,4]`. Merging `[1,2,3]` with `[5,4]` alternately gives `1 -> 5 -> 2 -> 4 -> 3` (node `3` is left over from the longer first half and correctly terminates the list). ✓
- `[1,2]`: handled directly — after finding the split, first half is `[1]`, second half `[2]` reversed is still `[2]`; merging gives `1 -> 2`, unchanged. ✓

## CS Fundamentals

### 1. Computer Networks (Conceptual/Definition)

Explain the TCP three-way handshake step by step. Why are three steps necessary instead of just two?

**Answer:**

The TCP three-way handshake is the process by which two hosts establish a reliable, connection-oriented session before exchanging application data. It consists of three messages:

1. **SYN** — The client sends a segment with the `SYN` flag set and an initial sequence number (ISN), say `seq = x`, to the server. This says "I want to open a connection, and my byte stream will start counting from `x`."
2. **SYN-ACK** — The server responds with a segment that has both `SYN` and `ACK` flags set. The `ACK` field is `x + 1` (acknowledging the client's SYN), and it includes the server's own initial sequence number `seq = y`. This says "I acknowledge your SYN, and here is my own starting sequence number."
3. **ACK** — The client sends a final segment with `ACK` set and `ack = y + 1`, acknowledging the server's SYN. This says "I acknowledge your SYN too — connection established."

After this exchange, both sides have confirmed two things about each other: that they can *send* data (their SYN was received) and that they can *receive* data (their SYN was acknowledged).

**Why not two steps?** A two-way handshake (just SYN, then ACK) would only let the server confirm that the client can send and receive, but the client would have no confirmation that the server received its SYN acknowledgment correctly — and more importantly, the server would have committed resources (allocated a connection state) without knowing if the client actually intends to proceed, making the server vulnerable to being tricked into opening connections from spoofed or duplicate SYNs. The third step (client's final ACK) is what confirms to the *server* that the client actually received the server's SYN-ACK and is ready to communicate — without it, the server can never be sure the connection is genuinely two-way live rather than a stray or delayed packet from an old/duplicate connection attempt.

**Why this matters:** This handshake is the foundation of every reliable TCP connection (HTTP/HTTPS, SSH, database connections, etc.). It's also the root cause of the classic **SYN flood** DoS attack — an attacker sends many SYNs without ever completing step 3, exhausting the server's half-open connection table — which is why real-world servers use defenses like SYN cookies (avoiding pre-allocating state until the handshake fully completes).

### 2. OOP (Scenario/Applied)

You're designing a payment processing system that must support credit cards, PayPal, and cryptocurrency today, with more payment methods likely to be added later. How would you apply OOP principles — specifically abstraction and the Strategy pattern — to design this so adding a new payment method never requires touching existing code?

**Answer:**

**Step 1 — Identify the varying behavior.** The part of the system that changes per payment method is *how a payment is actually processed* (the API calls, validation, and confirmation logic differ for a credit card gateway vs. PayPal vs. a crypto wallet). Everything else — order creation, showing a receipt, logging — stays the same regardless of payment method. This is exactly the situation the **Strategy pattern** is built for: encapsulate the varying algorithm/behavior behind a common interface, and let the surrounding code depend only on that interface.

**Step 2 — Define an abstraction.** Create an abstract base class (or interface) that declares the contract every payment method must fulfill:

```cpp
class PaymentStrategy {
public:
    virtual bool pay(double amount) = 0;      // returns success/failure
    virtual ~PaymentStrategy() = default;
};

class CreditCardPayment : public PaymentStrategy {
public:
    bool pay(double amount) override {
        // credit card gateway API call, validation, etc.
        return true;
    }
};

class PayPalPayment : public PaymentStrategy {
public:
    bool pay(double amount) override {
        // PayPal API call
        return true;
    }
};

class CryptoPayment : public PaymentStrategy {
public:
    bool pay(double amount) override {
        // blockchain transaction logic
        return true;
    }
};
```

**Step 3 — Depend on the abstraction, not the concrete classes.** The order-processing code holds a `PaymentStrategy*` (or a smart pointer / reference), never a `CreditCardPayment` or `PayPalPayment` directly:

```cpp
class Order {
    PaymentStrategy* paymentMethod;
public:
    Order(PaymentStrategy* method) : paymentMethod(method) {}
    bool checkout(double amount) {
        return paymentMethod->pay(amount); // dynamic dispatch picks the right pay()
    }
};
```

**Step 4 — Adding a new method (e.g., Apple Pay) later.** You write a new `ApplePayPayment : public PaymentStrategy` class implementing `pay()`. Nothing in `Order`, or anywhere else that already depends on `PaymentStrategy`, needs to change or even be recompiled against — this is the **Open/Closed Principle** in action (open for extension, closed for modification), made possible directly by abstraction (the interface hides implementation differences) and polymorphism (the correct `pay()` is dispatched at runtime via the vtable based on the actual object type).

**Why this matters:** Without this design, adding a new payment method would mean editing a growing `if/else` or `switch` chain scattered across the codebase (`if (type == "creditcard") ... else if (type == "paypal") ...`), which is fragile and risks breaking existing payment flows every time a new one is added. The Strategy pattern isolates that risk to one new, self-contained class per payment method — this is precisely why it's one of the most common design-pattern questions in interviews for payment, notification, and pricing-engine style systems.

### 3. System Design Basics (Comparison)

Compare horizontal scaling and vertical scaling for a web application whose traffic is growing steadily. When would you pick one over the other?

**Answer:**

| Aspect | Vertical Scaling (Scale Up) | Horizontal Scaling (Scale Out) |
|---|---|---|
| Definition | Add more power (CPU, RAM, faster disk) to a **single existing machine**. | Add **more machines** running the same application, splitting load across them. |
| Ceiling | Hard physical/cost ceiling — there's a biggest machine money can buy, and costs rise non-linearly near the top end. | Effectively unbounded — keep adding commodity machines as needed. |
| Complexity | Simple — no code changes needed; the application doesn't need to be aware it's on a bigger machine. | Requires the application to be stateless (or externalize state), plus a load balancer to distribute requests, and often a distributed data layer. |
| Fault tolerance | Single point of failure — if that one machine goes down, the whole application is down. | Naturally fault-tolerant — if one node fails, traffic is routed to the remaining healthy nodes. |
| Downtime for scaling | Often requires a restart/downtime window to resize the machine. | New nodes can be added or removed without downtime (rolling deploys, auto-scaling groups). |
| Cost model | Cost grows faster than linearly at the high end (premium hardware is disproportionately expensive). | Cost grows roughly linearly with commodity hardware, and can scale down again when traffic drops (elastic). |

**When to pick vertical scaling:** Early-stage applications, or workloads that are inherently hard to distribute (e.g., a single large in-memory dataset that a certain class of algorithm needs to process as one unit, or a legacy monolith not built for statelessness). It buys time cheaply and simply when traffic is still small-to-moderate and engineering effort is scarce.

**When to pick horizontal scaling:** Once traffic grows past what a single machine can reasonably handle, or once **availability** matters (you can't tolerate a single point of failure), or once traffic is spiky/elastic (you want to scale nodes up and down with demand rather than paying for peak capacity 24/7). This is the standard approach for any web application expected to grow significantly, but it requires upfront design work: the application tier must be stateless (session data moved to a shared store like Redis), and the database layer typically needs read replicas or sharding since the database is usually the hardest part of the system to scale horizontally.

**Why this matters:** In practice, most systems that "steadily grow" end up doing both — vertically scaling individual components (e.g., giving the database more RAM) up to a comfortable ceiling, while horizontally scaling the stateless application tier behind a load balancer for both capacity and fault tolerance. Recognizing which layer of the system is the actual bottleneck (CPU-bound app servers vs. a single database instance) is what determines which scaling strategy actually helps.
