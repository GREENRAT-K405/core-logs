## DSA

### Question: Combination Sum (Recursion/Backtracking — Medium)

You are given an array of **distinct** positive integers `candidates` and a target integer `target`. Return **all unique combinations** of numbers from `candidates` where the chosen numbers sum to `target`. The **same number may be chosen from `candidates` an unlimited number of times** (as long as the running sum doesn't exceed `target`). Combinations may be returned in any order, but two combinations are considered the same if they contain the same numbers with the same frequency, regardless of order (i.e. `[2,2,3]` and `[3,2,2]` are duplicates and only one should appear).

**Input format:**
- An array of distinct positive integers `candidates`.
- An integer `target`.

**Output format:**
- A list of lists of integers — every unique combination of numbers from `candidates` (repetition allowed) that sums exactly to `target`.

**Worked Examples:**

1. `candidates = [2,3,6,7]`, `target = 7` → output `[[2,2,3],[7]]` (`2+2+3=7` and `7=7`; no other combination works).
2. `candidates = [2,3,5]`, `target = 8` → output `[[2,2,2,2],[2,3,3],[3,5]]`.
3. `candidates = [2]`, `target = 1` → output `[]` (the smallest available number, `2`, already exceeds the target).

**Constraints:**
- `1 <= candidates.length <= 30`
- `2 <= candidates[i] <= 40`
- All elements of `candidates` are **distinct**.
- `1 <= target <= 40`

---

### Step-by-Step Walkthrough

**Approach — Backtracking (DFS) over choices, with reuse and index-based pruning**

The problem is asking us to explore every way of building up to `target` by repeatedly choosing numbers from `candidates`. This is a textbook backtracking shape: at each step we either "take" the current candidate again, or "move on" and never consider it again for the rest of this branch. The tricky part is avoiding duplicate combinations like `[2,3]` and `[3,2]` — we solve that by always choosing candidates in non-decreasing order within a combination, using a `start` index that never goes backward.

1. **Sort `candidates`** first. Sorting isn't required for correctness of the recursion itself, but it lets us **prune early**: once `candidates[i] > remaining`, every later candidate (being larger, since the array is sorted) will also overshoot, so we can `break` out of the loop immediately instead of checking the rest.
2. **Define a recursive helper** `backtrack(start, remaining, path)`:
   - **Base cases:**
     - If `remaining == 0`: the current `path` sums exactly to the original target — record a copy of `path` as a valid combination, and return.
     - If `remaining < 0`: this branch overshot — return without recording anything (in practice we avoid ever recursing into a negative remaining by checking before the call, but conceptually this is the failure case).
   - **Recursive case:** iterate `i` from `start` to the end of `candidates`:
     - If `candidates[i] > remaining`, break (sorted-order pruning, see above).
     - Otherwise, "choose" `candidates[i]`: push it onto `path`, then recurse as `backtrack(i, remaining - candidates[i], path)`. Note the recursive call passes `i`, **not `i + 1`** — this is what allows the same number to be reused.
     - "Un-choose" (backtrack): pop `candidates[i]` off `path` before moving to the next `i`, so the next iteration explores a sibling branch cleanly.
3. Start the whole process with `backtrack(0, target, {})` and collect every recorded `path` into the answer.

**Why it works:** Because we only ever recurse forward from the current `start` index (never backward), each recombination of numbers is generated in exactly one non-decreasing order — so we can never produce `[2,3]` in one branch and `[3,2]` in another; only `[2,3]` is ever built. Allowing the recursive call to reuse index `i` (instead of advancing to `i+1`) is exactly what permits picking the same number multiple times, while still respecting the non-decreasing constraint since we never go back to an earlier, smaller index after moving on. The sorted-order early `break` is a pure optimization — it doesn't change correctness, since we've already established that if the smallest remaining candidate that hasn't been ruled out overshoots, every one after it does too.

**Complexity Analysis:**
- **Time complexity:** Exponential in the worst case — roughly `O(2^target)` in the number of leaves of the recursion tree, since at each depth we branch across candidates and depth is bounded by `target / min(candidates)`. More precisely it's bounded by the number of valid combinations times the average combination length (for the copying work), which is what makes this problem "backtracking with pruning" rather than a polynomial-time one — pruning (sorting + early break, plus never exceeding `remaining`) keeps it practical for the given constraints (`target <= 40`).
- **Space complexity:** `O(target / min(candidates))` for the recursion stack and the `path` buffer at any point in time (not counting the space needed to store the output itself, which is proportional to the total number and length of valid combinations found).

### C++ Code

```cpp
#include <iostream>
#include <vector>
#include <algorithm>
using namespace std;

class Solution {
public:
    vector<vector<int>> combinationSum(vector<int>& candidates, int target) {
        sort(candidates.begin(), candidates.end()); // enables the early-break pruning below
        vector<vector<int>> result;
        vector<int> path;
        backtrack(candidates, target, 0, path, result);
        return result;
    }

private:
    void backtrack(vector<int>& candidates, int remaining, int start,
                    vector<int>& path, vector<vector<int>>& result) {
        if (remaining == 0) {
            result.push_back(path); // found a valid combination, record a copy
            return;
        }

        for (int i = start; i < static_cast<int>(candidates.size()); ++i) {
            if (candidates[i] > remaining) {
                // sorted array => every candidate after this one is even larger, stop early
                break;
            }

            path.push_back(candidates[i]);
            // pass i (not i + 1) so the same candidate can be reused
            backtrack(candidates, remaining - candidates[i], i, path, result);
            path.pop_back(); // undo the choice before trying the next candidate
        }
    }
};

void printResult(const vector<vector<int>>& combos) {
    cout << "[";
    for (size_t i = 0; i < combos.size(); ++i) {
        cout << "[";
        for (size_t j = 0; j < combos[i].size(); ++j) {
            cout << combos[i][j];
            if (j + 1 < combos[i].size()) cout << ",";
        }
        cout << "]";
        if (i + 1 < combos.size()) cout << ",";
    }
    cout << "]" << endl;
}

int main() {
    Solution sol;

    vector<int> c1 = {2, 3, 6, 7};
    cout << "combinationSum([2,3,6,7], 7) = ";
    printResult(sol.combinationSum(c1, 7)); // expected [[2,2,3],[7]]

    vector<int> c2 = {2, 3, 5};
    cout << "combinationSum([2,3,5], 8) = ";
    printResult(sol.combinationSum(c2, 8)); // expected [[2,2,2,2],[2,3,3],[3,5]]

    vector<int> c3 = {2};
    cout << "combinationSum([2], 1) = ";
    printResult(sol.combinationSum(c3, 1)); // expected []

    return 0;
}
```

**Trace against the examples:**
- `[2,3,6,7]`, target `7`: sorted stays `[2,3,6,7]`. Branch `2 -> 2 -> 3` sums to `7` (recorded as `[2,2,3]`); branch `2 -> 2 -> 2` overshoots when adding another `2` (remaining would go negative before recording, so backtracks); branch `7` alone sums to `7` (recorded as `[7]`); `6` alone leaves remaining `1`, and the only candidate `>= 6` left is `7 > 1`, so it prunes with nothing found. Final: `[[2,2,3],[7]]`. ✓
- `[2,3,5]`, target `8`: branches explore `2,2,2,2` (sums to 8, recorded), `2,2,3,?` remaining `1` after `2,2,3` — next candidate must be `>=3` but `3>1`, dead end; wait, correctly the recursion tries `2,3,3` (2+3+3=8, recorded) since after choosing `2` then `3`, remaining is `3`, and choosing `3` again (index stays at `3`'s position) reaches `0`; and `3,5` (3+5=8, recorded). Final: `[[2,2,2,2],[2,3,3],[3,5]]`. ✓
- `[2]`, target `1`: the loop's first check is `candidates[0]=2 > remaining=1`, so it breaks immediately without recursing — `result` stays empty → `[]`. ✓

### 1. DBMS (Conceptual/Definition)

What are the ACID properties of a database transaction? Define each of the four properties and explain what could go wrong in a multi-user database system if any single one of them were dropped.

**Answer:**

ACID is an acronym describing four guarantees a database transaction system provides so that transactions can be relied upon even under concurrency and failures:

- **Atomicity** — A transaction is treated as a single indivisible unit: either *all* of its operations are applied, or *none* of them are. If a transaction fails partway through (a crash, a constraint violation), the database rolls back every change it had already made, so no partial update is ever left behind. *Without it:* a bank transfer that debits one account but crashes before crediting the other would silently destroy money — the system would be left in an inconsistent, partially-applied state with no way to know it happened.

- **Consistency** — A transaction takes the database from one valid state to another valid state, respecting all defined rules: constraints, foreign keys, triggers, and application-level invariants. *Without it:* a transaction could complete "successfully" while leaving the database violating its own schema rules (e.g., an order referencing a customer ID that doesn't exist), silently corrupting data integrity that other transactions and reports depend on.

- **Isolation** — Concurrently executing transactions must not interfere with each other's intermediate state; the end result must look as if the transactions had run one after another (serially), even though they may physically overlap in time. *Without it:* one transaction could read another transaction's uncommitted, half-finished changes (a "dirty read"), or two transactions could race to update the same row and one update could silently overwrite the other (a "lost update").

- **Durability** — Once a transaction is committed, its changes must survive any subsequent crash, power loss, or restart — typically guaranteed by writing to a write-ahead log (WAL) or non-volatile storage before acknowledging the commit. *Without it:* a user could be told "your payment succeeded," the server could crash a second later, and the payment record could simply vanish on restart, even though the client was already told it worked.

**Why this matters:** ACID is the contract that lets application developers reason about a database as if only one thing happens at a time, even when thousands of transactions are actually running concurrently across many connections. It's also the axis along which many modern NoSQL and distributed databases deliberately trade off — e.g., "eventual consistency" systems relax the Consistency/Isolation guarantees in exchange for higher availability and throughput, which is a reasonable trade for a social media like-counter, but would be unacceptable for a bank ledger. Knowing which of the four properties a system actually gives you is the real question behind any "is this database safe for X?" decision.

### 2. OOP (Comparison)

Compare **composition** and **inheritance** as two ways of reusing behavior across classes in object-oriented design. When would you prefer one over the other, and what's the classic pitfall that leads experienced developers to favor "composition over inheritance"?

**Answer:**

| Aspect | Inheritance | Composition |
|---|---|---|
| Relationship modeled | "is-a" — a `Car` *is a* `Vehicle`. | "has-a" — a `Car` *has an* `Engine`. |
| Mechanism | A subclass extends a base class, inheriting its fields/methods directly and can override them. | An object holds a reference/instance of another object and delegates work to it through its public interface. |
| Coupling | Tight — subclass depends on the base class's internal implementation details, not just its interface; a base class change can silently break subclasses ("fragile base class problem"). | Loose — the containing object only depends on the composed object's public interface, and the composed object can be freely swapped for another implementation of the same interface. |
| Flexibility at runtime | Fixed at compile time — the inheritance hierarchy of an object can't change after it's created. | Flexible — the composed object (e.g., a strategy or a dependency) can be swapped at runtime, enabling patterns like Strategy or Dependency Injection. |
| Code reuse style | Reuses by inheriting an entire "is-a" contract, including behavior you may not want. | Reuses by explicitly picking only the specific behaviors/objects you need. |
| Typical pitfall | Deep or wide inheritance hierarchies become hard to reason about, and multiple inheritance (where supported) creates ambiguity (the "diamond problem"). | Slightly more boilerplate up front (you must explicitly write delegating methods or hold references), since there's no automatic "inherit everything." |

**When to prefer inheritance:** when there's a genuine, stable "is-a" relationship and you want polymorphism — e.g., a `Shape` base class with `Circle`/`Square` subclasses that all need to be usable interchangeably wherever a `Shape` is expected.

**When to prefer composition:** when you want to reuse behavior without committing to a rigid hierarchy, or when the relationship is really "uses" rather than "is" — e.g., a `Car` shouldn't inherit from `Engine` (a car is not a kind of engine), it should *contain* one.

**The classic pitfall:** the "fragile base class problem" — a deep inheritance chain (e.g., `Bird -> FlyingBird -> Sparrow`) looks clean until you hit a case the hierarchy didn't anticipate (e.g., a `Penguin`, which is a `Bird` but can't fly), forcing awkward overrides, exceptions, or a hierarchy rewrite. Composition avoids this because behaviors are assembled from independent, swappable pieces (e.g., a `FlyBehavior` interface a `Penguin` simply doesn't attach) rather than baked into a rigid "is-a" chain — which is exactly the reasoning behind the well-known design principle "favor composition over inheritance."

### 3. Computer Architecture (Scenario/Applied)

You profile a performance-critical C++ loop that iterates over a large 2D array (say 4096 x 4096 doubles) and sums all its elements. Version A iterates row-major (`for row { for col { sum += arr[row][col]; } }`) and Version B iterates column-major (`for col { for row { sum += arr[row][col]; } }`), with the array stored in standard row-major layout. Version A runs dramatically faster than Version B on the same hardware and data. Explain why, in terms of cache behavior.

**Answer:**

The difference comes down to **spatial locality and how CPU caches load memory**, not anything about the arithmetic itself (both versions do the exact same number of additions).

**How the array is actually stored:** In row-major layout (the C/C++ default for a 2D array or `vector<vector<double>>`-style flattening), all elements of row 0 are stored contiguously in memory, immediately followed by all elements of row 1, and so on. So `arr[row][col]` and `arr[row][col+1]` sit right next to each other in RAM, while `arr[row][col]` and `arr[row+1][col]` are `4096 * sizeof(double)` = 32KB apart.

**What the CPU cache does:** A CPU doesn't fetch memory one variable at a time — it fetches memory in fixed-size **cache lines** (typically 64 bytes, i.e. 8 doubles). When the program reads `arr[row][col]`, the hardware pulls in that entire 64-byte line, which (in row-major layout) also contains `arr[row][col+1]` through `arr[row][col+7]`.

- **Version A (row-major traversal)** accesses `arr[row][0], arr[row][1], arr[row][2], ...` in order. The first access to a cache line is a cache miss (must go to RAM/L2/L3), but the next 7 accesses land in the *same* already-loaded cache line — 7 out of every 8 accesses are cheap cache hits. This is **excellent spatial locality**.
- **Version B (column-major traversal)** accesses `arr[0][col], arr[1][col], arr[2][col], ...` — each of these is 32KB apart in memory, meaning each access lands in a *different* cache line, and with a 4096-row array those lines don't stay resident (they get evicted long before the loop comes back around to reuse them). Essentially **every single access is a cache miss**, forcing a trip out to slower memory each time.

**The cost:** A cache hit (L1) typically costs a few CPU cycles; a full miss out to main memory can cost on the order of 100+ cycles. Since Version B turns nearly every access into a miss instead of roughly 1-in-8, it can easily run several times slower — even though the CPU executes the exact same number of `+=` operations in both versions. This is entirely a memory-access-pattern problem, invisible if you only look at the algorithm's "time complexity" (both are `O(n^2)`), which is precisely why it matters: Big-O analysis doesn't capture constant-factor effects like cache locality, but on real hardware those constants can dominate wall-clock time.

**Why this matters:** This is the practical reasoning behind advice like "iterate arrays in memory order," "prefer array-of-structs vs. struct-of-arrays depending on access pattern," and why techniques like *loop tiling/blocking* exist for larger workloads (restructuring loops to reuse a small block of data while it's still cache-resident, before moving to the next block) — squeezing out cache-friendly access patterns is often a bigger real-world performance win than micro-optimizing the arithmetic itself.
