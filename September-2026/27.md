### Question: Linked List Cycle II (Linked Lists — Medium)

**Problem Statement**

Given the `head` of a singly linked list, determine if the list contains a cycle. If it does, return the node where the cycle *begins*. If there is no cycle, return `null` (`nullptr`).

A cycle exists if, by repeatedly following the `next` pointer, you can eventually return to a node you've already visited. Internally this is represented by a `pos` value: the zero-indexed position in the list that `tail.next` points back to, or `-1` if there is no cycle. `pos` is only used to build the test case — your function does not receive it.

You must solve it using **O(1) extra memory** (no hash sets of visited nodes).

**Input/Output Format**

- Input: the head node of a singly linked list (each node has an `int val` and a `next` pointer).
- Output: the node at which the cycle begins, or `nullptr` if the list is acyclic.

**Examples**

1. Input: `head = [3,2,0,-4]`, `pos = 1` (tail connects to the node with value `2`, index 1) → Output: the node with value `2`.
2. Input: `head = [1,2]`, `pos = 0` (tail connects back to the head) → Output: the node with value `1`.
3. Input: `head = [1]`, `pos = -1` (no cycle) → Output: `nullptr`.

**Constraints**

- The number of nodes is in the range `[0, 10^4]`.
- `-10^5 <= Node.val <= 10^5`
- `pos` is `-1` or a valid index into the list.
- Follow-up: can you solve it without allocating any extra data structure? (Yes — that's the required solution here.)

### Step-by-Step Walkthrough

**The naive approach.** Walk the list while inserting each visited node's address into a hash set; the moment you're about to visit a node already in the set, that node is the cycle start. This is correct and O(n) time, but O(n) space — it fails the O(1) memory requirement.

**Getting to O(1) space: Floyd's Tortoise and Hare.** Use two pointers, `slow` (moves one step at a time) and `fast` (moves two steps at a time), both starting at `head`.

*Phase 1 — detect whether a cycle exists.* Advance `slow` by 1 and `fast` by 2 each iteration. If the list is acyclic, `fast` (or `fast->next`) hits `nullptr` and you can return `nullptr` immediately. If a cycle exists, `fast` eventually laps `slow` from behind and they land on the same node — this must happen within one full loop of the cycle, because each step `fast` closes the gap between them by exactly 1 node once both are inside the cycle.

*Phase 2 — find the cycle's start.* This is the part that needs a short proof, not just a memorized trick. Let:
- `L` = the distance from `head` to the cycle's entry node.
- `C` = the length of the cycle.
- `k` = the distance from the entry node to the point where `slow` and `fast` first met, measured going forward around the cycle.

When they meet, `slow` has traveled `L + k` steps. `fast` has traveled `2(L + k)` steps (twice as far, since it moves twice as fast). `fast` has also gone around the cycle some whole number of extra times compared to `slow`, so the *difference* in their distances, `2(L+k) - (L+k) = L + k`, must be a multiple of the cycle length `C`. So `L + k = m·C` for some integer `m ≥ 1`, which rearranges to:

```
L = m·C - k
```

Now place one pointer back at `head` and leave the other at the meeting point, and advance *both* one step at a time. The pointer from `head` needs `L` steps to reach the entry node. The pointer at the meeting point needs `C - k` steps to reach the entry node (it has `k` left to close the loop back to the entry, so `C - k` steps get it there — and since `L = mC - k`, walking `L` steps from the meeting point lands on the same node modulo the cycle length, because `mC - k ≡ C - k (mod C)`). Both pointers therefore reach the entry node at exactly the same time, regardless of `m`. That shared meeting point is the answer.

**Why this matters / why not just "hash set + return":** the interview follow-up (O(1) space) is testing whether you know Floyd's algorithm and can actually derive *why* resetting one pointer to `head` and walking both at speed 1 finds the entry node, rather than just reciting the steps.

**Complexity.**
- Time: O(n) — phase 1 takes at most O(n) steps (the fast pointer can't loop more than a bounded number of times before catching up in an n-node cycle), phase 2 takes at most O(n) steps.
- Space: O(1) — only a constant number of pointers are used, no matter the list size.

### C++ Code

```cpp
#include <cstddef>

struct ListNode {
    int val;
    ListNode* next;
    ListNode(int x) : val(x), next(nullptr) {}
};

ListNode* detectCycle(ListNode* head) {
    if (head == nullptr || head->next == nullptr) return nullptr;

    ListNode* slow = head;
    ListNode* fast = head;

    // Phase 1: determine whether a cycle exists.
    bool hasCycle = false;
    while (fast != nullptr && fast->next != nullptr) {
        slow = slow->next;
        fast = fast->next->next;
        if (slow == fast) {
            hasCycle = true;
            break;
        }
    }

    if (!hasCycle) return nullptr; // fast ran off the end -> acyclic

    // Phase 2: find the entry point of the cycle.
    // Reset one pointer to head; advance both one step at a time.
    // They provably meet at the cycle's start node (see walkthrough).
    ListNode* ptr1 = head;
    ListNode* ptr2 = slow; // slow is somewhere inside the cycle
    while (ptr1 != ptr2) {
        ptr1 = ptr1->next;
        ptr2 = ptr2->next;
    }

    return ptr1; // == ptr2, the cycle's entry node
}
```

### 1. Operating Systems (Conceptual)

What are the four necessary conditions (the "Coffman conditions") for a deadlock to occur in an operating system, and why must all four hold simultaneously for a deadlock to actually happen?

**Answer:**

A deadlock is a state where a set of processes are each waiting for a resource held by another process in the set, so none of them can ever proceed. The four Coffman conditions describe exactly the circumstances under which this can happen — and critically, **all four must be true at once**; breaking any single one makes deadlock impossible for that resource-allocation scheme.

1. **Mutual exclusion.** At least one resource must be held in a non-shareable mode — only one process can use it at a time (a printer, a write lock on a file, a mutex). If every resource could be freely shared by any number of processes simultaneously, no process would ever need to *wait* for one.

2. **Hold and wait.** A process must be allowed to hold at least one resource while simultaneously waiting to acquire additional resources held by other processes. If processes were forced to request all the resources they will ever need up front (and release everything if they can't get them all), they couldn't sit holding one resource while blocked waiting for another.

3. **No preemption.** Resources cannot be forcibly taken away from a process holding them — they can only be released voluntarily by the process itself once it finishes using them. If the OS could reach in and revoke a resource from a blocked process to hand it to another, that alone would break any cycle of waiting.

4. **Circular wait.** There must exist a set of processes `P0, P1, ..., Pn` where `P0` is waiting on a resource held by `P1`, `P1` is waiting on one held by `P2`, ..., and `Pn` is waiting on one held by `P0` — a closed loop of "waiting for." Without a cycle, the waiting chain eventually terminates at a process that *can* get what it needs, and progress cascades back through the chain.

**Why all four are required together.** Each condition on its own is common and often unavoidable in real systems (mutual exclusion is inherent to locks; hold-and-wait is how most programs naturally acquire multiple resources). The *combination* is what traps the system: mutual exclusion creates the possibility of waiting, hold-and-wait lets a process be simultaneously an obstacle and a blocked party, no-preemption means the OS can't break the standoff by force, and circular wait means the blocking chain loops back on itself with no free process left to unblock the rest. Remove any one — for example, impose a strict ordering on how resources must be requested (preventing circular wait), or use a wait-die/wound-wait scheme (relaxing no-preemption by aborting or restarting one of the transactions) — and the remaining three conditions alone cannot produce a deadlock. This is exactly why practical deadlock-*prevention* strategies (lock ordering, timeouts, resource preemption) each work by deliberately denying one specific condition rather than trying to detect and recover after the fact.

### 2. Computer Networks (Scenario/Applied)

A user types `www.example.com` into a browser that has never visited this domain before, on a machine with an empty local DNS cache. Walk through the sequence of DNS lookups that happens before the browser can even open a TCP connection to the site.

**Answer:**

DNS resolution is a **recursive query from the client to its resolver, followed by an iterative walk down the DNS hierarchy** by that resolver. Concretely:

1. **Browser/OS cache check.** The browser first checks its own cache, then the OS's stub resolver cache. Since the cache is empty here, nothing is found, and the request is handed to the configured **recursive resolver** — typically the ISP's DNS server or a public one like `8.8.8.8` or `1.1.1.1`.

2. **Recursive resolver checks its cache.** If no other client has recently asked this resolver about `www.example.com`, it has nothing cached either, so it must walk the DNS hierarchy itself, on the client's behalf, one level at a time.

3. **Query the root nameservers.** The resolver asks one of the 13 root server clusters, "who handles `.com`?" The root server doesn't know the answer to the full query — it only knows which servers are authoritative for the `.com` top-level domain (TLD), and returns a referral (NS records) to those TLD servers.

4. **Query the TLD nameservers.** The resolver then asks a `.com` TLD server, "who handles `example.com`?" The TLD server responds with a referral to `example.com`'s **authoritative nameservers** (the ones the domain's registrar has on file — e.g. run by the domain owner's DNS host).

5. **Query the authoritative nameserver.** The resolver asks `example.com`'s authoritative nameserver directly for the `A` (or `AAAA`) record of `www.example.com`. This server holds the actual answer and returns the IP address, along with a **TTL** (time-to-live) telling the resolver how long it's allowed to cache this answer before re-checking.

6. **Resolver caches and replies.** The recursive resolver caches the IP (and intermediate referrals) for the TTL duration, then returns the final IP address back to the browser/OS, which also caches it locally.

7. **Only now does the transport layer start.** With the IP address in hand, the browser initiates the TCP three-way handshake (`SYN` / `SYN-ACK` / `ACK`) to that IP on port 443, then proceeds with the TLS handshake, and only after all of that does the actual HTTP request go out.

**Why the caching at each layer matters.** Every layer in this chain (browser, OS, recursive resolver) caches results according to the record's TTL specifically so that step 3–5 (querying root → TLD → authoritative servers) — the slowest, most hierarchy-heavy part — almost never has to happen again for the same domain, for any client sharing that same recursive resolver, until the TTL expires. This is why the very first request to a brand-new domain from a "cold" network is noticeably slower than every subsequent one: the first request pays the full recursive-resolution cost, and every later one is served straight out of a cache at some layer.

### 3. OOP (Comparison)

Compare inheritance and composition as ways to reuse code and share behavior between classes. Why is "favor composition over inheritance" common advice, and when is inheritance still the better tool?

**Answer:**

Both let one class build on the behavior of another, but they model that relationship very differently.

**Inheritance** expresses an **"is-a"** relationship: a `Car` *is a* `Vehicle`. A subclass automatically gets its parent's fields and methods and can override them. The relationship is fixed at compile time (in most statically-typed languages) and is baked into the class hierarchy — you cannot change what a given object inherits from at runtime.

**Composition** expresses a **"has-a"** relationship: a `Car` *has a* `Engine`. Instead of inheriting behavior, a class holds a reference to another object and delegates to it for the behavior it needs. The composed object is typically supplied from outside (constructor injection) rather than hardcoded, so it can be swapped for a different implementation of the same interface — including at runtime.

| | Inheritance | Composition |
|---|---|---|
| Relationship | "is-a" | "has-a" |
| Coupling | Tight — subclass depends on parent's internal implementation details, not just its public contract (the "fragile base class" problem: changing the parent can silently break subclasses) | Loose — depending only on the composed object's interface |
| Flexibility | Fixed at compile time; single-inheritance languages also cap you to one parent | Can swap the composed implementation at runtime; freely combine multiple unrelated behaviors |
| Reuse granularity | Whole-hierarchy — you get everything the parent defines, whether you want it or not | Pick-and-choose — compose exactly the behaviors you need |
| Encapsulation | Weaker — subclass can reach into protected members, and overriding a method can violate invariants the parent relied on | Stronger — the composed object's internals stay hidden behind its interface |

**Why "favor composition" is common advice.** The core problem with inheritance-heavy designs is the **fragile base class problem**: a change to a parent class's implementation (not even its public interface) can silently break every subclass that depends on assumptions about *how* the parent works internally, because subclasses are tightly coupled to that implementation, not just to a contract. Deep inheritance hierarchies also tend to force awkward is-a relationships that don't really hold (a classic example: making `Square` inherit from `Rectangle` breaks when `Rectangle` exposes independent `setWidth`/`setHeight`, because a `Square` can't honor both independently — a violation of the Liskov Substitution Principle). Composition avoids both problems: a class only depends on the narrow interface of whatever it's composed with, and that dependency can be swapped freely — which is exactly what makes dependency injection and strategy-pattern-style designs so much easier to test and extend.

**When inheritance is still the right tool.** Inheritance genuinely shines when the "is-a" relationship is real, stable, and unlikely to be violated later — e.g. modeling a small, closed set of variants that all *must* satisfy the exact same contract and are unlikely to need independent substitution (a `Shape` base class with a fixed `area()` contract implemented by `Circle`, `Triangle`, etc., where you never need to swap a shape's "shape-ness" at runtime), or when you specifically want to reuse a well-tested, stable implementation and are confident the base class's internals won't shift under you. It's also simply less ceremony for small, genuinely hierarchical problems — composition's flexibility isn't free, since it often means more interfaces, more constructor wiring, and more indirection to read through. The practical rule of thumb: reach for inheritance when the relationship is truly "is-a" and the hierarchy is shallow and stable; reach for composition whenever you're unsure, need to swap behavior, or are tempted to inherit just to reuse a chunk of code.
