## DSA

### Question: Copy List with Random Pointer (Linked Lists — Medium)

You are given a linked list of `n` nodes. Each node has:
- An integer `val`.
- A `next` pointer to the next node (or `null` at the end).
- A `random` pointer that can point to **any** node in the list (including itself), or to `null`.

Construct a **deep copy** of the list — an entirely new set of nodes with the same `val` values and the same relative `next`/`random` structure, sharing no nodes with the original list.

**Input format:**
- The head of a linked list where each node is `(val, random_index)` — `random_index` is the index (0-based) of the node that `random` points to, or `null`.

**Output format:**
- The head of the deep-copied list (structurally identical, but made of entirely new node objects).

**Worked Examples:**

1. `[[7,null],[13,0],[11,4],[10,2],[1,0]]` → a new list with values `7,13,11,10,1` in order, where the copy of node `13` has `random` pointing to the copy of node `7` (index 0), the copy of node `11` has `random` pointing to the copy of node `1` (index 4), the copy of node `10` has `random` pointing to the copy of node `11` (index 2), and the copy of node `1` has `random` pointing to the copy of node `7` (index 0).
2. `[[1,1],[2,1]]` → a new list of two nodes, where both copied nodes have `random` pointing to the copy of node at index 1 (the second node).
3. `[[3,null],[3,0],[3,null]]` → a new list of three nodes all with `val = 3`; the copy of the middle node's `random` points to the copy of the first node, and the other two have `random = null`. (Tests that identical `val`s don't get confused with each other — pointer identity must be preserved structurally, not by value.)

**Constraints:**
- `0 <= n <= 1000`
- `-10^4 <= Node.val <= 10^4`
- `Node.random` is `null` or points to a node in the list.

---

### Step-by-Step Walkthrough

**Approach — O(1) extra space via list interleaving**

The hard part of this problem isn't copying `val`/`next` — it's copying `random`, since a node's `random` can point to a node **anywhere** in the list, including one that hasn't been created yet if we copy left-to-right naively. A common first idea is to use a hash map from original node → copy node, which works in `O(n)` time and `O(n)` space. We can do better on space with a clever trick: temporarily weave the copied nodes into the original list itself, using the original list as our own "lookup map."

1. **Pass 1 — Interleave copies.** Walk the original list. For each original node `cur`, create a copy node `copy` with the same `val`, and splice it in right after `cur`: `cur->next = copy; copy->next = originalNext;`. After this pass, the list looks like `A -> A' -> B -> B' -> C -> C' -> ...` where `X'` is the copy of `X`. Crucially, **every original node's copy is now reachable as `cur->next`**, which is exactly the lookup we need for step 2.
2. **Pass 2 — Assign `random` pointers on the copies.** Walk the interleaved list again, this time two nodes at a time (`cur`, then `cur->next` is `copy`). If `cur->random` is not null, then the node we want `copy->random` to point to is the **copy of `cur->random`**, which — thanks to the interleaving — is simply `cur->random->next`. So: `copy->random = cur->random ? cur->random->next : nullptr;`. This works because every original node `X` has its copy sitting immediately at `X->next`.
3. **Pass 3 — Un-interleave (restore the original list, extract the copy list).** Walk through both lists simultaneously, detaching each `copy` node from between the two original nodes and re-linking `copy->next` to the *next* copy node (`cur->next->next`), while restoring `cur->next` to point to the next original node. This restores the input list to its original state (good practice — don't mutate the caller's structure permanently) and produces the fully independent copied list.

**Why it works:** The interleaving step turns "find the copy of node X" from a hash-map lookup into a simple pointer dereference (`X->next`), because we guarantee by construction that every original node's copy sits immediately after it. This removes the need for any auxiliary map, at the cost of two extra full passes over the list (which doesn't change the asymptotic time complexity).

**Complexity Analysis:**
- **Time complexity:** `O(n)` — three linear passes over a list of `n` nodes.
- **Space complexity:** `O(1)` extra space (not counting the output list itself, which is required regardless of approach), since we reuse the original list's structure instead of a hash map.

### C++ Code

```cpp
#include <iostream>
#include <unordered_map>
using namespace std;

// Definition for a node with a next and a random pointer.
class Node {
public:
    int val;
    Node* next;
    Node* random;
    Node(int _val) : val(_val), next(nullptr), random(nullptr) {}
};

class Solution {
public:
    Node* copyRandomList(Node* head) {
        if (head == nullptr) return nullptr;

        // Pass 1: interleave a copy of each node right after the original.
        // A -> B -> C  becomes  A -> A' -> B -> B' -> C -> C'
        for (Node* cur = head; cur != nullptr; ) {
            Node* copy = new Node(cur->val);
            copy->next = cur->next;
            cur->next = copy;
            cur = copy->next; // advance to the next *original* node
        }

        // Pass 2: set random pointers on the copies using the interleaving.
        // The copy of any original node X is always X->next.
        for (Node* cur = head; cur != nullptr; cur = cur->next->next) {
            Node* copy = cur->next;
            copy->random = (cur->random != nullptr) ? cur->random->next : nullptr;
        }

        // Pass 3: unweave the two lists, restoring the original and
        // extracting the fully independent copy.
        Node* copyHead = head->next;
        for (Node* cur = head; cur != nullptr; ) {
            Node* copy = cur->next;
            cur->next = copy->next; // restore original list's next
            copy->next = (copy->next != nullptr) ? copy->next->next : nullptr; // link copy list
            cur = cur->next;
        }

        return copyHead;
    }
};

// Helper to build a test list from (val, random_index) pairs.
Node* buildList(vector<pair<int,int>> spec) {
    vector<Node*> nodes;
    for (auto& p : spec) nodes.push_back(new Node(p.first));
    for (size_t i = 0; i + 1 < nodes.size(); i++) nodes[i]->next = nodes[i + 1];
    for (size_t i = 0; i < spec.size(); i++) {
        int idx = spec[i].second;
        if (idx >= 0) nodes[i]->random = nodes[idx];
    }
    return nodes.empty() ? nullptr : nodes[0];
}

void printList(Node* head) {
    // Print val and the val of the random target (or "null") for each node.
    for (Node* cur = head; cur != nullptr; cur = cur->next) {
        cout << "(" << cur->val << ", ";
        cout << (cur->random ? to_string(cur->random->val) : "null") << ") ";
    }
    cout << "\n";
}

int main() {
    // Example 1: [[7,null],[13,0],[11,4],[10,2],[1,0]]
    Node* head1 = buildList({{7,-1},{13,0},{11,4},{10,2},{1,0}});
    Solution sol;
    Node* copy1 = sol.copyRandomList(head1);
    cout << "Original after copy (should be unchanged): ";
    printList(head1);
    cout << "Deep copy:                                  ";
    printList(copy1);

    // Example 2: [[1,1],[2,1]]
    Node* head2 = buildList({{1,1},{2,1}});
    Node* copy2 = sol.copyRandomList(head2);
    cout << "Deep copy 2: ";
    printList(copy2);

    // Example 3: [[3,null],[3,0],[3,null]]
    Node* head3 = buildList({{3,-1},{3,0},{3,-1}});
    Node* copy3 = sol.copyRandomList(head3);
    cout << "Deep copy 3: ";
    printList(copy3);

    return 0;
}
```

**Trace against the examples:**
- Example 1: After interleaving, `7 -> 7' -> 13 -> 13' -> 11 -> 11' -> 10 -> 10' -> 1 -> 1'`. Pass 2 sets `13'->random = 7->random->next = 7'` (since `13`'s random is index 0 = node `7`), `11'->random = 1->next... ` — more precisely, `11`'s random is index 4 (node `1`), so `11'->random = (node 1)->next = 1'`; `10`'s random is index 2 (node `11`), so `10'->random = 11'`; `1`'s random is index 0 (node `7`), so `1'->random = 7'`. Pass 3 restores the original chain `7->13->11->10->1` untouched and yields copy chain `7'->13'->11'->10'->1'` with matching random pointers. ✓
- Example 2: Both nodes' random points to index 1 (node `2`), so both copies' random correctly point to `2'`. ✓
- Example 3: Values are all `3`, but because we key off `cur->next` (pointer identity via interleaving, not value), the middle copy's random correctly points to the *first* copy specifically, not any node that merely has `val == 3`. ✓

### 1. Operating Systems (Conceptual/Definition)

What is virtual memory, and how does paging implement it? Explain what happens during a page fault, and describe the role of the Translation Lookaside Buffer (TLB) in making address translation fast.

**Answer:**

**Virtual memory** is an abstraction that gives each process the illusion of having its own large, contiguous, private address space, independent of how much physical RAM is actually installed and independent of where other processes' data lives in RAM. This provides two major benefits: **isolation** (one process cannot accidentally or maliciously read/write another process's memory, since each process's virtual addresses map to different physical locations) and the ability to **run programs larger than physical RAM** (by keeping only the actively-used parts of a program in RAM and the rest on disk).

**How paging implements it:** Both virtual and physical address spaces are divided into fixed-size chunks called **pages** (virtual side) and **frames** (physical side) — commonly 4 KB each. The OS maintains a **page table** per process that maps virtual page numbers to physical frame numbers. When a program accesses a virtual address, the CPU's Memory Management Unit (MMU) splits the address into a page number and an offset, looks up the page number in the page table to get the corresponding physical frame, and combines that frame with the offset to get the real physical address — all transparently to the running program.

**Page faults:** A page table entry has a "present" bit indicating whether that virtual page currently has a valid mapping to a physical frame. If a process accesses a page that is *not* currently loaded in RAM (e.g., it was swapped out to disk, or never loaded because of lazy/demand paging), the MMU raises a **page fault** — a hardware trap into the OS. The OS's page-fault handler then: (1) finds a free physical frame (evicting some other page via a replacement policy like LRU if RAM is full), (2) reads the required page's contents in from disk (the swap file or the executable's backing file), (3) updates the page table to mark that page present and pointing at the new frame, and (4) resumes the faulting instruction, which now succeeds. This is what allows programs to run with a working set larger than RAM, at the cost of disk I/O latency on a fault.

**Role of the TLB:** Doing a full page-table walk (which can itself require multiple memory accesses, since page tables are often multi-level trees) on *every single memory access* would be prohibitively slow. The **Translation Lookaside Buffer (TLB)** is a small, extremely fast hardware cache inside the CPU that stores recently-used virtual-to-physical page translations. On each memory access, the MMU first checks the TLB: on a **TLB hit**, the physical frame is available in essentially zero extra cycles; on a **TLB miss**, the MMU must fall back to walking the full page table (slow), and then caches that result in the TLB for next time. Because programs exhibit locality of reference (they tend to reuse the same pages repeatedly in a short time window), TLB hit rates are typically very high, which is what keeps virtual memory's overhead low in practice.

**Why this matters:** Virtual memory with paging is the reason multitasking operating systems can run many processes safely and can run software that wouldn't otherwise fit in RAM, and understanding the TLB is essential to understanding why certain workloads (e.g., ones that randomly scatter accesses across huge amounts of memory) suffer performance cliffs from TLB thrashing, and why techniques like "huge pages" (using larger page sizes to reduce the number of TLB entries needed) exist as a real-world optimization.

### 2. Computer Networks (Comparison)

Compare IPv4 and IPv6 addressing. Cover address size and total capacity, header design/complexity, and why IPv6 was introduced. Give an example address in each format.

**Answer:**

| Aspect | IPv4 | IPv6 |
|---|---|---|
| Address size | 32 bits | 128 bits |
| Total address space | ~4.3 billion (`2^32`) addresses | ~340 undecillion (`2^128`) addresses — practically inexhaustible |
| Notation | Dotted decimal, e.g. `192.168.1.1` (four 8-bit octets) | Colon-separated hextets, e.g. `2001:0db8:85a3:0000:0000:8a2e:0370:7334` (eight 16-bit groups, leading zeros and consecutive all-zero groups can be compressed with `::`, e.g. `2001:db8:85a3::8a2e:370:7334`) |
| Header design | 20-40 bytes, variable length due to optional fields; includes a header checksum that routers must recompute at every hop. | Fixed 40-byte header, no header checksum (relies on lower/upper layers for integrity), with optional data moved to "extension headers" chained after the base header — this simplifies and speeds up router processing. |
| Address configuration | Manual configuration or DHCP (Dynamic Host Configuration Protocol) is required to assign addresses. | Supports **stateless address autoconfiguration (SLAAC)**, where a host can generate its own address from the network prefix and its interface identifier without a DHCP server. |
| NAT (Network Address Translation) | Heavily relied upon in practice, since address exhaustion means most private/home networks share one public IPv4 address across many devices. | Designed so NAT is largely unnecessary — every device can have its own globally unique address, simplifying end-to-end connectivity (though NAT66/firewalling is still sometimes used for other reasons). |
| Security | IPsec is optional, bolted on. | IPsec support was originally part of the core specification (though in practice its use is still optional in deployment, this was a key original design goal). |

**Why IPv6 was introduced:** The core driver was **IPv4 address exhaustion** — with only ~4.3 billion possible addresses and an exploding number of internet-connected devices (phones, IoT devices, servers), the world ran out of freely allocatable IPv4 address blocks years ago, which is why NAT became a near-universal workaround (letting many devices share one public IP). IPv6's 128-bit space was designed to be large enough that every device on Earth (and then some) could have its own globally unique, routable address indefinitely, while also cleaning up header design for more efficient router processing and building in native support for autoconfiguration and (originally) mandatory IPsec.

**Why this matters:** Despite IPv6 solving IPv4's core scarcity problem, adoption has been slow and gradual because the two protocols are not directly interoperable (a pure IPv4-only host cannot natively talk to a pure IPv6-only host without a translation mechanism like NAT64 or dual-stack support), so the internet has spent over two decades in a transitional "dual-stack" period where most systems support both — a good example of how backward-compatibility constraints can make even a clearly superior technical design take decades to fully roll out.

### 3. OOP (Scenario/Applied)

You're building a logging system for an application that needs to write log messages to different destinations depending on configuration — console, a local file, and a remote logging server — and the set of destinations may grow in the future (e.g., adding a cloud log aggregator later). Describe how you would design the class hierarchy using OOP principles so that adding a new destination doesn't require modifying existing code, and name the design pattern this follows.

**Answer:**

**Design approach:** Define an abstract base class (or interface) `LogDestination` with a pure virtual method, e.g. `void write(const string& message) = 0;`. Each concrete destination — `ConsoleLogger`, `FileLogger`, `RemoteLogger` — is a subclass that implements `write()` in its own way (printing to `stdout`, appending to a file handle, or sending over a network socket, respectively). The main application code (say, a `Logger` class that callers actually use to log messages) holds a collection of `LogDestination*` (or `shared_ptr<LogDestination>`) pointers/references, and its `log(message)` method simply loops over that collection calling `destination->write(message)` on each one — it never needs to know the concrete type of any destination, only that it satisfies the `LogDestination` interface.

```cpp
class LogDestination {
public:
    virtual void write(const string& message) = 0;
    virtual ~LogDestination() = default;
};

class ConsoleLogger : public LogDestination {
public:
    void write(const string& message) override { cout << message << "\n"; }
};

class FileLogger : public LogDestination {
    ofstream file;
public:
    FileLogger(const string& path) : file(path, ios::app) {}
    void write(const string& message) override { file << message << "\n"; }
};

class RemoteLogger : public LogDestination {
public:
    void write(const string& message) override { /* send over network socket */ }
};

class Logger {
    vector<shared_ptr<LogDestination>> destinations;
public:
    void addDestination(shared_ptr<LogDestination> dest) { destinations.push_back(dest); }
    void log(const string& message) {
        for (auto& dest : destinations) dest->write(message); // polymorphic dispatch
    }
};
```

**OOP principles applied:**
- **Abstraction:** Callers of `Logger::log()` depend only on the `LogDestination` interface's contract ("something that can write a message"), not on how any particular destination actually delivers it.
- **Polymorphism:** The loop in `Logger::log()` calls `write()` through a base-class pointer, and the correct override (console/file/remote) is dispatched at runtime for each concrete object — this is what lets one uniform loop handle arbitrarily different destinations.
- **Open/Closed Principle (from SOLID):** The system is *open for extension* (adding a `CloudLogger` later is just a new subclass) but *closed for modification* (`Logger`'s code, and every existing destination's code, never needs to change to support the new destination) — this is exactly the property the scenario asks for.
- **Encapsulation:** Each destination hides its own implementation details (file handles, socket connections) behind the single `write()` method, so the rest of the system doesn't need to know or care how a `FileLogger` manages its file handle internally.

**Design pattern:** This is the **Strategy pattern** (each `LogDestination` subclass is an interchangeable "strategy" for how to deliver a message) combined with the `Logger` acting as a simple **composite/broadcaster** over multiple strategies at once. It's also a specific application of "**program to an interface, not an implementation**" — one of the most broadly useful OOP design guidelines.

**Why this matters:** This exact shape — an abstract interface plus a collection of interchangeable concrete implementations, driven by a class that only knows the interface — is one of the most common ways real systems stay maintainable as requirements grow; without it, adding each new log destination would mean editing a growing `if/else` chain inside `Logger::log()` itself, which violates Open/Closed and risks breaking existing destinations every time a new one is added.
