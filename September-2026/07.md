### Question: Word Ladder (Graphs — Hard)

You are given a `beginWord`, an `endWord`, and a dictionary `wordList` (all lowercase words of the same fixed length, made only of letters `a`-`z`). Find the **length of the shortest transformation sequence** from `beginWord` to `endWord`, such that:

- Only **one letter** can be changed at a time.
- Each transformed word **must exist in `wordList`** (the `beginWord` does not need to be in `wordList`, but every intermediate word and the `endWord` do).

Return the number of words in the shortest such sequence (including `beginWord` and `endWord`), or `0` if no such sequence exists.

**Input format:**
- A string `beginWord`.
- A string `endWord`.
- An array of strings `wordList` (the dictionary).

**Output format:**
- An integer — the length of the shortest transformation sequence, or `0` if `endWord` is unreachable.

**Worked Examples:**

1. `beginWord = "hit"`, `endWord = "cog"`, `wordList = ["hot","dot","dog","lot","log","cog"]` → output `5` (one shortest path is `hit -> hot -> dot -> dog -> cog`, which has 5 words).
2. `beginWord = "hit"`, `endWord = "cog"`, `wordList = ["hot","dot","dog","lot","log"]` → output `0` (`cog` is not in the dictionary, so it can never be reached).
3. `beginWord = "hot"`, `endWord = "dog"`, `wordList = ["hot","dog"]` → output `0` (there is no single-letter-change chain from `"hot"` to `"dog"` through only these two words — `"hot"` and `"dog"` differ in two letters, and no intermediate word exists in the list to bridge them).

**Constraints:**
- `1 <= beginWord.length <= 10`
- `endWord.length == beginWord.length`
- `1 <= wordList.length <= 5000`
- `wordList[i].length == beginWord.length`
- `beginWord`, `endWord`, and every word in `wordList` consist of lowercase English letters only.
- `beginWord != endWord`
- All the words in `wordList` are distinct.

---

### Step-by-Step Walkthrough

**Approach — Breadth-First Search over an implicit graph of one-letter-edit neighbors**

Think of every word (the dictionary words plus `beginWord`) as a node in a graph, with an edge between two words if they differ in exactly one letter position. "Shortest transformation sequence" is then exactly "shortest path from `beginWord` to `endWord`" in this unweighted graph — which is precisely what **BFS** is built for: BFS explores nodes in increasing order of distance from the source, so the first time it reaches `endWord`, that distance is guaranteed minimal.

1. **Build a fast membership check.** Put all of `wordList` into a hash set `dict`. If `endWord` is not in `dict`, we can return `0` immediately — it can never be part of a valid chain.
2. **BFS setup.** Use a queue holding `(word, distance)` pairs, seeded with `(beginWord, 1)` (distance `1` because the sequence length counts `beginWord` itself as the first word). Use a `visited` hash set (or just erase words from `dict` as we visit them) so we never re-process the same word twice — this is what keeps the algorithm from cycling or doing redundant work.
3. **Expand neighbors by trying every single-letter mutation.** For the current word, for each of its `L` character positions, try substituting every one of the 26 letters `a`-`z` (skipping the letter already there). If the resulting mutated word is in `dict` (i.e., it's a real, unvisited dictionary word):
   - If the mutated word equals `endWord`, we've found the shortest path — return `distance + 1`.
   - Otherwise, mark it visited (remove it from `dict` so it isn't enqueued again from a different branch), and push `(mutated_word, distance + 1)` onto the queue.
4. **Why generate-all-26-substitutions instead of comparing against every dictionary word directly?** Comparing the current word against all `N` dictionary words to find one-letter-diff neighbors costs `O(N * L)` per word. Generating all `26 * L` single-letter mutations and doing an `O(L)` hash-set lookup for each costs `O(26 * L)` per word — independent of `N`. Since `N` can be up to 5000 and `L` up to 10, `26*L` (260) is far cheaper than `N*L` (up to 50000), so mutation generation is the standard optimization for this exact problem shape.
5. If the queue empties without ever reaching `endWord`, no valid transformation sequence exists — return `0`.

**Why it works:** BFS visits nodes in strictly non-decreasing order of distance from the start. The moment we generate `endWord` as a neighbor of some word at distance `d`, we know no shorter path could exist — if one did, BFS would have already discovered and returned via that shorter path in an earlier layer, since every node is enqueued exactly once (the visited/erase step guarantees this) and layers are processed strictly in order.

**Complexity Analysis:**
- **Time complexity:** `O(N * L * 26)`, where `N` is the number of words in `wordList` and `L` is the word length — each of up to `N` words is dequeued once, and for each we try `L` positions × `26` letters, with an `O(L)` hash lookup/mutation cost folded in.
- **Space complexity:** `O(N * L)` for the dictionary hash set, the queue, and the strings generated during mutation.

### C++ Code

```cpp
#include <iostream>
#include <string>
#include <vector>
#include <queue>
#include <unordered_set>

using namespace std;

class Solution {
public:
    int ladderLength(string beginWord, string endWord, vector<string>& wordList) {
        // Put all dictionary words into a hash set for O(L) membership checks
        // and so we can erase words once visited (acts as our "visited" set).
        unordered_set<string> dict(wordList.begin(), wordList.end());

        // endWord must be reachable from the dictionary at all.
        if (dict.find(endWord) == dict.end()) {
            return 0;
        }

        queue<pair<string, int>> bfsQueue; // (word, distance-so-far including beginWord)
        bfsQueue.push({beginWord, 1});

        int wordLen = beginWord.size();

        while (!bfsQueue.empty()) {
            auto [currentWord, distance] = bfsQueue.front();
            bfsQueue.pop();

            // Try mutating every position to every other lowercase letter.
            for (int pos = 0; pos < wordLen; pos++) {
                string mutated = currentWord;
                char originalChar = mutated[pos];

                for (char c = 'a'; c <= 'z'; c++) {
                    if (c == originalChar) continue; // must actually change the letter
                    mutated[pos] = c;

                    if (mutated == endWord) {
                        return distance + 1; // found the shortest path
                    }

                    auto it = dict.find(mutated);
                    if (it != dict.end()) {
                        // Valid, unvisited dictionary word: enqueue and mark visited
                        // by erasing it so no other branch re-enqueues it.
                        dict.erase(it);
                        bfsQueue.push({mutated, distance + 1});
                    }
                }
                // restore not needed; mutated is a local copy re-created each pos iteration
            }
        }

        // Queue exhausted without reaching endWord.
        return 0;
    }
};

int main() {
    Solution sol;

    vector<string> words1 = {"hot", "dot", "dog", "lot", "log", "cog"};
    cout << sol.ladderLength("hit", "cog", words1) << "\n"; // expected 5

    vector<string> words2 = {"hot", "dot", "dog", "lot", "log"};
    cout << sol.ladderLength("hit", "cog", words2) << "\n"; // expected 0

    vector<string> words3 = {"hot", "dog"};
    cout << sol.ladderLength("hot", "dog", words3) << "\n"; // expected 0

    return 0;
}
```

### 1. Operating Systems (Conceptual)

What is a race condition, and what are the standard mechanisms an operating system (or a programmer) uses to prevent one? Explain using a concrete example involving shared memory between threads.

**Answer:**

A **race condition** occurs when two or more threads (or processes) access shared data concurrently, and the final outcome of the program depends on the unpredictable timing/interleaving of their execution. The bug is "invisible" in the source code — it only manifests depending on scheduling, which is why race conditions are notoriously hard to reproduce and debug.

**Concrete example:** Suppose two threads both execute `balance = balance + 100;` on a shared integer `balance` starting at `0`. This single line of C++ actually compiles down to at least three machine steps:
1. Load `balance` into a register.
2. Add `100` to the register.
3. Store the register back into `balance`.

If Thread A executes step 1 (loads `0`), then gets preempted before step 3, and Thread B runs all three steps (loads `0`, adds `100`, stores `100`), and then Thread A resumes and finishes its own step 2 and 3 (adds `100` to its stale register value of `0`, stores `100`) — the final value is `100`, even though we expected `200` from two increments of `100`. One update was silently lost. This is a classic **lost update** race condition, because the "load-modify-store" sequence is not atomic.

**Standard mechanisms to prevent race conditions:**

1. **Mutexes / Locks:** A mutual-exclusion lock ensures only one thread can execute a "critical section" (the code touching shared data) at a time. Other threads attempting to acquire the lock block until it's released. This is the most common general-purpose tool (e.g., `std::mutex` in C++, `pthread_mutex_t` in POSIX).
2. **Semaphores:** A more general synchronization primitive holding a count; useful not just for mutual exclusion (binary semaphore) but also for limiting concurrent access to a pool of `N` resources (counting semaphore), or for signaling between threads (e.g., producer-consumer).
3. **Atomic operations:** Hardware-supported instructions like `compare-and-swap (CAS)` or atomic increment let you perform a read-modify-write as a single indivisible step, avoiding the overhead of a full lock for simple operations (e.g., `std::atomic<int>` in C++).
4. **Monitors / Condition variables:** Higher-level constructs built on top of locks that let threads wait for a condition to become true (e.g., "queue is non-empty") without busy-waiting, releasing the lock while waiting and reacquiring it when signaled.
5. **Avoiding shared mutable state entirely:** The most robust fix at a design level — e.g., message-passing between threads/processes instead of shared memory, or giving each thread its own private copy of data and merging results afterward (common in map-reduce style parallelism).

**Why it matters:** Understanding race conditions is foundational to writing correct concurrent code — it's not enough for code to "usually work"; a correct concurrent program must be correct under *every* possible interleaving the scheduler could choose, which is why disciplined use of the above primitives (rather than "it passed my tests") is what actually guarantees correctness.

### 2. DBMS (Comparison)

Compare a **clustered index** and a **non-clustered index** in a relational database. What is the key structural difference, how many of each can a table have, and how does this affect read performance for range queries versus point lookups on a non-indexed column?

**Answer:**

**Structural difference:** A **clustered index** determines the *physical storage order* of the actual table rows — the table data itself is stored sorted by the clustered index key, essentially making the table itself the index's leaf level (in a B+ tree, the leaf nodes *are* the actual row data). A **non-clustered index**, by contrast, is a separate structure: its leaf nodes contain the indexed column's value plus a *pointer* (a row locator — either the physical row address, or, more commonly in modern engines, the clustered index key) back to the actual row, which lives elsewhere in its own storage order.

**Cardinality:** Because a clustered index dictates the physical row order, a table can have **at most one clustered index** (rows can only be sorted one way on disk at a time). A table can have **many non-clustered indexes** — one per column or column-combination that benefits from fast lookup, since each is just an auxiliary structure pointing back at the real rows.

**Performance implications:**

| Query type | Clustered index | Non-clustered index |
|---|---|---|
| Range query on the indexed key (e.g., `WHERE id BETWEEN 100 AND 200`) | Very fast — matching rows are physically contiguous on disk, so it's a single sequential scan of that range. | Slower — the index quickly finds the matching leaf entries, but each one requires a separate "bookmark lookup" back to the heap/clustered table to fetch the full row, which can mean many scattered disk reads. |
| Point lookup on a non-indexed column | Requires a full table scan (`O(n)`) since there's no structure to jump to the right row. | Same — without an index on that column, neither index type helps; you'd need a non-clustered index built specifically on that column to get `O(log n)` lookup. |
| Point lookup on the indexed key | `O(log n)` tree traversal directly to the row. | `O(log n)` traversal to find the pointer, plus one extra hop to fetch the actual row (unless it's a "covering index" that contains all needed columns, avoiding the extra hop). |

**Why it matters:** Choosing the clustered index key is one of the most consequential schema decisions in relational database design — it's typically placed on the primary key or another column with high range-query value (like a timestamp for time-series data), because range scans benefit enormously from physical contiguity, whereas a poorly chosen clustered key (e.g., a random UUID) causes expensive page splits and fragmentation on every insert. Non-clustered indexes are then added liberally on top for other frequently-filtered columns, at the cost of extra storage and slower writes (since every index must be updated on insert/update/delete).

### 3. System Design Basics (Scenario)

You are designing a URL shortener service (like `bit.ly`) that must handle very high read traffic (users clicking short links) compared to write traffic (users creating new short links). Describe the key components of a scalable architecture, and explain specifically how you would use caching to handle the read-heavy load.

**Answer:**

**Core requirements recap:** Given a long URL, generate a short unique code (e.g., `abc123`) and store the mapping `abc123 -> https://original-long-url.com`. When a user visits `short.ly/abc123`, look up the mapping and issue an HTTP redirect (`301`/`302`) to the original URL. Reads (redirects) vastly outnumber writes (new short links created), so the architecture should be optimized to serve reads as cheaply and fast as possible.

**Key components:**

1. **Application/API servers (stateless, horizontally scaled):** Handle two endpoints — `POST /shorten` (create a mapping) and `GET /{code}` (look up and redirect). Being stateless, these can be scaled out behind a load balancer as traffic grows.
2. **Unique code generation:** Options include (a) a counter-based approach (an auto-incrementing ID converted to base62, giving a short, collision-free code, requiring a centralized or sharded counter/ID-generation service like Twitter's Snowflake) or (b) hashing the long URL (e.g., MD5/SHA and taking the first few characters), handling collisions by appending characters or checking uniqueness before commit. Counter-based approaches are generally preferred for guaranteed uniqueness without collision-retry overhead.
3. **Primary datastore:** A key-value or relational store holding the `short_code -> long_url` mapping (plus metadata like creation time, expiry, click count). Given the access pattern is simple key lookups, a distributed key-value store (e.g., DynamoDB, Cassandra) or a sharded relational database works well; it can be sharded/partitioned by the short code's hash to scale writes and storage horizontally.
4. **Load balancer:** Distributes incoming requests (both shorten and redirect traffic) across the fleet of stateless application servers.

**Caching strategy for the read-heavy load:** Since redirects vastly dominate traffic, and popular short links follow a classic Zipfian/"hot key" distribution (a small fraction of links account for a large fraction of clicks), an **in-memory cache layer** (e.g., Redis or Memcached) sitting in front of the primary datastore is critical:

- On `GET /{code}`, the application server first checks the cache for `code -> long_url`. On a **cache hit** (the common case for popular links), it returns the redirect immediately without ever touching the primary database — this is what lets the system absorb massive read QPS with low latency.
- On a **cache miss**, it falls through to the primary datastore, fetches the mapping, redirects the user, and **populates the cache** with that mapping (a "cache-aside" / "lazy-loading" pattern) so subsequent requests for the same code are served from cache.
- Cache entries are given a **TTL (time-to-live)** or use an **LRU eviction policy**, since the cache is far smaller than the full dataset and only needs to hold the "hot" subset of frequently-accessed links at any time.
- For extremely hot individual keys (a link that goes viral), a single Redis node could still bottleneck; this is mitigated by **read replicas of the cache** or a **CDN edge cache** for the redirect responses themselves, pushing the hottest lookups even closer to the user and off the origin infrastructure entirely.

**Why it matters:** This read-through/cache-aside pattern is the standard, general-purpose way to shield a primary datastore from read-heavy traffic in any system with a skewed access distribution (not just URL shorteners) — it trades a small amount of staleness risk (mitigated with TTLs, or cache invalidation on updates) for a dramatic reduction in database load and read latency, and is a foundational building block referenced across almost all high-read-QPS system design interview questions.
