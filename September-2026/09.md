### Question: Longest Substring Without Repeating Characters (Strings — Medium)

Given a string `s`, find the length of the longest substring that contains no repeating characters.

**Input format:**
- A string `s` consisting of English letters, digits, symbols, and spaces.

**Output format:**
- An integer: the length of the longest substring of `s` with all unique characters.

**Worked Examples:**

1. `s = "abcabcbb"` → `3` (the answer is `"abc"`, with length 3).
2. `s = "bbbbb"` → `1` (the answer is `"b"`, with length 1).
3. `s = "pwwkew"` → `3` (the answer is `"wke"`, with length 3 — note that `"pwke"` is a subsequence, not a substring, so it doesn't count).

**Constraints:**
- `0 <= s.length <= 5 * 10^4`
- `s` consists of ASCII characters.

---

### Step-by-Step Walkthrough

**Approach — Sliding Window with a Hash Map of Last-Seen Indices**

The brute-force approach would check every substring for uniqueness, which costs `O(n^3)` (or `O(n^2)` with a smarter uniqueness check) — too slow for `n` up to `5 * 10^4`. Instead, we can maintain a **window** `[left, right]` that always contains only unique characters, and slide it across the string in a single pass.

1. Keep a hash map `lastIndex` that stores, for each character seen so far, the most recent index at which it appeared.
2. Keep two pointers, `left` and `right`, both starting at `0`, marking the current window of unique characters. Track `maxLen`, the best window length seen so far.
3. Move `right` across the string one character at a time:
   - If `s[right]` has been seen before **and** its last occurrence is inside the current window (i.e., `lastIndex[s[right]] >= left`), then the window must shrink: move `left` to `lastIndex[s[right]] + 1`, which drops everything up to and including the previous occurrence of this character out of the window. This is the key step — we don't need to shrink one character at a time; we can jump `left` directly.
   - Update `lastIndex[s[right]] = right`.
   - Update `maxLen = max(maxLen, right - left + 1)`.
4. After processing all characters, `maxLen` holds the answer.

**Why it works:** At every step, the window `[left, right]` is maintained as an invariant to contain no repeated characters. Whenever we're about to include a character that already exists in the current window, we shrink from the left just enough to evict the earlier copy of that character (and everything before it) — never more than necessary, and never less. Since `left` only ever moves forward (never backward) and `right` sweeps forward exactly once, each pointer traverses the string at most once.

**Complexity Analysis:**
- **Time complexity:** `O(n)` — each character is visited by `right` exactly once, and `left` only ever advances forward, so the total pointer movement across the whole run is bounded by `O(n)`.
- **Space complexity:** `O(min(n, k))` where `k` is the size of the character set (e.g., 128 for ASCII), since `lastIndex` stores at most one entry per distinct character.

---

### C++ Code

```cpp
#include <iostream>
#include <string>
#include <unordered_map>
using namespace std;

class Solution {
public:
    int lengthOfLongestSubstring(const string& s) {
        unordered_map<char, int> lastIndex; // char -> most recent index seen at
        int left = 0;
        int maxLen = 0;

        for (int right = 0; right < (int)s.size(); ++right) {
            char c = s[right];

            // If c was seen before AND that occurrence is inside the current
            // window, shrink the window to just past that previous occurrence.
            auto it = lastIndex.find(c);
            if (it != lastIndex.end() && it->second >= left) {
                left = it->second + 1;
            }

            lastIndex[c] = right; // record/update the latest position of c
            maxLen = max(maxLen, right - left + 1);
        }

        return maxLen;
    }
};

int main() {
    Solution sol;

    // Example 1: expect 3 ("abc")
    cout << "Input: \"abcabcbb\" -> " << sol.lengthOfLongestSubstring("abcabcbb")
         << " (expected 3)" << endl;

    // Example 2: expect 1 ("b")
    cout << "Input: \"bbbbb\" -> " << sol.lengthOfLongestSubstring("bbbbb")
         << " (expected 1)" << endl;

    // Example 3: expect 3 ("wke")
    cout << "Input: \"pwwkew\" -> " << sol.lengthOfLongestSubstring("pwwkew")
         << " (expected 3)" << endl;

    // Edge case: empty string -> 0
    cout << "Input: \"\" -> " << sol.lengthOfLongestSubstring("")
         << " (expected 0)" << endl;

    return 0;
}
```

**Trace against the examples:**
- `"abcabcbb"`: window grows to `"abc"` (length 3) at `right=2`. At `right=3` (`'a'`), `lastIndex['a']=0 >= left(0)`, so `left` jumps to `1`; window becomes `"bca"` (length 3). The pattern repeats, and `maxLen` never exceeds `3`. ✓
- `"bbbbb"`: at every step past the first `'b'`, `lastIndex['b'] >= left`, so `left` jumps right alongside `right`, keeping the window at length `1` throughout. ✓
- `"pwwkew"`: window grows to `"pw"` (length 2), then hits the second `'w'` at `right=2`, so `left` jumps to `2`; window becomes `"w"`. It then grows to `"wke"` (length 3) before hitting `'w'` again at `right=5`, at which point `lastIndex['w']=2 < left(3)`, so `left` does **not** jump this time (that `'w'` is outside the current window) — window becomes `"kew"`, still length 3. Final `maxLen = 3`. ✓

### 1. Operating Systems (Conceptual/Definition)

What is a context switch? Describe what state the operating system must save and restore when switching from one process (or thread) to another, and explain why context switches have measurable performance overhead even though no "useful" work happens during one.

**Answer:**

A **context switch** is the act of the CPU suspending execution of one process or thread, saving enough information about its state to resume it later, and loading the saved state of a different process or thread so it can run instead. This is the mechanism that makes multitasking possible on a machine with far fewer CPU cores than runnable processes — the OS scheduler rapidly switches between them, giving the illusion of parallelism (or providing real parallelism across cores, with switching still happening on each core individually).

**What gets saved and restored (the "context"):**
- **CPU registers** — the program counter (instruction pointer), stack pointer, general-purpose registers, and flags/status register, all captured into that process's Process Control Block (PCB) (or Thread Control Block for a thread switch).
- **Memory management state** — for a full process switch, the memory-mapping information (e.g., the page table base register / CR3 on x86) must be swapped so the CPU now translates virtual addresses using the incoming process's address space.
- **Scheduling state** — process/thread state (ready, running, waiting), priority, and scheduling metadata the OS scheduler needs to decide what runs next.
- **Kernel-mode stack pointer and other kernel bookkeeping** the OS needs to resume the process exactly where it left off, including in the middle of a system call.

**Why it has overhead, even though it does no "useful" work:**
1. **Direct CPU cost** — the instructions to save/restore registers and update the PCB take real CPU cycles that produce no application progress.
2. **Cache and TLB pollution** — the outgoing process's working set was warm in the CPU cache and Translation Lookaside Buffer (TLB); after the switch, the incoming process's memory accesses mostly miss the cache/TLB until its own working set warms back up, incurring extra memory-latency stalls that don't show up as "context switch time" directly but are a real consequence of it.
3. **Pipeline disruption** — modern CPUs speculatively execute and pipeline instructions; a switch flushes this speculative state, costing additional cycles to refill the pipeline for the new process.
4. **Mode switch overhead** — a context switch is normally triggered via a trap into kernel mode (timer interrupt, system call, or I/O interrupt), which itself has a fixed cost independent of the actual state-swap work.

**Why this matters:** Context switch overhead is a first-order concern in OS and systems design — it's the reason threads are cheaper than processes (threads share an address space, so no page table swap is needed, only register/stack state), why servers under high concurrency can suffer from "thrashing" between too many runnable threads, and why techniques like thread pooling, batching, and cooperative/async scheduling (e.g., event loops, coroutines) exist specifically to reduce how often the OS has to pay this cost.

### 2. OOP (Comparison)

Compare an **interface** and an **abstract class** in object-oriented programming. When would you choose one over the other, and how does C++ approximate the "interface" concept even though it has no dedicated `interface` keyword?

**Answer:**

| Aspect | Interface | Abstract Class |
|---|---|---|
| Purpose | Defines a **contract** — a set of method signatures a class promises to implement, with no shared implementation. | Defines a **partial implementation** to be extended — a common base with some concrete (already-implemented) methods and some methods left abstract for subclasses to fill in. |
| Method bodies | Traditionally none (pure contract), though modern languages (e.g., Java 8+ default methods) allow some. | Can freely mix implemented and unimplemented (pure virtual) methods. |
| State (fields) | Cannot hold instance state (no member variables representing object data). | Can hold instance state/fields, shared and inherited by all subclasses. |
| Inheritance model | A class can typically implement **multiple** interfaces. | A class can typically extend only **one** abstract class (single inheritance in most languages). |
| Relationship expressed | "Can-do" relationship — e.g., a class *can be* `Comparable`, *can be* `Serializable`. | "Is-a" relationship — e.g., a `Circle` *is a* `Shape`. |
| C++ equivalent | A class with **only pure virtual functions** (`virtual void f() = 0;`) and no data members — a convention, not a distinct keyword. | A class with **at least one** pure virtual function, but which may also have data members and implemented methods. |

**When to choose which:**
- Use an **interface** when you want to guarantee unrelated classes can all respond to the same set of operations, without forcing a shared class hierarchy or shared state — e.g., both a `File` and a `NetworkSocket` class might implement a `Closeable` interface even though they share nothing else in common.
- Use an **abstract class** when subclasses genuinely share common state and behavior, and you want to avoid duplicating that shared implementation — e.g., an abstract `Employee` class holding a `name` and `salary` field plus a concrete `printPaySlip()` method, while leaving `calculateBonus()` abstract for each employee subtype to define differently.

**C++ specifically:** C++ has no `interface` keyword. The idiomatic way to express an interface is a class containing *only* pure virtual functions (`= 0`) and no data members, e.g.:

```cpp
class Drawable {
public:
    virtual void draw() const = 0;
    virtual ~Drawable() = default; // virtual destructor is essential for polymorphic cleanup
};
```

Any class that inherits from `Drawable` and implements `draw()` satisfies the "interface," and because C++ supports multiple inheritance, a class can inherit from several such pure-virtual "interfaces" at once — something languages with single class inheritance (like Java, before it added a separate `interface` keyword) cannot do directly.

**Why this matters:** This distinction is a staple of both interview questions and real API design — choosing interface vs. abstract class incorrectly leads either to rigid hierarchies that force unrelated classes into an artificial "is-a" relationship, or to duplicated boilerplate because a true shared-implementation opportunity was expressed as a contract-only interface instead.

### 3. System Design Basics (Scenario/Applied)

You're asked to design the backend for a **notification delivery system** that sends emails and push notifications to users (e.g., "your order has shipped," "someone commented on your post"). It must handle spikes of millions of notifications triggered by a single event (e.g., a flash sale announcement), must not send duplicate notifications for the same event, and should not let a slow downstream provider (e.g., a flaky email API) block the rest of the system. Walk through your high-level design.

**Answer:**

**Step 1 — Decouple notification producers from senders with a queue.** Instead of having application services (order service, comment service, etc.) call the email/push provider directly and synchronously, have them publish a "notification request" message (containing user ID, notification type, template ID, and payload data) onto a **message queue** (e.g., Kafka, RabbitMQ, or SQS). This decoupling means the service that *triggers* a notification (e.g., order service) doesn't block on, or fail because of, a slow or down notification pipeline — it just enqueues and moves on.

**Step 2 — Use worker pools to consume and fan out.** A pool of **notification worker** processes consumes from the queue. For each message, a worker:
1. Looks up the user's notification preferences/channels (email, push, SMS) and their device tokens/email address from a user-profile store.
2. Renders the message using the appropriate template.
3. Calls the relevant downstream provider (e.g., SendGrid for email, FCM/APNs for push).

Workers scale horizontally — during a spike (e.g., a flash sale notifying millions of users), simply add more worker instances consuming from the same queue partitions to increase throughput, since the queue absorbs the burst and lets workers drain it at a sustainable rate rather than requiring the whole system to handle the spike instantaneously.

**Step 3 — Isolate slow/flaky downstream providers.** Wrap each provider call in a **timeout** and a **circuit breaker**: if the email provider starts timing out or erroring above a threshold, the circuit breaker "opens" and short-circuits further calls to it for a cooldown period (routing those messages to a retry queue instead), so a struggling provider doesn't exhaust worker threads or delay push notifications that are unaffected. Each channel (email vs. push) should have its own dedicated worker pool/queue partition so one channel's slowness never starves another.

**Step 4 — Prevent duplicate sends (idempotency).** Give every notification request a unique **idempotency key** (e.g., a hash of `event ID + user ID + notification type`, or a UUID generated once at the producer). Before actually dispatching, a worker checks a fast idempotency store (e.g., Redis, with a TTL of a few hours/days) for that key:
- If present → the notification was already sent (or is currently being processed) — skip it.
- If absent → atomically set the key (e.g., Redis `SETNX`) and proceed to send.

This is critical because message queues typically offer **at-least-once delivery** — a worker crash after sending but before acknowledging the queue message would otherwise cause the same message to be redelivered and re-sent.

**Step 5 — Handle failures with retry + dead-letter queue.** Failed sends (transient provider errors) go back onto the queue with **exponential backoff** for a bounded number of retries. After exhausting retries, the message moves to a **dead-letter queue (DLQ)** for manual inspection or alerting, rather than being silently dropped or retried forever.

**Step 6 — Rate-limit per provider, not just per user.** Downstream providers (SendGrid, FCM) often have their own rate limits; the worker pool must throttle its outbound call rate to stay under those limits (e.g., a token bucket per provider), independent of how fast the internal queue is being drained.

**Why this matters:** This design touches the recurring building blocks of reliable distributed systems — using a queue to absorb bursty load and decouple producers from consumers, horizontal scaling of stateless workers, idempotency to survive at-least-once delivery semantics, and circuit breakers/bulkheads to contain the blast radius of one failing dependency instead of letting it cascade into a full outage.
