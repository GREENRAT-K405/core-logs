### Question: Palindrome Partitioning II (Dynamic Programming — Hard)

**Problem Statement**

Given a string `s`, partition it into one or more substrings such that every substring is a palindrome. Return the **minimum number of cuts** needed to achieve such a partition.

**Input/Output Format**

- Input: a string `s` of lowercase letters.
- Output: a single integer — the minimum number of cuts.

**Examples**

1. Input: `s = "aab"` → Output: `1`. Cut it as `"aa" | "b"` — both pieces are palindromes, and this is achieved with just one cut.
2. Input: `s = "a"` → Output: `0`. The whole string is already a single palindrome, so no cuts are needed.
3. Input: `s = "racecar"` → Output: `0`. The entire string is itself a palindrome.
4. Input: `s = "abcd"` → Output: `3`. No two adjacent characters match, so every character must be its own palindrome piece: `"a" | "b" | "c" | "d"`.

**Constraints**

- `1 <= s.length <= 2000`
- `s` consists only of lowercase English letters.

### Step-by-Step Walkthrough

**Why brute force fails.** There are exponentially many ways to place cuts in a string of length `n` (each of the `n-1` gaps between characters can be cut or not), so trying every partition and checking whether every piece is a palindrome is O(2^n) — hopeless beyond tiny strings. We need to avoid re-deciding the same subproblem over and over.

**Breaking the problem into two subproblems.** The overall task bundles two different kinds of work:

1. "Is `s[i..j]` a palindrome?" — asked repeatedly, for overlapping ranges, as part of every candidate partition.
2. "What is the minimum number of cuts for a prefix of `s`?" — this is the actual quantity we want, and it only needs answer (1) as a fast lookup.

Solving each as its own DP, in that order, turns an exponential search into two polynomial passes.

**DP #1 — precompute palindrome substrings.** Define `isPal[i][j] = true` iff `s[i..j]` (inclusive) is a palindrome. The recurrence builds on smaller ranges:
- Base case: every single character `isPal[i][i] = true`.
- `isPal[i][j] = (s[i] == s[j])` **and** (the range has length 2, **or** `isPal[i+1][j-1]` is true).

Filling this table by increasing substring length guarantees `isPal[i+1][j-1]` is already known when we need it. This costs O(n^2) time and O(n^2) space, and turns "is this range a palindrome?" into an O(1) lookup for the next DP.

**DP #2 — minimum cuts for each prefix.** Define `dp[i]` = minimum cuts needed to partition the prefix `s[0..i-1]` (length `i`) into palindromes. We want `dp[n]`.
- `dp[0] = -1`. This is a deliberate trick, not a real answer: if the *entire* prefix `s[0..i-1]` turns out to be one palindrome, we want that to cost `0` cuts, and the recurrence below computes it as `dp[0] + 1`. Seeding `dp[0] = -1` makes that arithmetic come out right instead of needing a special case.
- For each `i` from `1` to `n`, try every possible *last piece* `s[j..i-1]` (for `j` from `0` to `i-1`): if that piece is a palindrome (an O(1) lookup in `isPal`), then one valid way to build `dp[i]` is "however many cuts `s[0..j-1]` needed, plus one more cut to separate off this last piece": `dp[i] = min(dp[i], dp[j] + 1)`.

**Why it's correct.** `dp[i]` is built from strictly smaller prefixes (`j < i`), so by the time we compute `dp[i]`, every `dp[j]` it depends on is already final and optimal — this is the standard DP inductive argument. Trying *every* valid last palindrome piece ending at position `i-1` guarantees we don't miss the globally optimal split; we just keep the cheapest one.

**Complexity.**
- Time: O(n^2) to fill `isPal` (one O(1) decision per cell) plus O(n^2) for the `dp` double loop (for each `i`, scan all `j < i`) — O(n^2) overall.
- Space: O(n^2) for the `isPal` table, O(n) for `dp`.

### C++ Code

```cpp
#include <vector>
#include <string>
#include <algorithm>
#include <climits>
using namespace std;

int minCut(string s) {
    int n = (int)s.size();
    if (n <= 1) return 0;

    // isPal[i][j]: true if s[i..j] (inclusive) is a palindrome.
    vector<vector<bool>> isPal(n, vector<bool>(n, false));
    for (int i = 0; i < n; i++) isPal[i][i] = true;

    // Fill by increasing length so isPal[i+1][j-1] is already known.
    for (int len = 2; len <= n; len++) {
        for (int i = 0; i + len - 1 < n; i++) {
            int j = i + len - 1;
            if (s[i] == s[j] && (len == 2 || isPal[i + 1][j - 1])) {
                isPal[i][j] = true;
            }
        }
    }

    // dp[i] = minimum cuts to partition s[0..i-1] into palindromes.
    // dp[0] = -1 so a prefix that is one whole palindrome costs dp[0] + 1 = 0.
    vector<int> dp(n + 1, INT_MAX);
    dp[0] = -1;
    for (int i = 1; i <= n; i++) {
        for (int j = 0; j < i; j++) {
            // s[j..i-1] is the candidate last palindrome piece.
            if (isPal[j][i - 1] && dp[j] != INT_MAX) {
                dp[i] = min(dp[i], dp[j] + 1);
            }
        }
    }

    return dp[n];
}
```

## CS Fundamentals

### 1. DBMS (Conceptual/Definition)

What is database normalization? Walk through 1NF, 2NF, and 3NF, and give a concrete example of the anomaly each one fixes.

**Answer:**

Normalization is the process of structuring tables to eliminate redundant data, so that every fact is stored in exactly one place. Each normal form fixes a specific kind of redundancy left over by the previous one, and each anomaly it prevents falls into one of three buckets: **insertion**, **update**, or **deletion** anomalies.

**1NF (First Normal Form):** every column holds a single, atomic value — no repeating groups or comma-separated lists in one cell, and every row is uniquely identifiable (typically via a primary key).
*Violation example:* a `Students` table with a column `Courses = "Math, Physics, Chemistry"`. You can't efficiently query "which students take Physics?" without parsing strings, and adding a fourth course means editing that one cell's text rather than adding a row.
*Fix:* split into a separate `StudentCourses` table with one row per `(student_id, course)` pair.

**2NF (Second Normal Form):** must already be in 1NF, **and** every non-key column must depend on the *whole* primary key, not just part of it. This only matters when the primary key is composite (more than one column).
*Violation example:* an `OrderItems` table keyed on `(order_id, product_id)`, with a column `product_name`. `product_name` depends only on `product_id`, not on the full composite key — so the same product's name is duplicated across every order that contains it. Update the product's name, and you must update it in every single order row, or the data goes inconsistent (an **update anomaly**).
*Fix:* move `product_name` into a separate `Products` table keyed on `product_id` alone; `OrderItems` keeps only `(order_id, product_id, quantity)`.

**3NF (Third Normal Form):** must already be in 2NF, **and** no non-key column may depend on another *non-key* column (no "transitive dependencies").
*Violation example:* an `Employees` table with `(employee_id, department_id, department_name)`. `department_name` depends on `department_id`, not directly on `employee_id` — it's a fact about the department, riding along on the employee row. Delete the last employee in a department, and the fact "department 7 is called Marketing" vanishes with them (a **deletion anomaly**); insert a new department with no employees yet, and you can't record its name at all (an **insertion anomaly**) without a dummy employee row.
*Fix:* move `department_name` into a separate `Departments` table keyed on `department_id`; `Employees` keeps only a `department_id` foreign key.

**Why it matters in practice:** normalization isn't free — splitting data across tables means queries need more `JOIN`s, which costs read performance. That's exactly why real systems sometimes **denormalize** deliberately (duplicating a column back in for read-heavy paths, e.g., caching `department_name` on an `Employees` row in a reporting table): it's a conscious trade of write-side consistency guarantees for read-side speed, made *after* understanding what normalization was protecting in the first place — not a shortcut taken out of not knowing the rules.

### 2. Computer Networks (Scenario/Applied)

You're building a product with two features: live video calls, and a "share a file" transfer tool. Which transport protocol, TCP or UDP, would you pick for each, and why? Concretely, what would go wrong if you used TCP for the video stream?

**Answer:**

**File transfer → TCP.** A file must arrive byte-for-byte correct and complete — losing or reordering even one chunk silently corrupts the output. TCP is built exactly for this: it guarantees **reliable, in-order, complete delivery** via acknowledgments and automatic retransmission of lost segments, plus **congestion control** so the transfer backs off gracefully when the network is busy instead of making things worse. The cost (retransmission delay, connection setup overhead) is irrelevant here — nobody cares if a file transfer takes an extra 200ms, they care that the file isn't silently truncated or scrambled.

**Live video call → UDP.** Here the priority inverts: **low latency matters more than perfect delivery.** A video call is a stream of frames that must be displayed close to the moment they were captured; a frame that arrives late is often *worse than useless* — by the time it arrives, the call has moved on, and displaying it would make the conversation feel laggy and out of sync. UDP sends packets with no acknowledgment, no retransmission, and no enforced ordering, so a dropped frame is simply dropped — the next one that arrives on time gets displayed, maybe with a brief visual glitch. That's the right trade: losing one frame out of thirty per second is barely noticeable; waiting for it to be retransmitted is not.

**Concretely, what breaks if you force TCP onto the video stream:** TCP's core guarantee — strict in-order delivery — becomes a liability. If a single packet is lost, TCP will **not** deliver any later packet to the application until the lost one is retransmitted and received, even though those later packets already physically arrived. This is called **head-of-line blocking**. Every subsequent frame, already sitting in the OS buffer, is held hostage waiting for one retransmission round trip. On a call with even modest packet loss (a few percent, common on real-world Wi-Fi/cellular links), this produces exactly the stutter-then-freeze-then-catch-up pattern anyone has seen on a bad video call — the receiver falls further and further behind the live moment, and TCP has no mechanism to say "skip it, just give me what's newest." UDP-based protocols (e.g., WebRTC's media transport) instead let the application decide per-frame: drop it, or decode what partial data arrived and move on.

The general lesson: **TCP optimizes for correctness of the stream as a whole; UDP optimizes for timeliness of each unit.** Pick based on which failure mode — corruption or staleness — actually hurts your use case.

### 3. Computer Architecture (Comparison)

Compare RISC and CISC instruction set architectures. What does each one optimize for, and why did RISC become the dominant design in mobile and embedded CPUs (e.g., ARM) rather than CISC?

**Answer:**

RISC (**Reduced** Instruction Set Computer) and CISC (**Complex** Instruction Set Computer) represent two opposite answers to the same question: should the CPU's instruction set do more work per instruction, or should it do less, more predictably?

**CISC** (e.g., x86) provides a large number of specialized instructions, some of which can do a lot in a single instruction — a single `x86` instruction can, for example, read from memory, perform an arithmetic operation, and write the result back to memory, all as one instruction. The goal was originally to **minimize the number of instructions per program**, which mattered when memory was small and expensive, and to let the hardware absorb complexity that would otherwise need many simpler instructions chained together by the compiler.

**RISC** (e.g., ARM, MIPS, RISC-V) deliberately keeps the instruction set small and uniform: instructions are fixed-length, each does one simple thing (e.g., `ADD`, `LOAD`, `STORE` are separate instructions — arithmetic never touches memory directly), and most instructions execute in a single clock cycle. The goal is **simplicity and speed of execution per instruction**, accepting that a given program needs *more* instructions in exchange for each one being trivially fast and easy to pipeline.

| | CISC | RISC |
|---|---|---|
| Instructions per program | Fewer | More |
| Instruction complexity | High, variable-length, variable-cycle | Low, fixed-length, (near) single-cycle |
| Decoder complexity | High (hardware must handle many complex forms) | Low |
| Pipelining | Harder (variable instruction length/timing stalls the pipeline) | Easy (uniform instructions are predictable to schedule) |
| Power efficiency | Lower (complex decode logic burns power even when idle) | Higher |
| Typical use | Desktop/server x86 | Mobile, embedded, ARM-based laptops |

**Why RISC won mobile and embedded:** the deciding factor is **power and silicon efficiency, not raw performance**. A CISC decoder has to be able to recognize and execute a huge, variable-length, variable-timing instruction set, and that decode logic consumes die area and power *on every single instruction*, whether or not the program needs the complex forms. A phone or embedded device is battery-constrained first and performance-constrained second, so RISC's simple, uniform, easily-pipelined instructions translate directly into a smaller, cooler, more power-efficient chip — exactly the trade mobile hardware needs. Modern high-end x86 CPUs actually blur the line internally (they decode CISC instructions into simpler RISC-like **micro-ops** before execution), which is itself evidence of the same conclusion: simple, uniform instructions are what the execution hardware actually wants to run, whatever instruction set the compiler emits.
