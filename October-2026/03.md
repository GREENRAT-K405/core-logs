### Question: Distinct Subsequences (Dynamic Programming — Hard)

**Problem Statement**

Given two strings `s` and `t`, return the number of distinct subsequences of `s` which equal `t`.

A subsequence is formed by deleting zero or more characters from `s` without changing the relative order of the remaining characters. Two subsequences are counted separately if they are formed by deleting *different positions* in `s`, even if the resulting characters happen to be identical.

**Input/Output Format**

- Input: two strings `s` (the source) and `t` (the target).
- Output: a single integer — the count of distinct ways to pick index positions out of `s` so that the characters at those positions, read in order, spell `t`.

**Examples**

1. `s = "rabbbit"`, `t = "rabbit"` → Output: `3`. The three ways correspond to choosing which one of the three `b`'s at positions 2, 3, 4 to *skip*: `ra**b**_bbit` is shorthand for picking subsequences `rabb(b)it`, `rab(b)bit`, `ra(b)bbit` — concretely, index sets `{0,1,2,3,5,6}`, `{0,1,2,4,5,6}`, `{0,1,3,4,5,6}` of `s` all spell `"rabbit"`.
2. `s = "babgbag"`, `t = "bag"` → Output: `5`. There are five distinct index triples `(i, j, k)` with `i < j < k`, `s[i]='b'`, `s[j]='a'`, `s[k]='g'`.
3. `s = "xyz"`, `t = "xyzz"` → Output: `0`. `t` is longer than `s`, so no subsequence of `s` can equal it.

**Constraints**

- `1 <= s.length <= 1000`
- `1 <= t.length <= 1000`
- `s` and `t` consist only of lowercase English letters.
- The answer is guaranteed to fit in a 32-bit signed integer for the given constraints, but intermediate reasoning should treat counts as potentially large.

### Step-by-Step Walkthrough

**Why brute force fails.** The naive idea — enumerate every subset of positions in `s` and check whether it spells `t` — is `2^|s|`, hopeless even for `|s| = 1000`. We need to avoid re-examining the same (prefix of `s`, prefix of `t`) pair more than once, which is the signature of an overlapping-subproblems DP.

**Defining the state.** Let `dp[i][j]` = the number of distinct subsequences of `s[0..i)` (the first `i` characters of `s`) that equal `t[0..j)` (the first `j` characters of `t`). The final answer is `dp[m][n]` where `m = s.length()`, `n = t.length()`.

**Base cases.**
- `dp[i][0] = 1` for every `i` (including `i = 0`): there is exactly one way to form the empty string from any prefix of `s` — delete everything. This is the base case that makes the whole recurrence work.
- `dp[0][j] = 0` for `j > 0`: an empty prefix of `s` can never produce a non-empty target.

**The recurrence.** To build `dp[i][j]`, think about what role the last character of the `s`-prefix, `s[i-1]`, plays. We're deciding how to match `t[0..j)` using `s[0..i)`:

- **Option A — never use `s[i-1]`.** Every way of forming `t[0..j)` from `s[0..i-1)` alone still works; that contributes `dp[i-1][j]` ways. This option is always valid, regardless of whether `s[i-1]` matches anything in `t`.
- **Option B — use `s[i-1]` as the match for `t[j-1]`.** This is only valid when `s[i-1] == t[j-1]`. If so, the remaining task is forming `t[0..j-1)` from `s[0..i-1)`, which contributes `dp[i-1][j-1]` ways.

Since these two options pick disjoint sets of subsequences (one explicitly skips `s[i-1]`, the other explicitly consumes it as the final matched character), they don't double-count, so we simply add them:

```
dp[i][j] = dp[i-1][j]                          if s[i-1] != t[j-1]
dp[i][j] = dp[i-1][j] + dp[i-1][j-1]            if s[i-1] == t[j-1]
```

**Why this correctly counts distinct subsequences, not distinct strings.** `dp[i-1][j-1]` and `dp[i-1][j]` count index-position choices, not string values — every unit added to the sum corresponds to a genuinely different set of positions picked from `s`, which is exactly what the problem asks us to count (example 1 above relies on this: three different "which b do I skip" choices, same resulting string).

**Tracing example 2 briefly.** For `s = "babgbag"`, `t = "bag"`, the DP fills a `(7+1) x (3+1)` table; row 0 is `[1,0,0,0]`, and each subsequent row only grows the match count at columns where that row's character equals the corresponding `t` character, carrying forward `dp[i-1][j]` everywhere else. Working through it (or trusting the recurrence) lands on `dp[7][3] = 5`, matching the expected output.

**Complexity.**
- Time: `O(m * n)` — one pass filling an `(m+1) x (n+1)` table.
- Space: `O(m * n)` for the straightforward 2D table, reducible to `O(n)` since row `i` only ever depends on row `i-1`: keep a single 1D array of size `n+1` and update it **right to left** within each outer iteration (so that `dp[j-1]` read during the update of `dp[j]` still refers to the *previous* row's value, not the current row's value that would otherwise have already overwritten it).

### C++ Code

```cpp
#include <string>
#include <vector>
using namespace std;

int numDistinct(string s, string t) {
    int m = s.size(), n = t.size();

    // dp[j] represents dp[i][j] for the row currently being computed,
    // reusing the previous row's values until they're overwritten.
    // Using long long as a safety margin against overflow for large inputs,
    // even though the problem guarantees the final answer fits in 32 bits.
    vector<long long> dp(n + 1, 0);
    dp[0] = 1; // empty target: exactly one way (delete everything), for every prefix of s

    for (int i = 1; i <= m; ++i) {
        // Walk j from n down to 1 so that dp[j - 1] on the right-hand side
        // still holds last row's (i.e. dp[i-1][...]) value when it's read,
        // not this row's value that a left-to-right pass would have already written.
        for (int j = n; j >= 1; --j) {
            if (s[i - 1] == t[j - 1]) {
                dp[j] = dp[j] + dp[j - 1];
            }
            // else: dp[j] (i.e. dp[i-1][j]) is already correct and needs no change,
            // since dp[i][j] = dp[i-1][j] when characters don't match.
        }
    }

    return static_cast<int>(dp[n]);
}
```

### 1. Operating Systems (Comparison)

Compare three CPU scheduling algorithms: First-Come-First-Served (FCFS), Shortest Job First (SJF), and Round Robin. For each, describe how it picks the next process to run, and explain what starvation is, which of these algorithms is most prone to it, and how "aging" fixes it.

**Answer:**

All three are policies for answering the same question — "given a ready queue of waiting processes, which one gets the CPU next?" — and each optimizes for a different goal at the cost of a different weakness.

**First-Come-First-Served (FCFS).** The simplest policy: processes run strictly in arrival order, non-preemptively (once a process starts, it runs to completion or until it blocks on I/O). Implementation is trivial — a plain FIFO queue. The problem is the **convoy effect**: if a long CPU-bound process arrives first, every short process behind it must wait for the entire long burst to finish, even though servicing the short ones first would have let far more processes complete quickly. Average waiting time can be very poor despite the policy being "fair" in the naive sense of first-arrived-first-served.

**Shortest Job First (SJF).** Always picks the ready process with the smallest remaining CPU burst time next (can be non-preemptive, running the chosen job to completion, or preemptive — "Shortest Remaining Time First" — which re-evaluates whenever a new process arrives). SJF is *provably optimal* for minimizing average waiting time among all scheduling policies, given accurate burst-time estimates. Its weakness is twofold: (1) burst times generally aren't known in advance and must be estimated (e.g., via exponential averaging of past bursts), and (2) it is the algorithm **most prone to starvation** — a long job can be repeatedly skipped over by a continuous stream of newly arriving short jobs, in principle waiting indefinitely even though it was ready the whole time.

**Round Robin (RR).** Each process gets a fixed time slice (a "quantum"); if it hasn't finished when the quantum expires, it's preempted and moved to the back of the ready queue, and the next process in line runs. This guarantees every ready process gets CPU time within a bounded number of quanta — no process can be skipped forever — making RR a natural fit for time-sharing/interactive systems where responsiveness matters more than minimizing average completion time. Its own tradeoff is quantum-size sensitivity: too large a quantum degenerates toward FCFS (and its convoy effect); too small a quantum means context-switch overhead starts to dominate actual useful work.

**Starvation and aging.** Starvation is when a ready, runnable process is denied the CPU indefinitely because the scheduling policy always finds something else (by its own criteria) more deserving to run first — SJF's pure "always prefer shortest" rule is the classic example, since an unlucky long job can be perpetually outranked by a steady supply of shorter newcomers. **Aging** fixes this directly: the scheduler gradually increases the effective priority of a process the longer it has waited (e.g., SJF's "remaining time" comparison is adjusted downward the longer a job has sat in the queue), so that no matter how it keeps losing comparisons against fresher arrivals, its boosted priority eventually guarantees it wins and gets scheduled. This preserves most of SJF's efficiency benefit while putting a practical ceiling on worst-case wait time.

| | FCFS | SJF | Round Robin |
| --- | --- | --- | --- |
| Selection rule | Arrival order | Smallest remaining burst | Fixed time slice, cyclic |
| Preemptive? | No | Optionally (SRTF) | Yes, always |
| Optimizes for | Simplicity/fairness-by-arrival | Average waiting time (optimal) | Response time / fairness over time |
| Starvation risk | Low (every job eventually reached) | High, without aging | None — bounded wait by design |
| Typical use | Batch systems, simple queues | Batch systems with known/estimated burst times | Interactive/time-sharing systems |

### 2. Computer Networks (Scenario/Applied)

You and a friend are both behind the same home router, which gives your laptops private IP addresses like `192.168.1.5` and `192.168.1.8` while the router itself has a single public IP address on the internet. You want to run a small game server on your laptop so your friend — who is traveling, on a different network entirely — can connect to it directly from outside. Explain what Network Address Translation (NAT) is doing in this setup, why it makes your friend's direct connection attempt fail by default, and describe one concrete way to fix it.

**Answer:**

**What NAT does.** Your home router performs NAT because IPv4's ~4.3 billion addresses were never enough for every device on every home and business network to have its own globally unique public address. Instead, your router is assigned one public IP by your ISP, and every device behind it (your laptop, your friend's-visit-equivalent devices, phones, smart TVs) gets a private address from a reserved private range (like `192.168.x.x`). When your laptop sends a packet to the internet, the router rewrites the packet's source address/port from your private `192.168.1.5:54321` to the router's own public `IP:port`, and keeps an internal translation table entry mapping that public port back to your laptop's private address and port. When the reply comes back addressed to that public port, the router consults the table and forwards it to the correct internal device. This is why dozens of devices on your home network can all reach the internet simultaneously through one public IP — NAT multiplexes them by port.

**Why this breaks your friend's direct connection.** NAT's translation table is normally only populated **outbound** — it's built reactively, the moment a packet leaves your network, so the router knows where to route the reply. Your friend's connection attempt is an *unsolicited inbound* packet arriving at your router's public IP on some port, with no prior outbound packet from your laptop to have created a matching table entry. The router has no idea which internal device (if any) that packet is meant for, so by default it simply drops it. This is also a deliberate security benefit of NAT — it incidentally acts like a basic firewall, since random internet hosts can't reach devices behind it uninvited — but it's exactly what stands between your friend and your game server.

**Fixing it: port forwarding.** You configure a static rule on the router itself: "any inbound packet arriving on public port `25565` should always be forwarded to `192.168.1.5:25565`" (your laptop's private address and the game server's listening port). This permanently seeds the translation table with that one mapping instead of waiting for an outbound packet to create it, so your friend's connection to `your_public_ip:25565` now has somewhere to go. (The other common real-world fix — used by things like video calls and peer-to-peer apps where you can't ask every user to configure their router — is **STUN/hole punching**: both sides send an outbound packet first, each creating a temporary NAT mapping, and a third-party server helps them discover each other's public-facing address/port so their already-open mappings line up without either router needing manual configuration.)

**Why this matters:** NAT is the reason "it works on my machine's local server but nobody else can connect" is one of the most common early networking surprises, and understanding it (rather than just port-forwarding by rote) is what lets you reason correctly about VPNs, cloud load balancers, and why peer-to-peer apps need relay/signaling servers at all.

### 3. System Design Basics (Conceptual/Definition)

What is the CAP theorem? Define its three properties, explain why a distributed system cannot have all three simultaneously during a network partition, and give one real example of a system that chooses each side of the trade-off.

**Answer:**

**The theorem.** In any distributed data store, when a **network partition** occurs (some nodes can't communicate with others, due to a dropped link, a crashed switch, or a slow/unreliable network), the system can provide at most two of the following three properties — it cannot give all three at once:

- **Consistency (C):** every read receives the most recent write, or an error — all nodes see the same data at the same time, as if there were only one copy.
- **Availability (A):** every request to a non-failing node receives a (non-error) response, even if it isn't the most recent write.
- **Partition tolerance (P):** the system continues to operate correctly despite network partitions splitting it into disconnected groups of nodes.

**Why you can't have all three.** Partition tolerance isn't really optional in practice — real networks *do* partition (a cable gets cut, a data center loses connectivity, a packet gets dropped) — so the real-world choice is between C and A **once a partition has actually happened**. Suppose the system is split into two groups of nodes that can't talk to each other, and a write arrives at a node in group 1. To stay **consistent**, that node would have to either refuse the write (since it can't confirm the other group doesn't have a conflicting newer value) or refuse to answer reads from group 2 (since it can't guarantee group 2 has the latest data) — either way, something stops answering, sacrificing **availability**. Alternatively, to stay **available**, every node keeps answering requests using whatever data it locally has — but then group 1 and group 2 can diverge and disagree, sacrificing **consistency**. There is no third option: during the partition, you must pick one.

**Important nuance:** CAP is specifically about behavior *during a partition*; when the network is healthy (the common case), a well-designed system can offer both C and A. CAP doesn't say you're sacrificing consistency or availability all the time — only that you must declare which one you give up for the (hopefully rare, hopefully brief) duration of an actual partition.

**CP example — a traditional relational database running as a consistent cluster (e.g., a bank's core ledger using a system like a strongly-consistent distributed SQL database, or ZooKeeper/etcd used for cluster coordination).** On a partition, the minority side stops accepting writes (or even reads) rather than risk serving or recording an inconsistent value, because for a bank balance or a distributed lock, serving stale or conflicting data is worse than being temporarily unavailable.

**AP example — a system like Cassandra or DynamoDB configured for high availability, or a social media "like" counter / shopping cart service.** On a partition, every node keeps accepting reads and writes using its local data, and conflicts are reconciled later (e.g., "last write wins," or application-level merge logic) once the partition heals. A shopping cart or a like-count can tolerate briefly showing a stale number far better than it can tolerate telling the user "service unavailable" during a routine network hiccup.

**Why this matters:** CAP forces an explicit, early design decision rather than an accidental one — picking a database or replication strategy without understanding which side of C/A it favors under partition means you'll discover your system's actual behavior only when a real partition happens in production, which is the worst possible time to find out.
