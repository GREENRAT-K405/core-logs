### Question: Combination Sum II (Recursion/Backtracking — Medium)

Given a collection of candidate numbers `candidates` (which **may contain duplicates**) and a target number `target`, find all **unique combinations** in `candidates` where the candidate numbers sum to `target`.

Each number in `candidates` **may only be used once** in each combination. The solution set must not contain duplicate combinations.

**Input format:**
- An integer array `candidates` (may contain duplicate values).
- An integer `target`.

**Output format:**
- A list of lists of integers: every unique combination of elements from `candidates` (each used at most once) that sums to `target`. The order of combinations and the order of numbers within a combination do not matter, but no two combinations in the result may be identical as multisets.

**Worked Examples:**

1. `candidates = [10,1,2,7,6,1,5]`, `target = 8` → Output: `[[1,1,6],[1,2,5],[1,7],[2,6]]`
2. `candidates = [2,5,2,1,2]`, `target = 5` → Output: `[[1,2,2],[5]]`
3. `candidates = [2]`, `target = 1` → Output: `[]` (no combination of the single element `2` sums to `1`)

**Constraints:**
- `1 <= candidates.length <= 100`
- `1 <= candidates[i] <= 50`
- `1 <= target <= 30`

---

### Step-by-Step Walkthrough

**Approach — Sort, then backtrack with duplicate-skipping and pruning**

This is a classic constrained-subset-sum problem where the twist is that the input array itself contains duplicate *values*, yet each physical element may be used at most once, and the output combinations must be unique as multisets (no two identical `[1,1,6]` results, for example, even though there are two `1`s available to choose from).

1. **Sort `candidates` first.** Sorting serves two purposes: it lets us prune the search early (once the smallest remaining candidate exceeds the remaining target, every later candidate — being even larger — will too, so we can `break` out of the loop instead of just `continue`-ing), and it groups equal values next to each other, which is what makes duplicate-skipping possible.

2. **Backtrack with a `start` index.** Define a recursive function `backtrack(start, remainingTarget, path)` that tries to extend the current partial combination `path` using only candidates at index `>= start` (this enforces "each element used at most once per combination," since we never revisit an earlier index within the same recursive branch).

3. **Base case:** if `remainingTarget == 0`, the current `path` is a valid combination — record a copy of it and return (no need to add more, since all candidate values are positive, so adding anything else would only overshoot).

4. **At each recursive level, iterate `i` from `start` to `end`:**
   - **Skip same-value siblings:** if `i > start` and `candidates[i] == candidates[i-1]`, skip this `i`. This is the key duplicate-avoidance trick: we only allow a repeated value to be the ***first*** occurrence considered *at this particular tree depth/level* — once we've already explored "include the first `1` here," exploring "include the second `1` here instead" at the exact same decision point would just reproduce an identical combination, so we skip it. (Crucially, this check only blocks *siblings* in the recursion tree, not *descendants* — a `1` can still be followed by another `1` deeper in the same branch, which is exactly what allows `[1,1,6]`.)
   - **Prune:** if `candidates[i] > remainingTarget`, break the loop entirely (sorted order guarantees everything after is also too big).
   - **Choose:** push `candidates[i]` onto `path`, recurse with `backtrack(i + 1, remainingTarget - candidates[i], path)`.
   - **Un-choose (backtrack):** pop `candidates[i]` off `path` before trying the next `i`, so the next sibling branch starts from a clean `path`.

**Why it works:** The `start` index guarantees each array position is used at most once along any single root-to-leaf path (enforcing "use each element once"). The sibling-skip rule at a fixed level removes exactly the redundant branches that would otherwise generate the same *set* of chosen values through a different *choice of which physical duplicate* was used — since the values are indistinguishable, using "the first `1`" versus "the second `1`" at the same decision point always yields an identical combination, so only one needs to be explored. The sort-and-break pruning keeps the search from wasting time on branches that can never reach the target.

**Complexity Analysis:**
- **Time complexity:** `O(2^n * n)` in the worst case — there are up to `2^n` subsets to potentially explore, and copying a valid combination of length up to `n` into the result costs `O(n)`; in practice the duplicate-skip and sum-pruning cut this down substantially, but the bound captures the theoretical worst case over all subset-sum search trees. Sorting costs `O(n log n)`, dominated by the search itself.
- **Space complexity:** `O(n)` for the recursion stack and the current `path` buffer (excluding the space needed to store the output itself, which can be up to `O(2^n * n)` in the worst case if many combinations are valid).

### C++ Code

```cpp
#include <vector>
#include <algorithm>
#include <iostream>
using namespace std;

class Solution {
    vector<vector<int>> result;
    vector<int> path;

    // start: lowest index we may still pick from (enforces "use each element once").
    // remaining: target sum still left to reach.
    void backtrack(vector<int>& candidates, int start, int remaining) {
        if (remaining == 0) {
            result.push_back(path); // record a copy of the current valid combination
            return;
        }

        for (int i = start; i < (int)candidates.size(); ++i) {
            // Skip duplicate values at the SAME recursion level to avoid
            // generating the same combination twice (siblings, not descendants).
            if (i > start && candidates[i] == candidates[i - 1]) {
                continue;
            }

            // Sorted array: once a candidate alone exceeds what's left, so will
            // every candidate after it -- stop exploring this branch entirely.
            if (candidates[i] > remaining) {
                break;
            }

            path.push_back(candidates[i]);               // choose
            backtrack(candidates, i + 1, remaining - candidates[i]); // explore
            path.pop_back();                              // un-choose (backtrack)
        }
    }

public:
    vector<vector<int>> combinationSum2(vector<int>& candidates, int target) {
        sort(candidates.begin(), candidates.end()); // enables pruning + duplicate-skipping
        result.clear();
        path.clear();
        backtrack(candidates, 0, target);
        return result;
    }
};

int main() {
    Solution sol;

    vector<int> c1 = {10, 1, 2, 7, 6, 1, 5};
    auto r1 = sol.combinationSum2(c1, 8);
    cout << "Example 1 (expected 4 combinations): " << r1.size() << " found -> ";
    for (auto& combo : r1) {
        cout << "[";
        for (size_t i = 0; i < combo.size(); ++i) cout << combo[i] << (i + 1 < combo.size() ? "," : "");
        cout << "] ";
    }
    cout << endl;

    vector<int> c2 = {2, 5, 2, 1, 2};
    auto r2 = sol.combinationSum2(c2, 5);
    cout << "Example 2 (expected 2 combinations): " << r2.size() << " found -> ";
    for (auto& combo : r2) {
        cout << "[";
        for (size_t i = 0; i < combo.size(); ++i) cout << combo[i] << (i + 1 < combo.size() ? "," : "");
        cout << "] ";
    }
    cout << endl;

    vector<int> c3 = {2};
    auto r3 = sol.combinationSum2(c3, 1);
    cout << "Example 3 (expected 0 combinations): " << r3.size() << " found" << endl;

    return 0;
}
```

**Trace against the examples:**
- `candidates = [10,1,2,7,6,1,5]`, `target = 8`: after sorting → `[1,1,2,5,6,7,10]`. The search finds `[1,1,6]`, `[1,2,5]`, `[1,7]`, `[2,6]` — exactly the 4 expected combinations, with the duplicate-skip rule preventing a second copy of `[1,7]` or `[1,1,6]` arising from choosing "the other `1`" at the same level. ✓
- `candidates = [2,5,2,1,2]`, `target = 5`: after sorting → `[1,2,2,2,5]`. The search finds `[1,2,2]` (using two of the three available `2`s along one branch, which is allowed since they're different *depths*) and `[5]`; the duplicate-skip rule at each level prevents redundant `[1,2,2]` duplicates from the three interchangeable `2`s. ✓
- `candidates = [2]`, `target = 1`: the single candidate `2 > 1 = remaining`, so the loop breaks immediately without ever choosing anything, leaving `result` empty. ✓

### 1. OOP (Comparison)

Explain the difference between **abstraction** and **encapsulation** in object-oriented programming. Many developers use these terms interchangeably — why is that a mistake, and how would you demonstrate the difference with a concrete example?

**Answer:**

**Abstraction** and **encapsulation** are related but solve different problems, and conflating them hides the real design value each one provides.

**Abstraction** is about **hiding complexity by exposing only the essential behavior**, independent of how it's implemented. It's a *design-level* concept concerned with *what* an object does from the perspective of its users. For example, a `Car` class might expose a method `drive()`; the caller doesn't need to know whether `drive()` internally manages a combustion engine, a battery and electric motor, or a hybrid system — abstraction lets the caller reason about "a thing that drives" without caring about the mechanism.

**Encapsulation** is about **bundling data and the methods that operate on that data together, and restricting direct access to the internal state** (typically via access modifiers like `private`/`protected`, exposed only through public getters/setters or methods). It's an *implementation-level* mechanism concerned with *protecting* an object's internal consistency from external interference — e.g., making a `balance` field `private` in a `BankAccount` class so external code cannot set it to a negative number directly, forcing all mutation through a `withdraw()` method that enforces the business rule.

**Why conflating them is a mistake:** You can have one without the other.
- A class can be **encapsulated but not abstracted**: e.g., a class with all `private` fields and public getters/setters for every single field offers no abstraction at all — it's really just exposing its internal representation through a slightly different door; callers still need to understand (and manage) its internal state piece by piece.
- Conversely, an **interface or abstract class provides abstraction with no encapsulation of its own** — an interface has no state to protect; it purely declares *what* operations exist, leaving concrete classes to decide *how* to encapsulate their own data.

**Concrete example:**
```java
interface Shape {               // Abstraction: callers only know "a Shape can compute area"
    double area();
}

class Circle implements Shape {
    private double radius;      // Encapsulation: radius is hidden, only accessible via methods

    public Circle(double radius) { this.radius = radius; }

    public double area() {      // Implementation detail hidden behind the abstraction
        return Math.PI * radius * radius;
    }
}
```
A caller using `Shape s = new Circle(5); s.area();` benefits from **abstraction** (it doesn't know or care that `area()` uses `π * r²`) and separately benefits from **encapsulation** (it cannot directly corrupt `radius` to an invalid negative value; it can only interact through the constructor and public methods).

**Why it matters:** Abstraction drives *interface design* (minimizing what callers need to know, enabling swapping implementations freely), while encapsulation drives *robustness and maintainability* (protecting invariants, enabling internal refactoring without breaking callers). Good OOP design deliberately applies both, but for different reasons — treating them as synonyms leads to designs that get one benefit while silently missing the other.

### 2. Computer Networks (Scenario/Applied)

You are building two features for the same product: (1) a **live video call** feature, and (2) a **file backup/sync** feature that uploads files to cloud storage. One of these should use **UDP** and the other **TCP**. Which goes where, and why? Walk through what happens to each feature's data if a packet is lost on the network.

**Answer:**

**Assignment:** The **live video call** feature should use **UDP** (or a protocol built on it, like RTP/WebRTC's media transport), and the **file backup/sync** feature should use **TCP**.

**Why — reasoning from the guarantees each protocol provides:**

**TCP** provides **reliability** (guaranteed delivery via acknowledgments and retransmission), **ordering** (bytes arrive in the exact sequence they were sent, reassembled from segments if needed), and **congestion control** (it dynamically throttles its sending rate to avoid overwhelming the network, via mechanisms like slow start and congestion avoidance). These guarantees come at the cost of latency: if a segment is lost, TCP must detect this (via a timeout or duplicate ACKs) and retransmit it, and — critically — every segment *after* the lost one must wait in a buffer until the missing one arrives and is placed back in order (this is called **head-of-line blocking**).

**UDP** provides none of those guarantees by default — it is a bare-bones, connectionless protocol that just fires datagrams onto the network with no acknowledgment, no retransmission, and no automatic congestion control. This sounds strictly worse, but it means UDP has **minimal latency overhead** and no head-of-line blocking.

**What happens on packet loss — file backup (TCP):**
1. A chunk of the file is sent as one or more TCP segments.
2. One segment is lost in transit.
3. The receiver's TCP stack notices a gap in the sequence numbers; either the sender's retransmission timer fires, or the receiver sends duplicate ACKs that trigger fast retransmit.
4. The lost segment is **retransmitted**, and all segments received *after* it are held in the receive buffer, unusable by the application, until the gap is filled.
5. Once the retransmitted segment arrives, everything is delivered to the application **in the original, correct byte order** — the file is reconstructed byte-for-byte identical to the original, just with some added latency for that portion of the transfer.
   This is exactly what we want for a file: a backup with a corrupted or missing byte range is worse than useless, so it is worth waiting for perfect, ordered, complete delivery.

**What happens on packet loss — live video call (UDP):**
1. A frame (or part of a frame) of video/audio is sent as a UDP datagram.
2. The datagram is lost.
3. **Nothing retransmits it.** There is no protocol-level recovery at all (unless the application layer, e.g. WebRTC, adds its own optional mechanisms like forward error correction or selective retransmission with tight deadlines).
4. The receiving application simply **skips or interpolates** the missing frame/samples — e.g., the video shows a brief glitch or the previous frame holds a moment longer, and audio might have a tiny gap or use packet-loss concealment — and moves on immediately to the next arriving datagram.
   This is exactly what we want for a live call: by the time a retransmitted TCP-style packet would arrive, that moment of the conversation is already stale — a user would much rather see a half-second glitch and keep talking in real time than have the whole call stall for a fraction of a second waiting for one lost video frame to be perfectly recovered, only for the call to become more and more desynchronized from real time as more packets are lost.

**Why it matters:** The right transport protocol is decided by the *data's tolerance for delay versus tolerance for imperfection*. Data where **correctness and completeness matter more than timeliness** (files, financial transactions, web pages) belongs on TCP. Data where **timeliness matters more than occasional imperfection** (live audio/video, real-time gaming state) belongs on UDP (often with a thin application-layer protocol on top to add just enough loss-tolerant resilience, without reintroducing TCP's head-of-line blocking).

### 3. Computer Architecture (Conceptual/Definition)

What is a **cache miss**, and what are the three classic categories of cache misses (the "3 Cs")? For each category, briefly explain the underlying cause and one technique architects use to reduce it.

**Answer:**

A **cache miss** occurs when the CPU requests data (or an instruction) that is **not currently present** in a given level of cache (L1/L2/L3), forcing the memory system to fetch it from a slower level (a lower cache level, or all the way from main memory/DRAM), which costs significantly more cycles than a **cache hit** (where the requested data is already in the cache and returned almost immediately). Miss rate and miss *penalty* (the extra cycles a miss costs) together determine how much caches actually help real performance.

**The "3 Cs" of cache misses:**

1. **Compulsory misses** (also called "cold start" misses)
   - **Cause:** The very first access to a block of memory can never be a hit, because that data has simply never been brought into the cache before — there's no history to have cached it from.
   - **Reduction technique:** **Prefetching** — the hardware (or compiler-inserted instructions) speculatively loads data into the cache *before* it's actually requested, based on predictable access patterns (e.g., sequential array traversal), so that by the time the CPU actually asks for it, it's already present. Increasing block size can also help, since a larger block pulls in more "nearby" data on the first access, amortizing the compulsory miss over more subsequent (now-hit) accesses — though this has diminishing returns and can waste bandwidth on unused data.

2. **Capacity misses**
   - **Cause:** The cache is simply **too small** to hold the entire *working set* of data the program is actively using. Even with a perfect replacement policy, if more distinct blocks are needed than the cache has room for, old (still-needed) blocks must be evicted to make room for new ones, and will miss again when re-referenced.
   - **Reduction technique:** **Increase cache size** (more capacity directly reduces how often the working set overflows it), or restructure the program/algorithm to improve **locality** (e.g., **loop tiling/blocking** in matrix multiplication, which processes data in small sub-blocks that fit within the cache rather than sweeping across the whole large matrix repeatedly).

3. **Conflict misses**
   - **Cause:** The cache has enough *total* capacity to hold the needed data, but the specific **mapping scheme** (e.g., a direct-mapped or low-associativity set-associative cache) forces two or more frequently-used blocks to compete for the *same* cache line/set, evicting each other even though plenty of other cache space sits unused elsewhere.
   - **Reduction technique:** **Increase associativity** (e.g., moving from direct-mapped to 4-way or 8-way set-associative, or fully associative), which gives each memory address more possible cache lines it could occupy, reducing the chance that two hot blocks are forced to collide on the same single slot.

**Why it matters:** Classifying *why* a miss happened points directly at the right fix — throwing a bigger cache at a conflict-miss-dominated workload wastes die area and power for little benefit, while increasing associativity does nothing for a workload that's genuinely capacity-bound. Architects (and performance engineers tuning software) use this taxonomy, often informed by cache simulators/profilers, to decide whether the next improvement should come from hardware (cache size/associativity/prefetch logic) or software (restructuring data access patterns for better locality).
