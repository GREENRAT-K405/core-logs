### Question: Word Break II (Recursion/Backtracking — Hard)

Given a string `s` and a dictionary of strings `wordDict`, add spaces in `s` to construct a sentence where each word is a valid dictionary word. Return **all** such possible sentences in any order.

The same word in `wordDict` may be reused multiple times in the segmentation.

**Input/Output format:**
- Input: a string `s`, and a list of strings `wordDict`.
- Output: a list of strings, each a valid space-separated sentence. Return an empty list if no valid segmentation exists.

**Example 1:**
```
Input:  s = "catsanddog", wordDict = ["cat","cats","and","sand","dog"]
Output: ["cats and dog", "cat sand dog"]
```

**Example 2:**
```
Input:  s = "pineapplepenapple", wordDict = ["apple","pen","applepen","pine","pineapple"]
Output: ["pine apple pen apple", "pineapple pen apple", "pine applepen apple"]
```

**Example 3:**
```
Input:  s = "catsandog", wordDict = ["cats","dog","sand","and","cat"]
Output: []
```

**Constraints:**
- `1 <= s.length <= 20`
- `1 <= wordDict.length <= 1000`
- `1 <= wordDict[i].length <= 10`
- `s` and `wordDict[i]` consist of only lowercase English letters.
- All the strings of `wordDict` are unique.

### Step-by-Step Walkthrough

**Approach.** This is the natural extension of "Word Break I" (which only asks *whether* a segmentation exists) to enumerating *every* segmentation. The brute-force idea is: at each starting index `start`, try every prefix of the remaining string that is a dictionary word, and recursively solve the rest of the string (`start + word.length` onward). Each full path from `start = 0` to `start = s.length()` that only ever consumes dictionary words is one valid sentence.

Done naively, this recursion recomputes the answer for the same suffix `s.substr(start)` many times, because different earlier word choices can land on the same `start` index. That overlap is exactly what memoization is for: cache the **list of sentences** that solve `s.substr(start)`, keyed by `start`. The next time any branch reaches that same `start`, it reuses the cached list instead of recomputing it.

**Why it works.** Define `helper(start)` = list of all valid space-separated sentences for `s.substr(start)`. The base case `helper(n)` (where `n = s.length()`) is the single "empty" sentence, representing "nothing left to break, we're done" — this lets every real word simply be the first token of whatever `helper(end)` returns, without special-casing the last word. For `start < n`, try every `end` in `(start, n]`; if `s.substr(start, end-start)` is in the dictionary, then every sentence returned by `helper(end)` can be extended by prepending that word (with a space, unless the suffix sentence is empty). Because `helper(start)` only depends on `helper(end)` for `end > start`, there's no cyclic dependency, and the memo table fills in correctly from the back of the string toward the front.

**Complexity.** There are `O(n)` distinct subproblems (one per start index), so with memoization each suffix is solved only once. For each `start`, we try up to `n - start` candidate end points, each with an `O(L)` hash lookup (`L` = max word length, bounded by 10), so the "pure segmentation search" part costs `O(n^2 * L)`. The part that can blow up is building and copying the sentence strings themselves: if the number of valid sentences is `S` and their total length is `T`, constructing the output costs `O(T)` additional work, and `T` can be exponential in `n` in the worst case (e.g. `s` is all `a`'s and the dictionary contains every prefix `"a", "aa", "aaa", ...`) — that blow-up is inherent to the problem (the output itself can be exponentially large), not a flaw in the algorithm. Memoization guarantees we never redo the *search* work for the same suffix twice, which is the best we can do. Space complexity is `O(n)` for the recursion stack plus `O(T)` to store the memoized sentence lists.

### C++ Code

```cpp
#include <bits/stdc++.h>
using namespace std;

class Solution {
public:
    vector<string> wordBreak(string s, vector<string>& wordDict) {
        unordered_set<string> dict(wordDict.begin(), wordDict.end());
        unordered_map<int, vector<string>> memo;
        return helper(s, 0, dict, memo);
    }

private:
    // Returns every valid sentence for s.substr(start); memoized by start index
    // since many recursive branches land on the same suffix.
    vector<string> helper(const string& s, int start, unordered_set<string>& dict,
                          unordered_map<int, vector<string>>& memo) {
        if (memo.count(start)) return memo[start];

        vector<string> result;
        if (start == static_cast<int>(s.size())) {
            // Sentinel "empty sentence" so the last real word doesn't need
            // special-case handling when it gets prepended by the caller.
            result.push_back("");
            return result;
        }

        for (int end = start + 1; end <= static_cast<int>(s.size()); ++end) {
            string word = s.substr(start, end - start);
            if (dict.count(word)) {
                vector<string> rest = helper(s, end, dict, memo);
                for (const string& r : rest) {
                    result.push_back(r.empty() ? word : word + " " + r);
                }
            }
        }

        memo[start] = result;
        return result;
    }
};

int main() {
    Solution sol;

    vector<string> dict1 = {"cat", "cats", "and", "sand", "dog"};
    for (const string& sentence : sol.wordBreak("catsanddog", dict1)) {
        cout << sentence << "\n";
    }
    cout << "---\n";

    vector<string> dict2 = {"apple", "pen", "applepen", "pine", "pineapple"};
    for (const string& sentence : sol.wordBreak("pineapplepenapple", dict2)) {
        cout << sentence << "\n";
    }
    cout << "---\n";

    vector<string> dict3 = {"cats", "dog", "sand", "and", "cat"};
    vector<string> out3 = sol.wordBreak("catsandog", dict3);
    cout << "count = " << out3.size() << "\n"; // 0, no valid segmentation

    return 0;
}
```

### 1. Operating Systems (Conceptual)

What is thrashing in a virtual memory system, and what causes it? Name two techniques an operating system can use to prevent or recover from it.

**Answer:**

Thrashing happens when a system is so busy swapping pages in and out of physical memory that very little CPU time is actually spent executing instructions. In a demand-paged virtual memory system, each process has a "working set" — the set of pages it actively needs over a short time window to make progress without constantly faulting. If the operating system schedules more processes than the available physical frames can comfortably support, every process's working set can't stay resident simultaneously. As soon as one process's page gets evicted to make room for another, and then gets faulted back in a moment later (evicting someone else's page in turn), the system spends almost all of its time servicing page faults instead of running code. Paradoxically, increasing the degree of multiprogramming in this state makes throughput go *down*, not up, because CPU utilization drops as page-fault service time dominates.

Two standard techniques to prevent or recover from it:

1. **Working-set / admission control.** The OS tracks the working-set size of each process (e.g., the set of distinct pages referenced in the last Δ time units) and only admits or schedules a new process if the sum of working sets of all resident processes still fits within physical memory. If memory pressure is detected, the OS can suspend (fully swap out) one or more processes to shrink the degree of multiprogramming, freeing enough frames for the remaining processes to run without constant faulting.
2. **Page-Fault Frequency (PFF) control.** Rather than modeling the working set directly, the OS monitors each process's page-fault rate. If a process's fault rate climbs above an upper threshold, it's allocated more frames (its working set isn't fitting); if it falls below a lower threshold, frames can be reclaimed from it. This keeps each process's frame allocation matched to its actual locality of reference, which keeps overall fault rates — and thus thrashing — in check.

Both techniques work by matching the amount of memory handed out to the amount of memory actually being used, which is the root cause thrashing exploits when that balance is violated.

### 2. DBMS (Comparison)

Compare clustered and non-clustered indexes in a relational database. What are the key structural differences, and why can a table have only one clustered index but many non-clustered indexes?

**Answer:**

A **clustered index** determines the physical storage order of the table's rows. The table data itself is organized (typically as the leaf level of a B+ tree) according to the clustered index key — so the row data *is* the index, there's no separate pointer to chase. A **non-clustered index** is a separate structure: its own B+ tree whose leaves hold the indexed column value(s) plus a row locator (either the clustered index key, if one exists, or a direct row ID/RID for a heap table) pointing to where the actual row lives.

Key differences:

| Aspect | Clustered index | Non-clustered index |
|---|---|---|
| Storage | Reorders the table's physical rows | Separate structure; table rows untouched |
| Lookup cost | Direct — leaf node *is* the row | Extra hop: find locator, then fetch row ("bookmark lookup") unless the index covers the query |
| Range scans | Very fast — matching rows are physically adjacent | Slower unless covering, since matching rows can be scattered |
| Insert cost | Can be expensive if key isn't sequential (mid-table page splits) | Cheaper to maintain in isolation, but every index still adds write overhead |
| Count per table | Exactly one | Many |

The "only one" restriction follows directly from what a clustered index *is*: physical row ordering. A set of rows can only be laid out in one physical order at a time (you can't simultaneously sort the same table by `user_id` and by `created_at` on disk), so a table can have at most one clustered index. Non-clustered indexes don't touch physical row order at all — they're just auxiliary lookup structures layered on top, each independently mapping a key to "where the row actually is" — so there's no structural limit on how many of those a table can have (only the usual practical cost in storage and write amplification on every insert/update/delete).

This is also why primary keys are so often implemented as the clustered index and chosen to be sequential (e.g., auto-increment IDs): it keeps inserts appending to the end of physical storage rather than forcing page splits in the middle of the table.

### 3. Computer Architecture (Scenario)

You benchmark two versions of a function that sums every element of a large N×N matrix of integers stored in a standard row-major 2D array. Version A iterates row by row (`for i: for j: sum += matrix[i][j]`); Version B iterates column by column (`for j: for i: sum += matrix[i][j]`). Both perform exactly the same number of additions and array reads, but for a large N, Version A runs dramatically faster. Explain why, in terms of cache behavior.

**Answer:**

The difference comes entirely from how the two access patterns interact with the CPU cache, not from the number of operations performed. In a row-major layout (the default for C/C++ arrays), `matrix[i][j]` and `matrix[i][j+1]` are adjacent in memory — an entire row is stored contiguously, with row `i+1` immediately following row `i`.

**Version A (row-major traversal)** accesses memory in exactly the order it's laid out: `matrix[i][0], matrix[i][1], matrix[i][2], ...`. The CPU doesn't fetch memory one word at a time — it pulls in a whole cache line (commonly 64 bytes, i.e. 16 consecutive 32-bit ints) on a miss. So the first access to a row pulls in that element plus the next 15 for free; the next 15 accesses are cache hits. This is **spatial locality**, and it's also exactly the pattern hardware prefetchers are built to detect and exploit — they'll start pulling in further cache lines before the program even asks for them.

**Version B (column-major traversal)** accesses `matrix[0][j], matrix[1][j], matrix[2][j], ...` — each successive access jumps forward by an entire row's width (`N * sizeof(int)` bytes) in memory. Once `N` is large enough that a row doesn't fit in (or get reused from) cache before you come back to it, essentially every single access lands in a different cache line than the previous one, so almost every read is a cache miss that has to go out to a slower level of the memory hierarchy (L2, L3, or main memory). The stride also defeats the hardware prefetcher, since consecutive accesses don't follow the simple "next cache line" pattern it's optimized for, and it can even cause extra TLB misses if rows span different memory pages.

The net effect: Version A's accesses are almost all cache hits after the first element of each line; Version B's accesses are close to all cache misses for large N. Since a cache miss can cost on the order of 100x the latency of a cache hit, the two versions can differ in wall-clock time by a large factor despite executing the identical arithmetic. The general lesson — traverse memory in the order it's physically laid out whenever possible — applies broadly: it's the same reason "array of structs vs. struct of arrays" layout choices and loop-tiling/blocking techniques matter in performance-sensitive code.
