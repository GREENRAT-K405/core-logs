### Question: Recover Binary Search Tree (Trees — Hard)

You are given the root of a **binary search tree (BST)** where the values of exactly **two nodes** were swapped by mistake. Recover the tree **without changing its structure** — i.e., fix the BST in place by restoring the correct values at the two swapped nodes, so that an in-order traversal of the tree yields a sorted sequence.

**Input format:** The root of a binary tree (given as a level-order array in examples below, with `null` marking missing children).
**Output format:** The tree is modified in place; no return value is required (as validated by its in-order traversal being sorted).

**Example 1:**
```
Input:  root = [1,3,null,null,2]
Output: [3,1,null,null,2]
```
Explanation: The tree looks like:
```
    1
   /
  3
   \
    2
```
Node `3` cannot be a left child of `1` (3 > 1), so `1` and `3` were swapped. Swapping their values back gives:
```
    3
   /
  1
   \
    2
```

**Example 2:**
```
Input:  root = [3,1,4,null,null,2]
Output: [2,1,4,null,null,3]
```
Explanation: The tree looks like:
```
    3
   / \
  1   4
     /
    2
```
Node `2` cannot be in the right subtree of `3` (2 < 3), so `3` and `2` were swapped. Swapping them back gives a valid BST with root `2`.

**Example 3 (adjacent swap):**
```
Input:  root = [2,3,1]
Output: [2,1,3]
```
Here the two swapped nodes are adjacent in the in-order sequence (`3` and `1` should have been `1` and `3`), which is a special case the algorithm must also handle correctly.

**Constraints:**
- The number of nodes in the tree is in the range `[2, 1000]`.
- `-2^31 <= Node.val <= 2^31 - 1`.
- It is guaranteed that exactly two nodes' values were swapped.
- Follow-up: can you solve it using only `O(1)` extra space (i.e., without recursion or an explicit stack)?

### Step-by-Step Walkthrough

**Key insight:** The in-order traversal of a valid BST visits nodes in strictly increasing order. If exactly two nodes' values have been swapped, the in-order sequence will contain either:
- **One "dip"** (`prev.val > curr.val`) if the two swapped nodes are *adjacent* in the in-order sequence, or
- **Two dips** if the swapped nodes are *not adjacent*.

So the plan is:
1. Perform an in-order traversal, keeping track of the previously visited node (`prev`).
2. Every time we find `prev->val > curr->val`, we have found a violation of the increasing order.
   - On the **first** violation, the offending pair is `(prev, curr)`. We record `first = prev` (the larger value that appears too early) tentatively, and `second = curr` (the smaller value that appears too late).
   - If a **second** violation occurs later, it means the two swapped nodes were not adjacent — the true swapped pair is actually the `prev` from the *first* violation and the `curr` from the *second* violation. We keep `first` fixed (set only once) but keep updating `second` to the latest violation's `curr`.
3. After the traversal, swap `first->val` and `second->val`. This restores the BST property without touching any pointers/structure.

**Why this works:** Consider the sorted sequence that the BST *should* produce. Swapping two values in that sequence creates violations only at the boundaries where the swapped elements now sit next to a value they're incompatible with. If the swapped elements are adjacent in the sequence, exactly one boundary breaks (one dip, and the dip itself directly gives us `first` and `second`). If they are not adjacent, two boundaries break: the first dip's `prev` is the actual larger misplaced value, and the second dip's `curr` is the actual smaller misplaced value — everything strictly between them is still internally sorted and untouched.

**Implementation choice:** An iterative in-order traversal using an explicit stack avoids recursion overhead/stack-depth concerns for large trees and makes the "running `prev` pointer" logic easy to follow. (The follow-up `O(1)`-space version replaces the stack with Morris traversal, which temporarily threads `right` pointers from in-order predecessors back to the current node, then removes them as it goes — same violation-detection logic, just a different way of producing the in-order sequence without extra memory.)

**Complexity:**
- Time: `O(n)` — every node is visited exactly once during the in-order traversal.
- Space: `O(h)` where `h` is the tree height, for the explicit stack (`O(log n)` for a balanced tree, `O(n)` worst case for a skewed one). The Morris-traversal variant achieves `O(1)` extra space at the cost of temporarily mutating and restoring tree pointers.

### C++ Code

```cpp
#include <bits/stdc++.h>
using namespace std;

struct TreeNode {
    int val;
    TreeNode *left, *right;
    TreeNode(int x) : val(x), left(nullptr), right(nullptr) {}
};

class Solution {
public:
    void recoverTree(TreeNode* root) {
        TreeNode *first = nullptr, *second = nullptr, *prev = nullptr;
        stack<TreeNode*> st;
        TreeNode* curr = root;

        while (curr != nullptr || !st.empty()) {
            // Walk to the leftmost node, pushing ancestors along the way
            while (curr != nullptr) {
                st.push(curr);
                curr = curr->left;
            }
            curr = st.top();
            st.pop();

            // In a valid BST, prev->val must be strictly less than curr->val
            if (prev != nullptr && prev->val > curr->val) {
                if (first == nullptr) {
                    first = prev;   // larger value that appears too early
                }
                second = curr;     // keeps updating to the latest dip's curr
            }

            prev = curr;
            curr = curr->right;
        }

        // Restore the BST property by swapping just the two values
        swap(first->val, second->val);
    }
};

// Helper to build a tree from a level-order vector for quick manual testing
// (nullopt entries represent missing children); not required by the judge.
TreeNode* buildTree(const vector<optional<int>>& vals) {
    if (vals.empty() || !vals[0].has_value()) return nullptr;
    TreeNode* root = new TreeNode(*vals[0]);
    queue<TreeNode*> q;
    q.push(root);
    size_t i = 1;
    while (!q.empty() && i < vals.size()) {
        TreeNode* node = q.front(); q.pop();
        if (i < vals.size()) {
            if (vals[i].has_value()) {
                node->left = new TreeNode(*vals[i]);
                q.push(node->left);
            }
            i++;
        }
        if (i < vals.size()) {
            if (vals[i].has_value()) {
                node->right = new TreeNode(*vals[i]);
                q.push(node->right);
            }
            i++;
        }
    }
    return root;
}
```

### 1. Operating Systems (Conceptual/Definition)

What is a page fault? Explain the difference between a **minor (soft) page fault** and a **major (hard) page fault**, and describe what the operating system does when each occurs.

**Answer:**

A page fault is a trap (exception) raised by the CPU's memory management unit (MMU) when a running process accesses a virtual memory page that is not currently mapped to a physical frame in RAM according to the page table. The OS's page-fault handler intervenes to resolve the situation before resuming the process.

There are two broad categories:

- **Minor (soft) page fault:** The page is not mapped in the current process's page table, but the physical frame already holding the needed data exists somewhere in memory — for example, the page was evicted from this process's mapping but is still in the system's page cache, or it is a shared library page already loaded by another process, or it's a freshly requested anonymous page that just needs a zeroed frame allocated. The OS only needs to update page table entries (and possibly allocate a frame) — no disk I/O is required. This is fast, typically on the order of microseconds.

- **Major (hard) page fault:** The data is not in physical memory at all and must be fetched from secondary storage — e.g., the page was swapped out to disk, or it's a demand-paged portion of an executable/mapped file being read for the first time. The OS must: (1) locate the page on disk (from the page table entry or swap metadata), (2) allocate a free physical frame (possibly evicting another page via the page replacement policy, e.g., LRU/clock), (3) issue a disk I/O read to bring the page into that frame, (4) update the page table to map the virtual page to the new frame, and (5) resume the faulting instruction. This is orders of magnitude slower (milliseconds) because it's bottlenecked by disk/storage latency.

Why this matters in practice: major faults are a key signal of memory pressure — a system that is "thrashing" (spending most of its time servicing major faults and swapping) will show severe performance degradation even though the CPU itself isn't overloaded. Tools like `vmstat`, `/proc/vmstat`, or `perf` distinguish minor vs. major faults precisely because major faults indicate a disk-bound bottleneck that scaling CPU won't fix — the real fix is adding RAM, reducing working-set size, or tuning swappiness.

### 2. Computer Networks (Comparison)

Compare **TCP** and **QUIC** in terms of connection establishment, reliability/retransmission, and head-of-line (HOL) blocking.

**Answer:**

| Aspect | TCP (+ TLS on top) | QUIC |
|---|---|---|
| Transport layer | Runs directly over IP; a separate protocol (TLS) is layered on top for encryption | Runs over UDP; encryption (TLS 1.3) is built into the protocol itself, not layered separately |
| Connection establishment | Requires a 3-way handshake (SYN, SYN-ACK, ACK) for TCP itself, *then* a separate TLS handshake (1-RTT or 2-RTT) on top — commonly 2-3 RTTs before application data flows on a fresh connection | Combines the transport and cryptographic handshake into a single step: a full handshake is just 1 RTT, and a resumed connection to a previously-seen server can send application data in 0-RTT (at the cost of some replay-attack risk for that first flight) |
| Reliability/retransmission | A single ordered, reliable byte stream per connection; the OS kernel manages one set of sequence numbers and one retransmission timer for the whole connection | Multiplexes independent *streams* within one QUIC connection, each with its own flow control and retransmission; a lost packet is retransmitted only for the specific stream(s) whose data it carried |
| Head-of-line blocking | Because all application streams (e.g., multiple HTTP/2 streams) are multiplexed onto one TCP byte stream, a single lost TCP segment stalls delivery of *all* streams to the application until that segment is retransmitted and received — this is "HOL blocking at the transport layer" | Since each QUIC stream is tracked independently, a packet loss affecting one stream's data does not block the delivery of other streams' already-received data to the application — this largely eliminates transport-level HOL blocking (though a single stream itself can still stall waiting on its own retransmission) |
| Migration/middleboxes | Tied to the 4-tuple (src/dst IP + port); a client changing networks (e.g., Wi-Fi to cellular) breaks the connection and requires a new handshake | Connections are identified by a Connection ID independent of the IP/port tuple, so QUIC supports seamless connection migration across network changes |

Why it matters: QUIC (standardized as the transport for HTTP/3) was designed specifically to fix TCP+TLS's handshake latency and HOL-blocking problems for web traffic, at the cost of needing to reimplement reliability/congestion-control logic in user space (since UDP itself provides none) rather than relying on well-optimized kernel TCP stacks.

### 3. Computer Architecture (Scenario/Applied)

Two threads run on separate CPU cores and each repeatedly increments its *own* independent integer counter in a tight loop. The two counters happen to be adjacent elements of the same array, e.g. `int counters[2]; // thread 0 increments counters[0], thread 1 increments counters[1]`. Even though there is no logical data race (each thread only touches its own variable), the program runs dramatically slower than if the counters were far apart in memory. Why does this happen, and how would you fix it?

**Answer:**

This is the classic **false sharing** problem. Modern CPUs manage cache coherence (keeping each core's cache consistent with main memory and other cores' caches) at the granularity of a **cache line**, typically 64 bytes on most x86/ARM systems — not at the granularity of individual variables. If `counters[0]` and `counters[1]` are adjacent `int`s (4 bytes each), they very likely sit inside the *same* 64-byte cache line.

When core 0 writes to `counters[0]`, the cache-coherence protocol (e.g., MESI) must invalidate that entire cache line in every other core's cache, because from the protocol's point of view the whole line — not just the 4 bytes that changed — may now be stale elsewhere. So when core 1 next reads or writes `counters[1]` (which lives in that same invalidated line), it suffers a cache miss and must re-fetch the line from core 0's cache or from memory. Then core 1's write to `counters[1]` invalidates the line in core 0's cache, forcing core 0 to miss on its *next* access to `counters[0]`. The two cores end up ping-ponging the same cache line back and forth continuously, even though they never touch each other's actual data — each "local" increment is turned into an expensive cross-core cache-coherence round trip instead of a cheap L1-cache hit.

**Fixes:**
1. **Padding:** Pad each counter out so that each one occupies its own cache line, e.g.
   ```cpp
   struct alignas(64) PaddedCounter { int value; char pad[60]; };
   PaddedCounter counters[2];
   ```
   This guarantees `counters[0]` and `counters[1]` never share a cache line, so each core's writes only invalidate a line the other core isn't using.
2. **Per-thread local accumulation:** Have each thread accumulate into a genuinely thread-local variable (e.g., `thread_local` storage, or a local stack variable) during the hot loop, and only combine results into a shared structure once at the end — eliminating the shared cache line from the hot path entirely.
3. **Restructuring data layout:** More generally, when designing data structures accessed concurrently by multiple threads (e.g., per-thread statistics arrays, sharded counters), align and pad each thread's slice to cache-line boundaries (`std::hardware_destructive_interference_size` in C++17 gives the platform's recommended padding size) rather than packing them tightly.

Why it matters: false sharing is invisible in the source code's logical correctness (there's no race condition to catch with a thread sanitizer) but can cause order-of-magnitude slowdowns in multi-threaded code; profiling tools that report cache-miss / cache-coherence traffic (e.g., `perf c2c` on Linux) are typically needed to diagnose it, since standard CPU-time profiling just shows "slow" without indicating why.
