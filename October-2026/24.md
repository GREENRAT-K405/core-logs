### Question: Expression Add Operators (Recursion/Backtracking — Hard)

**Problem Statement**

Given a string `num` that contains only digits, and an integer `target`, return *all* ways to insert the binary operators `+`, `-`, and `*` between the digits of `num` so that the resulting expression evaluates to `target`.

Rules:
- Operators are inserted strictly *between* digits — you cannot add a unary sign, and you cannot drop digits.
- An operand cannot have a leading zero unless the operand is exactly `"0"` itself (e.g. `"05"` is never a valid operand, but `"0"` alone is fine).
- The expression must be evaluated with standard operator precedence (`*` binds tighter than `+`/`-`), left to right, not just left-to-right with equal precedence.
- Return the list of valid expression strings in any order.

**Input/Output Format**

- Input: a string `num` of digits, and an integer `target`.
- Output: a list of strings, each a valid expression built from `num` that evaluates to `target`.

**Examples**

1. Input: `num = "123"`, `target = 6` → Output: `["1+2+3", "1*2*3"]`
2. Input: `num = "232"`, `target = 8` → Output: `["2*3+2", "2+3*2"]`
3. Input: `num = "105"`, `target = 5` → Output: `["1*0+5", "10-5"]`
4. Input: `num = "00"`, `target = 0` → Output: `["0+0", "0-0", "0*0"]` (note: `"00"` as a single two-digit operand is invalid because of the leading zero, but splitting into two `"0"` operands is fine)

**Constraints**

- `1 <= num.length <= 10`
- `num` consists of digits `0`–`9` only.
- `-2^31 <= target <= 2^31 - 1`

### Step-by-Step Walkthrough

**Why brute force over substrings is the natural shape.** We're deciding, at every gap between digits, which operator (or none, if we're still extending the current operand) goes there. That's a sequence of choices with a cutoff (reach `target` or don't) — the textbook signature of backtracking: build a partial expression, recurse on the rest of the string, undo, try the next choice.

**What "a choice" actually is.** At each position `pos` in `num`, we don't just choose an operator — we also choose *how many digits* the next operand consumes (1 digit, 2 digits, …, up to the rest of the string). So the recursion tries every operand length starting at `pos`, and for each length tries appending it with `+`, `-`, or `*` (except for the very first operand, which has no operator before it).

**The leading-zero prune.** If `num[pos] == '0'` and we're considering an operand longer than 1 digit, every longer operand starting there (`"00"`, `"05"`, `"012"`, …) is invalid. So the moment we see a leading `'0'`, we take the 1-digit operand `"0"` and then `break` out of the length loop — no valid longer operand can start here.

**The one subtlety: redoing multiplication.** You can't track "running total" with a single accumulator the way you can for `+`/`-`, because `*` doesn't combine with the running total directly — it only applies to the *last* operand. If the expression so far evaluated to `curVal` using a last operand `lastOperand` (added or subtracted in with its sign already folded in), and the next operand is `x` with a `*` in front, the correct new total isn't `curVal * x`, it's:

```
newVal = curVal - lastOperand + lastOperand * x
newLast = lastOperand * x
```

i.e., peel the last operand back out, then add in the product instead. This is exactly how you'd re-derive `"1+2*3"` by hand: after `1+2` you have `curVal=3, lastOperand=2`; seeing `*3` means undo the `+2` (back to `1`), then add `2*3=6`, giving `7` — matching real precedence instead of naively getting `(1+2)*3=9`.

For `+` and `-`, it's simpler:
- `+x`: `newVal = curVal + x`, `newLast = x` (positive, since it was added)
- `-x`: `newVal = curVal - x`, `newLast = -x` (stored negative, so a *later* `*` on it still peels out correctly via `curVal - lastOperand + lastOperand * nextX`)

**Base case.** When `pos` reaches the end of `num` and `curVal == target`, the expression built so far is a valid answer — append it to the result.

**Overflow guard.** `num` can be up to 10 digits, so an operand can be as large as `9999999999`, which overflows a 32-bit `int` (max ~2.1 billion) even though `target` itself fits in 32 bits. Every running value and operand must be carried in a 64-bit integer (`long long`) to avoid undefined behaviour from signed overflow during the search.

**Why it terminates and is correct.** The recursion always advances `pos` by at least 1 digit per call, so depth is bounded by `n = num.length()`. At each call there are at most `n` choices of operand length and 3 operator choices, so the total work is bounded by roughly `O(n * 3^n)` in the worst case (small `n <= 10`, so this is trivially fast in practice) — exponential, but the only way to enumerate "all" valid insertions is to actually consider the combinatorial space, and `n <= 10` keeps it small by design.

**Complexity.**
- Time: `O(n * 4^n)` worst case (branching over operand lengths and 3 operators at each of up to `n` positions; `n <= 10` so this is fast in practice).
- Space: `O(n)` for the recursion stack and the expression string under construction, plus `O(k * n)` to store `k` output expressions.

### C++ Code

```cpp
#include <string>
#include <vector>
using namespace std;

class Solution {
public:
    vector<string> addOperators(string num, int target) {
        vector<string> result;
        string expr;
        // curVal: value of the expression built so far.
        // lastOperand: the (signed) value of the most recently applied
        // operand, needed so a future '*' can "undo" the last +/- and
        // redo it as a product, per standard operator precedence.
        backtrack(num, target, 0, 0LL, 0LL, expr, result);
        return result;
    }

private:
    void backtrack(const string& num, long long target, int pos,
                    long long curVal, long long lastOperand,
                    string& expr, vector<string>& result) {
        int n = (int)num.size();

        if (pos == n) {
            if (curVal == target) {
                result.push_back(expr);
            }
            return;
        }

        int exprLenBefore = (int)expr.size();

        // Try every operand length starting at `pos`.
        long long operandVal = 0;
        for (int len = 1; pos + len <= n; ++len) {
            // Leading-zero guard: an operand longer than 1 digit can't
            // start with '0'. Take the single "0" and stop extending.
            if (len > 1 && num[pos] == '0') break;

            operandVal = operandVal * 10 + (num[pos + len - 1] - '0');
            string operandStr = num.substr(pos, len);

            if (pos == 0) {
                // First operand: no operator placed before it.
                expr += operandStr;
                backtrack(num, target, pos + len, operandVal, operandVal, expr, result);
                expr.resize(exprLenBefore);
            } else {
                // '+'
                expr += '+';
                expr += operandStr;
                backtrack(num, target, pos + len, curVal + operandVal, operandVal, expr, result);
                expr.resize(exprLenBefore);

                // '-'
                expr += '-';
                expr += operandStr;
                backtrack(num, target, pos + len, curVal - operandVal, -operandVal, expr, result);
                expr.resize(exprLenBefore);

                // '*': undo the last operand's contribution, then redo it
                // as a product, so precedence matches real arithmetic.
                expr += '*';
                expr += operandStr;
                long long newLast = lastOperand * operandVal;
                long long newVal = curVal - lastOperand + newLast;
                backtrack(num, target, pos + len, newVal, newLast, expr, result);
                expr.resize(exprLenBefore);
            }
        }
    }
};
```

Checking it against the examples: `"123", 6` explores `1+2+3=6` and `1*2*3=6` and finds both; `"105", 5` finds `1*0+5=5` and `10-5=5` while correctly rejecting `"05"` as an operand because of the leading-zero break; `"00", 0` only ever builds operands `"0"` and `"0"` (never `"00"`), giving `0+0`, `0-0`, `0*0`.

### 1. DBMS (Conceptual)

What is a covering index, and how does it reduce the cost of a query compared to a regular secondary index that isn't "covering"?

**Answer:**

A **secondary index** maps a key (say, `email`) to the location of the full row — typically a pointer to a slot in the table's heap, or in index-organized engines like InnoDB, the primary key value. When a query filters on `email` but also needs to read other columns (`name`, `created_at`, …) that aren't in that index, the engine has to do two steps per matching row: (1) look up the row's location in the secondary index, then (2) follow that pointer back to the actual table (or, in InnoDB, do a second lookup into the clustered index keyed by primary key) to fetch the remaining columns. That second step is called a **lookup** or **bookmark lookup**, and when it happens once per matching row, it can dominate the query's cost — especially if those rows are scattered across many disk pages, turning a handful of logical reads into a storm of random I/O.

A **covering index** is a secondary index that already contains *every column the query needs* — every column in the `SELECT` list, every column in the `WHERE` clause, and every column in `ORDER BY`/`GROUP BY` — either as key columns or as extra "included" columns. If the index covers the query, the engine can answer it directly from the index's own pages and never has to touch the base table at all. This turns a plan with a lookup-per-row into a single sequential scan of (typically much smaller, often fully cached) index pages — visible in a query plan as something like "Index Only Scan" (Postgres) or a `Using index` note (MySQL), as opposed to "Index Scan" / a plan with a separate heap/table fetch.

**Trade-offs:** a covering index is wider than a minimal index on just the filter columns, so it costs more disk space and, more importantly, more write overhead — every `INSERT`/`UPDATE`/`DELETE` that touches any column in the index has to maintain that index too. So covering indexes are a deliberate choice: you widen a specific hot, read-heavy query's index just enough to eliminate its lookups, you don't blanket every index with every column "just in case."

### 2. System Design Basics (Comparison)

Compare horizontal scaling and vertical scaling for the database tier of a web application. For each, say how it's achieved, what eventually limits it, and give one scenario where it is clearly the better choice.

**Answer:**

**Vertical scaling** ("scale up") means making the single database server more powerful: more CPU cores, more RAM (so more of the working set and indexes stay cached instead of hitting disk), faster storage (NVMe over spinning disk), or a bigger network pipe. It's achieved with no application changes at all — the data model, queries, and client code don't know the machine got bigger.
- *Limit:* there's a hard ceiling — at some point you're renting the largest instance type that exists, and you're still one hardware failure away from the whole database being down (a single point of failure). Cost also tends to grow faster than linearly as you approach the top of the available instance sizes.
- *Best scenario:* a dataset and workload that fit comfortably on one well-specced machine, where the team values simplicity and strong consistency (one node means one source of truth, joins and transactions stay trivial) more than it needs to future-proof against 100x growth. Most applications never outgrow this.

**Horizontal scaling** ("scale out") means adding more machines instead of a bigger one: **sharding** writes/data across multiple database nodes by some partition key, and/or adding **read replicas** to spread read traffic. It's achieved with real application and schema changes — picking a shard key that distributes load evenly, handling cross-shard joins and transactions (often by avoiding them), and routing queries to the right node(s).
- *Limit:* complexity, not hardware. Rebalancing data when you add/remove shards, keeping replicas' replication lag acceptable for the app's consistency needs, and the loss of cheap cross-row transactions/joins once data is split across machines.
- *Best scenario:* a dataset or write throughput that has genuinely outgrown what any single machine can hold or process (e.g. a multi-terabyte table with heavy concurrent writes), or a read-heavy workload where adding read replicas behind the primary is a cheap way to absorb load without touching the write path at all.

**In practice** these aren't mutually exclusive: a common path is "scale up until it's clearly not enough, add read replicas for read load, and only shard writes once a single primary's write throughput or storage is the actual bottleneck" — because sharding is the most expensive (in engineering effort) of the three and should be reached for last, not first.

### 3. Computer Networks (Scenario)

Users of a web service report intermittent timeouts connecting to a backend API during peak traffic, but the backend's CPU and memory usage look completely normal throughout. Walk through how you would figure out whether the problem sits at the TCP connection-handling layer (accept queue / backlog, ephemeral port exhaustion, NAT) versus the application layer (e.g. a saturated worker/thread pool).

**Answer:**

Normal CPU/memory is the key clue that rules out "the server is just overloaded doing work" and points toward something *queuing* rather than *computing* — so the investigation should walk outward from the network stack toward the application, checking for queues that are full rather than resources that are maxed out.

1. **Check the TCP accept/SYN queues first.** Every listening socket has two OS-level queues: the SYN backlog (half-open connections completing the handshake) and the accept queue (fully-established connections waiting for the application to call `accept()`). On Linux, `ss -lnt` shows `Recv-Q`/`Send-Q` against `Listen` sockets — if `Recv-Q` is consistently near the configured backlog (`somaxconn` / the backlog argument passed to `listen()`), new connections are being queued or dropped *before the application even sees them*. `netstat -s | grep -i overflow` (or the equivalent `nstat TcpExtListenOverflows`/`TcpExtListenDrops`) directly counts SYN/accept-queue overflow events — a nonzero and climbing count during peak hours is strong evidence the bottleneck is here, independent of app CPU.

2. **Check for ephemeral port / connection-table exhaustion**, especially if the app opens a new short-lived connection per request (rather than pooling/reusing). `ss -s` gives a summary of total sockets and states; a pile-up in `TIME_WAIT` (sockets that finished but haven't expired yet) under high connection churn can exhaust the local ephemeral port range (default roughly 32768–60999 on Linux, so ~28,000 ports) faster than it seems like it should, causing new outbound/accepted connections to fail or stall. If there's a NAT device or load balancer in the path, its **connection-tracking table** can fill up the same way (visible as `conntrack -C` approaching `net.netfilter.nf_conntrack_max`), silently dropping or delaying new connections even though both the client and server look fine individually.

3. **Only after ruling those out, look at the application layer.** If the OS-level queues and port/conntrack tables are healthy, but requests still stall, check the app's own worker/thread pool or connection-pool size: a fixed pool (say, 50 workers) will queue incoming requests once all 50 are busy waiting on something *else* slow (a downstream DB call, a slow dependency) — and a thread stuck waiting on I/O doesn't show up as CPU usage, which is exactly why CPU/memory can look "normal" while users still see timeouts. Thread-dump or pool-metrics (active vs. queued count) during a peak window will show this directly: queued-request count climbing while CPU stays flat is the application-layer signature, as opposed to the kernel-level counters climbing in step 1.

**Mitigations follow directly from where the bottleneck is found:** raise the listen backlog and tune `somaxconn` for queue overflow; enable connection reuse/keep-alive (or a client-side connection pool) to cut the rate of new handshakes for port/conntrack exhaustion; and size the application's worker pool to the downstream dependency's real latency (or make the slow call async) for an application-layer queue — three different fixes for three different root causes that all present as "intermittent timeouts under load."
