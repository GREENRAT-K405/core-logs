### Question: Single Number III (Bit Manipulation — Medium)

Given an integer array `nums` in which exactly two elements appear exactly once and every other element appears exactly twice, find the two elements that appear only once. You may return the answer in any order.

**Input format:**
- An integer array `nums` of length `n`, where `n` is even and `n >= 4`.

**Output format:**
- An array/pair of the two integers that appear exactly once, in any order.

**Worked Examples:**

1. `nums = [1, 2, 1, 3, 2, 5]` → Output: `[3, 5]` (or `[5, 3]`). `1` and `2` each appear twice; `3` and `5` each appear once.
2. `nums = [-1, 0]` → Output: `[-1, 0]` (or `[0, -1]`). Both appear exactly once (trivial case, n = 2 conceptually but constraints guarantee at least two singles).
3. `nums = [0, 1]` → Output: `[1, 0]` (or `[0, 1]`).

**Constraints:**
- `2 <= nums.length <= 3 * 10^4`
- `-2^31 <= nums[i] <= 2^31 - 1`
- Each element in `nums` appears exactly twice, except for two elements which appear exactly once.
- Follow-up: solve it in **linear runtime** and using **constant extra space**.

---

### Step-by-Step Walkthrough

**Why plain XOR isn't enough:** For the classic "Single Number" problem (only *one* element appears once), XOR-ing the whole array works because every duplicated value cancels out (`x ^ x = 0`), leaving just the single value. Here, two different values `a` and `b` appear once each. XOR-ing everything still cancels all the duplicates, but leaves `a ^ b`, not `a` or `b` individually — we need one more trick to separate them.

**Key idea — use a differing bit to split the array into two groups:**

1. XOR every number in `nums` together. Call the result `xorAll`. Since every duplicate cancels, `xorAll = a ^ b`.
2. Because `a != b`, `xorAll` is non-zero, and at least one bit position differs between `a` and `b` (specifically, every bit set in `xorAll` is a position where `a` and `b` disagree).
3. Isolate **any one** such differing bit — conventionally the lowest set bit of `xorAll`, computed as `diffBit = xorAll & (-xorAll)` (this is the standard "isolate lowest set bit" trick: `-xorAll` is the two's-complement negation, and ANDing with the original clears every bit except the lowest one that was set).
4. Partition all numbers in `nums` into two groups based on whether `diffBit` is set in each number:
   - Group 1: numbers where `diffBit` is set.
   - Group 2: numbers where `diffBit` is clear.
   - Crucially, `a` and `b` land in **different** groups (since they disagree on that bit), while every duplicated pair `x, x` lands in the **same** group (since both copies of `x` have the same bits).
5. XOR all numbers within Group 1 — every duplicate pair cancels, leaving exactly one of `a`/`b`. Same for Group 2, leaving the other one.

**Why it works:** The partition step is the crux — it converts "find two unique numbers mixed into one XOR" into two independent instances of the easy "find one unique number" problem, by exploiting a bit position where the two answers provably differ.

**Complexity Analysis:**
- **Time complexity:** `O(n)` — three linear passes over the array (one to compute `xorAll`, one to partition-and-XOR; these can even be merged into two passes total).
- **Space complexity:** `O(1)` — only a handful of integer accumulators, no auxiliary data structures (satisfies the follow-up constraint).

---

### C++ Code

```cpp
#include <iostream>
#include <vector>
using namespace std;

class Solution {
public:
    vector<int> singleNumber(vector<int>& nums) {
        // XOR everything: every duplicated value cancels out (x ^ x = 0),
        // leaving xorAll = a ^ b for the two values that appear once.
        unsigned int xorAll = 0;
        for (int num : nums) {
            xorAll ^= static_cast<unsigned int>(num);
        }

        // Isolate the lowest set bit of (a ^ b). Since a != b, this bit
        // is guaranteed to be set in exactly one of a, b.
        unsigned int diffBit = xorAll & (-xorAll);

        int a = 0, b = 0;
        for (int num : nums) {
            if (static_cast<unsigned int>(num) & diffBit) {
                a ^= num;   // group where diffBit is set
            } else {
                b ^= num;   // group where diffBit is clear
            }
        }
        return {a, b};
    }
};

int main() {
    Solution sol;

    vector<int> nums1 = {1, 2, 1, 3, 2, 5};
    vector<int> res1 = sol.singleNumber(nums1);
    cout << "Example 1 -> {" << res1[0] << ", " << res1[1] << "} (expected {3,5} in some order)" << endl;

    vector<int> nums2 = {-1, 0};
    vector<int> res2 = sol.singleNumber(nums2);
    cout << "Example 2 -> {" << res2[0] << ", " << res2[1] << "} (expected {-1,0} in some order)" << endl;

    vector<int> nums3 = {0, 1};
    vector<int> res3 = sol.singleNumber(nums3);
    cout << "Example 3 -> {" << res3[0] << ", " << res3[1] << "} (expected {1,0} in some order)" << endl;

    return 0;
}
```

**Trace against the examples:**
- `[1, 2, 1, 3, 2, 5]`: `xorAll = 1^2^1^3^2^5 = 3^5 = 6` (`0b110`). `diffBit = 6 & (-6) = 2` (`0b010`). Group by bit 1: `3` (`0b011`, bit set) and `2` (`0b010`, bit set, appears twice) go to group `a`; `1` and `5` (`0b101`, bit clear) go to group `b`. XOR-ing group `a`: `2^3^2 = 3`. XOR-ing group `b`: `1^1^5 = 5`. Result `{3, 5}`. ✓
- `[-1, 0]`: `xorAll = (-1) ^ 0 = 0xFFFFFFFF`. `diffBit = xorAll & (-xorAll) = 1` (lowest bit). `-1` has bit 0 set → group `a`; `0` has bit 0 clear → group `b`. Result `a = -1`, `b = 0`. ✓
- `[0, 1]`: `xorAll = 1`. `diffBit = 1`. `0` → group `b`, `1` → group `a`. Result `a = 1`, `b = 0`. ✓

## CS Fundamentals

### 1. DBMS (Conceptual/Definition)

What is the difference between a **clustered index** and a **non-clustered index** in a relational database? Explain how each one affects the physical storage of data and typical query performance.

**Answer:**

A database index is a separate structure (almost always a B-tree or B+-tree) that lets the database engine locate rows without scanning the whole table. Clustered and non-clustered indexes differ in how they relate to the actual data rows:

- **Clustered index:** Determines the **physical order** in which rows are stored on disk. The table's data rows themselves are the leaf nodes of the B+-tree, sorted by the clustered index key. Because the data can only be physically sorted one way, **a table can have at most one clustered index** (often the primary key, by default in engines like SQL Server and MySQL/InnoDB).
  - *Performance effect:* Range queries and lookups on the clustered key are very fast (no extra pointer-chasing — once you find the leaf, you have the row). Inserts with random clustered keys can cause page splits/fragmentation; inserting with a monotonically increasing key (e.g., an auto-increment ID) tends to append efficiently instead.

- **Non-clustered index:** A **separate structure** from the table's physical row storage. Its leaf nodes store the indexed column's value plus a pointer/row-locator (either the clustered key, or a direct row ID in a heap table) back to the actual row. A table can have **many** non-clustered indexes, one per query pattern that needs fast lookup.
  - *Performance effect:* A lookup first searches the non-clustered index's B-tree, then follows the pointer to fetch the full row — an extra "bookmark lookup" step compared to a clustered index. If a query only needs columns already present in the index (a "covering index"), this extra step can be skipped entirely, which is why covering indexes are a common optimization technique.

**Why this matters:** Choosing the clustered key well (narrow, stable, ideally sequential) minimizes page splits and keeps range scans fast, while non-clustered indexes are the main lever for speeding up queries that filter/sort on columns other than the clustered key — but each additional non-clustered index adds write overhead (every insert/update/delete must also maintain it), so indexing is a storage/write-speed vs. read-speed tradeoff, not a free win.

### 2. OOP (Scenario/Applied)

You're designing a notification system that must support sending alerts via **Email**, **SMS**, and **Push notification**, and new channels will likely be added later. The logic for *deciding when and what* to send (triggers, templating, retry policy) should stay independent of *how* a message is actually delivered. Would you model the delivery mechanism using **inheritance** or **composition**? Walk through your design and justify the choice.

**Answer:**

**Composition** (specifically the **Strategy pattern**) is the better fit here, not inheritance.

**Why not inheritance:** A naive approach might create a base `Notification` class with subclasses `EmailNotification`, `SmsNotification`, `PushNotification`, each overriding a `send()` method. This fails as requirements grow: if you later need "retry with exponential backoff" logic that should apply to *every* channel, or want to send the *same* logical alert through *multiple* channels at once, inheritance forces awkward multiple-subclassing or duplicated logic in every leaf class. Inheritance also locks the delivery mechanism in at compile time — you can't swap a user's preferred channel at runtime without re-instantiating a different object type.

**The composition-based design:**

```cpp
#include <iostream>
#include <memory>
#include <string>
#include <vector>
using namespace std;

// The delivery mechanism is an interface, injected rather than inherited.
class INotifier {
public:
    virtual void send(const string& recipient, const string& message) = 0;
    virtual ~INotifier() = default;
};

class EmailNotifier : public INotifier {
public:
    void send(const string& recipient, const string& message) override {
        cout << "[Email] to " << recipient << ": " << message << endl;
    }
};

class SmsNotifier : public INotifier {
public:
    void send(const string& recipient, const string& message) override {
        cout << "[SMS] to " << recipient << ": " << message << endl;
    }
};

// The service HOLDS a notifier (composition) instead of BEING one (inheritance).
class NotificationService {
    vector<shared_ptr<INotifier>> channels;
public:
    void addChannel(shared_ptr<INotifier> notifier) {
        channels.push_back(notifier);
    }

    // Trigger/templating logic lives here, fully decoupled from delivery.
    void alertUser(const string& recipient, const string& event) {
        string message = "Alert: " + event + " occurred.";
        for (auto& channel : channels) {
            channel->send(recipient, message);
        }
    }
};

int main() {
    NotificationService service;
    service.addChannel(make_shared<EmailNotifier>());
    service.addChannel(make_shared<SmsNotifier>());
    service.alertUser("user@example.com", "payment failed");
    return 0;
}
```

`NotificationService` depends only on the `INotifier` interface, not on any concrete channel. Adding Push support later just means writing a new `PushNotifier` class — zero changes to `NotificationService`. Channels can also be composed per-user at runtime (e.g., read from user preferences) instead of being baked into a class hierarchy.

**Why this matters:** This is the classic "favor composition over inheritance" principle in action. Inheritance models an **is-a** relationship and is best for a genuinely stable hierarchy; composition models **has-a**/**uses-a** and is better whenever behavior needs to vary independently or be swapped/combined at runtime — which is exactly the shape of a multi-channel delivery problem. It also keeps each class's responsibility narrow (Single Responsibility Principle): `NotificationService` orchestrates, each `Notifier` only knows how to deliver.

### 3. Computer Architecture (Comparison)

Compare **RISC** (Reduced Instruction Set Computer) and **CISC** (Complex Instruction Set Computer) processor architectures. What are the key design-philosophy differences, and what tradeoffs do they produce in practice?

**Answer:**

| Aspect | RISC | CISC |
|---|---|---|
| Instruction set size | Small, simple instruction set — each instruction does one basic operation. | Large, rich instruction set — single instructions can do multi-step operations (e.g., load-modify-store in one instruction). |
| Instruction complexity | Fixed-length, simple instructions, mostly register-to-register operations. | Variable-length instructions, many addressing modes, instructions can directly operate on memory. |
| Cycles per instruction | Designed so most instructions execute in **one clock cycle**. | Instructions often take **multiple cycles**, since one instruction may internally perform several micro-operations. |
| Code density | Lower — a complex task may need several simple instructions, so compiled programs are larger. | Higher — a single powerful instruction can replace several RISC instructions. |
| Compiler vs hardware complexity | More work shifted to the **compiler** (it must sequence several simple instructions to express complex operations); hardware/control logic is simpler. | More work built into **hardware** (microcode decodes complex instructions); compiler can emit fewer, denser instructions. |
| Pipelining | Simple, uniform instructions pipeline very cleanly — a major reason RISC designs favor deep, efficient pipelines. | Variable-length, variable-cycle instructions make pipelining harder (though modern x86 chips work around this, see below). |
| Power/die efficiency | Simpler decode logic → generally better performance-per-watt, which is why RISC (ARM) dominates mobile/embedded. | Historically more power-hungry decode/control logic, though modern CISC chips mitigate this heavily (see below). |
| Real-world examples | ARM, RISC-V, older MIPS/SPARC. | x86/x86-64 (Intel, AMD). |

**The modern nuance:** Pure RISC vs. CISC is now more of a historical/ISA-level distinction than a strict hardware reality. Modern x86 (CISC) CPUs internally **decode complex instructions into simpler RISC-like micro-ops** before executing them on a RISC-style pipelined, out-of-order execution core — so the performance gap at the hardware level has narrowed considerably. What persists is the **instruction set philosophy** exposed to the compiler/programmer: x86 still exposes complex, variable-length instructions and many addressing modes, while ARM/RISC-V expose a small, fixed-length, uniform instruction set.

**Why this matters:** This tradeoff — hardware simplicity and pipelining efficiency (RISC) vs. code density and historically easier hand-written assembly (CISC) — is a recurring theme in architecture interviews because it explains real industry splits: ARM's dominance in power-constrained mobile/embedded devices versus x86's entrenched position in desktops/servers where raw performance and legacy software compatibility matter more than power efficiency, and it sets up the discussion of why Apple Silicon (ARM-based) achieves strong performance-per-watt compared to traditional x86 laptop chips.
