### Question: Maximum XOR of Two Numbers in an Array (Bit Manipulation — Hard)

Given an integer array `nums`, return the **maximum result** of `nums[i] XOR nums[j]`, where `0 <= i <= j < nums.length`.

**Input format:**
- An integer array `nums` of length `n`.

**Output format:**
- A single integer: the maximum possible value of `nums[i] XOR nums[j]` over all valid pairs.

**Worked Examples:**

1. `nums = [3,10,5,25,2,8]` → Output: `28` (`5 XOR 25 = 28`).
2. `nums = [14,70,53,83,49,91,36,80,92,51,66,70]` → Output: `127` (`83 XOR 92 = 127`).
3. `nums = [0,0]` → Output: `0` (every pair XORs to `0`).

**Constraints:**
- `1 <= nums.length <= 2 * 10^5`
- `0 <= nums[i] <= 2^31 - 1`

---

### Step-by-Step Walkthrough

**Approach — Bitwise Trie (Binary Trie over bit representations)**

The brute-force approach checks every pair, giving `O(n^2)` — too slow for `n` up to `2*10^5`. To do better, think about how XOR is maximized: for two numbers, the result is largest when their bits differ as much as possible, starting from the **most significant bit**. This greedy, bit-by-bit structure is exactly what a **binary trie** built over the bit representations of the numbers lets us exploit.

1. **Build a trie of bits.** For each number in `nums`, insert it into a trie bit by bit, from the most significant bit (say bit 31, since values fit in 32-bit unsigned range) down to bit 0. Each trie node has at most two children: `0` and `1`.

2. **For each number, greedily find its best XOR partner.** Walk the trie again for each `num`, and at each bit position, look at the bit `b` of `num`. To maximize XOR at this bit, we *want* to step into the child representing `1 - b` (the opposite bit), because that bit position of the XOR would then become `1`, which is more valuable than any combination of lower bits. If that opposite child exists in the trie, go there; otherwise we're forced to take the same-bit child. Accumulate the resulting XOR bit by bit.

3. **Track the maximum** of these per-number best-partner XOR values across all numbers; that is the answer.

**Why it works:** XOR comparisons are lexicographic from the most significant bit down — a `1` at a higher bit position always beats any arrangement of lower bits. By greedily preferring the opposite bit at every trie level (when available), we are guaranteed to construct, for each number, the maximum XOR achievable with *some* other number in the array. Taking the max over all numbers then gives the global maximum pair. Because every number is inserted into the trie before any lookups begin (or we simply allow self-pairs, since `i <= j` permits `i == j`, so pairing a number against itself is a valid lower bound), every lookup always finds a valid partner.

**Complexity Analysis:**
- **Time complexity:** `O(n * L)`, where `L` is the number of bits per number (here `L = 32`), since we insert each number once (`O(L)`) and query each number once (`O(L)`). This is effectively `O(n)` for fixed-width integers.
- **Space complexity:** `O(n * L)` in the worst case for the trie nodes (at most `2nL` nodes), i.e., `O(n)` for fixed-width integers.

---

### C++ Code

```cpp
#include <vector>
#include <iostream>
#include <algorithm>
using namespace std;

// Binary trie node: children[0] = bit 0 branch, children[1] = bit 1 branch.
struct TrieNode {
    TrieNode* children[2] = {nullptr, nullptr};
};

class Solution {
    static const int BITS = 31; // highest bit index we care about (values < 2^31)

    TrieNode* root;

    // Insert the bits of 'num' into the trie, from most significant to least.
    void insert(int num) {
        TrieNode* node = root;
        for (int i = BITS; i >= 0; --i) {
            int bit = (num >> i) & 1;
            if (!node->children[bit]) {
                node->children[bit] = new TrieNode();
            }
            node = node->children[bit];
        }
    }

    // Find the maximum XOR achievable between 'num' and any number already in the trie.
    int queryMaxXor(int num) {
        TrieNode* node = root;
        int result = 0;
        for (int i = BITS; i >= 0; --i) {
            int bit = (num >> i) & 1;
            int wantedBit = 1 - bit; // opposite bit maximizes this position of the XOR
            if (node->children[wantedBit]) {
                result |= (1 << i);
                node = node->children[wantedBit];
            } else {
                // Forced to go down the same-bit branch (always exists, since every
                // number inserted shares a path at least with itself).
                node = node->children[bit];
            }
        }
        return result;
    }

public:
    int findMaximumXOR(vector<int>& nums) {
        root = new TrieNode();

        // Insert all numbers first so every query can find a valid partner
        // (including pairing a number with itself, which satisfies i <= j).
        for (int num : nums) {
            insert(num);
        }

        int best = 0;
        for (int num : nums) {
            best = max(best, queryMaxXor(num));
        }
        return best;
    }
};

int main() {
    Solution sol;

    vector<int> nums1 = {3, 10, 5, 25, 2, 8};
    cout << "findMaximumXOR([3,10,5,25,2,8]) = " << sol.findMaximumXOR(nums1) << " (expected 28)" << endl;

    vector<int> nums2 = {14, 70, 53, 83, 49, 91, 36, 80, 92, 51, 66, 70};
    cout << "findMaximumXOR([...]) = " << sol.findMaximumXOR(nums2) << " (expected 127)" << endl;

    vector<int> nums3 = {0, 0};
    cout << "findMaximumXOR([0,0]) = " << sol.findMaximumXOR(nums3) << " (expected 0)" << endl;

    return 0;
}
```

**Trace against the examples:**
- `nums = [3,10,5,25,2,8]`: `5 = 00101`, `25 = 11001`. At the top bit where they differ, the trie-guided walk for `5` greedily steers toward branches holding `25`'s opposite bits, accumulating `5 XOR 25 = 00101 ^ 11001 = 11100 = 28`. No other pair beats this, so the max over all numbers is `28`. ✓
- `nums = [14,70,...,92,...]`: the greedy walk for `83` (`1010011`) finds `92` (`1011100`) as its best opposite-bit partner, giving `83 XOR 92 = 127` (`1111111`), which is also the maximum found across all numbers (since `127` is the max possible for 7-bit values here). ✓
- `nums = [0,0]`: only one distinct value is ever inserted, so every query is forced down the same-bit (`0`) branch at every level, producing `0 XOR 0 = 0`. ✓

## CS Fundamentals

### 1. Operating Systems (Conceptual/Definition)

What is **thrashing** in the context of virtual memory management? Explain why it happens and how an operating system can detect and recover from it.

**Answer:**

**Thrashing** is a condition where a system spends the vast majority of its time servicing **page faults** (swapping pages between RAM and disk) rather than executing actual process instructions, causing CPU utilization and overall throughput to collapse even though the system is extremely "busy."

**Why it happens:** Thrashing arises when the combined **working set** (the set of pages a process actively needs in a given time window) of all currently-running processes exceeds the amount of physical memory (RAM) available to hold them. When memory is over-committed like this:
1. A process touches a page not currently in RAM → page fault → OS evicts some other page to make room and loads the needed one from disk.
2. But because memory is so tight, the page just evicted is often one that will be needed again very soon (sometimes by the very next instruction of another process), triggering another fault.
3. This creates a vicious cycle: more processes competing for too little RAM leads to more page faults, which consumes more CPU and I/O time on swapping, which leaves even less effective capacity, causing yet more faults.

Degree of multiprogramming is the classic trigger: as the OS admits more processes to improve CPU utilization, at some point the combined working sets overflow RAM, and throughput — instead of continuing to rise — suddenly drops off a cliff.

**Detection:** The OS can monitor the **page-fault rate** (faults per unit time) relative to CPU utilization. A hallmark signature of thrashing is CPU utilization dropping sharply *while* the page-fault rate is climbing — in a healthy system, CPU utilization and fault rate both increase together with load up to a point, but in thrashing, CPU utilization crashes even as faults keep rising, because the CPU is now idle waiting on disk I/O almost constantly.

**Recovery / Mitigation:**
- **Working-set model:** Track each process's working set size and ensure it is guaranteed its working set in RAM before being scheduled; if total demand exceeds RAM, suspend (swap out entirely) one or more processes rather than letting all of them starve for pages.
- **Reduce the degree of multiprogramming:** Temporarily suspend or kill some processes so the remaining ones' working sets fit comfortably in RAM.
- **Local vs. global page replacement:** Use a replacement policy that only evicts pages belonging to the faulting process itself (local), so one memory-hungry process cannot starve others and spread thrashing system-wide.
- **PFF (Page-Fault Frequency) control:** Set upper and lower bounds on a process's allowed fault rate; if the rate goes above the upper bound, give the process more frames; if well below the lower bound, take some frames away (and redistribute or admit more processes).

**Why it matters:** Thrashing is the classic illustration of why simply adding more processes (or increasing concurrency) does not monotonically improve throughput — system designers must size memory and admission control around *working sets*, not just raw process counts, or performance degrades catastrophically rather than gracefully.

### 2. DBMS (Scenario/Applied)

You are designing a banking application where two concurrent transactions both try to transfer money out of the *same* account at nearly the same instant. Explain, step by step, how the database should use **transactions and locking (or an equivalent concurrency-control mechanism)** to guarantee the account balance never goes negative or becomes inconsistent, and relate this to the relevant **ACID** property.

**Answer:**

**The scenario:** Suppose `Account A` has a balance of `100`. `Transaction T1` tries to withdraw `80`, and `Transaction T2` tries to withdraw `50`, submitted almost simultaneously. If both transactions read the balance (`100`) before either writes back its result, each might independently conclude the withdrawal is valid (`80 <= 100` and `50 <= 100`), and both could commit — leaving the account at `-30`, violating the business rule that balance must stay `>= 0`. This is a classic **lost update / read-write race**.

**Step-by-step fix using locking:**

1. **Begin transaction (T1):** `BEGIN TRANSACTION;`
2. **Acquire an exclusive (write) lock on Account A's row:** typically via `SELECT balance FROM accounts WHERE id = 'A' FOR UPDATE;` — this tells the database engine "I intend to modify this row; block any other transaction that wants to read-for-update or write it until I'm done."
3. **T1 reads balance = 100, checks `100 - 80 >= 0`,** which holds, so it proceeds: `UPDATE accounts SET balance = balance - 80 WHERE id = 'A';`
4. **Meanwhile, T2 tries to acquire the same exclusive lock** (via its own `FOR UPDATE` read or simply its `UPDATE` statement) and is **blocked** — the database makes T2 wait rather than letting it read a stale balance.
5. **T1 commits:** `COMMIT;` — this releases T1's lock and durably persists `balance = 20`.
6. **T2's lock request is now granted.** It (re-)reads the *current* balance, which is now `20` (not the stale `100`), checks `20 - 50 >= 0`, which **fails**, so T2's application logic rejects the withdrawal (or the transaction rolls back) instead of allowing the balance to go negative.

**Relating this to ACID:**
- This mechanism is fundamentally about **Isolation** — the "I" in ACID — which guarantees that concurrently executing transactions do not see each other's intermediate, uncommitted state and that the net effect is *as if* the transactions ran one after another (serializably), even though they physically overlapped in time. Locking is one classic mechanism (alongside optimistic concurrency control / MVCC with validation) used to enforce isolation.
- **Atomicity** also matters here: each transaction's read-check-write sequence must be all-or-nothing — if T1 crashed after decrementing the balance but before committing, the database must roll the whole operation back rather than leaving a partially-applied debit.
- **Consistency** is the business invariant being protected (`balance >= 0`); isolation and atomicity are the mechanisms that let the application-level consistency check (`if balance >= amount`) actually be trustworthy under concurrency.

**Why it matters:** Without correct isolation (via locking, MVCC with proper isolation levels, or equivalent), "check-then-act" logic like a withdrawal is inherently racy under concurrency — the check and the act must be made effectively atomic with respect to other transactions, which is precisely what transactional concurrency control exists to guarantee.

### 3. System Design Basics (Comparison)

Compare **vertical scaling** and **horizontal scaling** as strategies for handling increased load on a backend system. What are the trade-offs, and what architectural changes does horizontal scaling typically require that vertical scaling does not?

**Answer:**

| Aspect | Vertical Scaling ("scale up") | Horizontal Scaling ("scale out") |
|---|---|---|
| Definition | Increase the capacity of a single machine — more CPU cores, more RAM, faster disks/SSDs. | Add more machines (nodes/instances) running the same software, and distribute load across them. |
| Implementation effort | Usually simple — often just resizing a VM/instance or buying bigger hardware; application code frequently needs no changes. | Requires the application to be designed (or re-designed) to run as multiple cooperating instances. |
| Upper limit | Hard ceiling — there is a maximum machine size available at any point in time (and it's expensive near the top end). | In principle near-unlimited — you can keep adding commodity machines. |
| Single point of failure | Yes — if that one machine goes down, the whole service goes down. | No (if designed correctly) — other nodes keep serving while one is replaced/healed. |
| Cost curve | Tends to get disproportionately expensive at the high end (bigger machines cost more than linearly more). | Tends to scale more linearly in cost using commodity hardware, though with added operational overhead. |
| Downtime for scaling | Often requires a reboot or brief downtime to resize. | New nodes can usually be added/removed with zero downtime. |

**Architectural changes horizontal scaling typically requires (that vertical scaling does not):**

1. **Load balancing:** A load balancer (e.g., round-robin, least-connections, or consistent hashing) must sit in front of the fleet to distribute incoming requests across nodes — a single machine needs no such component.
2. **Statelessness (or externalized state):** Each application server instance should ideally be **stateless** — e.g., not keep user session data only in its own local memory — because any request might be routed to any node. This usually means moving session/state into a shared store (e.g., Redis, a database) rather than in-process memory.
3. **Data layer scaling:** The database itself often becomes the new bottleneck, requiring techniques like **read replicas**, **sharding/partitioning**, or caching layers (e.g., a CDN or Redis cache) — vertical scaling of a single app server doesn't force these changes on the data layer in the same way.
4. **Service discovery / health checks:** The system needs a mechanism for the load balancer (or orchestrator) to know which nodes are healthy and currently in the pool, and to add/remove nodes dynamically (e.g., via Kubernetes, an autoscaling group, or a service mesh).
5. **Distributed consistency and coordination:** Any cross-node coordination (e.g., rate limiting, distributed locks, leader election for background jobs) now needs explicit handling, since you no longer have a single process's in-memory state as a natural source of truth.

**When to choose which:** Vertical scaling is simpler and often the right first step for moderate load growth or when the bottleneck is genuinely CPU/RAM-bound on a single workload that's hard to parallelize. Horizontal scaling is the right long-term strategy for systems that need high availability, need to scale well beyond what any single machine can offer, and are built (or can be refactored) around stateless, independently-deployable units of work.
