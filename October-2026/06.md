### Question: Longest Palindromic Substring (Strings — Medium)

Given a string `s`, return the longest substring of `s` that is a palindrome (reads the same forwards and backwards).

If there are multiple longest palindromic substrings of the same maximum length, you may return any one of them.

**Input format:**
- A single string `s` consisting of digits and/or English letters.

**Output format:**
- A string: the longest palindromic substring found in `s`.

**Worked Examples:**

1. `s = "babad"` → Output: `"bab"` (or `"aba"` — both are valid length-3 palindromes).
2. `s = "cbbd"` → Output: `"bb"`.
3. `s = "a"` → Output: `"a"` (a single character is trivially a palindrome).

**Constraints:**
- `1 <= s.length <= 1000`
- `s` consists of only digits and English letters (uppercase and/or lowercase).

---

### Step-by-Step Walkthrough

**Approach — Expand Around Center**

A palindrome is symmetric around its middle. There are only two kinds of "middles" a palindrome can have:
1. A single character (odd-length palindrome, e.g. `"aba"` centered at `'b'`).
2. A gap between two adjacent characters (even-length palindrome, e.g. `"bb"` centered between the two `'b'`s).

Since `s.length <= 1000`, there are at most `2n - 1` possible centers (n single-character centers + `n-1` gap centers). For each possible center, we can "expand" outward in both directions simultaneously, as long as the characters on both sides match, and track the longest palindrome found this way.

**Algorithm:**
1. For every index `i` from `0` to `n-1`, treat `i` as the center of an odd-length palindrome and expand: start with `left = i`, `right = i`, and while `left >= 0 && right < n && s[left] == s[right]`, decrement `left` and increment `right`. The palindrome found is `s[left+1 ... right-1]`.
2. Also treat the gap between `i` and `i+1` as the center of an even-length palindrome: start with `left = i`, `right = i+1`, and expand the same way.
3. After each expansion, compare the length of the palindrome found (`right - left - 1`) against the best length seen so far, and update the answer's start index and length if it's longer.
4. Return the substring defined by the best start index and length found across all `2n - 1` centers.

**Why it works:** Every palindrome, no matter its length, has exactly one center (a character, for odd length, or a gap, for even length) from which it is perfectly symmetric. By trying every possible center and greedily expanding outward as far as the palindrome property holds, we are guaranteed to discover every maximal palindromic substring in `s` — including the longest one — because expansion from the correct center always finds the *maximal* palindrome around that center (it can't be extended further once characters mismatch, and stopping early would miss a longer valid palindrome centered there).

**Complexity Analysis:**
- **Time complexity:** `O(n^2)` — there are `O(n)` centers, and each expansion can take up to `O(n)` steps in the worst case (e.g., a string of all identical characters).
- **Space complexity:** `O(1)` extra space (excluding the output string itself), since we only track indices and lengths, no auxiliary data structures like DP tables.

*(A DP table-based approach also solves this in `O(n^2)` time but uses `O(n^2)` space; expand-around-center achieves the same time complexity with constant extra space, which is why it's preferred here.)*

---

### C++ Solution

```cpp
#include <iostream>
#include <string>
using namespace std;

class Solution {
public:
    string longestPalindrome(string s) {
        int n = s.size();
        if (n < 1) return "";

        int bestStart = 0;
        int bestLen = 1; // every single character is a palindrome of length 1

        // Expands outward from (left, right) as long as characters match.
        // Returns the length of the palindrome found, and updates left/right
        // to the final (one-past-the-boundary) positions via reference.
        auto expand = [&](int left, int right) -> int {
            while (left >= 0 && right < n && s[left] == s[right]) {
                left--;
                right++;
            }
            // After the loop, the actual palindrome is s[left+1 .. right-1].
            return right - left - 1;
        };

        for (int i = 0; i < n; i++) {
            // Odd-length palindrome centered at i.
            int len1 = expand(i, i);
            if (len1 > bestLen) {
                bestLen = len1;
                bestStart = i - (len1 - 1) / 2;
            }

            // Even-length palindrome centered between i and i+1.
            int len2 = expand(i, i + 1);
            if (len2 > bestLen) {
                bestLen = len2;
                bestStart = i - (len2 / 2) + 1;
            }
        }

        return s.substr(bestStart, bestLen);
    }
};

int main() {
    Solution sol;

    // Example 1
    cout << "s = \"babad\" -> " << sol.longestPalindrome("babad")
         << " (expected \"bab\" or \"aba\")" << endl;

    // Example 2
    cout << "s = \"cbbd\" -> " << sol.longestPalindrome("cbbd")
         << " (expected \"bb\")" << endl;

    // Example 3
    cout << "s = \"a\" -> " << sol.longestPalindrome("a")
         << " (expected \"a\")" << endl;

    return 0;
}
```

**Trace against the examples:**
- `"babad"`: centers at index 1 (`'a'`) expand to `"bab"` (length 3); center at index 2 (`'b'`) expands to `"aba"` (length 3). Both are valid maximal-length answers; the algorithm returns whichever it finds first depending on iteration order (here, `"bab"`, since index 1 is checked before index 2). ✓
- `"cbbd"`: the gap-center between indices 1 and 2 (`'b'`, `'b'`) expands to `"bb"` (length 2), which beats every length-1 fallback. ✓
- `"a"`: `n = 1`, the loop runs once with `i = 0`; the odd-center expansion gives length 1 (`"a"`); the even-center expansion from `(0, 1)` immediately fails since `right = 1 >= n`, contributing length 0. Final answer is `"a"`. ✓

### 1. Computer Networks (Conceptual/Definition)

Explain what happens during DNS resolution when a browser looks up `www.example.com` for the first time (assume nothing is cached anywhere). Describe the role of each server involved.

**Answer:**

DNS (Domain Name System) resolution is the process of translating a human-readable domain name into the IP address a computer needs to actually open a network connection. With nothing cached, resolution proceeds as an iterative, hierarchical lookup:

1. **Browser → Operating System stub resolver:** The browser asks the OS's DNS resolver (stub resolver) to resolve `www.example.com`. The stub resolver typically forwards the request to a configured **recursive resolver** (e.g., the ISP's DNS server, or a public one like `8.8.8.8` or `1.1.1.1`).

2. **Recursive resolver → Root name server:** Since the recursive resolver has nothing cached, it first asks one of the 13 logical **root servers** ("."), which don't know the answer directly but know which server is responsible for the `.com` **TLD (top-level domain)**. The root server responds with a referral to the `.com` TLD name servers.

3. **Recursive resolver → TLD name server:** The resolver then asks a `.com` TLD server for `www.example.com`. The TLD server doesn't have the final answer either, but it knows which **authoritative name servers** are responsible for the `example.com` domain (these are the servers the domain's owner configured, e.g., via their registrar). It returns a referral to those.

4. **Recursive resolver → Authoritative name server:** Finally, the resolver queries the authoritative name server for `example.com`, which actually holds the DNS records for that domain (A/AAAA records mapping `www.example.com` to an IP address, among others). This server returns the actual IP address.

5. **Recursive resolver → Browser:** The recursive resolver caches the result (according to the record's TTL) and returns the IP address back up the chain to the stub resolver and finally the browser, which can now open a TCP connection to that IP.

**Why this matters:** This hierarchical, delegated design is what lets DNS scale globally — no single server needs to know every domain's IP address; responsibility is delegated level by level (root → TLD → authoritative), and caching at the recursive resolver (governed by each record's TTL) means this full chain is only walked on a true cold lookup. Understanding this flow is essential for diagnosing real-world issues like DNS propagation delay after changing a record, or why lowering a TTL before a planned IP migration reduces the window where clients see stale data.

### 2. OOP (Comparison)

Compare Abstraction and Encapsulation in Object-Oriented Programming. They're often confused — explain what distinguishes them and give a short C++ example of each.

**Answer:**

| Aspect | Abstraction | Encapsulation |
|---|---|---|
| Definition | Hiding **implementation complexity** and exposing only the essential, relevant behavior/interface to the user of a class. | Bundling data and the methods that operate on it into a single unit (a class), and **restricting direct access** to the internal state (e.g., via `private`/`protected` access modifiers). |
| Focus | *What* a thing does, not how — a design-level/conceptual concern (interface design). | *How* the data is protected and accessed — an implementation-level mechanism (access control). |
| Achieved via | Abstract classes, interfaces/pure virtual functions, or simply well-designed public APIs that hide internal logic. | Access specifiers (`private`, `protected`, `public`), getter/setter methods. |
| Analogy | A car's steering wheel and pedals let you drive without knowing how the engine or transmission works — you interact with a simplified interface. | The engine itself is sealed under the hood — you can't reach in and directly rewire its internals; you can only interact with it through the pedals the car exposes. |

**Example (C++):**

```cpp
// Abstraction: the caller only sees "connect()" and "sendData()" — 
// the actual protocol handshake details are hidden behind the interface.
class NetworkConnection {
public:
    virtual void connect() = 0;       // pure virtual -> defines *what*, not *how*
    virtual void sendData(string d) = 0;
};

// Encapsulation: the internal socket handle and connection state are
// private; outside code cannot directly manipulate them, only through
// the controlled public methods.
class TcpConnection : public NetworkConnection {
private:
    int socketHandle;       // hidden internal state
    bool isConnected;       // hidden internal state

public:
    TcpConnection() : socketHandle(-1), isConnected(false) {}

    void connect() override {
        // ... actual TCP handshake logic hidden here ...
        isConnected = true;
    }

    void sendData(string d) override {
        if (isConnected) {
            // ... actual send() syscall logic hidden here ...
        }
    }
};
```

**Why this matters:** The two work together but solve different problems: abstraction is about **interface design** (reducing cognitive load for the consumer of a class — "I just need to call `connect()`, I don't care about handshakes"), while encapsulation is about **data protection and invariant enforcement** (preventing external code from putting an object into an inconsistent state, e.g., calling `sendData()` before `isConnected` is true, by keeping that flag private and only mutable through controlled methods). You can have encapsulation without strong abstraction (a class with private fields but a messy, over-exposed API), and conceptually you can design an abstraction without encapsulation (an interface with no hidden state at all) — which is why interviewers consider them orthogonal, not synonyms.

### 3. System Design Basics (Scenario/Applied)

You're asked to design a push-notification system that can deliver notifications (e.g., "your order has shipped") to millions of mobile users, with delivery typically expected within a few seconds. Walk through your high-level design.

**Answer:**

**Step 1 — Clarify the requirement.** Backend services (order service, chat service, etc.) need to trigger notifications to specific users' devices. Scale: millions of registered devices, bursts of notifications (e.g., a flash sale alert to a large segment), and delivery latency on the order of seconds, not guaranteed real-time but "soon."

**Step 2 — Core components:**
- **Notification API / ingestion service:** Internal services call this (e.g., `POST /notify {userId, message, type}`) instead of talking to device providers directly. It validates the request and decouples callers from delivery mechanics.
- **Message queue (e.g., Kafka, SQS):** The ingestion service pushes notification requests onto a queue rather than sending synchronously. This absorbs bursts (a sudden spike of 1M notifications doesn't overwhelm downstream systems) and lets producers and consumers scale independently.
- **Device/token registry (database):** A mapping from `userId` → list of registered device tokens (one user may have multiple devices) and which **push provider** each token belongs to (APNs for iOS, FCM for Android/web). This needs to be kept up to date as users log in/out or reinstall the app (tokens can expire or rotate).
- **Worker/dispatcher pool:** Consumers that read from the queue, look up the user's device tokens in the registry, batch requests where the provider supports it, and call the appropriate external push provider (APNs/FCM) to actually deliver the notification to the device.
- **Retry & dead-letter handling:** If a provider call fails transiently (rate-limited, timeout), retry with backoff; if a token is reported invalid/expired by the provider, remove it from the registry so we stop wasting calls on it.

**Step 3 — Handle scale:**
- Partition the queue by `userId` hash (or by provider) so dispatcher workers can scale horizontally and process partitions independently.
- Batch notifications to the same provider where the provider API supports multi-token sends, reducing per-call overhead.
- Rate-limit/throttle sends per provider to respect their API quotas (APNs/FCM both impose limits), and shed or delay lower-priority notification types under extreme load rather than dropping high-priority ones (e.g., OTP/security alerts take precedence over marketing pushes).

**Step 4 — Reliability considerations:**
- Make the ingestion API idempotent (accept a client-supplied request ID) so retried calls from upstream services don't cause duplicate notifications.
- Track delivery status per notification (queued → sent → delivered/failed) in a lightweight store, so other systems can query "was this notification delivered?" if needed, and so failures are observable rather than silent.

**Why this matters:** This is a good interview scenario because it forces a candidate to recognize that direct, synchronous calls to third-party push providers don't scale or tolerate bursts — introducing a queue to decouple ingestion from delivery, horizontally scaling stateless workers behind it, and handling the device-token lifecycle (registration, rotation, invalidation) are the key design moves that come up repeatedly across many "fan-out" style systems (email digests, SMS alerts, webhooks), not just push notifications specifically.
