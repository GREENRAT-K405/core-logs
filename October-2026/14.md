### Question: LFU Cache (Hashing/Maps — Hard)

Design and implement a **Least Frequently Used (LFU) cache** with a fixed capacity. It should support two operations, each in **O(1)** average time:

- `LFUCache(int capacity)` — initializes the cache with positive size `capacity`.
- `int get(int key)` — returns the value of `key` if it exists in the cache, otherwise returns `-1`. Accessing a key counts as a "use" and increases its usage frequency by 1.
- `void put(int key, int value)` — updates the value of `key` if present (and increases its frequency), otherwise inserts the `(key, value)` pair. If inserting a new key exceeds the cache's `capacity`, it should **invict the least frequently used key** first. If there is a **tie in frequency**, the **least recently used** key among that tie should be evicted.

**Input format:** a sequence of constructor/`put`/`get` calls (as in the LeetCode-style driver below).
**Output format:** the return value of each `get` call (`put` and the constructor return nothing).

**Example 1:**
```
LFUCache cache = new LFUCache(2);
cache.put(1, 1);   // cache={1=1}, freq={1:1}
cache.put(2, 2);   // cache={1=1, 2=2}, freq={1:1, 2:1}
cache.get(1);       // returns 1, freq={1:2, 2:1}
cache.put(3, 3);   // capacity full. key 2 has freq 1 (the minimum), so it is evicted.
                    // cache={1=1, 3=3}, freq={1:2, 3:1}
cache.get(2);       // returns -1 (not found)
cache.get(3);       // returns 3, freq={1:2, 3:2}
cache.put(4, 4);   // capacity full. keys 1 and 3 are tied at freq 2 — 1 is evicted
                    // because it was used less recently than 3.
                    // cache={3=3, 4=4}, freq={3:2, 4:1}
cache.get(1);       // returns -1 (evicted)
cache.get(3);       // returns 3
cache.get(4);       // returns 4
```

**Example 2:**
```
LFUCache cache = new LFUCache(0);
cache.put(0, 0);   // capacity is 0, so nothing is ever stored
cache.get(0);       // returns -1
```

**Constraints:**
- `0 <= capacity <= 10^4`
- `0 <= key <= 10^5`
- `0 <= value <= 10^9`
- At most `2 * 10^5` calls will be made to `get` and `put` combined.

### Step-by-Step Walkthrough

**Why a plain hash map isn't enough.** A hash map alone gives O(1) lookup, but eviction requires knowing *which* key has the lowest frequency, and breaking ties requires knowing recency *within* that frequency. Scanning all keys to find the minimum frequency on every `put` would cost O(n), so we need auxiliary structures that keep "current minimum frequency" and "recency order within a frequency" both available in O(1).

**The key insight — bucket by frequency.** Group all keys that currently have the *same* access frequency into their own doubly-linked list, ordered by recency (most-recently-used at the front, least-recently-used at the back). Within one of these buckets, eviction is now just "pop the back of the list" — O(1). We only need two maps plus one integer:

- `freqMap[f]`: a doubly-linked list (`std::list<Node>`) holding all keys currently at frequency `f`, most-recently-used first.
- `keyIter[key]`: an iterator directly into the node for `key` inside whichever `freqMap[f]` list currently holds it — this is what makes "find this key's node" O(1) instead of a list scan.
- `minFreq`: the smallest frequency that currently has at least one key in it — this is exactly the bucket we evict from.

**`get(key)`:**
1. If `key` isn't in `keyIter`, return `-1`.
2. Otherwise, look up its node via the iterator, remove it from `freqMap[oldFreq]` (O(1) list erase using the stored iterator — no scan needed), and if that bucket becomes empty, erase the bucket and bump `minFreq` if it was the bucket we just emptied (since the key we just touched can't have been the *only* representative of the old minimum unless it's now gone).
3. Re-insert the node at the **front** of `freqMap[oldFreq + 1]` (marks it as most-recently-used at its new frequency) and refresh `keyIter[key]` to the new iterator.
4. Return the value.

**`put(key, value)`:**
1. If `capacity == 0`, do nothing.
2. If `key` already exists: update its stored value, then run the exact same "move to `freq+1`, update `minFreq`" logic as `get`.
3. If `key` is new and the cache is at capacity: evict the **back** element of `freqMap[minFreq]` (least-recently-used among the least-frequent keys) — this is where the tie-breaking rule is enforced for free, since the list is already recency-ordered. Erase that key from `keyIter` and, if the bucket is now empty, from `freqMap`.
4. Insert the new key at the front of `freqMap[1]` (every new key starts at frequency 1) and set `minFreq = 1` (a freshly-inserted key is always now the minimum).

**Why this is O(1).** Every step above is a constant number of hash-map lookups/inserts plus a constant number of doubly-linked-list operations (`push_front`, `pop_back`, iterator-based `erase`) — none of them scan a list or a map. `minFreq` is maintained incrementally rather than recomputed, so it never costs more than O(1) to read or update.

**Complexity.** Both `get` and `put` run in **O(1)** average time. Space is **O(capacity)** for the key→node and frequency→bucket structures.

### C++ Code

```cpp
#include <unordered_map>
#include <list>
using namespace std;

class LFUCache {
    struct Node {
        int key, value, freq;
    };

    int capacity;
    int minFreq;
    unordered_map<int, list<Node>> freqMap;                  // frequency -> MRU...LRU list of nodes
    unordered_map<int, list<Node>::iterator> keyIter;         // key -> iterator into its node in freqMap

    // Moves the node for `key` (currently at its old frequency) to the next
    // frequency bucket, placing it at the front (most-recently-used slot).
    void touch(int key) {
        auto it = keyIter[key];
        Node node = *it;
        int oldFreq = node.freq;

        freqMap[oldFreq].erase(it);
        if (freqMap[oldFreq].empty()) {
            freqMap.erase(oldFreq);
            if (minFreq == oldFreq) minFreq++;
        }

        node.freq++;
        freqMap[node.freq].push_front(node);
        keyIter[key] = freqMap[node.freq].begin();
    }

public:
    LFUCache(int capacity) : capacity(capacity), minFreq(0) {}

    int get(int key) {
        if (capacity == 0 || keyIter.find(key) == keyIter.end()) return -1;
        int value = keyIter[key]->value;
        touch(key);
        return value;
    }

    void put(int key, int value) {
        if (capacity == 0) return;

        if (keyIter.find(key) != keyIter.end()) {
            // Update the value in place, then bump its frequency like a get().
            keyIter[key]->value = value;
            touch(key);
            return;
        }

        if ((int)keyIter.size() >= capacity) {
            // Evict the least-recently-used node among the least-frequent bucket.
            auto& lruList = freqMap[minFreq];
            int evictKey = lruList.back().key;
            lruList.pop_back();
            if (lruList.empty()) freqMap.erase(minFreq);
            keyIter.erase(evictKey);
        }

        Node node{key, value, 1};
        freqMap[1].push_front(node);
        keyIter[key] = freqMap[1].begin();
        minFreq = 1;
    }
};
```

Traced against Example 1: after the sequence of calls, `get(2)` returns `-1` (evicted for low frequency), `get(1)` later returns `-1` (evicted as the LRU key among the freq-2 tie with key 3), and `get(3)` / `get(4)` return `3` and `4` respectively — matching the expected trace. Example 2 (`capacity = 0`) short-circuits every call to a no-op / `-1`, as required.

### 1. Operating Systems (Conceptual)

What is a race condition? Explain how a mutex prevents one, and how a mutex differs from a semaphore.

**Answer:**

A **race condition** occurs when two or more threads/processes access shared data concurrently, and the final outcome depends on the unpredictable timing/interleaving of their execution — rather than being deterministic. The classic example is `counter++` on a shared integer: this is really three steps (read `counter`, add 1, write back), and if two threads interleave those steps, one increment can be silently lost (e.g., both threads read `counter = 5`, both compute `6`, both write `6` — the net effect is `+1` instead of `+2`).

A **mutex (mutual exclusion lock)** prevents this by guaranteeing that only one thread at a time can hold the lock and execute the protected "critical section." Any other thread calling `lock()` blocks until the holder calls `unlock()`. By wrapping the read-modify-write sequence in `lock()`/`unlock()`, the three steps become atomic with respect to other threads — no interleaving is possible, so the lost-update race condition disappears.

**Mutex vs. semaphore:**
- A mutex is a **binary** lock with a notion of **ownership** — conceptually it has exactly two states (locked/unlocked), and in most implementations only the thread that locked it is allowed to unlock it. Its sole purpose is mutual exclusion over a critical section.
- A semaphore holds an **integer count** and has no ownership concept — `wait()`/`signal()` (a.k.a. `acquire()`/`release()`) decrement/increment the count, and any thread can call either operation (not just the one that last decremented it). A semaphore initialized to 1 can behave like a mutex, but semaphores are more general: a counting semaphore initialized to `N` can let up to `N` threads into a section concurrently, which makes it the right tool for **resource-pool limiting** (e.g., allowing at most 5 concurrent connections to a database) rather than strict single-thread exclusion.

In short: reach for a mutex when exactly one thread should hold a resource at a time and you want ownership semantics; reach for a semaphore when you need to control concurrent access to a pool of `N` interchangeable resources, or when signaling needs to happen from a different thread than the one that waited.

### 2. System Design Basics (Scenario)

You're asked to design a URL-shortening service (like bit.ly) that must handle a 100:1 read-to-write ratio and generate unique short codes for hundreds of millions of URLs. How would you generate the short codes, and how would you architect the read path for low latency at scale?

**Answer:**

**Short-code generation.** The two common approaches are hashing and counter-based encoding:
- *Hashing the long URL* (e.g., MD5/SHA-256 truncated to 6-7 characters, base62-encoded) is simple but requires a **collision-check step**: two different URLs can truncate to the same short code, so you must check the datastore for the code before committing, and retry with a different slice/salt on collision — this adds a read-before-write and doesn't scale perfectly cleanly under high write concurrency.
- *Counter-based generation* avoids collisions entirely: maintain a globally unique, monotonically increasing ID (e.g., from a dedicated ID-generation service, a database auto-increment sequence, or a Twitter-Snowflake-style distributed ID generator), then **base62-encode** that integer directly into the short code (base62 because it's URL-safe and compact — a 62^6 ≈ 56 billion address space from just 6 characters). This is deterministic, requires no collision retries, and is the generally preferred approach at scale. To avoid a single counter becoming a write bottleneck/single point of failure, pre-allocate counter *ranges* to each application server (e.g., server A gets IDs 1-1,000,000, server B gets 1,000,001-2,000,000) so each server can mint new IDs locally without contending on a shared counter for every request.

**Read-path architecture.** Since reads (redirects) outnumber writes 100:1, the read path is what must be optimized:
- Put a **cache (Redis/Memcached) in front of the database**, keyed by short code, storing the long-URL mapping. Since short URLs are immutable once created (a given code always maps to the same long URL), cache entries never need invalidation on write — only population on first miss (cache-aside pattern) — which makes caching unusually effective here.
- Use a **CDN or edge-level redirect cache** for extremely hot links (e.g., a viral link), since an HTTP 301/302 redirect response is tiny and highly cacheable.
- **Shard/partition the database** by short code (e.g., consistent hashing on the code) so no single database node becomes a hotspot as the dataset grows into the hundreds of millions of rows, and so reads scale horizontally by adding more shards/replicas.
- Use **read replicas** of the backing datastore for the (already cache-reduced) fraction of reads that miss the cache, keeping the single primary free to focus on handling writes.

The core design principle: because the workload is overwhelmingly read-heavy and the data is immutable per key, push as much of the read traffic as possible into cheap, cache-friendly layers (CDN -> in-memory cache -> read replica) and reserve the primary datastore almost entirely for the comparatively rare write path.

### 3. Computer Architecture (Comparison)

Compare row-major and column-major traversal of a 2D array in terms of CPU cache behavior, and explain why one is typically much faster than the other for the same logical access pattern.

**Answer:**

In a language like C/C++, a 2D array (e.g., `int arr[rows][cols]`) is stored **row-major** in memory: all elements of row 0 are laid out contiguously, followed by all elements of row 1, and so on. This is a layout fact, independent of how you choose to traverse it.

**Row-major traversal** (outer loop over rows, inner loop over columns — `for (i) for (j) arr[i][j]`) accesses memory in the same order it is physically laid out: sequentially, address by address. This interacts very well with the CPU's **cache line** mechanism — when the CPU fetches `arr[i][j]` from main memory, it doesn't fetch just that one integer; it pulls in an entire cache line (typically 64 bytes, e.g., 16 consecutive `int`s) into L1 cache. Because row-major traversal's very next accesses (`arr[i][j+1]`, `arr[i][j+2]`, ...) are exactly those neighboring addresses, they are served as **cache hits** from the line already fetched — no extra trip to main memory needed. This is known as good **spatial locality**.

**Column-major traversal** of the same row-major-stored array (`for (j) for (i) arr[i][j]`) jumps by an entire row's width (`cols` elements) on every single access. Each such access lands in a completely different cache line (since the previous line's other 15 elements, fetched "for free," are never used before being evicted), so almost every access is a **cache miss**, forcing a trip to main memory (or at best a slower L2/L3 lookup) on nearly every iteration.

The performance gap can be dramatic — often 5-10x+ slower for column-major traversal on large arrays, purely from memory-access pattern, with **zero change in the number of logical operations performed**. This is a key reason why "the algorithm's big-O complexity is the same" does not imply "the two implementations run at the same speed" — real hardware has a deep memory hierarchy (registers -> L1 -> L2 -> L3 -> RAM), and an access pattern that respects locality (both **spatial locality**, as here, and **temporal locality**, reusing recently accessed data) can be an order of magnitude faster than one that doesn't, even though both do the exact same asymptotic amount of "work."
