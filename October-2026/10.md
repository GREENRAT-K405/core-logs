## DSA

### Question: 3Sum (Arrays — Medium)

**Problem Statement**

Given an integer array `nums`, return all the triplets `[nums[i], nums[j], nums[k]]` such that `i != j`, `i != k`, `j != k`, and `nums[i] + nums[j] + nums[k] == 0`. The solution set must not contain duplicate triplets (as sets of values — order within a triplet, and order of the triplets, does not matter).

**Input/Output Format**

- Input: an integer array `nums`.
- Output: a list of integer triplets, each summing to zero, with no duplicate triplet repeated.

**Examples**

1. Input: `nums = [-1, 0, 1, 2, -1, -4]` → Output: `[[-1, -1, 2], [-1, 0, 1]]`. Both triplets sum to `0`; no other combination of three distinct indices does, and the duplicate `-1` values don't produce a repeated triplet.
2. Input: `nums = [0, 1, 1]` → Output: `[]`. The only triplet available is `(0, 1, 1)`, which sums to `2`, not `0`.
3. Input: `nums = [0, 0, 0]` → Output: `[[0, 0, 0]]`. There is exactly one triplet of indices, and it happens to sum to zero.

**Constraints**

- `3 <= nums.length <= 3000`
- `-10^5 <= nums[i] <= 10^5`
- Aim for O(n^2) time, better than the brute-force O(n^3).

### Step-by-Step Walkthrough

**The brute-force approach first.** Try every triplet of indices `(i, j, k)` and check if they sum to zero, using a set to dedupe the sorted triplet values. That's O(n^3) time just to enumerate triplets, plus the cost of deduping. With `n` up to 3000, that's up to ~2.7 * 10^10 combinations — far too slow. We need to cut one whole dimension of the search.

**Key insight.** Once the array is **sorted**, the inner "find two numbers that sum to a target" step no longer needs a nested loop — it can be done with a two-pointer sweep in O(n), because in a sorted array, moving a left pointer right only increases the pair sum, and moving a right pointer left only decreases it. That turns the O(n^2) inner search for a pair into O(n), bringing the whole problem down to O(n^2) total.

So the algorithm is: fix one element as an "anchor," then use two pointers to find all pairs among the remaining elements that sum to `-anchor`.

1. **Sort `nums`.** This is what makes two-pointer search possible, and it also makes duplicate-skipping trivial (equal values end up adjacent).
2. **Iterate `i` from `0` to `n - 3`** as the anchor.
   - **Skip duplicate anchors**: if `nums[i] == nums[i-1]`, skip — any triplet starting with this value was already found in the previous iteration.
   - **Early exit**: since the array is sorted, if `nums[i] > 0`, then `nums[i]` plus two numbers that come after it (which are `>= nums[i] > 0`) can never sum to zero — so no later `i` can work either. Break entirely.
   - Set `left = i + 1`, `right = n - 1`, and look for a pair summing to `-nums[i]`:
     - If `nums[i] + nums[left] + nums[right] == 0`: record the triplet, then advance both pointers inward — and additionally skip over any further duplicates of `nums[left]` and `nums[right]` so the same pair isn't recorded twice.
     - If the sum is negative: the total is too small, so move `left` rightward to increase it.
     - If the sum is positive: the total is too large, so move `right` leftward to decrease it.
   - Continue until `left` meets `right`.

**Why it's correct.** For a fixed anchor, the two-pointer sweep examines every pair `(left, right)` with `left < right` implicitly: it never skips a pair that could be the answer, because the sum is monotonic in each pointer's direction — if the current sum is too low, *no* pair with a smaller `right` or the same `left` could have fixed it except by increasing `left`, and symmetrically for too-high sums. Duplicate skipping at both the anchor level and the pair level guarantees each distinct triplet of *values* is emitted exactly once, since sorting groups equal values together.

**Complexity.**
- Time: O(n^2) — O(n log n) to sort, then O(n) anchors each doing an O(n) two-pointer sweep.
- Space: O(1) extra (sorting can be done in place, ignoring the output list itself; sorting algorithms may use O(log n) stack space internally).

### C++ Code

```cpp
#include <vector>
#include <algorithm>
using namespace std;

vector<vector<int>> threeSum(vector<int>& nums) {
    vector<vector<int>> result;
    sort(nums.begin(), nums.end());
    int n = (int)nums.size();

    for (int i = 0; i < n - 2; i++) {
        // Skip duplicate anchors: this value already produced every
        // triplet it can in a previous iteration.
        if (i > 0 && nums[i] == nums[i - 1]) continue;

        // Sorted array: once the anchor itself is positive, the two
        // numbers after it (both >= nums[i]) can never bring the sum
        // back down to zero. No later i can succeed either.
        if (nums[i] > 0) break;

        int left = i + 1, right = n - 1;
        while (left < right) {
            // Use a wider type to avoid any overflow risk when summing.
            long long sum = (long long)nums[i] + nums[left] + nums[right];

            if (sum == 0) {
                result.push_back({nums[i], nums[left], nums[right]});
                left++;
                right--;
                // Skip duplicate values on both sides to avoid
                // recording the same triplet more than once.
                while (left < right && nums[left] == nums[left - 1]) left++;
                while (left < right && nums[right] == nums[right + 1]) right--;
            } else if (sum < 0) {
                left++;  // sum too small, grow it
            } else {
                right--; // sum too large, shrink it
            }
        }
    }

    return result;
}
```

## CS Fundamentals

### 1. System Design Basics (Scenario/Applied)

You are asked to design a URL shortener (like `bit.ly`): given a long URL, produce a short code such as `abc123` that redirects to it. How would you generate the short codes so they stay unique at scale, and how do reads vs. writes shape the storage design?

**Answer:**

**Generating the short code.** There are two broad strategies:

1. **Hash-based**: hash the long URL (e.g., MD5/SHA-256), take the first 6-7 characters of a base62 (`[a-zA-Z0-9]`) encoding of that hash. Problem: different URLs can collide on a truncated hash, so you need a collision-check-and-retry loop (append a salt, rehash) — simple, but adds unpredictable extra writes under heavy collision rates.
2. **Counter-based (preferred at scale)**: maintain a globally unique, monotonically increasing ID (e.g., from a dedicated ID-generation service, or pre-allocated ID ranges handed out to each application server), then base62-encode that ID directly into the short code. This guarantees uniqueness by construction — no collision checking needed — and a 7-character base62 code already covers `62^7 ≈ 3.5 * 10^12` values, far more than any realistic number of URLs.

The counter-based approach is generally better precisely because it turns "is this code already taken?" from a runtime check into a mathematical guarantee.

**Storage design — read/write asymmetry.** A URL shortener is overwhelmingly **read-heavy**: each URL is written once (when shortened) but read many times (every time someone clicks the link). That asymmetry should drive the architecture:

- **Writes** go to a primary datastore (a key-value store or a simple relational table of `short_code -> long_url` is enough; the access pattern is a simple point lookup, so you don't need relational joins or strong consistency across rows).
- **Reads** should hit a **cache** (e.g., Redis) in front of the datastore, since a small fraction of links (recently created or viral ones) account for most of the traffic — classic hot-key behavior. A cache miss falls through to the datastore and populates the cache.
- The redirect itself should be an **HTTP 302** (temporary redirect), not a 301 (permanent), because a 301 gets cached by browsers and CDNs indefinitely — if you ever wanted to track click counts or change the destination, a browser-cached 301 would silently stop hitting your server at all. A 302 keeps every click visible to your service.

The core lesson this scenario tests: **uniqueness should come from the ID-generation strategy, not from runtime collision detection**, and **the read/write ratio should decide where caching sits in the architecture**, not be an afterthought bolted on later.

### 2. Computer Architecture (Comparison)

Compare direct-mapped, fully-associative, and set-associative cache mapping. What does each one trade off, and why do most real CPU caches land on set-associative rather than either extreme?

**Answer:**

All three answer the same question — "where in the cache can a given memory block go?" — but they differ in how much freedom a block has to pick its location, and freedom trades directly against lookup cost and conflict rate.

**Direct-mapped**: each memory block maps to exactly **one** specific cache line, usually via `(block address) mod (number of cache lines)`. Lookup is trivial and fast — compute the index, check one tag, done. The downside is **conflict misses**: if two frequently-used blocks happen to map to the same line, they keep evicting each other even though the rest of the cache sits idle. This is the cheapest hardware but the worst hit rate under bad access patterns.

**Fully-associative**: a block can go into **any** cache line at all. This eliminates conflict misses entirely — the only misses are from genuine capacity or cold-start effects. The cost is that a lookup must compare the requested tag against *every* line in the cache simultaneously (in parallel hardware comparators), which is expensive in silicon area and power, and that cost grows with cache size. This is why fully-associative is only practical for small structures (e.g., TLBs), never for a large L1/L2/L3 cache.

**Set-associative** (the middle ground, and what almost every real CPU cache uses): the cache is divided into **sets**, each containing `N` lines ("N-way set-associative," e.g., 8-way). A block maps to exactly one *set* (like direct-mapped), but within that set it can occupy any of the `N` lines (like fully-associative on a small scale). This needs only `N` tag comparators per lookup, not one per whole-cache line, while still absorbing most conflict misses — two blocks that map to the same set no longer evict each other unless the set itself overflows past `N` resident blocks.

| | Direct-mapped | Set-associative | Fully-associative |
|---|---|---|---|
| Placement freedom | 1 line | N lines (one set) | Any line |
| Conflict misses | Highest | Low (tunable via N) | None |
| Lookup cost | 1 comparator | N comparators | 1 comparator per line |
| Hardware cost | Lowest | Moderate | Highest |

**Why set-associative wins in practice:** it is a tunable dial, not a fixed point. Going from direct-mapped (1-way) to 2-way, 4-way, or 8-way set-associative captures the large majority of the conflict-miss reduction that full associativity would give, while keeping the comparator and power cost roughly constant and small (`N` stays fixed regardless of total cache size, since you just add more sets, not more ways, as the cache grows). That's why you'll see "8-way set-associative L1 cache" far more often than a genuinely fully-associative general-purpose cache.

### 3. OOP (Conceptual/Definition)

What is the difference between method overloading and method overriding? Explain how each is resolved (compile-time vs. runtime) and why that distinction matters for polymorphism.

**Answer:**

Both let a method name mean different things depending on context, but they operate at completely different points in a program's lifecycle, which is the real distinction.

**Method overloading** is having multiple methods with the **same name but different parameter lists** (different number, type, or order of parameters) within the same class (or class hierarchy). Which one gets called is decided by the **compiler**, purely from the static types of the arguments at the call site — this is called **static (compile-time) binding**. For example, `print(int)` and `print(string)` are two unrelated methods that happen to share a name; the compiler picks the matching one before the program even runs. Overloading has nothing to do with inheritance — a class can overload a method entirely on its own.

**Method overriding** is a **subclass providing its own implementation** of a method that's already defined in its superclass, with the **same signature** (same name, same parameters). Which implementation actually runs is decided at **runtime**, based on the *actual* (dynamic) type of the object the reference points to, not the declared type of the variable — this is **dynamic (runtime) binding**, typically implemented via a virtual method table (vtable) in languages like C++ or Java.

```cpp
class Animal {
public:
    virtual void speak() { cout << "..."; }
};
class Dog : public Animal {
public:
    void speak() override { cout << "Woof"; }
};

Animal* a = new Dog();
a->speak();  // prints "Woof" — resolved at runtime via the vtable,
             // even though the static type of `a` is Animal*
```

**Why the distinction matters for polymorphism:** overriding is the actual *mechanism* of runtime polymorphism — the ability to write code against a base-class reference and have it transparently invoke the correct derived-class behavior without knowing the concrete type ahead of time. This is what makes `Animal* a = ...; a->speak();` useful in a loop over a mixed collection of `Dog`, `Cat`, and `Bird` objects. Overloading, by contrast, is **compile-time polymorphism** (sometimes called "static polymorphism") — it's a convenience for giving related operations a shared name, but it offers none of the "decide the behavior based on what's actually in memory right now" power that overriding provides. A common interview trap is conflating the two because both involve "one name, many behaviors" — the resolving question that cuts through it is always: *is this decided by the compiler from declared types, or by the runtime from the actual object?*
