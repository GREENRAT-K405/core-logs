## DSA

### Question: Sliding Window Maximum (Arrays, Hard)

Given an integer array `nums` and an integer `k` representing the size of a sliding window, return an array of the maximum element in each window as the window slides from the very left of the array to the very right, moving one element at a time.

**Input format:** An array `nums` of integers and an integer `k`.
**Output format:** An array of length `nums.length - k + 1`, where the i-th element is the maximum of `nums[i..i+k-1]`.

**Example 1:**
```
Input: nums = [1,3,-1,-3,5,3,6,7], k = 3
Output: [3,3,5,5,6,7]
Explanation:
Window position                Max
---------------                ---
[1  3  -1] -3  5  3  6  7        3
 1 [3  -1  -3] 5  3  6  7        3
 1  3 [-1  -3  5] 3  6  7        5
 1  3  -1 [-3  5  3] 6  7        5
 1  3  -1  -3 [5  3  6] 7        6
 1  3  -1  -3  5 [3  6  7]       7
```

**Example 2:**
```
Input: nums = [9,11], k = 2
Output: [11]
```

**Example 3:**
```
Input: nums = [4,-2], k = 2
Output: [4]
```

**Constraints:**
- `1 <= k <= nums.length <= 10^5`
- `-10^4 <= nums[i] <= 10^4`

### Step-by-Step Walkthrough

A brute-force scan recomputes the maximum of every window from scratch, which costs `O(n * k)` — too slow for `n` up to `1e5`. The key realization is that once an element is beaten by a *later, larger* element within the same window, it can never again be the maximum of any future window that still contains that larger element — so it can be discarded forever.

This suggests maintaining a **monotonic deque** of indices whose corresponding values are in strictly decreasing order from front to back. The front of the deque always holds the index of the current window's maximum.

Algorithm, processing index `i` from `0` to `n-1`:
1. **Shrink from the back:** while the deque is non-empty and `nums[i]` is greater than or equal to the value at the back index, pop from the back. These back elements can never be a window maximum again because `nums[i]` is both larger and will stay in the window longer.
2. **Push `i`** onto the back of the deque.
3. **Shrink from the front:** if the index at the front has fallen out of the current window (i.e. `front_index <= i - k`), pop it from the front.
4. **Record the answer:** once `i >= k - 1` (the first full window has formed), the maximum of the current window is `nums[front_index]`, so append it to the result.

Each index is pushed once and popped at most once, so the total work across all deque operations is `O(n)`. No index is ever re-examined once discarded, and the deque never holds more than `k` indices at a time, bounding space at `O(k)`.

**Correctness intuition:** the deque always stores, in order, the indices of a "staircase" of decreasing values still within the window; any value that was skipped during the back-shrink step is provably dominated by a value that outlives it in the window, so dropping it never loses the true maximum.

**Complexity:**
- Time: `O(n)` — amortized constant work per element.
- Space: `O(k)` for the deque, plus `O(n - k + 1)` for the output.

### C++ Code

```cpp
#include <vector>
#include <deque>
using namespace std;

vector<int> maxSlidingWindow(vector<int>& nums, int k) {
    deque<int> dq;              // indices, values strictly decreasing front to back
    vector<int> result;
    result.reserve(nums.size() - k + 1);

    for (int i = 0; i < (int)nums.size(); i++) {
        // Discard back indices whose values can never win again.
        while (!dq.empty() && nums[dq.back()] <= nums[i]) {
            dq.pop_back();
        }
        dq.push_back(i);

        // Discard front index once it has slid out of the window.
        if (dq.front() <= i - k) {
            dq.pop_front();
        }

        // First full window has formed; record its maximum.
        if (i >= k - 1) {
            result.push_back(nums[dq.front()]);
        }
    }

    return result;
}
```

### 1. Operating Systems (Comparison)

Compare a process and a thread. Specifically, explain what each one owns in memory, why switching between two threads of the same process is cheaper than switching between two separate processes, and give one practical reason an application might choose multiple threads over multiple processes.

**Answer:**

A **process** is an independent unit of execution with its own virtual address space: its own code, data, heap segments, and page tables, along with OS-managed resources such as open file descriptors and signal handlers. A **thread** is a unit of execution that lives *inside* a process and shares that process's address space, open files, and most other resources with every other thread in the same process — but each thread keeps its own stack, its own set of CPU registers, and its own program counter, since that is the minimum state needed to run independently.

This difference in what is shared versus private is exactly why thread context switches are cheaper:
- Switching between **threads of the same process** only requires saving/restoring registers, the program counter, and the stack pointer. The page tables (and therefore the TLB, the CPU's cache of virtual-to-physical address mappings) do not need to change, since both threads use the same address space.
- Switching between **processes** requires all of that, plus swapping the page table base register, which typically invalidates the TLB. The resulting wave of TLB misses means the next several memory accesses are slower until the cache "warms up" again. The OS must also reload more per-process kernel bookkeeping.

A practical reason to prefer multiple threads over multiple processes: when several concurrent tasks need to share large, frequently-updated in-memory state (e.g. a web server's in-memory cache, or worker threads cooperating on a shared data structure), threads can read/write that shared memory directly. Separate processes would need explicit inter-process communication (pipes, shared memory segments, sockets) to achieve the same sharing, which adds latency, complexity, and serialization overhead that threads avoid entirely. The tradeoff is isolation: a bug in one thread (e.g. a stray pointer write) can corrupt another thread's data because they share an address space, whereas a crashing process cannot directly corrupt another process's memory.

### 2. DBMS (Scenario)

A banking application lets two users concurrently transfer money out of the same account. User A transfers $50 and User B transfers $30 at nearly the same instant, both starting from a balance of $200. Without any protection, both transactions could read the balance as $200, each compute their own new balance ($150 and $170 respectively), and whichever write happens last overwrites the other — leaving the account at $170 or $150 instead of the correct $120. Which ACID property is being violated, and what database mechanism actually prevents this "lost update" problem in practice?

**Answer:**

The property being violated is **Isolation** — the "I" in ACID. Isolation guarantees that concurrently executing transactions produce a result as if they had run one after another (serially), even though they may physically overlap in time. In the scenario above, both transactions' read-modify-write cycles interleaved instead of being isolated from each other, so the second transaction's write silently discarded the effect of the first — this is the classic **lost update** anomaly.

In practice, databases prevent this through **concurrency control mechanisms**, most commonly one of:
- **Locking (pessimistic concurrency control):** before a transaction can modify a row, it must acquire a write (exclusive) lock on it. If Transaction A has already locked the account row to debit $50, Transaction B's attempt to lock the same row for its $30 debit blocks until A commits (and releases the lock). B then reads the *updated* balance of $150, not the stale $200, and correctly computes $120. This is what running the transactions under an isolation level like `SERIALIZABLE` or `REPEATABLE READ` with proper row locking enforces.
- **Optimistic concurrency control (OCC):** instead of locking upfront, each transaction reads a version number or timestamp along with the row. Before committing, it checks whether that version is still current. If another transaction committed a change in between, the commit is rejected and the transaction retries with fresh data — preventing it from blindly overwriting someone else's update.

Either mechanism restores isolation: the two transfers end up effectively serialized with respect to that row, so the final balance correctly reflects both debits ($200 - $50 - $30 = $120), and no update is silently lost.

### 3. System Design Basics (Conceptual)

Explain the CAP theorem: what do Consistency, Availability, and Partition tolerance mean in this context, and why can a distributed system only fully guarantee two of the three at any given moment?

**Answer:**

The CAP theorem describes a fundamental tradeoff for any distributed data store that replicates data across multiple nodes:

- **Consistency:** every read receives the most recent write, or an error. All nodes, regardless of which one a client talks to, agree on the current value of the data at all times.
- **Availability:** every request to a non-failing node receives a (non-error) response, even if it cannot guarantee that response reflects the most recent write.
- **Partition tolerance:** the system continues to operate correctly even when network failures ("partitions") prevent some nodes from communicating with others.

The theorem states that when a **network partition actually occurs** — which is unavoidable in any real distributed system given enough time, since networks do fail — a system is forced to choose between Consistency and Availability for the duration of that partition; it cannot have both:

- If the system chooses **Consistency over Availability (CP)**, then nodes on the "wrong" side of the partition must refuse to serve requests (or return an error) rather than risk returning stale or conflicting data, because they cannot confirm they are in sync with the rest of the cluster. This sacrifices availability during the partition.
- If the system chooses **Availability over Consistency (AP)**, then every node keeps responding to requests even while partitioned, but nodes on different sides of the partition may now have diverged data (e.g. two different values for the same key), so reads can return stale or conflicting results until the partition heals and the nodes reconcile.

Partition tolerance itself is not really optional in practice — any system spanning more than one machine over a real network must tolerate partitions, since you cannot prevent the network from failing. So in practice, CAP is really a choice between **CP** and **AP** during a partition, not a free choice among all three: for example, a system like a traditional single-leader relational database replica setup that refuses writes during a network split is leaning CP, while a system like many NoSQL stores configured for "eventual consistency" (e.g. DynamoDB's default mode) is leaning AP. The practical takeaway for system design is to pick the tradeoff deliberately based on the use case: a banking ledger usually needs strong consistency even at some cost to availability, while a social media "like" counter can tolerate brief staleness in exchange for always being responsive.
