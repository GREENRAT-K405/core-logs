## DSA

### Question: Asteroid Collision (Stacks/Queues — Medium)

**Problem Statement**

We are given an array `asteroids` of integers representing asteroids in a row. For each asteroid, the absolute value represents its size, and the sign represents its direction (positive meaning right, negative meaning left). Every asteroid moves at the same speed.

Find out the state of the asteroids after all collisions. Two asteroids moving in the same direction never meet. When two asteroids moving toward each other meet:

- The smaller one explodes (disappears).
- If both are the same size, both explode.
- Two asteroids moving in the same direction never collide.

**Input/Output Format**

- Input: an integer array `asteroids`, where each element is non-zero.
- Output: an integer array representing the asteroids remaining after all collisions resolve, left to right.

**Examples**

1. Input: `[5, 10, -5]` → Output: `[5, 10]`
   (The 10 and -5 collide; 10's size wins, so -5 explodes. The 5 never interacts with either since it keeps moving right ahead of them with nothing catching up to it from the left.)
2. Input: `[8, -8]` → Output: `[]`
   (Equal sizes moving toward each other — both explode.)
3. Input: `[10, 2, -5]` → Output: `[10]`
   (2 and -5 collide first: -5 is bigger, so 2 explodes. Then 10 and -5 collide: 10 is bigger, so -5 explodes.)

**Constraints**

- `2 <= asteroids.length <= 10^4`
- `-1000 <= asteroids[i] <= 1000`
- `asteroids[i] != 0`
- Aim for O(n) time.

### Step-by-Step Walkthrough

**Why this is a stack problem.** A collision can only happen between an asteroid moving right (`+`) that is *immediately followed*, among the ones still "alive", by an asteroid moving left (`-`). Nothing earlier than the most recent surviving right-mover can ever collide with a new left-mover, because any right-mover behind it is blocked from view — it would have to pass through the surviving one first, which physically doesn't happen (same-direction asteroids never catch each other). That "only the most recent surviving one matters" property is exactly what a stack gives you for free: push survivors, and when a new asteroid might fight the top of the stack, only the top is ever a candidate.

**The algorithm.** Process the array left to right, maintaining a stack of asteroids that have survived everything so far (in order, bottom = oldest survivor):

1. For each new asteroid `a`:
   - If `a > 0` (moving right), or the stack is empty, or the top of the stack is negative (moving left, so it can never meet `a` — both would be moving further apart or in parallel... actually re-derive: top negative means top is moving left, `a` incoming), it cannot collide with something already moving the same way or away from it, so just push `a`. Concretely: **a right-mover never fights anything already on the stack unless** nothing is pending — so push it freely.
   - If `a < 0` (moving left), it can only collide with a right-mover sitting on top of the stack (a left-mover already on the stack is moving away from it, so no collision). So: while the stack is non-empty, its top is positive, and `top < -a` (the right-mover on top is smaller), pop the top — it explodes — and keep checking the new top against `a`.
     - If after that the stack is non-empty and its top equals `-a`, both are equal size: pop the top (it explodes) and discard `a` too (it explodes) — do **not** push `a`.
     - Else if the stack is non-empty and its top is positive and `top > -a`, the right-mover wins: discard `a` (it explodes), don't push.
     - Else (stack empty or top is negative), `a` survives everything in its path: push it.
2. After processing every asteroid, the stack (bottom to top) is exactly the final surviving configuration, left to right.

**Why it's correct.** Every asteroid is compared only against candidates that could physically still be in its way — the stack discipline guarantees that whatever is "in front of" (to the left of, for a left-mover scanning backward) the current asteroid and still alive is exactly the stack's current top, because anything that would have been in front of it but died, already got popped. Induction on prefixes: assume the stack correctly represents survivors of `asteroids[0..i-1]`; processing `asteroids[i]` against that stack top-down correctly resolves all the collisions it causes, by the same local reasoning, and leaves the stack correctly representing survivors of `asteroids[0..i]`.

**Complexity.**
- Time: O(n). Each asteroid is pushed at most once and popped at most once, so the total work across all iterations is O(n) even though a single asteroid can trigger multiple pops.
- Space: O(n) for the stack in the worst case (e.g., all moving right, or no collisions occur).

### C++ Code

```cpp
#include <vector>
using namespace std;

vector<int> asteroidCollision(vector<int>& asteroids) {
    vector<int> stack; // holds surviving asteroids seen so far, left to right

    for (int a : asteroids) {
        bool destroyed = false;

        // A left-mover (a < 0) can only collide with a right-mover
        // sitting on top of the stack. Keep resolving collisions while
        // that is the case.
        while (!destroyed && a < 0 && !stack.empty() && stack.back() > 0) {
            if (stack.back() < -a) {
                // Right-mover on top is smaller: it explodes, keep
                // checking the new top against the same incoming asteroid.
                stack.pop_back();
            } else if (stack.back() == -a) {
                // Exactly equal size: both explode.
                stack.pop_back();
                destroyed = true;
            } else {
                // Right-mover on top is bigger: incoming asteroid explodes.
                destroyed = true;
            }
        }

        if (!destroyed) {
            stack.push_back(a);
        }
    }

    return stack;
}
```

The loop condition `a < 0 && !stack.empty() && stack.back() > 0` is the whole trick: it's the only configuration where a collision is even possible, so everything else (both moving right, both moving left, or a right-mover meeting an empty/left-topped stack) falls straight through to "just push it."

## CS Fundamentals

### 1. Operating Systems (Conceptual/Definition)

What are the four necessary conditions for deadlock to occur, and how does each deadlock-avoidance or deadlock-prevention strategy map to breaking one specific condition?

**Answer:**

Deadlock requires all four of the **Coffman conditions** to hold simultaneously. Break any single one, and deadlock becomes impossible — which is exactly why every prevention strategy targets one of these four, not "deadlock" as a vague whole.

1. **Mutual exclusion.** At least one resource is held in a non-shareable mode (only one process/thread can use it at a time).
2. **Hold and wait.** A process holding at least one resource is waiting to acquire additional resources currently held by other processes.
3. **No preemption.** Resources cannot be forcibly taken away from a process; they are only released voluntarily.
4. **Circular wait.** There exists a cycle of processes, each waiting for a resource held by the next one in the cycle.

**How prevention strategies map to each:**

| Condition broken | Strategy | Example |
| --- | --- | --- |
| Mutual exclusion | Make resources shareable where possible | Read-only files, or lock-free data structures that avoid exclusive locks entirely |
| Hold and wait | Require a process to request all resources it will ever need up front, or release held resources before requesting new ones | A transaction that acquires all table locks at the start rather than incrementally |
| No preemption | Allow the OS/runtime to forcibly take a resource from a process and roll it back | Database deadlock detectors that abort and roll back one of the transactions, releasing its locks |
| Circular wait | Impose a strict global ordering on resource acquisition, so a cycle can never form | Always acquire locks in increasing order of, say, account ID when transferring money between two accounts |

**Why this framing matters in practice:** it tells you deadlock *detection and recovery* (letting deadlocks happen occasionally and then breaking them, usually by preempting a victim) is a legitimate alternative to prevention, because it only needs to violate "no preemption" after the fact rather than enforcing a rule up front on every acquisition. This is the trade-off real databases make: strict lock ordering across an entire application is often impractical, so engines like PostgreSQL and MySQL instead run a deadlock detector that periodically looks for wait-for cycles and aborts one transaction to break them, rather than preventing the cycle from ever forming.

### 2. OOP (Comparison)

Compare composition and inheritance as two ways to reuse code across classes. What does the "has-a vs. is-a" heuristic actually protect you from, and when does inheritance's convenience turn into a liability?

**Answer:**

Both let one class reuse another's behavior, but they create a very different kind of coupling.

**Inheritance** (`class Dog extends Animal`) models an **is-a** relationship: the subclass is claiming to be a more specific version of the superclass, inheriting its entire interface and implementation, and it can be substituted anywhere the superclass is expected (the Liskov substitution principle is really just this claim made precise). The coupling is tight and compile-time: a subclass's correctness can depend on the superclass's internal implementation details, not just its documented contract — the classic "fragile base class" problem, where changing a private detail of the base class silently breaks subclasses that happened to rely on it.

**Composition** (`class Car { private Engine engine; }`) models a **has-a** relationship: the containing class holds a reference to another object and delegates to it through that object's public interface only. The coupling is to a contract, not an implementation, and it can be rebound at runtime (swap in a different `Engine` implementation without touching `Car`'s class hierarchy at all).

**What the heuristic protects you from:** reaching for inheritance purely to reuse a chunk of code when there's no genuine is-a relationship. A common anti-pattern is `class Stack extends ArrayList` just to reuse `ArrayList`'s storage logic — but a `Stack` is not substitutable for an `ArrayList` (callers shouldn't be able to call `.add(5, x)` to insert into the middle of a stack), so this is really a has-a relationship wearing an is-a costume. It compiles, and it leaks: every method `ArrayList` ever had is now part of `Stack`'s public surface, whether or not it makes sense there.

**Where inheritance's convenience becomes a liability:** deep hierarchies. Each added layer multiplies the ways a subclass can depend on base-class internals, and a change several levels up can break something several levels down in a way neither author anticipated, since there's no explicit contract being checked — only whatever the subclass's code happened to assume. This is precisely the motivation behind the common guidance "favor composition over inheritance": composition confines the dependency to an explicit interface, so the chain of fragile, implicit assumptions never gets the chance to form in the first place. Inheritance is still the right tool when a true is-a relationship holds and polymorphic substitution is the actual goal (a `Circle` really is a `Shape` and should be usable anywhere a `Shape` is expected) — the heuristic isn't "never inherit," it's "don't inherit just to steal code."

### 3. System Design Basics (Scenario/Applied)

You're asked to design a rate limiter for a public API that must allow each user at most 100 requests per minute. Walk through which algorithm you'd pick, why, and how it behaves differently from a naive fixed-window counter under bursty traffic right at a window boundary.

**Answer:**

**The naive approach: fixed window counter.** Keep a counter per user, reset to 0 at the start of each 60-second window, increment on each request, and reject once it hits 100. It's simple and O(1) per request, but it has a real correctness problem at window boundaries: a user can send 100 requests in the last second of one window and another 100 in the first second of the next window — 200 requests in about two seconds, well above the intended rate of 100/minute, yet every single request was "within its window." The limiter technically never lied, but the guarantee it was supposed to provide (no more than 100 requests in any 60-second span) silently failed to hold for the specific 60-second span straddling the boundary.

**A better fit: sliding window log, or its cheaper approximation, the sliding window counter.**

- **Sliding window log:** store a timestamp per request per user (e.g., in a sorted structure or a deque). On each new request, drop timestamps older than `now - 60s`, then check whether the remaining count is `< 100`. This is exactly correct for any 60-second window, not just aligned ones, because it's evaluating the actual trailing window rather than a fixed calendar bucket. The cost is storing up to 100 timestamps per active user, and the drop step, which is still O(1) amortized per request with a deque since you only ever pop from the front.
- **Sliding window counter (approximation):** keep two fixed-window counters (current and previous) and estimate the count in the trailing window as a weighted combination — `current_count + previous_count * (overlap fraction of the previous window still inside the trailing 60s)`. This is far cheaper than storing individual timestamps (two integers per user instead of up to 100 timestamps) and eliminates the boundary-burst problem almost entirely, at the cost of being an approximation rather than exact.

**Why I'd pick the sliding window counter for this scenario specifically:** at "100 requests per user per minute" scale, exactness down to the single request rarely matters commercially, but memory per user does, since this has to run for every user concurrently, likely in a shared store like Redis (using `INCR` with `EXPIRE` for each window bucket). The sliding window counter gets memory cost down to the fixed-window counter's level while fixing its main correctness flaw, which is the right trade-off here. If the limiter were protecting something where exactness genuinely matters (billing based on request count, or a security-critical throttle), I'd justify the extra memory of the sliding window log instead, since an approximation that's occasionally a little too permissive isn't acceptable there.

**One more practical detail:** the limiter needs to be checked atomically against the store (e.g., a Lua script in Redis doing read-check-increment in one round trip), otherwise concurrent requests from the same user can race past each other and both read "99, still under the limit" before either one's increment is visible — letting the user burst past 100 anyway, just from a race rather than from the algorithm's own boundary behavior.
