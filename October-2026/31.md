### Question: Count of Smaller Numbers After Self (Sorting/Searching — Hard)

Given an integer array `nums`, return an array `counts` where `counts[i]` is the number of elements to the right of `nums[i]` (i.e., at indices `> i`) that are strictly smaller than `nums[i]`.

**Input format:**
- An integer array `nums` of length `n`.

**Output format:**
- An integer array `counts` of the same length `n`, where `counts[i]` is the count described above.

**Worked Examples:**

1. `nums = [5, 2, 6, 1]` → `counts = [2, 1, 1, 0]`
   - For `5` (index 0): elements to its right that are smaller are `2` and `1` → count `2`.
   - For `2` (index 1): only `1` to its right is smaller → count `1`.
   - For `6` (index 2): only `1` to its right is smaller → count `1`.
   - For `1` (index 3): nothing to its right → count `0`.
2. `nums = [-1]` → `counts = [0]` (no elements to the right at all).
3. `nums = [-1, -1]` → `counts = [0, 0]` (the second `-1` is not *strictly* smaller than the first, so both counts are `0`).

**Constraints:**
- `1 <= nums.length <= 10^5`
- `-10^4 <= nums[i] <= 10^4`

---

### Step-by-Step Walkthrough

**Approach — Coordinate Compression + Fenwick Tree (Binary Indexed Tree), processed right to left**

A brute-force double loop (`O(n^2)`) checks, for every `i`, how many later elements are smaller — correct but too slow for `n` up to `10^5`. We need something closer to `O(n log n)`.

**Key insight:** If we process the array from **right to left** and, at each step, ask "how many elements I've already seen (which are all to my right in the original array) are smaller than me?", that's exactly `counts[i]`. This reframes the problem as repeatedly inserting values into a structure and querying "how many inserted values are less than X" — which a Fenwick tree (BIT) answers in `O(log n)` per operation, provided the values are mapped to a compact range of ranks.

**Steps:**
1. **Coordinate-compress** the values: sort a copy of `nums`, remove duplicates, and assign each distinct value a rank from `1` to `m` (the number of distinct values), where larger values get larger ranks. This is necessary because raw values can be negative or span a huge range, but a Fenwick tree needs small positive indices.
2. **Initialize** a Fenwick tree of size `m`, all zeros — it will track, for each rank, how many times a value with that rank has been inserted so far.
3. **Iterate `i` from `n - 1` down to `0`:**
   - Let `r` be the rank of `nums[i]`.
   - `counts[i] = query(r - 1)` — the prefix sum over all ranks strictly less than `r`, i.e., how many already-inserted (= already-seen-to-the-right) elements are strictly smaller than `nums[i]`.
   - `update(r, +1)` — now record that we've seen one more element with this rank, for future (further-left) queries.
4. Return `counts`.

**Why it works:** Because we go right-to-left, by the time we process index `i`, the Fenwick tree contains exactly the multiset of elements at indices `i+1 .. n-1` — precisely "everything to the right of `i`". A prefix-sum query up to rank `r - 1` counts exactly the elements strictly smaller than `nums[i]`, which is the definition of `counts[i]`. Using strictly `r - 1` (not `r`) ensures we don't count elements equal to `nums[i]` — matching the third worked example.

**Complexity Analysis:**
- **Time complexity:** `O(n log n)` — sorting for compression is `O(n log n)`, and each of the `n` Fenwick `update`/`query` calls is `O(log n)`.
- **Space complexity:** `O(n)` — for the Fenwick tree array, the rank map, and the output array.

### C++ Code

```cpp
#include <bits/stdc++.h>
using namespace std;

class Fenwick {
    vector<int> tree;
    int n;
public:
    Fenwick(int size) : n(size), tree(size + 1, 0) {}

    // Add 'delta' at position idx (1-indexed).
    void update(int idx, int delta) {
        for (; idx <= n; idx += idx & (-idx))
            tree[idx] += delta;
    }

    // Prefix sum over [1, idx].
    int query(int idx) {
        int sum = 0;
        for (; idx > 0; idx -= idx & (-idx))
            sum += tree[idx];
        return sum;
    }
};

class Solution {
public:
    vector<int> countSmaller(vector<int>& nums) {
        int n = nums.size();
        vector<int> counts(n, 0);
        if (n == 0) return counts;

        // Coordinate-compress values into dense ranks 1..m.
        vector<int> sortedVals(nums);
        sort(sortedVals.begin(), sortedVals.end());
        sortedVals.erase(unique(sortedVals.begin(), sortedVals.end()), sortedVals.end());

        unordered_map<int, int> rank;
        rank.reserve(sortedVals.size());
        for (int i = 0; i < (int)sortedVals.size(); ++i)
            rank[sortedVals[i]] = i + 1;

        Fenwick bit((int)sortedVals.size());

        // Process right to left: the BIT always holds exactly the elements
        // already seen, which are all to the right of the current index.
        for (int i = n - 1; i >= 0; --i) {
            int r = rank[nums[i]];
            counts[i] = bit.query(r - 1);
            bit.update(r, 1);
        }
        return counts;
    }
};

int main() {
    Solution sol;

    vector<int> nums1 = {5, 2, 6, 1};
    vector<int> res1 = sol.countSmaller(nums1);
    cout << "Input: [5,2,6,1] -> Output: [";
    for (size_t i = 0; i < res1.size(); ++i) cout << res1[i] << (i + 1 < res1.size() ? "," : "");
    cout << "] (expected [2,1,1,0])" << endl;

    vector<int> nums2 = {-1};
    vector<int> res2 = sol.countSmaller(nums2);
    cout << "Input: [-1] -> Output: [" << res2[0] << "] (expected [0])" << endl;

    vector<int> nums3 = {-1, -1};
    vector<int> res3 = sol.countSmaller(nums3);
    cout << "Input: [-1,-1] -> Output: [" << res3[0] << "," << res3[1] << "] (expected [0,0])" << endl;

    return 0;
}
```

**Trace against the examples:**
- `[5,2,6,1]`: processing right to left inserts `1` (rank 1), then `6` (rank 4, sees one smaller rank → `1`), then `2` (rank 2, sees one smaller rank, the `1` → `1`), then `5` (rank 3, sees two smaller ranks, `1` and `2` → `2`). Final `counts = [2,1,1,0]`. ✓
- `[-1]`: single element, nothing inserted yet when queried → `[0]`. ✓
- `[-1,-1]`: both map to the same rank; querying `rank - 1` excludes equal values, so both get `0`. ✓

### 1. Computer Networks (Conceptual/Definition)
Describe the TCP three-way handshake used to establish a connection. What is exchanged in each of the three steps, and why is a third step needed instead of just two?

**Answer:**

The TCP three-way handshake synchronizes sequence numbers and confirms that both sides are ready to communicate before any application data flows:

1. **SYN** — The client sends a segment with the `SYN` flag set and an initial sequence number (ISN), say `x`. This says "I want to connect, and my byte stream starts at sequence number `x`."
2. **SYN-ACK** — The server responds with both `SYN` and `ACK` flags set: it acknowledges the client's sequence number (`ACK = x + 1`) and sends its own initial sequence number `y`. This says "I got your request, here is *my* starting sequence number, and I'm also requesting to connect."
3. **ACK** — The client sends a final segment with `ACK = y + 1`, acknowledging the server's sequence number. This says "I received your sequence number too."

**Why not just two steps?** TCP is a *bidirectional* protocol — each side maintains its own independent sequence number space for the data *it* sends. A two-step handshake (SYN, then ACK) would only let the server confirm the client's sequence number; the server's own initial sequence number would never be acknowledged by the client, so the server couldn't be sure the client actually received it. The third step closes this gap: without it, a lost `SYN-ACK` could lead the client to never confirm it got the server's starting sequence number, while the server believes the connection is already up (half-open connection) — wasting resources and risking delivery of data the client hasn't actually synchronized on. The third step is also what lets the client safely open a connection immediately after sending it, since by then both sequence numbers are mutually confirmed.

### 2. DBMS (Comparison)
Compare a clustered index and a non-clustered index in a relational database. How does each one physically organize data, and how many of each can a single table have?

**Answer:**

| Aspect | Clustered Index | Non-Clustered Index |
|---|---|---|
| Physical data order | The table's actual rows are **physically sorted and stored** on disk in the order of the index key. The index *is* the data. | A **separate structure** (typically a B-tree) that stores the index key plus a pointer/reference (row ID, or the clustered key) back to the actual row, which lives elsewhere in its own order. |
| Count per table | Only **one** per table, since rows can physically exist in only one order. | **Many** can exist on the same table, since each is just an auxiliary lookup structure. |
| Lookup speed (on indexed column) | Very fast for range scans and exact lookups — once you find the key, the row's data is right there. | Fast for finding the key, but if the row isn't fully covered by the index, it requires an extra "lookup" step to fetch the row via the pointer (unless it's a "covering index" containing all needed columns). |
| Typical choice of key | Usually the primary key (e.g., auto-increment ID), since inserts stay largely sequential and avoid expensive row reshuffling. | Any frequently-queried or frequently-filtered/sorted column, e.g., an email column used in `WHERE` clauses. |
| Insert/update cost | Can be more expensive if inserting out of key order, since rows may need to be physically moved to maintain sort order (page splits). | Cheaper to maintain relative to data movement, but every non-clustered index adds its own write overhead on every insert/update. |

**Why this matters:** Choosing the clustered index key is one of the most consequential schema decisions in a relational database — it dictates physical row layout and therefore the performance of range queries and joins on that key. Non-clustered indexes are then layered on top, trading extra storage and write cost for faster lookups on other columns, so a developer must balance "how many non-clustered indexes" against "how much do writes slow down" for that specific workload.

### 3. Operating Systems (Scenario/Applied)
Four processes P1, P2, P3, P4 each hold one instance of a resource and are each requesting one more instance held by another process, forming a cycle: P1 holds R1 and wants R2 (held by P2), P2 holds R2 and wants R3 (held by P3), P3 holds R3 and wants R4 (held by P4), and P4 holds R4 and wants R1 (held by P1). Is this necessarily a deadlock? Name the four conditions that must all hold for deadlock to occur, and describe one practical strategy to prevent it in this kind of system.

**Answer:**

Yes — this is a textbook deadlock, because all four necessary conditions (Coffman conditions) are satisfied simultaneously:

1. **Mutual Exclusion** — Each resource (R1–R4) can be held by only one process at a time (a single instance each, in this scenario).
2. **Hold and Wait** — Each process is already holding one resource while waiting to acquire another (e.g., P1 holds R1 and is blocked waiting for R2).
3. **No Preemption** — Resources cannot be forcibly taken away from a process; they're only released voluntarily when the holding process finishes with them.
4. **Circular Wait** — There's a cycle of processes, each waiting on the next: P1 → P2 → P3 → P4 → P1. This is exactly the resource-allocation graph cycle described, and with single-instance resources, a cycle in the wait-for graph *guarantees* deadlock (no process in the cycle can ever proceed, since each is waiting on the next, which is itself blocked).

**Prevention strategy — breaking Circular Wait via resource ordering:** A simple and widely used practical approach is to impose a **total (linear) ordering** on all resource types and require that every process request resources only in strictly increasing order of that ranking. For example, number the resources `R1 < R2 < R3 < R4`; a process already holding `R3` would then be prohibited from ever requesting `R1` or `R2` (only `R4` or higher) — it could request `R2` only if it hadn't yet acquired `R3`. This makes a circular wait structurally impossible: any cycle in the wait-for graph would require some process to request a lower-ranked resource while already holding a higher-ranked one, which the ordering rule forbids. This is cheaper than runtime deadlock *detection* (which needs periodic cycle-checking in the resource-allocation graph) or the Banker's Algorithm (which needs advance knowledge of each process's maximum resource needs to check if a grant keeps the system in a "safe state") — at the cost of requiring processes to be designed around a fixed global resource order, which isn't always practical for dynamically determined resource needs.
