### Question: Critical Connections in a Network (Graphs — Hard)

**Problem Statement**

There are `n` servers numbered from `0` to `n - 1`, connected by `n - 1` or more bidirectional `connections` forming a network. Each `connections[i] = [a, b]` represents a direct connection between server `a` and server `b`. The network is guaranteed to be connected (there is a path between any two servers).

A **critical connection** (also called a **bridge**) is a connection that, if removed, would split the network into two or more disconnected components — i.e., some pair of servers would no longer be able to reach each other.

Return all critical connections in the network, in any order. Each connection should be returned as a pair `[a, b]` (in either orientation).

**Input/Output Format**

- Input: `int n` (number of servers), `vector<vector<int>> connections` (each an undirected edge `[a, b]`, `a != b`, no duplicate edges).
- Output: `vector<vector<int>>`, the list of critical connections (bridges).

**Examples**

1. `n = 4`, `connections = [[0,1],[1,2],[2,0],[1,3]]`
   → `[[1,3]]`
   (`0-1-2-0` forms a cycle, so none of those three edges are critical — removing any one still leaves a path via the other two. But `1-3` is the only link to server `3`; removing it strands server `3` entirely.)

2. `n = 2`, `connections = [[0,1]]`
   → `[[0,1]]`
   (The only edge in the network. Removing it disconnects the two servers, so it's trivially critical.)

3. `n = 6`, `connections = [[0,1],[1,2],[2,0],[1,3],[3,4],[4,5],[5,3]]`
   → `[[1,3]]`
   (Servers `0,1,2` form a triangle/cycle and servers `3,4,5` form a triangle/cycle, but the single edge `1-3` is the sole bridge joining the two cycles — remove it and the network splits into two components.)

**Constraints**

- `2 <= n <= 10^5`
- `n - 1 <= connections.length <= 10^5`
- `0 <= a, b <= n - 1`
- The graph is connected and has no self-loops or repeated edges.

### Step-by-Step Walkthrough

**Reframe the problem: a bridge is an edge that belongs to no cycle.** If an edge `(u, v)` sits on some cycle, then removing it still leaves an alternate path between `u` and `v` via the rest of the cycle, so it can't be critical. Conversely, if `(u, v)` is on no cycle, it is the *only* path between the two halves of the graph it connects, so removing it must disconnect them. So the real task is: find every edge that is not part of any cycle. This is exactly what **Tarjan's bridge-finding algorithm** does, in one linear-time DFS pass.

**Discovery time and low-link value.** Run a DFS from any node, numbering each node with a `disc[node]` value in the order it is first visited. Alongside that, maintain `low[node]` = the smallest `disc` value reachable from `node`'s subtree using at most one "back edge" (an edge to an already-visited ancestor, not through the parent edge we just came from). Intuitively, `low[node]` answers: "ignoring the edge I used to get here, how far back up the tree can this subtree reach?"

`low[node]` is computed as the DFS unwinds, by taking the minimum over:
- `disc[node]` itself,
- `low[child]` for every DFS-tree child,
- `disc[neighbor]` for every neighbor reachable by a non-parent back edge.

**The bridge condition.** For a tree edge `(parent, child)` discovered during DFS, that edge is a bridge **if and only if** `low[child] > disc[parent]`. This says: the child's subtree has *no* way to reach `parent` or anything discovered before `parent`, except by going back through the very edge we're testing — meaning that edge is the subtree's only connection to the rest of the graph, so it's not part of any cycle.

**Why we must skip the immediate parent edge, not just visited nodes.** A naive "don't revisit a visited node" check would also skip the direct edge back to the parent along a tree edge, incorrectly treating it as a back edge and making `low[child]` artificially small (equal to `disc[parent]`), which would mask every bridge. The standard fix is to pass the id of the edge used to enter a node (not just the parent node) and skip only that exact edge index — this correctly handles graphs with parallel edges too, though this problem guarantees no duplicate edges so skipping the parent *node* once is also safe here.

**Algorithm.**
1. Build an adjacency list from `connections`.
2. Run an iterative (to avoid stack overflow on up to `10^5` nodes) or recursive DFS, tracking `disc[]`, `low[]`, and a `visited[]` flag.
3. For each tree edge `(u, v)` where `v` was freshly discovered from `u`: after returning from `v`'s recursion, update `low[u] = min(low[u], low[v])`. If `low[v] > disc[u]`, record `(u, v)` as a bridge.
4. For each edge `(u, w)` where `w` is already visited and is not the edge we arrived on: update `low[u] = min(low[u], disc[w])`.

**Complexity.**
- Time: O(V + E) — a single DFS pass visiting every node and edge a constant number of times.
- Space: O(V + E) for the adjacency list, plus O(V) for `disc`, `low`, `visited`, and the explicit recursion/iteration stack.

### C++ Code

```cpp
#include <vector>
using namespace std;

class Solution {
public:
    vector<vector<int>> criticalConnections(int n, vector<vector<int>>& connections) {
        vector<vector<pair<int,int>>> adj(n); // adj[u] = {neighbor, edgeId}
        int m = static_cast<int>(connections.size());
        for (int i = 0; i < m; i++) {
            int a = connections[i][0], b = connections[i][1];
            adj[a].push_back({b, i});
            adj[b].push_back({a, i});
        }

        vector<int> disc(n, -1), low(n, -1);
        vector<vector<int>> bridges;
        int timer = 0;

        // Iterative DFS using an explicit stack to avoid recursion-depth
        // issues on graphs with up to 1e5 nodes.
        // Stack frame: {node, parentEdgeId, iteratorIndex}
        vector<int> stkNode, stkParentEdge, stkIter;

        for (int start = 0; start < n; start++) {
            if (disc[start] != -1) continue;

            stkNode.push_back(start);
            stkParentEdge.push_back(-1);
            stkIter.push_back(0);
            disc[start] = low[start] = timer++;

            while (!stkNode.empty()) {
                int u = stkNode.back();
                int parentEdge = stkParentEdge.back();
                int &it = stkIter.back();

                if (it < static_cast<int>(adj[u].size())) {
                    auto [v, edgeId] = adj[u][it];
                    it++; // advance this frame's iterator before possibly descending

                    if (edgeId == parentEdge) continue; // skip the edge we arrived on

                    if (disc[v] == -1) {
                        // Tree edge: descend into v.
                        disc[v] = low[v] = timer++;
                        stkNode.push_back(v);
                        stkParentEdge.push_back(edgeId);
                        stkIter.push_back(0);
                    } else {
                        // Back edge to an already-visited node: tighten u's low-link.
                        low[u] = min(low[u], disc[v]);
                    }
                } else {
                    // Done exploring u's neighbors; pop and propagate low[u] to parent.
                    stkNode.pop_back();
                    stkParentEdge.pop_back();
                    stkIter.pop_back();

                    if (!stkNode.empty()) {
                        int parent = stkNode.back();
                        low[parent] = min(low[parent], low[u]);
                        if (low[u] > disc[parent]) {
                            bridges.push_back({parent, u});
                        }
                    }
                }
            }
        }

        return bridges;
    }
};
```

## CS Fundamentals

### 1. OOP (Conceptual/Definition)

What is the Liskov Substitution Principle (the "L" in SOLID)? Give an example of a class hierarchy that technically compiles but violates it.

**Answer:**

The Liskov Substitution Principle states that if `S` is a subtype of `T`, then objects of type `T` in a program should be replaceable with objects of type `S` without altering any of the desirable properties of that program (correctness, expected behavior, invariants). In plain terms: a subclass must honor the *behavioral contract* of its parent class, not just its method signatures. Inheritance should model an "is-substitutable-for" relationship, not merely an "is-a" relationship in the informal English sense.

**The classic violation: Square extends Rectangle.** A `Rectangle` has `setWidth(w)` and `setHeight(h)`, with the implicit contract that setting one doesn't change the other. Mathematically, a square *is* a rectangle, so it's tempting to write `class Square : public Rectangle` and override `setWidth`/`setHeight` so that setting either one sets both (to keep the square, well, square). This compiles fine and respects the geometric "is-a" relationship. But it breaks the contract: code written against `Rectangle` that does `rect->setWidth(5); rect->setHeight(10); assert(rect->area() == 50);` will fail if `rect` actually points to a `Square`, because setting the height silently changed the width too. The subclass is not safely substitutable, even though it "is-a" rectangle in the geometric sense — it violates an invariant the base class's clients reasonably depend on.

**Why this matters practically.** LSP violations are dangerous specifically because they don't show up as compile errors or even obvious bugs in the subclass's own tests — they show up as surprising failures in *other* code that correctly trusted the base class's contract, often far away from where the subclass was written. The practical guideline: when overriding a method, never strengthen preconditions (don't demand more from callers than the base class did) and never weaken postconditions (don't promise less than the base class did) — including implicit invariants like "changing one property doesn't change another." If a subclass can't honor those, prefer composition over inheritance, or model the relationship differently (e.g., both `Square` and `Rectangle` implementing a common `Shape` interface, neither inheriting from the other).

### 2. System Design Basics (Comparison)

Compare horizontal scaling and vertical scaling. Why do most large-scale distributed systems eventually favor horizontal scaling despite it being architecturally harder?

**Answer:**

| | Vertical Scaling (Scale Up) | Horizontal Scaling (Scale Out) |
| --- | --- | --- |
| Approach | Add more resources (CPU, RAM, faster disk) to a single machine | Add more machines, and distribute load across them |
| Ceiling | Hard physical/cost ceiling — there's a biggest machine money can buy | Effectively unbounded — keep adding commodity machines |
| Complexity | Simple — no code changes, same single-node architecture | Harder — needs load balancing, data partitioning/replication, coordination |
| Single point of failure | Yes — one machine means one failure takes everything down | No (if designed well) — other nodes keep serving if one fails |
| Cost curve | Non-linear and steep at the high end (top-tier hardware is disproportionately expensive) | Roughly linear — commodity hardware scales cost with capacity |
| Downtime to scale | Often requires a restart/migration to a bigger machine | New nodes can usually be added without taking the system down |

**Why horizontal scaling wins at large scale.** Vertical scaling hits two walls that horizontal scaling doesn't: a *physical* wall (there's a maximum amount of CPU/RAM/IO you can put in one box, and at extreme scale even the biggest available machine isn't enough) and an *availability* wall (no matter how powerful, a single machine is a single point of failure — when it goes down or needs maintenance, the whole service goes down with it). Horizontal scaling sidesteps both: capacity grows by adding nodes (no inherent ceiling), and the system can tolerate individual node failures by routing around them, which is essential for the "five nines" uptime large systems target.

**The cost of horizontal scaling — why it's "architecturally harder."** You can't just throw more machines at a problem; the application has to be designed to use them. That means: a load balancer to distribute requests, statelessness (or externalized session state) so any node can handle any request, data partitioning/sharding so no single database becomes the new bottleneck, replication and consensus to keep distributed data consistent, and handling partial failure as a normal condition rather than an edge case (per the CAP theorem, a partitioned distributed system must choose between consistency and availability). This is genuinely more complex than "buy a bigger server," which is why small systems or early-stage products often scale vertically first — it's cheaper in engineering time — and only invest in horizontal scaling once vertical scaling's ceiling or single-point-of-failure risk becomes the actual bottleneck.

### 3. DBMS (Scenario/Applied)

Two transactions run concurrently on a bank database under the **Read Committed** isolation level: Transaction A reads a customer's balance twice, with Transaction B updating and committing that same balance in between A's two reads. Explain what anomaly A observes, why Read Committed permits it, and which isolation level would prevent it.

**Answer:**

**What A observes.** This is a **non-repeatable read**. Transaction A's first read of the balance returns, say, `$1000`. While A is still running, Transaction B updates the balance to `$800` and commits. When A reads the *same row* again later in its own transaction, it now sees `$800` — a different value for a row it already read, without A itself having changed anything. If A's logic assumed the balance would stay stable for the duration of its transaction (e.g., it read it once to display it, did some other work, then re-read it to validate before finalizing a withdrawal), it now sees inconsistent data within what should feel like one atomic unit of work.

**Why Read Committed permits this.** Read Committed guarantees only that a transaction never reads *uncommitted* (dirty) data from another transaction — each individual read sees only committed values at the moment it executes. It does **not** guarantee that two reads of the same row *within the same transaction* return the same value, because it takes a fresh snapshot (or fresh lock-based read) for every single statement, not one snapshot for the whole transaction. So between A's two reads, B's commit becomes "visible" to A, and A's second read faithfully reflects the new committed state — which is correct per Read Committed's own contract, but surprising if you expected transaction-level consistency.

**What prevents it: Repeatable Read (or stricter).** At the **Repeatable Read** isolation level, a transaction takes its snapshot of the data (or acquires the relevant read locks) at the start of the transaction and guarantees that every subsequent read within that same transaction sees the same values for rows it has already read, regardless of what other transactions commit in the meantime — B's update would simply not be visible to A until A itself commits and starts a new transaction. (Repeatable Read still permits **phantom reads** — new rows matching a range query appearing on a re-run — which only **Serializable**, the strictest level, fully eliminates by making the schedule behave as if transactions ran one at a time.)

**Why this matters practically.** The right isolation level is a trade-off between correctness guarantees and concurrency/throughput: stricter levels (Repeatable Read, Serializable) prevent more anomalies but typically increase lock contention or require more snapshot/version bookkeeping, hurting throughput under heavy concurrent writes. Read Committed is the default in many production databases (e.g., PostgreSQL, Oracle) precisely because it's "good enough" for most workloads and fast — but any code path that reads the same row multiple times within a transaction and depends on it not changing (balance checks before a transfer, inventory counts before a sale) needs to either use a stricter isolation level or take explicit locks (e.g., `SELECT ... FOR UPDATE`) to get the guarantee it actually needs.
