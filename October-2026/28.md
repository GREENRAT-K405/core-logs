## DSA

### Question: Partition Labels (Greedy — Medium)

**Problem Statement**

You are given a string `s` consisting of lowercase English letters. Partition `s` into as many contiguous parts as possible so that each letter appears in at most one part (i.e. every occurrence of a given letter must fall entirely within a single part — no letter may be split across two parts). Return a list of integers representing the length of each part, in order.

**Input/Output Format**

- Input: a string `s` of lowercase English letters.
- Output: a list of integers — the length of each partition, left to right, summing to `s.length()`.

**Examples**

1. Input: `s = "ababcbacadefegdehijhklij"` → Output: `[9, 7, 8]`
   (The first part is `"ababcbaca"` — `a`, `b`, and `c` all have their last occurrence within the first 9 characters. The second is `"defegde"`, the third `"hijhklij"`.)
2. Input: `s = "eccbbbbdec"` → Output: `[10]`
   (`e` appears at index 0 and again at index 9, so the whole string must be one part.)
3. Input: `s = "abc"` → Output: `[1, 1, 1]`
   (No letter repeats, so every character is free to be its own part — and splitting as much as possible is what "as many parts as possible" asks for.)

**Constraints**

- `1 <= s.length <= 500`
- `s` consists only of lowercase English letters.
- Aim for O(n) time.

### Step-by-Step Walkthrough

**Reframe the problem.** A part is valid exactly when every letter inside it has *all* of its occurrences inside it — none of its occurrences leak into a later part. So a part that starts at index `start` can only close at some index `end` if, for every character seen between `start` and `end`, that character's **last occurrence in the whole string** is `<= end`. If some character seen in that window has its last occurrence further to the right, the part can't close yet — it has to stretch out to cover that occurrence too.

This is a greedy, single-pass problem once framed that way: at each position, the current part must extend at least as far as the furthest "last occurrence" of any character it has swallowed so far.

**Step 1 — precompute last occurrence of every character.** Scan `s` once and record, for each letter, the highest index at which it appears: `last[c] = index`. This takes O(n) time and O(1) extra space (at most 26 entries).

**Step 2 — greedily grow and close partitions.** Walk `s` with two markers: `start` (the beginning of the current partition) and `end` (the furthest index the current partition is currently known to need). For each index `i` from `start` to the end of the string:
- Update `end = max(end, last[s[i]])` — the current letter forces the partition to reach at least as far as *its* last occurrence.
- If `i == end`, every character seen so far in this partition has had its last occurrence accounted for by position `i` — the partition can safely close here. Record its length `i - start + 1`, then set `start = i + 1` (and `end` will get reset by the next character).

**Why this is correct (and maximal).** Closing the moment `i == end` is always safe, because at that exact index every letter encountered in `[start, i]` has already had its last occurrence seen — nothing later in the string can force this part to re-open. And it's never *too early* to close, because by definition `end` already accounts for the furthest reach of every letter in the window; if it weren't safe to close, `end` would still be ahead of `i`. Since we close at the very first index where it becomes safe, we produce the maximum possible number of parts — merging two parts you didn't have to merge would only ever reduce the count, never required for validity.

**Complexity.**
- Time: O(n) — one pass to build `last`, one pass to partition. (With `n` capped at 500 and the alphabet at 26, this is effectively linear in input size either way.)
- Space: O(1) extra — the `last` array is fixed size 26, independent of `n`.

### C++ Code

```cpp
#include <vector>
#include <string>
using namespace std;

vector<int> partitionLabels(const string& s) {
    // last[c] = the highest index at which character c occurs in s.
    int last[26] = {0};
    for (int i = 0; i < (int)s.size(); i++) {
        last[s[i] - 'a'] = i;
    }

    vector<int> result;
    int start = 0; // start index of the current partition
    int end = 0;   // furthest index the current partition must reach

    for (int i = 0; i < (int)s.size(); i++) {
        // This character forces the partition to extend at least to its
        // own last occurrence.
        end = max(end, last[s[i] - 'a']);

        // Every character seen in [start, i] has had its last occurrence
        // accounted for by now, so it's safe (and maximal) to close here.
        if (i == end) {
            result.push_back(i - start + 1);
            start = i + 1;
        }
    }

    return result;
}
```

Note that `end` never needs an explicit reset when a partition closes: the very next iteration recomputes it from `max(end, last[...])`, but since `end == i` right when we close, and `start` moves to `i + 1`, the next character's own `last` value will always be `>= i + 1 > end`'s stale value, so the comparison still behaves correctly — `end` effectively starts tracking the new partition's reach from the next character onward.

## CS Fundamentals

### 1. Computer Networks (Scenario/Applied)

HTTP is described as a "stateless" protocol — the server treats every request as independent, with no memory of previous requests from the same client. Yet websites clearly remember you're logged in across many page loads. Explain the contradiction: what does "stateless" actually mean here, and mechanically, how do cookies and sessions bolt state on top of a protocol that has none?

**Answer:**

"Stateless" describes the **protocol**, not the application built on top of it. HTTP itself defines no concept of a connection that persists meaning between requests — each HTTP request contains, in principle, everything the server needs to process *that* request, and the server is not required to retain anything about it afterward. Request #2 from the same browser is, as far as bare HTTP is concerned, indistinguishable from a first-ever request from a totally different client. This is a deliberate design choice: statelessness is what lets any server behind a load balancer handle any request, with no need to route a client back to "the same server that remembers them" — a huge scalability win.

The problem is that almost every real website *needs* some notion of "this request belongs to the same user as that earlier one" (staying logged in, a shopping cart). Since the protocol won't carry that for you, the application layer fakes it, with two cooperating pieces:

1. **Cookies** are the transport mechanism. On an early response, the server sends a `Set-Cookie: session_id=abc123` header. The browser stores that value and automatically attaches `Cookie: session_id=abc123` to every subsequent request to that domain. This is the only part of "statelessness" that's actually being worked around at the protocol level — the browser, not the server, is doing the remembering and re-sending it every single time.
2. **Sessions** are where the actual state lives. The server never trusts the cookie's value as data in itself — it's just an opaque lookup key. On login, the server creates a session record (in memory, in a database, or in a distributed cache like Redis) keyed by `session_id`, holding whatever it needs: `user_id`, permissions, cart contents. Every incoming request's cookie is used to look that record up, and the server now has "memory" of the user for the duration of that one request — but it reconstructs that memory by lookup every time, rather than any request-to-request persistence inside the protocol itself.

So the mechanism is: the protocol stays genuinely stateless (no request depends on the server having kept anything from a prior one), while the *client* carries a token on every request that lets the *application* rebuild state server-side, on demand, each time. This is also why logging out is just deleting that session record (or the cookie) rather than "ending a connection" — there was never a persistent connection holding the state to begin with.

(A related, newer approach is **JWT-based auth**, where the token itself carries the user's claims, signed, so the server can verify it without a session-store lookup at all — trading a stateful session store for a slightly larger token and the complexity of revocation, which is harder when the server isn't keeping a lookup table it can simply delete from.)

### 2. OOP (Comparison)

Overloading, overriding, and polymorphism are three related but distinct ideas that get mixed up constantly. Define each one precisely, and explain how overriding is what actually makes runtime polymorphism possible — while overloading does not.

**Answer:**

**Overloading** is having multiple methods in the *same scope* (often the same class) that share a name but differ in their parameter list (number, types, or order of parameters). Which one gets called is decided by the compiler, purely from the *static* types of the arguments at the call site — this is **compile-time (static) dispatch**. `area(int radius)` and `area(int length, int width)` can coexist as overloads of `area`; the compiler picks based on how many arguments you pass and their types, before the program ever runs.

**Overriding** is a subclass providing its *own* implementation of a method that's already defined (with the identical signature) in its superclass. Unlike overloading, which the method lives purely at compile time, which implementation actually runs is decided **at runtime**, based on the *actual* (dynamic) type of the object the reference points to — not the type of the reference variable itself. This is **dynamic dispatch**.

**Polymorphism** ("many forms") is the broader capability this all serves: writing code that operates on a reference/pointer of a general (base/interface) type, while the specific behavior that executes depends on the concrete object actually behind that reference. `Shape* s = new Circle(); s->area();` calls `Circle`'s `area()`, even though the static type of `s` is just `Shape*`.

**Why overriding — not overloading — is what makes this work:** polymorphism's entire value is calling the *same* method name through a *base-type* reference and getting *object-specific* behavior back, resolved at runtime. Overriding is precisely that mechanism: the subclass's implementation replaces the base's for that exact signature, and the language's dynamic-dispatch machinery (in C++, a virtual function table; in Java, dispatch is virtual by default) looks up, at the moment of the call, which actual implementation belongs to the object's real runtime type — not the type the code happens to be written against.

Overloading cannot do this, because overload resolution happens at **compile time**, driven by the *static* type of the expression. Given `Shape* s = new Circle();`, the compiler decides which overload of a function to call by looking at `s`'s declared type (`Shape*`), never the object it happens to point to at runtime — there is no mechanism by which "the object turns out to be a `Circle`" can retroactively change which overload the compiler already locked in. So overloading gives you multiple *compile-time-selectable* variants of a name; overriding gives you one name whose *behavior* is selected *per actual object, at runtime* — and runtime-selected behavior through a common interface is the entire definition of polymorphism.

### 3. System Design Basics (Conceptual/Definition)

State the CAP theorem precisely — what do Consistency, Availability, and Partition tolerance each mean in this context, and why can a distributed system not simply have all three? Give a concrete example of a system that chooses each side of the trade-off.

**Answer:**

The CAP theorem says that a distributed data store, **when a network partition occurs** (some nodes can't communicate with others), must choose between two of the following and cannot preserve both:

- **Consistency (C)** — every read receives the most recent write, or an error. Every node that responds agrees on the current value; there is no stale or divergent data returned.
- **Availability (A)** — every request to a non-failing node receives a (non-error) response, even if it can't be guaranteed to be the most recent write.
- **Partition tolerance (P)** — the system continues to operate despite an arbitrary number of messages being dropped or delayed between nodes due to a network failure.

**Why you can't have all three.** Partition tolerance isn't really an optional design choice you can decline — in any real distributed system spanning more than one machine, network partitions *will* eventually happen (a switch fails, a data-center link drops, a node is slow enough to look partitioned). So the actual, practical trade-off CAP forces is: **when a partition happens, do you sacrifice consistency or availability?** Concretely: a node that gets cut off from the rest of the cluster receives a write request. It has exactly two choices:
- **Reject/block the request** (or forward it and wait, possibly forever, for the rest of the cluster) until it can confirm the rest of the cluster agrees — this preserves consistency but sacrifices availability, because that node is now refusing to serve requests it otherwise could.
- **Serve the request locally anyway**, using only what it can see — this preserves availability but risks inconsistency, because the rest of the cluster may be processing conflicting writes it has no way to know about right now.

There is no third option during the partition itself; you must pick which guarantee bends. (In normal operation, with no partition, a well-designed system can offer both C and A simultaneously — CAP is specifically about forced behavior *during* a partition.)

**Concrete examples:**
- **CP (Consistency + Partition tolerance, sacrifices Availability):** systems like **HBase**, **MongoDB** (in its default strongly-consistent configuration), or a traditional RDBMS replication setup configured for strong consistency. If a replica can't confirm with the primary/quorum during a partition, it refuses to answer reads/writes rather than risk serving stale or conflicting data — correctness over uptime. This fits something like a banking ledger, where returning a wrong balance is worse than returning an error.
- **AP (Availability + Partition tolerance, sacrifices Consistency):** systems like **Cassandra** or **DynamoDB** (in their typical tunable-consistency configurations), which keep answering reads and writes on every reachable node during a partition, and reconcile divergent data afterward (e.g. via vector clocks, last-write-wins, or application-level conflict resolution). This fits something like a shopping cart or a social media "like" counter, where it's far better to stay responsive and briefly show slightly stale data than to go down entirely.

The practical takeaway for system design interviews: naming CAP alone is table stakes — the useful discussion is *which* side a given feature should pick, because the right answer is different for a payments ledger than for a "number of likes on a post," and most real systems mix both choices across different subsystems rather than picking one globally.
