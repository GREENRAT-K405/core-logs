## DSA

### Question: Binary Tree Maximum Path Sum (Trees — Hard)

**Problem Statement**

Given the root of a binary tree, return the maximum **path sum** of any path in the tree. A path is a sequence of nodes where each pair of adjacent nodes in the sequence is connected by an edge. A node can appear in the sequence at most once, and the path does **not** need to pass through the root. The path must contain at least one node (itself), and node values may be negative.

**Input/Output Format**

- Input: the root of a binary tree, where each node's value satisfies `-1000 <= Node.val <= 1000`.
- Output: an integer, the maximum path sum achievable.

**Examples**

1. Tree `[1,2,3]` (root 1, left child 2, right child 3) → Output: `6`. The best path is `2 -> 1 -> 3`.
2. Tree `[-10,9,20,null,null,15,7]` → Output: `42`. The best path is `15 -> 20 -> 7`, entirely inside the right subtree, ignoring the root (`-10`) altogether.
3. Tree `[-3]` (a single node) → Output: `-3`. With only one node and no way to avoid including it, the "best" path is forced to be negative.

**Constraints**

- `1 <= number of nodes <= 3 * 10^4`
- `-1000 <= Node.val <= 1000`
- Aim for O(n) time.

### Step-by-Step Walkthrough

**Why brute force is wasteful.** The naive idea — for every node, try every possible path that passes through it — recomputes subtree sums over and over, giving something like O(n²). We want each node visited once.

**The key structural observation.** Any path in a binary tree has a single highest node — the one closest to the root among all nodes on that path. From that highest node, the path can go down into the left subtree, down into the right subtree, or both (bending at that node). It can never go "through" a node into a third direction, because a tree node only has two children and one parent, and once a path commits to going up to the parent it can't also use that parent's *other* child without that other child's subtree being reached via the parent, not via this node.

This means: **if we fix a node as the "peak" of the path, the best path through it is `node.val + bestDownwardPathInLeftSubtree + bestDownwardPathInRightSubtree`** (treating either side as contributing 0 if it would only hurt, i.e., if its best downward path is negative).

**Two different numbers, computed together.** For each node we need two things:
1. **The best path *through* this node, usable as a final answer** — because the path might end here, bending across both children. We fold this into a running global `best`.
2. **The best path *starting* at this node and extending into only one child, because if this node's parent wants to extend the path further up, the path can only continue through one branch of this node (a path can't fork).** This is the value we actually `return` from the recursive call, since it's the only thing a parent can use.

**Algorithm (post-order DFS).**
1. Define `maxGain(node)`: if `node` is null, return 0 (a path of length zero contributes nothing, and lets us skip a non-existent child cleanly).
2. Recursively compute `leftGain = max(maxGain(node->left), 0)` and `rightGain = max(maxGain(node->right), 0)`. Clamping to 0 is what lets us *not* extend the path into a subtree whose best contribution would actually lower the sum.
3. Update the global answer: `best = max(best, node->val + leftGain + rightGain)` — this is the best path that bends at `node` and uses both sides.
4. Return `node->val + max(leftGain, rightGain)` to the caller — the best *extendable* path rooted at `node`, using only the better of its two children.
5. After the DFS finishes at the root, `best` holds the answer.

**Why it's correct.** Every possible path in the tree has a unique highest node. When the DFS visits that node, `leftGain` and `rightGain` are, by induction, the correct best downward sums from its children (already clamped to never make things worse by skipping a bad subtree). So `node->val + leftGain + rightGain`, which we fold into `best` at exactly that visit, is exactly the best path peaking at that node. Since we take this max over every node in the tree, and every possible path's peak is visited exactly once, the overall maximum is found.

**Complexity.**
- Time: O(n) — each node is visited exactly once, doing O(1) work besides the recursive calls.
- Space: O(h) for the recursion stack, where `h` is the tree height (O(log n) for a balanced tree, O(n) worst case for a degenerate one).

### C++ Code

```cpp
#include <algorithm>
#include <climits>
using namespace std;

struct TreeNode {
    int val;
    TreeNode *left;
    TreeNode *right;
    TreeNode(int x) : val(x), left(nullptr), right(nullptr) {}
};

class Solution {
public:
    int maxPathSum(TreeNode* root) {
        int best = INT_MIN;
        maxGain(root, best);
        return best;
    }

private:
    // Returns the best sum of a downward path that STARTS at `node`
    // (i.e. the piece node's parent is allowed to extend upward).
    // Along the way, updates `best` with the best path that bends
    // AT `node`, using both children -- a path the parent can't reuse.
    int maxGain(TreeNode* node, int& best) {
        if (!node) return 0;

        // A negative contribution is never worth taking; clamping to 0
        // means "don't extend into this child at all."
        int leftGain = max(maxGain(node->left, best), 0);
        int rightGain = max(maxGain(node->right, best), 0);

        // The best path that bends at this node, using both sides at once.
        // This path cannot be extended further up, so it only ever
        // updates the global answer, never the return value.
        int throughNode = node->val + leftGain + rightGain;
        best = max(best, throughNode);

        // What a parent can actually use: this node plus at most ONE
        // child's contribution, since a path can't fork.
        return node->val + max(leftGain, rightGain);
    }
};
```

## CS Fundamentals

### 1. Operating Systems (Comparison)

What is the difference between a mutex and a semaphore? Both are used to manage access to a shared resource among concurrent threads — explain what each one actually represents, how a *counting* semaphore differs from a *binary* one, and why having one thread unlock a mutex that a different thread locked is undefined behavior, while the equivalent action is perfectly normal for a semaphore.

**Answer:**

Both are synchronization primitives, and a binary semaphore even *looks* like a mutex on the surface (a value that's either 0 or 1), which is exactly why the distinction is easy to blur — but they encode different concepts.

**A mutex (mutual exclusion lock) represents ownership.** It is a locking mechanism tied to the specific thread that acquired it: that thread, and only that thread, is expected to release it. Conceptually a mutex answers the question "is this resource currently being used, and by whom?" Many implementations actively enforce this — a `std::mutex` unlocked by a thread that never locked it is explicitly undefined behavior, and some OS-level mutex implementations store the owning thread ID internally and will error out (`EPERM`) if the wrong thread tries to unlock it.

**A semaphore represents a count of available permits, with no concept of ownership.** It's fundamentally a counter, decremented by `wait()`/`acquire()` and incremented by `signal()`/`release()`, used to control access to a pool of identical resources (e.g., "only 4 threads may hold a database connection at once"). A **counting semaphore** can take any non-negative integer value — initialize it to `N` and up to `N` threads can proceed concurrently. A **binary semaphore** is just a counting semaphore restricted to `{0, 1}`, which makes it *usable* like a mutex, but it still isn't one: nothing stops thread A from calling `wait()` and thread B from calling `signal()` on the same semaphore, because the semaphore has no idea which thread holds its single permit. This is precisely why it's normal (and a common pattern — e.g., in producer/consumer pipelines) for a semaphore to be signaled by a thread other than the one that waited on it: a producer thread signals a semaphore that a consumer thread is waiting on, and they are different threads by design.

**The practical consequence.** Use a mutex when the goal is "protect this critical section / shared state, and whoever enters must be the one who leaves" (ownership and symmetry matter). Use a semaphore when the goal is "signal between threads" or "cap concurrent access to N identical resources," where the thread that decrements the count is often, by design, not the same thread that increments it later (e.g., a bounded producer-consumer queue uses one semaphore to signal "slots free" and another to signal "items available," with producers and consumers on opposite ends of each).

### 2. Computer Networks (Conceptual/Definition)

When a browser connects to an HTTPS website, a TLS handshake happens before any actual HTTP request is sent. Walk through what happens during a TLS 1.3 handshake, and explain what role the Certificate Authority (CA) plays in letting the browser trust the server's identity.

**Answer:**

HTTPS is just HTTP sent over a TLS-encrypted connection, so before a single byte of the actual web page request goes out, the client and server have to agree on encryption keys and the client has to decide it trusts the server. That negotiation is the handshake.

**TLS 1.3 handshake, step by step:**

1. **ClientHello.** The browser sends the TLS versions and cipher suites it supports, plus — critically, as a 1.3 optimization — a set of "key share" values for a Diffie-Hellman key exchange, guessing which algorithm the server will pick. This guess-ahead is what lets TLS 1.3 finish in one round trip instead of two.
2. **ServerHello + certificate + key share.** The server picks a cipher suite, responds with its own key share (completing the Diffie-Hellman exchange so both sides can now independently derive the same symmetric session keys), and sends its **digital certificate** — which contains its public key and identity (domain name), signed by a Certificate Authority.
3. **Key derivation.** Both sides now independently compute the same shared secret from the exchanged key-share values (neither secret key ever crosses the wire — this is the whole point of Diffie-Hellman), and derive symmetric session keys from it.
4. **Certificate verification (client side).** The browser checks the server's certificate: is it signed by a CA the browser already trusts (chaining up to a trusted root CA baked into the OS/browser), is it for the right domain, and has it not expired or been revoked? If any of this fails, the browser shows the "connection is not private" warning instead of connecting.
5. **Finished messages.** Both sides send a MAC over the handshake transcript, encrypted with the just-derived keys, proving each side actually computed the same session keys. Once verified, the handshake is done and the connection switches to encrypting application data (the actual HTTP request) with the symmetric session keys.

**Why the CA matters.** Public-key cryptography alone proves the server knows a private key — it does **not** prove that the server is actually `www.example.com` rather than an attacker who generated their own key pair and claims to be `www.example.com`. The CA solves exactly this: it verifies (out of band, before issuing the certificate) that whoever requested the certificate actually controls the domain in question, then signs the certificate with the CA's own private key. The browser ships with a built-in list of trusted root CA public keys, so it can verify that signature itself, with no prior contact with that specific server. This is the chain of trust: Root CA → (optionally) Intermediate CA → Server certificate, and if every link's signature checks out back to a root the browser already trusts, the server's claimed identity is accepted. Without this, TLS would still give you *encryption* against a passive eavesdropper, but it would give you no protection against a **man-in-the-middle** actively impersonating the server.

### 3. System Design Basics (Scenario/Applied)

You're running a single PostgreSQL database for a growing application, and read traffic is starting to overwhelm it even though writes are still relatively low. You decide to add leader-follower (primary-replica) replication. Explain how this works, the difference between synchronous and asynchronous replication, and what specific problem your application will need to handle as a consequence.

**Answer:**

**The setup.** One database instance is designated the **leader** (primary): it's the only node that accepts writes. One or more **follower** (replica) instances continuously receive a stream of the leader's changes — typically by shipping the leader's write-ahead log (WAL) and replaying it — and keep their own copy of the data up to date. The application's read traffic is then spread across the followers (and optionally the leader too), while all writes still go to the single leader. This directly attacks the read-overload problem: read capacity now scales roughly linearly by adding more followers, without touching how writes are handled at all.

**Synchronous vs. asynchronous replication — the trade-off is latency vs. durability/freshness guarantees:**

- **Synchronous replication:** the leader waits for at least one follower to confirm it has received (and often applied) the write *before* the leader reports the write as committed back to the client. This guarantees that a committed write is never lost even if the leader dies immediately after — a follower already has it. The cost is that every write now pays the network round-trip latency to that follower, and if that follower is slow or unreachable, writes stall.
- **Asynchronous replication:** the leader commits the write and tells the client it succeeded immediately, without waiting for any follower. Writes stay fast and aren't affected by follower health. The cost is a window where the leader has data no follower has yet — if the leader crashes in that window, those last few writes can be lost permanently, even though the client was already told they succeeded.

Most real systems (including PostgreSQL's default streaming replication) use asynchronous replication for this latency reason, sometimes with one designated **synchronous** follower for a middle ground: guaranteed durability on at least that one replica, at the cost of that replica's latency.

**The consequence the application must handle: replication lag.** Because followers apply changes slightly after the leader (milliseconds under normal load, but potentially much more under load spikes or network hiccups), a follower can briefly serve **stale data**. The classic failure mode: a user submits a form (write goes to the leader), the page immediately redirects and re-reads the data (read goes to a lagging follower), and the user sees their own just-submitted change missing or reverted — which looks like a bug even though both the write and the read individually "worked." Standard mitigations: **read-your-own-writes consistency** (route a user's reads to the leader, or to a follower known to be caught up, for a short window right after that same user writes), monitoring replication lag and routing reads away from a follower that falls too far behind, or simply accepting eventual consistency for read paths where slightly stale data is acceptable (e.g., a public product listing, as opposed to "did my payment go through").
