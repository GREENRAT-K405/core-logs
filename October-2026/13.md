## DSA

### Question: Jump Game II (Greedy — Medium)

You are given a 0-indexed array of non-negative integers `nums` of length `n`. You are initially positioned at index `0`. Each element `nums[i]` represents the maximum jump length from that position — that is, from index `i`, you may jump to any index in the range `[i + 1, i + nums[i]]`.

Return the **minimum number of jumps** required to reach the last index (`n - 1`). It is guaranteed that you can always reach the last index.

**Input format:** an array of integers `nums`.
**Output format:** a single integer, the minimum number of jumps.

**Example 1:**
```
Input:  nums = [2,3,1,1,4]
Output: 2
Explanation: Jump 1 step from index 0 to index 1, then 3 steps to the last index (1 -> 4).
```

**Example 2:**
```
Input:  nums = [2,3,0,1,4]
Output: 2
Explanation: Jump from index 0 to index 1 (step 2), then from index 1 to index 4 (step 3).
```

**Example 3:**
```
Input:  nums = [1,1,1,1,1]
Output: 4
Explanation: Only one step is possible from each position, so every index must be visited.
```

**Constraints:**
- `1 <= n <= 10^4`
- `0 <= nums[i] <= 1000`
- It is guaranteed that you can reach `nums[n - 1]`.

### Step-by-Step Walkthrough

**Reframing the problem.** Think of each index as a node and each possible jump as a directed edge. Finding the minimum number of jumps to go from index `0` to index `n - 1` is exactly a shortest-path problem on this implicit graph, and since all edges have the same "cost" (one jump), the answer is the BFS shortest-path distance. We don't need to build the graph explicitly — we can simulate BFS level-by-level using the jump ranges directly, which turns it into a greedy, single-pass algorithm.

**The greedy/BFS-levels idea.** At any point, think of "level `k`" as the set of indices reachable using exactly `k` jumps. We don't track the whole set — only two numbers:
- `currentEnd`: the farthest index reachable using the jumps taken so far (the right boundary of the current BFS level).
- `farthest`: the farthest index reachable by jumping from *any* index we've scanned so far within the current level.

As we scan `i` from `0` to `n - 2`, we update `farthest = max(farthest, i + nums[i])` — this explores every node in the current level. When `i` reaches `currentEnd` (i.e., we've finished scanning every node in the current level), we know the current level is exhausted, so we commit to taking one more jump: increment `jumps`, and set the new `currentEnd = farthest`, which becomes the boundary of the next level.

**Why this is correct.** Every index inside `[previousEnd + 1, currentEnd]` is reachable in exactly `jumps` jumps (by definition of BFS levels), and `farthest` computed while scanning that range is precisely the best boundary for level `jumps + 1`. Because BFS levels expand monotonically and we never need to "go back" (jump ranges are determined solely by position and value, not by history), a greedy choice — always pushing the boundary as far as possible within the current level — can never do worse than any alternative strategy. This greedy choice is optimal because any index reachable at all from the current level is reachable using the single farthest-reaching jump within that level; no jump saved by being "less greedy" is ever needed.

**Termination.** We stop scanning early once `currentEnd >= n - 1`, since the last index is already within the current level and no further jumps are needed. The loop only needs to go up to `n - 2` (i.e., `i < n - 1`) because once we are *at* the last index there's nothing left to jump from.

**Complexity.** Each index is visited once: **O(n) time**. We only keep three integer counters: **O(1) extra space**.

### C++ Code

```cpp
#include <vector>
#include <algorithm>
using namespace std;

class Solution {
public:
    int jump(vector<int>& nums) {
        int n = nums.size();
        if (n <= 1) return 0; // already at the last index, no jumps needed

        int jumps = 0;
        int currentEnd = 0;   // farthest index reachable using 'jumps' jumps so far
        int farthest = 0;     // farthest index reachable by exploring the current level

        // Only need to scan up to n - 2: once we're AT the last index we're done.
        for (int i = 0; i < n - 1; ++i) {
            farthest = max(farthest, i + nums[i]);

            // We've finished exploring every index in the current BFS level.
            if (i == currentEnd) {
                ++jumps;
                currentEnd = farthest;

                // The last index is already within reach; no need to scan further.
                if (currentEnd >= n - 1) break;
            }
        }

        return jumps;
    }
};
```

Traced against the examples: `[2,3,1,1,4]` -> 2, `[2,3,0,1,4]` -> 2, `[1,1,1,1,1]` -> 4, all matching the expected outputs.

## CS Fundamentals

### 1. OOP (Comparison)

Compare composition and inheritance as mechanisms for code reuse in object-oriented design. When should each be preferred, and why is "favor composition over inheritance" considered good practice?

**Answer:**

Inheritance models an **"is-a"** relationship: a subclass inherits the fields and methods of a base class and can override its behavior. Composition models a **"has-a"** relationship: an object holds a reference to another object and delegates part of its behavior to it.

Inheritance's main weakness is tight coupling across the class hierarchy. A subclass depends not just on the base class's public interface but often on its internal implementation details (the "fragile base class" problem) — a seemingly safe change to the base class can silently break every subclass. Inheritance is also fixed at compile time and is single-rooted in most languages (no multiple inheritance of implementation in Java/C#, for instance), which makes it inflexible when an object needs to combine behaviors from multiple, unrelated sources.

Composition avoids these issues: the containing object only depends on the composed object's public interface, components can be swapped at runtime (enabling patterns like Strategy or Decorator), and an object can compose as many collaborators as it needs without hierarchy constraints. The cost is slightly more boilerplate — you must explicitly write delegating methods instead of getting them "for free."

In practice: use **inheritance** when there is a genuine, stable is-a relationship and you want to leverage polymorphism (e.g., `Circle` and `Square` both are `Shape`s and are substitutable wherever a `Shape` is expected — the Liskov Substitution Principle should hold). Use **composition** when you want to reuse behavior without committing to a rigid taxonomy, when the relationship might change at runtime, or when you'd otherwise need multiple inheritance. "Favor composition over inheritance" doesn't mean "never use inheritance" — it means reach for composition first because it produces more decoupled, flexible, and testable systems, and reserve inheritance for cases where polymorphic substitutability is genuinely the goal.

### 2. Computer Networks (Conceptual)

Explain TCP's three-way handshake (SYN, SYN-ACK, ACK). What problem does it solve, and what piece of information is each side confirming at each step?

**Answer:**

TCP is a connection-oriented, reliable protocol, so before either side sends application data, both ends must agree on a set of **initial sequence numbers (ISNs)** and confirm that both directions of the connection are actually working. The three-way handshake accomplishes this:

1. **SYN** — The client picks a random initial sequence number `client_ISN` and sends a segment with the `SYN` flag set, announcing: "I want to open a connection, and my byte stream will start at sequence number `client_ISN`."
2. **SYN-ACK** — The server receives the SYN, picks its own random initial sequence number `server_ISN`, and replies with both the `SYN` and `ACK` flags set. The `ACK` field is `client_ISN + 1`, confirming receipt of the client's SYN, while the `SYN` with `server_ISN` announces the server's own starting sequence number for its byte stream back to the client.
3. **ACK** — The client receives the SYN-ACK and replies with an `ACK` segment whose acknowledgment number is `server_ISN + 1`, confirming it received the server's SYN.

After this exchange, both sides have proven two things to each other: that they can *receive* data from the other side (since each ACK can only be constructed after receiving the peer's sequence number), and that they can *send* data to the other side (since the peer actually received and responded to the segment). This is why a two-way handshake would be insufficient — the initiator would never get proof that its own SYN was actually delivered until the first data exchange, and sequence numbers couldn't be reliably synchronized in both directions at once.

Random, unpredictable ISNs also exist for a security reason: if sequence numbers were predictable (e.g., always starting at 0 or incrementing in a simple counter), an attacker could guess them and inject spoofed packets into the stream or hijack the connection (TCP sequence number prediction attacks).

### 3. DBMS (Scenario)

You're designing the database for a high-traffic e-commerce product catalog. Reads (browsing, search, product pages) vastly outnumber writes (price/inventory updates). A fully normalized schema (3NF) would require joining `products`, `categories`, `brands`, and `inventory` tables on every product-listing page load. Would you normalize, denormalize, or use a hybrid approach? Justify your reasoning.

**Answer:**

This is a classic **read-heavy workload** tradeoff between normalization (optimizes for write consistency and storage efficiency) and denormalization (optimizes for read latency at the cost of redundancy and write complexity).

Full 3NF normalization minimizes data redundancy and guarantees that updates (e.g., renaming a category) only touch one row, avoiding update anomalies. But it forces every page load to perform multiple joins across `products`, `categories`, `brands`, and `inventory` — expensive at scale, especially under high read concurrency, since joins don't parallelize or cache as cleanly as flat row reads.

Given reads vastly outnumber writes here, a **hybrid approach** is the right call rather than an all-or-nothing choice:

- Keep the **normalized schema as the source of truth** for writes (price changes, inventory updates, category edits) — this preserves consistency guarantees and avoids update anomalies where it matters (inventory and pricing must never drift out of sync).
- Maintain a **denormalized read model** for the catalog-browsing path: a flattened `product_listing` table or materialized view that pre-joins category name, brand name, and a cached inventory-availability flag directly onto each product row. This is what the product page and search index actually query, so a page load becomes a single-row (or single-index) lookup instead of a multi-table join.
- Keep the denormalized copy in sync via either (a) application-level writes that update both the normalized tables and the read model in the same transaction/outbox pattern, (b) a materialized view refreshed on a short interval (acceptable if slight staleness, e.g., a few seconds of lag on a category rename, is tolerable), or (c) a cache layer (Redis) in front of the normalized data, invalidated on write.
- For inventory specifically, which changes far more often than catalog metadata, it's often worth keeping it in its own fast-updating table (or even a separate store) rather than baking exact counts into the denormalized listing — showing "in stock" as a cached boolean with a short TTL is usually acceptable even if the exact count is only fetched normalized at checkout time, where correctness actually matters.

The underlying principle: normalize where write-consistency correctness is non-negotiable (inventory counts, prices), and denormalize the read path where staleness of a few seconds is an acceptable tradeoff for dramatically lower read latency and database load — because the system is overwhelmingly read-dominated.
