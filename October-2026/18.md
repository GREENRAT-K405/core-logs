### Question: Text Justification (Strings — Hard)

**Problem Statement**

Given an array of strings `words` and an integer `maxWidth`, format the text so that each line has exactly `maxWidth` characters and is **fully (left and right) justified**.

Pack as many words as possible into each line, using a **greedy** approach: pick up words left to right until the next word doesn't fit. Then pad the line with spaces so that it is exactly `maxWidth` characters long:

- For a line that is **not** the last line and has **more than one word**, distribute the extra spaces as evenly as possible between the words; if the spaces don't divide evenly, the **earlier** gaps (left to right) get one extra space each.
- For the **last line**, or for any line that ends up with only **one word**, left-justify it: a single space between words, and all the extra padding goes on the right.

Return the list of formatted lines.

**Input/Output Format**

- Input: `vector<string> words` (each word is non-empty, contains no spaces, and has length `<= maxWidth`), and an integer `maxWidth`.
- Output: `vector<string>`, one fully formatted line per entry, each of length exactly `maxWidth`.

**Examples**

1. `words = ["This","is","an","example","of","text","justification."]`, `maxWidth = 16`
   → `["This    is    an", "example  of text", "justification.  "]`
   (Line 1 has 3 words / 2 gaps and 8 extra spaces → 4 and 4. Line 2 has 3 words / 2 gaps and 3 extra spaces → 2 and 1, the earlier gap getting the extra one. Line 3 is the last line, so it's left-justified with trailing padding.)

2. `words = ["Hello","World"]`, `maxWidth = 11`
   → `["Hello World"]`
   (Only one line, and it's also the last line, so it's left-justified; it happens to already be exactly 11 characters, so no padding is needed.)

3. `words = ["Edge","cases","matter","immensely","here"]`, `maxWidth = 10`
   → `["Edge cases", "matter    ", "immensely ", "here      "]`
   (Lines 2 and 3 each end up with a single word — "matter" doesn't fit with "immensely", and "immensely" doesn't fit with "here" — so both are left-justified with right padding even though neither is the last line. Only the genuinely last line, "here", is left-justified for that reason too; the rule that triggers is "single word", not "last line", for lines 2 and 3.)

**Constraints**

- `1 <= words.length <= 300`
- `1 <= words[i].length <= 20`
- `words[i]` consists of only lowercase/uppercase English letters and punctuation, no spaces.
- `1 <= maxWidth <= 100`
- `words[i].length <= maxWidth`

### Step-by-Step Walkthrough

**Break the problem into two independent sub-problems.** The hard part isn't one algorithm, it's that there are two unrelated jobs happening in sequence: (1) decide *which words go on which line*, then (2) decide *how to pad a given set of words into exactly `maxWidth` characters*. Solving them separately makes each one easy.

**Sub-problem 1 — greedy line packing.** For the current line, start with an empty line length and keep adding words left to right as long as they fit *with at least one space before each additional word*: if `currentLength + 1 + nextWord.length() > maxWidth`, stop — that word starts the next line. This greedy choice is actually optimal here (not just a heuristic): since every word must appear, and words are placed in a fixed left-to-right order, packing as many words as will fit onto the current line can never do worse than stopping early — stopping early only ever leaves *more* words for later lines, never fewer.

**Sub-problem 2 — padding a line once its words are fixed.** Two cases:
- *Single word, or the last line overall:* join words with a single space (irrelevant if there's only one word), then append spaces on the right until the line reaches `maxWidth`. There is no "middle" to stretch — either there's nothing to stretch between, or the rule explicitly says not to stretch the last line.
- *Multiple words, not the last line:* let `totalLetters` = sum of the words' lengths, `numGaps` = `numWords - 1`, `totalSpaces` = `maxWidth - totalLetters`. Every gap gets at least `totalSpaces / numGaps` spaces (`baseSpaces`); the remainder `totalSpaces % numGaps` can't be split evenly, so hand one extra space each to the first `remainder` gaps, left to right (this matches the problem's tie-breaking rule and keeps text looking more natural, front-loaded rather than back-loaded).

**Why check `numWords == 1` separately.** If a line ends up with exactly one word (because the next word simply doesn't fit, independent of whether more words remain overall), `numGaps` would be zero and `totalSpaces / numGaps` is a division by zero. The problem statement sidesteps this by defining that case as left-justified too — which conveniently also avoids the crash.

**Complexity.**
- Time: O(total characters in `words`) for the line-packing pass, plus O(total characters in the output) for building the padded strings — each word and each output character is touched a constant number of times. Since the output size is itself bounded by `numLines * maxWidth`, overall it's O(N + L·maxWidth) where N is the total input length and L is the number of lines — effectively linear in the size of the output, which is the best possible since every output character must be written.
- Space: O(L·maxWidth) for the result (unavoidable — that's the output), O(1) extra beyond that.

### C++ Code

```cpp
#include <vector>
#include <string>
using namespace std;

vector<string> fullJustify(vector<string>& words, int maxWidth) {
    vector<string> result;
    int n = static_cast<int>(words.size());
    int i = 0;

    while (i < n) {
        // Greedily collect words for this line: start with words[i] alone,
        // then keep adding words while they still fit with a mandatory
        // single space before each one.
        int lineLen = static_cast<int>(words[i].size());
        int j = i + 1;
        while (j < n) {
            if (lineLen + 1 + static_cast<int>(words[j].size()) > maxWidth) break;
            lineLen += 1 + static_cast<int>(words[j].size());
            j++;
        }

        int numWords = j - i;
        bool isLastLine = (j == n);
        string line;

        if (isLastLine || numWords == 1) {
            // Left-justify: single spaces between words, pad the remainder on the right.
            for (int k = i; k < j; k++) {
                if (k > i) line += ' ';
                line += words[k];
            }
            while (static_cast<int>(line.size()) < maxWidth) line += ' ';
        } else {
            // Fully justify: spread the extra spaces across the gaps, earlier
            // gaps getting the leftover one first.
            int totalLetters = 0;
            for (int k = i; k < j; k++) totalLetters += static_cast<int>(words[k].size());

            int numGaps = numWords - 1;
            int totalSpaces = maxWidth - totalLetters;
            int baseSpaces = totalSpaces / numGaps;
            int extra = totalSpaces % numGaps;

            for (int k = i; k < j; k++) {
                line += words[k];
                if (k < j - 1) {
                    int gapIndex = k - i;
                    int spaces = baseSpaces + (gapIndex < extra ? 1 : 0);
                    line += string(spaces, ' ');
                }
            }
        }

        result.push_back(line);
        i = j;
    }

    return result;
}
```

### 1. Operating Systems (Conceptual/Definition)

What is a deadlock, and what are the four necessary conditions (the Coffman conditions) for one to occur? Give a short concrete example showing all four.

**Answer:**

A deadlock is a state where two or more threads/processes are each waiting for a resource held by another member of the same group, and none of them can ever proceed, because the wait is circular and nothing external breaks it. It's distinct from mere contention or slowness — a deadlocked set of threads will wait forever, not just for a while.

Four conditions must **all** hold simultaneously for a deadlock to be possible; prevent any one of them and deadlock becomes impossible by construction. That's why they're worth memorizing precisely — they're a checklist for deadlock-proofing a system, not just trivia.

1. **Mutual exclusion.** At least one resource is held in a non-shareable mode — only one thread can use it at a time (e.g., a lock, a single DB connection).
2. **Hold and wait.** A thread holds at least one resource while simultaneously waiting to acquire another resource that's currently held by someone else.
3. **No preemption.** Resources can't be forcibly taken away from the thread holding them; they're only released voluntarily.
4. **Circular wait.** There's a cycle of threads T1 → T2 → ... → Tn → T1, where each Ti is waiting for a resource held by T(i+1).

**Concrete example.** Thread A locks resource `X`, then tries to lock `Y`. Thread B locks resource `Y`, then tries to lock `X`. Check each condition: `X` and `Y` are each held exclusively (mutual exclusion); both threads hold one lock while waiting for the other (hold and wait); neither lock can be yanked away by the system (no preemption); A waits on B and B waits on A, which is a two-node cycle (circular wait). All four hold, so this configuration is permanently stuck — it isn't bad luck, it's guaranteed by the logic.

**Why this matters practically.** The standard fix exploited in real codebases is breaking circular wait: establish a global lock ordering (e.g., "always acquire the lock with the smaller address/id first") so a cycle can never form, since every thread acquires resources in the same relative order. Other strategies target the other conditions — e.g., requiring threads to request all resources up front (attacks hold-and-wait), or using a lock that supports timeouts and forces a thread to release what it holds and retry (attacks no-preemption) — but ordering locks consistently is by far the cheapest to reason about and the most common in practice.

### 2. Computer Networks (Comparison)

Compare TCP and UDP. Why would a real-time video call application typically prefer UDP over TCP, despite TCP's reliability guarantees?

**Answer:**

Both are transport-layer protocols sitting on top of IP, but they make opposite trade-offs between reliability and latency.

| | TCP | UDP |
| --- | --- | --- |
| Connection | Connection-oriented (3-way handshake) | Connectionless — just send |
| Reliability | Guaranteed delivery via ACKs + retransmission | No delivery guarantee |
| Ordering | Guarantees in-order delivery | No ordering guarantee |
| Flow/congestion control | Yes — adapts send rate to receiver and network | None built in |
| Overhead | Higher (headers, handshake, ACKs, state) | Lower (minimal 8-byte header, stateless) |
| Head-of-line blocking | Yes — a lost packet blocks everything after it until retransmitted | No — later packets are delivered immediately |
| Typical use | Web pages, file transfer, email — anything where correctness matters more than instant delivery | DNS, live video/audio, online gaming — anything where freshness matters more than completeness |

**Why video calls choose UDP.** The core issue is TCP's **retransmission + in-order delivery** combination, which is exactly wrong for a live stream. If packet 100 is lost, TCP will not hand packet 101 (which already arrived) to the application until packet 100 is retransmitted and received — this is head-of-line blocking. For a file download that's fine: you'll wait a few extra milliseconds and get a byte-perfect file. For a live video call, that lost packet probably represented a single frame from a fraction of a second ago. By the time it's retransmitted and the stream can "catch up," that frame is stale — nobody wants to see it. It's strictly better to drop it, keep playing the frames that *do* arrive, and let the visual briefly glitch or blur, than to freeze the entire call waiting for ancient data.

So real-time applications build what they need **on top of UDP** instead: they accept out-of-order/missing packets, hide small gaps with jitter buffers, use their own light-weight sequence numbers to detect loss, and sometimes apply forward error correction, but they explicitly reject TCP's "wait and retransmit" behavior because *recent-but-imperfect* beats *complete-but-late* for a live medium. Protocols like RTP (often inside WebRTC) are the concrete embodiment of this choice. The general lesson: TCP is the right default, but any time staleness is worse than loss, UDP (plus a thin application-level protocol) is usually the better fit.

### 3. DBMS (Scenario/Applied)

An `orders` table has a separate non-unique index on `customer_id` and a separate non-unique index on `order_date`. A reporting query runs `SELECT * FROM orders WHERE customer_id = ? AND order_date > ?`. Explain why having two single-column indexes usually doesn't give you the performance you'd expect for this query, and how a composite index changes that.

**Answer:**

**Why two single-column indexes underperform here.** Each index is a separate sorted structure (typically a B-tree) mapping its own column's values to row locations. The query planner can use *at most one* of them to actually narrow down rows efficiently for a single table scan path in most engines — it picks whichever index looks more selective (say, `customer_id`, assuming a given customer has relatively few orders), seeks to the matching entries, and retrieves those row locations. But that index only knows about `customer_id` — it has no idea which of those rows also satisfy `order_date > ?`. So the engine must fetch each candidate row (often via an extra lookup back to the table, called a "bookmark lookup" or using the clustered index) and check the date condition in memory, one row at a time. If a customer has thousands of orders, you pay that per-row fetch-and-filter cost thousands of times even though the final result set might be tiny.

(Some engines, like certain modes of MySQL/PostgreSQL, can perform "index intersection" — using both indexes and intersecting the row-ID sets before touching the table — but this is comparatively rare, has its own overhead, and isn't something you should rely on; it's never as efficient as a single targeted range scan.)

**How a composite index fixes it.** Build one index on `(customer_id, order_date)`. A composite B-tree index is sorted first by `customer_id`, and *within each `customer_id` group*, sorted by `order_date`. That ordering is exactly what this query needs: the engine seeks directly to the start of this customer's block (via the `customer_id` equality predicate), and because entries for that customer are already sorted by date, it can do one contiguous **range scan** from `order_date > ?` to the end of that customer's block — no filtering of unrelated rows, no revisiting the index from scratch, no wasted row fetches outside the actual answer set.

**Why column order matters (the leftmost-prefix rule).** `(customer_id, order_date)` supports both "`customer_id = ?`" alone and "`customer_id = ? AND order_date > ?`" efficiently, because both queries use a prefix of the index's column order. The reverse index, `(order_date, customer_id)`, would *not* help this query well — matching an equality on `customer_id` would require scanning across unrelated dates first, since the index's primary sort key is the date, not the customer. The rule of thumb: put equality-filtered columns before range-filtered columns in a composite index.

**One more lever — covering indexes.** If the query only needed a few columns (say `order_id` and `total`) rather than `SELECT *`, you could extend the index to `(customer_id, order_date, order_id, total)` and let the engine answer the query *entirely from the index*, never touching the underlying table at all (a "covering index"). That's the next optimization step once the basic composite index is in place, though `SELECT *` as given here would defeat it since it needs every column anyway.
