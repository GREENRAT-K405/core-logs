### Question: Search in Rotated Sorted Array (Sorting/Searching — Medium)

There is an integer array `nums` sorted in ascending order (with **distinct** values). Prior to being passed to your function, `nums` is **rotated** at an unknown pivot index `k` (`0 <= k < nums.length`), so that it becomes `[nums[k], nums[k+1], ..., nums[n-1], nums[0], nums[1], ..., nums[k-1]]` (0-indexed).

Given the rotated array `nums` and an integer `target`, return the index of `target` if it is in `nums`, or `-1` if it is not.

You must write an algorithm with `O(log n)` runtime complexity.

**Input format:**
- An integer array `nums`, rotated at some unknown pivot, all values distinct.
- An integer `target`.

**Output format:**
- The index of `target` in `nums`, or `-1` if it doesn't exist.

**Worked Examples:**

1. `nums = [4,5,6,7,0,1,2]`, `target = 0` → Output: `4` (0 sits at index 4).
2. `nums = [4,5,6,7,0,1,2]`, `target = 3` → Output: `-1` (3 is not present anywhere in the array).
3. `nums = [1]`, `target = 0` → Output: `-1` (single-element array, target absent).

**Constraints:**
- `1 <= nums.length <= 5000`
- `-10^4 <= nums[i] <= 10^4`
- All values of `nums` are **unique**.
- `nums` is guaranteed to be an ascending array that has possibly been rotated.
- `-10^4 <= target <= 10^4`

---

### Step-by-Step Walkthrough

**Approach — Modified Binary Search**

A plain binary search needs a fully sorted array to decide which half to discard. Here the array isn't globally sorted, but it has a crucial property: **at least one of the two halves around any midpoint is always sorted** (because the array is just a sorted array split into two contiguous sorted blocks and swapped).

So at each step of the binary search:

1. Compute `mid`. If `nums[mid] == target`, we're done — return `mid`.
2. Determine which half is the sorted one by comparing `nums[left]` with `nums[mid]`:
   - If `nums[left] <= nums[mid]`, the **left half** `[left..mid]` is sorted (no rotation point inside it).
   - Otherwise, the **right half** `[mid..right]` must be the sorted one.
3. Once we know which half is sorted, we can cheaply check with ordinary comparisons whether `target` could lie inside that sorted half's value range:
   - If the sorted half is the left one and `nums[left] <= target < nums[mid]`, the target (if present) must be there, so search `[left, mid-1]`. Otherwise it must be in the other half, so search `[mid+1, right]`.
   - Symmetrically if the sorted half is the right one: if `nums[mid] < target <= nums[right]`, search `[mid+1, right]`, else search `[left, mid-1]`.
4. Repeat until `left > right` (not found, return `-1`) or the target is found.

**Why it works:** Every iteration still halves the search space exactly like standard binary search — we've just added one extra `O(1)` check per iteration to figure out *which* half is safe to reason about with ordinary "is target within this range" logic. The algorithm never needs to actually know where the rotation pivot is; it only needs local information at each midpoint.

**Complexity Analysis:**
- **Time complexity:** `O(log n)` — each iteration discards half of the remaining search space, exactly as in standard binary search.
- **Space complexity:** `O(1)` — only a constant number of index variables are used, no recursion or extra storage.

### C++ Code

```cpp
#include <vector>
#include <iostream>
using namespace std;

class Solution {
public:
    // Returns the index of 'target' in the rotated sorted array 'nums', or -1.
    int search(vector<int>& nums, int target) {
        int left = 0, right = (int)nums.size() - 1;

        while (left <= right) {
            int mid = left + (right - left) / 2;

            if (nums[mid] == target) {
                return mid;
            }

            if (nums[left] <= nums[mid]) {
                // Left half [left..mid] is sorted.
                if (nums[left] <= target && target < nums[mid]) {
                    right = mid - 1;   // target in the sorted left half
                } else {
                    left = mid + 1;    // target must be in the right half
                }
            } else {
                // Right half [mid..right] is sorted.
                if (nums[mid] < target && target <= nums[right]) {
                    left = mid + 1;    // target in the sorted right half
                } else {
                    right = mid - 1;   // target must be in the left half
                }
            }
        }

        return -1; // target not found
    }
};

int main() {
    Solution sol;

    vector<int> nums1 = {4, 5, 6, 7, 0, 1, 2};
    cout << "search([4,5,6,7,0,1,2], 0) = " << sol.search(nums1, 0) << " (expected 4)" << endl;

    vector<int> nums2 = {4, 5, 6, 7, 0, 1, 2};
    cout << "search([4,5,6,7,0,1,2], 3) = " << sol.search(nums2, 3) << " (expected -1)" << endl;

    vector<int> nums3 = {1};
    cout << "search([1], 0) = " << sol.search(nums3, 0) << " (expected -1)" << endl;

    return 0;
}
```

**Trace against the examples:**
- `nums = [4,5,6,7,0,1,2]`, `target = 0`: `mid=3` (`nums[3]=7`). Left half `[4,5,6,7]` is sorted (`nums[0]=4 <= 7`), but `0` isn't in `[4,7)`, so move right: `left=4`. Now `mid=5` (`nums[5]=1`). Left half `[0,1]` sorted (`nums[4]=0 <= 1`), and `0` is in `[0,1)`, so move left: `right=4`. Now `left=right=4`, `nums[4]=0 == target` → return `4`. ✓
- `nums = [4,5,6,7,0,1,2]`, `target = 3`: the same narrowing process never finds a range containing `3`, and the loop terminates with `left > right` → returns `-1`. ✓
- `nums = [1]`, `target = 0`: `mid=0`, `nums[0]=1 != 0`. Left half `[1]` is trivially sorted, but `0` is not in `[1,1)`, so `left = mid+1 = 1`. Now `left > right` → returns `-1`. ✓

### 1. OOP (Comparison)

Compare **abstract classes** and **interfaces** in object-oriented programming. What are the key structural differences, and when would you choose one over the other in a real design?

**Answer:**

| Aspect | Abstract Class | Interface |
|---|---|---|
| Definition | A class that cannot be instantiated directly and may contain both fully implemented methods and unimplemented (pure virtual / abstract) methods. | A pure contract that declares method signatures (and sometimes default implementations, in languages like Java 8+) with no instance state of its own. |
| State | Can hold member variables / fields and constructors to initialize shared state. | Traditionally cannot hold instance state (only constants); nothing to construct. |
| Inheritance model | A class can usually extend only **one** abstract class (single inheritance of implementation). | A class can implement **multiple** interfaces, giving a form of multiple inheritance of type. |
| Purpose | Models an "is-a" relationship with **shared implementation** — a common base with some behavior already filled in. | Models a "can-do" capability/contract — unrelated classes can all promise to support the same operations without sharing any implementation or ancestry. |
| C++ equivalent | A class with at least one pure virtual function (`virtual void f() = 0;`) that also has normal member functions/data. | A class with **only** pure virtual functions and no data members (sometimes called a "pure abstract class" or "protocol class" in C++). |

**Example (C++):**

```cpp
// Abstract class: shares state (name) and a concrete method (describe()),
// but leaves area() to be implemented by subclasses.
class Shape {
protected:
    string name;
public:
    Shape(string n) : name(n) {}
    void describe() { cout << name << " has area " << area() << endl; } // shared behavior
    virtual double area() const = 0; // must be overridden
};

// Interface-like class: pure contract, no state, no shared implementation.
class Serializable {
public:
    virtual string toJson() const = 0;
    virtual ~Serializable() {}
};

class Circle : public Shape, public Serializable {
    double radius;
public:
    Circle(double r) : Shape("Circle"), radius(r) {}
    double area() const override { return 3.14159 * radius * radius; }
    string toJson() const override { return "{\"radius\":" + to_string(radius) + "}"; }
};
```

**When to choose which:** Use an **abstract class** when a family of related types shares real, reusable implementation and state (e.g., all `Shape`s store a `name` and share a `describe()` method) — it avoids duplicating that logic in every subclass. Use an **interface** when unrelated classes need to promise the same capability without being forced into the same inheritance hierarchy (e.g., `Circle`, `Report`, and `UserProfile` can all implement `Serializable` even though they share nothing else) — this keeps designs flexible and avoids the fragility of deep, forced inheritance chains.

### 2. Computer Networks (Scenario/Applied)

A client opens a TCP connection to a server, sends a request, receives the response, and then closes the connection cleanly. Walk through what happens during the **three-way handshake** at the start and the **four-way termination** at the end, and explain why each step exists.

**Answer:**

**Connection establishment — three-way handshake:**

1. **SYN:** The client picks an initial sequence number (ISN_c) and sends a segment with the `SYN` flag set, announcing "I want to start a connection, and my byte stream will start at sequence number ISN_c."
2. **SYN-ACK:** The server responds with its own `SYN` (announcing its own initial sequence number, ISN_s) combined with an `ACK` of the client's SYN (acknowledging ISN_c + 1). This single segment does two jobs at once — that's why it's only three steps instead of four.
3. **ACK:** The client acknowledges the server's SYN (ISN_s + 1) with a plain `ACK`. At this point both sides have confirmed they can send *and* receive, so the connection moves to `ESTABLISHED` and data can flow.

*Why three steps, not two:* A two-way handshake would let the client confirm the server can receive, but the server would never get confirmation that the client can actually receive its reply — a lost or duplicate old SYN could otherwise cause the server to half-open a connection with no client on the other end. The third step closes that gap on both sides.

**Connection termination — four-way termination:**

1. The client (having no more data to send) sends a `FIN`.
2. The server acknowledges it with an `ACK`. At this point the client→server direction is closed, but the server might still have data left to send, so the connection is only "half-closed."
3. Once the server also has nothing more to send, it sends its own `FIN`.
4. The client acknowledges that with an `ACK`, and then enters a `TIME_WAIT` state for a bounded interval (typically 2×Maximum Segment Lifetime) before fully releasing the connection's resources.

*Why four steps, not two:* TCP connections are full-duplex — each direction (client→server and server→client) must be closed independently, since one side may still have data to send after the other side is done. That's why closing takes one `FIN`/`ACK` pair per direction. *Why `TIME_WAIT`:* it ensures any delayed/duplicate packets still in flight from the old connection are drained before the same (IP, port) pair could be reused for a new connection, preventing data from an old connection from being misinterpreted as part of a new one.

### 3. Computer Architecture (Conceptual/Definition)

What is **pipelining** in CPU design? Name the main types of hazards that can disrupt a pipeline, and briefly describe how each is typically mitigated.

**Answer:**

**Pipelining** is a CPU design technique that overlaps the execution of multiple instructions by splitting instruction processing into sequential stages (commonly: Fetch, Decode, Execute, Memory access, Write-back) and letting different instructions occupy different stages simultaneously — much like an assembly line. Instead of waiting for one instruction to fully finish before starting the next, a new instruction enters the pipeline every clock cycle, which dramatically increases instruction throughput even though the latency of any single instruction doesn't decrease (and may slightly increase due to pipeline register overhead).

**Hazards** are situations where the next instruction cannot execute in its designated clock cycle because of a conflict, and they come in three main types:

1. **Structural hazards** — Two instructions in the pipeline need the same hardware resource at the same time (e.g., a single shared memory unit needed for both an instruction fetch and a data load in the same cycle). *Mitigation:* duplicate the resource (e.g., separate instruction and data caches/memories, the classic Harvard-style split) or add arbitration logic/stall one of the instructions.

2. **Data hazards** — An instruction depends on the result of a previous instruction that hasn't finished producing that result yet (e.g., `ADD R1, R2, R3` immediately followed by `SUB R4, R1, R5`, where `R1` isn't ready yet). *Mitigation:* **forwarding/bypassing** (route the result directly from the Execute or Memory stage back into a later stage's input before it's officially written back) when possible, and **stalling** (insert pipeline bubbles) when forwarding can't resolve the dependency in time (e.g., a load immediately followed by a dependent use, known as a load-use hazard).

3. **Control hazards** — Caused by branches/jumps, where the pipeline doesn't know which instruction to fetch next until the branch is resolved (often several stages later). *Mitigation:* **branch prediction** (statically or dynamically guess the branch outcome and speculatively fetch down that path, flushing and rolling back on a misprediction), or simpler schemes like **delay slots** (always execute a fixed instruction after a branch regardless of outcome) or just stalling until the branch resolves (cheap but slow).

**Why this matters:** Modern high-performance CPUs rely heavily on deep pipelining combined with aggressive forwarding and branch prediction to keep instruction throughput close to one instruction per cycle; understanding these hazards is central to reasoning about why certain code patterns (tight dependency chains, unpredictable branches) run slower than their instruction count alone would suggest.
