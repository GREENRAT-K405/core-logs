## DSA

### Question: Alien Dictionary (Graphs — Hard)

**Problem Statement**

There is a new alien language that uses the English alphabet, but the order among the letters is unknown. You are given a list of `words` from this language's dictionary, where the words are **sorted lexicographically** according to this alien language's (unknown) rules.

Derive the order of letters in this language, and return it as a string. If there is no valid order (the constraints imply a cycle), return `""`. If there are multiple valid orders, return **any one** of them.

**Input/Output Format**

- Input: `words`, a list of lowercase strings, sorted according to the alien ordering.
- Output: a string containing each distinct letter that appears in `words` exactly once, in a valid alien alphabetical order — or `""` if no valid order exists.

**Examples**

1. Input: `["wrt","wrf","er","ett","rftt"]` → Output: `"wertf"`
2. Input: `["z","x"]` → Output: `"zx"`
3. Input: `["z","x","z"]` → Output: `""` (implies `z < x` and `x < z` simultaneously — a cycle, so invalid)

**Constraints**

- `1 <= words.length <= 100`
- `1 <= words[i].length <= 100`
- `words[i]` consists only of lowercase English letters.
- All words in `words` are unique.

### Step-by-Step Walkthrough

**Reframing the problem.** "Derive the alphabet order from a sorted word list" is really "derive an ordering between individual letters, then combine those pairwise facts into one global order." The two words `"wrt"` and `"wrf"` being adjacent in sorted order tells us something very specific: at the first position where they differ, the letter from the earlier word must come before the letter from the later word in the alien alphabet. That's a **directed edge**: `t → f`, meaning `t` precedes `f`.

So the natural model is a **directed graph** where nodes are letters and an edge `u → v` means "`u` comes before `v`". Once that graph is built, "find a valid overall letter order consistent with all the pairwise constraints" is exactly **topological sort**.

**Building the graph.** Walk every pair of *adjacent* words in the list (we only need adjacent pairs — ordering is transitive, so if `a < b` and `b < c` are both enforced, `a < c` follows automatically through the topological sort, we don't need to compare `a` and `c` directly). For each pair `(a, b)`:
1. Scan characters together until the first index where `a[j] != b[j]`. Add the edge `a[j] → b[j]` (if not already present) and bump `b[j]`'s in-degree.
2. If no differing character is found within the shorter word's length (one word is a prefix of the other), the *only* valid case is `a` being no longer than `b` (e.g. `"ab"` before `"abc"` is fine). If `a` is longer than `b` with `b` a prefix of `a` (e.g. `"abc"` before `"ab"`), that's a contradiction no letter ordering can fix — return `""` immediately.

**Topological sort via Kahn's algorithm.** Track in-degree for every distinct letter seen (initialized to 0 so letters with no incoming constraint still appear). Seed a queue with every letter currently at in-degree 0 — these can safely be placed first. Repeatedly pop a letter, append it to the answer, and for each letter it points to, decrement that letter's in-degree; if it hits 0, it's now safe to place, so enqueue it.

**Why a leftover letter means a cycle.** If the graph has a cycle (as in example 3: `z → x → z`), every letter on that cycle always has at least one unsatisfied incoming edge, so none of them ever reaches in-degree 0 and none is ever enqueued. At the end, `order.size() < (number of distinct letters)` — that gap is exactly the signature of a cycle, so we return `""`.

**Complexity.**
- Let `C` = total length of all words, `V` ≤ 26 distinct letters, `E` ≤ `V·(V-1)` possible edges.
- Building the graph: each adjacent pair costs `O(min(len(a), len(b)))` to compare, so overall `O(C)`.
- Kahn's algorithm: `O(V + E)`, and since `V ≤ 26` this is effectively constant, bounded by a small constant regardless of input size.
- Total: **O(C)** time, **O(V + E)** extra space for the graph (so O(1) in practice since the alphabet is capped at 26).

### C++ Code

```cpp
#include <vector>
#include <string>
#include <unordered_map>
#include <unordered_set>
#include <queue>
#include <algorithm>
using namespace std;

string alienOrder(vector<string>& words) {
    // adj[c] = set of letters that must come immediately after c in some
    // directly-observed constraint. indegree[c] = number of letters that
    // must come before c.
    unordered_map<char, unordered_set<char>> adj;
    unordered_map<char, int> indegree;

    // Register every letter that appears anywhere, with indegree 0 so far.
    for (const string& w : words) {
        for (char c : w) {
            if (indegree.find(c) == indegree.end()) {
                indegree[c] = 0;
                adj[c] = {};
            }
        }
    }

    // Derive one edge per adjacent pair of words from their first
    // differing character.
    for (size_t i = 0; i + 1 < words.size(); i++) {
        const string& a = words[i];
        const string& b = words[i + 1];
        size_t minLen = min(a.size(), b.size());
        bool foundDiff = false;

        for (size_t j = 0; j < minLen; j++) {
            if (a[j] != b[j]) {
                // a[j] must precede b[j] in the alien alphabet.
                if (adj[a[j]].insert(b[j]).second) {
                    indegree[b[j]]++;
                }
                foundDiff = true;
                break;
            }
        }

        // No differing character: 'a' must not be the longer word, or the
        // sorted order given to us is self-contradictory.
        if (!foundDiff && a.size() > b.size()) {
            return "";
        }
    }

    // Kahn's algorithm: letters with no unresolved prerequisite go first.
    queue<char> ready;
    for (auto& entry : indegree) {
        if (entry.second == 0) {
            ready.push(entry.first);
        }
    }

    string order;
    while (!ready.empty()) {
        char c = ready.front();
        ready.pop();
        order += c;

        for (char next : adj[c]) {
            if (--indegree[next] == 0) {
                ready.push(next);
            }
        }
    }

    // Fewer letters placed than exist means some letters never reached
    // indegree 0 -- a cycle in the constraints, so no valid order exists.
    if (order.size() != indegree.size()) {
        return "";
    }
    return order;
}
```

## CS Fundamentals

### 1. OOP (Conceptual/Definition)

What is the Liskov Substitution Principle (the "L" in SOLID)? Give a concrete example of code that violates it, and explain how you'd fix the design.

**Answer:**

The **Liskov Substitution Principle** states that if `S` is a subtype of `T`, then objects of type `T` in a program may be replaced with objects of type `S` without altering any of the desirable properties of that program (correctness, expected behavior, invariants). In plain terms: a subclass must honor the *behavioral contract* of its base class, not just its method signatures. Inheriting is a promise about behavior, not just a way to reuse a type name.

**Classic violation — Rectangle/Square.** Suppose `Rectangle` has `setWidth(w)` and `setHeight(h)`, each mutating one dimension independently, with an implicit invariant that the two are independent. Now make `Square extends Rectangle`, overriding `setWidth` and `setHeight` so that each one sets *both* dimensions equal (to keep it a square):

```cpp
class Rectangle {
public:
    virtual void setWidth(int w) { width = w; }
    virtual void setHeight(int h) { height = h; }
    int area() const { return width * height; }
protected:
    int width = 0, height = 0;
};

class Square : public Rectangle {
public:
    void setWidth(int w) override { width = height = w; }
    void setHeight(int h) override { width = height = h; }
};
```

Now take code written against `Rectangle` that assumes width and height vary independently:

```cpp
void resize(Rectangle& r) {
    r.setWidth(5);
    r.setHeight(4);
    assert(r.area() == 20); // holds for any real Rectangle
}
```

Pass a `Square` in, and the assertion fails: `setHeight(4)` silently also rewrites the width, so `area()` is `16`, not `20`. The code is correct for the base type but breaks the moment a `Square` is substituted in — a textbook LSP violation. The bug isn't "`Square` is buggy code"; it's that inheritance was used to model an "is-a" relationship (a square *is* mathematically a kind of rectangle) while ignoring that the *behavioral* contract (independent mutable dimensions) is not something a square can honor.

**The fix.** Don't force a parent/child relationship where the subtype can't uphold the supertype's contract. Options, in order of preference:
1. **Don't inherit at all** — make `Rectangle` and `Square` both implement a common read-only `Shape` interface exposing only `area()`, with no mutable setters in the shared contract. Mutation, if needed, is type-specific (`Square::setSide(int)`).
2. **Make the base type immutable** — if `Rectangle` only exposes a constructor and `area()`, there's no mutating contract to violate, and `Square` can genuinely substitute for it everywhere.
3. If you must keep the mutable hierarchy, **weaken the base class's exposed contract** so it never promises independent-axis mutation in the first place — but this usually just reintroduces the same problem under a different name, which is why (1) is the usual real answer.

The general lesson: LSP violations are a sign the type hierarchy is modeling *taxonomy* ("a square is a rectangle" — true in geometry) instead of *behavioral substitutability* ("can code written against the base type keep working, unmodified, when handed a derived instance?" — false here). Favoring composition and narrow interfaces over deep inheritance trees is the usual way to sidestep this class of bug entirely.

### 2. Computer Architecture (Scenario/Applied)

You have a quad-core CPU where each core has its own private L1 cache, and all cores share the same main memory. Core A reads a variable `x` into its L1 cache, then Core B writes a new value to `x`. What goes wrong if there's no cache coherence mechanism, and how does the MESI protocol prevent it?

**Answer:**

**The problem without coherence.** Each core's L1 cache is a private, fast copy of a subset of main memory. If Core A reads `x` (say, `x = 5`) into its L1, it now holds a cached copy. If Core B then writes `x = 10` — and that write only updates Core B's own cache (or even goes straight to main memory) — Core A's cached copy still reads `5`. Core A has no mechanism to know its copy is now stale. The two cores now disagree about the value of the same memory location, silently and indefinitely. This breaks every assumption concurrent code relies on: a lock release Core B performs might never become visible to Core A, a flag Core A spins on might never update, and so on. This is **not a race-condition bug in the program** — it's the hardware itself failing to maintain a single consistent view of memory.

**MESI's fix: track a state per cache line, and talk to each other.** MESI names four states a cache line can be in, in *any* given core's cache:

- **Modified (M):** this core has the only copy, and it's been written — it differs from main memory and this cache is responsible for eventually writing it back.
- **Exclusive (E):** this core has the only copy, and it matches main memory (no write yet).
- **Shared (S):** this line may also be cached by other cores, and all copies match main memory.
- **Invalid (I):** this cache's copy (if any) is not usable and must be re-fetched.

Cores enforce coherence by **snooping** a shared bus (or an equivalent directory/interconnect protocol) and reacting to each other's cache-line transactions:

1. Core A reads `x`: its cache is empty, so the line is fetched from memory, marked **Exclusive**.
2. Core B also reads `x`: it notices (via snooping) Core A already holds the line. Both caches downgrade to **Shared** — both now agree it's safe to read, and neither owns it exclusively.
3. Core B now writes `x`: before completing the write, Core B must broadcast an **invalidate** for that line. Every other core snooping the bus — including Core A — sees this and transitions its copy of the line from Shared to **Invalid**, discarding it. Core B's own copy becomes **Modified**.
4. If Core A now tries to read `x` again, its cache sees the line is Invalid, so it's forced to fetch the current value — either from main memory or (in real implementations) directly from Core B's Modified cache line — getting `10`, not the stale `5`.

The key mechanism is step 3: **a write can't silently happen in one core's cache while another core still thinks its own stale copy is valid.** The invalidation broadcast is what forces every other core to notice and discard its outdated copy before it can be read again, which is exactly what restores a single consistent view of `x` across all cores — without it, A would read stale data forever; with it, A is forced to refetch and sees B's write. This is also why heavy false sharing (two unrelated variables that happen to sit on the same cache line, written by different cores) is a real performance hazard: every write triggers this invalidate/refetch dance even though the cores aren't logically touching the same data.

### 3. Operating Systems (Comparison)

Compare mutexes and semaphores. What does each actually guarantee, and when would a counting semaphore be the right tool where a mutex would not work at all?

**Answer:**

Both are synchronization primitives used to control access to a shared resource, and both are frequently (and wrongly) used interchangeably, but they answer different questions and are backed by different invariants.

**Mutex (mutual exclusion lock).** A mutex is a binary lock with a notion of **ownership**: exactly one thread can hold it at a time, and — critically — the thread that locked it is the only thread allowed to unlock it. Its entire purpose is protecting a critical section so that at most one thread executes it at once, preventing data races on shared state.

**Semaphore.** A semaphore is an integer counter with two atomic operations: `wait()`/`acquire()` (decrement; block if the result would go below zero) and `signal()`/`release()` (increment; wake a waiter if any). Crucially, a semaphore has **no ownership concept** — any thread can call `signal()`, even one that never called `wait()`. A **binary semaphore** (counter capped at 1) looks superficially like a mutex, but without ownership enforcement it's weaker: nothing stops thread B from "releasing" a resource thread A never actually acquired, which is a correctness hazard a real mutex rules out by construction.

| | Mutex | Semaphore |
| --- | --- | --- |
| Core value | Binary (locked/unlocked) | Integer counter (bounded by initial value) |
| Ownership | Yes — only the locking thread may unlock | No — any thread may signal |
| Purpose | Protect a critical section (mutual exclusion) | Manage availability of N interchangeable resource slots, or signal between threads |
| Typical misuse | — | Used as a mutex substitute, losing ownership safety |

**Where a counting semaphore does something a mutex structurally cannot: bounding concurrent access to a pool of N identical resources.** Suppose you have a connection pool of 10 database connections, and up to 10 threads should be allowed to hold a connection concurrently — not 1, and not unlimited. Initialize a semaphore to 10. Each thread calls `wait()` before taking a connection (the 11th thread blocks until someone calls `signal()`) and `signal()` after releasing it. A mutex cannot express this at all — it only has two states, "available" and "held by exactly one," with no notion of "held by up to N." You'd need N separate mutexes and a scheme to pick a free one, which is just reimplementing a counting semaphore badly.

Semaphores are also the right tool for pure **signaling** between threads with no shared critical section involved at all — e.g., a producer thread calling `signal()` once per item produced, and a consumer thread calling `wait()` once per item it wants to consume, where the semaphore's count literally *is* the number of items available. A mutex has no notion of "signal this happened N times"; a semaphore's counter is built for exactly that.

**The practical rule of thumb:** reach for a mutex when the goal is "only one thread in this critical section, and whoever locked it must unlock it." Reach for a counting semaphore when the goal is "allow up to N concurrent holders" or "count/signal events between threads" — anything where the binary ownership model of a mutex doesn't match the actual resource-counting or signaling semantics you need.
