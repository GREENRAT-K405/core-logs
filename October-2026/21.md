## DSA

### Question: Copy List with Random Pointer (Linked Lists — Medium)

**Problem Statement**

A linked list is given where each node contains an additional `random` pointer, which could point to any node in the list, or to `null`. Construct a **deep copy** of the list — every new node's `val` must match the original, and every new node's `next` and `random` pointers must point to nodes *within the new list* (never back into the original list).

Return the head of the copied list.

**Input/Output Format**

- Input: the head of a linked list where each node is `{int val; Node* next; Node* random;}`.
- Output: the head of a fully independent deep copy with the same structure, `next` chain, and `random` targets (re-pointed to the corresponding new nodes).

**Examples**

1. Nodes (by index) `0,1,2,3` with `val = [7,13,11,10]` and `random = [null, 0, 4→null, 2]` (i.e. node 0's random is null, node 1's random points to node 0, node 2's random points to itself, node 3's random points to node 2).
   → A new list of 4 nodes with the same `val`s, the same `next` chain `0→1→2→3`, and `random` pointers landing on the *corresponding new* nodes (new-1's random → new-0, new-2's random → new-2 itself, new-3's random → new-2).

2. `val = [1,2]`, `random = [1, 1]` (both nodes' random points to node 1).
   → A 2-node copy where both new nodes' `random` point to the new node 1 — not the original node 1.

3. `val = [3]`, `random = [null]` (single node, no self/other random target).
   → A single new node with `val = 3`, `next = null`, `random = null`.

**Constraints**

- `0 <= n <= 1000` nodes.
- `-10^4 <= val <= 10^4`.
- `random` is `null` or points to some node in the list (possibly itself).
- Aim for O(n) time; both O(n) and O(1) extra space (excluding the output) are acceptable, but explain the trade-off.

### Step-by-Step Walkthrough

**Why a naive copy doesn't work.** If we just allocate a new node for each original node and copy `val`, we still need `random` (and `next`) on the *new* list to point at *new* nodes, not old ones. The catch is that when we're copying node `i`, its `random` pointer may target a node we haven't created yet (e.g. node 3's random points backward to node 2, but node 2's random points to itself, and node 1's random points even further back to node 0 — targets can point anywhere, forward or backward, including nodes not yet visited in a single left-to-right pass). We need a way to look up "the new node corresponding to old node X" regardless of visit order.

**Approach 1 — hash map (old → new), two passes.** This is the direct, easy-to-reason-about solution:
1. **Pass 1:** walk the original list once. For every original node, create a *new* node holding the same `val` (leave `next`/`random` unset for now), and record the mapping `oldNode → newNode` in a hash map.
2. **Pass 2:** walk the original list again. For each original node `cur`, set `map[cur]->next = map[cur->next]` (or `nullptr` if `cur->next` is null) and `map[cur]->random = map[cur->random]` (or `nullptr` if `cur->random` is null).
3. Return `map[head]` (or `nullptr` if the list was empty).

This works because by the time pass 2 runs, *every* original node already has its new counterpart sitting in the map — order of traversal no longer matters, since we're not building pointers on the fly, we're looking them up.

**Why this is correct.** The map gives a total, O(1)-lookup function from "old node identity" to "new node identity." Since every `next` and `random` target in the original list is itself some node already in the map (or null), substituting each old pointer with `map[old pointer]` reproduces the exact same graph shape, just entirely over new nodes — none of the new list's pointers ever alias back into the old list.

**Approach 2 — O(1) extra space via interleaving (worth knowing).** Instead of a hash map, splice each new node directly after its original counterpart: `old1 → new1 → old2 → new2 → ...`. Then `new_i->random` can be found as `old_i->random->next` (the new node interleaved right after the old random target), and `new_i->next` is `old_i->next->next`. A final pass detaches the interleaved list back into two separate lists, restoring the original list to its initial state. This trades the O(n) hash map for three O(n) passes over the same interleaved structure — same time complexity, but O(1) *extra* space (not counting the output copy itself). The hash-map approach is simpler to get right and is the one implemented below; the interleaving trick is the standard follow-up when an interviewer asks for O(1) space.

**Complexity (hash-map approach).**
- Time: O(n) — two linear passes over the list.
- Space: O(n) — the hash map holds one entry per node, plus O(n) for the new list itself (which is the required output, not "extra").

### C++ Code

```cpp
#include <unordered_map>
using namespace std;

class Node {
public:
    int val;
    Node* next;
    Node* random;
    Node(int _val) : val(_val), next(nullptr), random(nullptr) {}
};

class Solution {
public:
    Node* copyRandomList(Node* head) {
        if (!head) return nullptr;

        // Pass 1: create every new node, map old -> new.
        unordered_map<Node*, Node*> oldToNew;
        for (Node* cur = head; cur != nullptr; cur = cur->next) {
            oldToNew[cur] = new Node(cur->val);
        }

        // Pass 2: wire up next/random on the new nodes using the map,
        // so pointer targets created "out of order" are already available.
        for (Node* cur = head; cur != nullptr; cur = cur->next) {
            oldToNew[cur]->next = cur->next ? oldToNew[cur->next] : nullptr;
            oldToNew[cur]->random = cur->random ? oldToNew[cur->random] : nullptr;
        }

        return oldToNew[head];
    }
};
```

A subtle correctness point worth calling out: both passes must index the map with the *original* node (`cur`, `cur->next`, `cur->random`), never with a new node — the map's keys are exclusively old-list identities, so looking it up with anything else is a bug that would silently return `nullptr` for every lookup (since that new node was never inserted as a key).

### 1. Computer Architecture (Comparison)

Compare RISC and CISC instruction set philosophies. Why did RISC "win" inside modern high-performance CPUs even though x86 (a CISC design) still dominates desktops and servers?

**Answer:**

**RISC (Reduced Instruction Set Computer)** uses a small set of simple, fixed-length instructions, each doing one basic operation (add, load, store, branch) and typically executing in a single clock cycle. Complex operations are built by composing several simple instructions. Examples: ARM, RISC-V, MIPS.

**CISC (Complex Instruction Set Computer)** uses a larger, variable-length instruction set where a single instruction can encode a multi-step operation (e.g. one `x86` instruction can load from memory, perform arithmetic, and store the result back, all in one encoded instruction). The goal historically was to reduce the number of instructions per program and keep programs compact, which mattered when memory was scarce and compilers were primitive.

| | RISC | CISC |
| --- | --- | --- |
| Instruction count per program | More instructions | Fewer, denser instructions |
| Instruction complexity | Simple, uniform, fixed-length | Complex, variable-length |
| Cycles per instruction | Mostly 1 | Varies, often multiple |
| Decoder complexity | Simple | Complex (must handle many formats) |
| Pipelining | Easy — uniform instructions pipeline cleanly | Harder — variable-length/complex instructions complicate pipeline stages |
| Example ISAs | ARM, RISC-V, MIPS | x86/x86-64 |

**Why RISC "won" at the micro-architectural level.** Pipelining and superscalar execution (issuing multiple instructions per cycle) are dramatically easier to build when every instruction is simple and uniform in length and cost — the decoder, scheduler, and execution units don't need special-case logic for a long tail of complex instruction forms. This is exactly why RISC-style designs dominate where pipeline depth, power efficiency, and instruction-level parallelism matter most: mobile SoCs, embedded systems, and now Apple's M-series and most server-grade ARM chips.

**Why x86 still dominates desktops/servers anyway.** Software compatibility and decades of ecosystem lock-in (compilers, operating systems, binaries) matter more commercially than ISA purity. Intel and AMD resolved the apparent contradiction by **translating CISC to RISC internally**: modern x86 chips decode the complex, variable-length x86 instructions into simpler internal **micro-ops**, which then flow through a RISC-like pipelined, superscalar, out-of-order execution core. So the CISC instruction set is really just a compatibility-preserving *frontend* — the actual execution hardware underneath has looked RISC-like for decades. This is why the "RISC vs. CISC" debate is less about raw performance today and more about instruction decode overhead and power efficiency, which is where ARM's simpler, fixed-length decode still gives it an edge, especially on battery-powered devices.

### 2. Computer Networks (Scenario/Applied)

You're designing a live video call feature and a file-download feature for the same app. One should use UDP, the other TCP. Which is which, and why would using the wrong one actively make each feature worse — not just "theoretically suboptimal"?

**Answer:**

**File download → TCP. Live video/voice call → UDP (typically, via RTP over UDP).** The reasoning comes down to what each transport actually guarantees and what each application actually needs.

**TCP** guarantees reliable, in-order, complete delivery: lost packets are retransmitted, out-of-order packets are reordered, and the receiving application only ever sees a correct, gap-free byte stream — at the cost of added latency (retransmission waits for timeout/ACK) and head-of-line blocking (a single lost packet stalls delivery of everything after it, even packets that already arrived, until the gap is filled).

**UDP** is connectionless and makes no delivery guarantees at all: packets can be lost, duplicated, or arrive out of order, and the application gets whatever shows up, whenever it shows up, with no retransmission and no reordering — but with minimal latency overhead, since there's no waiting for acknowledgments.

**Why the match matters, not just "which is faster":**
- A **file download** has no deadline on any individual byte, but it is *useless* if even one byte is silently wrong or missing — a corrupted executable or a `.zip` with a missing chunk is a broken file. TCP's guarantees are exactly what's needed, and the latency cost of occasional retransmission is irrelevant to overall throughput over a multi-second/minute transfer. Using UDP here would require re-implementing TCP's reliability logic (ordering, retransmission, flow control) yourself just to get a usable file — strictly worse, not just "less safe."
- A **live video call** has the opposite priority: a frame from half a second ago is *useless* even if it eventually arrives perfectly intact, because the call has moved on — stale data is worse than no data. If this ran over TCP, a single lost packet would stall the entire stream (head-of-line blocking) while TCP retransmits and reorders, causing the call to freeze and then jump, compounding latency with every loss on a lossy network (e.g. mobile data). UDP lets the application simply skip the lost/late frame and keep playing the next one that arrives — producing a brief glitch instead of a stall, which is far more acceptable for real-time media. Any reliability the application does want (e.g. periodic keyframes, forward error correction, or light application-level retransmission for audio) is implemented selectively on top of UDP, at the specific points where it's worth the latency cost — not uniformly, the way TCP forces it.

The general principle: pick TCP when **correctness of the whole** matters more than timeliness of any one piece (downloads, web pages, API calls, database traffic); pick UDP when **timeliness of the latest piece** matters more than guaranteeing every piece arrives (live video/voice, multiplayer game state, DNS queries).

### 3. DBMS (Conceptual/Definition)

What is a B+ tree, and why do virtually all relational databases use it (rather than a plain binary search tree or a hash table) as the default structure for a table index?

**Answer:**

A **B+ tree** is a self-balancing, multi-way (not binary) search tree where every key lives at a **leaf** node, leaves are **linked together** in sorted order, and internal nodes exist purely to route a search down to the correct leaf — they hold no actual row data, only keys and child pointers used for navigation. Every leaf sits at the same depth, so the tree stays perfectly balanced by construction, and each node typically holds many keys (tens to hundreds), not just one or two.

**Why not a plain binary search tree (BST)?** A BST's node holds exactly one key and has at most two children, and a database index can hold millions of rows. A balanced BST over N keys still needs O(log₂ N) *disk reads* in the worst case to walk from root to leaf — and each read from disk is vastly slower (by orders of magnitude) than a read from RAM. For a million rows, log₂(10⁶) ≈ 20 disk reads per lookup. A B+ tree instead makes each node as large as one disk page (typically 4–16 KB) and packs it with hundreds of keys, giving a much higher **branching factor**. That turns the same million rows into a tree of depth 3–4 instead of 20 — because each level of the tree divides the search space by hundreds, not by 2. Since disk I/O (or even a cache-line fetch) dominates the real-world cost, minimizing the *number of node reads* (not the number of key comparisons) is what actually matters, and that's precisely what a high branching factor buys.

**Why not a hash table?** A hash index gives O(1) average lookup for exact-match (`WHERE id = 5`), which sounds strictly better — but it destroys **ordering**. Hash tables scatter keys pseudo-randomly across buckets, so they cannot efficiently answer range queries (`WHERE age BETWEEN 20 AND 30`), prefix queries (`WHERE name LIKE 'Al%'`), or `ORDER BY`/`MIN`/`MAX` — all of which are extremely common in real query workloads. A B+ tree's leaves are linked in sorted order specifically so that a range scan is just "find the start leaf, then walk the leaf-level linked list forward" — no re-traversal of the tree needed per row.

**Why leaves are linked and data isn't stored in internal nodes.** Keeping internal nodes data-free maximizes how many keys fit per page (more fan-out, shallower tree), and the leaf-level linked list turns range scans and ordered iteration into a simple sequential walk instead of repeated tree descents. This combination — high fan-out for shallow depth, plus sorted sequential leaves for range scans — is exactly why the B+ tree is the default index structure in MySQL (InnoDB), PostgreSQL, Oracle, and SQL Server: it gives good performance for both point lookups and range queries, which covers the overwhelming majority of real SQL workloads, whereas a hash index is reserved for the narrower case of pure equality lookups.
