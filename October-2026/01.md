## DSA

### Question: Group Anagrams (Hashing/Maps — Medium)

**Problem Statement**

Given an array of strings `strs`, group the anagrams together. Two strings are anagrams if one can be rearranged into the other (same letters, same multiplicity, any order). Return the groups in any order; the strings within a group can be in any order too.

**Input/Output Format**

- Input: an array of strings `strs`, each consisting of lowercase English letters.
- Output: a list of lists of strings — each inner list is one anagram group.

**Examples**

1. Input: `["eat","tea","tan","ate","nat","bat"]` → Output: `[["eat","tea","ate"],["tan","nat"],["bat"]]`
2. Input: `[""]` → Output: `[[""]]`
3. Input: `["a"]` → Output: `[["a"]]`

**Constraints**

- `1 <= strs.length <= 10^4`
- `0 <= strs[i].length <= 100`
- `strs[i]` consists of lowercase English letters only.

### Step-by-Step Walkthrough

**The brute-force approach first.** Compare every string against every other string to check if they're anagrams of each other (e.g., by sorting both and comparing), then union them into groups. That's O(n^2) comparisons just to find the groups, which is wasteful — we're redoing the same "are these anagrams" check over and over instead of recognizing that anagram-ness is really an equivalence relation with a natural canonical form.

**Key insight — a canonical key per anagram class.** Two strings are anagrams of each other if and only if they reduce to the *same* canonical representation. Two natural choices for that representation:
1. **Sorted string.** Sorting `"eat"` and `"tea"` and `"ate"` all produce `"aet"`. Anagrams always sort to the identical string, and non-anagrams never do.
2. **Character-count signature.** Since the alphabet is fixed (lowercase a-z), build a 26-length count array for each string and use it (or a string built from it, e.g. `"a2b0c1..."`) as the key. Anagrams always produce the identical count array.

Either way, the problem collapses into: *compute a key for every string, then bucket strings by key using a hash map.* That's a single pass plus one hash-map insert per string — no pairwise comparison needed at all.

**The algorithm (sorted-string key, simplest to implement correctly).**
1. Create a hash map from `string -> vector<string>` (key → group).
2. For each string `s` in `strs`: copy it, sort the copy's characters, and use that sorted copy as the key. Append the *original* string `s` to `map[key]`.
3. After the pass, the map's values are exactly the anagram groups. Collect them into the result list.

**Why it's correct.** Sorting is a canonical form for the multiset of characters in a string: two strings sort to the same result if and only if they contain exactly the same characters with the same multiplicities, which is the precise definition of being anagrams. So grouping by the sorted key partitions the input exactly into anagram-equivalence classes — nothing is grouped incorrectly, and nothing that belongs together is split apart.

**Complexity.**
- Time: O(n · k log k), where `n` is the number of strings and `k` is the maximum string length — sorting each string dominates. (Using the count-signature key instead gives O(n · k), trading the `log k` for a fixed 26-slot pass per string.)
- Space: O(n · k) to store all the strings and keys in the map.

### C++ Code

```cpp
#include <vector>
#include <string>
#include <unordered_map>
#include <algorithm>
using namespace std;

vector<vector<string>> groupAnagrams(vector<string>& strs) {
    unordered_map<string, vector<string>> groups;

    for (const string& s : strs) {
        string key = s;
        sort(key.begin(), key.end()); // canonical form: anagrams sort identically
        groups[key].push_back(s);     // bucket the ORIGINAL string under that key
    }

    vector<vector<string>> result;
    result.reserve(groups.size());
    for (auto& entry : groups) {
        result.push_back(move(entry.second));
    }
    return result;
}
```

### 1. OOP (Comparison)

What is the difference between compile-time polymorphism and runtime polymorphism? Give a concrete mechanism for each and explain why one can be resolved earlier than the other.

**Answer:**

Both let the "same name" behave differently depending on context, but they differ in *when* the decision about which code actually runs gets made.

**Compile-time polymorphism** (also called static binding or early binding) is resolved by the compiler using only information available in the source code — no object's runtime type is involved. The classic mechanism is **function overloading**: multiple functions share a name but differ in parameter types or count, e.g. `add(int, int)` vs `add(double, double)`. The compiler looks at the argument types at the call site and picks the matching overload before the program ever runs. Operator overloading works the same way.

**Runtime polymorphism** (dynamic binding, late binding) is resolved while the program is executing, based on the *actual* type of the object behind a pointer or reference — not its declared/static type. The mechanism is **virtual functions** (method overriding): a base class declares a method `virtual`, and derived classes override it. A call through a base-class pointer, like `shape->draw()`, is dispatched via a **vtable** (virtual function table) lookup — the compiler can't know at compile time whether `shape` points to a `Circle` or a `Square`, so the actual function address is looked up at the call, adding a small indirection cost.

| | Compile-time | Runtime |
| --- | --- | --- |
| Resolved by | Compiler, from argument types | Vtable lookup, from actual object type |
| Mechanism | Overloading | Overriding (virtual functions) |
| Cost | None at runtime | One indirect call per dispatch |
| Flexibility | Fixed at compile time | Can vary per object, even unknown at compile time |

**Why one can resolve earlier:** overload resolution only needs *static* information — the types written at the call site, which the compiler already has in hand. Override resolution fundamentally needs to know *which concrete subclass* an object is, and a base-class pointer or reference can point to any subclass decided only at runtime (e.g., constructed from user input or a factory). There's no way to know that earlier, so the lookup has to be deferred — that deferral is the entire reason virtual dispatch and vtables exist.

### 2. Operating Systems (Scenario/Applied)

Two processes, P1 and P2, each need exclusive access to two shared resources, a printer and a scanner. P1 acquires the printer and then tries to acquire the scanner. At the same time, P2 has acquired the scanner and is now trying to acquire the printer. Both then block, waiting on each other forever. Name the four necessary conditions for this situation, identify which one is most practical to break, and describe a concrete fix.

**Answer:**

This is a textbook **deadlock**. For a deadlock to occur, all four of these conditions must hold simultaneously (Coffman conditions):

1. **Mutual exclusion** — each resource (printer, scanner) can be held by only one process at a time.
2. **Hold and wait** — a process holding one resource (P1 holding the printer) can request another (the scanner) without releasing what it already has.
3. **No preemption** — a resource can't be forcibly taken away from a process; it must be released voluntarily.
4. **Circular wait** — there's a cycle of processes, each waiting on a resource held by the next: P1 waits for the scanner (held by P2), and P2 waits for the printer (held by P1).

In this scenario all four clearly hold: P1 holds printer → wants scanner; P2 holds scanner → wants printer. Neither will release what it holds, so both block forever.

**Which one is most practical to break:** Mutual exclusion generally can't be removed (some resources genuinely must be exclusive — you can't let two jobs print simultaneously onto the same printer). No-preemption is often hard too, since forcibly yanking a resource can corrupt whatever the process was doing with it. Hold-and-wait and circular wait are the two realistic targets, and **circular wait** is usually the cheapest one to eliminate.

**Concrete fix — resource ordering:** impose a global, fixed ordering on all resources (e.g., printer = resource 1, scanner = resource 2), and require every process to request resources in increasing order only. Under this rule, P2 could never request the printer (order 1) while already holding the scanner (order 2) — it would have had to acquire the printer *first*. This makes a circular wait structurally impossible: a cycle would require some process to request a lower-ordered resource while holding a higher-ordered one, which the rule forbids. It's a purely organizational discipline enforced in application/driver code, with no runtime overhead and no need to preempt anything — which is why it's the most commonly used practical deadlock-prevention technique.

### 3. DBMS (Conceptual/Definition)

What is a database index, and what problem does it solve? Compare a B-Tree index with a Hash index — when is each the better choice?

**Answer:**

A **database index** is an auxiliary data structure, built on one or more columns of a table, that lets the database engine locate matching rows without scanning every row in the table (a **full table scan**). The tradeoff it makes is deliberate: it speeds up reads for queries matching the indexed column(s), at the cost of extra storage and the overhead of updating the index on every `INSERT`, `UPDATE`, and `DELETE`.

**The problem it solves:** without an index, `SELECT * FROM users WHERE email = 'x@example.com'` must check every row — O(n) — which is unacceptable once a table has millions of rows. An index turns that into something close to O(log n) or even O(1), depending on its structure.

**B-Tree index** (what most databases use by default, e.g. PostgreSQL's and MySQL InnoDB's default index type):
- A balanced tree structure where leaf nodes are kept in sorted order and linked, so a range scan can walk sequentially after one descent.
- Supports **equality** (`=`), **range** (`<`, `>`, `BETWEEN`), **prefix matching** (`LIKE 'abc%'`), and **sorting**/`ORDER BY` efficiently, because the data is physically ordered.
- Lookup, insert, and delete are all O(log n).

**Hash index:**
- Applies a hash function to the indexed value and stores entries in buckets keyed by that hash.
- Supports only **exact equality** (`=`) lookups extremely fast — close to O(1).
- Cannot support range queries or sorting at all, because similar values can hash to completely unrelated buckets — there's no notion of "the next value" in a hash table.

**When to use which:**
- Use a **Hash index** when the column is only ever queried with exact-match lookups and never with ranges or ordering — e.g., looking up a session token or a UUID by exact value. It wins on raw equality-lookup speed and has a simpler, more compact structure.
- Use a **B-Tree index** (the safer default) whenever the column might be used in range filters, sorting, or prefix matches, or when you're unsure — e.g., timestamps, prices, names used with `ORDER BY` or `BETWEEN`. This is why it's the default index type in nearly every relational database: it's the only one of the two that doesn't paint you into a corner if query patterns evolve.
