### Question: Merge k Sorted Lists (Linked Lists — Hard)

**Problem Statement**

You are given an array of `k` linked lists, each sorted in ascending order. Merge all the linked lists into one sorted linked list and return its head.

**Input/Output Format**

- Input: an array `lists` of `k` linked-list heads (each node has an `int val` and a `next` pointer; a list may be empty, i.e. `nullptr`).
- Output: the head of a single linked list containing all nodes from all input lists, in ascending sorted order.

**Examples**

1. Input: `lists = [[1,4,5],[1,3,4],[2,6]]` → Output: `[1,1,2,3,4,4,5,6]`
2. Input: `lists = []` → Output: `[]` (return `nullptr`)
3. Input: `lists = [[]]` → Output: `[]` (a single empty list, return `nullptr`)

**Constraints**

- `0 <= k <= 10^4`
- `0 <= length of each list <= 500`
- `-10^4 <= node.val <= 10^4`
- The total number of nodes across all lists is at most `5 * 10^4`.
- Aim for better than the naive O(N·k) approach, where N is the total number of nodes.

### Step-by-Step Walkthrough

**The naive approach first.** At every step, look at the current head of each of the `k` lists, pick the smallest one, and advance that list. This is correct, but scanning all `k` heads to find the minimum costs O(k) per node produced, so merging all N nodes costs O(N·k) overall. With k up to 10^4 and N up to 5*10^4, that's far too slow.

**Key insight.** The repeated work in the naive approach is "find the minimum among the current heads of k lists." That is exactly what a **min-heap (priority queue)** is built for — it gives the minimum in O(1) and lets you swap it out for a new candidate in O(log k), instead of O(k).

**The algorithm:**
1. Push the head node of every non-empty input list into a min-heap, keyed by node value. The heap holds at most `k` nodes at any time.
2. While the heap is not empty:
   - Pop the node with the smallest value — call it `node`. This is guaranteed to be the next smallest remaining value across *all* lists, because every list the heap hasn't exhausted has its current smallest element represented in the heap.
   - Append `node` to the output list.
   - If `node->next` exists, push it into the heap (it becomes that list's new representative).
3. Return the dummy head's `next`.

**Why it's correct.** At any point, the heap contains exactly one node from each list that still has unconsumed nodes — specifically, the smallest unconsumed node of that list (because we only ever advance a list's pointer after consuming its current front, and we immediately push the new front). The true global minimum of all remaining nodes must be the minimum of these per-list minimums, since every list's remaining elements are themselves sorted, so nothing smaller than a list's current front can appear later in that list. Hence popping the heap's minimum at each step always yields nodes in overall sorted order.

**Alternative (also valid, mentioned for completeness).** A pairwise-merge / divide-and-conquer approach — merge lists two at a time, then merge the results two at a time, like the merge step of merge sort — achieves the same O(N log k) bound without a heap, by doing O(log k) merge "rounds" each costing O(N). The heap approach is simpler to implement and is what's shown below.

**Complexity.**
- Time: O(N log k) — each of the N nodes is pushed and popped from a heap of size at most k exactly once, and each heap operation costs O(log k).
- Space: O(k) for the heap, plus O(N) for the output list itself (which is required regardless, since we must produce N nodes). The heap's auxiliary space is O(k).

### C++ Code

```cpp
#include <vector>
#include <queue>
using namespace std;

struct ListNode {
    int val;
    ListNode* next;
    ListNode(int x) : val(x), next(nullptr) {}
};

class Solution {
public:
    ListNode* mergeKLists(vector<ListNode*>& lists) {
        // Min-heap of (value, node pointer), ordered by value.
        // Using a custom comparator so the heap pops the smallest value first.
        auto cmp = [](ListNode* a, ListNode* b) { return a->val > b->val; };
        priority_queue<ListNode*, vector<ListNode*>, decltype(cmp)> minHeap(cmp);

        // Seed the heap with the head of every non-empty list.
        for (ListNode* head : lists) {
            if (head != nullptr) {
                minHeap.push(head);
            }
        }

        ListNode dummy(0);
        ListNode* tail = &dummy;

        while (!minHeap.empty()) {
            ListNode* smallest = minHeap.top();
            minHeap.pop();

            // Attach the smallest remaining node to the output list.
            tail->next = smallest;
            tail = smallest;

            // That list's next node becomes its new representative in the heap.
            if (smallest->next != nullptr) {
                minHeap.push(smallest->next);
            }
        }

        tail->next = nullptr; // terminate the merged list cleanly
        return dummy.next;
    }
};
```

Edge cases handled: an empty `lists` array leaves the heap empty, so the loop never runs and `dummy.next` (`nullptr`) is returned directly; a `lists` array containing only empty sublists (`nullptr` heads) is filtered out by the `if (head != nullptr)` check during seeding, with the same result.

### 1. Operating Systems (Conceptual/Definition)

What are the four necessary conditions for deadlock to occur in an operating system, and how does each standard prevention strategy work by breaking exactly one of them?

**Answer:**

A deadlock is a state where a set of processes are each waiting for a resource held by another process in the same set, so none of them can ever proceed. Coffman (1971) showed that deadlock requires all four of the following conditions to hold **simultaneously** — which is the key practical insight, because it means breaking just *one* of them anywhere in the system is enough to make deadlock impossible, without needing to touch the other three.

1. **Mutual exclusion.** At least one resource is held in a non-shareable mode — only one process can use it at a time (e.g. a printer, a mutex-protected data structure).
2. **Hold and wait.** A process currently holding at least one resource is waiting to acquire additional resources that are currently held by other processes.
3. **No preemption.** Resources cannot be forcibly taken away from a process; they can only be released voluntarily by the process holding them.
4. **Circular wait.** There exists a cycle of processes `P1 → P2 → ... → Pn → P1`, where each `Pi` is waiting for a resource held by `P(i+1)`.

**How each prevention strategy maps to breaking one condition:**

| Condition broken | Strategy | How it works |
| --- | --- | --- |
| Mutual exclusion | Avoid where possible | Rarely practical to eliminate for genuinely exclusive resources, but make shareable resources (e.g. read-only files) shareable rather than exclusive. |
| Hold and wait | Require all-or-nothing acquisition | A process must request and be granted *all* the resources it will ever need at once, before starting, and holds nothing while waiting. Downside: poor resource utilization, and a process may not know its full future needs in advance. |
| No preemption | Allow preemption | If a process holding resources requests another that isn't available, it is forced to release what it already holds (its state is saved and later restored). Works well when resource state is easy to checkpoint (e.g. CPU registers), poorly for others (e.g. a half-written database transaction, though this is effectively what transaction rollback/abort does). |
| Circular wait | Impose a total ordering on resources | Every resource type is assigned a unique number, and every process must request resources in strictly increasing numeric order. This makes a cycle impossible: if `Pi` holds a resource numbered `m` and waits for one numbered `n`, then `n > m` always, so you can never loop back to a smaller number already held earlier in the cycle. |

**Why this matters in practice:** the circular-wait fix (resource ordering) is by far the most commonly used in real systems, because it's cheap and doesn't sacrifice concurrency the way "acquire everything upfront" does — it's the reason style guides for multi-lock code say "always acquire locks in a fixed global order." A related but distinct approach, **deadlock avoidance** (e.g. the Banker's Algorithm), doesn't break any of the four conditions structurally; instead it allows all of them to be possible but refuses any individual resource request that *would* move the system into an unsafe state, by checking in advance.

### 2. Computer Networks (Comparison)

Compare TCP and UDP. Beyond "TCP is reliable and UDP isn't," what specific mechanisms does TCP use to provide its guarantees, and what concretely do those mechanisms cost — which is why UDP still exists and is the right choice for some applications?

**Answer:**

Both are transport-layer protocols sitting on top of IP, but they make opposite trade-offs between guarantees and overhead.

**TCP (Transmission Control Protocol)** is connection-oriented and reliable. Its guarantees come from specific mechanisms, each with a cost:

- **Three-way handshake (SYN, SYN-ACK, ACK)** establishes a connection before any data flows, synchronizing initial sequence numbers. *Cost:* at least one extra round trip of latency before the first byte of real data is sent.
- **Sequence numbers and acknowledgments** let the receiver detect missing or out-of-order segments and let the sender know what was actually received. *Cost:* extra header bytes on every segment, and the sender must buffer sent-but-unacknowledged data in case it needs to retransmit.
- **Retransmission on timeout/loss** resends unacknowledged data. *Cost:* latency — a lost packet stalls delivery of everything after it until the resend arrives (head-of-line blocking at the transport level), which is exactly why TCP is a poor fit for real-time media where a late packet is worse than a dropped one.
- **Flow control (sliding window)** prevents a fast sender from overwhelming a slow receiver's buffer. **Congestion control** (slow start, AIMD, etc.) prevents the sender from overwhelming the *network*. *Cost:* throughput is deliberately throttled below the physical link capacity whenever the algorithm senses or predicts congestion, and connections need time to "ramp up" to full speed.
- **In-order delivery** is reconstructed at the receiver by buffering and reordering segments before handing data to the application. *Cost:* added latency and receive-buffer memory.

**UDP (User Datagram Protocol)** is connectionless and provides none of this: no handshake, no acknowledgments, no retransmission, no ordering guarantee, no congestion control. A sent datagram may arrive, arrive out of order, arrive duplicated, or simply vanish, and UDP will never tell either side. In exchange, it has a tiny fixed 8-byte header, no connection setup latency, and no head-of-line blocking — one lost or late datagram never holds up the ones behind it.

**Why UDP still exists / when it's the right choice:** applications where a stale or missing packet is worthless and arriving late is as bad as not arriving — live video/audio calls (VoIP, video conferencing), competitive online gaming (you want this tick's position, not a retransmitted old one), and DNS queries (small enough to just retry at the application level if lost, and a single round trip matters more than guaranteed delivery). These applications either tolerate loss gracefully (video codecs degrade gracefully frame-to-frame) or implement their own lightweight, purpose-specific reliability on top of UDP (e.g. QUIC, which HTTP/3 is built on, reimplements reliability and congestion control over UDP while avoiding TCP's head-of-line blocking across independent streams).

### 3. OOP (Scenario/Applied)

You're designing a `NotificationService` that must send alerts via email, SMS, and push notification, with more channels likely to be added later. A teammate suggests a single `send(String type, String message)` method with an `if/else` chain checking `type`. Explain why this violates good OOP design, and describe how polymorphism gives a better structure — including what specifically becomes easier when a new channel is added.

**Answer:**

**What's wrong with the `if/else` version:** it violates the **Open/Closed Principle** — a class should be open for extension but closed for modification. Every time a new channel (say, Slack) is added, you must go back and edit the existing `send` method, inserting another `else if` branch. This is risky for several concrete reasons: (1) it's easy to accidentally break an existing branch while adding a new one, since all channels now share one function body; (2) the method accumulates channel-specific logic (SMTP details, SMS gateway API calls, push token handling) all tangled together, making it long and hard to reason about; (3) testing one channel means the whole method — and its growing combined complexity — is in scope; (4) anyone calling `send` with a typo'd or unsupported `type` string only finds out at runtime, often in a silent fallthrough or a thrown exception deep in the chain.

**The polymorphic structure:** define a common interface (or abstract base class),

```cpp
class NotificationChannel {
public:
    virtual void send(const std::string& message) = 0;
    virtual ~NotificationChannel() = default;
};

class EmailChannel : public NotificationChannel {
    void send(const std::string& message) override { /* SMTP logic */ }
};

class SmsChannel : public NotificationChannel {
    void send(const std::string& message) override { /* SMS gateway logic */ }
};

class PushChannel : public NotificationChannel {
    void send(const std::string& message) override { /* push token logic */ }
};
```

`NotificationService` then holds a collection of `NotificationChannel*` (or a single one it was configured with) and calls `channel->send(message)` without ever knowing or caring which concrete type it's dealing with — that decision is resolved at runtime via the vtable, based on the object's actual dynamic type. This is **polymorphism** doing exactly what it's for: letting calling code depend on an abstraction (`NotificationChannel`) rather than a concrete enumeration of cases.

**What specifically becomes easier when adding Slack support:**
- You write exactly one new class, `SlackChannel : public NotificationChannel`, implementing `send`.
- You touch **zero existing code** — `NotificationService`, `EmailChannel`, `SmsChannel`, and `PushChannel` are all untouched and need no re-testing, because nothing about them changed.
- The new channel can be unit-tested entirely in isolation, with no need to exercise the if/else chain's other branches.
- If channels are instantiated via a registry/factory (e.g. a `map<string, function<NotificationChannel*()>>`), adding Slack can even avoid touching the factory's call sites — just register the new mapping.
- The compiler enforces the contract: forgetting to implement `send` in a new subclass is a compile error, whereas forgetting an `else if` branch for a new type string is a silent runtime gap that only surfaces when someone calls it.

This is also a textbook case for the **Strategy pattern** — the "algorithm" (how to deliver a message) is factored out into interchangeable, independently substitutable objects, and `NotificationService` is the context that uses whichever strategy it's handed, without encoding any of the strategies' details itself.
