### Question: Course Schedule II (Graphs — Medium)

**Problem Statement**

There are `numCourses` courses labeled `0` to `numCourses - 1`. You are given an array `prerequisites` where `prerequisites[i] = [a, b]` means you must take course `b` before course `a`. Return **any** valid ordering of courses you could take to finish all courses. If it is impossible to finish all courses (because of a circular dependency), return an empty array.

**Input/Output Format**

- Input: `int numCourses`, `vector<vector<int>> prerequisites` (each inner vector has exactly 2 elements `[a, b]`).
- Output: `vector<int>` — a valid course order of length `numCourses`, or an empty vector if no valid order exists.

**Examples**

1. Input: `numCourses = 4`, `prerequisites = [[1,0],[2,0],[3,1],[3,2]]` → Output: `[0,1,2,3]` (also valid: `[0,2,1,3]`) — course 0 has no prerequisites, 1 and 2 both depend only on 0, and 3 depends on both 1 and 2.
2. Input: `numCourses = 2`, `prerequisites = [[1,0]]` → Output: `[0,1]`.
3. Input: `numCourses = 2`, `prerequisites = [[1,0],[0,1]]` → Output: `[]` — course 0 needs course 1 and course 1 needs course 0, a cycle, so no valid order exists.

**Constraints**

- `1 <= numCourses <= 2000`
- `0 <= prerequisites.length <= 5000`
- `prerequisites[i].length == 2`
- `0 <= a, b < numCourses`, `a != b`
- No duplicate edges in `prerequisites`.

### Step-by-Step Walkthrough

**Reframing the problem.** "Course `a` requires course `b` first" is a directed edge `b → a` in a dependency graph. A valid course order is exactly a **topological order** of this directed graph: every node appears after all the nodes it depends on. A topological order exists if and only if the graph has no cycle, so this problem is really "topologically sort the graph, or detect that it's cyclic."

**Algorithm — Kahn's algorithm (BFS-based topological sort):**

1. Build an adjacency list `adj[b] = [a, ...]` for every edge `b → a`, and an `indegree[]` array counting, for each node, how many prerequisites it still has.
2. Push every node with `indegree == 0` into a queue — these are courses that can be taken immediately, with no outstanding prerequisites.
3. While the queue is not empty:
   - Pop a node `u`, append it to the result order (we are "taking" course `u`).
   - For every neighbor `v` in `adj[u]` (every course that depended on `u`), decrement `indegree[v]`. If it drops to 0, `v` has no remaining unmet prerequisites, so push it onto the queue.
4. After the loop, if the result order contains all `numCourses` nodes, return it. Otherwise, some nodes never reached indegree 0 — they're stuck in a cycle (or depend on something stuck in a cycle) — so return an empty array.

**Why it's correct.** A node is only added to the result once every one of its prerequisites has already been added (that's precisely what "indegree reaches 0" encodes — all incoming edges have been processed). So the result is built in an order that always respects every dependency, which is the definition of a topological order. If a cycle exists, every node in that cycle has at least one incoming edge from another node in the same cycle that can never be "processed" (since that node is itself waiting on the cycle), so no node in the cycle ever reaches indegree 0, and the result ends up short of `numCourses` — which is exactly how we detect the impossible case without a separate DFS-based cycle check.

**Complexity.**
- Time: O(V + E), where V = `numCourses` and E = `prerequisites.size()`. Building the adjacency list and indegree array is O(V + E); the BFS visits each node once and each edge once.
- Space: O(V + E) for the adjacency list and indegree array, plus O(V) for the queue and result.

### C++ Code

```cpp
#include <vector>
#include <queue>
using namespace std;

class Solution {
public:
    vector<int> findOrder(int numCourses, vector<vector<int>>& prerequisites) {
        vector<vector<int>> adj(numCourses);
        vector<int> indegree(numCourses, 0);

        // Edge b -> a: must take b before a.
        for (const auto& p : prerequisites) {
            int a = p[0], b = p[1];
            adj[b].push_back(a);
            indegree[a]++;
        }

        queue<int> ready;
        for (int i = 0; i < numCourses; ++i) {
            if (indegree[i] == 0) {
                ready.push(i);
            }
        }

        vector<int> order;
        order.reserve(numCourses);

        while (!ready.empty()) {
            int u = ready.front();
            ready.pop();
            order.push_back(u);

            for (int v : adj[u]) {
                if (--indegree[v] == 0) {
                    ready.push(v);
                }
            }
        }

        // If we couldn't order every course, a cycle blocked some of them.
        if ((int)order.size() != numCourses) {
            return {};
        }
        return order;
    }
};
```

Edge cases handled: `prerequisites` empty means every node starts with indegree 0, so all nodes are pushed immediately and any order (here, `0..numCourses-1`) is returned; a cycle (Example 3) leaves the involved nodes permanently stuck at indegree > 0, so `order.size() != numCourses` and `{}` is returned.

### 1. DBMS (Conceptual/Definition)

Explain the four ACID properties of a database transaction. For each one, give a concrete example of what goes wrong in a real application (e.g. a bank transfer) if that specific property is violated.

**Answer:**

ACID is the set of guarantees a database makes about how transactions behave, so that application code can treat a transaction as a single, safe unit of work even when failures, concurrency, or crashes happen in the middle of it. The canonical example throughout is transferring $100 from account A to account B, which requires two writes: `A.balance -= 100` and `B.balance += 100`.

1. **Atomicity** — a transaction's operations either *all* happen or *none* happen; there is no partially-applied state. *Violation example:* the debit from A succeeds, but the server crashes before the credit to B runs. Without atomicity, $100 has simply vanished — A lost it, B never got it, and there is no way to recover the "intended" state from what's on disk. Atomicity is what lets you write a multi-step transfer without manually writing crash-recovery logic for every possible failure point; the database guarantees that on crash, the whole transaction is rolled back as if it never started.

2. **Consistency** — a transaction can only take the database from one valid state to another valid state, per all declared constraints (foreign keys, check constraints, application invariants like "total money in the system is conserved"). *Violation example:* if a `CHECK (balance >= 0)` constraint exists but is bypassed, a transaction could leave A with a balance of -100 with no corresponding error, silently corrupting an invariant the rest of the application logic assumes always holds (e.g. a report that sums "money owed" would now be wrong).

3. **Isolation** — concurrent transactions don't see each other's intermediate, uncommitted state; the result looks as if transactions ran one at a time (to whatever degree the isolation level promises). *Violation example:* without isolation, a second transaction reading A and B's balances *during* the transfer could observe a moment where A has already been debited but B hasn't been credited yet (a "dirty read" of an inconsistent intermediate state) — e.g. a balance-report job reading in that window would report $100 less total money in the system than actually exists, even though the transfer itself eventually completes correctly.

4. **Durability** — once a transaction commits, its effects survive any subsequent crash (power loss, OS crash, etc.) — they are persisted, typically via a write-ahead log flushed to disk before commit is acknowledged. *Violation example:* the transfer commits and the application tells the user "transfer successful," but the server crashes a second later and the write was only in memory, not on durable storage. On reboot the debit/credit never happened, yet the user was already told it succeeded — a silent, undetectable data loss that's especially dangerous because the acknowledgment already went out.

**Why this matters in practice:** these four properties are often in tension with performance — stricter isolation levels (e.g. `SERIALIZABLE`) prevent more anomalies but cost more locking/throughput than looser ones (e.g. `READ COMMITTED`), and synchronous durability (fsync on every commit) is slower than async durability. Most real systems let you choose the isolation level and durability mode per workload, which is why understanding exactly what each property protects against — rather than treating "ACID" as one indivisible guarantee — matters when picking those settings.

### 2. Computer Architecture (Comparison)

Compare pipelining and superscalar execution as techniques for increasing CPU instruction throughput. What form of parallelism does each exploit, and what specifically limits how far each one can be pushed?

**Answer:**

Both techniques aim to execute more instructions per unit time than a naive one-instruction-at-a-time CPU, but they exploit different kinds of parallelism and hit different walls.

**Pipelining** overlaps the *stages* of different instructions' execution. A classic 5-stage pipeline (Fetch, Decode, Execute, Memory access, Writeback) lets instruction 2 be in Decode while instruction 1 is in Execute, instruction 3 be in Fetch at the same time, and so on — at steady state, one instruction *finishes* every clock cycle, even though each individual instruction still takes 5 cycles start to finish. This exploits **overlap of sequential work**, not true simultaneous execution of multiple instructions' actual computation.

- **What limits it — hazards.** A *structural hazard* occurs when two stages need the same hardware resource simultaneously (e.g. one shared memory port). A *data hazard* occurs when an instruction needs a value that a previous, still-in-flight instruction hasn't produced yet — mitigated by **forwarding/bypassing** (routing the result directly from one stage to another before it's officially written back) or, when forwarding isn't possible, by stalling (inserting a "bubble"). A *control hazard* occurs at branches — the pipeline doesn't know which instruction to fetch next until the branch resolves, several stages later — mitigated by **branch prediction** (guess and fetch speculatively) with a **pipeline flush** penalty when the guess is wrong. In practice, pipelining is limited by how deep you can make the pipeline before hazard-handling overhead (flush penalties, forwarding logic complexity) eats the throughput gains, and by the fact that a single pipeline can still only *retire* one instruction per cycle at best.

**Superscalar execution** issues and executes *multiple independent instructions in the same clock cycle*, using duplicated execution units (e.g. two ALUs, a separate load/store unit, a separate floating-point unit) and hardware that checks for dependencies between instructions in the current fetch window, often combined with **out-of-order execution** (a reorder buffer lets an independent later instruction execute before an earlier stalled one, as long as results are still committed in correct program order). This exploits genuine **instruction-level parallelism (ILP)** — truly independent work happening at the same instant, not just overlapped stages of sequential work (and is typically combined with pipelining, not instead of it: each of the multiple execution units is itself pipelined).

- **What limits it.** The amount of *extractable* ILP in real code — how many mutually-independent instructions exist close together in the instruction stream — is finite and workload-dependent; code full of tight data dependencies (`x = f(x)` chains) offers little to extract regardless of how many execution units you add. Beyond that, the hardware cost of dependency-checking grows faster than linearly with the issue width (checking all pairs of instructions in a wider issue window for conflicts), and the chip has to spend real die area and power on the extra execution units, reorder buffers, and register renaming logic — which is a large part of why "wide" superscalar designs (6+ wide) hit steep diminishing returns and why clock speed sometimes has to come down to accommodate the extra logic's complexity and heat.

**In short:** pipelining is about not wasting idle time between the stages of sequential instructions; superscalar execution is about doing genuinely independent instructions at the same literal instant. Real modern CPUs (x86, ARM) combine both — a deeply pipelined, wide superscalar, often out-of-order core — because they attack different bottlenecks and their limits (hazard overhead vs. available ILP and hardware cost) are largely independent of each other.

### 3. System Design Basics (Scenario/Applied)

You're designing a URL-shortener service like bit.ly: users submit a long URL and get back a short code (e.g. `short.ly/aZ9kT`); visiting the short URL redirects to the original. Walk through the core data model, how you'd generate the short codes, and how you'd scale to handle far more reads (redirects) than writes (new URLs created).

**Answer:**

**Core data model.** A single table/collection is enough at the core: `short_code (primary key) -> { long_url, created_at, expires_at?, creator_id? }`. The short code is the natural primary key because the hot-path operation — resolving a redirect — is a point lookup by short code, and a key-value store or a simple relational table indexed on that column serves this well; you don't need a relational join for the core redirect path.

**Generating the short code — two viable approaches:**

1. **Base62 encode an auto-incrementing ID.** Maintain a global (or sharded-range) counter; when a new URL comes in, take the next ID (say, `125,000,000`) and encode it in base62 (`[0-9a-zA-Z]`, 62 symbols) to get a compact string like `8M0kX`. This guarantees uniqueness by construction (no collision checking needed) and a 7-character base62 code supports `62^7 ≈ 3.5 trillion` distinct codes — far more than needed. The only wrinkle is generating unique IDs without a single counter becoming a bottleneck/single point of failure at scale — solved by handing out **ID ranges** to each application server (server claims IDs 1,000,000–1,000,999 from a coordinator, then hands them out locally without round-tripping), similar to how Twitter's Snowflake or a database's `AUTO_INCREMENT` with sharded ranges work.
2. **Hash the long URL** (e.g. MD5/SHA-256) and take the first 6–8 characters of the base62-encoded hash. This is simpler (no counter coordination) but introduces the possibility of hash collisions (two different long URLs truncating to the same short prefix) and also means the same long URL submitted twice could reasonably get the same or a different code depending on whether you dedupe — both are design choices, but you now need a uniqueness check-and-retry (append a salt/counter on collision) that approach 1 doesn't need.

I'd default to **approach 1 (counter + base62)** for a service at real scale, since it avoids collision-handling complexity entirely and gives short, predictable-length codes; approach 2 is attractive mainly when you specifically want the same long URL to deterministically map to the same short code without a lookup.

**Scaling reads vs. writes.** A URL shortener is heavily read-skewed — every redirect is a read, and a given short URL is typically clicked many times after being created once — so the redirect path is exactly where I'd invest:

- **Cache the hot mappings.** Put a cache (e.g. Redis) in front of the database, keyed by short code, holding `short_code -> long_url`. Popular links (the ones actually driving most traffic, per typical power-law/Zipfian click distributions) stay cache-resident, so the overwhelming majority of redirects never touch the database at all. Cache invalidation is simple here because mappings are near-immutable once created (a short code's target essentially never changes), so there's no real staleness problem to design around — write-through on creation (write to DB and cache at the same time) is sufficient.
- **Horizontally scale the redirect-serving tier.** The redirect service itself (read cache, 302/301 to `long_url`) is stateless, so it scales trivially behind a load balancer — just add more instances.
- **Shard the backing store if needed.** If the dataset outgrows a single database (billions of URLs), shard by a hash of `short_code`, which distributes load evenly since short codes are already effectively random/sequential-but-well-distributed after base62 encoding — no hot-shard problem the way sharding by, say, `creator_id` could create for a popular user.
- **301 vs. 302 redirect choice is a real tradeoff, not a footnote:** a `301 (permanent)` redirect lets browsers cache the redirect locally, which reduces load on your service even further (repeat visits by the same browser never hit your server again) — but it also means you lose the ability to track click analytics on those cached hits, and you can't repoint or expire the short code later for that browser. A `302 (temporary)` redirect costs you that caching benefit but keeps every click visible to your analytics and keeps the mapping changeable. Which one is "right" depends on whether the product needs click analytics/expiring links (favor 302) or needs maximum scalability with immutable permanent links (301 is fine).

The write path (creating a new short code) is comparatively low-volume and doesn't need nearly as much optimization — a single well-indexed database (or the sharded version above, once you're at real scale) handles it without difficulty, since even a popular shortener service creates URLs at a small fraction of the rate it serves redirects for previously-created ones.
