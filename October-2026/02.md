### Question: Median of Two Sorted Arrays (Sorting/Searching — Hard)

**Problem Statement**

Given two sorted arrays `nums1` (size `m`) and `nums2` (size `n`), return the median of the two combined sorted arrays. The overall run-time complexity must be `O(log(min(m, n)))` — merging the arrays first is not acceptable.

**Input/Output Format**

- Input: two arrays of integers, each already sorted in ascending order.
- Output: a single floating-point value, the median of the `m + n` combined elements.

**Examples**

1. `nums1 = [1, 3]`, `nums2 = [2]` → Output: `2.0` (combined sorted: `[1,2,3]`, odd count, middle element).
2. `nums1 = [1, 2]`, `nums2 = [3, 4]` → Output: `2.5` (combined sorted: `[1,2,3,4]`, even count, average of the two middle elements).
3. `nums1 = []`, `nums2 = [1]` → Output: `1.0` (one array can be empty).

**Constraints**

- `0 <= m, n <= 1000`
- `1 <= m + n <= 2000` (at least one element total)
- `-10^6 <= nums1[i], nums2[i] <= 10^6`
- Both arrays are sorted in non-decreasing order.

### Step-by-Step Walkthrough

**The obvious approach first.** Merge both sorted arrays into one sorted array of size `m + n` (a standard merge-sort merge step), then read off the median directly — the middle element if the total count is odd, or the average of the two middle elements if even. This is `O(m + n)` time and easy to get right, and it is a perfectly fine answer under time pressure. But the problem explicitly asks for `O(log(min(m, n)))`, which rules out touching every element — we need a genuine search, not a scan.

**Reframing the problem as a partition problem.** A median splits a sorted sequence into a left half and a right half of (near-)equal size, where every element on the left is `≤` every element on the right. If we could find, without merging, a way to carve `nums1` into a left part of size `i` and a right part of size `m - i`, and `nums2` into a left part of size `j` and a right part of size `n - j`, such that:

1. `i + j` equals exactly half of the total count (rounded appropriately for odd totals), and
2. every element in `nums1`'s left part and `nums2`'s left part is `≤` every element in `nums1`'s right part and `nums2`'s right part,

then the combined left part *is* the left half of the merged array, and the combined right part is the right half — without ever actually merging. The median then reads off the boundary elements only: `max(left)` and/or `min(right)`.

**Reducing two unknowns to one via binary search.** We have two partition indices `i` (into `nums1`) and `j` (into `nums2`), but they're not independent: once we fix `i`, the constraint `i + j = halfLeftSize` pins down `j = halfLeftSize - i`. So we only need to binary-search over `i`, the partition index in the *smaller* array (searching the smaller array bounds the binary search to `O(log(min(m, n)))`, which is exactly the required complexity — and guarantees `j` always stays in valid range `[0, n]`).

For a candidate `i`, define:
- `maxLeft1 = nums1[i-1]` (or `-∞` if `i == 0`), `minRight1 = nums1[i]` (or `+∞` if `i == m`).
- `maxLeft2 = nums2[j-1]` (or `-∞` if `j == 0`), `minRight2 = nums2[j]` (or `+∞` if `j == n`).

The partition is valid exactly when `maxLeft1 <= minRight2` AND `maxLeft2 <= minRight1`. This says: nothing on `nums1`'s left exceeds anything on `nums2`'s right, and vice versa — which is precisely the condition for "combined left half, combined right half" to actually be sorted halves.

**How binary search converges.** If `maxLeft1 > minRight2`, `nums1`'s left partition reaches too far right — too many large elements from `nums1` are on the left, so shrink `i` (search left half of the binary search range). If `maxLeft2 > minRight1`, the opposite holds — `i` is too small, so grow `i` (search right half). Because the arrays are sorted, these two conditions are monotonic in `i`, which is exactly what makes binary search valid here.

**Reading the median once a valid partition is found.** Let `halfLeftSize = (m + n + 1) / 2` (integer division — this correctly allocates the extra element to the left half when the total is odd).
- If `(m + n)` is odd, the median is `max(maxLeft1, maxLeft2)` — the largest element among everything placed on the left.
- If `(m + n)` is even, the median is the average of `max(maxLeft1, maxLeft2)` and `min(minRight1, minRight2)` — the two elements straddling the boundary.

**Complexity.**
- Time: `O(log(min(m, n)))` — binary search runs only over the smaller array.
- Space: `O(1)` — only a handful of index and sentinel variables.

### C++ Code

```cpp
#include <vector>
#include <algorithm>
#include <climits>
using namespace std;

double findMedianSortedArrays(vector<int>& nums1, vector<int>& nums2) {
    // Always binary-search the smaller array so the search space,
    // and hence the time complexity, is O(log(min(m, n))).
    if (nums1.size() > nums2.size()) {
        return findMedianSortedArrays(nums2, nums1);
    }

    int m = nums1.size();
    int n = nums2.size();
    int halfLeftSize = (m + n + 1) / 2; // extra element (if any) goes left

    int lo = 0, hi = m;

    while (lo <= hi) {
        int i = lo + (hi - lo) / 2; // partition index into nums1
        int j = halfLeftSize - i;  // forced partition index into nums2

        // Sentinels handle the "partition at the very edge" cases cleanly,
        // so there is no need for separate boundary branches below.
        int maxLeft1 = (i == 0) ? INT_MIN : nums1[i - 1];
        int minRight1 = (i == m) ? INT_MAX : nums1[i];
        int maxLeft2 = (j == 0) ? INT_MIN : nums2[j - 1];
        int minRight2 = (j == n) ? INT_MAX : nums2[j];

        if (maxLeft1 <= minRight2 && maxLeft2 <= minRight1) {
            // Valid partition found.
            if ((m + n) % 2 == 1) {
                return max(maxLeft1, maxLeft2);
            }
            return (max(maxLeft1, maxLeft2) + min(minRight1, minRight2)) / 2.0;
        } else if (maxLeft1 > minRight2) {
            // nums1's left partition reaches too far right; shrink i.
            hi = i - 1;
        } else {
            // nums2's left partition reaches too far right; grow i.
            lo = i + 1;
        }
    }

    // Unreachable if inputs are valid sorted arrays with m + n >= 1.
    return -1.0;
}
```

## CS Fundamentals

### 1. Computer Networks (Comparison)

Compare HTTP/1.1, HTTP/2, and HTTP/3 (over QUIC). What specific problem does each new version solve over its predecessor, and what is head-of-line blocking?

**Answer:**

Each version exists to remove a specific bottleneck the previous one hit at scale, and the thread connecting all three is **head-of-line (HOL) blocking** — a situation where one stalled item in a queue blocks everything queued behind it, even items that are otherwise ready to proceed.

**HTTP/1.1.** One request must fully complete before the next can be sent on the same TCP connection, unless you use pipelining (rarely deployed, since a slow response still blocks every pipelined response behind it — HOL blocking at the application layer). Browsers worked around this by opening multiple parallel TCP connections per origin (typically 6), which has its own costs: every connection pays its own TCP handshake and, over HTTPS, its own TLS handshake, and every connection runs its own independent congestion-control ramp-up, which is wasteful when loading many small assets.

**HTTP/2.** Introduces **multiplexing**: a single TCP connection carries many concurrent request/response streams, interleaved as framed messages, so one slow resource no longer blocks unrelated ones at the application layer. This also lets you drop the six-connections-per-origin workaround, reusing one connection's warmed-up TLS session and congestion window for everything. But HTTP/2 multiplexes *on top of* TCP, and TCP itself guarantees strictly in-order, reliable delivery of bytes on the wire. So if a single TCP packet is lost, TCP will not deliver *any* later-arriving bytes to the application until that lost packet is retransmitted and arrives — even if those later bytes belong to a completely unrelated HTTP/2 stream that suffered no loss of its own. This is **transport-layer HOL blocking**, and it's precisely the problem HTTP/2 could not solve because it lives one layer below HTTP/2's control.

**HTTP/3.** Solves transport-layer HOL blocking by replacing TCP with **QUIC**, built on top of UDP. QUIC implements its own reliability and congestion control, but critically, it multiplexes streams *at the transport layer itself* and tracks loss and retransmission **per stream** rather than as one ordered byte pipe. So if a packet carrying data for stream A is lost, stream B's already-arrived packets are delivered to the application immediately — only stream A stalls while its lost packet is retransmitted. QUIC also folds the transport and TLS 1.3 handshakes into a single combined round trip (and supports 0-RTT resumption for returning clients), and because a QUIC connection is identified by a connection ID rather than a 4-tuple (source/dest IP and port), it survives a client's network change (e.g., Wi-Fi to cellular) without dropping the connection — something impossible for a TCP socket bound to that 4-tuple.

| | HTTP/1.1 | HTTP/2 | HTTP/3 (QUIC) |
| --- | --- | --- | --- |
| Transport | TCP | TCP | UDP (QUIC) |
| Concurrency | Multiple TCP connections | Multiplexed streams, 1 connection | Multiplexed streams, 1 connection |
| HOL blocking | Yes, at the application layer | Yes, at the transport layer (TCP) | Eliminated — per-stream loss recovery |
| Handshake cost | TCP + TLS per connection | TCP + TLS, once | Combined transport+TLS1.3, 0-RTT possible |
| Survives IP change | No | No | Yes (connection ID, not 4-tuple) |

The general lesson: multiplexing at one layer only removes HOL blocking if the layer beneath it is also multiplexed — which is exactly why HTTP/2 needed HTTP/3 to finish the job.

### 2. System Design Basics (Scenario/Applied)

A social media feed API is read-heavy: the same celebrity's profile and recent posts are fetched thousands of times per second, while writes (new posts, likes) are comparatively rare. The database is overloaded. Walk through how you'd introduce caching to fix this, where you'd place the cache(s), and how you'd handle invalidation so users don't see badly stale data.

**Answer:**

**Diagnose first.** A read-heavy, write-light workload with highly skewed access (a small number of "hot" keys — popular profiles — getting most of the traffic) is the textbook case for caching: the data is read far more often than it changes, so recomputing or re-fetching it from the database on every request is almost entirely wasted work.

**Where to place the cache(s), from closest to the user inward:**

1. **CDN / edge cache.** For content that's identical for every viewer and changes infrequently (profile pictures, static post media, sometimes fully-rendered public profile pages), cache at the CDN edge, close to the user. This removes load before it even reaches your infrastructure, at the cost of being unsuitable for personalized or rapidly-changing data.
2. **Application-layer cache (e.g., Redis/Memcached), in front of the database.** This is the main fix here. On a read, the service checks the cache first; on a hit, it returns immediately without touching the database; on a miss, it reads from the database, populates the cache, and returns the result (the **cache-aside / lazy-loading** pattern). Because the workload is read-heavy and skewed, a small cache holding the hot keys absorbs the overwhelming majority of traffic — this is the layer that actually relieves the overloaded database.
3. **Database-level cache (e.g., a buffer pool, or read replicas).** A useful supplementary layer, but it doesn't change the *shape* of the problem the way an application cache does, since every request still round-trips to the database tier.

**Why cache-aside over always-write-through here:** write-through (every write immediately updates the cache) adds latency to every write and, more importantly, warms cache entries nobody may ever read — wasteful under a long-tail access pattern. Cache-aside only populates the cache for keys that are actually requested, which matches this workload's skew.

**Invalidation — the actually hard part.** Options, roughly in order of what to reach for first:

- **TTL (time-to-live) expiration.** Set a short TTL (seconds to low minutes) on cached entries. Simple, self-healing (a bug that fails to invalidate explicitly still resolves itself), and bounds staleness to a known window. The tradeoff is that users can see data up to the TTL's age — acceptable for a feed where "like count is 30 seconds stale" is a non-issue, not acceptable for anything requiring strong consistency (e.g., account balance).
- **Explicit invalidation on write.** When a post is edited or deleted, actively delete (not update) the corresponding cache key(s) as part of the write path, so the next read is a guaranteed cache miss that re-fetches fresh data. Deleting rather than updating the cache avoids a race where two concurrent writes could leave a stale value cached if updates are applied out of order.
- **Combine both.** Explicit invalidation handles the common case promptly; TTL is the safety net that bounds staleness for any invalidation that's missed (e.g., a write path that forgot to invalidate, or a multi-service deployment where not every writer path is covered).

**Handling the "thundering herd" on a hot key's expiry.** When a very hot key (a celebrity's profile) expires, many concurrent requests can simultaneously miss the cache and hammer the database at once. Mitigate with **request coalescing** (only the first miss triggers a database fetch; concurrent requests wait on that in-flight fetch and share its result) or by **jittering TTLs** (randomizing expiry slightly per key so many keys don't expire in the same instant).

**The underlying principle:** caching trades a small, bounded amount of staleness for a large reduction in load on the system of record, and the right invalidation strategy is whichever one keeps that staleness within what the product can tolerate — a feed can tolerate seconds of staleness; a bank balance cannot.

### 3. Computer Architecture (Comparison)

Compare direct-mapped, fully associative, and set-associative cache mapping techniques. What problem does each design trade off against the others?

**Answer:**

All three answer the same question — "given a memory address, which cache line(s) could it possibly be stored in?" — and the differences come down to a fundamental tradeoff between **lookup speed/hardware cost** and **flexibility in placement** (which affects how often useful data gets evicted prematurely, called a **conflict miss**).

**Direct-mapped cache.** Each memory block maps to *exactly one* possible cache line, typically via `line_index = (block_address) mod (number_of_cache_lines)`. Checking for a hit means checking exactly one line's tag — fast and cheap, requiring only a single comparator in hardware.

The problem: if two frequently-used blocks happen to map to the *same* line (because they share the same low-order address bits despite being at very different memory locations), they will repeatedly evict each other even though the rest of the cache sits unused. This pattern, called **thrashing**, can produce a high miss rate even on a cache that is nowhere near full.

**Fully associative cache.** A memory block can be placed in *any* line of the cache; there is no fixed mapping. This eliminates conflict misses entirely — a block is only evicted when the whole cache is full and a replacement policy (e.g., LRU) chooses a victim, not because of an address coincidence. 

The problem: checking for a hit requires comparing the tag against *every* line in the cache simultaneously (via a **content-addressable memory**, comparators on every line in parallel). This is expensive in hardware (silicon area and power) and gets worse as cache size grows, which is why fully associative caches are only practical for very small caches (e.g., a TLB, or a tiny victim cache).

**Set-associative cache (the practical middle ground, and what real CPU caches use — e.g., 8-way or 16-way L2/L3 caches).** The cache is divided into *sets*, each containing `N` lines (an "N-way set-associative" cache). A block maps to exactly one *set* (via an index, like direct-mapped), but within that set it can go in any of the `N` lines (like fully associative, but only among those `N`). A hit check compares the tag against only the `N` lines in the relevant set — `N` comparators, not one and not "all of them."

This directly trades off against the other two: increasing `N` (more ways) reduces conflict misses — approaching fully-associative behavior — at the cost of more comparators and slightly higher per-access latency and power than direct-mapped. Decreasing `N` approaches direct-mapped's simplicity and speed but reintroduces more conflict-miss risk.

| | Direct-mapped | Set-associative (N-way) | Fully associative |
| --- | --- | --- | --- |
| Placement choices per block | 1 line | N lines (within one set) | Any line |
| Comparators needed per lookup | 1 | N | All lines |
| Conflict misses | Highest | Lower as N increases | None (only capacity/compulsory misses) |
| Hardware cost / power | Lowest | Moderate | Highest |
| Typical use | Simple/tiny caches | Most real L1/L2/L3 caches | TLBs, tiny victim caches |

**Why this is the right default for most CPU caches:** direct-mapped is too prone to pathological thrashing for general-purpose workloads, and fully associative doesn't scale to the sizes (hundreds of KB to many MB) modern L2/L3 caches need. Set-associativity — commonly 4-way to 16-way — captures most of fully-associative's conflict-miss reduction while keeping the per-access hardware cost bounded and roughly constant regardless of total cache size, since only `N` (not the whole cache) is searched per lookup.
