### Question: Decode String (Stacks/Queues — Medium)

Given an encoded string `s`, return its decoded string.

The encoding rule is: `k[encoded_string]`, where the `encoded_string` inside the square brackets is repeated exactly `k` times. Note that `k` is guaranteed to be a positive integer.

You may assume that the input string is always valid: no extra white space, square brackets are well-formed, etc. Also, you may assume that the original data does not contain any digits — digits only appear as the repeat counts `k`. Encodings can be nested, e.g. `2[a2[bc]]`.

**Input format:**
- A single string `s` consisting of lowercase English letters, digits, `[`, and `]`.

**Output format:**
- The fully decoded string.

**Worked Examples:**

1. `s = "3[a]2[bc]"` → `"aaabcbc"`
   (`3[a]` expands to `"aaa"`, `2[bc]` expands to `"bcbc"`, concatenated.)
2. `s = "3[a2[c]]"` → `"accaccacc"`
   (Inner `2[c]` → `"cc"`, giving `"acc"` inside the brackets; the outer `3[...]` repeats `"acc"` three times.)
3. `s = "2[abc]3[cd]ef"` → `"abcabccdcdcdef"`
   (`2[abc]` → `"abcabc"`, `3[cd]` → `"cdcdcd"`, then the trailing literal `"ef"` is appended as-is.)

**Constraints:**
- `1 <= s.length <= 30`
- `s` consists of lowercase English letters, digits, and the characters `[` and `]`.
- `s` is guaranteed to be a valid encoding.
- `1 <= k <= 300` for every repeat count `k` appearing in `s`.
- The length of the decoded output is guaranteed to fit in a 32-bit integer.

---

### Step-by-Step Walkthrough

**Approach — Two Stacks (counts and partial strings)**

The core difficulty is nesting: `3[a2[c]]` requires finishing the *inner* bracket before the *outer* one can be resolved. That "finish the innermost thing first, then resume the thing that was paused" pattern is exactly what a stack gives us for free, so we process the string left to right with a stack-based state machine instead of recursion (though a recursive-descent parser would also work — the stack version avoids explicit recursion overhead and is easier to reason about iteratively).

We keep:
- `countStack`: pending repeat counts, one per currently-open `[`.
- `stringStack`: the partially-built string accumulated *before* each currently-open `[`.
- `currentString`: the string being built for the current (innermost) bracket level.
- `currentNum`: the multi-digit number currently being parsed (counts can be more than one digit, e.g. `300[x]`).

Walk through each character `c` of `s`:

1. **If `c` is a digit:** the number might be multiple digits long (`"300"`), so accumulate: `currentNum = currentNum * 10 + (c - '0')`.
2. **If `c` is `[`:** we're about to enter a new nesting level. Push the number built so far onto `countStack`, push the string built so far onto `stringStack`, then reset `currentNum = 0` and `currentString = ""` to start fresh for the new level. (Everything built before this `[` must wait until we come back out, so we park it on the stacks.)
3. **If `c` is `]`:** we've just finished one complete bracket group. Pop the repeat count `k` and the string that was waiting (`prevString`) from the stacks. The decoded content for this level is `currentString` repeated `k` times. Append that to `prevString`, and that becomes the new `currentString` — i.e., we resume building the *outer* level exactly where we left off, now with the inner group's expansion folded in.
4. **If `c` is a lowercase letter:** simply append it to `currentString`.

At the end, `currentString` holds the fully decoded result, since every `]` always "pops back up" into the string that was paused.

**Why it works:** Each stack frame represents exactly one level of nesting that is "in progress." Pushing on `[` freezes the outer context so the inner one can be built in isolation; popping on `]` thaws it and merges the now-complete inner result back in. Because stacks are LIFO, the innermost (most recently opened) bracket is always the one resolved first — which is precisely the correct evaluation order for nested encodings.

**Complexity Analysis:**
- **Time complexity:** `O(maxK × n)` in the worst theoretical case (where `maxK` is the largest repeat count), because building the final string requires writing out every repeated character once — but bounded in practice by the problem's guarantee that the final decoded length fits in 32 bits; more precisely it is `O(length of final decoded string)`, since every character of the output is appended exactly once across the whole run.
- **Space complexity:** `O(n + length of final decoded string)` — the two stacks hold at most `O(n)` entries (one push per `[`/digit-run), plus the space needed to hold the growing `currentString` values, which in total is bounded by the final output length.

### C++ Code

```cpp
#include <iostream>
#include <string>
#include <stack>
using namespace std;

class Solution {
public:
    string decodeString(string s) {
        stack<int> countStack;          // pending repeat counts per open bracket
        stack<string> stringStack;      // string accumulated before each open bracket
        string currentString = "";      // string being built at the current nesting level
        int currentNum = 0;             // multi-digit number currently being parsed

        for (char c : s) {
            if (isdigit(c)) {
                // Accumulate multi-digit counts, e.g. "300[x]".
                currentNum = currentNum * 10 + (c - '0');
            } else if (c == '[') {
                // Entering a new nesting level: park the current count/string,
                // then start fresh for the bracketed sub-expression.
                countStack.push(currentNum);
                stringStack.push(currentString);
                currentNum = 0;
                currentString = "";
            } else if (c == ']') {
                // Closing the innermost bracket: repeat currentString k times,
                // then glue it back onto the string that was paused.
                int k = countStack.top();
                countStack.pop();
                string prevString = stringStack.top();
                stringStack.pop();

                string expanded = "";
                expanded.reserve(currentString.size() * k);
                for (int i = 0; i < k; ++i) {
                    expanded += currentString;
                }
                currentString = prevString + expanded;
            } else {
                // Plain lowercase letter: just append it.
                currentString += c;
            }
        }

        return currentString;
    }
};

int main() {
    Solution sol;

    // Example 1
    cout << sol.decodeString("3[a]2[bc]") << " (expected aaabcbc)" << endl;

    // Example 2 (nested)
    cout << sol.decodeString("3[a2[c]]") << " (expected accaccacc)" << endl;

    // Example 3 (trailing literal text)
    cout << sol.decodeString("2[abc]3[cd]ef") << " (expected abcabccdcdcdef)" << endl;

    return 0;
}
```

**Trace against the examples:**
- `"3[a]2[bc]"`: at `[` after `3`, push count `3` and string `""`; build `"a"`; at `]`, pop `(3, "")`, expand to `"aaa"`, currentString = `"aaa"`. Continue: at `[` after `2`, push count `2` and string `"aaa"`; build `"bc"`; at `]`, pop `(2, "aaa")`, expand `"bc"` → `"bcbc"`, currentString = `"aaa" + "bcbc"` = `"aaabcbc"`. ✓
- `"3[a2[c]]"`: outer `[` pushes `(3, "")`; build `"a"`; inner `[` pushes `(2, "a")`, resets; build `"c"`; inner `]` pops `(2, "a")`, expands `"c"` → `"cc"`, currentString = `"a" + "cc"` = `"acc"`; outer `]` pops `(3, "")`, expands `"acc"` ×3 → `"accaccacc"`, currentString = `"" + "accaccacc"`. ✓
- `"2[abc]3[cd]ef"`: produces `"abcabc"`, then `"cdcdcd"` appended, then plain letters `"ef"` appended directly (no bracket involved) → `"abcabccdcdcdef"`. ✓

### 1. Operating Systems (Conceptual/Definition)

What are the four necessary conditions for deadlock to occur in an operating system? Briefly explain how the "deadlock prevention" and "deadlock avoidance" strategies differ in how they target these conditions.

**Answer:**

A deadlock is a state where a set of processes are each waiting for a resource held by another process in the same set, so none of them can ever proceed. Coffman (1971) showed that all four of the following conditions must hold simultaneously for a deadlock to occur:

1. **Mutual Exclusion** — At least one resource must be held in a non-shareable mode; only one process can use that resource at a time (e.g., a single printer, a lock on a data structure).
2. **Hold and Wait** — A process currently holding at least one resource is waiting to acquire additional resources that are currently held by other processes.
3. **No Preemption** — Resources cannot be forcibly taken away from a process; they can only be released voluntarily by the process holding them, once it has finished using them.
4. **Circular Wait** — There exists a set of processes `{P0, P1, ..., Pn}` such that `P0` is waiting for a resource held by `P1`, `P1` is waiting for a resource held by `P2`, ..., and `Pn` is waiting for a resource held by `P0`, forming a cycle.

**Prevention vs. Avoidance:**

- **Deadlock Prevention** works statically, at design time: it guarantees deadlock can *never* occur by ensuring at least one of the four conditions can structurally never be satisfied. For example: eliminate Hold-and-Wait by requiring a process to request all resources it will ever need up front, before execution starts; or eliminate Circular Wait by imposing a total ordering on resource types and requiring every process to request resources only in increasing order. This is simple to reason about but often hurts resource utilization and concurrency (processes hold more than they need, or wait longer than necessary).

- **Deadlock Avoidance** works dynamically, at runtime: it allows all four conditions to potentially exist, but before granting any resource request, the OS checks whether granting it could ever lead to an unsafe state (one from which deadlock becomes unavoidable regardless of future scheduling). The classic example is the **Banker's Algorithm**, which requires processes to declare their maximum possible resource needs in advance, and the OS only grants a request if the resulting system state is still "safe" (there exists some order in which all processes could still finish). Avoidance achieves better resource utilization than prevention, but at the cost of needing advance knowledge of maximum resource claims and the runtime overhead of the safety check on every request.

**Why this matters:** Understanding exactly which of the four conditions a given technique attacks is the key to analyzing *any* deadlock-handling scheme (prevention, avoidance, detection-and-recovery, or simply ignoring it as most general-purpose OSes like Linux/Windows do, relying on the fact that deadlocks are rare enough in practice that the overhead of avoidance isn't worth it — the "ostrich algorithm").

### 2. Computer Networks (Comparison)

Compare TCP and UDP as transport-layer protocols. For each of the following three use cases, state which protocol is the better fit and justify why: (a) a live video call, (b) transferring a large file, (c) a single DNS lookup.

**Answer:**

| Aspect | TCP | UDP |
|---|---|---|
| Connection | Connection-oriented — requires a 3-way handshake (`SYN`, `SYN-ACK`, `ACK`) before data flows. | Connectionless — a sender just fires datagrams with no setup. |
| Reliability | Guarantees delivery via acknowledgments and retransmission of lost segments. | Best-effort only; no acknowledgment, no retransmission — packets can be lost silently. |
| Ordering | Guarantees in-order delivery to the application (reorders out-of-order segments using sequence numbers). | No ordering guarantee; packets can arrive out of order and are delivered as-is. |
| Flow/Congestion control | Built-in (sliding window, slow start, congestion avoidance) to avoid overwhelming the receiver or the network. | None — the application must implement its own if needed. |
| Overhead | Higher — handshake, ACKs, retransmissions, and a larger (20-byte minimum) header add latency and bandwidth cost. | Lower — minimal 8-byte header, no handshake, no retransmission delay. |
| Typical use | File transfer, web browsing (HTTP), email — anywhere correctness matters more than latency. | Streaming media, gaming, DNS, VoIP — anywhere low latency matters more than occasional loss. |

**Applying this to the three scenarios:**

(a) **Live video call → UDP.** A dropped or late video/audio frame is better off being skipped entirely than retransmitted — by the time a TCP retransmission arrives, the moment it was meant for has already passed, and waiting for it causes visible stutter/lag far worse than a brief glitch. Real-time communication prioritizes low, consistent latency over perfect completeness, which is exactly UDP's trade-off (real systems like WebRTC build their own lightweight reliability/jitter-buffering on top of UDP rather than using TCP's heavier mechanism).

(b) **Large file transfer → TCP.** Every single byte of the file must arrive, and in the correct order, or the file is corrupted — correctness is non-negotiable here, and the latency cost of TCP's handshake/ACKs is negligible relative to the total transfer time. TCP's built-in congestion control also helps the transfer play fairly with other traffic on the network.

(c) **Single DNS lookup → UDP** (with TCP as a fallback for large responses). A DNS query is a small, single request/response exchange; the overhead of a full TCP handshake would often cost more time than the query itself. If the response doesn't arrive, the client can simply retry the whole query faster than waiting on TCP's connection setup — and DNS does fall back to TCP only when a response would exceed the UDP datagram size limit (e.g., for responses with many records, or when using DNSSEC).

**Why this matters:** The TCP-vs-UDP choice is the canonical example of the classic networking trade-off between reliability and latency — recognizing which one a given application actually needs (rather than defaulting to "TCP because it's reliable") is a recurring theme in both systems design interviews and real protocol design (it's also why QUIC, the protocol underlying HTTP/3, is built on top of UDP — to get TCP-like reliability features while avoiding TCP's head-of-line blocking and slow connection setup).

### 3. DBMS (Scenario/Applied)

You're building the backend for an analytics dashboard that aggregates order data and must serve read-heavy queries (totals per region, per day, per product category) to hundreds of concurrent dashboard viewers, with writes happening only a few times per minute from an order-processing pipeline. Would you normalize or denormalize this schema, and how would you approach the design?

**Answer:**

**Start from the trade-off itself.** Normalization (organizing data to minimize redundancy, typically up to 3NF/BCNF, by splitting data into related tables joined via foreign keys) optimizes for write correctness and storage efficiency: every fact is stored exactly once, so updates never risk leaving stale/inconsistent copies around. Denormalization intentionally reintroduces redundancy (duplicating or pre-aggregating data) to optimize for read speed, at the cost of more complex/careful writes and extra storage.

**Applying it to this scenario:** The workload described is heavily read-skewed (hundreds of concurrent dashboard reads vs. a handful of writes per minute), and the reads are aggregate queries (sums/counts grouped by region, day, category) — exactly the kind of query that gets expensive on a fully normalized schema, because every dashboard load would require joining `orders` with `products`, `regions`, `customers`, etc., and re-computing aggregates from scratch over potentially millions of rows. Given that read volume dominates by orders of magnitude and the aggregation logic is repeated identically for every viewer, I would lean toward a **denormalized** design for the read path, while keeping the normalized tables as the system of record:

1. **Keep a normalized OLTP schema** (`orders`, `order_items`, `products`, `regions`, etc.) as the source of truth, written to by the order-processing pipeline. This preserves write correctness and avoids update anomalies in the authoritative data.
2. **Build a denormalized reporting layer on top of it** — e.g., a pre-aggregated summary table like `daily_region_category_sales(date, region, category, total_amount, order_count)`, updated incrementally (or via a scheduled batch job / materialized view refresh) whenever new orders land. Since writes happen only a few times a minute, the cost of maintaining this derived table is small relative to the read savings.
3. **Point the dashboard at the denormalized table**, so each dashboard query becomes a cheap, indexed lookup/filter on pre-computed numbers instead of a multi-table join with on-the-fly aggregation.
4. **Decide freshness requirements explicitly** — if the dashboard can tolerate being a few seconds to minutes stale, a periodically refreshed materialized view or a change-data-capture pipeline into the summary table is simplest; if near-real-time is required, update the summary table transactionally (or near-transactionally) alongside each order write.

**Why this matters:** This is the standard OLTP-vs-OLAP split seen in real systems (normalized transactional store feeding a denormalized/columnar reporting store, e.g., via ETL into a data warehouse or a materialized view). The underlying principle — normalize where correctness and write integrity matter most, denormalize where read performance at scale matters most, and don't force a single schema to serve both roles equally well — comes up constantly in system design interviews whenever a workload description leans heavily toward one side of the read/write ratio.
