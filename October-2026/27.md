## DSA

### Question: Serialize and Deserialize Binary Tree (Trees — Hard)

**Problem Statement**

Design an algorithm to serialize and deserialize a binary tree. Serialization is the process of converting a tree into a string representation that can later be reconstructed back into the original tree structure (not just the same values — the exact same shape, including which nodes are null). There is no restriction on how the serialization algorithm works, as long as a tree can be serialized to a string and deserialized back to the original tree.

**Input/Output Format**

- `serialize(root)`: takes the root of a binary tree (node values are integers, nodes may be `null`) and returns a single string.
- `deserialize(data)`: takes a string produced by `serialize` and returns the root of a binary tree that is structurally and value-identical to the original.

**Examples**

1. Input tree: `[1,2,3,null,null,4,5]` (level order, i.e. `1` is root with left child `2` and right child `3`; `3` has left child `4` and right child `5`) → `serialize` produces some string `S`; `deserialize(S)` must reproduce the exact same tree shape.
2. Input tree: `[]` (empty tree, `root = null`) → `serialize(null)` returns a string representing "empty"; `deserialize` on that string returns `null`.
3. Input tree: `[1]` (single node, no children) → round-trips to a single node with both children `null`.

**Constraints**

- The number of nodes in the tree is in the range `[0, 10^4]`.
- `-1000 <= Node.val <= 1000`.
- The round trip `deserialize(serialize(root))` must produce a tree identical in shape and values to `root`.

### Step-by-Step Walkthrough

**Why naive level-order (BFS) output isn't quite enough on its own.** The usual LeetCode-style array representation `[1,2,3,null,null,4,5]` *implicitly* relies on knowing which positions are null to reconstruct parent-child relationships, which gets awkward to parse unambiguously as a flat string without extra bookkeeping. A cleaner approach that sidesteps all of that is to explicitly encode **every** null child as a sentinel in a **preorder** (root, then left subtree, then right subtree) traversal. Preorder is the natural choice because it visits a node *before* its children, so when we rebuild the tree we always know "the next token in the stream is the root of whatever subtree I'm currently reconstructing" — recursion falls out directly.

**Serialization.** Do a preorder DFS. At each node:
- If the node is `null`, emit a sentinel token (e.g. `"#"`) and stop recursing down that branch.
- Otherwise emit the node's value, then recurse into the left subtree, then the right subtree.

Join all emitted tokens with a delimiter (e.g. `,`) into one string. Because every null is explicitly recorded, the string fully determines the shape — there's no ambiguity about which child slot is missing.

Example for tree `1(2, 3(4, 5))`: preorder visits `1, 2, #, #, 3, 4, #, #, 5, #, #` → string `"1,2,#,#,3,4,#,#,5,#,#"`.

**Deserialization.** Split the string back into tokens and process them with an index/iterator that advances as we consume tokens (not an index we recompute — a simple queue or a shared position counter works cleanly). Define a recursive helper `buildNext()`:
- Pop the next token.
- If it's the sentinel `"#"`, return `null` — no node here, don't consume anything further for this slot.
- Otherwise, create a new node with that integer value, then recursively call `buildNext()` to assign its left child, and again to assign its right child, then return the node.

Because serialization was preorder with explicit nulls, the very first token is always the root of whatever subtree we're currently rebuilding, and the two recursive calls automatically consume exactly the tokens that belonged to the left subtree and then the right subtree — no lookahead or length bookkeeping needed. This mirrors serialization exactly, which is what guarantees a correct round-trip: every node written is read back in the same order, in the same role (root-then-left-then-right).

**Why this reconstructs the tree exactly.** Preorder traversal order (root, left, right), combined with explicit null markers, is a *complete, unambiguous* encoding of the tree's shape — it's a classic result that a binary tree is uniquely determined by its preorder traversal when null children are included (you need that inclusion; preorder *without* nulls alone is not enough to reconstruct shape, which is why many textbook "reconstruct from preorder+inorder" problems exist — we avoid needing a second traversal entirely by paying the small cost of writing out the nulls).

**Complexity.**
- `serialize`: visits each of the `n` real nodes once and emits one sentinel per null child (at most `n + 1` nulls for `n` nodes), so **O(n)** time and **O(n)** output size.
- `deserialize`: consumes each token exactly once, doing O(1) work per token (besides string→int parsing), so **O(n)** time.
- Both use **O(h)** auxiliary recursion-stack space, where `h` is the tree height (worst case `O(n)` for a degenerate/skewed tree), plus **O(n)** for the token buffer itself.

### C++ Code

```cpp
#include <string>
#include <vector>
#include <sstream>
using namespace std;

struct TreeNode {
    int val;
    TreeNode *left;
    TreeNode *right;
    TreeNode(int x) : val(x), left(nullptr), right(nullptr) {}
};

class Codec {
public:
    // Preorder DFS: root value (or '#' for null), then left subtree, then right.
    string serialize(TreeNode* root) {
        string out;
        serializeHelper(root, out);
        return out;
    }

    TreeNode* deserialize(string data) {
        // Split the comma-delimited stream into tokens up front.
        vector<string> tokens;
        stringstream ss(data);
        string token;
        while (getline(ss, token, ',')) {
            tokens.push_back(token);
        }
        size_t pos = 0; // shared read cursor, advanced by buildNext()
        return buildNext(tokens, pos);
    }

private:
    void serializeHelper(TreeNode* node, string& out) {
        if (!out.empty()) out += ',';
        if (!node) {
            out += '#';
            return;
        }
        out += to_string(node->val);
        serializeHelper(node->left, out);
        serializeHelper(node->right, out);
    }

    TreeNode* buildNext(const vector<string>& tokens, size_t& pos) {
        // Each call consumes exactly one token for "this slot", then (if it
        // was a real node) recursively consumes the tokens for its left
        // subtree and then its right subtree.
        const string& tok = tokens[pos++];
        if (tok == "#") {
            return nullptr;
        }
        TreeNode* node = new TreeNode(stoi(tok));
        node->left = buildNext(tokens, pos);
        node->right = buildNext(tokens, pos);
        return node;
    }
};
```

## CS Fundamentals

### 1. DBMS (Conceptual/Definition)

Explain the four ACID properties a database transaction must satisfy. For each property, give a concrete one-sentence example of what would go wrong if that property alone were dropped.

**Answer:**

**ACID** stands for **Atomicity, Consistency, Isolation, Durability** — the four guarantees that let a database treat a sequence of operations as one reliable unit of work, even in the presence of crashes, concurrent transactions, or errors mid-operation.

- **Atomicity** — a transaction is "all or nothing": either every operation inside it commits, or none of its effects are visible at all, even if the transaction fails partway through. *Without it:* a bank transfer that debits account A but crashes before crediting account B would leave the money permanently vanished — the debit half completed while the credit half silently didn't, with no way to tell from the data alone that anything went wrong.
- **Consistency** — a transaction can only move the database from one valid state to another valid state, never violating declared constraints (foreign keys, unique constraints, check constraints, application-level invariants the transaction is supposed to preserve). *Without it:* an "ON DELETE" that removes a parent row could leave child rows pointing at a foreign key that no longer exists, silently corrupting referential integrity that every other query assumes holds.
- **Isolation** — concurrently running transactions must not observe each other's uncommitted intermediate states; the net effect must look as if transactions ran one at a time in some order (the exact strength of this guarantee is tunable via isolation levels like Read Committed, Repeatable Read, Serializable). *Without it:* transaction 1 reads a row transaction 2 is in the middle of modifying (a "dirty read"), bases a calculation on that half-written value, and if transaction 2 then rolls back, transaction 1's result is built on data that officially never existed.
- **Durability** — once a transaction commits, its effects survive any subsequent crash, power loss, or restart — committed data is written somewhere (typically a write-ahead log flushed to disk) that outlives a process failure. *Without it:* the database could report "transfer successful" to the user, then lose power a second later and come back up with the transfer silently undone, even though the system already told the user it succeeded.

The reason all four are bundled as one acronym rather than treated separately is that they're *interdependent* in practice: for instance, atomicity is usually what durability's crash-recovery log is built to restore (undo incomplete transactions, redo committed ones), and isolation is what prevents one transaction's intermediate, not-yet-atomic state from corrupting another transaction's view of consistency. Dropping any single one undermines guarantees application code typically assumes hold unconditionally, which is why relaxing them (e.g. weaker isolation levels for performance) is always a deliberate, documented trade-off, not a default.

### 2. Computer Networks (Comparison)

Compare TCP and UDP. Beyond "TCP is reliable, UDP is not," explain *mechanically* how TCP achieves reliability, and describe a real scenario where UDP's lack of those guarantees is actually the better engineering choice.

**Answer:**

Both are transport-layer protocols sitting on top of IP, but they make opposite trade-offs between guarantees and overhead.

| | TCP | UDP |
| --- | --- | --- |
| Connection | Connection-oriented (three-way handshake: SYN, SYN-ACK, ACK) | Connectionless — no handshake, packets ("datagrams") just get sent |
| Ordering | Guaranteed — receiver reorders out-of-order segments using sequence numbers | Not guaranteed — datagrams can arrive in any order, or not at all |
| Reliability | Guaranteed delivery via acknowledgments and retransmission | Best-effort — no acknowledgment, no retransmission |
| Flow/congestion control | Yes — sliding window, slow start, congestion avoidance algorithms | None — sender can overwhelm the receiver or the network with no backoff |
| Overhead | Higher (20+ byte header, handshake round-trip, retransmission state) | Minimal (8-byte header, no connection state) |

**Mechanically, how TCP gets reliability:**
1. **Sequence numbers** — every byte of the stream is numbered. The receiver can detect gaps (missing data) and reorder segments that arrive out of sequence, reconstructing the original byte stream regardless of the order packets actually arrived over the network.
2. **Acknowledgments (ACKs)** — the receiver tells the sender the sequence number it's successfully received up to (cumulative ACK). The sender keeps a copy of any data it has sent but not yet had acknowledged.
3. **Retransmission timers / fast retransmit** — if an ACK for some data doesn't arrive within a timeout (or the sender sees duplicate ACKs signaling a gap), it resends that data, assuming it was lost. This repeats until the receiver confirms receipt.
4. **Flow control (sliding window)** — the receiver advertises how much buffer space it has (its "window"), and the sender won't send more unacknowledged data than that, preventing it from overrunning a slow receiver.
5. **Congestion control** (slow start, AIMD, etc.) — the sender ramps up how much data it sends based on observed network conditions, backing off sharply when it detects loss, which it interprets as a signal of congestion.

Together, these mean: no byte is silently dropped (retransmission), no byte is delivered out of order (sequence numbers), and the sender won't flood a slow receiver or a congested network (flow/congestion control).

**Where UDP's lack of all that overhead is the right call: real-time voice/video calls (VoIP, video conferencing) or live multiplayer game state updates.** In a live audio call, a packet representing 20ms of audio that arrives late is *worse than useless* — by the time TCP would retransmit it and have it arrive in order, that moment in the conversation has already passed, and playing it back out of order just garbles the audio further. The application would rather just drop that one sample and move on to the current one than stall waiting for TCP's in-order, no-gaps guarantee. UDP lets the application receive datagrams as they arrive, decide for itself how to handle loss (often: just skip it, maybe interpolate), and avoids the handshake latency and retransmission stalls that would make the "reliability" actively hurt a latency-sensitive, "freshest data wins" use case. The general pattern: reach for UDP (often with a thin custom protocol on top, as real-time media protocols do) whenever stale-but-complete is worse than current-but-lossy.

### 3. System Design Basics (Scenario/Applied)

You're asked to design a URL shortener (like bit.ly): given a long URL, return a short unique code; given the short code, redirect to the original URL. Walk through how you'd generate the short codes, how you'd avoid collisions, and what happens as the system needs to scale to billions of URLs.

**Answer:**

**Core data model.** At minimum you need a mapping `short_code -> long_url`, stored in some database (a key-value store or a simple relational table `(short_code PRIMARY KEY, long_url, created_at, ...)` works fine — the access pattern is almost entirely point lookups by `short_code`, which is exactly what a key-value store or an indexed primary key is built for).

**Generating the short code — two main strategies:**

1. **Hash the long URL** (e.g. MD5/SHA-256) and take the first N characters, base-62 encoded (`[a-zA-Z0-9]`) to keep the code short and URL-safe. With base-62 and, say, 7 characters, you get `62^7 ≈ 3.5 trillion` possible codes — plenty of keyspace. The problem: **hash collisions are possible** (two different long URLs truncating to the same short prefix), so you must explicitly check: look up the generated code; if it's already taken by a *different* long URL, either append more hash characters, append a small disambiguating suffix, or just retry with a different salt. This makes the write path "generate, check, possibly retry" rather than a guaranteed one-shot.
2. **Counter-based / ID-based generation** (the more common real-world choice): maintain a globally unique, monotonically increasing integer ID (from an auto-increment column, a distributed ID generator like Snowflake, or a pre-allocated range handed out to each server) for every new URL, then base-62 encode *that integer* directly into the short code. Because the integer is unique by construction, **the short code is unique by construction too — no collision checking needed at all**, which is the main reason this approach is preferred at scale: it removes an entire class of write-path contention (no "check if taken, retry" loop).

**Redirect path (the hot path — reads vastly outnumber writes for a URL shortener).** `GET /{short_code}` → look up `long_url` by `short_code` → return an HTTP 301/302 redirect. This needs to be *fast* and handle very high read QPS, so:
- Put a **cache** (e.g. an in-memory key-value cache) in front of the database for hot short codes — most real-world traffic follows a power law where a small fraction of links get the vast majority of clicks, so cache hit rates are typically very high.
- Choose **302 (temporary) over 301 (permanent)** redirects if you want click-through analytics on every request — browsers aggressively cache 301s and may stop even hitting your server on repeat visits, which breaks click tracking; 302 keeps every click flowing through your system if that data matters to the product.

**Scaling to billions of URLs:**
- **Database sharding/partitioning** — once a single database instance can't hold or serve the volume, partition by `short_code` (e.g. consistent hashing, or ranges of the counter-based ID) across many database shards, so each shard holds a manageable slice of the keyspace and read/write load is spread out.
- **Distributed ID generation** — if using the counter approach, a single centralized auto-increment counter becomes a bottleneck and single point of failure at scale. Use a distributed ID scheme (e.g. Snowflake-style IDs embedding a timestamp + machine ID + sequence number, or pre-allocating blocks of IDs to each application server so they can generate IDs locally without a round-trip per request) so no single component has to serialize every ID allocation in the world.
- **Horizontal scaling of the stateless redirect service** — since redirect servers don't hold state themselves (the database/cache does), you can run many identical redirect-service instances behind a load balancer and scale that tier independently of the storage tier.
- **CDN / edge caching** for extremely hot links, and read replicas for the database tier, to keep the heavy read traffic off the primary write path entirely.

The overarching design principle driving most of these choices: URL shorteners are **read-heavy and latency-sensitive on redirects, but comparatively low-volume and latency-tolerant on URL creation** — so nearly every scaling decision (collision-free ID-based codes over checked hashes, aggressive caching, 302s vs 301s, sharding by lookup key) optimizes the redirect path first, and treats the creation path as the place where it's fine to spend a bit more work to make redirects cheap and simple.
