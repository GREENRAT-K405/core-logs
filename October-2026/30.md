## DSA

### Question: Subarray Sum Equals K (Hashing/Maps — Medium)

**Problem Statement**

Given an integer array `nums` and an integer `k`, return the total number of **contiguous subarrays** whose elements sum to exactly `k`.

**Input/Output Format**

- Input: an integer array `nums`, and an integer `k`.
- Output: an integer — the count of contiguous subarrays summing to `k`.

**Examples**

1. `nums = [1, 1, 1]`, `k = 2` → Output: `2` (the subarrays `[1,1]` at indices `[0,1]` and `[1,2]`).
2. `nums = [1, 2, 3]`, `k = 3` → Output: `2` (the subarrays `[1,2]` and `[3]`).
3. `nums = [1, -1, 0]`, `k = 0` → Output: `3` (the subarrays `[1,-1]`, `[1,-1,0]`, and `[0]` — negative numbers mean a naive "shrink the window when the sum is too big" approach does not work here).

**Constraints**

- `1 <= nums.length <= 2 * 10^4`
- `-1000 <= nums[i] <= 1000`
- `-10^7 <= k <= 10^7`
- Aim for better than O(n^2).

### Step-by-Step Walkthrough

**The brute-force baseline.** For every pair `(i, j)` with `i <= j`, sum `nums[i..j]` and check if it equals `k`. That's O(n^2) time (or O(n^3) if you re-sum from scratch instead of extending a running total). It's correct but too slow for `n = 2 * 10^4`, and it doesn't use the fact that sums can be combined incrementally.

**Why a sliding window doesn't work here.** The classic "shrink from the left while the sum is too large" trick only works when all elements are non-negative, because growing the window monotonically increases the sum. Example 3 above has a `-1` in it — enlarging the window can *decrease* the sum, so there's no monotonic relationship to exploit. This is the detail that makes the problem a hashing problem rather than a two-pointer problem.

**Key insight — prefix sums.** Define `prefix[i] = nums[0] + nums[1] + ... + nums[i-1]` (the sum of the first `i` elements, with `prefix[0] = 0`). Then the sum of any subarray `nums[i..j-1]` is just `prefix[j] - prefix[i]`.

The condition "subarray `nums[i..j-1]` sums to `k`" becomes:

```
prefix[j] - prefix[i] = k
         prefix[i] = prefix[j] - k
```

So as you scan the array computing a running prefix sum `sum` at each position `j`, the number of valid subarrays ending at `j` is exactly the number of earlier prefix values equal to `sum - k`. That's a lookup, not a scan — if you've been recording how many times each prefix-sum value has occurred so far in a hash map, it's O(1) amortized per position.

**Algorithm.**

1. Initialize a hash map `prefixCount` with `{0: 1}` — this accounts for subarrays that start at index 0 (a prefix of the array itself summing to `k`; the "empty prefix before the array" is defined to have sum 0, occurring once).
2. Walk the array left to right, maintaining a running sum.
3. At each element, look up `sum - k` in the map and add its count to the answer (each occurrence is a valid starting point for a subarray ending here).
4. Then increment `prefixCount[sum]` by 1, so later positions can pair with this prefix.

**Why the `{0: 1}` seed matters.** Without it, a subarray starting at index 0 (e.g. `nums = [3]`, `k = 3`) would never be counted: its prefix sum after one element is 3, and you'd be looking for `sum - k = 0`, which must already be in the map *before* you process any elements.

**Complexity.**
- Time: O(n) — one pass, O(1) amortized hash map operations.
- Space: O(n) — up to one entry per distinct prefix sum.

### C++ Code

```cpp
#include <vector>
#include <unordered_map>
using namespace std;

int subarraySum(vector<int>& nums, int k) {
    // Maps a prefix-sum value to how many times it has occurred so far.
    // Seeded with {0: 1} so subarrays starting at index 0 are counted.
    unordered_map<int, int> prefixCount;
    prefixCount[0] = 1;

    int runningSum = 0;
    int answer = 0;

    for (int num : nums) {
        runningSum += num;

        // Any earlier prefix equal to (runningSum - k) marks a valid
        // subarray start: prefix[j] - prefix[i] = k  =>  prefix[i] = prefix[j] - k.
        auto it = prefixCount.find(runningSum - k);
        if (it != prefixCount.end()) {
            answer += it->second;
        }

        // Record this prefix sum for future positions to pair against.
        prefixCount[runningSum]++;
    }

    return answer;
}
```

## CS Fundamentals

### 1. Computer Architecture (Conceptual/Definition)

**Question:** What is cache coherence, and why does a multi-core processor need a cache coherence protocol (e.g. MESI) at all?

**Answer:**

**The problem it solves.** Each core on a modern CPU has its own private L1 (and usually L2) cache, sitting between it and a shared main memory. If two cores both cache the same memory address and one of them writes to its local copy, the other core's cache now holds a **stale** value it doesn't know is stale. Cache coherence is the guarantee that, despite each core having its own cache, all cores observe a single, consistent view of memory — specifically, that a write by one core is eventually visible to reads by every other core, and that writes to the same location appear in the same order to all cores.

**Why this is hard.** Without any protocol, cores have no way to find out that another core's write invalidated their cached copy — caches don't automatically talk to each other. Left unaddressed, this produces silent correctness bugs: a flag one thread sets to signal "data ready" might never be observed as set by another thread, because that thread is still reading its own stale cached copy.

**MESI, concretely.** MESI names four states a cache line can be in:

- **Modified (M):** this cache has the only copy, and it's been written — dirty, must eventually be written back to memory.
- **Exclusive (E):** this cache has the only copy, but it matches memory (clean).
- **Shared (S):** multiple caches may hold this line, all consistent with memory.
- **Invalid (I):** this cache's copy is stale/unusable and must be refetched.

Cores don't manage this manually — hardware **snoops** a shared bus (or an interconnect protocol) so that every cache sees every other cache's reads and writes to a given line. When core A wants to write to a line that core B holds as Shared, A broadcasts an invalidation; B's copy transitions to Invalid, and A's transitions to Modified. If B subsequently reads that address, it detects it has no valid copy, and either fetches from A (cache-to-cache transfer) or from memory, and the two settle into Shared again if neither writes further.

**Why this matters beyond correctness.** Coherence traffic is a real performance cost — "false sharing" (two unrelated variables that happen to land in the same cache line, written by different cores) causes constant invalidation ping-pong even though the cores aren't logically contending for the same data. This is also precisely the hardware mechanism that makes software memory models (what "happens-before" guarantees a language gives you) possible to implement efficiently: coherence guarantees a single order of writes *per address*; a memory model on top of it additionally has to order operations *across different addresses*, which is a separate, harder problem that coherence alone does not solve.

### 2. OOP (Comparison)

**Question:** Compare inheritance and composition as ways to reuse code across classes. Why is "favor composition over inheritance" common advice, and when is inheritance still the better tool?

**Answer:**

Both let one class reuse another's behavior, but they create very different relationships and failure modes.

**Inheritance** models an "is-a" relationship: a `Car` *is a* `Vehicle`. The subclass gets the superclass's implementation automatically, and — critically — it is bound to it at **compile time**, as a fixed hierarchical slot. This gives polymorphism "for free" wherever the base type is used.

**Composition** models a "has-a" relationship: a `Car` *has an* `Engine`. The containing class holds a reference/instance of the other class and explicitly delegates to it. The relationship can be wired up at runtime (constructor injection, setters), and swapped out.

| | Inheritance | Composition |
| --- | --- | --- |
| Relationship | is-a | has-a |
| Coupling | Tight — subclass depends on superclass internals | Loose — depends only on the composed object's interface |
| Flexibility | Fixed at compile time, single hierarchy slot (in most languages) | Can be swapped/reconfigured at runtime |
| Encapsulation | Weak — subclass can see/break protected state ("fragile base class" problem) | Strong — only the public interface is exposed |
| Reuse granularity | All-or-nothing (the whole superclass) | Pick exactly the behaviors you delegate to |

**Why composition is usually favored.** Inheritance creates the **fragile base class problem**: a seemingly safe change to a base class (adding a method, changing an internal call another method relied on) can silently break every subclass, because subclasses are coupled to implementation details, not just a contract. It also commits you to a single hierarchy — a class can extend only one base class in most mainstream OOP languages — so if you need two independent sets of reusable behavior, inheritance forces an awkward hierarchy while composition just means holding two objects. And a deep inheritance chain (`D extends C extends B extends A`) means understanding `D` requires reading four classes; a composed object's behavior is visible by reading its interface.

**When inheritance is still the right tool.** Inheritance earns its cost when there is a genuine, stable "is-a" relationship that the domain itself guarantees won't need to change shape — e.g. a GUI framework where `Button`, `Checkbox`, and `Slider` are all genuinely specializations of `Widget`, sharing layout/rendering plumbing that's meant to be inherited, not reconfigured at runtime. It's also the natural fit when you specifically want **polymorphic substitutability** baked into the type system itself (you want `List<Widget>` to transparently hold any of them) rather than built by hand through an interface that each composed class implements. The practical rule of thumb: reach for inheritance when the relationship is a true taxonomy and the shared code is meant to be fixed; reach for composition when you're assembling behavior from interchangeable parts, which is most of the time in application code.

### 3. Computer Networks (Scenario/Applied)

**Question:** Your mobile app's API calls are fast and reliable on office wifi, but on cellular networks with higher latency and occasional packet loss, requests feel sluggish and sometimes stall for several seconds before completing. Explain how TCP's behavior under latency and loss produces this, and what you would actually change.

**Answer:**

**Why latency alone slows things down — the handshake and slow start tax.** Every new TCP connection pays at least one round trip for the SYN/SYN-ACK handshake (more with TLS on top — see the TLS handshake discussion from an earlier day's CS Fundamentals) before a single byte of application data moves. On wifi with a ~5ms round-trip time (RTT) that's negligible; on cellular with a 100-300ms RTT, that's a quarter-second-plus spent before the request even starts. Worse, TCP's **slow start** congestion control doesn't send at full speed immediately — it starts with a small congestion window and roughly doubles it each round trip until it either fills the available bandwidth or hits loss. On a short-lived API call, the connection may never get out of slow start before the response is fully sent, meaning throughput is RTT-bound, not bandwidth-bound: the data transfer is dominated by "wait a round trip, send a bit more, wait another round trip" rather than one continuous stream.

**Why loss makes it much worse, not just a little worse.** Packet loss on cellular links is common (fading, handoffs between towers) and TCP's reaction to loss is aggressive by design: on a lost segment, standard congestion control (e.g. Reno-style) halves the congestion window, and if a retransmission timeout (RTO) is needed rather than fast retransmit, the sender has to *wait* for that timer to expire — typically starting around 200ms-1s and backing off exponentially on repeated loss — before resending. This is exactly the "stalls for several seconds" symptom: it's not that data is moving slowly, it's that the connection is sitting idle waiting for a retransmission timer, and each additional loss during that recovery compounds the wait.

**Mitigations, concretely:**

1. **Reduce round trips spent on setup.** Reuse connections (HTTP keep-alive / connection pooling) instead of opening a fresh TCP+TLS handshake per request. Where available, use TLS 1.3 (one round trip instead of two) and HTTP/2 or HTTP/3 to multiplex many logical requests over one already-warm connection, so only the first request pays the setup cost.
2. **Use QUIC/HTTP3 where possible.** QUIC runs over UDP and implements its own loss recovery, avoiding TCP head-of-line blocking at the transport level (one lost packet on a multiplexed TCP/HTTP2 connection stalls *all* in-flight streams until it's retransmitted; QUIC's independent streams don't have this problem) and supports 0-RTT reconnection to previously-seen servers.
3. **Tune client-side timeouts and retries deliberately.** A connect/request timeout tuned for wifi RTTs will fire false "failures" on cellular; but leaving it unbounded lets a user stare at a stalled spinner through a multi-second RTO. Set timeouts to realistic cellular RTT budgets, and retry idempotent requests with jittered backoff rather than relying on TCP's own retransmission timer alone.
4. **Reduce what has to be sent.** Smaller payloads (pagination, compression, trimming unnecessary response fields) mean fewer round trips are needed to clear slow start, so the RTT tax is paid once instead of several times.
5. **Don't fight the network layer in application code.** Resist the temptation to implement a custom reliability layer on top of TCP to "fix" this — TCP's behavior here is a reasonable, standardized response to real congestion/loss signals; the actual lever is reducing *how much* that behavior is triggered (fewer connections, fewer round trips, smaller payloads) and designing the UI to tolerate the tail latency that will still occasionally occur.
