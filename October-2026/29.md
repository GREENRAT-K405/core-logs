### Question: Maximum XOR With an Element From Array (Bit Manipulation — Hard)

**Problem Statement**

You are given an array `nums` of `n` non-negative integers, and an array `queries` where `queries[i] = [xi, mi]`. For the `i`-th query, find the maximum value of `nums[j] XOR xi` over all indices `j` such that `nums[j] <= mi`. If no element of `nums` satisfies `nums[j] <= mi`, the answer for that query is `-1`.

Return an array `answer` where `answer[i]` is the result of the `i`-th query.

**Input/Output Format**

- Input: `nums` (array of non-negative integers), `queries` (array of pairs `[xi, mi]`).
- Output: an array of integers, one per query, in the original query order.

**Examples**

1. Input: `nums = [0,1,2,3,4]`, `queries = [[3,1],[1,3],[5,6]]` → Output: `[3,3,7]`
   - Query `[3,1]`: eligible elements (`<= 1`) are `{0,1}`. Best is `3 XOR 0 = 3`.
   - Query `[1,3]`: eligible elements are `{0,1,2,3}`. Best is `1 XOR 2 = 3`.
   - Query `[5,6]`: eligible elements are `{0,1,2,3,4}`. Best is `5 XOR 2 = 7`.
2. Input: `nums = [5,2,4,6,6,3]`, `queries = [[12,4],[8,1],[6,3]]` → Output: `[15,-1,5]`
   - Query `[12,4]`: eligible elements are `{2,4,3}`. Best is `12 XOR 3 = 15`.
   - Query `[8,1]`: no element of `nums` is `<= 1`, so the answer is `-1`.
   - Query `[6,3]`: eligible elements are `{2,3}`. Best is `6 XOR 3 = 5`.
3. Input: `nums = [1]`, `queries = [[0,0]]` → Output: `[-1]`
   (`nums[0] = 1 > 0`, so no element is eligible.)

**Constraints**

- `1 <= nums.length, queries.length <= 10^5`
- `0 <= nums[i], xi, mi <= 10^9`
- Aim for roughly `O((n + q) log(max_value))` time, not `O(n * q)`.

### Step-by-Step Walkthrough

**Why brute force is too slow.** For each query we could scan all of `nums`, filter the elements `<= mi`, and XOR each against `xi` to find the max — that's `O(n)` per query, `O(n * q)` overall, which is up to `10^10` operations with the given constraints. We need something close to logarithmic per query.

**Key idea: separate "which elements are eligible" from "which XORs max."** The `mi` threshold only decides *which subset* of `nums` is in play; it has nothing to do with maximizing XOR. If we could answer "what's the max XOR of `x` against *any currently available* number" quickly, and incrementally grow the available set as the threshold rises, each query becomes cheap.

**Step 1 — sort `nums` ascending, and sort the queries by `mi` ascending** (keeping track of each query's original index so we can place answers back correctly). This lets us process queries in increasing order of threshold, and *incrementally* insert exactly the new elements of `nums` that just became eligible (`nums[j] <= mi`) as we move from one query to the next, using a pointer that only moves forward. No element is ever inserted twice, and we never need to remove one — thresholds only grow.

**Step 2 — maintain a binary trie (bitwise prefix tree) of the eligible numbers.** Each inserted number is represented as a fixed-width (30-bit, since `10^9 < 2^30`) binary string, walked from the most significant bit to the least, creating trie nodes as needed. This is the standard structure for "maximum XOR with some element of a dynamic set."

**Step 3 — answer each query by greedy bit matching.** To maximize `x XOR y` over all `y` currently in the trie, walk the trie from the root, and at each bit position prefer the child representing the *opposite* bit of `x` at that position (since `1 XOR 0 = 1` contributes to the answer, while matching bits contribute `0`). If that opposite-bit child doesn't exist, we're forced to take the matching-bit child (every internal node in the trie has at least one child, since it was created by some insertion). This greedy choice is correct because fixing the most significant differing bit first always yields a strictly larger result than any choice that only matches on a more significant bit — exactly the same greedy argument used for "maximum XOR pair in an array."

**Step 4 — handle emptiness.** If, by the time we process a query, no elements have been inserted yet (the pointer into sorted `nums` is still at 0), there is no eligible element at all, so the answer is `-1`.

**Why the complexity works out.** Each number is inserted into the trie exactly once, taking `O(log(max_value))` = `O(30)` per insertion, for `O(n log(max_value))` total. Each query does one `O(log(max_value))` trie walk. Sorting `nums` and the queries costs `O(n log n + q log q)`. Overall: `O((n + q) log(max_value) + n log n + q log q)`, comfortably fast enough for `n, q <= 10^5`.

- **Time:** `O(n log n + q log q + (n + q) * B)` where `B = 30` is the bit width — effectively `O((n + q) log(max_value))`.
- **Space:** `O(n * B)` for the trie in the worst case (no shared prefixes), plus `O(q)` for the answer and ordering arrays.

### C++ Code

```cpp
#include <vector>
#include <algorithm>
using namespace std;

class Solution {
public:
    static const int BITS = 30; // 0 <= value <= 1e9 < 2^30

    // Binary trie stored as parallel arrays: child[node][0/1] = index of child node, or -1.
    vector<array<int, 2>> trie;

    void insertNumber(int num) {
        int node = 0;
        for (int b = BITS - 1; b >= 0; --b) {
            int bit = (num >> b) & 1;
            if (trie[node][bit] == -1) {
                trie.push_back({-1, -1});
                trie[node][bit] = (int)trie.size() - 1;
            }
            node = trie[node][bit];
        }
    }

    // Max XOR of x against any number currently stored in the (non-empty) trie.
    int queryMaxXor(int x) {
        int node = 0;
        int result = 0;
        for (int b = BITS - 1; b >= 0; --b) {
            int bit = (x >> b) & 1;
            int want = bit ^ 1; // opposite bit maximizes this position's XOR contribution
            if (trie[node][want] != -1) {
                result |= (1 << b);
                node = trie[node][want];
            } else {
                node = trie[node][bit]; // guaranteed to exist: every internal node has >=1 child
            }
        }
        return result;
    }

    vector<int> maximizeXor(vector<int>& nums, vector<vector<int>>& queries) {
        sort(nums.begin(), nums.end());

        int n = (int)nums.size();
        int q = (int)queries.size();

        // Sort query indices by their threshold mi, ascending.
        vector<int> order(q);
        for (int i = 0; i < q; ++i) order[i] = i;
        sort(order.begin(), order.end(), [&](int a, int b) {
            return queries[a][1] < queries[b][1];
        });

        vector<int> answer(q, -1);
        trie.clear();
        trie.push_back({-1, -1}); // root

        int idx = 0; // next index in sorted nums not yet inserted
        for (int qi : order) {
            int x = queries[qi][0];
            int m = queries[qi][1];

            while (idx < n && nums[idx] <= m) {
                insertNumber(nums[idx]);
                ++idx;
            }

            if (idx == 0) {
                answer[qi] = -1; // nothing eligible yet
            } else {
                answer[qi] = queryMaxXor(x);
            }
        }

        return answer;
    }
};
```

## CS Fundamentals

### 1. DBMS (Comparison)

Compare a clustered index and a non-clustered (secondary) index: how is the data physically organized in each case, how many index lookups does a typical query need, and why can a table have only one clustered index but many non-clustered ones?

**Answer:**

A **clustered index** determines the *physical order* of the actual table rows on disk — the rows themselves are stored sorted by the clustered index key, typically as the leaf level of a B+ tree whose leaves *are* the data pages. Because the data can only be physically sorted one way at a time, a table can have **at most one** clustered index (often the primary key, by default in many engines like SQL Server and InnoDB/MySQL).

A **non-clustered index** is a *separate* structure from the table data: it's its own B+ tree whose leaves hold the indexed column's value plus a pointer back to the actual row — either the row's physical location, or (in InnoDB's case) the clustered index key, which is then used for a second lookup into the clustered index to fetch the full row. The table data itself is untouched and keeps whatever physical order the clustered index gave it (or heap order, if there's no clustered index at all). Because a non-clustered index is just extra metadata pointing *at* the data rather than *being* the data, a table can have **many** of them — one per column or column-combination you commonly filter/sort/join on.

**Lookup cost, concretely:**
- A query using the **clustered index** (e.g. `WHERE id = 5` when `id` is the clustered key) walks the B+ tree once and lands directly on the full row — one structure, one traversal.
- A query using a **non-clustered index** on a different column (e.g. `WHERE email = 'x@y.com'`) walks that index's B+ tree to find the matching entry, then (unless the query only needed columns already present in the index itself — a "covering index") follows the stored pointer and does a **second** lookup into the clustered index (or heap) to retrieve the rest of the row. This second hop is exactly what's called a "bookmark lookup" or "key lookup," and it's the reason non-clustered indexes are powerful for selective filtering but still costlier than a clustered hit when you need many columns back.

**Why this matters in practice:** choosing the clustered index key well (e.g. an auto-incrementing ID, so inserts append rather than causing page splits in the middle of the sorted order) is a bigger design decision than adding a non-clustered index, precisely because it dictates the physical layout of the whole table, not just one extra lookup structure — and changing it later means physically rewriting every row.

### 2. Operating Systems (Scenario/Applied)

Two processes, `P1` and `P2`, each need both a printer and a scanner to complete their jobs. `P1` acquires the printer first and then requests the scanner; `P2` acquires the scanner first and then requests the printer. Both are now blocked, each waiting on a resource the other holds. Name the four Coffman conditions, identify which ones are satisfied by this scenario, and describe one practical prevention technique that would have stopped this specific deadlock from forming.

**Answer:**

The **four Coffman conditions** are the necessary conditions that must *all* hold simultaneously for a deadlock to be possible:

1. **Mutual exclusion** — a resource can be held by only one process at a time (non-shareable).
2. **Hold and wait** — a process holding at least one resource is waiting to acquire additional resources currently held by other processes.
3. **No preemption** — a resource can only be released voluntarily by the process holding it; it cannot be forcibly taken away.
4. **Circular wait** — there exists a cycle of processes, each waiting for a resource held by the next one in the cycle.

**In this scenario, all four hold:**
- *Mutual exclusion*: the printer and scanner are each held exclusively by one process.
- *Hold and wait*: `P1` holds the printer while waiting for the scanner; `P2` holds the scanner while waiting for the printer.
- *No preemption*: neither process's held resource can be snatched away by the OS to hand to the other — each must release voluntarily, which won't happen since both are blocked.
- *Circular wait*: `P1` → waits on `P2` (for the scanner) → waits on `P1` (for the printer) → forms a cycle of length 2.

Since all four conditions are present, deadlock is not just possible here — it has already occurred.

**A practical prevention technique: resource ordering (breaking circular wait).** Deadlock prevention works by making at least one Coffman condition structurally impossible, and circular wait is usually the cheapest one to attack. Impose a global total order on all resource types (e.g. "printer = 1, scanner = 2") and require every process to request resources only in increasing order of this numbering. Under this rule, `P2` would have been *forced* to request the printer (order 1) before the scanner (order 2), just like `P1` — so `P2` would have had to wait for the printer first, never ending up holding the scanner while demanding the printer out of order. With both processes constrained to request low-numbered resources before high-numbered ones, the "wait for someone who waits for you" cycle can no longer form, because a cycle would require some process to request a lower-numbered resource while already holding a higher-numbered one, which the ordering rule forbids outright.

(Other valid approaches exist — e.g. requiring processes to request *all* resources they'll ever need up front, attacking hold-and-wait — but resource ordering is usually preferred in practice because it doesn't force a process to over-reserve resources it may not end up using.)

### 3. Computer Architecture (Conceptual/Definition)

Explain instruction pipelining in a CPU: what problem does it solve, what are the classic stages, and what are the three main types of hazards that can stall a pipeline?

**Answer:**

**The problem pipelining solves.** Without pipelining, a CPU executes one instruction completely — fetch, decode, execute, memory access, write-back — before starting the next one. Each stage uses different hardware (the fetch unit isn't doing anything useful while the ALU is executing, for instance), so running instructions strictly one-at-a-time leaves most of the chip idle most of the time. **Pipelining** overlaps these stages across *different* instructions, the way an assembly line overlaps different cars at different stations: while instruction 1 is being decoded, instruction 2 can already be fetched; while instruction 1 executes, instruction 2 decodes and instruction 3 fetches, and so on. This doesn't make any single instruction finish faster (it's still the same five stages), but it dramatically increases **throughput** — ideally, once the pipeline is full, one instruction completes every clock cycle instead of every five.

**Classic stages (the canonical 5-stage RISC pipeline):**
1. **IF — Instruction Fetch:** read the next instruction from memory (using the program counter).
2. **ID — Instruction Decode** (and register fetch): figure out what the instruction is and read its source operand registers.
3. **EX — Execute:** perform the ALU operation (arithmetic, address calculation, etc.).
4. **MEM — Memory Access:** read from or write to data memory, if the instruction needs to (e.g. a load or store).
5. **WB — Write Back:** write the result back into the destination register.

**The three classic hazard types — situations where the naive overlap breaks correctness or stalls the pipeline:**

1. **Structural hazards** — two instructions, in different pipeline stages at the same time, need the *same piece of hardware* simultaneously (e.g. a single combined memory unit needed by one instruction's fetch stage and another's memory-access stage in the same cycle). Fixed by duplicating hardware (e.g. separate instruction and data caches) or by stalling one instruction a cycle.
2. **Data hazards** — an instruction needs a value that a *previous, still-in-flight* instruction hasn't finished computing yet (e.g. `ADD R1, R2, R3` immediately followed by `SUB R4, R1, R5` — the second instruction needs `R1` before the first has written it back). Fixed primarily by **forwarding/bypassing** (routing the computed value directly from the EX stage of the first instruction to the EX stage of the second, instead of waiting for write-back), and where forwarding can't close the gap in time, by stalling (inserting a "bubble").
3. **Control hazards** — caused by branches: the pipeline doesn't know *which* instruction to fetch next until the branch is resolved (often several stages later), but by then it may have already speculatively fetched the wrong instructions. Fixed by techniques like **branch prediction** (guess a direction and speculatively execute, rolling back on a misprediction), **delayed branching**, or simply stalling until the branch resolves.

Deeper pipelines (modern CPUs often have 10-20+ stages) increase the potential throughput gain but make all three hazard types *more* costly when they occur — a misprediction on a 20-stage pipeline flushes far more in-flight work than on a 5-stage one — which is the fundamental tension pipeline-depth design has to balance.
