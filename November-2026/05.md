## DSA

### Question: Binary Tree Zigzag Level Order Traversal (Trees — Medium)

**Problem Statement**

Given the root of a binary tree, return the values of its nodes grouped level by level, but alternating direction: the first level left-to-right, the second level right-to-left, the third left-to-right again, and so on.

**Input/Output Format**

- Input: the root of a binary tree (nodes may hold any comparable value, e.g. integers; `root` may be `null` for an empty tree).
- Output: a list of lists of values — one inner list per level, in zigzag order.

**Examples**

1. Input: `[3,9,20,null,null,15,7]` (level 0: `3`; level 1: `9,20`; level 2: `15,7`) → Output: `[[3],[20,9],[15,7]]`
2. Input: `[1]` → Output: `[[1]]`
3. Input: `[]` (empty tree) → Output: `[]`

**Constraints**

- `0 <= number of nodes <= 2000`
- `-100 <= node value <= 100`
- Aim for O(n) time, where n is the number of nodes.

### Step-by-Step Walkthrough

**Start from the ordinary case.** A plain level-order traversal is a textbook BFS: push the root into a queue, and repeatedly drain exactly the nodes currently in the queue (that's one level), recording their values and pushing their children for the next round. The zigzag twist doesn't change *which* nodes belong to which level — it only changes the *order values are recorded in* on alternating levels. So the right move is: do the normal BFS, and just reverse the output list for every other level.

**Why track level size explicitly.** The queue mixes nodes from "the level I'm reading" with nodes from "the level I'm about to produce" unless we snapshot how many nodes belong to the current level *before* we start popping. Taking `levelSize = queue.size()` at the top of each round and looping exactly that many times is what keeps one level's nodes from bleeding into the next.

**The algorithm:**

1. If `root` is null, return an empty result immediately.
2. Initialize a queue with `root`, and a boolean `leftToRight = true`.
3. While the queue is non-empty:
   - Let `levelSize = queue.size()`.
   - Create an empty list `level`.
   - Pop exactly `levelSize` nodes, one at a time: append each popped node's value to `level`, and push its non-null children (left, then right) onto the queue for the next round.
   - If `leftToRight` is false, reverse `level` in place.
   - Append `level` to the result, and flip `leftToRight`.
4. Return the result.

**Why it's correct.** BFS visits nodes in strict level order because the queue is FIFO: every node pushed while processing level *k* is necessarily a child of a level-*k* node, so it can only be popped after all of level *k* is exhausted — i.e. it belongs entirely to level *k+1*. Snapshotting `levelSize` guarantees each iteration of the outer loop consumes exactly one full level and no more. The values within a level are collected left-to-right by construction (children pushed left-before-right); reversing that list for every other level is exactly the zigzag requirement, and reversing a short, already-materialized list doesn't disturb the queue or the traversal order for later levels.

**An alternative worth naming.** You could instead always append left-to-right but insert into the front of a deque on odd levels. That avoids a separate reverse step but is more fiddly to get right; reversing a plain list after the fact is easier to reason about and costs nothing asymptotically.

**Complexity.**
- Time: O(n) — every node is pushed and popped exactly once, and each level is reversed once; the total work across all reversals is still bounded by n.
- Space: O(n) — the queue holds at most one level's worth of nodes at a time (worst case O(n) for a wide tree), and the output stores every value exactly once.

### C++ Code

```cpp
#include <vector>
#include <queue>
using namespace std;

struct TreeNode {
    int val;
    TreeNode* left;
    TreeNode* right;
    TreeNode(int x) : val(x), left(nullptr), right(nullptr) {}
};

vector<vector<int>> zigzagLevelOrder(TreeNode* root) {
    vector<vector<int>> result;
    if (!root) return result;

    queue<TreeNode*> q;
    q.push(root);
    bool leftToRight = true;

    while (!q.empty()) {
        int levelSize = (int)q.size(); // snapshot: freeze this level's boundary
        vector<int> level(levelSize);

        for (int i = 0; i < levelSize; i++) {
            TreeNode* node = q.front();
            q.pop();

            // Fill left-to-right first; reverse afterwards if needed.
            int pos = leftToRight ? i : (levelSize - 1 - i);
            level[pos] = node->val;

            if (node->left) q.push(node->left);
            if (node->right) q.push(node->right);
        }

        result.push_back(level);
        leftToRight = !leftToRight;
    }

    return result;
}
```

The code places each value directly at its final index (`pos`) instead of appending then reversing — functionally identical to the two-step version described above, but it avoids a second pass over the level.

## CS Fundamentals

### 1. DBMS (Conceptual/Definition)

**Question:** What is a database index, how does it typically make reads faster, and what does it cost you in return?

**Answer:**

A **database index** is an auxiliary data structure, stored separately from the table itself, that maps column values to the physical location of the rows that hold them — so the engine can find matching rows without scanning the whole table.

**How it speeds up reads.** Without an index, looking up `WHERE email = 'x@y.com'` means a **full table scan**: read every row, check the predicate, discard most of them — O(n) work no matter how selective the query is. Most relational databases index using a **B-tree** (balanced, sorted, typically wide and shallow), so a lookup becomes a root-to-leaf descent plus a short leaf scan — O(log n) to find the first match, then a cheap walk through any additional matches, because B-trees keep keys sorted and clustered. Some engines also offer **hash indexes** for pure equality lookups (O(1)-ish, but useless for range queries like `BETWEEN` or `<`, since a hash destroys ordering) and other specialized forms (e.g. inverted indexes for full-text search).

**What it costs.**
- **Storage.** An index duplicates the indexed column's data (plus a pointer back to the row), so every index adds disk space roughly proportional to the table size.
- **Write overhead.** Every `INSERT`, `UPDATE` of an indexed column, or `DELETE` must also update every index on that table to keep it consistent — so each additional index makes writes slower. A table with ten indexes pays that cost ten times on every insert.
- **Planner complexity.** More indexes give the query planner more options, but also more choices to get wrong (it can pick a suboptimal index), and indexes themselves need periodic maintenance (rebuilding/reorganizing) as they fragment under heavy writes.

**Why it matters in practice:** indexing is a trade-off you make deliberately, column by column — you index the columns that appear in `WHERE`, `JOIN`, and `ORDER BY` clauses on your hottest queries, and you deliberately *don't* index columns that are rarely queried or updated extremely frequently, because an unused index is pure write-cost with no read benefit. "Just index everything" is a common beginner mistake that quietly degrades write-heavy workloads.

### 2. Computer Networks (Comparison)

**Question:** Compare TCP and UDP. What does TCP's extra machinery actually buy you, and when would you deliberately choose UDP despite giving that up?

**Answer:**

Both are transport-layer protocols that sit on top of IP, but they make opposite trade-offs between **reliability** and **overhead/latency**.

**TCP (Transmission Control Protocol)** is connection-oriented and reliable:
- **Handshake.** A 3-way handshake (`SYN`, `SYN-ACK`, `ACK`) establishes a connection before any data flows.
- **Guaranteed, ordered delivery.** Every byte is sequenced; the receiver acknowledges what it got, and the sender retransmits anything lost. The application never sees out-of-order or missing data — TCP reassembles it correctly before delivering it.
- **Flow control and congestion control.** TCP throttles the send rate to match the receiver's buffer and the network's capacity, backing off when it detects loss (a signal of congestion).
- **Cost.** All of this means per-packet overhead (sequence numbers, ACKs, retransmit timers) and extra latency, especially the handshake before the first byte of data even goes out.

**UDP (User Datagram Protocol)** is connectionless and unreliable:
- No handshake — the first packet you send *is* the first data the receiver gets (or doesn't).
- No acknowledgment, no retransmission, no ordering guarantee, no congestion control. A packet is sent once, and it either arrives or it's gone; the application gets no notification either way.
- Minimal header (8 bytes vs. TCP's 20+), so less overhead per packet and no connection-setup latency.

**Why you'd still choose UDP.** For many real-time use cases, a late or re-ordered packet is *worse than useless* — TCP would stall the whole stream waiting to retransmit and re-sequence a single lost packet, which is exactly the wrong behavior when the data is already stale by the time it could arrive. So:
- **Video/voice calls and live streaming** — a dropped video frame from a moment ago isn't worth delaying every frame after it; better to skip it and keep playing.
- **Online multiplayer games** — a stale position update is useless once a newer one exists; retransmitting it just adds lag.
- **DNS queries** — a single small request/response, where the application itself just retries on timeout; TCP's setup cost would dwarf the actual payload.

The underlying principle: TCP is the right default when correctness of every byte matters more than timeliness (file transfer, web pages, APIs); UDP (often with a thin application-level reliability layer bolted on only where it's actually needed, as QUIC and WebRTC do) is the right choice when timeliness matters more than any single packet.

### 3. OOP (Scenario/Applied)

**Question:** You're building a payroll system that must compute pay differently for `SalariedEmployee`, `HourlyEmployee`, and `CommissionedEmployee`. A colleague suggests a single `Employee` class with an `employeeType` string field and a `calculatePay()` method full of `if (type == "salaried") ... else if (type == "hourly") ...`. What's wrong with that design, and how would polymorphism fix it?

**Answer:**

The `if/else` chain on a type tag is a classic smell usually called a **type code** or **switch on type**, and it causes two concrete problems as the system grows.

**Problem 1 — it violates the Open/Closed Principle.** Every time payroll adds a new employee category (say, `ContractEmployee`), you have to go back into `calculatePay()` and add another branch. That single method becomes a growing, shared bottleneck that every new employee type must modify — and it's not just `calculatePay()`; realistically there will be parallel `if/else` chains for `calculateBonus()`, `calculateTax()`, and so on, all needing the same edit in lockstep. Forget one, and you have a silent bug: a new employee type that computes bonus correctly but defaults to $0 pay.

**Problem 2 — it's fragile and untyped.** `employeeType` is just a string. Nothing stops a typo (`"salaried "` with a trailing space) from silently falling through to an `else` branch that does the wrong thing, and the compiler can't catch it — you only find out at runtime, maybe in production payroll.

**The polymorphic fix.** Make `Employee` an abstract base class (or interface) declaring `calculatePay()` as a pure virtual method, with no implementation and no type tag. Each concrete subclass — `SalariedEmployee`, `HourlyEmployee`, `CommissionedEmployee` — implements `calculatePay()` with *its own* logic:

```cpp
class Employee {
public:
    virtual double calculatePay() const = 0;
    virtual ~Employee() = default;
};

class SalariedEmployee : public Employee {
    double monthlySalary;
public:
    explicit SalariedEmployee(double s) : monthlySalary(s) {}
    double calculatePay() const override { return monthlySalary; }
};

class HourlyEmployee : public Employee {
    double hourlyRate; double hoursWorked;
public:
    HourlyEmployee(double r, double h) : hourlyRate(r), hoursWorked(h) {}
    double calculatePay() const override { return hourlyRate * hoursWorked; }
};
```

The payroll loop then just does:

```cpp
for (Employee* e : allEmployees) {
    totalPayout += e->calculatePay(); // runtime dispatch picks the right override
}
```

The caller never asks "what type is this?" — it asks the object to do its own job, and virtual dispatch (via the vtable) routes the call to the correct override automatically.

**Why this actually solves both problems.** Adding `ContractEmployee` means writing one new class with its own `calculatePay()` — the payroll loop, and every other existing class, is untouched (satisfying Open/Closed: open for extension, closed for modification). And because each subclass is a distinct type, the compiler enforces that every concrete employee class *must* provide `calculatePay()` (it's pure virtual) — there's no string to typo and no branch to forget. This is precisely what polymorphism is for: pushing type-specific behavior into the types themselves, so calling code can stay generic over the abstraction (`Employee`) instead of enumerating its subtypes.
