### Question: Merge k Sorted Linked Lists (Linked Lists — Hard)

You are given an array of `k` linked lists, `lists`, each linked list is sorted in ascending order.

Merge all the linked lists into one sorted linked list and return its head.

**Input format:** An array `lists` of `k` list-heads (each `ListNode*`, possibly `nullptr` for an empty list).

**Output format:** The head of a single sorted linked list containing all the nodes.

**Example 1:**
```
Input: lists = [[1,4,5],[1,3,4],[2,6]]
Output: [1,1,2,3,4,4,5,6]
Explanation: The linked lists are:
1->4->5
1->3->4
2->6
merging them into one sorted list:
1->1->2->3->4->4->5->6
```

**Example 2:**
```
Input: lists = []
Output: []
```

**Example 3:**
```
Input: lists = [[]]
Output: []
```

**Constraints:**
- `k == lists.length`
- `0 <= k <= 10^4`
- `0 <= lists[i].length <= 500`
- `-10^4 <= lists[i][j] <= 10^4`
- `lists[i]` is sorted in ascending order.
- The sum of `lists[i].length` won't exceed `10^4`.

### Step-by-Step Walkthrough

**The naive idea:** Merge the lists two at a time, left to right (merge list 1 with list 2, merge that result with list 3, and so on). If there are `k` lists and roughly `N` total nodes, this does `k-1` merge passes, and each pass can touch up to `N` nodes, giving `O(k*N)` time. For large `k` this is wasteful — most nodes get re-scanned many times across passes.

**Key insight:** At any point during merging, we only need to know which of the current "head" nodes of the remaining lists is the smallest, so we can pop it off and advance that list. A **min-heap (priority queue)** is exactly the structure for "give me the smallest of a dynamic set, repeatedly" in `O(log k)` per operation instead of `O(k)` (a linear scan).

**Algorithm:**
1. Push the head node of every non-empty list into a min-heap, keyed by node value. The heap holds at most `k` nodes at any time.
2. Build a dummy head for the answer list, with a `tail` pointer to its current end.
3. While the heap is not empty:
   - Pop the smallest node `cur`.
   - Attach `cur` to `tail`, then advance `tail = cur`.
   - If `cur->next` exists, push `cur->next` into the heap (it's the new head of that particular list).
4. Return `dummy->next`.

**Why it works:** The heap always contains exactly the current frontier (the smallest unconsumed node of each still-non-empty list). Popping the global minimum of that frontier and replacing it with its successor maintains the invariant that the true next-smallest overall node is always in the heap. This is the same idea as k-way merge in external sorting.

**Alternative (divide and conquer):** Pair up lists and merge pairs (like merge sort's merge step) in `log k` rounds, each round touching all `N` nodes once: also `O(N log k)` total, same complexity, heap approach is simpler to code and has the same asymptotic cost.

**Complexity:**
- Time: `O(N log k)` — each of the `N` nodes is pushed/popped from a heap of size at most `k` once.
- Space: `O(k)` for the heap (output list reuses input nodes, no extra node allocation).

### C++ Code

```cpp
#include <vector>
#include <queue>

struct ListNode {
    int val;
    ListNode *next;
    ListNode() : val(0), next(nullptr) {}
    ListNode(int x) : val(x), next(nullptr) {}
    ListNode(int x, ListNode *next) : val(x), next(next) {}
};

class Solution {
public:
    ListNode* mergeKLists(std::vector<ListNode*>& lists) {
        // Min-heap of node pointers, ordered by node value.
        auto cmp = [](ListNode* a, ListNode* b) {
            return a->val > b->val; // priority_queue is a max-heap by default, so flip it.
        };
        std::priority_queue<ListNode*, std::vector<ListNode*>, decltype(cmp)> heap(cmp);

        // Seed the heap with the head of every non-empty list.
        for (ListNode* head : lists) {
            if (head != nullptr) {
                heap.push(head);
            }
        }

        ListNode dummy(0);
        ListNode* tail = &dummy;

        while (!heap.empty()) {
            ListNode* cur = heap.top();
            heap.pop();

            tail->next = cur;
            tail = cur;

            if (cur->next != nullptr) {
                heap.push(cur->next);
            }
        }

        tail->next = nullptr; // terminate the merged list cleanly
        return dummy.next;
    }
};
```

### 1. Operating Systems (Conceptual)

What is thrashing in the context of virtual memory, what causes it, and what are two concrete ways an operating system can detect and mitigate it?

**Answer:**

Thrashing is a state where a system spends the vast majority of its time on page faults and the associated swapping between RAM and disk, instead of doing useful work for processes. CPU utilization paradoxically drops even though the system looks "busy," because most cycles go into servicing page faults rather than executing instructions.

**Why it happens:** Each process needs a minimum "working set" of pages in memory to run efficiently. If the total memory demand of all currently running processes (the sum of their working sets) exceeds physical RAM, the OS keeps evicting pages that are about to be needed again. A process faults, the OS brings in a page (possibly evicting a page another process needs), that other process then faults, and so on — the degree of multiprogramming has exceeded what memory can support.

**Detection:**
1. **Page-fault frequency (PFF) monitoring** — the OS tracks each process's fault rate (faults per unit time or per instruction). A fault rate that suddenly spikes above a high-water mark signals the process's working set no longer fits comfortably in its allotted frames.
2. **CPU utilization vs. degree of multiprogramming graph** — classically, as more processes are admitted, CPU utilization rises (more work is available to overlap with I/O), but past a point it sharply falls off a cliff; that falling edge is thrashing, and the OS (or an administrator) can watch for utilization dropping while multiprogramming level is still high as an indirect thrashing signal.

**Mitigation:**
- **Working-set model**: allocate each process exactly the set of pages it has referenced in a recent time window (its working set), and only admit/run a new process if enough free frames remain after satisfying all current working sets — this directly prevents over-commitment.
- **Local (per-process) page replacement with load control**: if PFF is too high for a process, give it more frames (if available); if none are available system-wide, suspend/swap out one or more whole processes to free their frames for the rest, reducing the degree of multiprogramming until fault rates stabilize.

This matters in practice because it explains why adding more concurrent processes (or containers, in a modern cloud-native context) past a memory ceiling causes throughput to collapse rather than degrade gracefully — capacity planning and autoscaling policies need headroom precisely to avoid this cliff.

### 2. Computer Networks (Comparison)

Compare TCP and UDP, and explain which one you would choose for (a) a video conferencing app and (b) a file transfer utility, and why.

**Answer:**

**TCP (Transmission Control Protocol):**
- Connection-oriented: establishes a connection via a three-way handshake (SYN, SYN-ACK, ACK) before data flows.
- Reliable: guarantees delivery via acknowledgments and retransmission of lost segments.
- Ordered: resequences out-of-order segments at the receiver so the application sees a correctly ordered byte stream.
- Flow control (sliding window) and congestion control (e.g., slow start, congestion avoidance) to avoid overwhelming the receiver or the network.
- Higher overhead: handshake latency, per-segment acknowledgments, header overhead (20+ bytes).

**UDP (User Datagram Protocol):**
- Connectionless: no handshake, each datagram is sent independently.
- Unreliable: no acknowledgment or retransmission — a lost datagram is simply gone unless the application layer handles it.
- Unordered: datagrams may arrive out of order; the application must reorder if it cares.
- No built-in flow/congestion control (though well-behaved applications implement their own).
- Lower overhead: minimal 8-byte header, no handshake latency, no retransmission delay.

**(a) Video conferencing → UDP.** Real-time audio/video cares about low, predictable latency far more than perfect delivery. A dropped or late frame is better handled by the application (interpolate, skip, degrade quality) than by TCP's retransmission, which would stall the entire stream waiting for one lost packet to be resent — introducing exactly the kind of lag that ruins a live call. Protocols like RTP are built on UDP for this reason.

**(b) File transfer → TCP.** Here correctness (every byte must arrive, and in order) matters far more than latency — a file with a missing or corrupted chunk is useless. TCP's reliability, ordering, and congestion control (so it shares bandwidth fairly and doesn't overwhelm the network) make it the natural fit; this is why FTP, HTTP downloads, and SCP all run over TCP.

The general principle: pick UDP when timeliness trumps completeness and the application can tolerate/handle loss itself; pick TCP when completeness and correctness are non-negotiable and some added latency is acceptable.

### 3. System Design Basics (Scenario)

You are asked to design a URL-shortening service (like bit.ly) that must handle 100 million new short links per month and far more redirect reads than writes. Walk through the key components of your design and the main trade-off you'd make.

**Answer:**

**Core requirements:** Given a long URL, generate a short, unique alias; given the alias, redirect (HTTP 301/302) to the original URL. Read-heavy (redirects vastly outnumber creations — a typical ratio is 100:1 or more), so the design should optimize reads without sacrificing write correctness.

**Key components:**

1. **ID generation.** Need a way to produce a unique, compact identifier for each long URL. Two common approaches:
   - *Base62 encoding of an auto-incrementing counter* (e.g., a distributed counter service, or a range of IDs pre-allocated per application server to avoid a single point of contention). Base62 (`[a-zA-Z0-9]`) keeps aliases short — 7 characters of base62 covers `62^7 ≈ 3.5 trillion` values, comfortably more than needed.
   - *Hashing the long URL* (e.g., MD5/SHA, take the first few bytes, base62-encode) and checking for collisions, retrying with a salt if one occurs. This avoids a centralized counter but adds collision-handling complexity.
   - For 100M/month at scale, a pre-allocated-range counter approach (each server claims a block of IDs from a coordination service like Zookeeper/etcd, so it can mint IDs locally without a round trip per request) is simpler to reason about and avoids collision retries.

2. **Storage.** A key-value store mapping `short_code → long_url` (plus metadata like creation time, expiry, owner). Given the simple access pattern (point lookups by key), a distributed key-value store or a sharded relational table keyed by `short_code` both work; key-value stores (e.g., DynamoDB, Cassandra) scale horizontally more naturally for this pattern. Shard by a hash of `short_code` to spread load evenly.

3. **Caching layer.** Since reads dominate heavily, put a cache (e.g., Redis) in front of the data store for the hottest short codes, following an LRU eviction policy — a small fraction of links (recently created/viral ones) account for a disproportionate share of redirect traffic, so even a modest cache hit rate dramatically cuts datastore load and redirect latency.

4. **Redirect service.** Stateless application servers that take an incoming short-code request, check cache → fall back to datastore on miss → populate cache → issue the HTTP redirect. Being stateless lets you scale this tier horizontally behind a load balancer.

5. **Write path.** A smaller, separate set of stateless servers (or the same fleet) handling creation requests: validate/normalize the long URL, mint an ID, write to the datastore (and optionally warm the cache).

**Main trade-off:** 301 (permanent) vs. 302 (temporary) redirect. A 301 lets browsers cache the redirect locally, reducing load on your service for repeat visits to the same link — but it means you lose the ability to track click analytics on subsequent visits (the browser never asks you again) and you can't easily repoint or deactivate a link later. A 302 keeps every redirect flowing through your servers, costing more load but preserving full analytics and the ability to change/disable links after the fact. Most production URL shorteners choose 302 specifically to retain click-tracking and link-management control, accepting the extra server load and relying on the caching layer (component 3) to absorb it instead of browser caching.
