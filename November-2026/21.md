## DSA

### Question: Non-overlapping Intervals (Greedy — Medium)

**Problem Statement**

Given an array of intervals where `intervals[i] = [start_i, end_i]`, return the minimum number of intervals you need to remove so that the rest of the intervals are pairwise non-overlapping. Two intervals `[a, b]` and `[c, d]` are considered overlapping if they share more than just a touching endpoint (i.e. `[1,2]` and `[2,3]` do **not** overlap).

**Input/Output Format**

- Input: a list of intervals, each `[start, end]` with `start < end`.
- Output: a single integer — the minimum number of intervals to remove.

**Examples**

1. Input: `[[1,2],[2,3],[3,4],[1,3]]` → Output: `1` (remove `[1,3]`; the rest — `[1,2],[2,3],[3,4]` — are non-overlapping)
2. Input: `[[1,2],[1,2],[1,2]]` → Output: `2` (keep exactly one of the three identical intervals)
3. Input: `[[1,2],[2,3]]` → Output: `0` (they only touch at `2`, which is allowed)

**Constraints**

- `1 <= intervals.length <= 10^5`
- `intervals[i].length == 2`
- `-5 * 10^4 <= start_i < end_i <= 5 * 10^4`
- Aim for O(n log n) time.

### Step-by-Step Walkthrough

**Reframe the problem.** "Minimum removals to make everything non-overlapping" is the complement of "maximum number of intervals you can keep while staying non-overlapping." If you can find the largest possible non-overlapping subset of size `k`, the answer is `n - k`. This reframing matters because "maximize the number of non-overlapping intervals you keep" is the classic **activity selection** problem, which has a well-known greedy solution.

**Why sorting by end time is the right greedy choice.** Sort all intervals by their `end` value, ascending. Then walk through them left to right, greedily keeping an interval whenever it doesn't overlap the last interval you kept (i.e. its `start >= lastKeptEnd`). The intuition: among all intervals competing for a slot, the one that finishes earliest leaves the most room for everything that comes after it. If you instead kept an interval that ends later, you can never do better in the remaining suffix than if you'd kept the earlier-ending one — any set of non-overlapping intervals that work with the later end also work with the earlier end, but not vice versa. This exchange argument is what makes the greedy choice provably optimal (it's the same argument that underlies classic interval scheduling).

**Algorithm.**
1. Sort intervals by `end` ascending. (Tie-breaking on `start` doesn't matter for correctness here.)
2. Initialize `lastEnd = -infinity` and `kept = 0`.
3. For each interval `[s, e]` in sorted order: if `s >= lastEnd`, it doesn't overlap the last kept interval — keep it: `kept++`, `lastEnd = e`. Otherwise it overlaps, so it must be one of the intervals we remove; skip it (don't update `lastEnd`, since the interval we already kept still ends earlier and remains the tighter bound).
4. Return `n - kept`.

**Trace on Example 1.** Sorted by end: `[1,2] (end 2), [2,3] (end 3), [1,3] (end 3), [3,4] (end 4)` (ties on end 3 — order between `[2,3]` and `[1,3]` doesn't affect the count). Start `lastEnd = -inf`.
- `[1,2]`: `1 >= -inf` → keep, `lastEnd = 2`, `kept = 1`.
- `[2,3]`: `2 >= 2` → keep, `lastEnd = 3`, `kept = 2`.
- `[1,3]`: `1 >= 3`? No → overlaps, skip (remove).
- `[3,4]`: `3 >= 3` → keep, `lastEnd = 4`, `kept = 3`.
`kept = 3`, `n = 4`, answer `= 1`. Matches.

**Complexity.**
- Time: O(n log n), dominated by the sort; the scan afterward is O(n).
- Space: O(1) extra (O(n) if the sort isn't in-place, but no auxiliary data structures are needed beyond the input array).

### C++ Code

```cpp
#include <vector>
#include <algorithm>
using namespace std;

int eraseOverlapIntervals(vector<vector<int>>& intervals) {
    if (intervals.empty()) return 0;

    // Greedy choice: sort by end time so the interval that frees up
    // the earliest "slot" is always considered first.
    sort(intervals.begin(), intervals.end(),
         [](const vector<int>& a, const vector<int>& b) {
             return a[1] < b[1];
         });

    int kept = 1;                       // first interval (smallest end) is always kept
    int lastEnd = intervals[0][1];

    for (size_t i = 1; i < intervals.size(); ++i) {
        int start = intervals[i][0];
        int end = intervals[i][1];

        if (start >= lastEnd) {
            // Doesn't overlap the last interval we kept -- keep this one too.
            ++kept;
            lastEnd = end;
        }
        // else: it overlaps, so it's one of the intervals we must remove.
        // lastEnd stays as-is, since it's already the tighter (earlier) bound.
    }

    return static_cast<int>(intervals.size()) - kept;
}
```

## CS Fundamentals

### 1. OOP (Conceptual/Definition)

What is the difference between method overloading and method overriding? How does each get resolved — at compile time or at runtime — and what specific C++ mechanism makes the runtime case possible?

**Answer:**

**Overloading** means defining multiple methods with the *same name but different parameter lists* (different number, types, or order of parameters) within the same scope. Which one gets called is decided by the compiler by matching the argument list against the available signatures — this is **static (compile-time) binding**. There's no inheritance or virtual dispatch involved at all; it's purely a name-resolution problem solved before the program ever runs.

**Overriding** means a derived class redefining a method that it inherited from a base class, using the *exact same signature*, so that calling it through a base-class reference or pointer invokes the derived class's version instead. This is **dynamic (runtime) binding** — the actual function that runs depends on the real type of the object the pointer points to, not the declared type of the pointer, and that can only be known while the program is executing.

**The mechanism that makes runtime resolution possible in C++ is the virtual function table (vtable) plus the `virtual` keyword.** When a class declares at least one `virtual` method, the compiler gives every instance of that class a hidden pointer (commonly called the vptr) to a per-class vtable — an array of function pointers, one slot per virtual method, pointing at whichever override is appropriate for that concrete class. The vptr is set up in the constructor to point at the correct class's vtable. A call like `basePtr->foo()` compiles to "look up `foo`'s slot in the vtable `basePtr`'s vptr points at, and jump through that pointer" — a level of indirection resolved at runtime, not compile time.

**Why `virtual` is not optional.** If a derived class redefines a base method *without* the base declaring it `virtual`, you get function **hiding**, not overriding: calling the method through a base-class pointer still statically resolves to the base version at compile time, because there's no vtable indirection to consult — the compiler just emits a direct call based on the pointer's declared (static) type. This is a classic C++ bug: code that looks polymorphic silently isn't, because someone forgot `virtual` on the base class method.

### 2. System Design Basics (Comparison)

You need to rate-limit a public API endpoint to protect it from abuse. Compare the **token bucket** and **sliding window log** algorithms for rate limiting. What does each actually guarantee, and which would you pick for an API where legitimate clients send traffic in short bursts rather than a steady trickle?

**Answer:**

**Token bucket.** Each client has a bucket with a maximum capacity of `C` tokens, which refills at a steady rate of `r` tokens per second (up to the cap). Every incoming request consumes one token if available; if the bucket is empty, the request is rejected or queued. Over any long window, the client is capped at roughly `r` requests/second on average — but because tokens can accumulate up to `C` while the client is idle, it can legitimately spend a *burst* of up to `C` requests all at once, then resume at the steady rate. State per client is tiny: just a token count and a last-refill timestamp, so it's O(1) memory and cheap to check.

**Sliding window log.** For each client, store the timestamp of every request made within the trailing window (e.g. the last 60 seconds). On each new request, discard timestamps older than the window, then check whether the remaining count is below the limit. This gives an *exact* guarantee: no more than `N` requests in *any* rolling window of that length, with no burst exception whatsoever. The cost is that memory and per-request work scale with the limit itself (you're storing up to `N` timestamps per client), which gets expensive at scale — commonly approximated instead with a "sliding window counter" that splits time into two fixed buckets and interpolates, trading a little precision for O(1) memory.

**Which to pick:** for an API whose legitimate clients are bursty (e.g. a page load that fires a dozen requests at once, then goes quiet), **token bucket** is the better fit — its whole design point is to tolerate a bounded burst while still enforcing a long-run average, and it's far cheaper to implement at scale. A sliding window log is the right tool when the requirement is a hard, auditable cap with zero tolerance for burst overshoot (e.g. a strict per-second quota tied to a billing contract), since token bucket would let a client exceed that instantaneous rate as long as it had saved-up tokens.

### 3. Computer Architecture (Conceptual/Definition)

What is instruction pipelining in a CPU, and what are the three classic categories of hazards that can stall a pipeline? Give one concrete example of a hazard from any category.

**Answer:**

**Instruction pipelining** overlaps the execution of multiple instructions by splitting instruction processing into stages — typically Fetch, Decode, Execute, Memory access, and Writeback — and running different instructions through different stages *in the same clock cycle*, like cars moving through stations on an assembly line. A single instruction still takes the same number of cycles to fully complete (its latency is unchanged), but because up to five instructions can be mid-flight at once in a 5-stage pipeline, the CPU can retire roughly one instruction per cycle in steady state instead of one instruction per five cycles — a large throughput win, which is the entire point of pipelining.

That overlap is also exactly what creates **hazards**: situations where the next instruction can't safely proceed through the pipeline on schedule.

**1. Structural hazards.** Two instructions in the pipeline simultaneously need the *same piece of hardware* in the same cycle. Classic example: a single unified memory port needed both to fetch a new instruction and to do a data load/store for an instruction already further along the pipeline. Fix: duplicate the resource (separate instruction and data caches/ports) or stall one of the instructions.

**2. Data hazards.** An instruction needs a value that an earlier, still-in-flight instruction hasn't produced yet — most commonly **Read-After-Write (RAW)**. Example: `ADD R1, R2, R3` immediately followed by `SUB R4, R1, R5`. By the time `SUB` reaches its Decode/Execute stage and needs `R1`, `ADD` may not have reached Writeback yet, so `R1` isn't updated in the register file. Fixed either by **stalling** (inserting bubbles until the value is ready) or, much more commonly, **forwarding/bypassing** — routing the freshly computed value directly from `ADD`'s execute stage into `SUB`'s execute stage without waiting for the register file write.

**3. Control hazards.** Caused by branch instructions: the pipeline doesn't know which instruction to fetch next until the branch's condition and target are resolved, which may not happen until several stages in. Fetching blindly and guessing wrong means every instruction fetched behind the branch must be discarded (a pipeline "flush" or "bubble"). Mitigated with **branch prediction** (guess taken/not-taken based on history and speculatively execute down that path) combined with a **misprediction recovery** mechanism that flushes the wrongly-fetched instructions when the guess turns out wrong.
