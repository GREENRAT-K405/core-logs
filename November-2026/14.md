### Question: Shortest Path Visiting All Nodes (Graphs — Hard)

You are given an **undirected, connected** graph of `n` nodes labeled `0` to `n - 1`, represented as an adjacency list `graph`, where `graph[i]` is a list of all the nodes adjacent to node `i`.

Return the length (number of edges) of the **shortest path** that visits **every node at least once**. You may start at any node, end at any node, and revisit nodes and edges as many times as needed.

**Input format:** `graph`, a list of `n` lists of integers (adjacency list).
**Output format:** a single integer, the minimum number of edges in a walk that touches every node.

**Example 1:**
```
Input: graph = [[1,2,3],[0],[0],[0]]
Output: 4
Explanation: One shortest walk is 1 -> 0 -> 2 -> 0 -> 3 (4 edges), touching nodes {0,1,2,3}.
```

**Example 2:**
```
Input: graph = [[1],[0,2,4],[1,3,4],[2],[1,2]]
Output: 4
Explanation: One shortest walk is 0 -> 1 -> 4 -> 2 -> 3 (4 edges).
```

**Example 3:**
```
Input: graph = [[1,2,3]]
Output: 0
Explanation: n = 1, there is nothing else to visit, so the empty walk already visits every node.
```

**Constraints:**
- `n == graph.length`
- `1 <= n <= 12`
- `0 <= graph[i].length < n`
- `graph[i]` does not contain `i`
- if `graph[a]` contains `b`, then `graph[b]` contains `a` (undirected)
- the graph is guaranteed to be connected

### Step-by-Step Walkthrough

**Why brute force over permutations doesn't scale:** naively this looks like a Traveling-Salesman-style problem — try every order of visiting nodes and take the shortest. With `n <= 12` that's a strong hint the intended solution is **bitmask dynamic programming / BFS over state space**, since `2^12 = 4096` is tiny but `12!` is not.

**Key idea — state = (current node, set of nodes visited so far).** Since `n <= 12`, the set of visited nodes fits in a bitmask of up to 12 bits. A state is `(node, mask)` where bit `i` of `mask` is 1 if node `i` has been visited on the walk so far. The walk is complete as soon as some state has `mask == fullMask` (all bits set) — we don't care *which* node we end on, only that every node has been touched.

**Why BFS instead of Dijkstra/DP-over-masks:** every edge has weight 1 (an unweighted graph), and we want the minimum number of edges to reach *any* state with the full mask. BFS naturally explores states in order of increasing distance, so the first time we reach a full-mask state, that distance is guaranteed minimal — no need for a priority queue.

**Why start BFS from every node simultaneously:** the walk is allowed to start anywhere, so instead of running BFS once per starting node (n runs) we push all `n` single-node states `(i, 1<<i)` with distance 0 into one queue up front. This is equivalent to n independent BFS runs merged into one, and it's correct because all of them start at distance 0 — the first time any of them reaches a full mask, that's the global minimum over all starting points too.

**Transition:** from state `(node, mask)` at distance `d`, for every neighbor `next` of `node`, move to state `(next, mask | (1 << next))` at distance `d + 1`, provided that state hasn't been visited before (track visited states in a `dist` table to avoid re-expanding, which also prevents infinite loops from revisiting edges).

**Termination:** the moment we pop a state whose mask equals `fullMask = (1 << n) - 1`, its stored distance is the answer. Since the graph is connected and BFS explores in non-decreasing distance order, this is guaranteed to happen.

**Complexity analysis:**
- **States:** there are `n` nodes × `2^n` possible masks, so at most `n * 2^n` states.
- **Time:** each state is expanded once, and expanding a state costs `O(n)` (degree is at most `n - 1`), giving `O(n^2 * 2^n)` overall. With `n <= 12` this is at most `~12^2 * 4096 ≈ 590k` operations — trivial.
- **Space:** the `dist` table holding one entry per `(node, mask)` pair takes `O(n * 2^n)`.

### C++ Code

```cpp
#include <bits/stdc++.h>
using namespace std;

class Solution {
public:
    int shortestPathLength(vector<vector<int>>& graph) {
        int n = graph.size();
        if (n == 1) return 0; // single node: already "visits every node"

        int fullMask = (1 << n) - 1;

        // dist[node][mask] = fewest edges to reach this (node, visited-set) state, -1 if unseen
        vector<vector<int>> dist(n, vector<int>(1 << n, -1));
        queue<pair<int, int>> q; // (node, mask)

        // Seed BFS from every node at once: the walk may start anywhere.
        for (int i = 0; i < n; ++i) {
            int startMask = 1 << i;
            dist[i][startMask] = 0;
            q.push({i, startMask});
        }

        while (!q.empty()) {
            auto [node, mask] = q.front();
            q.pop();
            int d = dist[node][mask];

            if (mask == fullMask) {
                return d; // first time we complete the visited-set: minimal by BFS order
            }

            for (int next : graph[node]) {
                int nextMask = mask | (1 << next);
                if (dist[next][nextMask] == -1) {
                    dist[next][nextMask] = d + 1;
                    q.push({next, nextMask});
                }
            }
        }

        return -1; // unreachable in practice since the graph is guaranteed connected
    }
};
```

### 1. Operating Systems (Conceptual)

What is a race condition? Describe the conditions under which one can occur, and name at least two mechanisms an operating system provides to prevent one.

**Answer:**

A **race condition** occurs when two or more threads or processes access shared data concurrently, and the final outcome of that access depends on the unpredictable timing (interleaving) of their execution, rather than on the logic of the program. If the operations happen to interleave one way, the result is correct; interleaved another way, the result is wrong — and because scheduling is non-deterministic, the bug appears only intermittently, which is what makes race conditions notoriously hard to reproduce and debug.

A race condition requires three ingredients, all of which must be true at once:
1. **Shared, mutable state** — two or more execution contexts can read and write the same memory or resource (a shared counter, a linked list, a file).
2. **A critical section** — a sequence of operations that must execute as an indivisible unit to preserve correctness (e.g., read a value, increment it, write it back).
3. **No mutual exclusion** — nothing stops two threads from being inside that critical section at the same time.

The classic example: two threads both execute `counter++` on a shared `counter`. That single line is actually three machine steps — load, increment, store. If Thread A loads the value, then Thread B loads the same (stale) value before A stores its result, one increment is silently lost.

The OS and language runtimes offer several mechanisms to eliminate the data race by enforcing mutual exclusion or avoiding shared mutable state altogether:

- **Mutexes (locks):** only one thread may hold the lock at a time; a thread must acquire the mutex before entering the critical section and release it after. This serializes access, at the cost of threads blocking while they wait.
- **Semaphores:** a generalized lock with a counter, useful for limiting concurrent access to `N` resources (e.g., a connection pool) rather than just 1.
- **Atomic instructions (e.g., compare-and-swap):** hardware-supported operations that perform read-modify-write as a single, uninterruptible step, avoiding the overhead of a full lock for simple operations like incrementing a counter.
- **Monitors / condition variables:** higher-level constructs (built on mutexes) that let a thread wait for a condition to become true and be woken up safely when it does, without busy-waiting.
- **Avoiding shared state entirely:** message passing between isolated processes/threads (as in the actor model, or Go's channels) sidesteps the problem by never letting two execution contexts touch the same memory directly.

Why it matters in practice: race conditions are a top cause of flaky tests, data corruption in databases, and some serious security vulnerabilities (TOCTOU — time-of-check to time-of-use bugs). Recognizing the three ingredients above is the fastest way to spot a potential race while reviewing concurrent code, even before a bug ever manifests.

### 2. OOP (Comparison)

Compare composition and inheritance as mechanisms for code reuse in object-oriented design. What are the trade-offs, and when would you prefer one over the other?

**Answer:**

Both are ways to build new behavior out of existing code, but they differ fundamentally in the kind of relationship they create between classes.

**Inheritance** expresses an **"is-a"** relationship: a subclass extends a base class, inheriting its fields and methods and optionally overriding them. The relationship is fixed at compile time and is part of the class's static type.

**Composition** expresses a **"has-a"** relationship: a class holds a reference to an instance of another class and delegates work to it, rather than inheriting from it. The relationship can be assembled and even swapped at runtime.

| Aspect | Inheritance | Composition |
|---|---|---|
| Relationship | "is-a" | "has-a" |
| Coupling | Tight — subclass depends on base class's internal implementation details, not just its interface (the "fragile base class" problem: a change to the base class can silently break every subclass) | Loose — the containing class depends only on the composed object's public interface |
| Flexibility | Fixed at compile time; a class can't change its parent at runtime | Can be assembled or swapped at runtime (e.g., inject a different strategy object) |
| Reuse granularity | Reuses an entire class hierarchy, including things you may not want | Reuses exactly the behavior you choose to delegate to |
| Multiple behaviors | Most OOP languages only allow single inheritance of implementation, forcing awkward hierarchies when an object needs two unrelated sets of behavior | Trivial — just hold multiple composed objects, each contributing one capability |
| Encapsulation | Can leak: subclasses often need to know base-class internals to override correctly | Preserved: the outer class only sees what the inner object's interface exposes |

**When inheritance is the better fit:** when there is a genuine, stable taxonomic relationship and you want polymorphism — e.g., `Circle` and `Square` both truly *are* `Shape`s, and calling code wants to treat them uniformly via a `Shape` reference while each overrides `area()` differently. It shines when the hierarchy is shallow and the "is-a" claim will remain true as the code evolves.

**When composition is the better fit:** when you want to reuse behavior without committing to a rigid taxonomy, or when behavior needs to vary independently and be swapped at runtime — e.g., a `Car` *has a* `Engine`, and you'd like to swap in an `ElectricEngine` without rewriting `Car`. This is the idea behind the well-known design principle **"favor composition over inheritance"**: composition keeps classes smaller, more testable in isolation (you can inject a mock dependency), and avoids deep, brittle hierarchies that are hard to refactor later. Many design patterns (Strategy, Decorator, Dependency Injection) are really composition used deliberately to get inheritance-like flexibility without inheritance's tight coupling.

In short: reach for inheritance only when the "is-a" relationship is true and stable and polymorphism is the actual goal; default to composition for everything else, since it's generally easier to change later.

### 3. System Design Basics (Scenario)

You're asked to design a URL-shortening service (like bit.ly) that must support 100 million new short links created per day and an even higher read (redirect) volume. Walk through how you would generate the short codes, store the mapping, and keep redirects fast at that scale.

**Answer:**

**1. Generating the short code.** The core requirement is a short, unique identifier for each long URL. Two common approaches:

- **Hashing the long URL** (e.g., take the first 6-8 characters of a base62-encoded MD5/SHA hash) is simple but collision-prone at 100M/day scale, so it needs a collision-check-and-retry loop against the datastore — extra read-before-write latency on every creation.
- **A counter-based scheme** is more robust: maintain a globally unique, monotonically increasing ID (e.g., from a distributed ID generator such as a Snowflake-style service, or pre-allocated ID ranges handed out to each application server), then base62-encode that ID into a short string (`[0-9a-zA-Z]`). Base62 encoding of a 64-bit integer comfortably fits in 6-7 characters and is collision-free by construction — no need to check for existing codes before writing.

Given the write volume, the counter-based approach is preferable: it avoids the read-before-write collision check entirely, which matters a lot at 100M writes/day (~1,160 writes/sec average, with much higher peaks). Handing out ID ranges per server (e.g., server A gets IDs 1-1,000,000, server B gets 1,000,001-2,000,000) lets each server generate IDs locally without coordinating with others on every single write.

**2. Storing the mapping.** The access pattern is a simple key-value lookup: `short_code -> long_url` (plus maybe metadata like creation time, expiry, click count). This is a textbook fit for a **key-value store or a sharded relational/NoSQL table** keyed by `short_code`, rather than anything requiring joins. Shard by a hash of the short code (or by the ID ranges used for generation) to spread both the 100M daily writes and the much larger read volume across many nodes horizontally.

**3. Making redirects fast.** Reads (someone clicking a short link) vastly outnumber writes in a URL shortener, and a redirect is latency-sensitive (users notice even 100ms of delay). The standard approach is a **read-through cache** (e.g., Redis/Memcached) in front of the datastore, keyed by `short_code`:
- On a redirect request, check the cache first; on a hit, issue an HTTP 301/302 immediately.
- On a miss, read from the backing store, populate the cache, then redirect.
- Since short URLs are immutable once created (the mapping never changes), cache entries can be cached aggressively with a long TTL — there's no invalidation problem to worry about, which is the easy case for caching.
- A small but real design choice: 301 (permanent) redirects let browsers cache the redirect themselves, reducing load on the service even further, but make it impossible to update analytics or change the destination later — many production systems deliberately use 302 to keep click analytics and flexibility, trading a bit of extra traffic for that control.

**4. Scaling the write path.** 100M/day is ~1,160/sec average but real traffic is bursty, so the write path (ID generation + datastore insert) should sit behind a horizontally scaled fleet of stateless application servers, with the ID-generation step designed (as above) to need no cross-server coordination per request — that's what keeps the write path horizontally scalable instead of bottlenecked on a single counter.

**Why this shape works:** the workload is read-heavy, latency-sensitive, and has a simple key-value access pattern with no relational joins — so the design leans on (a) a collision-free ID scheme to make writes cheap, (b) horizontal sharding to make both reads and writes scale linearly with nodes, and (c) an aggressive cache to absorb the read-heavy, immutable-data workload, which is exactly the shape of problem caching solves best.
