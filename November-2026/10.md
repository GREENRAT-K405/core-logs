### Question: Minimum XOR Sum of Two Arrays (Bit Manipulation — Hard)

**Problem Statement**

You are given two integer arrays `nums1` and `nums2` of the same length `n`. The **XOR sum** of the two arrays is defined as:

```
(nums1[0] XOR nums2[0]) + (nums1[1] XOR nums2[1]) + ... + (nums1[n-1] XOR nums2[n-1])
```

You are allowed to rearrange the elements of `nums2` in **any order** (the order of `nums1` stays fixed). Return the **minimum possible XOR sum** after optimally rearranging `nums2`.

**Input/Output Format**

- Input: two integer arrays `nums1` and `nums2`, both of length `n`.
- Output: an integer, the minimum achievable XOR sum.

**Examples**

1. Input: `nums1 = [1,2]`, `nums2 = [2,3]` → Output: `2`
   Rearranging `nums2` to `[3,2]` gives `(1 XOR 3) + (2 XOR 2) = 2 + 0 = 2`, which is optimal.
2. Input: `nums1 = [1,0,3]`, `nums2 = [5,3,4]` → Output: `8`
   Rearranging `nums2` to `[5,4,3]` gives `(1 XOR 5) + (0 XOR 4) + (3 XOR 3) = 4 + 4 + 0 = 8`.
3. Input: `nums1 = [0]`, `nums2 = [0]` → Output: `0`
   Only one possible pairing, and `0 XOR 0 = 0`.

**Constraints**

- `n == nums1.length == nums2.length`
- `1 <= n <= 14`
- `0 <= nums1[i], nums2[i] <= 10^7`

### Step-by-Step Walkthrough

**Why brute force is tempting but wrong.** The direct idea — try every permutation of `nums2`, compute the XOR sum for each, and keep the minimum — is correct, but it costs `O(n! * n)` time. Even for `n = 14`, `14!` is about 87 billion; nowhere near fast enough. The constraint `n <= 14` is a strong hint: it's small enough for something exponential in `n` (like `2^n`), but too large for anything factorial.

**Reframing as an assignment problem.** `nums1`'s order never changes, so this is really: *which element of `nums2` gets assigned to each position of `nums1`, so that the total XOR cost is minimized?* This is a classic bipartite assignment problem — match each index of `nums1` to a distinct index of `nums2` to minimize total cost. With `n <= 14`, a bitmask over "which elements of `nums2` have been used so far" fits comfortably in an `int` (`2^14 = 16384` states), which is the signal to reach for **bitmask dynamic programming**.

**Defining the DP state.** Let `dp[mask]` = the minimum XOR sum achievable by assigning the elements of `nums2` whose indices are set in `mask` to the *first* `popcount(mask)` elements of `nums1` (i.e., `nums1[0..popcount(mask)-1]`), in some optimal one-to-one pairing.

- Why this works: the number of set bits in `mask` always tells us exactly how many positions of `nums1` have been filled so far (positions `0` to `popcount(mask)-1`), since we fill `nums1` left to right. So `mask` alone — without separately tracking *which* `nums1` positions are done — fully determines the DP's progress.

**Transition.** To reach `dp[mask]`, the last element of `nums1` filled was `nums1[k-1]`, where `k = popcount(mask)`. That slot was paired with *some* `nums2[j]` where bit `j` is set in `mask`. Removing that bit gives the state before this pairing was made:

```
dp[mask] = min over all j in mask of:
    dp[mask without bit j] + (nums1[k-1] XOR nums2[j])
```

**Base case and answer.** `dp[0] = 0` (nothing assigned yet, zero cost). The answer is `dp[(1 << n) - 1]` — every bit of `nums2` used, meaning all `n` positions of `nums1` have been paired.

**Why it's correct.** Every full assignment (permutation of `nums2`) corresponds to exactly one path from `mask = 0` to `mask = (1<<n)-1` through this DP, built by adding one bit at a time, and the DP always extends the cheapest way to reach each intermediate state. Since `nums1`'s fill order is fixed (position `k-1` is always the next one filled when `popcount(mask) = k`), there's no ambiguity about which `nums1` element a given mask transition pairs against — so the recurrence explores every distinct assignment exactly once, taking the minimum over all of them.

**Complexity.**
- Time: `O(n * 2^n)` — for each of the `2^n` masks, we loop over at most `n` set bits to consider removing.
- Space: `O(2^n)` — one DP entry per subset of `nums2`'s indices.

### C++ Code

```cpp
#include <vector>
#include <climits>
using namespace std;

int minimumXORSum(vector<int>& nums1, vector<int>& nums2) {
    int n = (int)nums1.size();
    int fullMask = 1 << n;

    // dp[mask] = minimum XOR sum pairing nums1[0..popcount(mask)-1]
    // with the nums2 elements whose indices are set in mask.
    vector<int> dp(fullMask, INT_MAX);
    dp[0] = 0;

    for (int mask = 1; mask < fullMask; mask++) {
        int k = __builtin_popcount(mask); // nums1 positions filled so far
        int nextNums1 = nums1[k - 1];     // the nums1 slot this transition fills

        for (int j = 0; j < n; j++) {
            if (!(mask & (1 << j))) continue; // nums2[j] must be used in this mask

            int prevMask = mask ^ (1 << j);
            if (dp[prevMask] == INT_MAX) continue; // unreachable state

            int cost = dp[prevMask] + (nextNums1 ^ nums2[j]);
            if (cost < dp[mask]) {
                dp[mask] = cost;
            }
        }
    }

    return dp[fullMask - 1];
}
```

## CS Fundamentals

### 1. Computer Architecture (Conceptual/Definition)

Why do CPUs use a multi-level cache hierarchy (L1, L2, L3) instead of just one large, fast cache? What is the "principle of locality" this design relies on, and what happens on a cache miss at each level?

**Answer:**

A cache's speed and its size trade off directly against each other: the circuitry needed to search a cache and return a result in roughly one CPU cycle only scales to a few tens of kilobytes before the physical distance signals travel, and the complexity of the lookup logic, make it too slow. A single cache big enough to hold a program's whole working set would be far too slow to access every cycle; a single cache fast enough to keep up with the CPU would be far too small to hold much of anything. Multi-level caching resolves this by using several caches of increasing size and decreasing speed, each catching what the previous one missed.

**The hierarchy, typically:**

| Level | Size | Latency | Shared? |
| --- | --- | --- | --- |
| L1 | 32-64 KB (often split: instruction + data) | ~4 cycles | Per core |
| L2 | 256 KB-1 MB | ~12 cycles | Per core (usually) |
| L3 | A few MB-tens of MB | ~40 cycles | Shared across cores |
| DRAM (main memory) | GBs | ~200+ cycles | Shared, off-chip |

**Why this works at all — the principle of locality.** Caching is a bet that memory accesses aren't random, and that bet almost always pays off because of two patterns real programs exhibit:

- **Temporal locality**: if a memory address was accessed recently, it's likely to be accessed again soon (e.g., a loop counter, a frequently called function's instructions).
- **Spatial locality**: if an address was accessed, nearby addresses are likely to be accessed soon too (e.g., iterating over an array, or just the next instruction in sequence). This is why caches fetch data in fixed-size **cache lines** (commonly 64 bytes) rather than single bytes — pulling in the whole line front-loads the neighbors you're likely to need next.

**What happens on a miss.** A memory access first checks L1. If the data isn't there (an L1 miss), the request falls through to L2; if it's not there either, to L3; and only if it misses all three does the CPU pay the full cost of a round trip to DRAM. Each level that must be checked adds latency, which is exactly why the access pattern matters so much for performance: a program with good locality satisfies the overwhelming majority of its accesses from L1 and L2, while a program that jumps around unpredictably in memory (a classic symptom: traversing a huge linked list, or iterating a 2D array in the wrong stride order) forces frequent trips all the way to DRAM, which can be 50-100x slower than an L1 hit.

**The practical takeaway:** cache hierarchies make the "average" memory access fast by betting that most accesses aren't to brand-new, far-away addresses. Writing cache-friendly code (iterating arrays in memory order, keeping hot data structures small and contiguous) isn't a micro-optimization footnote — it's directly exploiting the hardware assumption the entire hierarchy is built on.

### 2. OOP (Comparison)

What does "favor composition over inheritance" mean? Give an example of a design where inheritance seems natural at first but causes problems, and show how composition fixes it.

**Answer:**

Both inheritance and composition let one class reuse another class's behavior, but they create a very different kind of relationship between them.

**Inheritance** models an "is-a" relationship: a subclass *is a* specialized version of its superclass, and it gets the superclass's implementation automatically, bound at compile time. **Composition** models a "has-a" relationship: a class holds a reference to another object and delegates to it, with the relationship assembled (and swappable) at runtime.

**Where inheritance seems natural but breaks down — the classic example:**

Suppose you model birds with a `Bird` base class that has a `fly()` method, and `Sparrow` and `Eagle` subclass it, inheriting `fly()` for free. This feels right — most birds fly. Then a `Penguin` needs to be a `Bird` too (it has feathers, lays eggs, etc.), but penguins can't fly. Now you're stuck:

- Override `fly()` in `Penguin` to throw an exception or do nothing — but this violates the **Liskov Substitution Principle**: any code that expects a `Bird` and calls `fly()` can now crash or silently misbehave when handed a `Penguin`, even though a `Penguin` is supposedly a valid `Bird`.
- Restructure the hierarchy (e.g., add a `FlightlessBird` branch) — this works until the *next* exception shows up (an ostrich that also can't swim like a penguin, a bird that flies but doesn't build nests the way the base class assumes), and the hierarchy keeps fracturing to accommodate each new combination of traits. This is the well-known "fragile base class" / combinatorial explosion problem: behavior that doesn't vary cleanly along a single `is-a` axis doesn't fit a single inheritance tree.

**How composition fixes it.** Instead of baking `fly()` into the class hierarchy, give `Bird` a `flightBehavior` object (e.g., implementing a `FlightBehavior` interface), and inject a concrete strategy per bird:

```cpp
struct FlightBehavior { virtual void fly() = 0; virtual ~FlightBehavior() = default; };
struct CanFly : FlightBehavior { void fly() override { /* actually fly */ } };
struct CannotFly : FlightBehavior { void fly() override { /* no-op, or waddle */ } };

class Bird {
public:
    Bird(FlightBehavior* behavior) : flightBehavior(behavior) {}
    void performFly() { flightBehavior->fly(); }
private:
    FlightBehavior* flightBehavior; // composed, not inherited
};
```

Now a `Penguin` is built with `CannotFly`, a `Sparrow` with `CanFly`, and neither has to misrepresent what it can do or trigger a surprising failure. New combinations of traits (swimming, nesting, flying) each get their own small interface and can be mixed per bird without rewriting a class hierarchy.

**The actual guidance, precisely stated.** "Favor composition over inheritance" doesn't mean inheritance is wrong — it's genuinely the right tool when the relationship is a true, stable "is-a" that won't need to vary independently across multiple axes (a `Car` *is a* `Vehicle` is usually safe). The guidance is to default to composition when you're reusing code for its *behavior*, not because of a genuine taxonomic relationship — composition keeps classes more loosely coupled, lets behavior change at runtime, and avoids hierarchies that fracture as new real-world exceptions show up.

### 3. System Design Basics (Scenario/Applied)

Your single web server is getting overwhelmed as traffic grows, so you decide to run multiple instances behind a load balancer. What are the main load-balancing algorithms you could choose between, and what's the specific problem with naively load-balancing a service where users log in and build up session state on whichever server they first hit?

**Answer:**

**Why one server stops being enough.** A single server has a hard ceiling on CPU, memory, and open connections. Once request volume approaches that ceiling, latency climbs and then requests start failing outright. The standard fix is **horizontal scaling**: run several identical instances of the service and put a **load balancer** in front of them to distribute incoming requests.

**Common load-balancing algorithms:**

- **Round robin**: requests are handed to servers in rotating order (server 1, 2, 3, 1, 2, 3, ...). Simple, but assumes every request and every server is roughly equal cost, which isn't always true.
- **Least connections**: send the next request to whichever server currently has the fewest active connections. Adapts better than round robin when requests have very different costs or servers have different capacities.
- **Weighted round robin / weighted least connections**: like the above, but servers are given weights (e.g., a bigger instance gets 2x the traffic share of a smaller one), useful in a fleet of mixed-size machines.
- **IP hash / consistent hashing**: route based on a hash of the client's IP (or another key), so the same client consistently lands on the same server. This is the mechanism most relevant to the session problem below.
- **Least response time**: route to the server currently responding fastest, factoring in both active connections and measured latency — more adaptive, but more expensive to compute.

**The specific problem: sticky sessions.** If a user logs in and the server stores their session (who they are, their shopping cart, etc.) only in that server's local memory, then on their *next* request the load balancer might route them to a *different* server — one that has never heard of their session. From the user's point of view, they're randomly logged out or lose their cart, because each server only knows about the sessions that happened to land on it.

**Two ways to fix it, with different trade-offs:**

1. **Sticky sessions (session affinity).** Configure the load balancer (often via IP hash, or a cookie it sets) to always route a given client to the *same* server for the duration of their session. This is simple and requires no application changes, but it has real downsides: it undermines even load distribution (a server that happens to be "stuck" with many active, chatty users stays hot even if others are idle), and if that specific server goes down, every user stuck to it loses their session entirely.
2. **Externalize the session state.** Instead of storing sessions in each server's local memory, store them in a shared, fast data store that every server instance can reach — commonly Redis or Memcached, or encode the session as a signed token (e.g., a JWT) the client holds and presents on every request, so the server doesn't need to remember anything about it at all. This makes the application **stateless** from the load balancer's point of view: any request can go to any server, which restores free load-balancer choice (plain round robin or least connections works fine again) and means a server crashing doesn't take anyone's session down with it.

**Why option 2 is generally preferred at scale.** Sticky sessions are a workaround that keeps working only as long as you don't need to freely redistribute load or tolerate server failures gracefully. Externalizing session state is more work up front (another moving part — the shared store — to run and keep available), but it's what lets you scale horizontally, roll out deployments, and handle server failures without users noticing, which is usually worth the added complexity for anything beyond a small, low-stakes service.
