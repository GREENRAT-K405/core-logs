## DSA

### Question: All Nodes Distance K in Binary Tree (Trees — Medium)

Given the root of a binary tree with **unique** node values, the value of a `target` node, and an integer `K`, return the values of all nodes that are at distance exactly `K` from the target node. Distance is measured as the number of edges on the path between two nodes — this includes paths that go *up* through ancestors and back *down* into another subtree, not just straight down from the target.

**Input format:** a binary tree (root pointer), an integer `targetVal` (guaranteed to exist in the tree), an integer `K`.
**Output format:** a list of integers (any order) — the values of all nodes at distance `K` from the target.

**Example 1:**
```
Tree:
        3
       / \
      5   1
     / \ / \
    6  2 0  8
      / \
     7   4

target = 5, K = 2
Output: [7, 4, 1]
```
Explanation: from node `5`, node `1` is reached via `5 -> 3 -> 1` (2 edges). Nodes `7` and `4` are reached via `5 -> 2 -> 7` and `5 -> 2 -> 4` (2 edges each).

**Example 2:**
```
target = 3, K = 1
Output: [5, 1]
```
Explanation: the direct children of the root are at distance 1.

**Example 3:**
```
target = 6, K = 0
Output: [6]
```
Explanation: distance 0 from a node is the node itself.

**Constraints:**
- The number of nodes is in the range `[1, 500]`.
- All node values are unique.
- `0 <= K <= 1000`.
- `target` is guaranteed to be the value of a node in the tree.

### Step-by-Step Walkthrough

A plain binary tree only gives you `left`/`right` pointers, so from the target node alone you can only walk *downward*. But the required distance-K set can include nodes reached by going *up* to an ancestor and then down a different branch (as with node `1` in Example 1). The clean way to handle "distance in any direction" is to stop thinking of the tree as a directed structure and instead treat it as an **undirected graph**, then run a standard multi-source-style BFS outward from the target.

**Step 1 — Build a parent map.**
Do one DFS/BFS over the whole tree starting at `root`, and for every node record a pointer to its parent (`parent[node] = node's parent`, with the root mapping to `nullptr`). While doing this traversal, also keep a pointer to the actual target node object (don't just remember its value — you need the node itself to start the BFS).

This turns every node's local neighborhood into three potential edges: `left child`, `right child`, and `parent`. That's exactly the adjacency list of the tree viewed as an undirected graph.

**Step 2 — BFS outward from the target.**
Starting from the target node, do a standard level-order BFS using those three neighbor pointers (`left`, `right`, `parent`), marking nodes visited so you don't walk back the way you came. After expanding `dist` levels, the queue holds exactly the nodes at distance `dist` from the target. Expand level by level; when the level counter reaches `K`, drain the current queue — that is your answer. If the queue empties before reaching `K`, no nodes exist at that distance, so the answer is an empty list.

**Why this works:** distance in a tree is the same whether you think of the edges as "child pointers" or "undirected links" — a tree has a unique simple path between any two nodes, and that path length is exactly the undirected-graph shortest-path distance. BFS is the standard way to compute shortest-path distances layer by layer from a source, so running it from `target` over the parent-augmented adjacency naturally produces "all nodes at distance K" as the Kth BFS frontier.

**Complexity:**
- Building the parent map: `O(N)` time, one pass over all nodes.
- BFS: in the worst case visits every node once, `O(N)` time.
- Space: `O(N)` for the parent map, visited set, and queue.
- Overall: **O(N) time, O(N) space**, where `N` is the number of nodes in the tree.

### C++ Code

```cpp
#include <bits/stdc++.h>
using namespace std;

struct TreeNode {
    int val;
    TreeNode *left, *right;
    TreeNode(int x) : val(x), left(nullptr), right(nullptr) {}
};

class Solution {
public:
    vector<int> distanceK(TreeNode* root, int targetVal, int K) {
        // Step 1: DFS once to record each node's parent, and to locate the
        // actual target node pointer (not just its value).
        unordered_map<int, TreeNode*> parent;
        TreeNode* targetNode = nullptr;
        buildParentMap(root, nullptr, targetVal, parent, targetNode);

        vector<int> result;
        if (!targetNode) return result; // target value not found (shouldn't happen per constraints)

        // Step 2: BFS outward from target, treating left/right/parent as
        // undirected edges, expanding one full level ("distance") at a time.
        unordered_set<int> visited;
        queue<TreeNode*> q;
        q.push(targetNode);
        visited.insert(targetNode->val);

        int dist = 0;
        while (!q.empty()) {
            int levelSize = q.size();

            if (dist == K) {
                // Everything currently queued is exactly K edges from target.
                for (int i = 0; i < levelSize; ++i) {
                    result.push_back(q.front()->val);
                    q.pop();
                }
                return result;
            }

            // Expand this level into the next one.
            for (int i = 0; i < levelSize; ++i) {
                TreeNode* node = q.front();
                q.pop();

                TreeNode* neighbors[3] = {
                    node->left,
                    node->right,
                    parent.count(node->val) ? parent[node->val] : nullptr
                };

                for (TreeNode* nb : neighbors) {
                    if (nb != nullptr && visited.find(nb->val) == visited.end()) {
                        visited.insert(nb->val);
                        q.push(nb);
                    }
                }
            }
            ++dist;
        }

        // Queue emptied before reaching level K: no node is that far away.
        return result;
    }

private:
    void buildParentMap(TreeNode* node, TreeNode* par, int targetVal,
                         unordered_map<int, TreeNode*>& parent, TreeNode*& targetNode) {
        if (!node) return;
        parent[node->val] = par;
        if (node->val == targetVal) targetNode = node;
        buildParentMap(node->left, node, targetVal, parent, targetNode);
        buildParentMap(node->right, node, targetVal, parent, targetNode);
    }
};
```

### 1. Operating Systems (Conceptual)

What is a race condition, and what are two concrete mechanisms (at the programming or OS level) that prevent one from occurring?

**Answer:**

A race condition occurs when two or more threads or processes access shared, mutable data concurrently, and the final outcome of the program depends on the unpredictable timing/interleaving of their execution rather than on well-defined logic. The classic example is two threads both executing `counter++` on a shared variable: each increment actually compiles down to "read counter, add 1, write counter back." If thread A reads `counter = 5`, then thread B reads `counter = 5` before A writes back, both will write `6` — one increment is silently lost, even though two increments happened.

The root cause is that the increment is not **atomic** — it's a sequence of steps that can be interleaved with another thread's steps on the *same* shared state. Any section of code that reads-then-writes shared state like this is called a **critical section**, and correctness requires enforcing **mutual exclusion**: at most one thread may execute the critical section at a time.

Two concrete mechanisms that prevent this:

1. **Mutexes/locks.** A thread must acquire a lock before entering the critical section and release it after. The OS or runtime guarantees that only one thread can hold the lock at a time, so the read-modify-write sequence completes atomically with respect to other threads. (Semaphores generalize this to allow up to N concurrent holders, useful for resource pools rather than strict exclusion.)
2. **Atomic hardware instructions.** Modern CPUs expose instructions like compare-and-swap (CAS) or atomic fetch-and-add that the hardware guarantees execute as a single, indivisible step even under concurrent access from multiple cores. Lock-free data structures and primitives like C++'s `std::atomic<int>` use these directly, avoiding the overhead of acquiring/releasing a full lock for simple operations.

Both approaches work by the same underlying principle: they turn a multi-step operation on shared state into something that, from the perspective of other threads, either hasn't happened at all or has happened completely — there is no observable "halfway" state for another thread to race against.

### 2. DBMS (Comparison)

Compare clustered and non-clustered indexes in a relational database. What is the key structural difference, and when would you choose one over the other?

**Answer:**

The key structural difference is *what the index actually controls*:

- A **clustered index** determines the physical order in which rows are stored on disk. The table's data pages themselves are organized (and kept sorted) according to the clustered index's key. Because the data can only be physically sorted one way, a table can have **at most one** clustered index — typically built automatically on the primary key.
- A **non-clustered index** is a completely separate structure (usually a B-tree) that stores the indexed column's values alongside a pointer or row locator back to where the actual row lives in the table's data pages, which are in some other physical order (often the clustered index's order, or unordered "heap" order if there is no clustered index). A table can have **many** non-clustered indexes.

This has direct performance consequences:
- Looking up a row via the clustered index key (or scanning a range of it) is very fast because the matching rows are physically adjacent — the engine just reads a contiguous run of pages. Range queries like `WHERE order_date BETWEEN ... AND ...` benefit enormously when `order_date` is the clustered key.
- Looking up a row via a non-clustered index normally costs **two** steps: first traverse the non-clustered index to find the row locator, then do a second lookup into the table's actual data pages to fetch the row's other columns (this second hop is sometimes called a "bookmark lookup"). If the query only needs columns already present in the non-clustered index itself, this second hop can be skipped — that's called a **covering index**.
- Writes (`INSERT`/`UPDATE`/`DELETE`) are generally cheaper against the clustered index alone, but more expensive the more non-clustered indexes exist, since each one must also be updated to stay consistent.

**When to choose which:** use the clustered index on the column(s) most frequently used for range scans or for retrieving rows in a natural order (often the primary key, or a date column in a time-series table). Use non-clustered indexes on columns frequently filtered or joined on in queries where you don't want to reorganize the whole table's physical layout — e.g., a `customer_email` lookup column on an `orders` table clustered by `order_id`. Avoid piling on too many non-clustered indexes on a write-heavy table, since each one adds update overhead.

### 3. Computer Architecture (Scenario)

Your program's inner loop accesses a large array with a large, fixed stride (e.g., `sum += array[i * 64]` for increasing `i`), touching the same *number* of elements as an equivalent version that accesses `array[i]` sequentially — yet the strided version runs dramatically slower. Explain why, in terms of the memory hierarchy.

**Answer:**

The slowdown comes from how CPU caches exploit **spatial locality**, and strided access with a large stride actively defeats it.

When the CPU fetches `array[i]`, it doesn't fetch just that one value — it pulls an entire **cache line** (commonly 64 bytes, e.g. 16 consecutive `int`s) from main memory into the L1/L2/L3 cache. In the sequential-access version, `array[i]`, `array[i+1]`, ..., `array[i+15]` all live in that same 64-byte line: the first access pays the full miss latency (a round trip to DRAM, potentially 100+ cycles), but the next 15 accesses are cheap L1 cache hits (a few cycles each), because they're already sitting in cache from that one fetch. The cost of the expensive miss is **amortized** over many fast hits.

In the strided version with stride 64 elements (which, if each element is 4 bytes, is 256 bytes — several cache lines apart), every single access lands on a *different* cache line that has very likely never been touched before. There is no reuse of what was just fetched: each iteration pays the full miss cost with no cheap hits to amortize it against. Worse, hardware prefetchers (which try to detect sequential or simple strided patterns and fetch ahead of time) are often tuned for small, predictable strides and can fail to keep up with a large stride like this, so the full memory latency is exposed on nearly every access instead of being hidden by prefetching. If the stride is large enough to also jump between virtual memory pages, you can additionally start taking **TLB misses**, adding address-translation overhead on top of the data cache misses.

Net effect: both versions do the same number of logical array accesses, but the sequential version does roughly `N/16` expensive DRAM fetches while the strided version does close to `N` of them — potentially an order-of-magnitude difference in wall-clock time, entirely explained by how well each pattern matches the cache's assumption that "nearby data is likely to be used soon." The standard mitigation is **loop blocking/tiling**: restructure the access pattern so that data is processed in cache-line- or cache-sized chunks, restoring spatial/temporal locality instead of striding far across memory on every step.
