### Question: Top K Frequent Elements (Hashing/Maps — Medium)

**Problem Statement**

Given an integer array `nums` and an integer `k`, return the `k` most frequent elements in `nums`. You may return the answer in any order.

**Input/Output Format**

- Input: an integer array `nums`, and an integer `k`.
- Output: an array of the `k` integers from `nums` that occur most frequently.

**Examples**

1. Input: `nums = [1,1,1,2,2,3]`, `k = 2` → Output: `[1,2]`
   `1` occurs 3 times, `2` occurs 2 times, `3` occurs once — the two most frequent are `1` and `2`.
2. Input: `nums = [1]`, `k = 1` → Output: `[1]`
   Only one distinct element, so it is trivially the most frequent.
3. Input: `nums = [4,4,4,6,6,7,7,7,7]`, `k = 2` → Output: `[7,4]`
   `7` occurs 4 times, `4` occurs 3 times, `6` occurs 2 times — the top 2 are `7` and `4`.

**Constraints**

- `1 <= nums.length <= 10^5`
- `-10^4 <= nums[i] <= 10^4`
- `k` is in the range `[1, number of distinct elements in nums]`
- The answer is guaranteed to be unique (given the problem's intent that any valid order is accepted).
- Expected to run in better than `O(n log n)` time (where `n = nums.length`).

### Step-by-Step Walkthrough

**Step 1 — count frequencies.** The first thing we need, regardless of approach, is how many times each distinct value appears. A hash map (`unordered_map<int,int>` in C++) built in one pass over `nums` gives us `value -> frequency` in `O(n)` time and `O(n)` space in the worst case (all distinct values).

**Step 2 — why sorting by frequency is the "obvious but slower" approach.** Once we have the frequency map, the naive idea is to dump `(frequency, value)` pairs into a vector and sort it descending by frequency, then take the first `k`. That works but costs `O(n log n)` — fine for most inputs, but it does more work than necessary since we don't actually need the *full* sorted order, only the top `k`.

**Step 3 — bucket sort by frequency (the optimal approach).** The key observation is that frequency is bounded: a value can occur at most `n` times in an array of length `n`. That means frequencies only range over `[0, n]` — a small, fixed range independent of the *values* themselves (which can be any 10^4-magnitude integer). So instead of sorting, we can bucket:

1. Build the frequency map as in Step 1 — `O(n)`.
2. Create `n + 1` buckets (a vector of vectors), where `buckets[f]` holds every value whose frequency is exactly `f`. Populate this by iterating the frequency map once — `O(n)` (number of distinct values is at most `n`).
3. Walk the buckets from `f = n` down to `f = 1`, collecting values into the answer until we have `k` of them. Since there are at most `n` buckets and at most `n` total values across all of them, this walk is `O(n)`.

Total time: `O(n)`. Total space: `O(n)` for the frequency map and the buckets.

**Why this is correct.** Bucketing by frequency and then scanning from the highest frequency bucket downward is exactly equivalent to a frequency-descending sort, except we exploit the fact that the "sort key" (frequency) only has `n + 1` possible values, so we can place items directly into their final relative order without comparison-based sorting. We stop as soon as we've gathered `k` elements, so we never do more work than needed.

**Edge cases considered.**
- `k` equal to the number of distinct elements: we simply drain every non-empty bucket, which naturally terminates once `k` elements are collected.
- All elements identical (`nums = [4,4,4]`, `k = 1`): one bucket at `f = 3` holding `[4]`; answer is `[4]`.
- Negative numbers in `nums`: irrelevant to the algorithm since we only hash/bucket by frequency, not by sign or magnitude of the value.

**Complexity.**
- Time: `O(n)` — one pass to count, one pass to bucket, one bounded pass to collect the top `k`.
- Space: `O(n)` — frequency map plus bucket array.

### C++ Code

```cpp
#include <vector>
#include <unordered_map>
using namespace std;

class Solution {
public:
    vector<int> topKFrequent(vector<int>& nums, int k) {
        int n = nums.size();

        // Step 1: count frequency of each value.
        unordered_map<int, int> freq;
        for (int x : nums) {
            freq[x]++;
        }

        // Step 2: bucket values by frequency. buckets[f] = all values with frequency f.
        vector<vector<int>> buckets(n + 1);
        for (auto& [value, count] : freq) {
            buckets[count].push_back(value);
        }

        // Step 3: walk buckets from highest frequency to lowest, collecting k values.
        vector<int> result;
        for (int f = n; f >= 1 && (int)result.size() < k; f--) {
            for (int value : buckets[f]) {
                result.push_back(value);
                if ((int)result.size() == k) {
                    break;
                }
            }
        }

        return result;
    }
};
```

## CS Fundamentals

### 1. Operating Systems (Conceptual)

What is thrashing in the context of virtual memory, and what typically causes it?

**Answer:**

Thrashing is a condition where a system spends more time swapping pages in and out of memory (paging) than actually executing processes, causing effective CPU throughput to collapse even though the CPU and disk both appear "busy."

**Why it happens:** Virtual memory lets each process believe it has access to more memory than physically exists, with the OS keeping only the "working set" (the pages a process is actively using) resident in RAM and the rest on disk. Thrashing occurs when the combined working sets of all active processes exceed the available physical RAM. In that state:

1. A process touches a page not currently resident → page fault.
2. The OS must evict some other page to make room, often choosing one that will be needed again very soon (because nearly everything is "hot").
3. The evicted page's owner then faults again shortly after, evicting yet another needed page, and so on.

The result is a vicious cycle: the disk I/O subsystem (orders of magnitude slower than RAM) becomes the bottleneck, CPU utilization paradoxically *drops* because processes are constantly blocked waiting on page faults, and overall system responsiveness craters.

**Common causes:**
- Too many processes running concurrently relative to available physical memory (over-commitment).
- A poor page replacement policy (e.g., naive FIFO can evict pages that are about to be reused — the "Belady's anomaly" scenario).
- A working set that genuinely doesn't fit in memory (e.g., a program iterating over a dataset much larger than RAM with poor locality).

**Mitigations:** admission control / load shedding (refuse to start new processes when memory pressure is already high), working-set-based scheduling (only run a process if its working set can fit in memory), increasing physical RAM, or using better replacement algorithms (e.g., approximations of LRU) that respect locality of reference. This matters in interviews because it connects memory management theory (paging, working sets) to observable, practical performance symptoms.

### 2. DBMS (Comparison)

Compare a clustered index and a non-clustered index: what is the structural difference, and how does that difference affect read and write performance?

**Answer:**

**Clustered index:** The table's actual row data is physically stored in the order of the indexed column(s). There can be only one clustered index per table, because the rows themselves can only be physically sorted one way. Think of it as the index *is* the table — the leaf nodes of the underlying B+ tree contain the full row data, not pointers to it.

**Non-clustered index:** A separate structure from the table's physical storage. Its leaf nodes contain the indexed column's value plus a pointer (or, in a clustered table, the clustering key) that locates the corresponding row in the actual table. A table can have many non-clustered indexes.

**Performance implications:**

| Aspect | Clustered | Non-clustered |
|---|---|---|
| Lookups on the indexed column | Very fast — data is found directly at the leaf, no extra hop | Requires an extra lookup ("bookmark lookup") into the base table unless the query is covered by the index alone |
| Range scans (e.g., `BETWEEN`, `ORDER BY` on the key) | Excellent — rows are already physically adjacent | Slower — logically adjacent keys may point to physically scattered rows |
| Insert/Update/Delete cost | Can be more expensive — inserting a row in the "middle" of the sort order may require physically relocating rows (page splits) | Cheaper per index, but every additional non-clustered index adds its own maintenance overhead on every write |
| Storage overhead | None beyond the table itself | Additional storage for each non-clustered index's structure |

**Why this matters in practice:** Primary keys are commonly implemented as the clustered index (e.g., an auto-incrementing `id`) because it gives fast point lookups and sequential inserts avoid costly page reordering. Columns frequently used in `WHERE` filters that aren't the primary key are good candidates for non-clustered indexes — but each one added trades faster reads for slower writes, since the database must keep every index consistent on every `INSERT`/`UPDATE`/`DELETE`. This is the classic read/write trade-off interviewers probe when asking "how many indexes should this table have?"

### 3. Computer Architecture (Scenario)

Scenario: You profile a C++ program that iterates over a 2D array of size `N x N` summing all elements. Version A iterates row-major (`for i: for j: sum += arr[i][j]`). Version B iterates column-major (`for j: for i: sum += arr[i][j]`) over the same array, which is stored in row-major order in memory. Version A runs noticeably faster than Version B for large `N`. Explain why, referencing the memory hierarchy.

**Answer:**

The slowdown in Version B comes from cache locality, not from the arithmetic itself — both versions do the exact same number of additions and array accesses, so the CPU's ALU work is identical. The difference is how efficiently each access pattern uses the cache hierarchy (L1/L2/L3 caches sitting between the CPU and main memory, which is dramatically slower than cache).

**Why Version A is fast:** In a row-major 2D array, `arr[i][j]` and `arr[i][j+1]` are stored at adjacent memory addresses. When the CPU fetches `arr[i][j]`, it doesn't just load that one value — it loads an entire cache line (typically 64 bytes, i.e., 16 consecutive 4-byte ints) from main memory into cache. Because Version A's inner loop walks `j` sequentially, every element after the first in a cache line is essentially "free" — it's already sitting in L1 cache from the line that was just fetched. This is **spatial locality**, and it means most memory accesses are cache hits.

**Why Version B is slow:** Version B's inner loop walks `i`, meaning consecutive accesses (`arr[0][j]`, `arr[1][j]`, `arr[2][j]`, ...) jump by `N` elements (one full row) in memory each time. For any reasonably large `N`, that stride is far bigger than a cache line, so almost every access pulls in a *new* cache line, most of which (the other 15 ints in that line) will never be used before being evicted. This causes a cache miss on nearly every single access, forcing a trip out to a slower cache level or even main memory, which can be 50-100x slower than an L1 hit.

**The underlying principle:** This is a direct, hands-on illustration of why "big-O time complexity" alone doesn't predict real-world performance — both versions are `O(N^2)`, but constant factors driven by the memory hierarchy (cache line size, associativity, prefetching behavior) can easily produce a 5-10x wall-clock difference. It's also why library implementations (e.g., matrix multiplication in BLAS) go to great lengths to restructure loops (tiling/blocking) specifically to maximize spatial and temporal locality rather than naively following the mathematical definition of the operation.
