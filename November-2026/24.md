### Question: Pacific Atlantic Water Flow (Graphs — Medium)

**Problem Statement**

There is an `m x n` rectangular island that borders both the Pacific Ocean and the Atlantic Ocean. The Pacific Ocean touches the island's left and top edges, and the Atlantic Ocean touches the island's right and bottom edges.

You are given an `m x n` integer matrix `heights` where `heights[r][c]` represents the height above sea level of the cell at coordinate `(r, c)`.

Rain water can flow from a cell to any of its four adjacent cells (up, down, left, right) if the neighbor's height is **less than or equal to** the current cell's height. Water can flow from any cell adjacent to an ocean into that ocean.

Return a list of grid coordinates `[r, c]` where rain water can flow to **both** the Pacific and Atlantic oceans.

**Input/Output Format**

- Input: a 2D integer array `heights` of size `m x n`.
- Output: a list of `[r, c]` pairs (order does not matter).

**Examples**

1. Input:
   ```
   heights = [[1,2,2,3,5],
              [3,2,3,4,4],
              [2,4,5,3,1],
              [6,7,1,4,5],
              [5,1,1,2,4]]
   ```
   Output: `[[0,4],[1,3],[1,4],[2,2],[3,0],[3,1],[4,0]]`

2. Input: `heights = [[1]]` → Output: `[[0,0]]` (the single cell touches both oceans trivially).

3. Input: `heights = [[2,1],[1,2]]` → Output: `[[0,0],[0,1],[1,0],[1,1]]`

**Constraints**

- `1 <= m, n <= 200`
- `0 <= heights[r][c] <= 10^5`
- Aim for O(m·n) time.

### Step-by-Step Walkthrough

**Why the brute force is too slow.** The direct reading of the problem is: for every cell, check whether water starting there can reach the Pacific *and* whether it can reach the Atlantic, via some downhill path. Doing a fresh BFS/DFS from every one of the `m*n` cells costs O(m·n) work per cell in the worst case, so O((m·n)²) overall — too slow for `m, n` up to 200 (that's 40,000 cells, 1.6 billion cell-visits).

**The key reframing: flow the water backwards.** Instead of asking "from this cell, can I reach the ocean?", ask the reverse question starting *from* the ocean: "which cells could have sent water here?" Water flows from a higher (or equal) cell to a lower (or equal) one, so reversing the direction means: starting at an ocean-adjacent cell, we can walk to a neighbor only if that neighbor's height is **greater than or equal to** the current cell's height (i.e., the neighbor could have flowed *down into* where we are).

This turns the problem into a **multi-source reachability** problem, run only twice total instead of once per cell:

1. Start a multi-source BFS/DFS from every cell on the top row and left column (the cells directly touching the Pacific). Mark every cell reachable under the "neighbor height >= current height" rule. Call this set `pacific`.
2. Do the same multi-source BFS/DFS from every cell on the bottom row and right column (touching the Atlantic). Call this set `atlantic`.
3. The answer is every cell that is in both `pacific` and `atlantic`.

**Why this is correct.** A cell `(r, c)` can send water to the Pacific (forward direction, non-increasing heights) if and only if there is a non-increasing path from `(r, c)` to some Pacific-adjacent cell. That is exactly the same set of cells reachable from the Pacific border by walking the *non-decreasing* reverse path — graph reachability is symmetric to path reversal: an edge `u -> v` exists in the forward "water flows" graph (meaning `height[v] <= height[u]`) exactly when the reverse edge `v -> u` exists in our backward walk (`height[u] >= height[v]`). So flood-filling backward from the ocean visits precisely the cells that can forward-flow into it.

**Complexity.**
- Time: O(m·n) — each of the two flood fills visits every cell at most once (standard visited-set BFS/DFS), and we start from O(m+n) border cells but each cell is still enqueued/processed once per flood fill.
- Space: O(m·n) — two boolean visited grids plus the BFS queue/recursion stack.

### C++ Code

```cpp
#include <vector>
#include <queue>
using namespace std;

class Solution {
public:
    vector<vector<int>> pacificAtlantic(vector<vector<int>>& heights) {
        int m = heights.size();
        if (m == 0) return {};
        int n = heights[0].size();
        if (n == 0) return {};

        vector<vector<bool>> pacific(m, vector<bool>(n, false));
        vector<vector<bool>> atlantic(m, vector<bool>(n, false));

        // Multi-source BFS from all cells touching a given ocean.
        // We "climb uphill" (or stay level): a move to a neighbor is
        // allowed only if the neighbor's height >= current height,
        // because that is the reverse of a legal downhill water flow.
        auto bfs = [&](queue<pair<int,int>> q, vector<vector<bool>>& visited) {
            int dr[4] = {-1, 1, 0, 0};
            int dc[4] = {0, 0, -1, 1};

            while (!q.empty()) {
                auto [r, c] = q.front();
                q.pop();
                for (int d = 0; d < 4; d++) {
                    int nr = r + dr[d];
                    int nc = c + dc[d];
                    if (nr < 0 || nr >= m || nc < 0 || nc >= n) continue;
                    if (visited[nr][nc]) continue;
                    if (heights[nr][nc] < heights[r][c]) continue; // must be non-decreasing uphill
                    visited[nr][nc] = true;
                    q.push({nr, nc});
                }
            }
        };

        queue<pair<int,int>> pacificQueue;
        queue<pair<int,int>> atlanticQueue;

        for (int c = 0; c < n; c++) {
            pacific[0][c] = true;
            pacificQueue.push({0, c});
            atlantic[m - 1][c] = true;
            atlanticQueue.push({m - 1, c});
        }
        for (int r = 0; r < m; r++) {
            pacific[r][0] = true;
            pacificQueue.push({r, 0});
            atlantic[r][n - 1] = true;
            atlanticQueue.push({r, n - 1});
        }

        bfs(pacificQueue, pacific);
        bfs(atlanticQueue, atlantic);

        vector<vector<int>> result;
        for (int r = 0; r < m; r++) {
            for (int c = 0; c < n; c++) {
                if (pacific[r][c] && atlantic[r][c]) {
                    result.push_back({r, c});
                }
            }
        }
        return result;
    }
};
```

A subtlety worth noting: when `m == 1` or `n == 1`, the top/left border and bottom/right border overlap on the same row or column, so some cells get pushed into both queues (or even the same queue twice) with their `visited` flag already set — the `if (visited[nr][nc]) continue;` guard and the initial `true` markers before pushing keep that safe, since re-adding an already-visited cell is simply skipped.

### 1. Operating Systems (Conceptual/Definition)

What is a deadlock in the context of an operating system, and what are the four necessary conditions (Coffman conditions) that must all hold simultaneously for one to occur?

**Answer:**

A **deadlock** is a state where a set of processes are each waiting for a resource that another process in the same set is holding, so none of them can ever make progress — every process is stuck waiting forever, and no external intervention can resolve it on its own. A classic concrete example: Process A holds printer and waits for the scanner; Process B holds the scanner and waits for the printer. Neither will ever release what it holds, because releasing is conditioned on first acquiring the thing it's waiting for.

Deadlock is only possible if **all four** of the following conditions hold at once — remove any one of them, and deadlock becomes structurally impossible:

1. **Mutual Exclusion.** At least one resource must be held in a non-shareable mode — only one process can use it at a time (e.g., a single printer, not a resource type that allows unlimited concurrent readers).
2. **Hold and Wait.** A process currently holding at least one resource is waiting to acquire additional resources that are currently held by other processes, instead of releasing what it already has while it waits.
3. **No Preemption.** Resources cannot be forcibly taken away from a process; a resource can only be released voluntarily by the process holding it, once it has finished using it.
4. **Circular Wait.** There exists a cycle of two or more processes, where each process is waiting for a resource held by the next process in the cycle (P1 waits on P2, P2 waits on P3, ..., Pn waits on P1).

**Why this matters practically:** these four conditions are precisely the four levers operating systems and application designers use to *prevent* deadlock rather than just detect and recover from it:
- Break mutual exclusion by using resources that support sharing where possible (e.g., read-only files), though this isn't always feasible for inherently exclusive resources.
- Break hold-and-wait by requiring a process to request all the resources it will ever need up front, atomically (so it never holds some while waiting for more).
- Break no-preemption by allowing a scheduler to forcibly revoke a resource from a waiting process (common in database lock managers, which abort and roll back a transaction to free its locks).
- Break circular wait by imposing a global ordering on resource acquisition (every process must request resources in the same fixed order, e.g., always lock the lower account ID before the higher one in a funds-transfer operation) — this is the most common real-world technique because it's cheap and doesn't sacrifice concurrency the way the others can.

### 2. Computer Networks (Comparison)

Compare TCP and UDP as transport-layer protocols. What does each one actually guarantee, and what concrete factors would make you choose one over the other for a given application?

**Answer:**

Both sit at the transport layer and both multiplex data to the right application via port numbers, but they make fundamentally different trade-offs between reliability and overhead.

| | TCP | UDP |
| --- | --- | --- |
| Connection | Connection-oriented (3-way handshake before data flows) | Connectionless (send and forget) |
| Reliability | Guaranteed delivery via acknowledgments and retransmission | No delivery guarantee at all |
| Ordering | Guarantees in-order delivery to the application | No ordering guarantee; packets can arrive out of sequence |
| Flow/congestion control | Built in (sliding window, slow start, congestion avoidance) | None — the application must handle it if needed |
| Overhead | Higher (handshake, ACKs, larger 20+ byte header, retransmission bookkeeping) | Lower (8-byte header, no handshake, no state to maintain) |
| Speed | Slower due to the above guarantees | Faster — minimal protocol overhead |

**Why TCP's guarantees exist:** every one of them is solving a real failure mode on an unreliable network — the handshake confirms both ends are actually reachable before data flows; sequence numbers let the receiver reorder packets that took different routes; ACKs plus retransmission recover from silent packet loss; congestion control backs off sending rate when the network signals it's overwhelmed (to avoid making congestion worse for everyone).

**When to choose TCP:** whenever correctness of every byte matters more than latency — file transfer (FTP), email (SMTP), web pages (HTTP/HTTPS), and anything where losing or reordering data silently corrupts the result (e.g., downloading a binary, or a banking API call).

**When to choose UDP:** whenever a late or missing packet is worse than a dropped one — live video/audio calls (VoIP, video conferencing), where retransmitting a 200ms-old audio frame is useless, you'd rather drop it and move on; online multiplayer games, where you want the *newest* player-position update, not a guaranteed-but-stale one; DNS queries, where the request is small and the client just retries on timeout rather than paying for a handshake; and live broadcast/streaming video, for the same reason as calls.

The deeper principle: TCP pushes reliability into the protocol so every application gets it "for free" at the cost of overhead and head-of-line blocking (a single lost packet stalls delivery of everything behind it until it's retransmitted); UDP pushes that decision back to the application, which is exactly right when the application's own notion of "reliable" differs from TCP's (e.g., "I only care about the latest state" rather than "I need every single update").

### 3. DBMS (Scenario/Applied)

A table of 50 million user rows is queried frequently with `SELECT * FROM users WHERE email = ?`, and this query has become slow. How would indexing fix this, and what trade-offs does adding the index introduce?

**Answer:**

Without an index, the database has no way to jump directly to the matching row — it must perform a **full table scan**, reading all 50 million rows from disk and checking each one's `email` column against the query value. That's O(n) work per lookup, and on a table that size it means scanning potentially gigabytes of data for a query that should return at most one row.

**The fix: create an index on `email`.**
```sql
CREATE INDEX idx_users_email ON users(email);
```
Most relational databases implement a standard index as a **B-tree** (or B+-tree): a balanced, sorted, multi-level structure of `(email value) -> (location of the row)` pairs. Looking up `email = 'x@y.com'` now means walking down the tree from root to leaf — O(log n) comparisons instead of O(n) — then following the pointer straight to the matching row(s) on disk. For 50 million rows, that's roughly log₂(50,000,000) ≈ 26 comparisons instead of up to 50 million row reads: a difference that turns a multi-second scan into a sub-millisecond lookup.

**Why this works specifically because the query filters on `email`:** an index only accelerates lookups on the column(s) it's built on (or a leading prefix of those columns, for a composite index). An index on `email` does nothing to speed up a query filtering on, say, `signup_date` — that would need its own index.

**The trade-offs, which is why you don't index every column:**
1. **Write cost.** Every `INSERT`, `UPDATE` (of the indexed column), or `DELETE` must now also update the index's B-tree structure to keep it consistent, not just the base table. On a write-heavy table, adding indexes can noticeably slow down writes.
2. **Storage cost.** An index is a real, separate data structure stored on disk (and often cached in memory) — it duplicates the indexed column's data alongside pointers to rows, so it costs additional space proportional to table size.
3. **Diminishing or negative returns on low-selectivity columns.** An index on a column with few distinct values (e.g., a boolean `is_active` flag) barely narrows the search — the optimizer may ignore it and fall back to a full scan anyway, since the index itself doesn't do much better than scanning.
4. **Maintenance overhead.** Indexes can fragment over time with heavy writes/deletes and may need periodic rebuilding (`REINDEX` / `OPTIMIZE TABLE`) to stay efficient.

**One extra useful note for this exact scenario:** since the query does `SELECT *` but filters only on `email`, a plain non-unique index on `email` still requires one extra step after the index lookup — a "bookmark lookup" back to the full row on disk to fetch the other columns. If `email` is also guaranteed unique (as it usually should be for a users table), declaring it `UNIQUE` additionally gets you a data-integrity constraint for free alongside the lookup speedup, and if the table is queried by `email` far more often than it's written to, that one index is a clear net win despite the trade-offs above.
