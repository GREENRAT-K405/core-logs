### Question: Trapping Rain Water (Arrays — Hard)

You are given `n` non-negative integers representing an elevation map, where the width of each bar is `1`. Compute how much water it can trap after raining.

**Input format:** an array `height` of non-negative integers.
**Output format:** a single integer — the total units of water trapped.

**Example 1:**
```
Input:  height = [0,1,0,2,1,0,1,3,2,1,2,1]
Output: 6
```
The elevation map traps 6 units of water between the bars (visualize the "basins" formed between taller bars on either side).

**Example 2:**
```
Input:  height = [4,2,0,3,2,5]
Output: 9
```

**Example 3:**
```
Input:  height = []
Output: 0
```
Edge case: fewer than 3 bars can never trap any water, since you need a wall on both sides.

**Constraints:**
- `0 <= n <= 2 * 10^4`
- `0 <= height[i] <= 10^5`

### Step-by-Step Walkthrough

**Key insight:** the amount of water sitting above any single bar `i` is determined entirely by the shorter of the two tallest walls on either side of it:

```
water(i) = max(0, min(maxLeft(i), maxRight(i)) - height[i])
```

where `maxLeft(i)` is the tallest bar anywhere to the left of (and including) `i`, and `maxRight(i)` is the tallest bar anywhere to the right of (and including) `i`.

**Naive approach (O(n) time, O(n) space):** precompute `leftMax[]` and `rightMax[]` arrays in two linear passes, then sum `min(leftMax[i], rightMax[i]) - height[i]` for every index. This works but uses extra memory we don't need.

**Optimal approach — two pointers (O(n) time, O(1) space):**
Maintain `left` and `right` pointers starting at the two ends of the array, and running maxima `leftMax` and `rightMax`. The crucial observation: whichever side currently has the *smaller* running maximum is the side whose water level we can safely finalize, because the other side is guaranteed to have (or will encounter) a wall at least that tall — so that smaller max is the true bottleneck for the current position.

Algorithm:
1. While `left < right`:
   - If `height[left] <= height[right]`:
     - Update `leftMax = max(leftMax, height[left])`.
     - Add `leftMax - height[left]` to the answer (this is safe because `rightMax` is guaranteed `>= height[right] >= height[left]`, so `leftMax` is the binding constraint).
     - Advance `left`.
   - Else (symmetric case):
     - Update `rightMax = max(rightMax, height[right])`.
     - Add `rightMax - height[right]` to the answer.
     - Decrement `right`.
2. Return the accumulated water.

**Why it works:** at each step we only ever commit water above the pointer whose side we *know* is the limiting wall, because the comparison `height[left] <= height[right]` tells us the opposite side already has an equal-or-taller boundary somewhere between the pointers. This lets us collapse the two-pass precomputation into a single pass with constant extra space.

**Complexity:**
- Time: `O(n)` — each pointer moves inward once, so the loop runs at most `n` times total.
- Space: `O(1)` — only a handful of scalar variables are used.

**Trace on Example 1** (`[0,1,0,2,1,0,1,3,2,1,2,1]`): the two pointers close in from both ends, accumulating water above the low points (indices 2, 4, 5, 6, 9) and the running maxima correctly bound each basin, totaling `6`.

### C++ Code

```cpp
#include <bits/stdc++.h>
using namespace std;

// Two-pointer solution: O(n) time, O(1) extra space.
int trap(vector<int>& height) {
    int n = height.size();
    if (n < 3) return 0; // need at least 3 bars to form a basin

    int left = 0, right = n - 1;
    int leftMax = 0, rightMax = 0;
    int water = 0;

    while (left < right) {
        if (height[left] <= height[right]) {
            // height[left] is the limiting wall on this side,
            // since the right side already has an equal-or-taller boundary.
            leftMax = max(leftMax, height[left]);
            water += leftMax - height[left];
            left++;
        } else {
            // Symmetric case: height[right] is the limiting wall.
            rightMax = max(rightMax, height[right]);
            water += rightMax - height[right];
            right--;
        }
    }
    return water;
}

int main() {
    vector<int> h1 = {0, 1, 0, 2, 1, 0, 1, 3, 2, 1, 2, 1};
    vector<int> h2 = {4, 2, 0, 3, 2, 5};
    vector<int> h3 = {};

    cout << trap(h1) << "\n"; // expected 6
    cout << trap(h2) << "\n"; // expected 9
    cout << trap(h3) << "\n"; // expected 0
    return 0;
}
```

## CS Fundamentals

### 1. Operating Systems (Comparison)

Compare preemptive and non-preemptive CPU scheduling. Name one scheduling algorithm example for each, and describe a scenario where non-preemptive scheduling would actually be preferred despite its drawbacks.

**Answer:**

In **preemptive scheduling**, the operating system can forcibly suspend a running process and switch the CPU to another process, typically triggered by a timer interrupt, a higher-priority process becoming ready, or an I/O completion event. The OS retains control over who gets the CPU and for how long. Example algorithms: **Round Robin** (time-sliced, fair) and **Shortest Remaining Time First (SRTF)**, the preemptive version of SJF.

In **non-preemptive scheduling**, once a process is given the CPU, it keeps it until it voluntarily yields — either by finishing, or by blocking on I/O. The scheduler only makes a decision at those natural transition points. Example algorithms: **First-Come-First-Served (FCFS)** and **Shortest Job Next (SJN)** (non-preemptive form).

Key trade-offs:
| Aspect | Preemptive | Non-preemptive |
|---|---|---|
| Responsiveness | High — short/urgent tasks don't starve behind long ones | Low — a long process blocks everything behind it |
| Overhead | Higher — frequent context switches cost CPU cycles and cache locality | Lower — fewer, more predictable switches |
| Implementation complexity | Higher — needs synchronization around shared data since a process can be interrupted mid-critical-section | Simpler — no partial-execution state to worry about mid-task |
| Predictability | Lower — execution time of any given process can be stretched unpredictably | Higher — once started, a process's remaining work is uninterrupted |

**Scenario favoring non-preemptive scheduling:** embedded or real-time control systems performing a short, atomic hardware operation (e.g., writing a sequence of bytes to a device register, or a safety-critical actuator control loop) often use non-preemptive scheduling for that operation specifically, because being interrupted mid-operation could leave hardware in an inconsistent or unsafe state, and the cost of guaranteeing safe preemption (locks, rollback, re-entrancy) is higher than the cost of occasionally blocking other work for a few microseconds. More generally, batch-processing systems where throughput and predictable total runtime matter more than individual responsiveness (e.g., a nightly ETL job scheduler) also favor non-preemptive or cooperative scheduling, since context-switch overhead directly eats into total batch throughput with no responsiveness benefit to justify it.

### 2. Computer Architecture (Conceptual)

What is a pipeline hazard in a CPU's instruction pipeline? Describe the three classic types — structural, data, and control — and name one mitigation technique for each.

**Answer:**

Instruction pipelining overlaps the execution of multiple instructions across stages (e.g., fetch, decode, execute, memory access, write-back) so that, ideally, one instruction completes every clock cycle instead of every several cycles. A **pipeline hazard** is any situation where the next instruction cannot execute in its designated clock cycle without producing an incorrect result, forcing the pipeline to stall, flush, or otherwise delay.

1. **Structural hazard:** occurs when two instructions in different pipeline stages need the same hardware resource at the same time (e.g., both need to access memory in the same cycle, but there's only one memory port). *Mitigation:* duplicate the contended resource — e.g., use separate instruction and data caches/memories (the classic Harvard-style split) so instruction fetch and data access never compete for the same port.

2. **Data hazard:** occurs when an instruction depends on the result of a prior instruction that hasn't finished producing that result yet (read-after-write being the most common case). For example, `ADD R1, R2, R3` followed immediately by `SUB R4, R1, R5` needs `R1`'s new value before it's written back. *Mitigation:* **operand forwarding (bypassing)** — route the result directly from the execute stage's output back into a later instruction's input before it's officially written to the register file, skipping the wait for write-back. When forwarding isn't possible (e.g., the value isn't computed yet), the pipeline falls back to **stalling** (inserting bubbles).

3. **Control hazard:** occurs because of branches — the pipeline doesn't know which instruction to fetch next until the branch is resolved, which may happen several stages later. *Mitigation:* **branch prediction** (static or dynamic, e.g., a branch history table/predictor) — guess the branch outcome and speculatively fetch down the predicted path, rolling back (flushing the pipeline) only on a misprediction. A simpler, older mitigation is a fixed **branch delay slot**, but modern high-performance CPUs rely almost entirely on dynamic prediction because of its much higher accuracy.

Why it matters: hazards are the main reason real pipelines don't achieve the "one instruction per cycle" ideal throughput; the entire discipline of out-of-order execution, register renaming, and speculative execution in modern CPUs exists largely to minimize the stalls these three hazard types would otherwise cause.

### 3. System Design Basics (Scenario)

You're asked to design a URL-shortener service (like bit.ly) expected to handle roughly 100 million new URLs created per day, with read (redirect) traffic far outweighing writes. Walk through your design: the encoding scheme, database choice, caching strategy, and how you'd handle key collisions.

**Answer:**

**1. Encoding scheme:** the core requirement is mapping a long URL to a short, unique key (typically 6-8 characters). Two common approaches:
   - **Counter + Base62 encoding:** maintain a globally unique, monotonically increasing ID (e.g., from a distributed counter service or a database auto-increment with pre-allocated ranges per server to avoid a single point of contention), then encode that integer in base62 (`[a-zA-Z0-9]`) to get a short string. This guarantees uniqueness by construction — no collision handling needed at all. At 100M/day, even a 6-character base62 key (62^6 ≈ 56 billion combinations) comfortably covers years of growth before needing a 7th character.
   - **Hash-based (e.g., first 6-8 chars of MD5/SHA-256 of the long URL):** simpler conceptually, but requires explicit collision detection (see below) since truncated hashes aren't guaranteed unique.
   I'd favor the **counter-based approach** for a system at this scale, since it sidesteps collisions entirely and keeps write-path logic simple — the main engineering cost is just building a reliable, horizontally-scalable unique ID generator (e.g., Snowflake-style IDs, or range allocation from a coordination service like ZooKeeper/etcd).

**2. Database choice:** the access pattern is simple key-value lookups (`short_key -> long_url`) with no need for complex joins or transactions, and it must scale horizontally to handle heavy read volume. A **NoSQL key-value or wide-column store** (e.g., DynamoDB, Cassandra) is a strong fit: it partitions naturally by `short_key`, scales reads/writes independently, and offers the low, predictable latency this lookup-heavy workload needs. A relational database would work too at smaller scale, but loses its main advantages (joins, complex transactions) here while adding scaling friction.

**3. Caching strategy:** since reads vastly outnumber writes, put a **caching layer (Redis/Memcached) in front of the database** for the hot set of frequently-accessed short URLs, following a cache-aside pattern: check cache first, fall through to the database on a miss, then populate the cache. Because `short_key -> long_url` mappings are immutable once created (we never need to invalidate on update), this cache is simple and highly effective — a large fraction of traffic typically concentrates on a small fraction of recently-created or viral links (classic long-tail/Zipfian access distribution). A CDN or edge-level redirect cache can push this even closer to the user for globally distributed read traffic.

**4. Collision handling:** with the counter-based scheme, collisions are structurally impossible, so no handling is needed. If a hash-based scheme were used instead, I'd handle collisions by checking the database for the generated key before insert; on a collision, append a fixed salt (or take a few more hash characters) and retry, looping until a free key is found — since truncated-hash collisions are rare, this retry loop resolves almost instantly in practice. Given the added complexity for no real benefit at this scale, this reinforces the choice of the counter-based scheme as the simpler, safer design.
