### Question: Task Scheduler (Greedy — Medium)

**Problem Statement**

You are given an array of CPU `tasks`, where each task is represented by a character (`'A'` to `'Z'`), and a non-negative integer `n` that represents the cooldown period between two **identical** tasks. The CPU can run one task per unit of time, or stay idle for one unit of time. However, between two occurrences of the *same* task, there must be at least `n` units of time in which the CPU either runs other tasks or is idle.

Return the minimum number of time units the CPU will need to finish all the given tasks.

**Input/Output Format**

- Input: a list of characters `tasks`, and an integer `n` (the cooldown).
- Output: an integer, the minimum total time units required.

**Examples**

1. Input: `tasks = ["A","A","A","B","B","B"]`, `n = 2` → Output: `8`
   One valid schedule: `A B idle A B idle A B` (8 slots).
2. Input: `tasks = ["A","A","A","B","B","B"]`, `n = 0` → Output: `6`
   No cooldown needed, so just run every task back to back: `A A A B B B`.
3. Input: `tasks = ["A","A","A","A","A","A","B","C","D","E","F","G"]`, `n = 2` → Output: `16`
   `A` needs 5 full gaps of size 3 (task + 2 cooldown slots) between its 6 occurrences, and there aren't enough other distinct tasks to fill every gap, so some slots stay idle.

**Constraints**

- `1 <= tasks.length <= 10^4`
- `tasks[i]` is an uppercase English letter.
- `0 <= n <= 100`

### Step-by-Step Walkthrough

**Why simulation is the wrong mental model.** You could imagine literally stepping through time, always picking whichever available task currently has the highest remaining count, and counting idle slots when nothing is available. That works, but it's doing far more bookkeeping than the problem needs — with `n` up to 100 and 26 possible task types, we can reason about the *shape* of the optimal schedule directly instead of building it slot by slot.

**Key insight — the bottleneck is the most frequent task.** Let `maxFreq` be the count of whichever task occurs most often, and suppose there's only one such task (ties are handled below). Every occurrence of that task needs a cooldown window of length `n` after it, except the very last occurrence. So the *skeleton* of the schedule looks like:

```
[task] [n cooldown slots] [task] [n cooldown slots] ... [task]
```

There are `maxFreq` occurrences of the bottleneck task and `maxFreq - 1` gaps between them, each of size `n`. That skeleton alone takes:

```
(maxFreq - 1) * (n + 1) + 1
```

(`n + 1` because each gap is `n` cooldown slots plus the 1 slot for the task that starts the *next* gap; the final `+1` accounts for the very last occurrence of the bottleneck task, which starts no new gap.)

**Filling the gaps with everything else.** Every other task gets slotted into those cooldown gaps wherever possible — a task with frequency `f <= maxFreq` can supply at most one occurrence per gap (if it appeared twice in the *same* gap, it would violate its own cooldown relative to itself, since the gap width is exactly `n`). So the skeleton can absorb other tasks "for free," without extending the schedule, **as long as there's enough skeleton to hold them**.

**Handling ties at the max frequency.** If `k` distinct tasks all share `maxFreq` (the highest count), then each of the `maxFreq - 1` gaps must additionally hold one occurrence of *each* of those `k - 1` other tied tasks (they can't be scheduled next to each other without violating their own cooldown either, if they also hit `maxFreq`). So the skeleton formula becomes:

```
(maxFreq - 1) * (n + 1) + k
```

where `k` is the number of distinct tasks tied for the maximum frequency.

**Why we then take a max with `tasks.length`.** The formula above is the length of the *minimal skeleton that enforces the cooldowns*. If there are enough other tasks lying around (because `n` is small or there are many distinct task types), they fill every idle slot and then some — in that case the schedule is simply *no longer idle at all*, and the answer is just `tasks.length` (every task runs back-to-back with no forced idle time). So the true answer is:

```
max(tasks.length, (maxFreq - 1) * (n + 1) + k)
```

**Why this is correct (sketch).** The skeleton-length formula is a hard lower bound: those cooldown constraints on the max-frequency task(s) cannot be satisfied in fewer slots, no matter how cleverly you interleave other tasks. It's also *achievable*: round-robin the remaining tasks (by decreasing frequency) into the gaps left by the skeleton; since no other task has frequency greater than `maxFreq`, it can never be forced to repeat within the same `n`-wide gap. And whenever `tasks.length` exceeds the skeleton length, there's simply no room left for idle slots, so the bound degrades gracefully to just running every task once.

**Complexity.**
- Time: O(N + 26) ≈ O(N), where N = `tasks.length` — one pass to count frequencies, one pass over the fixed 26-letter alphabet to find `maxFreq` and `k`.
- Space: O(1) — a fixed 26-entry frequency table.

### C++ Code

```cpp
#include <vector>
#include <array>
#include <algorithm>
using namespace std;

int leastInterval(vector<char>& tasks, int n) {
    array<int, 26> freq{};
    for (char c : tasks) {
        freq[c - 'A']++;
    }

    int maxFreq = 0;
    for (int f : freq) {
        maxFreq = max(maxFreq, f);
    }

    // Count how many distinct tasks share the maximum frequency.
    int tiedAtMax = 0;
    for (int f : freq) {
        if (f == maxFreq) {
            tiedAtMax++;
        }
    }

    // Length of the minimal schedule enforced by the cooldown on the
    // most frequent task(s): (maxFreq - 1) full gaps of size (n + 1),
    // plus one slot per tied-max task for the final round.
    int skeletonLength = (maxFreq - 1) * (n + 1) + tiedAtMax;

    // If there are enough other tasks to fill every idle slot (and more),
    // the answer is just the total task count -- no idle time needed.
    return max((int)tasks.size(), skeletonLength);
}
```

### 1. Operating Systems (Conceptual/Definition)

What is a deadlock, and what are the four necessary conditions that must all hold simultaneously for one to occur? Why does breaking just one of them prevent deadlock entirely?

**Answer:**

A **deadlock** is a state where two or more processes are each waiting for a resource held by another process in the group, so none of them can ever proceed — every process is blocked forever, with no external event able to free any of them.

Deadlock requires all four of the **Coffman conditions** to hold at once:

1. **Mutual exclusion.** At least one resource is held in a non-shareable mode — only one process can use it at a time.
2. **Hold and wait.** A process already holding at least one resource is waiting to acquire additional resources currently held by other processes.
3. **No preemption.** Resources cannot be forcibly taken away from a process; they can only be released voluntarily once the process is done with them.
4. **Circular wait.** There exists a cycle of processes `P1 -> P2 -> ... -> Pn -> P1`, where each `Pi` is waiting for a resource held by `P(i+1)`.

**Why breaking any one condition is enough:** the four conditions are jointly necessary — deadlock *cannot* happen unless all four are simultaneously true. So prevention strategies each target exactly one:

- Break **mutual exclusion** by making resources shareable where possible (e.g., read-only files) — not always feasible, since some resources are inherently exclusive (a printer, a write lock).
- Break **hold and wait** by requiring processes to request all resources they'll ever need up front, or to release everything before requesting more — simple but hurts resource utilization and concurrency.
- Break **no preemption** by allowing the OS to forcibly reclaim a resource from a waiting process (common for CPU and memory, much harder for things like a database lock mid-transaction).
- Break **circular wait** by imposing a global ordering on resources and requiring every process to request resources in increasing order — this is the most practically common fix, because it's enforceable purely by convention without needing to preempt anything.

In practice, most systems don't try to *prevent* deadlock structurally (it's expensive and restrictive); they instead use **detection and recovery** (periodically scan the resource-allocation graph for cycles and kill/rollback a process) or simply **avoidance** via algorithms like Banker's Algorithm, which only grants a resource request if doing so keeps the system in a state from which every process can still eventually finish.

### 2. Computer Networks (Comparison)

Compare TCP and UDP. Beyond "TCP is reliable and UDP isn't," what specific mechanisms does TCP use to provide that reliability, and in what situations does UDP's lack of those mechanisms make it the better choice?

**Answer:**

Both are transport-layer protocols sitting on top of IP, but they make opposite trade-offs between guarantees and overhead.

**TCP (Transmission Control Protocol)** is connection-oriented and reliable. Its guarantees come from concrete mechanisms, not just a design philosophy:

- **Three-way handshake** (`SYN`, `SYN-ACK`, `ACK`) establishes a connection and synchronizes initial sequence numbers before any data flows.
- **Sequence numbers** on every byte let the receiver detect missing, duplicate, or out-of-order segments and reassemble them in the correct order.
- **Acknowledgements and retransmission** — the sender keeps unacknowledged data in a buffer and retransmits it if an ACK doesn't arrive within a timeout (or after enough duplicate ACKs trigger fast retransmit), so lost packets are recovered automatically.
- **Flow control** via a sliding window advertised by the receiver, so a fast sender can't overwhelm a slow receiver's buffer.
- **Congestion control** (slow start, congestion avoidance, algorithms like Cubic or BBR) throttles the sending rate based on inferred network congestion, so TCP backs off under load instead of making congestion worse.

All of this machinery costs **latency and overhead**: the handshake adds a round trip before any data is sent, acknowledgements and retransmissions add delay under loss, and head-of-line blocking means one lost segment stalls delivery of everything behind it until it's recovered.

**UDP (User Datagram Protocol)** is connectionless: it just sends datagrams with a checksum for corruption detection and nothing else — no handshake, no sequencing, no retransmission, no congestion control. A lost or out-of-order datagram is simply gone; it's the application's job to notice and decide what to do, if anything.

**When UDP's lack of guarantees is actually the win:**

- **Real-time media (voice/video calls, live streaming).** A dropped frame from half a second ago is worthless if retransmitted now — by the time it arrives the call has moved on. Low latency matters more than completeness, so the application just drops the gap and keeps going.
- **DNS queries.** A single small request/response pair; if it's lost, the resolver just retries the whole query, which is simpler and faster than TCP's connection setup for something this short-lived (DNS falls back to TCP only for unusually large responses).
- **Online multiplayer games.** Only the *latest* position/state matters; an old, retransmitted position update is stale and should be discarded, not queued behind by head-of-line blocking.
- **Protocols that implement their own reliability layer on top** (e.g., QUIC, which runs over UDP) — when an application wants reliability semantics *different* from TCP's (such as avoiding head-of-line blocking across independent streams), building on UDP's blank slate is more flexible than fighting TCP's built-in assumptions.

The general rule: choose UDP when timeliness matters more than completeness, or when the application will implement its own tailored reliability; choose TCP when correctness and completeness of the byte stream matter more than any individual packet's latency.

### 3. DBMS (Scenario/Applied)

Your application's `orders` table has grown to 50 million rows, and a query that filters by `customer_id` has become slow. You're told "just add an index on `customer_id`." What does that actually do under the hood, why does it speed up this query, and what cost does it introduce that means you shouldn't index every column?

**Answer:**

Without an index, the database must perform a **full table scan**: read every one of the 50 million rows and check whether its `customer_id` matches, which is O(n) work regardless of how few rows actually match.

**What an index actually is:** a separate data structure — most commonly a **B+ tree** — that stores `customer_id` values in sorted order, with each entry pointing to the location of the corresponding row(s) in the table (either a direct pointer, or in a clustered index, the actual row data organized by that key). Because a B+ tree keeps its data sorted and balanced, looking up all rows matching a given `customer_id` becomes a tree traversal: O(log n) to find the first matching entry, then a cheap sequential walk across the matching leaf entries, instead of scanning the entire table. For 50 million rows, that's the difference between touching tens of millions of rows and touching perhaps a few dozen.

Concretely, after adding `CREATE INDEX idx_customer_id ON orders(customer_id);`, the query planner's `EXPLAIN` output for `SELECT * FROM orders WHERE customer_id = ?` flips from a `Seq Scan` / full table scan to an `Index Scan` (or `Index Range Scan`), because the planner now has a cheaper path to the matching rows than reading the whole table.

**Why you can't just index every column, though — indexes aren't free:**

- **Write cost.** Every `INSERT`, `UPDATE`, or `DELETE` on the table must also update every index on that table, to keep each index's sorted structure consistent. Ten indexes means ten structures to maintain on every write, which can turn a fast insert-heavy workload sluggish.
- **Storage cost.** Each index is itself a sizeable data structure stored on disk (and ideally cached in memory) — a handful of indexes on a 50-million-row table can easily add up to as much storage as the table itself.
- **Diminishing or negative returns on the wrong columns.** An index on a low-cardinality column (e.g., a boolean `is_active` flag with only two distinct values) rarely helps — the planner may still choose a full scan because filtering on it doesn't narrow the result enough to justify the extra lookup, and maintaining such an index is pure overhead.
- **Planner confusion.** Too many indexes can occasionally make the query planner choose a worse execution plan, since it has more (and sometimes misleading, if statistics are stale) options to evaluate.

The practical takeaway: index columns that are actually used in `WHERE`, `JOIN`, or `ORDER BY` clauses on large tables, especially high-cardinality ones, and verify with `EXPLAIN` that the index is actually being chosen — adding an index is a targeted trade of write cost and storage for read speed, not a universal "makes queries faster" switch.
