### Question: Next Greater Element II (Stacks/Queues — Medium)

Given a **circular** integer array `nums` (the element after the last one wraps around to the first one), return an array `result` where `result[i]` is the **next greater number** of `nums[i]`, searching circularly if needed.

The next greater number of `nums[i]` is the first number to its right (wrapping around the end of the array back to the front) that is strictly greater than `nums[i]`. If no such number exists, `result[i]` should be `-1`.

**Input/Output format:**
- Input: an integer array `nums`.
- Output: an integer array `result` of the same length, where `result[i]` is the next greater number of `nums[i]`, or `-1` if none exists.

**Example 1:**
```
Input:  nums = [1, 2, 1]
Output: [2, -1, 2]
```
Explanation: The first `1`'s next greater number is `2`. The `2` has no greater number anywhere, even wrapping around, so it gets `-1`. The second `1` finds `2` by wrapping back to the start.

**Example 2:**
```
Input:  nums = [1, 2, 3, 4, 3]
Output: [2, 3, 4, -1, 4]
```
Explanation: `4` is the maximum, so it never finds a greater number even after wrapping, and gets `-1`. The last `3` wraps around and finds `4` before it would reach itself again.

**Example 3:**
```
Input:  nums = [5, 5, 5]
Output: [-1, -1, -1]
```
Explanation: No element is *strictly* greater than `5` anywhere in the array, circular or not, so every answer is `-1`.

**Constraints:**
- `1 <= nums.length <= 10^4`
- `-10^9 <= nums[i] <= 10^9`

### Step-by-Step Walkthrough

**Why a brute force is too slow:** The naive approach checks, for every index `i`, up to `2n` positions going forward (to cover the circular wraparound) looking for the first larger value. That's O(n) work per element, O(n²) overall. For `n = 10^4` that's `10^8` comparisons — borderline, and inelegant. We can do it in a single O(n) pass.

**Key idea — monotonic stack:** The classic "next greater element" trick uses a stack that holds indices of elements for which we haven't yet found a next-greater value, kept in **decreasing order of their values from bottom to top**. We scan left to right. For the current value `val`:
- While the stack is non-empty and the value at the index on top of the stack is **smaller** than `val`, that top element's answer is `val` (it's the first larger value to its right) — pop it and record the answer.
- Once the stack's top value is no longer smaller than `val` (or the stack is empty), push the current index onto the stack — we don't know its answer yet.

Any index still left on the stack at the end of a single left-to-right pass simply has no greater element to its right in a *non-circular* array, so it would get `-1`.

**Handling the circularity:** The only change needed is to simulate the array being traversed **twice** (length `2n`), using `nums[i % n]` to wrap the index back into range. The trick is that during the *second* pass we only use values to resolve answers still sitting on the stack (via the popping step) — we must **not push new indices** during the second pass, since every real index has already been pushed once, and pushing it again would cause it to be processed (and possibly resolved) out of its true original position. So the condition `if (i < n) push(i)` guards exactly that: only push on the first pass, but keep popping/resolving on both passes.

Why this two-pass trick works: an index `i`'s true next-greater element (if any) that requires wrapping around must appear within the array's remaining elements *and* the elements before `i` — i.e., at some position in `[i+1, i-1+n]` in circular order, which is exactly covered by extending the scan to `2n` steps starting from `0`.

**Complexity:**
- **Time:** O(n). Each index is pushed exactly once and popped at most once across the whole `2n`-length scan, so the total work across all stack operations is O(n), and the loop itself runs `2n` times — overall O(n).
- **Space:** O(n) for the stack and the result array.

### C++ Code

```cpp
#include <vector>
#include <stack>
using namespace std;

vector<int> nextGreaterElements(vector<int>& nums) {
    int n = nums.size();
    vector<int> result(n, -1);   // default: no greater element found
    stack<int> indices;          // indices whose "next greater" is still unknown,
                                  // values at these indices are kept decreasing
                                  // from bottom to top of the stack

    // Walk the array twice (length 2n) to simulate the circular wraparound.
    for (int i = 0; i < 2 * n; ++i) {
        int val = nums[i % n];

        // Current value resolves every pending index whose value is smaller:
        // val is the first larger value appearing to their right.
        while (!indices.empty() && nums[indices.top()] < val) {
            result[indices.top()] = val;
            indices.pop();
        }

        // Only push "real" indices during the first pass (i < n).
        // The second pass exists purely to resolve leftovers via wraparound;
        // pushing again here would re-process an index out of order.
        if (i < n) {
            indices.push(i);
        }
    }

    return result; // any index still on the stack never got popped -> stays -1
}
```

### 1. Operating Systems (Scenario)

A multi-threaded server process has four worker threads that each need to lock two shared resources, `A` and `B`, to complete a transaction. Threads 1 and 3 always acquire `A` first, then `B`. Threads 2 and 4 always acquire `B` first, then `A`. Under heavy concurrent load, the server occasionally freezes completely and has to be restarted.

(a) What is happening here, and what are the necessary conditions for it to occur?
(b) Give two concrete strategies you could implement in the code to prevent it from happening again.

**Answer:**

(a) This is a classic **deadlock**. Threads 1/3 grab `A` and then block waiting for `B`, while threads 2/4 grab `B` and then block waiting for `A`. Each side is holding a resource the other side needs, and neither can proceed, so the process hangs forever (until something external, like a restart, intervenes).

For a deadlock to occur, all four of the **Coffman conditions** must hold simultaneously:
1. **Mutual exclusion** — each resource (`A`, `B`) can only be held by one thread at a time.
2. **Hold and wait** — a thread holding one resource (e.g. `A`) is waiting to acquire another (`B`) without releasing what it already has.
3. **No preemption** — a resource can't be forcibly taken away from the thread holding it; it must be released voluntarily.
4. **Circular wait** — there's a cycle of threads, each waiting on a resource held by the next (Thread 1 waits on `B`, held by Thread 2, which waits on `A`, held by Thread 1).

Break any one of these four conditions and deadlock becomes impossible.

(b) Two practical fixes (there are more, but these are the most common in real systems):
- **Impose a global lock ordering.** Require every thread to always acquire shared resources in the same canonical order (e.g., always lock the resource with the smaller ID first: `A` before `B`, never `B` before `A`). This directly eliminates the circular-wait condition — there's no longer a cycle possible, because everyone converges on the same acquisition order.
- **Use try-lock with timeout and back off.** Instead of blocking indefinitely on the second resource, attempt to acquire it with a timeout; if it fails, release the first lock, wait a randomized short interval, and retry the whole transaction from scratch. This breaks "hold and wait" by guaranteeing a thread never holds a resource indefinitely while permanently blocked on another.

(A less common but valid third option is acquiring all needed locks atomically up front via a single higher-level lock, or running periodic deadlock detection using a resource-allocation/wait-for graph and aborting one of the transactions in a detected cycle — this is what some database engines do.)

### 2. Computer Networks (Conceptual)

Describe the TCP three-way handshake used to establish a connection: what is sent in each of the three segments, and why does TCP need this exchange at all instead of simply sending data immediately the way UDP does?

**Answer:**

The three-way handshake synchronizes both sides on **starting sequence numbers** and confirms that both directions of the connection are actually working before any application data flows:

1. **SYN** — the client picks an initial sequence number `x` and sends a segment with the `SYN` flag set, announcing "I want to start a connection, and my sequence numbers will start at `x`."
2. **SYN-ACK** — the server picks its own initial sequence number `y`, and replies with a segment that has both `SYN` and `ACK` set: it acknowledges the client's `x` (by sending `ACK = x + 1`) and announces its own starting sequence number `y`.
3. **ACK** — the client acknowledges the server's `y` (`ACK = y + 1`) with a plain `ACK` segment. At this point both sides have confirmed, in both directions, that packets they send are actually reaching the other side and being understood.

Why TCP needs this and UDP doesn't:

- **TCP is connection-oriented and reliable.** It has to track sequence numbers so it can detect lost, duplicated, or reordered segments and retransmit anything missing. The handshake is how each side learns the other's starting sequence number, which both sides need before they can correctly interpret acknowledgments for the data that follows.
- **It verifies bidirectional reachability before committing resources.** If the server only received the SYN but could never reply, or the client never got the SYN-ACK, no connection state should be kept. The three steps make sure both directions are proven to work, not just one.
- **UDP is connectionless and makes no reliability promises.** It has no sequence numbers to synchronize and no notion of a "connection" to establish — a sender just fires datagrams and the network may drop, duplicate, or reorder them, with no acknowledgment mechanism built in. That's precisely why UDP has lower latency for the first packet (no round trip needed before sending data) but pushes the burden of reliability (if needed at all) up to the application.

### 3. OOP (Comparison)

Compare **composition** and **inheritance** as two ways to reuse code between classes. Give an example of a situation where composition is clearly the better choice, and explain why "favor composition over inheritance" is common advice in object-oriented design.

**Answer:**

**Inheritance** models an **"is-a"** relationship: a subclass extends a base class, inherits its public/protected members, and can override behavior. **Composition** models a **"has-a"** relationship: a class holds a reference/instance of another class as a member and delegates to it, without taking on its entire interface.

Example: a `Car` needs an engine. Modeling this with inheritance (`class Car : public Engine`) is wrong — a car *is not* an engine, it merely *has* one. The correct design is composition:

```cpp
class Engine {
public:
    void start();
};

class Car {
    Engine engine; // Car "has-a" Engine
public:
    void start() { engine.start(); } // delegate
};
```

With composition, swapping in a `ElectricEngine` or a `HybridEngine` at construction time (or even at runtime, via a pointer/interface) is trivial — `Car` doesn't care about `Engine`'s internals, only its interface. If `Car` instead inherited from `Engine`, every method of `Engine` would leak into `Car`'s public interface whether or not it made sense for a car (e.g. `Engine::disassemble()`), and swapping engine types would mean changing `Car`'s entire class hierarchy.

Why composition is generally favored:
- **Looser coupling.** A composed class only depends on the small interface it actually uses, not on the full implementation details of another class. Inheritance couples a subclass tightly to its parent's implementation — this is the well-known **fragile base class problem**, where an innocuous change to the base class can silently break subclasses that depended on its internal behavior.
- **Flexibility at runtime.** Composition allows swapping the "has-a" component dynamically (e.g., dependency injection, strategy pattern), whereas inheritance relationships are fixed at compile time and can't be changed once an object is constructed.
- **Avoids deep, fragile hierarchies.** Multiple levels of inheritance tend to produce rigid class trees that are hard to refactor; composition lets you build behavior by combining small, independent pieces instead.

Inheritance is still the right tool when there's a genuine, stable "is-a" relationship and you want polymorphic substitutability (e.g., a `Square` really is a `Shape` and should be usable anywhere a `Shape` is expected) — but when in doubt, or when the relationship is really "uses" or "has" rather than "is," composition is the safer default.
