### Question: Reverse Nodes in k-Group (Linked Lists — Hard)

Given the head of a singly linked list and an integer `k`, reverse the nodes of the list `k` at a time, and return the modified list's head. `k` is a positive integer and is less than or equal to the length of the linked list. If the number of nodes remaining at the end is not a multiple of `k`, those leftover nodes should be left as they are (not reversed).

You may only use `O(1)` extra memory — no copying node values into an array and no recursion that relies on the call stack to hold the whole list.

**Input format:** the head of a singly linked list, and an integer `k`.

**Output format:** the head of the list after reversing every full group of `k` nodes in place.

**Examples:**

Example 1:
```
Input: head = [1,2,3,4,5], k = 2
Output: [2,1,4,3,5]
Explanation: [1,2] reverses to [2,1], [3,4] reverses to [4,3]; node 5 is a leftover group of size 1 (< k), so it stays as-is.
```

Example 2:
```
Input: head = [1,2,3,4,5], k = 3
Output: [3,2,1,4,5]
Explanation: [1,2,3] reverses to [3,2,1]; only [4,5] remain, a group of size 2 (< k), so they stay as-is.
```

Example 3:
```
Input: head = [1,2,3,4,5,6], k = 3
Output: [3,2,1,6,5,4]
Explanation: [1,2,3] reverses to [3,2,1] and [4,5,6] reverses to [6,5,4] — both are full groups of size k.
```

**Constraints:**
- The number of nodes `n` in the list satisfies `1 <= k <= n <= 5000`.
- `0 <= Node.val <= 1000`.
- Follow-up (required here): solve it using only pointer manipulation, in `O(1)` extra space.

### Step-by-Step Walkthrough

**The shape of the problem.** We need to walk the list in fixed-size chunks of `k` nodes, reverse each chunk that is exactly `k` nodes long, and splice the reversed chunk back into the list so it connects correctly to what comes before and after it. Any trailing chunk shorter than `k` must be left untouched — which means we cannot start reversing a group blindly; we first have to confirm `k` nodes actually exist from the current position.

**Why a dummy node helps.** The very first group's reversal changes what the "head" of the whole list is (e.g., in example 2, the new head becomes node `3`, not node `1`). Rather than special-casing "is this the first group," we prepend a dummy node before the real head. Then every group — including the first — has a well-defined "node before the group" (`groupPrev`) whose `next` pointer needs to be rewired to the new start of that group after reversal. At the end, `dummy.next` is simply the answer.

**The per-group algorithm.** Maintain `groupPrev`, initially the dummy node.

1. **Look ahead `k` steps** from `groupPrev` to find the `k`-th node of the next group (call it `kth`). Walk `k` steps; if we fall off the end (hit `nullptr`) before reaching it, fewer than `k` nodes remain — stop entirely and leave the remainder as-is.
2. If `kth` exists, record `groupNext = kth->next` — the node immediately after this group, which the reversed group must reconnect to.
3. **Reverse exactly this group in place**, using the standard three-pointer in-place reversal (`prev`, `curr`, `tmp`), starting `curr` at `groupPrev->next` and stopping once `curr` reaches `groupNext` (so we never touch nodes outside this group).
4. **Reconnect:** before reversing, `groupPrev->next` pointed at the group's original first node — save that pointer (it is now the group's *tail* after reversal). After reversing, set `groupPrev->next = kth` (the group's original last node is now its head), and advance `groupPrev` to the saved old-first-node (the group's new tail), ready to anchor the next group.
5. Repeat from step 1 using the new `groupPrev`, until step 1 finds fewer than `k` nodes left.

**Why this is correct.** Each iteration only ever reverses a self-contained run of exactly `k` nodes whose boundaries (`groupPrev` and `groupNext`) are pointers *outside* that run, so reversing the internal links never risks losing track of the rest of the list — `groupNext` is captured before any pointer inside the group is touched. The look-ahead in step 1 guarantees we never reverse a short trailing group, satisfying the "leave leftovers as-is" rule exactly.

**Complexity.** Let `n` be the number of nodes. Every node is visited at most twice per group it belongs to — once during the look-ahead walk, once during the reversal — and each node belongs to exactly one group, so total work is `O(n)` time. We only ever hold a constant number of pointers (`groupPrev`, `kth`, `groupNext`, `prev`, `curr`, `tmp`), so space is `O(1)`, satisfying the follow-up constraint.

### C++ Code

```cpp
#include <iostream>
using namespace std;

struct ListNode {
    int val;
    ListNode* next;
    ListNode(int x) : val(x), next(nullptr) {}
};

class Solution {
public:
    ListNode* reverseKGroup(ListNode* head, int k) {
        ListNode dummy(0);
        dummy.next = head;
        ListNode* groupPrev = &dummy;

        while (true) {
            // Look ahead k nodes from groupPrev to find this group's last node.
            ListNode* kth = groupPrev;
            for (int i = 0; i < k && kth != nullptr; i++) {
                kth = kth->next;
            }
            // Fewer than k nodes remain -- leave the rest untouched.
            if (kth == nullptr) break;

            ListNode* groupNext = kth->next; // first node AFTER this group

            // Reverse the group [groupPrev->next ... kth] in place.
            ListNode* prev = groupNext;
            ListNode* curr = groupPrev->next;
            while (curr != groupNext) {
                ListNode* tmp = curr->next;
                curr->next = prev;
                prev = curr;
                curr = tmp;
            }

            // groupPrev->next still points at the group's ORIGINAL first node,
            // which is now the group's new tail after reversal.
            ListNode* newTail = groupPrev->next;
            groupPrev->next = kth;   // kth was the original last node, now the new head
            groupPrev = newTail;     // anchor for the next group
        }

        return dummy.next;
    }
};
```

## CS Fundamentals

### 1. Operating Systems (Conceptual/Definition)

What are the four necessary conditions (the Coffman conditions) for a deadlock to occur between processes competing for resources? Explain what each one means, and describe one practical strategy operating systems use to prevent deadlock by breaking just one of them.

**Answer:**

A **deadlock** is a state where a set of processes are each waiting for a resource held by another process in the same set, so none of them can ever proceed. This can only happen if **all four** of the following hold simultaneously — break any one of them, and deadlock becomes impossible:

1. **Mutual exclusion.** At least one resource must be held in a non-shareable mode — only one process can use it at a time (e.g., a single printer, a lock on a database row).
2. **Hold and wait.** A process is currently holding at least one resource while simultaneously waiting to acquire additional resources that are held by others.
3. **No preemption.** Resources cannot be forcibly taken away from a process; they can only be released voluntarily by the process holding them once it finishes using them.
4. **Circular wait.** There exists a cycle of processes `P1, P2, ..., Pn` where `P1` waits for a resource held by `P2`, `P2` waits for one held by `P3`, and so on, until `Pn` waits for one held by `P1` — closing the loop.

**A concrete example:** Process A holds Lock 1 and wants Lock 2; Process B holds Lock 2 and wants Lock 1. All four conditions hold (locks are exclusive, both processes hold-and-wait, neither lock can be preempted, and A→B→A forms a cycle), so neither process ever proceeds.

**One real prevention strategy — breaking circular wait via resource ordering.** Impose a global total order on all lockable resources (e.g., number every lock, or order them alphabetically by name), and require every process to acquire locks **only in increasing order**. In the example above, if both Lock 1 and Lock 2 must always be acquired in the order "Lock 1 before Lock 2," then Process B could never be holding Lock 2 while waiting for Lock 1 — it would have had to acquire Lock 1 first. This makes a circular wait graph structurally impossible, since a cycle would require some process to acquire a lower-numbered lock while already holding a higher-numbered one, which the ordering rule forbids outright.

This is why, in practice, code review for multi-lock systems often explicitly calls out "always acquire the row lock before the table lock" (or similar) — it's this exact deadlock-prevention technique being applied by convention.

### 2. DBMS (Scenario/Applied)

A `users` table has 10 million rows. A query like `SELECT * FROM users WHERE email = 'alice@example.com'` currently takes several seconds. Explain why this happens on an unindexed column, how adding an index fixes it, and what it costs you to add that index.

**Answer:**

**Why it's slow without an index:** with no index on `email`, the database has no way to know *where* a row with that email might live on disk, so it must perform a **full table scan** — reading every single one of the 10 million rows (or at least every row until it finds matches, and since `email` isn't guaranteed unique at the engine level unless constrained, it typically has to scan the *whole* table to be sure it found all matches) and comparing each one's `email` against the target value. This is `O(n)` I/O and comparison work relative to table size, and at 10 million rows, even a fast per-row check adds up to real seconds of wall-clock time, especially if the table doesn't fully fit in memory and pages must be read from disk.

**How an index fixes it:** an index (typically a **B-tree** for equality/range queries like this) is a separate, sorted structure that maps column values to the physical location of the rows containing them. With a B-tree index on `email`, looking up `'alice@example.com'` becomes a tree traversal — at each node, the engine compares the target value and follows one of a small number of child pointers, narrowing the search space by a large factor at each level. For 10 million rows, a balanced B-tree has a height of roughly `log(n)` ≈ 23-24 levels (with a high branching factor, often far fewer in practice, typically 3-4 disk reads), so the lookup touches a handful of pages instead of the entire table — turning an `O(n)` scan into an `O(log n)` lookup.

**What it costs you — the trade-offs are real, not free:**
- **Write overhead.** Every `INSERT`, `UPDATE` (of the indexed column), or `DELETE` must now also update the index structure to keep it consistent, not just the base table. On a write-heavy table with many indexes, this can noticeably slow down writes.
- **Storage overhead.** The index itself is additional data stored on disk (and often partially cached in memory) — for a large table, a single index can add a meaningful fraction of the base table's size.
- **Diminishing or negative returns on low-selectivity columns.** Indexing a column where most rows share only a few distinct values (e.g., a `status` column with only "active"/"inactive") often doesn't help, because the query planner may still find it cheaper to scan the table than to jump around the index and then fetch rows — so indexes should be added based on actual query patterns (what you filter/join/sort on frequently), not "index everything just in case."

In this scenario specifically, since `email` is almost certainly queried by exact match very often (logins, lookups) and has high selectivity (nearly every value is unique), the write/storage cost is well worth paying — but the general principle is that every index is a deliberate trade of write cost and storage for read speed, decided per-column based on how it's actually queried.

### 3. OOP (Comparison)

Compare **composition** and **inheritance** as ways to reuse code between classes. What does each one actually model, and why does the common advice "favor composition over inheritance" exist?

**Answer:**

Both let one class reuse behavior defined in another, but they model fundamentally different relationships and create different kinds of coupling.

**Inheritance** models an **"is-a"** relationship: a subclass *is a* specialized version of its superclass, and it reuses code by extending it — inheriting the superclass's fields and methods directly, and optionally overriding some of them. The relationship is fixed at compile time (in most statically-typed languages) and is **transparent but rigid**: the subclass is bound to exactly one superclass's implementation, and any change to the superclass's internals can silently ripple into every subclass that depends on it (the classic "fragile base class" problem).

**Composition** models a **"has-a"** relationship: a class reuses behavior by *holding a reference* to an instance of another class and delegating to it, rather than becoming that class. The composed object is typically swappable at runtime (e.g., via dependency injection), and the containing class only depends on the composed object's **public interface**, not its internals.

| Aspect | Inheritance | Composition |
| --- | --- | --- |
| Relationship modeled | "is-a" | "has-a" / "uses-a" |
| Coupling | Tight — bound to superclass's implementation | Loose — depends only on the held object's interface |
| Flexibility | Fixed at compile time (single superclass, typically) | Can swap the held object at runtime |
| Encapsulation risk | Can leak superclass internals into subclasses | Internals of the composed object stay hidden |
| Multiple behaviors | Awkward (most OOP languages: one superclass only) | Easy — hold as many composed objects as needed |

**Why "favor composition over inheritance" is common advice:** inheritance hierarchies tend to become brittle as a codebase grows, for two concrete reasons. First, **deep hierarchies amplify the fragile base class problem** — a change meant to fix or improve the base class can silently break several generations of subclasses that depended on its exact prior behavior, even if they never directly touch the changed code. Second, inheritance **locks in a single-axis classification**: if a `Bird` class has subclasses `FlyingBird` and `SwimmingBird`, a penguin (swims, doesn't fly) and a duck (does both) immediately expose that class-based "is-a" trees can't cleanly express combinations of independent behaviors.

Composition solves both: a `Duck` class can simply *hold* a `FlyBehavior` object and a `SwimBehavior` object (the classic Strategy pattern), mixing independent capabilities freely and letting each one change without touching the others. This is precisely why modern API design often favors small interfaces plus composition (sometimes summarized as "program to an interface, not an implementation") over deep class hierarchies — it keeps classes decoupled from each other's internal implementation details, favoring assembling behavior from interchangeable parts.

This doesn't mean inheritance is wrong — it's still the right tool when there's a genuine, stable "is-a" relationship with shared implementation that truly belongs to every subtype (e.g., a UI framework's base `Widget` class providing common layout machinery to every concrete widget). The advice is about defaulting to composition when the relationship is actually "uses a capability" rather than "fundamentally is a more specific version of," which is the more common case in practice and the one most often modeled wrong.
