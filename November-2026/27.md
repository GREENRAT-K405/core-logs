### Question: Candy (Arrays — Hard)

There are `n` children standing in a line, each assigned a rating value given in the integer array `ratings` (0-indexed). You must distribute candies to the children subject to the following rules:

- Every child must receive at least one candy.
- Any child with a strictly higher rating than an immediate neighbor must receive more candies than that neighbor. (Children with equal ratings have no ordering requirement between them — either can have more, fewer, or the same.)

Return the **minimum total number of candies** required to satisfy all children.

**Input format:** an integer array `ratings` of length `n`.
**Output format:** a single integer, the minimum total candies.

**Example 1:**
```
Input:  ratings = [1,0,2]
Output: 5
Explanation: candies = [2,1,2]. Child 0 (rating 1) > child 1 (rating 0) -> needs more than child 1.
             Child 2 (rating 2) > child 1 (rating 0) -> needs more than child 1. Total = 2+1+2 = 5.
```

**Example 2:**
```
Input:  ratings = [1,2,2]
Output: 4
Explanation: candies = [1,2,1]. Child 1 (rating 2) > child 0 (rating 1) -> needs more than child 0.
             Child 1 and child 2 have equal ratings (2 and 2), so no constraint forces child 2's
             candies to relate to child 1's; giving child 2 just 1 candy is valid and minimal.
             Total = 1+2+1 = 4.
```

**Example 3:**
```
Input:  ratings = [1,3,2,2,1]
Output: 7
Explanation: candies = [1,2,1,2,1]. Total = 1+2+1+2+1 = 7.
```

**Constraints:**
- `n == ratings.length`
- `1 <= n <= 2 * 10^4`
- `0 <= ratings[i] <= 2 * 10^4`

### Step-by-Step Walkthrough

**Why a single left-to-right (or right-to-left) pass isn't enough.** A greedy pass that only looks at the left neighbor ("if `ratings[i] > ratings[i-1]`, give one more candy than the left neighbor") correctly satisfies every *upward* slope read left-to-right, but it says nothing about a *downward* slope going left-to-right (which is an *upward* slope read right-to-left). For `ratings = [1,3,2,2,1]`, a left-to-right-only pass gives `[1,2,1,1,1]` — but that violates the rule between child 2 (rating 2) and child 3 (rating 2, fine) and more importantly between child 1 (rating 3) and child 2 (rating 2): child 1 *is* satisfied (2>1), but we never checked that child 2's rating 2 vs child 3's rating 2 and child 3 vs child 4 (rating 1) is fine, while the real problem is the falling run 3→2→2→1 isn't captured going left to right at all for the 2→1 edge needing child 3 > child 4, which a left-only pass does catch, but a falling run from a peak isn't bounded correctly in general. The clean fix is to require **both directions independently** and combine with a max.

**The two-pass greedy algorithm:**
1. Initialize an array `candies` of length `n`, all set to `1` (everyone gets the mandatory minimum).
2. **Left-to-right pass:** for `i` from `1` to `n-1`, if `ratings[i] > ratings[i-1]`, set `candies[i] = candies[i-1] + 1`. This guarantees every rising edge (scanned left to right) is satisfied: a strictly higher rating than the left neighbor gets strictly more candies than that neighbor.
3. **Right-to-left pass:** for `i` from `n-2` down to `0`, if `ratings[i] > ratings[i+1]`, set `candies[i] = max(candies[i], candies[i+1] + 1)`. This guarantees every falling edge (scanned left to right, i.e. a rise scanned right to left) is also satisfied, *without undoing* what the first pass already guaranteed — which is exactly why we take `max` instead of overwriting.

**Why taking the max of both passes is correct and minimal:** each pass independently computes the minimum candies needed to satisfy the constraints *in one direction*. A given child `i` might be forced up by its left neighbor (needs `candies[i-1]+1`) and independently forced up by its right neighbor (needs `candies[i+1]+1`); it must satisfy both simultaneously, so it needs at least the max of the two. Taking the max of the two single-direction passes gives, for every child, exactly the smallest value that satisfies both of its active constraints — and summing all of them gives the smallest valid total, since every child's value is already at its individual floor.

**Trace on Example 3** (`ratings = [1,3,2,2,1]`):
- Left pass: start `[1,1,1,1,1]`. `i=1`: `3>1` → `candies[1]=2`. `i=2`: `2>3`? no → stays `1`. `i=3`: `2>2`? no → stays `1`. `i=4`: `1>2`? no → stays `1`. Result: `[1,2,1,1,1]`.
- Right pass: `i=3`: `ratings[3]=2 > ratings[4]=1` → `candies[3] = max(1, candies[4]+1) = max(1,2) = 2`. `i=2`: `ratings[2]=2 > ratings[3]=2`? no (not strict) → unchanged, `1`. `i=1`: `ratings[1]=3 > ratings[2]=2` → `candies[1] = max(2, candies[2]+1) = max(2,2) = 2`. `i=0`: `ratings[0]=1 > ratings[1]=3`? no → unchanged, `1`.
- Final: `[1,2,1,2,1]`, sum `= 7`. Matches the expected output.

**Complexity analysis:**
- Time: `O(n)` — two linear passes over the array.
- Space: `O(n)` for the `candies` array. (This can be reduced to `O(1)` extra space with a more intricate single-pass "slope counting" trick that tracks the length of the current increasing/decreasing run, but the two-pass version is the clearer and standard approach and is already optimal in time.)

### C++ Code

```cpp
#include <vector>
#include <algorithm>
using namespace std;

class Solution {
public:
    int candy(vector<int>& ratings) {
        int n = ratings.size();
        if (n <= 1) return n;

        // Everyone starts with the mandatory minimum of 1 candy.
        vector<int> candies(n, 1);

        // Left-to-right pass: satisfy every rising edge (ratings[i] > ratings[i-1]).
        for (int i = 1; i < n; ++i) {
            if (ratings[i] > ratings[i - 1]) {
                candies[i] = candies[i - 1] + 1;
            }
        }

        // Right-to-left pass: satisfy every falling edge (ratings[i] > ratings[i+1]),
        // combining with the left pass via max so neither direction's guarantee is undone.
        for (int i = n - 2; i >= 0; --i) {
            if (ratings[i] > ratings[i + 1]) {
                candies[i] = max(candies[i], candies[i + 1] + 1);
            }
        }

        int total = 0;
        for (int c : candies) total += c;
        return total;
    }
};
```

### 1. OOP (Conceptual/Definition)

What is polymorphism in object-oriented programming, and what is the difference between its two common forms — compile-time (static) polymorphism and runtime (dynamic) polymorphism? Give a C++-flavored example of each.

**Answer:**

**Polymorphism** ("many forms") is the ability for the same interface — a function name, operator, or method call — to behave differently depending on the type or number of arguments it's invoked with, or on the actual runtime type of the object it's invoked on. It lets calling code be written generically against an interface, without needing to know the concrete type it will ultimately operate on.

**Compile-time (static) polymorphism** is resolved by the compiler before the program runs, based purely on the static information available at the call site (argument types/count, or the declared type of an expression). No runtime decision is involved — the compiler picks exactly one concrete function to call and bakes that choice into the generated code.
- **Function/operator overloading**: multiple functions share a name but differ in parameter types or count; the compiler picks the matching one based on the arguments at the call site.
  ```cpp
  void print(int x);
  void print(const std::string& x);
  print(5);        // compiler binds this to print(int) at compile time
  print("hello");  // compiler binds this to print(const string&) at compile time
  ```
- **Templates/generics** are also a form of compile-time polymorphism: the compiler generates a separate concrete function or class for each type it's instantiated with.

**Runtime (dynamic) polymorphism** is resolved while the program is running, based on the *actual* type of the object behind a pointer or reference — not the declared/static type of that pointer or reference. In C++ this requires `virtual` functions and is implemented via a vtable (virtual function table): each object of a polymorphic class carries a hidden pointer to a table of function pointers specific to its real type, and a virtual call is dispatched through that table at runtime.
  ```cpp
  struct Shape {
      virtual double area() const = 0;   // virtual -> dispatched at runtime
      virtual ~Shape() = default;
  };
  struct Circle : Shape {
      double r;
      double area() const override { return 3.14159 * r * r; }
  };
  struct Square : Shape {
      double s;
      double area() const override { return s * s; }
  };

  void printArea(const Shape& shape) {
      std::cout << shape.area();   // which area() runs is decided at runtime,
                                    // based on whether 'shape' is really a Circle or a Square
  }
  ```

**The key difference:** static polymorphism asks "which function matches these argument types?" and answers it once, at compile time, with zero runtime overhead (and in fact enables inlining). Dynamic polymorphism asks "what is the real type of the object this reference/pointer currently points to?" and answers it every time the call executes, via an indirect jump through the vtable — a small but nonzero runtime cost, in exchange for letting code written against a base-class interface work correctly on any derived type, including ones that didn't exist yet when that code was compiled (e.g. a new `Shape` subclass added in a plugin, with no need to recompile `printArea`).

### 2. Computer Architecture (Scenario/Applied)

A 5-stage pipelined CPU (Fetch, Decode, Execute, Memory, Writeback) executes this instruction sequence:
```
I1: ADD R1, R2, R3      ; R1 = R2 + R3
I2: SUB R4, R1, R5      ; R4 = R1 - R5   (uses R1 from I1)
I3: MUL R6, R7, R8      ; R6 = R7 * R8   (independent of I1, I2)
```
If the pipeline has no special handling, what problem occurs when `I2` tries to read `R1` in its Decode stage, and why? Name the hazard, and describe two different ways a real pipeline can resolve it.

**Answer:**

**The hazard:** this is a **data hazard**, specifically a **Read-After-Write (RAW)** hazard. `I1` doesn't compute `R1`'s new value until it finishes its **Execute** stage (and the value isn't actually stored back into the register file until **Writeback**). But with instructions issued one cycle apart in a simple pipeline, `I2` reaches its **Decode** stage (where operands are normally read from the register file) while `I1` is still in **Execute** — i.e., `I2` tries to read `R1` *before* `I1` has produced or written the correct value. Without any handling, `I2` would read `R1`'s *stale* (pre-`ADD`) value, silently computing the wrong result for `R4`. This happens specifically because `I2` is **data-dependent** on `I1` (it reads a register `I1` writes) and the two instructions are close together in the pipeline — `I3` has no such dependency on `I1` or `I2`, so it causes no hazard here.

**Resolution 1 — Operand forwarding / bypassing (the common hardware fix):** add extra data paths that route a value directly from the output of an earlier pipeline stage (e.g., the ALU output at the end of `I1`'s Execute stage) straight into the input of a later stage that needs it (e.g., `I2`'s Execute stage), bypassing the normal register-file read/write path entirely. Concretely, hardware detects that `I2` needs `R1` and that `I1` (still in flight) will produce it, and feeds `I1`'s ALU result directly into `I2`'s ALU input at the moment `I2` reaches Execute — no stall needed, because by the time `I2` actually *needs* the value (at Execute, one stage later than Decode), `I1` has already produced it.

**Resolution 2 — Pipeline stalling / bubble insertion (the simpler fallback):** if forwarding isn't available for a particular hazard shape (e.g., the dependent instruction needs the value even earlier than forwarding can deliver it, such as a load whose result isn't ready until Memory), the pipeline control logic detects the dependency and **stalls** the dependent instruction (and everything behind it) by inserting one or more "bubble" cycles — effectively `NOP`s — until the needed value is available, then lets it proceed. This is correct but costs throughput: every stall cycle is a wasted pipeline slot. Compilers can also help by **instruction scheduling** — reordering independent instructions like `I3` into the gap so the hardware has useful work to do during what would otherwise be a stall, though in this example an out-of-order-capable compiler/hardware could move `I3` between `I1` and `I2` since `I3` has no dependency on either.

In practice, real pipelined CPUs rely primarily on forwarding (cheap, fast, handles the common case) and fall back to stalling only for hazard shapes forwarding can't cover (most notably load-use hazards), which is exactly why pipeline diagrams in textbooks usually show a one-cycle stall specifically after loads but not after simple ALU operations like `ADD`.

### 3. System Design Basics (Conceptual/Definition)

What does the CAP theorem state about distributed data stores, and what does it actually force a system to choose between in practice when a network partition occurs?

**Answer:**

The **CAP theorem** (Eric Brewer) states that a distributed data store cannot simultaneously guarantee all three of the following properties when a network partition is present — it can provide at most two of three:
- **Consistency (C):** every read receives the most recent write, or an error — all nodes see the same data at the same time, as if there were only one copy.
- **Availability (A):** every request to a non-failing node receives a (non-error) response, though not necessarily the most recent data.
- **Partition tolerance (P):** the system continues to operate despite an arbitrary number of messages being dropped or delayed between nodes (i.e., the network splits the cluster into groups that can't talk to each other).

**Why it's really a C-vs-A choice in practice:** in any real distributed system that spans more than one machine (or data center), network partitions are a fact of life you cannot opt out of — cables get cut, switches fail, packets get dropped — so partition tolerance (P) is effectively mandatory, not optional. That means the actual design decision CAP forces is: **when a partition happens, does the system favor Consistency or Availability?**
- **Choosing C over A (a "CP" system):** when nodes can't communicate and can't be sure they have the latest data, the system refuses to serve some requests (returns an error or blocks) rather than risk serving stale or conflicting data. Example: a system requiring a quorum write/read (like many consensus-based stores, e.g. etcd, or a strongly consistent configuration store) will reject a write/read on the minority side of a partition rather than risk inconsistency.
- **Choosing A over C (an "AP" system):** the system keeps responding to every node's requests even during a partition, accepting that different nodes might temporarily return different (stale or divergent) data, which must be reconciled later (e.g., via last-write-wins, vector clocks, or application-level conflict resolution). Example: Cassandra or DynamoDB in their default configurations favor availability, serving reads/writes on both sides of a partition and resolving conflicts after the partition heals.

**Why this matters when designing a system:** CAP only applies *during* an actual partition — when the network is healthy, a well-designed system can and should offer both strong consistency and high availability simultaneously (this nuance is sometimes called PACELC, which also asks what you trade off between latency and consistency even when there's *no* partition). The practical takeaway for system design interviews and real architecture decisions is: identify whether your use case tolerates serving slightly stale data for better uptime (e.g., a social media feed, a shopping cart) — lean AP — or whether it absolutely cannot tolerate inconsistency even at the cost of refusing requests (e.g., a bank ledger, a leader-election/config store) — lean CP — and choose your database/replication strategy accordingly, rather than assuming any single store gives you "the best of all three" unconditionally.
