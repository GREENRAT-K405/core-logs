## DSA

### Question: LFU Cache (Hashing/Maps — Hard)

**Problem Statement**

Design and implement a data structure for a **Least Frequently Used (LFU)** cache with a fixed `capacity`. It must support two operations, both in **O(1)** amortized time:

- `get(key)`: Return the value of `key` if it exists in the cache, otherwise return `-1`. A successful `get` counts as a "use" of that key.
- `put(key, value)`: Update the value of `key` if it exists, otherwise insert `(key, value)`. If the number of keys exceeds `capacity` after insertion, evict the **least frequently used** key. If there is a tie in frequency, evict the **least recently used** key among that tied group. A `put` on an existing key also counts as a "use" of that key.

**Input/Output Format**

- `LFUCache(int capacity)` — constructor, `1 <= capacity <= 10^4`.
- `int get(int key)` — returns the cached value or `-1`.
- `void put(int key, int value)` — inserts or updates a key.
- Keys and values fit in `int`; up to `10^5` calls total across `get`/`put`.

**Examples**

1.
```
LFUCache lfu = new LFUCache(2);
lfu.put(1, 1);   // cache={1:1}, freq(1)=1
lfu.put(2, 2);   // cache={1:1, 2:2}, freq(1)=1, freq(2)=1
lfu.get(1);      // returns 1, freq(1)=2
lfu.put(3, 3);   // capacity exceeded; key 2 has the lowest freq (1) -> evict 2
                 // cache={1:1, 3:3}
lfu.get(2);      // returns -1 (evicted)
lfu.get(3);      // returns 3, freq(3)=2
lfu.put(4, 4);   // capacity exceeded; freq(1)=freq(3)=2 (tie) -> evict the
                 // less recently used of the two, which is 1 -> evict 1
                 // cache={3:3, 4:4}
lfu.get(1);      // returns -1 (evicted)
lfu.get(3);      // returns 3, freq(3)=3
lfu.get(4);      // returns 4, freq(4)=2
```
Full output sequence: `[null,null,null,1,null,-1,3,null,-1,3,4]`

2.
```
LFUCache lfu = new LFUCache(1);
lfu.put(1, 10);  // cache={1:10}
lfu.get(1);      // returns 10
lfu.put(2, 20);  // capacity 1, key1 is the only (and therefore least frequent)
                 // key -> evict 1. cache={2:20}
lfu.get(1);      // returns -1
lfu.get(2);      // returns 20
```

3.
```
LFUCache lfu = new LFUCache(0);
lfu.put(1, 1);   // capacity 0: nothing can ever be stored
lfu.get(1);      // returns -1
```

**Constraints**

- `0 <= capacity <= 10^4`
- `0 <= key, value <= 10^9`
- At most `2 * 10^5` calls to `get` and `put` combined.
- Both operations must run in O(1) amortized time.

### Step-by-Step Walkthrough

**Why a single hashmap isn't enough.** A plain `unordered_map<key, value>` gives O(1) get/put, but it has no notion of "frequency" or "which key to evict." We need to track, for every key: its value, how many times it has been used, and — among keys tied on frequency — which one was used longest ago. All of that has to be updated in O(1) whenever a key is touched.

**The standard trick: bucket keys by frequency, and keep insertion order inside each bucket.**

- `keyTable: key -> {value, freq}` — O(1) lookup of a key's current value and frequency.
- `freqTable: freq -> doubly linked list of keys` — all keys currently at frequency `freq`, ordered so the **front** is the least-recently-used key at that frequency and the **back** is the most-recently-used. A `list<int>` gives O(1) push/erase at any position (given an iterator).
- `keyIter: key -> iterator into the list inside freqTable[keyTable[key].freq]` — lets us erase a specific key from its current frequency bucket in O(1), without scanning the list.
- `minFreq` — the smallest frequency that currently has at least one key. This is the only thing we need to find the global eviction candidate: `freqTable[minFreq].front()`.

**`touch(key)` (shared by get and put-on-existing-key).** Whenever a key is used:
1. Look up its current `freq`, erase it from `freqTable[freq]` using the stored iterator (O(1)).
2. If that bucket is now empty, delete the bucket; if `freq` was `minFreq`, every key's frequency is now `>= freq + 1`, so bump `minFreq` to `freq + 1`.
3. Push the key onto the **back** of `freqTable[freq + 1]` (marking it as the most-recently-used at the new frequency) and store the new iterator. Update `keyTable[key].freq`.

This keeps the invariant that within any frequency bucket, list order = usage order (oldest first), and `minFreq` always points at a non-empty bucket (or is stale only in a direction that never causes a wrong read, since it's only consulted on eviction and always re-derived on insert).

**`get(key)`**: if absent, return `-1`. Otherwise read the value, call `touch(key)`, return the value.

**`put(key, value)`**:
- If `capacity == 0`, no-op.
- If the key already exists: overwrite its value, call `touch(key)` (a put counts as a use), done.
- If the key is new and the cache is at capacity: evict `freqTable[minFreq].front()` — the least frequently used key, and among ties, the least recently used (because it's been sitting at the front of its bucket the longest). Remove it from `keyTable` and `keyIter` too.
- Insert the new key with `freq = 1`: push it to the back of `freqTable[1]`, record the iterator, set `keyTable[key] = {value, 1}`, and set `minFreq = 1` (a brand-new key always has the minimum possible frequency, so this is always correct after an insert).

**Why this is O(1) amortized.** Every step — hashmap lookup/insert, list push/erase at a known iterator, incrementing/checking `minFreq` — is O(1). No operation ever scans a list or rebuilds a structure; the `minFreq` variable avoids ever searching for the minimum frequency.

**Complexity.**
- Time: O(1) amortized per `get` and `put`.
- Space: O(capacity) — at most `capacity` entries across `keyTable`, `keyIter`, and the combined lists in `freqTable`.

### C++ Code

```cpp
#include <unordered_map>
#include <list>
using namespace std;

class LFUCache {
public:
    LFUCache(int capacity) : capacity(capacity), minFreq(0) {}

    int get(int key) {
        auto it = keyTable.find(key);
        if (it == keyTable.end()) return -1;
        int value = it->second.first;
        touch(key);
        return value;
    }

    void put(int key, int value) {
        if (capacity <= 0) return;

        auto it = keyTable.find(key);
        if (it != keyTable.end()) {
            it->second.first = value; // update value
            touch(key);               // counts as a use
            return;
        }

        if ((int)keyTable.size() >= capacity) {
            // Evict least frequently used; ties broken by least recently used,
            // which is always the front of the minFreq bucket.
            int evictKey = freqTable[minFreq].front();
            freqTable[minFreq].pop_front();
            if (freqTable[minFreq].empty()) freqTable.erase(minFreq);
            keyIter.erase(evictKey);
            keyTable.erase(evictKey);
        }

        // Brand-new key always starts at frequency 1.
        keyTable[key] = {value, 1};
        freqTable[1].push_back(key);
        keyIter[key] = --freqTable[1].end();
        minFreq = 1;
    }

private:
    int capacity, minFreq;
    unordered_map<int, pair<int, int>> keyTable;      // key -> {value, freq}
    unordered_map<int, list<int>> freqTable;          // freq -> keys, front = LRU, back = MRU
    unordered_map<int, list<int>::iterator> keyIter;  // key -> its iterator in freqTable[freq]

    // Shared by get() and put() on an existing key: bumps a key's frequency by 1
    // and moves it to the back ("most recently used") of the new frequency bucket.
    void touch(int key) {
        int freq = keyTable[key].second;

        freqTable[freq].erase(keyIter[key]);
        if (freqTable[freq].empty()) {
            freqTable.erase(freq);
            if (minFreq == freq) minFreq++;
        }

        int newFreq = freq + 1;
        keyTable[key].second = newFreq;
        freqTable[newFreq].push_back(key);
        keyIter[key] = --freqTable[newFreq].end();
    }
};
```

### 1. OOP (Conceptual)

What does encapsulation actually mean in object-oriented design, and why does mechanically adding a public getter and setter for every private field defeat its purpose?

**Answer:**

**What encapsulation means.** Encapsulation is not "make fields private" — that's just the mechanism. The actual goal is **bundling state with the behavior that's allowed to change it, and hiding the internal representation so the object can enforce its own invariants.** The object, not the caller, is responsible for guaranteeing that its internal state is always valid. Callers interact only through a deliberately chosen public interface; everything else is free to change without breaking anyone who depends on the object.

**Why getter/setter-for-every-field defeats this.** Consider a `BankAccount` class with `private double balance;` plus `getBalance()` and `setBalance(double)`. This *looks* encapsulated — the field is private — but it isn't, in any meaningful sense:

- `setBalance()` lets any caller set the balance to `-500` or `NaN`. The class has handed back full, unchecked write access to its internal state through a one-line wrapper. The field might as well be public — the keyword `private` is providing a false sense of safety while the setter quietly reopens the exact same hole.
- The class never gets a chance to enforce its own invariant ("balance can't go negative," "a withdrawal larger than the balance must fail"). That logic has been pushed out to every caller, who now has to remember to check it themselves — and inevitably, some caller won't.
- It also locks in the representation. If later you want to track balance as cents (an `int`) instead of a `double` to avoid floating-point rounding bugs, every caller that used `setBalance(double)`/`getBalance()` as basically direct field access breaks, because they were never insulated from the internal representation in the first place.

**What proper encapsulation looks like instead:** expose behavior, not raw state access — `deposit(amount)`, `withdraw(amount)` (which can reject an invalid amount or insufficient funds and return/throw accordingly), and maybe a read-only `getBalance()` if read access is genuinely needed, but no generic `setBalance()`. The class is now the single place that can decide whether a mutation is valid, which is the entire point: **the object protects its own invariants**, instead of trusting every caller to do the right thing.

**The general principle:** a private field with a public getter and setter that just read/write it unconditionally is encapsulation in name only. Real encapsulation is judged by whether the object's invariants can *only* be violated by a bug inside the class itself — never by something a caller could legally do through the public interface.

### 2. DBMS (Comparison)

Compare clustered and non-clustered indexes: how the data is physically arranged in each case, what a lookup costs, and why a table can have only one clustered index but many non-clustered ones.

**Answer:**

**Clustered index.** The table's rows are physically **stored in the order of the index key** — the index *is* the data's physical layout, typically as the leaf level of a B+ tree where each leaf node contains the actual row (not a pointer to it). Think of a dictionary: the words themselves are physically sorted on the page; there's no separate "lookup table" pointing elsewhere.

- *Lookup cost:* a point lookup on the clustered key is a single B+ tree traversal straight to the row — O(log n) with no extra indirection. Range scans on the clustered key (`WHERE id BETWEEN 100 AND 200`) are extremely cheap, since matching rows are physically adjacent on disk — one sequential read of a contiguous block.
- *Why only one per table:* rows can only be sorted on disk in one physical order at a time. You cannot simultaneously store a table's rows sorted by `id` **and** sorted by `email` — those are two different orderings of the same physical pages. So a table gets exactly one clustered index, usually on the primary key.

**Non-clustered index.** A **separate structure** from the table's physical row storage: its own B+ tree, where the leaf level holds the index key plus a pointer (a row ID, or the clustered key's value) back to where the actual row lives — not the row itself.

- *Lookup cost:* a point lookup is two steps — traverse the non-clustered index's tree to find the pointer (O(log n)), then follow that pointer to fetch the actual row from the table's physical storage (another lookup, sometimes called a "bookmark lookup"). This extra hop is why a non-clustered index lookup usually costs slightly more than a clustered one, and why queries that touch many non-indexed columns across many rows can get expensive (many separate row fetches) unless the index is "covering" (contains every column the query needs, so the second hop is skipped entirely).
- *Why a table can have many:* a non-clustered index is just extra metadata pointing at the table — it doesn't dictate physical row order, so you can build as many as you want (on `email`, on `created_at`, on `(last_name, first_name)`, etc.), each optimized for a different query pattern, at the cost of extra storage and slower writes (every index must be updated on every insert/update/delete).

**Putting it together:** pick the clustered index for the single access pattern that matters most — usually the primary key, or whatever column range-scans or sorts most often (e.g., a time-series table clustered on `timestamp`) — because it gets the cheapest possible lookups and the cheapest range scans. Layer non-clustered indexes on top for every other frequently filtered/sorted column, accepting the extra storage and the write-amplification cost (each one must be maintained on every write) in exchange for fast lookups on those columns too.

### 3. Computer Architecture (Scenario)

A program sums a large array of doubles sequentially (`for i in 0..n: sum += arr[i]`) and runs noticeably faster than a version that sums every 100th element instead (`for i in 0..n step 100: sum += arr[i]`) over a comparable total number of additions, even though both do roughly the same arithmetic work per element touched. Explain this in terms of cache behavior, referencing locality and cache line size.

**Answer:**

**Why the sequential version is fast: spatial locality.** A CPU cache doesn't fetch one value at a time from main memory — it fetches a whole **cache line** (commonly 64 bytes on modern x86/ARM chips) and stores that entire line in the cache. For a `double` (8 bytes), one 64-byte cache line holds **8 consecutive elements**.

When the loop reads `arr[0]`, the hardware pulls in the cache line covering `arr[0]` through `arr[7]` — one relatively expensive trip to main memory (on the order of 100+ cycles). But then `arr[1]` through `arr[7]` are **already sitting in the cache** from that same fetch, so each of those next 7 reads is a cache hit (a few cycles). Net effect: roughly 1 expensive memory fetch per 8 elements, not per element. This is **spatial locality**: accessing memory addresses near ones you've just accessed is cheap, because the hardware over-fetches in blocks precisely to exploit that pattern.

**Why the strided version is slow.** Stepping by 100 elements means stepping by `100 × 8 = 800` bytes — far more than one 64-byte cache line (which covers 8 elements). So almost every single access lands in a *different* cache line than the previous one, meaning almost every access is a fresh cache miss that pays full main-memory latency. The CPU is still fetching a 64-byte line each time, but it only uses **1 of the 8** doubles in that line before discarding it and fetching a completely different line for the next access — the other 7 elements the hardware paid to bring in are wasted bandwidth. Despite doing the "same" number of additions in both versions, the strided version pays close to the full memory-latency cost on nearly every single access, instead of amortizing one memory fetch across 8 useful elements.

**Temporal locality, for contrast.** The other half of locality — reusing the *same* address soon after accessing it (e.g., re-reading a loop counter or an accumulator every iteration) — benefits from a value staying resident in a register or L1 cache across repeated use. This particular example is dominated by spatial locality (new addresses, but nearby ones) rather than temporal locality (the same address again), since each element of `arr` is only touched once.

**The general principle, and why it matters for real code:** cache hardware is built on the assumption that programs exhibit locality — that memory accesses cluster in time (temporal) and in address space (spatial). Data structures and access patterns that honor that assumption (contiguous arrays scanned in order, row-major traversal matching a 2D array's storage layout, structure-of-arrays over array-of-structures when only one field is needed per pass) run dramatically faster than ones that don't, often by an order of magnitude, even though the CPU executes the "same" arithmetic — because the real bottleneck in memory-bound code is almost always *getting the data to the CPU*, not the arithmetic once it's there.
