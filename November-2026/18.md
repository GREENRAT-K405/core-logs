### Question: First Missing Positive (Arrays — Hard)

**Problem Statement**

Given an unsorted integer array `nums`, return the smallest missing positive integer. Your algorithm must run in O(n) time and use O(1) auxiliary space.

**Input/Output Format**

- Input: an array of integers `nums` (can include zero, negatives, duplicates, and values larger than the array length).
- Output: a single integer — the smallest positive integer not present in `nums`.

**Examples**

1. Input: `nums = [1,2,0]` → Output: `3` (1 and 2 are present, 3 is the smallest missing positive)
2. Input: `nums = [3,4,-1,1]` → Output: `2` (1 is present, 2 is missing)
3. Input: `nums = [7,8,9,11,12]` → Output: `1` (no positive integer in the array is 1)

**Constraints**

- `1 <= nums.length <= 10^5`
- `-2^31 <= nums[i] <= 2^31 - 1`
- Time: O(n). Space: O(1) extra (in-place modification of `nums` is allowed).

### Step-by-Step Walkthrough

**The obvious approach first.** Dump every value into a hash set, then probe `1, 2, 3, ...` until one isn't in the set. That's correct and O(n) time, but the hash set itself is O(n) extra space, which violates the constraint. The constraint is the whole point of the problem: can we get the hashing behavior *without* allocating a hash structure?

**The key bound.** For an array of length `n`, the answer is always somewhere in `[1, n+1]`. Why: there are only `n` slots, so at most `n` distinct values in `[1, n]` can be present. If all of `1..n` happen to be present, the answer is `n+1`; otherwise some value in `1..n` is missing and that's the answer. This means we never need to consider any value outside `[1, n]` — anything negative, zero, or greater than `n` is irrelevant noise we can ignore.

**Turning the array into its own hash set.** Since the answer only depends on which of `1..n` are present, we can use the array's own `n` slots as a presence table: slot `i` (0-indexed) is "home" for value `i+1`. We rearrange `nums` in place so that, as much as possible, `nums[i] == i+1`. Concretely:

1. For each index `i` from `0` to `n-1`: while `nums[i]` is in range `[1, n]` and it is not already sitting in its home slot (`nums[nums[i] - 1] != nums[i]`), swap `nums[i]` with `nums[nums[i] - 1]`.
   - The swap moves the value toward where it belongs. We keep swapping at position `i` (not just once) because the value swapped *into* `nums[i]` might itself need to move again.
   - The loop condition `nums[nums[i]-1] != nums[i]` is what prevents an infinite loop on duplicates: if the target slot already holds that exact value, there's nothing left to do.
2. After this pass, scan `i` from `0` to `n-1`: the first index where `nums[i] != i+1` tells us `i+1` is missing — return it.
3. If every slot matches (`nums[i] == i+1` for all `i`), every value `1..n` is present, so return `n+1`.

**Why it's correct.** Out-of-range values (≤0 or >n) are simply skipped by the while-condition and left wherever they land — they can never be a "home" value for any slot, so they don't interfere with the invariant we care about: by the end, slot `i` holds `i+1` if and only if `i+1` was present somewhere in the original array.

**Why it's O(n) despite the nested while loop.** Every swap places at least one value into its correct home slot permanently (a value never gets swapped out of a slot it already correctly occupies, because the while-condition stops exactly when that happens). Since there are only `n` slots, there can be at most `n` "successful placements" total across the entire outer loop — so the total number of swaps across all iterations is bounded by `n`. That makes the whole pass O(n) amortized, not O(n²).

**Complexity.**
- Time: O(n) amortized for the placement pass + O(n) for the final scan = O(n).
- Space: O(1) — only the input array is touched, no extra structures.

### C++ Code

```cpp
#include <vector>
#include <algorithm>
using namespace std;

int firstMissingPositive(vector<int>& nums) {
    int n = (int)nums.size();

    // Place each value v in [1, n] at index v-1, using the array
    // itself as an O(1)-space presence table.
    for (int i = 0; i < n; i++) {
        while (nums[i] > 0 && nums[i] <= n && nums[nums[i] - 1] != nums[i]) {
            swap(nums[i], nums[nums[i] - 1]);
        }
    }

    // First slot that doesn't hold its "home" value reveals the
    // smallest missing positive integer.
    for (int i = 0; i < n; i++) {
        if (nums[i] != i + 1) {
            return i + 1;
        }
    }

    // 1..n were all present, so the answer is just past the array.
    return n + 1;
}
```

Traced against the examples: `[1,2,0]` settles to `[1,2,0]` (0 is out of range and never moves), mismatch at index 2 → returns `3`. `[3,4,-1,1]` settles to `[1,-1,3,4]`, mismatch at index 1 → returns `2`. `[7,8,9,11,12]` has every value out of range `[1,5]`, so nothing moves and the first scan mismatch is at index 0 → returns `1`. All three match the expected output.

## CS Fundamentals

### 1. DBMS (Conceptual/Definition)

**Question:** What is a database index, how does it actually speed up lookups under the hood, and what does adding one cost you?

**Answer:**

A **database index** is an auxiliary data structure that stores a sorted (or otherwise searchable) copy of one or more columns' values together with a pointer back to the full row, so the engine can locate rows without scanning the entire table.

**Why it speeds things up.** Without an index, `WHERE email = 'x@y.com'` forces a **full table scan** — O(n) row-by-row checks. Most relational databases implement indexes as a **B+ tree**: a balanced, disk-friendly tree where every leaf is at the same depth and leaves are linked together for fast range scans. Looking up a key means descending from the root through a handful of internal nodes — each node fans out to dozens or hundreds of children because B+ trees are deliberately wide and shallow, matching how database pages are read from disk. That turns an O(n) scan into roughly O(log n) disk reads, and because the leaves are linked in sorted order, range queries (`BETWEEN`, `ORDER BY` on the indexed column) are nearly free too — a hash index, by contrast, gives O(1) equality lookups but can't do ranges at all, which is why B+ trees are the default for general-purpose indexes.

**What it costs.**
- **Write overhead.** Every `INSERT`, `UPDATE`, or `DELETE` that touches an indexed column must also update every index on that column, so write throughput drops as you add more indexes.
- **Storage.** An index duplicates the indexed columns (plus tree-internal bookkeeping), so it takes real disk space — sometimes comparable to the table itself.
- **Diminishing/negative returns on low-cardinality columns.** Indexing a boolean or a column with only a few distinct values usually doesn't help — the optimizer often decides a full scan is cheaper than the overhead of bouncing between the index and the table (a "bookmark lookup"), so it ignores the index entirely.

**Why it matters in practice:** indexing is a read/write trade-off, not a free win. The real skill is indexing the columns that actually appear in `WHERE`/`JOIN`/`ORDER BY` clauses on your hot queries, and no more — an over-indexed write-heavy table (e.g., an audit log) can be far slower than one with just the indexes it needs.

### 2. Computer Architecture (Scenario/Applied)

**Question:** You have a large 2D array `int matrix[4000][4000]` stored in row-major order (the default in C/C++). One version of a function sums every element by iterating `for row { for col { sum += matrix[row][col]; } }`; another sums it with the loops swapped — `for col { for row { sum += matrix[row][col]; } }`. Both visit every element exactly once and do the same arithmetic. Why does the first version typically run several times faster?

**Answer:**

This is a textbook demonstration of **spatial locality** and how it interacts with the **cache hierarchy**.

In row-major storage, `matrix[row][col]` and `matrix[row][col+1]` are adjacent in memory — an entire row is one contiguous block. The CPU doesn't fetch memory one `int` at a time; it fetches a whole **cache line** (typically 64 bytes, i.e. 16 `int`s on a 4-byte-int system) from main memory into cache on any access. The first loop order (`row` outer, `col` inner) walks memory **sequentially**: fetching `matrix[row][0]` pulls in `matrix[row][0..15]` for free, and the next 15 accesses are cache hits. This access pattern is also regular enough that the CPU's **hardware prefetcher** detects it and starts pulling in the *next* cache line before the program even asks for it, hiding most of the memory latency entirely.

The second loop order (`col` outer, `row` inner) walks **down a column** — each successive access (`matrix[0][col]`, `matrix[1][col]`, ...) jumps `4000 * 4` bytes ahead in memory, landing in a completely different cache line almost every single time. Each of those is effectively a **cache miss**, forcing a trip out to a slower cache level or main memory, and the stride pattern defeats the prefetcher, which is tuned for sequential or simple strided access, not a stride as large as an entire row. With a 4000×4000 matrix, that's 16 million mostly-missed accesses instead of mostly-hit ones.

Both versions do the *same number of arithmetic operations* and have the *same Big-O complexity* — this is purely a memory-access-pattern effect, invisible to algorithmic analysis but very visible in wall-clock time (often a 5-10x difference on real hardware). The general principle: **access memory in the order it's laid out**, and when you can't, consider restructuring the data (e.g., tiling/blocking in numerical code) so that the working set for each phase of computation fits in cache.

### 3. System Design Basics (Comparison)

**Question:** Compare vertical scaling and horizontal scaling as responses to a web service running out of capacity. What does each actually buy you, and what breaks or gets harder as a result?

**Answer:**

**Vertical scaling** ("scale up") means giving the *existing* machine more resources — more CPU cores, more RAM, faster disks — without changing the architecture. **Horizontal scaling** ("scale out") means adding *more machines* that each handle a slice of the load, coordinated behind a load balancer.

| | Vertical Scaling | Horizontal Scaling |
| --- | --- | --- |
| How it grows | Bigger single machine | More machines of the same (or similar) size |
| Code changes needed | Usually none | Often significant — app must tolerate running as many instances |
| Ceiling | Hard physical/cost ceiling (biggest machine money can buy) | Effectively unbounded — add more nodes |
| Failure characteristics | Single point of failure — that one machine dying takes everything down | Naturally redundant — one node dying can leave others serving traffic |
| Typical cost curve | Non-linear and steep near the top end (top-tier hardware is disproportionately expensive) | Roughly linear — each additional commodity node costs about the same |
| Operational complexity | Low — one machine to manage | Higher — load balancing, service discovery, distributed state |

**What breaks going horizontal.** The moment you have more than one instance, anything that assumed "one process, one memory space" stops working: **in-memory session state** needs to move to a shared store (Redis, a database) or be made sticky at the load balancer; a local on-disk cache becomes inconsistent across nodes; and any assumption of a single global counter or lock now needs a distributed mechanism. This is exactly why horizontal scaling pushes a design toward **statelessness** — keep the application servers interchangeable and push all durable/shared state into a database or cache tier that itself scales separately (often vertically for the primary, with read replicas for horizontal read scaling).

**The practical pattern.** Most real systems do both, at different tiers: scale the stateless web/application layer horizontally (cheap, resilient, and limited only by your wallet), while scaling the stateful datastore tier mostly vertically (because distributing state correctly — sharding, replication, consistency — is the hard part), adding horizontal read replicas or sharding only once a single database instance genuinely can't keep up. Vertical scaling is also the right *first* move in practice: it buys time with zero code changes while you design the horizontal path properly, rather than bolting on distributed-systems complexity under pressure.
