### Question: Kth Largest Element in an Array (Sorting/Searching — Medium)

**Problem Statement**

Given an integer array `nums` and an integer `k`, return the `k`-th largest element in the array. Note that this means the `k`-th largest element in **sorted order**, not the `k`-th distinct element — duplicates count by position.

**Input/Output Format**

- Input: an integer array `nums`, and an integer `k` with `1 <= k <= nums.length`.
- Output: a single integer, the `k`-th largest value in `nums`.

**Examples**

1. Input: `nums = [3,2,1,5,6,4]`, `k = 2` → Output: `5` (sorted descending: `[6,5,4,3,2,1]`, 2nd is `5`)
2. Input: `nums = [3,2,3,1,2,4,5,5,6]`, `k = 4` → Output: `4` (sorted descending: `[6,5,5,4,3,3,2,2,1]`, 4th is `4`)
3. Input: `nums = [1]`, `k = 1` → Output: `1`

**Constraints**

- `1 <= nums.length <= 10^5`
- `-10^4 <= nums[i] <= 10^4`
- `1 <= k <= nums.length`
- Expected average time better than a full O(n log n) sort.

### Step-by-Step Walkthrough

**The obvious approach first.** Sort `nums` in descending order and return `nums[k-1]`. Correct, but O(n log n) time — we do far more work than the question actually needs, since we only care about one position in the sorted order, not the full ordering.

**Key insight.** This is exactly the "select the element that would sit at a given rank" problem, which has a sub-sort solution: **Quickselect**. Finding the k-th largest is the same as finding the element at index `n - k` in ascending sorted order (or, equivalently, index `k - 1` from the largest side). Quickselect is quicksort's partition step, but after partitioning around a pivot we only ever recurse into the *one* side that contains the target rank — we never recurse into both sides, which is what drops the expected time from O(n log n) to O(n).

**The algorithm (ascending-index framing).** Let `target = n - k` (the 0-indexed position the k-th largest element occupies if the array were sorted ascending).

1. Pick a pivot (randomizing the choice avoids worst-case behavior on adversarial or already-sorted input).
2. Partition the current subarray `[lo, hi]` around the pivot using Lomuto or Hoare partitioning, so that everything `< pivot` ends up left of its final resting position `p`, and everything `>= pivot` ends up at or right of it (the exact scheme just needs to return the pivot's final index `p`).
3. Compare `p` to `target`:
   - If `p == target`, `nums[p]` is the answer — done.
   - If `target < p`, the answer lies in the left part — recurse (or loop) on `[lo, p-1]`.
   - If `target > p`, the answer lies in the right part — recurse (or loop) on `[p+1, hi]`.
4. Because we only ever continue into one side, each round processes a shrinking range until it collapses to the target index.

**Why it's correct.** Partitioning guarantees `nums[p]` is in its correct *final* sorted position relative to every other element in the current range — every element left of `p` is `<= nums[p]` and every element right of `p` is `>= nums[p]` (for Lomuto on `< pivot` / `>= pivot`). So if `target` falls exactly on `p`, we're done; if it falls to one side, the final answer is guaranteed to be somewhere in that side only, and nothing on the other side can affect it, so discarding it is safe.

**Complexity.**
- Time: O(n) expected — each partition step does O(range size) work, and with a random pivot the expected range size shrinks geometrically (roughly halving), giving `n + n/2 + n/4 + ... = O(n)` total. Worst case (always picking the smallest/largest element as pivot) degrades to O(n²), which is why pivot randomization matters in practice.
- Space: O(1) extra if partitioning is done in place iteratively; O(log n) expected / O(n) worst case if implemented recursively, due to the call stack.

An alternative, simpler-to-reason-about approach is a min-heap of size `k`: push elements, and whenever the heap exceeds size `k`, pop the smallest. After processing all elements, the heap's root is the answer. That's a guaranteed O(n log k) time, O(k) space — a safer worst case than quickselect, at the cost of a slightly worse average case. Quickselect is the better answer when asked for the best *average* performance; the heap is the better answer when asked for a guaranteed worst-case bound.

### C++ Code

```cpp
#include <vector>
#include <cstdlib>
using namespace std;

class Solution {
public:
    int findKthLargest(vector<int>& nums, int k) {
        int n = (int)nums.size();
        int target = n - k; // 0-indexed position in ascending sorted order
        int lo = 0, hi = n - 1;

        while (true) {
            int p = partition(nums, lo, hi);
            if (p == target) {
                return nums[p];
            } else if (target < p) {
                hi = p - 1; // answer is in the left part
            } else {
                lo = p + 1; // answer is in the right part
            }
        }
    }

private:
    // Lomuto partition: picks a random pivot, moves everything smaller
    // than it to the left, and returns the pivot's final index.
    int partition(vector<int>& nums, int lo, int hi) {
        int randIdx = lo + rand() % (hi - lo + 1);
        swap(nums[randIdx], nums[hi]); // move pivot to the end
        int pivot = nums[hi];

        int storeIdx = lo;
        for (int i = lo; i < hi; i++) {
            if (nums[i] < pivot) {
                swap(nums[i], nums[storeIdx]);
                storeIdx++;
            }
        }
        swap(nums[storeIdx], nums[hi]); // move pivot into its final spot
        return storeIdx;
    }
};
```

Checking against the examples: for `nums = [3,2,1,5,6,4]`, `k = 2`, `n = 6`, so `target = 4`. Quickselect converges on whichever index ends up holding `5` once partitioning settles everything relative to it — `5` is the 2nd largest, which sits at ascending index 4 in the fully sorted array `[1,2,3,4,5,6]`, matching `target`.

### 1. Operating Systems (Comparison)

What is the difference between a process and a thread? Specifically, what do threads of the same process share that separate processes do not, and why does that make context-switching between threads cheaper than between processes?

**Answer:**

A **process** is an independent, self-contained unit of execution: it owns its own virtual address space, its own set of file descriptors, and its own OS-level resources (heap, page tables, open handles). Two processes are isolated from each other by design — one process cannot directly read or corrupt another's memory, because each has its own address space mapped by its own page tables.

A **thread** is a unit of execution *within* a process. A single process can have multiple threads, and all threads belonging to that process share:
- the same virtual **address space** (so the same heap, same global/static variables, same memory-mapped files),
- the same **open file descriptors** and other OS-level handles,
- the same **code segment** (the program's instructions).

What each thread keeps *private* to itself is comparatively small: its own **program counter**, its own **stack**, its own **register state**, and its own **thread-local storage**, if any.

**Why this makes thread context-switches cheaper:** switching the CPU from one process to another is expensive because the OS must save/restore the full register state *and* swap the page table / memory mapping (often flushing or invalidating the TLB — the cache of virtual-to-physical address translations), since the next process has a completely different address space. Switching between threads of the *same* process still needs to save/restore registers, the program counter, and the stack pointer, but it does **not** need to swap the address space or flush the TLB, because every thread of that process already shares the same page tables. Fewer things need to change, so the switch is faster.

**The practical trade-off this creates:** because threads share memory, communicating between threads is cheap (just read/write a shared variable) but unsafe without explicit synchronization (mutexes, semaphores, atomics) — concurrent, unsynchronized access to shared state is a data race. Communicating between processes is safer by default (isolated memory) but requires explicit, slower mechanisms — pipes, sockets, shared-memory segments, or message queues (IPC) — specifically *because* nothing is shared automatically.

### 2. DBMS (Conceptual/Definition)

What is database normalization? Explain what problem it solves, and walk through what 1NF, 2NF, and 3NF each additionally require, with an example of the anomaly each one eliminates.

**Answer:**

**Normalization** is the process of structuring relational tables to minimize **data redundancy** and prevent **update anomalies** — situations where the same fact is stored in more than one place, so an update, insert, or delete can leave the database inconsistent. It works by progressively splitting a table into smaller tables connected by foreign keys, according to a series of increasingly strict rules called **normal forms**.

**1NF (First Normal Form):** every column must hold a single, atomic value — no repeating groups, no comma-separated lists, no arrays stuffed into one cell. A table storing `phone_numbers = "555-1234, 555-5678"` in one column violates 1NF, because you cannot efficiently query, index, or update one of those numbers independently. The fix is a separate `phone_numbers` table with one row per number, linked by a foreign key.

**2NF (Second Normal Form):** the table must already be in 1NF, *and* every non-key column must depend on the **whole** primary key, not just part of it. This only matters when the primary key is composite (made of multiple columns). Example: a table `(student_id, course_id, course_name)` with primary key `(student_id, course_id)` — `course_name` depends only on `course_id`, not on the full composite key. This is a **partial dependency**, and it causes redundancy: `course_name` for "CS101" is repeated for every student enrolled in it, and if the course is renamed, you must update every single row or the data becomes inconsistent. The fix: move `course_id → course_name` into its own `courses` table.

**3NF (Third Normal Form):** the table must already be in 2NF, *and* every non-key column must depend **only** on the primary key — not on another non-key column. Example: a table `(employee_id, department_id, department_name)` — `department_name` depends on `department_id`, which is itself a non-key column, not directly on `employee_id`. This is a **transitive dependency**, and it causes the same kind of redundancy: the same `department_name` repeats across every employee in that department, and renaming a department means updating every one of those rows. The fix: move `department_id → department_name` into its own `departments` table.

**Why it matters in practice:** each normal form eliminates one specific *kind* of update anomaly, and the three build on each other — you cannot be in 3NF without already satisfying 2NF and 1NF. The trade-off is that highly normalized schemas need more `JOIN`s to reassemble a full picture, which is why read-heavy analytical systems sometimes deliberately **denormalize** (re-introduce controlled redundancy) to avoid expensive joins — but that is a conscious performance trade-off made *after* understanding what normalization protects, not a reason to skip understanding it.

### 3. System Design Basics (Scenario/Applied)

You're building a distributed cache made of several server nodes, and need to decide which node owns which key. Plain `hash(key) % number_of_servers` works until a server is added or removed — then explain what breaks, what **consistent hashing** does differently, and why it fixes that specific problem.

**Answer:**

**The problem with plain modulo hashing.** `hash(key) % N` maps a key to one of `N` servers. This works fine as long as `N` never changes. The moment you add or remove a single server — going from `N` to `N+1` or `N-1` — the modulus changes, and for almost *every* key, `hash(key) % N` and `hash(key) % (N±1)` land on a different server. In practice, adding or removing one node out of, say, 10 causes roughly 90% of keys to remap to a different owner. Since a cache's whole value is that the data is already sitting on the node that's about to be asked for it, remapping that much of the keyspace at once means a massive wave of cache misses hitting the backing database simultaneously — exactly the moment (scaling an under-provisioned cluster) when you can least afford that.

**What consistent hashing does differently.** Instead of hashing keys directly onto a small, fixed set of server indices, it hashes both the **servers** and the **keys** onto the same abstract space — conceptually a ring of hash values (e.g., 0 to 2^32 - 1). Each server occupies one or more points on this ring (hashing the server's ID, possibly several times for **virtual nodes** to smooth out load distribution). A key is assigned to whichever server's point is the first one encountered walking **clockwise** from the key's own hash position on the ring.

**Why this fixes the problem.** When a server is added, it claims a new point on the ring, and it only takes ownership of the slice of keyspace between its new point and the next server counter-clockwise from it — every other key on the ring is completely unaffected, because their "next server clockwise" hasn't changed. Symmetrically, when a server is removed, only the keys that were assigned to it need to move, and they move to the very next server clockwise — again, nothing else on the ring shifts. So instead of remapping ~90% of keys on a membership change, consistent hashing remaps roughly `1/N` of the keyspace — proportional to the size of the one node that changed, not to the size of the whole cluster.

**One more detail worth knowing:** without virtual nodes, a server occupying a single point on the ring can end up owning a disproportionately large or small arc purely by chance, causing uneven load. Giving each physical server many virtual points scattered around the ring averages this out, which is why production systems (e.g., Amazon DynamoDB's internal design, many memcached client libraries) use consistent hashing with virtual nodes rather than the single-point version.
