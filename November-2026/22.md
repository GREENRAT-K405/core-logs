### Question: Maximum XOR With an Element From Array (Bit Manipulation — Hard)

**Problem Statement**

You are given an array of non-negative integers `nums`, and an array of queries `queries` where `queries[i] = [x_i, m_i]`.

For the `i`-th query, find the maximum value of `x_i XOR y` over all `y` in `nums` such that `y <= m_i`. If no element of `nums` satisfies `y <= m_i`, the answer for that query is `-1`.

Return an array `answer` where `answer[i]` is the result for `queries[i]`.

**Input/Output Format**

- Input: `nums` (vector of non-negative ints), `queries` (vector of pairs `[x, m]`).
- Output: a vector of ints, one per query, each either the maximum XOR value or `-1`.

**Examples**

1. `nums = [0,1,2,3,4]`, `queries = [[3,1],[1,3],[5,6]]` → `answer = [3,3,7]`
   - Query `[3,1]`: candidates with `y <= 1` are `{0,1}`. `3^0=3`, `3^1=2` → max `3`.
   - Query `[1,3]`: candidates `{0,1,2,3}`. Best is `1^2=3`.
   - Query `[5,6]`: all of `nums` qualifies (`6 >= 4`). Best is `5^2=7`.

2. `nums = [5,2,4,6,6,3]`, `queries = [[12,4],[8,1],[6,3]]` → `answer = [15,-1,5]`
   - Query `[8,1]`: no element of `nums` is `<= 1`, so the answer is `-1`.
   - Query `[6,3]`: candidates `{2,3}`. Best is `6^3=5`.

3. `nums = [1]`, `queries = [[0,0]]` → `answer = [-1]` (no element `<= 0`).

**Constraints**

- `1 <= nums.length, queries.length <= 10^5`
- `0 <= nums[i] <= 10^9`
- `0 <= x_i, m_i <= 10^9`
- Need an approach faster than O(n · q), since both can be `10^5`.

### Step-by-Step Walkthrough

**Why brute force is too slow.** For each query, scanning all of `nums`, filtering `y <= m`, and XOR-ing against `x` is O(n) per query, so O(n·q) overall — up to `10^10` operations. We need to answer "best XOR partner under a value cap" much faster than a linear scan per query.

**Two separate sub-problems, fused.** There are two classic tricks here, and the hard part of this problem is realizing you need both at once:

1. **Maximum XOR against a fixed set, no cap** is the textbook *bitwise trie (XOR trie)* problem: insert every candidate number as a 30-bit binary string into a binary trie, then for a query value `x`, walk the trie from the most significant bit, greedily choosing the child whose bit is the *opposite* of `x`'s bit at that position whenever that child exists. Opposite bits contribute `1`s to the XOR at the most significant positions, which is exactly what maximizes the result (a `1` at a higher bit always beats any combination of lower bits).

2. **The `y <= m` cap** is an *offline range* problem. If we process queries in increasing order of `m`, and also sort `nums` in increasing order, we can maintain a pointer into `nums` and insert elements into the trie one at a time, only as they become `<= m` for the current query. By the time we reach a query with cap `m`, the trie contains exactly the set of `nums` elements that are `<= m` — no more, no less.

**Putting it together:**
1. Sort `nums` ascending.
2. Attach each query's original index, then sort queries ascending by `m`.
3. Walk queries in that sorted order, maintaining pointer `j` into sorted `nums`. Before answering a query, advance `j` and insert `nums[j]` into the trie for as long as `nums[j] <= m_i`.
4. If no element has been inserted yet (`j == 0` and `nums[0] > m_i`), the answer is `-1`.
5. Otherwise, greedily walk the trie with `x_i` to compute the maximum XOR, and write the result at the query's *original* index (since we reordered queries by `m`, we must remember where each one came from).

**Why the greedy trie walk is correct.** XOR value is determined bit by bit, most significant first, and a result with a `1` in a higher bit position is always larger than any result that only differs in lower bits (standard property of comparing binary numbers positionally). So at each trie level, taking the branch that flips the current bit of `x` (when it exists) can never be beaten by taking the other branch, no matter what happens at lower bits. This greedy choice is locally and therefore globally optimal — no backtracking or DP needed.

**Complexity.**
- Sorting `nums` and `queries`: O(n log n + q log q).
- Each number is inserted into the trie once: O(n · B) where `B = 30` bits (since `nums[i] <= 10^9 < 2^30`).
- Each query does one trie walk: O(q · B).
- Total time: O((n + q) log(n + q) + (n + q) · B) — effectively linear in the input size.
- Space: O(n · B) for the trie nodes (each number can create up to `B` new nodes).

### C++ Code

```cpp
#include <vector>
#include <algorithm>
using namespace std;

class XorTrie {
public:
    static const int BITS = 30; // nums[i], x_i <= 1e9 < 2^30

    // child[node][b] = index of the child reached via bit b, or 0 if absent.
    // Node 0 is reserved as the (always-empty) root/"no child" sentinel.
    vector<array<int, 2>> child;

    XorTrie() {
        child.push_back({0, 0}); // node 0 = root
    }

    void insert(int num) {
        int node = 0;
        for (int bit = BITS - 1; bit >= 0; --bit) {
            int b = (num >> bit) & 1;
            if (child[node][b] == 0) {
                child.push_back({0, 0});
                child[node][b] = (int)child.size() - 1;
            }
            node = child[node][b];
        }
    }

    // Trie must be non-empty (at least one insert) before calling this.
    int maxXorWith(int x) const {
        int node = 0;
        int result = 0;
        for (int bit = BITS - 1; bit >= 0; --bit) {
            int b = (x >> bit) & 1;
            int want = 1 - b; // the bit that maximizes this position of the XOR
            if (child[node][want] != 0) {
                result |= (1 << bit);
                node = child[node][want];
            } else {
                node = child[node][b]; // guaranteed to exist: every inserted
                                        // number produced a full-depth path
            }
        }
        return result;
    }
};

vector<int> maximizeXor(vector<int>& nums, vector<vector<int>>& queries) {
    int n = (int)nums.size();
    int q = (int)queries.size();

    sort(nums.begin(), nums.end());

    // Pair each query with its original index, then sort by the cap m.
    vector<int> order(q);
    for (int i = 0; i < q; ++i) order[i] = i;
    sort(order.begin(), order.end(), [&](int a, int b) {
        return queries[a][1] < queries[b][1];
    });

    vector<int> answer(q, -1);
    XorTrie trie;
    int j = 0; // next index in sorted `nums` to consider inserting

    for (int idx : order) {
        int x = queries[idx][0];
        int m = queries[idx][1];

        while (j < n && nums[j] <= m) {
            trie.insert(nums[j]);
            ++j;
        }

        if (j > 0) { // at least one element has been inserted
            answer[idx] = trie.maxXorWith(x);
        }
        // else: leave answer[idx] as -1
    }

    return answer;
}
```

### 1. Computer Networks (Comparison)

TCP and UDP both sit at the transport layer on top of IP, but they make opposite trade-offs. Describe the concrete mechanisms TCP uses to provide reliability, and explain why a real-time video call deliberately chooses UDP instead, even though UDP gives none of those guarantees.

**Answer:**

**What TCP actually does to be reliable.** "Reliable" is not a single feature — it's a bundle of mechanisms, each solving one specific failure mode:

- **Sequence numbers** on every byte let the receiver detect missing, duplicated, or reordered segments, and reassemble them in the correct order even if the network delivers them out of order.
- **Acknowledgements (ACKs)** tell the sender which bytes arrived, so it knows what still needs to be (re)sent.
- **Retransmission timers / fast retransmit** resend data that wasn't ACKed in time, recovering from packet loss.
- **The three-way handshake** (`SYN`, `SYN-ACK`, `ACK`) establishes agreed-upon starting sequence numbers before any data flows, so both sides have a consistent view of the stream.
- **Flow control** (sliding window, advertised by the receiver) prevents a fast sender from overrunning a slow receiver's buffer.
- **Congestion control** (slow start, AIMD, etc.) makes the sender back off when the *network path* — not just the receiver — is overloaded, which is what keeps the internet from collapsing under load.

UDP has none of this. It is a thin wrapper over IP: a 8-byte header (source/dest port, length, checksum) and nothing else. No handshake, no sequencing, no retransmission, no congestion control. Packets ("datagrams") can arrive out of order, duplicated, or not at all, and UDP will never tell you — it hands whatever arrives straight to the application, and silently drops anything that doesn't.

**Why a video call wants exactly that.** The thing TCP optimizes for — *eventually, every byte arrives, in order* — is the wrong goal for real-time media:

1. **A retransmitted frame from 400ms ago is worse than no frame at all.** If packet 500 (part of a video frame) is lost, TCP's answer is "stop delivering anything newer until packet 500 is resent and arrives." That means packets 501–600, which may already be sitting in the receiver's buffer, are held back — the whole stream stalls waiting for one old, now-stale frame. For a live call, a stale frame is useless; you'd rather skip it and show the next one.
2. **Head-of-line blocking compounds under loss.** The worse the network, the more TCP stalls, exactly when you most need the call to keep moving. UDP-based protocols (e.g., RTP, or WebRTC's underlying SRTP) just drop the lost packet, let the decoder interpolate or show a glitch for one frame, and move on with the next arriving data. The application-layer codec (not the transport) decides how to tolerate loss — e.g., skip a frame, degrade a video keyframe gracefully.
3. **Congestion control's timing doesn't fit the use case either.** TCP congestion control is tuned for throughput over a stream where *order and completeness* matter (file transfer, a web page). Real-time media wants to adapt bitrate quickly to *latency* and tolerate some loss, which is why WebRTC implements its own congestion control (e.g., Google Congestion Control) on top of UDP rather than reusing TCP's.
4. **No handshake overhead.** Every TCP connection needs a round trip before any data flows. For something latency-sensitive, skipping that (and the connection-teardown cost) matters.

**The general principle:** reliability mechanisms have a cost (latency, head-of-line blocking), and that cost is only worth paying when the application actually needs "complete and in-order" over "fast and current." File transfer, email, and web pages need the former (hence TCP/HTTP). Live video/audio, gaming, and DNS lookups need the latter, or implement their own lightweight, loss-tolerant logic on top of UDP.

### 2. System Design Basics (Scenario/Applied)

You're designing a URL shortener (like bit.ly) that must support roughly 10,000 writes/sec (new short links) and 100,000 reads/sec (redirects), with redirect latency as the top priority. Walk through: how you'd generate short codes, where you'd store data, and how you'd keep read latency low at that read volume.

**Answer:**

**1. Short code generation.** Two broad approaches:

- **Hash-based:** take an MD5/SHA hash of the long URL, base62-encode the first few bytes. Simple, but collisions require detection-and-retry logic, and it's not trivially possible to guarantee the code is unused without a lookup first — so every write still costs a read.
- **Counter-based (generally preferred here):** maintain a globally unique, monotonically increasing ID (e.g., a distributed ID generator like Twitter Snowflake, or a sharded counter/key-range allocator — each app server reserves a block of IDs like `[1,1000)` from a central service, hands them out locally, then asks for the next block), and base62-encode that ID into the short code. This guarantees uniqueness with no collision check, and at 10K writes/sec, handing out ID ranges in batches means the central allocator is barely touched.

I'd pick counter-based: it avoids the read-before-write cost hash-based schemes pay on every single write, and 10K writes/sec is well within what a range-based ID allocator handles trivially.

**2. Storage choice.** The access pattern is simple key-value: `short_code → long_url`, read far more than written (10:1 here, often much higher in real systems), and doesn't need relational joins or transactions across rows. That points to a **key-value or wide-column NoSQL store** (DynamoDB, Cassandra) over a relational database:

- Horizontal scaling by sharding on `short_code` (consistent hashing) is straightforward and these stores are built for it.
- We don't need ACID transactions spanning multiple short codes, so we give up nothing by skipping a relational engine.
- A relational DB would still *work* at this scale with good indexing, but it adds operational cost (vertical scaling limits, more careful sharding) for guarantees (joins, multi-row transactions) this workload doesn't use.

Each row: `short_code (partition key), long_url, created_at, expiry (optional), click_count (optional, better handled async — see below)`.

**3. Keeping redirect latency low at 100K reads/sec.** This is the part that actually drives the architecture, since reads dominate 10:1 and latency is the stated priority:

- **A cache in front of the database is mandatory, not optional.** Redirect lookups follow a classic power-law / hot-key distribution — a small fraction of short links (viral posts, marketing campaigns) account for a large fraction of traffic. Put **Redis or Memcached** in front of the KV store, keyed by `short_code`, with a TTL or LRU eviction. A well-tuned cache can realistically serve >95% of the 100K reads/sec, so the database only has to absorb the cache-miss trickle — often a 10–50x reduction in load that hits persistent storage.
- **CDN edge caching for the redirect itself.** An HTTP redirect (`301`/`302` with `Location:`) is cacheable. Routing redirects for popular links through a CDN or edge layer (with an appropriate `Cache-Control`) lets browsers and intermediate caches short-circuit the trip to your servers entirely for repeat clicks on the same hot link.
- **Choose 302 (temporary) over 301 (permanent) deliberately, or cap 301 caching, if you need click analytics** — browsers aggressively cache `301`s locally and will stop hitting your servers at all for that link, which kills your ability to count clicks. This is a real trade-off between "minimize server load" and "need accurate analytics," and the answer depends on the product requirement.
- **Decouple click-count updates from the read path.** Incrementing a counter synchronously on every redirect turns a cache-served read into a database write, instantly reintroducing the bottleneck you just engineered around. Instead, log the click event (short_code, timestamp) to a message queue (Kafka/Kinesis) and aggregate counts asynchronously — the redirect itself stays a pure cache lookup.
- **Read replicas** for the underlying store absorb cache misses across multiple nodes rather than hammering a single primary.

**The overarching pattern:** writes are infrequent and tolerate a little extra latency (ID allocation, a DB write), so optimize them for correctness and simplicity. Reads are the hot path at 10x the volume and latency-critical, so every layer — cache, CDN, async side-effects — exists to keep the actual redirect response as close to "serve from memory, nothing synchronous" as possible.

### 3. Computer Architecture (Comparison)

Compare write-through and write-back cache policies: what each one does on a write hit, what it costs, and which you'd choose for a system where sudden power loss is a real risk — and why.

**Answer:**

Both policies answer the same question: when the CPU writes to a memory location that's currently cached, when does that write actually reach main memory?

**Write-through.** Every write to the cache is immediately also written to main memory (or the next level down), synchronously. The cache line and memory are kept consistent at all times.

- *Pro:* main memory always holds the current value, so a cache line can be evicted or invalidated at any instant with zero extra work — there's never "data only the cache knows about." This also makes it trivially correct for multi-core cache coherence, since no other core can ever see a stale value in memory.
- *Con:* every write pays main-memory latency (tens to hundreds of cycles), even though the fast cache write itself completed instantly. Write-heavy workloads lose most of the benefit of caching for writes. (In practice this is softened with a **write buffer** that queues the memory writes asynchronously, but the fundamental cost — every write eventually hits memory — remains.)

**Write-back.** A write updates only the cache line and sets a **dirty bit**; the line is written to main memory only later, when it's **evicted** (to make room for something else) — not on every write.

- *Pro:* multiple writes to the same cache line (very common — loop counters, repeated field updates) cost one memory write total, at eviction, instead of one per write. This is why write-back is the dominant policy in modern CPU caches — it dramatically reduces memory bus traffic for typical write patterns.
- *Con:* main memory can hold a **stale** value for an arbitrarily long time while the cache holds the only up-to-date copy (the dirty line). This has two consequences: (a) cache coherence across cores needs an explicit protocol (e.g., MESI) so one core can find and retrieve the current value from another core's cache rather than from memory; (b) if the cache's contents are lost before a dirty line is evicted, that data is lost — a dirty line is the *only* place the current value exists.

**Power-loss scenario — which to choose, and why.** With write-back, a dirty cache line represents data that has been "written" from the CPU's point of view but does **not yet exist anywhere in non-volatile storage**. Caches (SRAM) are volatile — their contents vanish on power loss. If power is cut before that dirty line is evicted/flushed, that write is gone permanently, with no record it ever happened, even though the application believed the write succeeded.

Write-through doesn't have this failure mode in the same way: by the time a write "completes" (synchronously reaches memory, or is safely queued in a write buffer about to be flushed), it's already in main memory, which — if that memory is itself non-volatile or backed appropriately — survives the power event. The window of data-at-risk is just the in-flight write buffer, not an arbitrarily long accumulation of dirty, unflushed lines.

So for a system where sudden power loss is a real operational risk (e.g., an embedded controller, a storage system's metadata, a database's log buffer), **write-through** (or write-back with aggressive, frequent flushing / a battery-backed or non-volatile write buffer) is the safer choice, because it minimizes the amount of "acknowledged but not yet durable" data at any instant. This is exactly why database systems and filesystem journals treat "flush to disk" (`fsync`) as a hard durability boundary — they're explicitly working around the fact that caches (CPU cache, disk cache, OS page cache) all default to write-back-like behavior for performance, and durability requires deliberately forcing a flush at the right moments rather than trusting the cache to do it in time.

**The general trade-off:** write-back wins on performance (fewer memory writes) in the common case; write-through wins on simplicity and failure-safety, because consistency with backing storage is never deferred. Real systems often use write-back for performance but add explicit flush/sync points exactly where durability actually matters, getting most of the speed with a bounded, controlled risk window instead of an unbounded one.
