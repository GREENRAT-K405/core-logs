### Question: Sudoku Solver (Recursion/Backtracking — Hard)

Write a program to solve a 9x9 Sudoku puzzle by filling in the empty cells.

A sudoku solution must satisfy all of the following rules:
1. Each of the digits `1-9` must occur exactly once in each row.
2. Each of the digits `1-9` must occur exactly once in each column.
3. Each of the digits `1-9` must occur exactly once in each of the 9 `3x3` sub-boxes of the grid.

The `'.'` character indicates empty cells. You are guaranteed that the input board has exactly one solution.

**Input/Output format:**
- Input: a `9x9` grid `board`, given as a `vector<vector<char>>`, where each cell is a digit `'1'`-`'9'` or `'.'` for empty.
- Output: modify `board` in place so it holds the completed, valid solution.

**Example 1:**
```
Input:
board = [["5","3",".",".","7",".",".",".","."],
         ["6",".",".","1","9","5",".",".","."],
         [".","9","8",".",".",".",".","6","."],
         ["8",".",".",".","6",".",".",".","3"],
         ["4",".",".","8",".","3",".",".","1"],
         ["7",".",".",".","2",".",".",".","6"],
         [".","6",".",".",".",".","2","8","."],
         [".",".",".","4","1","9",".",".","5"],
         [".",".",".",".","8",".",".","7","9"]]

Output:
board = [["5","3","4","6","7","8","9","1","2"],
         ["6","7","2","1","9","5","3","4","8"],
         ["1","9","8","3","4","2","5","6","7"],
         ["8","5","9","7","6","1","4","2","3"],
         ["4","2","6","8","5","3","7","9","1"],
         ["7","1","3","9","2","4","8","5","6"],
         ["9","6","1","5","3","7","2","8","4"],
         ["2","8","7","4","1","9","6","3","5"],
         ["3","4","5","2","8","6","1","7","9"]]
```
Explanation: Every row, column, and 3x3 box now contains the digits 1-9 exactly once.

**Example 2 (smaller conceptual case, 4x4 board with 2x2 boxes, digits 1-4):**
```
Input:
["1",".",".","4"]
[".",".","1","."]
[".","1",".","."]
["4",".",".","1"]

A valid completion (one of possibly many on this toy example):
["1","2","3","4"]
["3","4","1","2"]
["2","1","4","3"]
["4","3","2","1"]
```
Explanation: This illustrates the same row/column/box constraint on a smaller grid; the real problem is always a fixed 9x9 board with 3x3 boxes.

**Example 3 (almost-complete board):**
```
Input: an otherwise-full valid board with exactly one '.' remaining in row 0, column 2,
where row 0 already has {5,3,_,_,7,_,_,_,_} and the missing value is forced to "4"
by the column and box constraints.
Output: that single cell filled with "4", rest unchanged.
```
Explanation: When only one empty cell remains, the constraints usually force a unique value immediately — this is the base case the recursion bottoms out on.

**Constraints:**
- `board.length == 9`
- `board[i].length == 9`
- `board[i][j]` is a digit `1-9` or `'.'`
- It is guaranteed that the input board has only one solution.

### Step-by-Step Walkthrough

**Why backtracking fits:** Sudoku is a constraint-satisfaction problem. At each empty cell we must choose a digit that doesn't currently violate the row/column/box rule, place it, and recurse into the rest of the board. If a later cell has no valid digit, the earlier choice was wrong, so we undo it (backtrack) and try the next candidate. This is the classic "try, recurse, undo" pattern.

**Approach:**
1. **Track constraints efficiently.** Instead of rescanning the row/column/box on every placement attempt (which is wasteful), maintain three arrays of bitmasks (or boolean sets) of size 9 each:
   - `rows[i]`: which digits are already used in row `i`.
   - `cols[j]`: which digits are already used in column `j`.
   - `boxes[k]`: which digits are already used in box `k`, where `k = (i / 3) * 3 + (j / 3)`.
   Using an `int` as a bitmask (bit `d` set means digit `d+1` is present) makes "is digit `d` usable here?" an O(1) check via `rows[i] & cols[j] & boxes[k]`.

2. **Collect empty cells up front** into a list, so the recursion walks a flat list of positions instead of re-scanning the grid for the "next empty cell" every call.

3. **Recursive solve(pos):**
   - If `pos == empties.size()`, every cell is filled validly — return `true` (done).
   - Otherwise, take `(i, j)` = `empties[pos]`.
   - For each digit `d` from 1 to 9 not yet used in `rows[i]`, `cols[j]`, or `boxes[k]`:
     - Place `d`: set the board cell, mark the digit used in `rows[i]`, `cols[j]`, `boxes[k]`.
     - Recurse on `pos + 1`. If it returns `true`, propagate `true` up immediately (solution found, no need to undo).
     - If it returns `false`, undo the placement (unset the board cell back to `'.'` and clear the digit from the three tracking structures), and try the next digit.
   - If no digit works, return `false` (triggers backtrack in the caller).

4. **Early termination:** because Sudoku is guaranteed to have exactly one solution, the first time `solve` returns `true` we stop immediately and the board already holds the answer — no need to search for alternatives.

**Why it's correct:** the bitmask checks guarantee every placement keeps the board consistent with rows/columns/boxes seen so far; exhaustively trying every digit at every empty cell (with undo) guarantees we explore the full search space, so if a solution exists we will find it. The problem guarantees uniqueness, so correctness isn't in question, only termination, which is guaranteed because the search space (9 digits per each of at most 81 cells) is finite.

**Complexity analysis:**
- **Time:** Worst-case exponential, O(9^m) where `m` is the number of empty cells, since in the worst case each empty cell could try up to 9 digits before constraint propagation prunes the branch. In practice, the constraint checks (row/col/box) prune the vast majority of branches almost immediately, so real Sudoku puzzles solve in milliseconds. This is standard for NP-complete-style CSPs — the worst-case bound is loose, but there's no known polynomial algorithm for general Sudoku.
- **Space:** O(1) additional space beyond the input board for the three bitmask arrays (fixed size 9 each) plus O(m) for the list of empty-cell positions and O(m) recursion depth on the call stack, where `m <= 81`.

### C++ Code

```cpp
#include <vector>
using namespace std;

class Solution {
public:
    void solveSudoku(vector<vector<char>>& board) {
        // Bitmask trackers: bit (d-1) set means digit d is already placed.
        vector<int> rows(9, 0), cols(9, 0), boxes(9, 0);
        vector<pair<int,int>> empties;

        // Initialize trackers from the given board and collect empty cells.
        for (int i = 0; i < 9; ++i) {
            for (int j = 0; j < 9; ++j) {
                char c = board[i][j];
                if (c == '.') {
                    empties.push_back({i, j});
                } else {
                    int d = c - '1';          // 0-indexed digit
                    int b = (i / 3) * 3 + (j / 3);
                    rows[i] |= (1 << d);
                    cols[j] |= (1 << d);
                    boxes[b] |= (1 << d);
                }
            }
        }

        solve(board, rows, cols, boxes, empties, 0);
    }

private:
    bool solve(vector<vector<char>>& board,
               vector<int>& rows, vector<int>& cols, vector<int>& boxes,
               vector<pair<int,int>>& empties, int pos) {
        if (pos == static_cast<int>(empties.size())) {
            return true; // all empty cells filled consistently
        }

        int i = empties[pos].first;
        int j = empties[pos].second;
        int b = (i / 3) * 3 + (j / 3);

        // used mask across row, column and box for this cell
        int used = rows[i] | cols[j] | boxes[b];

        for (int d = 0; d < 9; ++d) {
            int bit = 1 << d;
            if (used & bit) continue; // digit (d+1) already present in row/col/box

            // place digit d+1
            board[i][j] = static_cast<char>('1' + d);
            rows[i] |= bit;
            cols[j] |= bit;
            boxes[b] |= bit;

            if (solve(board, rows, cols, boxes, empties, pos + 1)) {
                return true; // propagate success, board already holds the answer
            }

            // undo (backtrack)
            board[i][j] = '.';
            rows[i] &= ~bit;
            cols[j] &= ~bit;
            boxes[b] &= ~bit;
        }

        return false; // no digit works here; caller must backtrack
    }
};
```

### 1. Operating Systems (Conceptual)

What is thrashing in the context of virtual memory, what causes it, and how does an operating system typically detect and recover from it?

**Answer:**

Thrashing is a state where a system spends more time paging (swapping pages in and out of physical memory) than executing actual process instructions, causing overall throughput to collapse even though the CPU and disk both appear "busy."

**Cause:** It happens when the combined working-set size of the currently running processes exceeds available physical memory. Each process doesn't have enough frames to hold its actively-used pages, so almost every memory access triggers a page fault. The OS evicts a page to make room, but that evicted page is likely to be needed again very soon (because the process's true working set didn't fit), so another fault follows almost immediately. As more processes are let in (e.g., by naive schedulers trying to "increase CPU utilization" by adding more jobs), the problem compounds: each process gets fewer frames, faults more, and system-wide paging I/O traffic explodes while real work stalls.

**Detection:** The classic signal is the OS monitoring CPU utilization vs. the degree of multiprogramming. Normally, adding more processes keeps CPU utilization climbing (more work queued up when one process blocks on I/O). But past a certain point, CPU utilization starts dropping sharply even as more processes are added — because the CPU is now mostly waiting on page-fault service rather than running instructions. This inflection point is the signature of thrashing. Modern systems also track metrics like page-fault rate, and a feedback loop that correlates rising page-fault rate with falling CPU utilization is a strong thrashing indicator.

**Recovery:**
- **Working-set model:** The OS estimates each process's "working set" (the set of pages it has referenced in a recent time window) and only admits/schedules a process if enough free frames exist to hold its whole working set. This directly targets the root cause.
- **Reducing the degree of multiprogramming:** Suspend or swap out one or more processes entirely, freeing their frames for the remaining processes, so those remaining processes can finally satisfy their working sets and stop faulting.
- **Local vs. global replacement policies:** Using a local page-replacement policy (a process can only evict its own pages) limits how much one thrashing process can damage others, compared to global replacement where a starving process can steal frames from everyone, spreading the thrashing.

Why it matters in practice: this is the theoretical basis for why systems (and container orchestrators like Kubernetes with memory limits/OOM killer, or cloud VMs with memory ballooning) actively limit how many memory-hungry workloads can run concurrently, rather than just letting the OS's page replacement "figure it out" — once thrashing sets in, it is self-reinforcing and the system doesn't recover on its own without intervention.

### 2. DBMS (Comparison)

Compare optimistic concurrency control (OCC) and pessimistic concurrency control (locking) for handling concurrent transactions in a database. When would you prefer one over the other?

**Answer:**

Both are strategies to guarantee isolation (prevent conflicting concurrent transactions from corrupting data), but they differ in *when* they check for conflicts.

**Pessimistic concurrency control (locking):**
- Assumes conflicts are likely, so it prevents them up front: before reading or writing a data item, a transaction must acquire a lock (shared for reads, exclusive for writes).
- If another transaction holds a conflicting lock, the requester blocks (waits) until the lock is released.
- Requires a lock manager, deadlock detection (or prevention via ordering/timeouts), and can reduce concurrency because transactions wait even when they would not have actually conflicted.
- Guarantees correctness by construction — a transaction never commits work that was invalidated by a concurrent writer, because it was blocked from ever touching data that would conflict.

**Optimistic concurrency control (OCC):**
- Assumes conflicts are rare, so it lets transactions proceed without locking, tracking what they read/wrote.
- Has three phases: (1) **read phase** — the transaction reads data and does its work on private/local copies without locking; (2) **validation phase** — at commit time, the system checks whether any other transaction modified the data this transaction read/wrote during its execution; (3) **write phase** — if validation passes, changes are committed; if validation fails, the transaction aborts and typically retries.
- Avoids lock contention and deadlocks entirely (no locks are held during execution), which is great for low-contention workloads.
- Under high contention, OCC can perform worse than locking because transactions do real work and then get aborted at commit time, wasting that work — this is sometimes called "optimistic concurrency thrashing" when abort/retry rates get high.

**When to prefer which:**
- Prefer **pessimistic/locking** when contention is high (many transactions touching the same hot rows), when transactions are long-running (so wasted work from a late abort would be expensive), or when the cost of a transaction retry is unacceptable (e.g., it has external side effects that are hard to roll back).
- Prefer **optimistic/OCC** when contention is low (most transactions touch disjoint data), when transactions are short, or in distributed/high-latency settings where holding locks across a network round-trip would be very costly (locking under high latency magnifies blocking time).

Why it matters: this tradeoff shows up directly in real systems — e.g., many web frameworks use OCC via a "version" column (check the version hasn't changed before committing an update) specifically because web request handling is short-lived and contention on any single row is usually low, making lock overhead not worth paying for.

### 3. Computer Networks (Scenario)

A client opens a TCP connection to a server, sends a request, and the server sends back a large response. Midway through, the client's receive buffer fills up because the client application is slow to read the incoming data. Walk through what happens at the TCP level, and explain how the server knows to slow down.

**Answer:**

This is TCP's **flow control** mechanism in action, implemented via the **sliding window** and advertised in the TCP header's **window size** field, and it's distinct from congestion control (which protects the network) — flow control protects the *receiver* from being overwhelmed.

**Step by step:**

1. **Normal operation:** Every TCP segment the client sends back to the server (including pure ACKs) carries a "window size" field in its header. This advertises how many additional bytes of data the client's receive buffer currently has room for, from the client's perspective as receiver of the server's data stream.

2. **Buffer filling up:** As the server's response arrives, data goes into the client's receive buffer. Data sitting in the buffer that the client application hasn't yet `read()` out stays there. If the client application is slow, unread bytes accumulate, shrinking the available free space in that buffer.

3. **Window shrinks in ACKs:** Each ACK the client sends back for data it received includes an updated window size reflecting the *current* free space, so if the buffer is filling, consecutive ACKs advertise a shrinking window: e.g., 64KB free -> 32KB free -> 8KB free -> eventually 0.

4. **Server respects the window:** The server's TCP stack tracks the most recently advertised window and will not send more unacknowledged data than that window allows (it keeps its "send window" bounded by `min(congestion window, receiver's advertised window)`). As the advertised window shrinks, the server simply stops sending new data once in-flight unacknowledged bytes reach the window limit — not because of network congestion, but purely because the receiver said "no more room."

5. **Zero window:** If the client's buffer completely fills (application never reads), the client advertises a **window size of 0**. The server must stop sending entirely at that point. To avoid a permanent deadlock (what if the client's follow-up "window now has room" ACK gets lost?), the server periodically sends small **window probe** segments (1 byte of data) to elicit a fresh ACK/window-size update from the client, so it can detect when the client starts reading again.

6. **Recovery:** Once the client application resumes reading and drains its buffer, subsequent ACKs advertise a growing window again, and the server resumes sending up to that newly available space.

Why it matters: this is exactly the mechanism that lets a fast server avoid overrunning a slow client (e.g., a mobile client on a weak CPU, or an application with a slow downstream consumer) purely through TCP's built-in signaling, with zero application-level protocol needed — the application only needs to correctly size its socket receive buffer and read from it; TCP handles the rest. This is also why advertised window size is a common thing to look at when debugging "why is this transfer slow" — a persistently small window is a strong signal the bottleneck is the receiver (slow consumer), not the network path.
