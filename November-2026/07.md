### Question: Largest Rectangle in Histogram (Stacks/Queues — Hard)

You are given an array `heights` representing the heights of bars in a histogram, where each bar has width `1` and the bars are adjacent to each other. Find the area of the largest rectangle that can be formed within the histogram's outline.

**Input format:** an array `heights` of non-negative integers.
**Output format:** a single integer — the maximum rectangular area.

**Example 1:**
```
Input:  heights = [2,1,5,6,2,3]
Output: 10
```
The largest rectangle is formed by the bars at indices 2 and 3 (heights 5 and 6): taking height `5` and width `2` gives area `10`.

**Example 2:**
```
Input:  heights = [2,4]
Output: 4
```
Either a single bar of height 4 (width 1, area 4) or both bars at the shorter height 2 (width 2, area 4) — both give area 4.

**Example 3:**
```
Input:  heights = []
Output: 0
```
Edge case: an empty histogram has no area to enclose.

**Constraints:**
- `0 <= n <= 10^5`
- `0 <= heights[i] <= 10^4`

### Step-by-Step Walkthrough

**Brute-force idea (O(n²)):** for every bar `i`, expand left and right as far as the histogram stays at least as tall as `heights[i]`, and compute `heights[i] * width`. This is correct but too slow for `n` up to `10^5`.

**Key insight:** for a fixed bar `i` to be the *limiting height* of some rectangle, that rectangle extends left until it hits a bar shorter than `heights[i]`, and right until it hits another bar shorter than `heights[i]`. So for every bar we really just need: the nearest shorter bar to the left, and the nearest shorter bar to the right. The maximum area using `heights[i]` as the height is then `heights[i] * (rightBoundary - leftBoundary - 1)`.

**Optimal approach — monotonic increasing stack (O(n) time, O(n) space):**
Maintain a stack of indices whose heights are in strictly increasing order from bottom to top. Walk left to right:
1. While the stack is non-empty and `heights[stack.top()] >= heights[i]`, the bar at `stack.top()` can no longer extend past index `i` on the right (we found its nearest-shorter-to-the-right). Pop it, and compute the area it forms:
   - `height = heights[poppedIndex]`
   - `width = i - stack.top() - 1` if the stack is non-empty after popping (the new top is its nearest-shorter-to-the-left), otherwise `width = i` (nothing shorter exists to the left, so it extends back to index 0).
2. Push `i` onto the stack.
3. Append a sentinel `0` to the end of the array before the loop (or handle it as a final pass) so every remaining bar in the stack gets flushed out and evaluated, since a height of `0` is shorter than anything that could remain.

**Why it works:** the stack only ever holds indices whose heights increase as you go up, because anything that would break that order gets popped and resolved immediately. When a bar is popped at step `i`, we know with certainty that index `i` is its nearest-shorter-to-the-right (that's *why* it got popped), and the new stack top (if any) is its nearest-shorter-to-the-left (it survived on the stack precisely because it's shorter than everything popped after it). So every bar's maximal rectangle is computed exactly once, using only comparisons already made during the single left-to-right pass.

**Complexity:**
- Time: `O(n)` — each index is pushed onto the stack exactly once and popped at most once.
- Space: `O(n)` — the stack can hold up to `n` indices in the worst case (a strictly increasing histogram).

**Trace on Example 1** (`[2,1,5,6,2,3]`, sentinel appended → `[2,1,5,6,2,3,0]`): bar `1` (height 1) pops bar `0` (height 2) with width 1 → area 2. Bars `5,6` get pushed, then at index 4 (height 2) they get popped: height 6 pops with width `4-2-1=1` → area 6; height 5 pops with width `4-1-1=2` → area **10** (the maximum). The sentinel at the end flushes the rest, none of which beats 10.

### C++ Code

```cpp
#include <bits/stdc++.h>
using namespace std;

// Monotonic increasing stack of indices: O(n) time, O(n) space.
int largestRectangleArea(vector<int>& heights) {
    heights.push_back(0); // sentinel: forces every remaining bar to be flushed and evaluated
    stack<int> st;        // holds indices with strictly increasing heights
    int maxArea = 0;
    int n = heights.size();

    for (int i = 0; i < n; i++) {
        // Current bar is shorter than (or equal to) the bar on top of the stack:
        // that means index i is the nearest-shorter-to-the-right for the top bar.
        while (!st.empty() && heights[st.top()] >= heights[i]) {
            int height = heights[st.top()];
            st.pop();
            // If the stack is empty, nothing to the left is shorter, so the
            // rectangle extends all the way back to index 0 (width = i).
            // Otherwise it extends from just after the new top (nearest-shorter-to-the-left).
            int width = st.empty() ? i : i - st.top() - 1;
            maxArea = max(maxArea, height * width);
        }
        st.push(i);
    }
    return maxArea;
}

int main() {
    vector<int> h1 = {2, 1, 5, 6, 2, 3};
    vector<int> h2 = {2, 4};
    vector<int> h3 = {};

    cout << largestRectangleArea(h1) << "\n"; // expected 10
    cout << largestRectangleArea(h2) << "\n"; // expected 4
    cout << largestRectangleArea(h3) << "\n"; // expected 0
    return 0;
}
```

### 1. Computer Networks (Conceptual)

What is the TCP three-way handshake? Describe each step and explain why a *three*-way exchange is necessary instead of a simpler two-way exchange.

**Answer:**

The three-way handshake is how TCP establishes a reliable, bidirectional connection between a client and a server before any application data flows. It consists of:

1. **SYN:** the client sends a segment with the `SYN` flag set and an initial sequence number (`ISN_client`), proposing to open a connection.
2. **SYN-ACK:** the server responds with both the `SYN` and `ACK` flags set — the `ACK` acknowledges the client's `ISN_client + 1`, and the `SYN` carries the server's own initial sequence number (`ISN_server`), proposing its side of the connection.
3. **ACK:** the client sends a final segment with the `ACK` flag set, acknowledging `ISN_server + 1`. At this point both sides have confirmed they can send *and* receive, so the connection is considered established.

**Why not two-way?** TCP is full-duplex — both sides independently track their own sequence numbers and need their own starting point acknowledged by the other. A two-way handshake (`SYN` → `ACK`) would only let the client confirm the server received its `ISN`; the server's own `ISN` would never be independently acknowledged by the client. This creates two concrete problems the third step solves:
- **Synchronization in both directions:** each side needs proof the *other* side's initial sequence number was received, so both halves of the duplex connection start with reliably agreed-upon sequence numbers. Two messages can only establish one direction's agreement.
- **Protection against stale/duplicate connection requests:** in a two-way scheme, the server would have to open the connection immediately upon sending its `SYN-ACK`, before knowing the client actually wanted it (rather than, say, a duplicated/delayed `SYN` from an old, already-closed connection). The third `ACK` is the client's explicit confirmation that it did initiate this connection and received the server's `ISN`, preventing the server from committing resources to a connection based on a stray retransmitted or delayed packet.

In short, three messages are the minimum needed for *both* parties to independently prove they sent and received a fresh initial sequence number, which is what "fully synchronized, mutually confirmed" connection establishment requires.

### 2. DBMS (Comparison)

Compare B-Tree and B+Tree indexing structures. Why do most relational databases use B+Trees for their primary indexes instead of plain B-Trees?

**Answer:**

Both are self-balancing, multi-way search trees designed to minimize disk I/O by keeping the tree shallow (high fan-out per node), which matters because each node access is typically a disk/page read.

**B-Tree:** stores both keys *and* their associated record data (or pointers to records) in every node — internal nodes as well as leaf nodes. A search can terminate at an internal node as soon as it finds a matching key, without descending all the way to a leaf.

**B+Tree:** stores keys in internal nodes purely to guide navigation (no associated data there); *all* actual record data/pointers live only in the leaf nodes. Additionally, the leaf nodes are linked together in a singly or doubly linked list.

| Aspect | B-Tree | B+Tree |
|---|---|---|
| Data location | Keys + data in internal and leaf nodes | Data only in leaf nodes |
| Internal node size | Larger (must store data per key) → lower fan-out | Smaller (keys only) → higher fan-out, shallower tree |
| Point lookup | Can short-circuit at an internal node | Always descends to a leaf (consistent cost) |
| Range queries | Requires repeated tree traversals / in-order traversal with backtracking | Fast — just follow the linked list of leaves after locating the start |
| Sequential/full scan | Less efficient | Very efficient, thanks to the leaf linked list |

**Why relational databases prefer B+Trees:** two reasons dominate.
1. **Higher fan-out → shallower trees:** since internal B+Tree nodes hold only keys (no data payload), many more keys fit per disk page, so the tree has fewer levels for the same number of records — fewer disk reads per lookup, which is the dominant cost.
2. **Efficient range scans:** SQL workloads constantly need range queries (`BETWEEN`, `ORDER BY`, `>`, `<`) and full table/index scans. Because B+Tree leaves are linked in sorted order, once you locate the start of a range you simply walk the linked list — no repeated root-to-leaf traversals. A B-Tree, with data scattered across internal and leaf nodes, has no equivalent fast path and would need an in-order traversal with backtracking through internal nodes.

The one thing you give up with a B+Tree is that an internal-node key match doesn't resolve the lookup early — but since you were going to hit the disk either way and the tree is shallower overall, this trade consistently wins for database workloads.

### 3. Computer Architecture (Scenario)

You're optimizing a performance-critical C++ loop that iterates over a large 2D array (say a `1000 x 1000` matrix stored in row-major order). Explain how cache locality affects performance here, and why iterating in row-major order can be dramatically faster than iterating in column-major order, even though both visit every element exactly once.

**Answer:**

A C++ 2D array (e.g., `int matrix[1000][1000]`, or a `vector<vector<int>>` with contiguous rows) is stored in **row-major order** in memory: all elements of row 0 are laid out contiguously, immediately followed by all elements of row 1, and so on. The CPU's cache doesn't fetch single bytes or single integers from main memory — it fetches data in fixed-size chunks called **cache lines** (commonly 64 bytes, so 16 consecutive `int`s on a 64-bit system). This exploits **spatial locality**: the assumption that if you access one memory address, you're likely to access nearby addresses very soon.

**Row-major traversal** (`for i: for j: matrix[i][j]`) accesses memory in the exact order it's physically laid out. The first access to `matrix[i][0]` pulls an entire cache line containing `matrix[i][0..15]` into the L1 cache; the next 15 accesses (`matrix[i][1]` through `matrix[i][15]`) are then **cache hits** — no memory access needed at all, just an L1 cache read, which costs roughly 1-4 CPU cycles. Over the full row, you only pay the full memory-latency cost (often 100+ cycles for a main-memory access, less if it hits L2/L3) once per 16 elements.

**Column-major traversal** (`for j: for i: matrix[i][j]`) over the same row-major-stored array accesses `matrix[0][j]`, `matrix[1][j]`, `matrix[2][j]`, ... — each of these is `1000 * sizeof(int)` = 4000 bytes apart in memory, i.e., many cache lines away from the last one. Every single access pulls in a *new* cache line (of which you only use 1 of the 16 integers it contains before moving on), and worse, for a large enough matrix the cache line fetched for `matrix[0][j]` is likely **evicted** by the time you loop back around to `matrix[0][j+1]`, since you've touched 1000 other cache lines in between. This means nearly every access becomes a cache miss requiring a full round-trip to main memory (or at best L2/L3), instead of 1 miss per 16 hits.

**Net effect:** for a `1000 x 1000` matrix, row-major traversal might incur roughly 1000*1000/16 ≈ 62,500 cache-line fetches, while column-major traversal can incur close to 1,000,000 fetches — a difference of over 10x in memory traffic, which in practice translates to a measurable multi-x slowdown in wall-clock time, even though the *number of arithmetic operations* performed is identical. This is why, when optimizing numeric code, the rule of thumb is: **always iterate in the order that matches the data's physical layout** (row-major for row-major storage), and why algorithms like cache-oblivious or blocked/tiled matrix multiplication exist specifically to maximize reuse of each cache line before it gets evicted.
