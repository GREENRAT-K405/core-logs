## DSA

### Question: Minimum Window Substring (Strings — Hard)

Given two strings `s` and `t`, find the **smallest substring** of `s` that contains every character of `t` (including duplicates — i.e., the substring's character counts must be at least `t`'s character counts for each character). If no such substring exists, return the empty string `""`. If there are multiple substrings of the same minimal length, return any one of them (we'll return the first one found by a left-to-right scan).

**Input format:**
- String `s` (the text to search within).
- String `t` (the characters that must all be covered, with multiplicity).

**Output format:**
- The shortest substring of `s` that contains all characters of `t` with at least their required multiplicity, or `""` if impossible.

**Worked Examples:**

1. `s = "ADOBECODEBANC"`, `t = "ABC"` → Output: `"BANC"`
   `"BANC"` contains `A`, `B`, and `C` and is the shortest such window. (`"ADOBEC"` also contains all three but is longer.)

2. `s = "a"`, `t = "a"` → Output: `"a"`
   The whole string is itself the minimal window.

3. `s = "a"`, `t = "aa"` → Output: `""`
   `t` requires **two** `a`s, but `s` only contains one `a` anywhere, so no valid window exists.

**Constraints:**
- `1 <= s.length, t.length <= 10^5`
- `s` and `t` consist of uppercase and lowercase English letters.
- It is guaranteed a solution exists only sometimes — your code must correctly return `""` when it doesn't.

---

### Step-by-Step Walkthrough

**Approach — Sliding Window with a character-frequency "need" map**

The brute-force approach of checking every possible substring of `s` is `O(n^2)` or worse just to enumerate windows, which is too slow for `n = 10^5`. Instead, we use the **two-pointer sliding window** technique, since the property we care about ("does this window cover all of `t`?") is monotonic in a useful way: if a window `[left, right]` is valid, shrinking it from the left might make it invalid, but we never need to re-grow it from a smaller right — we only ever need to extend `right` forward and try to shrink `left` as much as possible for each `right`.

**Step 1 — Build a frequency map of `t`.** Count how many of each character `t` requires, e.g. for `t = "ABC"`: `{A:1, B:1, C:1}`.

**Step 2 — Expand the window with a `right` pointer.** Walk `right` from `0` to `s.length - 1`, and every time we encounter a character that `t` needs, decrement a counter `have` (tracking how many of `t`'s *distinct required characters* are currently fully satisfied) — but only when that character's count in the current window transitions from "not enough" to "enough." We track per-character counts of the current window in a second map.

**Step 3 — Once the window satisfies all of `t`'s requirements (`have == need`, where `need` is the number of distinct characters in `t`), try to shrink from the left.** While the window is still valid, repeatedly:
- Check if this window is shorter than the best one found so far; if so, record it.
- Remove the leftmost character from the window (decrement its count, and if that makes a required character under-satisfied, decrement `have` and stop shrinking — advance `left` past it first).

**Step 4 — Continue expanding `right` until it reaches the end of `s`,** repeating the shrink step every time the window becomes valid again. By the end, the smallest valid window seen is the answer; if none was ever found, return `""`.

**Why it works:** Every character is only ever added to the window once (by `right`) and removed from the window once (by `left`), so each pointer only moves forward, never backward. This guarantees the total work across the whole sliding-window pass is bounded by the length of `s`, rather than being quadratic. The key correctness insight is that greedily shrinking from the left *as soon and as much as a window remains valid* always finds the true minimal window ending near that point — any window we skip over by shrinking was necessarily not shorter than one we already recorded, since we shrink until it's about to become invalid, not past that point.

**Complexity Analysis:**
- **Time complexity:** `O(|s| + |t|)`. Building the need-map from `t` is `O(|t|)`. The sliding window pass over `s` does `O(1)` amortized work per character for both the `right`-expansion and `left`-shrinking steps combined, since each index of `s` is touched a constant number of times across the whole run.
- **Space complexity:** `O(|t|)` (sometimes described as `O(1)` if the alphabet is fixed-size, e.g. 52 for upper+lowercase English letters) for the frequency maps — independent of `|s|`.

### C++ Code

```cpp
#include <iostream>
#include <string>
#include <unordered_map>
using namespace std;

class Solution {
public:
    string minWindow(string s, string t) {
        if (s.empty() || t.empty() || s.size() < t.size()) return "";

        // Frequency of each character required by t.
        unordered_map<char, int> need;
        for (char c : t) {
            need[c]++;
        }

        // Number of distinct characters whose requirement is currently satisfied
        // in the window, and how many distinct characters must be satisfied total.
        int required = need.size();
        int formed = 0;

        // Frequency of characters currently inside the window [left, right].
        unordered_map<char, int> windowCounts;

        int left = 0;
        int bestLen = INT_MAX;
        int bestLeft = 0;

        for (int right = 0; right < (int)s.size(); right++) {
            char c = s[right];
            windowCounts[c]++;

            // If c is a character t needs, and the window now has exactly enough
            // of it (not more, not less at the moment it crosses the threshold),
            // one more distinct requirement has just become satisfied.
            auto it = need.find(c);
            if (it != need.end() && windowCounts[c] == it->second) {
                formed++;
            }

            // While the current window satisfies every requirement, try to
            // shrink it from the left to find the smallest valid window ending
            // at (or before) 'right'.
            while (formed == required) {
                // Record this window if it's the smallest seen so far.
                if (right - left + 1 < bestLen) {
                    bestLen = right - left + 1;
                    bestLeft = left;
                }

                // Remove the leftmost character from the window.
                char leftChar = s[left];
                windowCounts[leftChar]--;

                auto leftIt = need.find(leftChar);
                // If leftChar is required and removing it drops the window's
                // count below what's needed, the window is no longer valid --
                // stop shrinking after this removal.
                if (leftIt != need.end() && windowCounts[leftChar] < leftIt->second) {
                    formed--;
                }

                left++;
            }
        }

        return (bestLen == INT_MAX) ? "" : s.substr(bestLeft, bestLen);
    }
};

int main() {
    Solution sol;

    // Example 1
    cout << sol.minWindow("ADOBECODEBANC", "ABC") << " (expected BANC)" << endl;

    // Example 2
    cout << sol.minWindow("a", "a") << " (expected a)" << endl;

    // Example 3
    string result3 = sol.minWindow("a", "aa");
    cout << "[" << result3 << "]" << " (expected [] i.e. empty string)" << endl;

    return 0;
}
```

**Trace against the examples:**
- `s = "ADOBECODEBANC", t = "ABC"`: `need = {A:1, B:1, C:1}`, `required = 3`. As `right` scans forward, the window first becomes valid at `right` pointing to the `C` in `"ADOBEC"` (window `"ADOBEC"`, length 6) — recorded as best so far. Shrinking from the left removes `A`, `D`, `O`, `B`, `E` one at a time until removing `B` would break validity (since `B` is required), so shrinking stops there with window `"BEC"`... continuing the scan, eventually the window `"BANC"` (length 4) is found and becomes the new best, and no shorter valid window exists afterward. Final answer: `"BANC"`. ✓
- `s = "a", t = "a"`: window immediately becomes `"a"`, which is valid and minimal. ✓
- `s = "a", t = "aa"`: `need = {a: 2}`. The window `windowCounts['a']` can reach at most `1` (only one `a` exists in `s`), so it never equals `need['a'] = 2`; `formed` never reaches `required = 1`. `bestLen` stays `INT_MAX`, so the function returns `""`. ✓

### 1. OOP (Comparison)

Compare inheritance and composition as ways to reuse code between classes. What does "favor composition over inheritance" mean in practice, and what concrete problem does composition avoid that inheritance tends to run into?

**Answer:**

**Inheritance ("is-a")** models a relationship where a subclass extends a base class, inheriting its implementation and (in languages that support it) its interface, and can override specific behavior. A `Car` class inheriting from `Vehicle` says "a `Car` *is a* `Vehicle`."

**Composition ("has-a")** models a relationship where a class holds a reference to an instance of another class and delegates to it for some behavior, rather than inheriting that behavior directly. A `Car` class holding an `Engine` member and calling `engine.start()` says "a `Car` *has an* `Engine`," without `Car` and `Engine` being related through a class hierarchy at all.

**What "favor composition over inheritance" means in practice:** when you need to reuse behavior from another class, prefer wiring in an instance of that class as a member (and delegating calls to it) over subclassing it — unless there is a genuine, stable "is-a" relationship and you specifically need polymorphic substitutability (treating many subtypes uniformly through a shared base type/pointer).

**The concrete problem composition avoids: fragile base class / rigid, exploding hierarchies.**
- Inheritance creates **tight coupling across compilation boundaries** — a subclass depends not just on its base class's public interface but often on its internal implementation details and invariants (how and when its methods call each other internally). A seemingly safe change to the base class's internals can silently break every subclass that depended on the old behavior, even though the base class's public contract didn't change. This is the classic "fragile base class problem."
- Inheritance hierarchies also tend to **explode combinatorially** when a class needs multiple independent axes of variation. Example: you want `Duck` objects that can independently vary in how they fly (`FlyWithWings`, `FlyNoWay`) and how they quack (`Quack`, `Squeak`, `MuteQuack`). Modeling this with inheritance alone forces you into a subclass for every *combination* (`MallardDuck`, `RubberDuck`, ...), and adding a third independent axis makes it worse. Composition solves this cleanly: `Duck` holds a `FlyBehavior` object and a `QuackBehavior` object as members, and any combination can be assembled at construction time or even swapped at runtime, with zero new classes needed per combination.
- Composition also keeps relationships **swappable and testable**: a class that holds a `Logger` member (an interface) can be given a real logger in production and a mock logger in a unit test, with no class-hierarchy entanglement — something far more awkward to achieve cleanly via inheritance.

**When inheritance is still the right call:** when there's a genuinely stable "is-a" relationship central to the design, and callers need to treat multiple subtypes uniformly through a common base type (e.g., a `Shape` base class with `Circle`/`Square` subtypes, where code elsewhere just wants to call `shape->area()` without caring which concrete shape it has). The guidance isn't "never use inheritance" — it's "don't reach for inheritance by default just to reuse a chunk of code when a `has-a` relationship with delegation would do the same job with less coupling."

### 2. System Design Basics (Scenario/Applied)

You're designing the caching layer for a product-catalog service that gets a very high read volume and a comparatively low write volume (prices and descriptions change a few times a day; reads happen thousands of times a second). Compare the **cache-aside** and **write-through** caching patterns for this workload, and explain which one you'd choose and why.

**Answer:**

**Cache-aside (a.k.a. lazy loading).** The application is responsible for the cache, and the cache is treated as a side-table the database doesn't know about:
- **Read:** check the cache first. On a hit, return the cached value. On a miss, read from the database, then populate the cache with that value before returning it to the caller.
- **Write:** write directly to the database, and either invalidate (delete) the corresponding cache entry or update it in place, so the next read either repopulates the cache fresh or sees the new value immediately.
- **Characteristic:** the cache is only ever populated by read-triggered misses (plus whatever a write chooses to do to the entry). This means the cache naturally only ever holds data that's actually being requested — no wasted memory on data nobody reads — but it also means the very first read after a cache miss (or after an invalidation) always pays the full database latency, a "cold" penalty.

**Write-through.** Every write goes through the cache, which synchronously writes to the database as part of the same operation (the write isn't considered complete until both the cache and the DB are updated). Reads then always hit the cache, which is guaranteed to be up to date, because no write path exists that could leave the cache stale relative to the database.
- **Characteristic:** writes get slower (every write pays the latency of updating both cache and DB, synchronously), but reads are simpler and always consistent, since the cache can't be stale — there's no window where a write has landed in the DB but not yet the cache.

**Which I'd choose here, and why: cache-aside.** This workload is read-heavy with infrequent writes, which is exactly the profile cache-aside is built for: the cost it imposes (a slower, cold first-read after a miss) is paid rarely, since writes — and therefore invalidations — happen only a few times a day, while the enormous volume of reads benefit from a cache that's warm almost all the time. Write-through would instead tax *every single write* with extra synchronous latency to keep the cache current — a cost that's wasted effort here, since the whole point of write-through (always-fresh reads with zero cold-read penalty) matters most for write-heavy or read-after-write-sensitive workloads, which this one isn't. Cache-aside also degrades more gracefully: if the cache layer goes down entirely, the application can fall back to reading straight from the database (slower, but correct), whereas a write-through design more tightly couples the write path's correctness to the cache being available.

**One addition for this scenario:** since writes (price/description changes) are infrequent but should become visible promptly, I'd pair cache-aside with a short TTL (time-to-live) on cached entries as a safety net, plus an explicit invalidation on write, so that even if an invalidation is ever missed or delayed, stale data self-corrects within a bounded window rather than staying wrong indefinitely.

### 3. Operating Systems (Comparison)

Compare a mutex and a semaphore as synchronization primitives. What is the key conceptual difference in what each represents, and why can a mutex's "unlock" only ever be called by the thread that locked it, while a semaphore's "release" has no such restriction?

**Answer:**

**Mutex (mutual exclusion lock).** A mutex represents **ownership of a single critical section by exactly one thread at a time.** It has exactly two states — locked and unlocked — and the thread that calls `lock()` is the one and only thread that is expected (and in many implementations, required) to call `unlock()`. Conceptually, a mutex answers the question "is this resource currently being used by someone, and if so, by whom?"

**Semaphore.** A semaphore represents **a count of available units of some resource** (a counting semaphore can go from `0` up to `N`; a binary semaphore is restricted to `0`/`1` and is sometimes confused with a mutex because it looks similar on the surface). `wait()`/`acquire()` decrements the count (blocking if it would go below zero), and `signal()`/`release()` increments it. Conceptually, a semaphore answers "how many units of this resource are free right now?" — with no inherent notion of *who* holds which unit.

**The key conceptual difference: ownership vs. counting.** A mutex is fundamentally about **exclusive ownership tied to a specific thread** — the lock/unlock pair is meant to bracket one thread's critical section, and the system (in many implementations) can track and enforce that the unlocking thread is the one that locked it. A semaphore has **no notion of ownership at all** — it's just a counter that any thread can increment or decrement, used to coordinate access to a *pool* of interchangeable resources (e.g., a connection pool with `N` database connections — any of the `N` threads holding one back can be the one to "release" it, and the semaphore doesn't track or care which thread incremented vs. decremented which unit).

**Why mutex unlock is restricted to the locking thread, but semaphore release isn't:**
- A mutex's entire safety guarantee rests on the invariant "only the thread that currently holds the lock may be inside the critical section." If any arbitrary thread (not the one that locked it) could call `unlock()`, a thread with no business being in the critical section could unlock it out from under the real owner — breaking mutual exclusion entirely and reintroducing the very race condition the mutex exists to prevent. Enforcing "only the owner unlocks" is what keeps that invariant airtight, and it's also what allows useful features like **priority inheritance** and deadlock-detection tooling that need to know exactly which thread owns a lock at any moment.
- A semaphore isn't protecting a single thread's exclusive access to a critical section — it's just tracking a count of available resource units. There's no "owner" concept to violate: if thread A takes a unit (decrements) and thread B is the one that finishes using that logical unit and increments the count back, that's a completely valid and common pattern (e.g., a producer thread signaling a semaphore to wake up a consumer thread that never itself called `wait()` on that particular signal — the classic producer-consumer pattern relies on exactly this asymmetry). Restricting release to only the thread that called wait() would break legitimate, common use cases like cross-thread signaling, which is a large part of why semaphores exist in the first place (mutexes alone can't coordinate "wake up a different thread when an event happens," since they're not designed for that).

**Practical rule of thumb:** use a mutex when you need to protect a critical section so that exactly one thread is inside it at a time (and that same thread must be the one to leave). Use a semaphore when you need to manage a countable pool of resources or signal between threads about events/availability, where there's no meaningful single "owner" of the lock/unlock pair.
