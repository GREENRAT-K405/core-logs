### Question: Palindrome Partitioning (Recursion/Backtracking — Medium)

**Problem Statement**

Given a string `s`, partition it such that every substring of the partition is a palindrome. Return all possible palindrome partitionings of `s`.

**Input/Output Format**

- Input: a string `s`.
- Output: a list of lists of strings, where each inner list is one valid partition of `s` into palindromic substrings, and every character of `s` is used exactly once per partition, in order.

**Examples**

1. Input: `"aab"` → Output: `[["a","a","b"], ["aa","b"]]`
2. Input: `"a"` → Output: `[["a"]]`
3. Input: `"efe"` → Output: `[["e","f","e"], ["efe"]]`

**Constraints**

- `1 <= s.length <= 16`
- `s` consists only of lowercase English letters.

### Step-by-Step Walkthrough

**Framing it as a decision tree.** At every position `start` in the string, we have to decide: how long is the *next* palindromic piece? For each candidate end position `end >= start`, if `s[start..end]` is a palindrome, we can "cut" there, recurse on the remainder starting at `end + 1`, and when we eventually reach the end of the string, the sequence of pieces we chose along the way is one valid partition. This is exactly backtracking: try a choice, recurse, undo the choice, try the next one.

**The naive palindrome check is the bottleneck.** If we check "is `s[start..end]` a palindrome" from scratch with two pointers every time we consider a cut, that's O(n) per check, and we do this inside a recursion that already explores an exponential number of branches — the checks start to dominate and repeat the same substring tests over and over across different recursive paths.

**Key insight — precompute palindromicity once.** A substring `s[i..j]` is a palindrome exactly when `s[i] == s[j]` AND the inner substring `s[i+1..j-1]` is also a palindrome (or there's no inner substring, i.e., `j - i < 2`). This is a classic overlapping-subproblems recurrence, so we fill a 2D boolean table `isPal[i][j]` bottom-up: iterate `i` from `n-1` down to `0`, and for each `i`, iterate `j` from `i` to `n-1`, using already-computed smaller substrings `isPal[i+1][j-1]`. After this O(n²) preprocessing pass, "is `s[i..j]` a palindrome?" is an O(1) table lookup.

**The backtracking itself:**
1. Maintain a `current` list of pieces chosen so far and a `start` index.
2. If `start == n`, we've partitioned the whole string — record a copy of `current` as one valid answer.
3. Otherwise, for every `end` from `start` to `n - 1`: if `isPal[start][end]` is true, push `s[start..end]` onto `current`, recurse with `start = end + 1`, then pop it off (undo) before trying the next `end`.

**Why it's correct.** The recursion explores every way to place the first cut, and for each, every way to place the next cut, and so on — this is precisely every possible partition into contiguous pieces, filtered down to only the ones where every piece is a palindrome (because we only recurse through cuts where `isPal[start][end]` holds). Backtracking (undoing the last choice before trying the next) ensures `current` always reflects exactly the path from the root to the current node, so each recorded answer is a genuinely distinct, complete partition.

**Complexity.**
- Preprocessing: O(n²) time and O(n²) space for the palindrome table.
- Search: in the worst case (e.g., `"aaaa...a"`), there are up to 2^(n-1) distinct partitions, and copying each one into the result costs O(n), giving O(n · 2ⁿ) time for the backtracking phase itself.
- Space: O(n²) for the table, plus O(n) for the recursion stack and the `current` buffer (excluding the space needed to store the output, which is unavoidable given how many partitions can exist).

### C++ Code

```cpp
#include <vector>
#include <string>
using namespace std;

class Solution {
public:
    vector<vector<string>> partition(const string& s) {
        int n = (int)s.size();

        // isPal[i][j] = true if s[i..j] (inclusive, i <= j) is a palindrome.
        // Filled bottom-up so isPal[i+1][j-1] is already known when we need it.
        vector<vector<bool>> isPal(n, vector<bool>(n, false));
        for (int i = n - 1; i >= 0; --i) {
            for (int j = i; j < n; ++j) {
                if (s[i] == s[j] && (j - i < 2 || isPal[i + 1][j - 1])) {
                    isPal[i][j] = true;
                }
            }
        }

        vector<vector<string>> result;
        vector<string> current;
        backtrack(0, s, isPal, current, result);
        return result;
    }

private:
    void backtrack(int start, const string& s, const vector<vector<bool>>& isPal,
                   vector<string>& current, vector<vector<string>>& result) {
        int n = (int)s.size();
        if (start == n) {
            result.push_back(current); // record a copy of the current partition
            return;
        }
        for (int end = start; end < n; ++end) {
            if (isPal[start][end]) {
                current.push_back(s.substr(start, end - start + 1)); // choose
                backtrack(end + 1, s, isPal, current, result);       // explore
                current.pop_back();                                  // un-choose
            }
        }
    }
};
```

## CS Fundamentals

### 1. Operating Systems (Conceptual/Definition)

**Question:** What is the difference between a process and a thread? Specifically, what does each thread of a process share with its sibling threads, what does it keep private, and why does that make threads "lighter weight" to create and switch between than processes?

**Answer:**

A **process** is an instance of a running program together with everything the OS allocates to isolate it: its own virtual address space (code, heap, data segments), its own set of open file descriptors, and at least one **thread** of execution. A **thread** is a unit of execution *within* a process — the actual sequence of instructions the CPU runs — and a single process can have many threads running concurrently.

**What threads of the same process share:** the entire address space (so they see the same global variables and heap-allocated objects directly, with no copying), open file descriptors, and other process-wide resources like signal handlers and the working directory.

**What each thread keeps private:** its own **program counter** (where it currently is in the instructions), its own **register set**, and its own **call stack** (local variables, function call/return addresses). This is the minimum a thread needs to be independently schedulable — without a private stack and program counter, two threads couldn't each be "in the middle of" different function calls at the same time.

**Why this makes threads cheaper:**
- **Creation.** Spawning a new process means the OS must set up a fresh virtual address space (new page tables, often copying or remapping the parent's memory via copy-on-write) and a fresh file descriptor table. Spawning a new thread inside an existing process just needs a new stack and register set — the address space and file descriptors already exist and are simply shared, so there's far less for the kernel to set up.
- **Context switching.** Switching between two threads of the *same* process only needs to swap the CPU registers, program counter, and stack pointer — the page table (and hence the TLB and virtual-to-physical mappings) stays valid. Switching between two *processes*, by contrast, typically means switching the page table, which invalidates the TLB (or requires tagging it by address-space ID) and causes more expensive cache/TLB misses afterward.

**The tradeoff this creates:** sharing memory makes inter-thread communication trivial (just read/write a shared variable) but makes threads mutually vulnerable — one thread corrupting shared data, or crashing via a bad pointer, can bring down the entire process, including every other thread in it. Processes are isolated from each other precisely so that one process crashing doesn't take others down with it; that isolation is also exactly what makes inter-process communication comparatively expensive (pipes, sockets, or shared memory segments that must be explicitly set up).

### 2. OOP (Comparison)

**Question:** Compare method overloading and method overriding. Both let a class present more than one "version" of behavior under the same name — what is actually different about when each is resolved, and what rules does each one have to obey?

**Answer:**

Both are forms of polymorphism, but they differ in *when* the decision of "which code actually runs" is made, which is the real distinction underneath the terminology.

**Overloading (compile-time / static polymorphism).** Multiple methods in the *same* class (or scope) share a name but differ in their parameter list — different number, order, or types of parameters. The compiler looks at the arguments at the *call site* and picks the matching version while compiling, before the program ever runs. Example: `void area(int side)` and `void area(int length, int width)` in the same class — calling `area(5)` vs `area(5, 3)` resolves to different functions purely from argument shape.

**Overriding (runtime / dynamic polymorphism).** A *derived* class redefines a method it inherited from a *base* class, keeping the exact same name and signature. Which version actually runs is decided at runtime, based on the real (dynamic) type of the object being pointed to or referenced — not the static type of the pointer/reference — which is why it requires the base method to be declared `virtual` in C++ (Java and C# make this the default): `Shape* s = new Circle(); s->draw();` calls `Circle::draw()` even though `s` is typed as `Shape*`, because the virtual dispatch mechanism (typically a vtable) looks up the function pointer appropriate to the object's actual type at the moment of the call.

**Rules each must obey:**
- Overloading requires a *different signature* — return type alone is not enough to distinguish two overloads; the compiler must be able to disambiguate from the arguments.
- Overriding requires the *same signature* (same parameters and a covariant-or-identical return type) as the base method; if you accidentally change the parameter list, you haven't overridden anything — you've created an unrelated overload that silently hides the base method instead (a classic bug), which is exactly why C++11 added the `override` keyword: it makes the compiler verify you actually matched an existing virtual function, and error out if you didn't.

**Why both exist:** overloading is about giving callers *convenience* — the same logical operation expressed for different input shapes, resolved for free by the compiler with zero runtime cost. Overriding is about letting different parts of a class hierarchy *specialize* shared behavior while still being usable interchangeably through a common base type — the entire mechanism that makes "program to an interface, not an implementation" possible.

### 3. System Design Basics (Comparison)

**Question:** Compare horizontal scaling and vertical scaling as strategies for handling increased load on a service. What are the practical limits of each, and why do most large-scale systems eventually have to adopt horizontal scaling even if vertical scaling was simpler to start with?

**Answer:**

**Vertical scaling (scaling up)** means making a single machine more powerful — more CPU cores, more RAM, faster disks — without changing the architecture of the application at all. It's the simplest option: the application code usually needs no changes, there's no distributed-systems complexity (no network calls between replicas, no data consistency questions), and it's the natural first move for a young system.

**Horizontal scaling (scaling out)** means adding *more machines* and spreading load across them, typically behind a load balancer. This requires the application to be designed for it: requests must be handled statelessly (or session state moved to a shared store) so that any instance can serve any request, and if there's a database involved, it usually needs to be partitioned (sharded) or replicated to avoid becoming the new bottleneck.

**Why vertical scaling hits a hard ceiling:**
- **Physical/hardware limits.** There is a maximum amount of CPU, RAM, and I/O bandwidth a single machine can physically hold, and that ceiling is reached long before most large services' real traffic demands.
- **Cost grows non-linearly.** The highest-end hardware tiers (the biggest CPUs, the most RAM) carry a steep price premium — doubling a machine's capacity often costs far more than double, whereas adding a second commodity machine of the same size roughly doubles cost linearly.
- **No redundancy.** A single powerful machine is still a single point of failure — if it goes down, the entire service goes down with it, regardless of how much headroom it had.

**Why horizontal scaling is where systems eventually land:**
- It has effectively no upper bound — you keep adding machines as load grows, which also means capacity can track demand incrementally rather than in big, expensive jumps.
- It gives you **fault tolerance for free**: if one instance fails, the load balancer routes around it while the others keep serving traffic, which a single scaled-up machine can never offer.
- The real cost is architectural, not financial: your application must become stateless (or externalize state), and your data layer must handle being read from and written to concurrently from many nodes — which is why teams defer this work as long as vertical scaling remains "good enough," but find it unavoidable once a single machine's ceiling is actually in sight.

The practical pattern most systems follow is therefore **vertical scaling first** (cheap, no architecture change, buys time), **horizontal scaling once that ceiling is near** (because beyond a certain point it is the only path left that also buys resilience).
