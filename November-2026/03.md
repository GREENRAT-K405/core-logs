## DSA

### Question: Partition Equal Subset Sum (Dynamic Programming — Medium)

Given an integer array `nums`, determine whether it can be partitioned into two subsets such that the sum of the elements in both subsets is equal.

**Input format:** an array of positive integers `nums`.

**Output format:** a boolean — `true` if such a partition exists, `false` otherwise.

**Examples:**

Example 1:
```
Input: nums = [1,5,11,5]
Output: true
Explanation: The array can be split into [1,5,5] and [11], both summing to 11.
```

Example 2:
```
Input: nums = [1,2,3,5]
Output: false
Explanation: The total sum is 11 (odd), so it cannot be split into two equal halves.
```

Example 3:
```
Input: nums = [1,2,3,4]
Output: true
Explanation: The array can be split into [1,4] and [2,3], both summing to 5.
```

**Constraints:**
- `1 <= nums.length <= 200`
- `1 <= nums[i] <= 100`

### Step-by-Step Walkthrough

**Reframe the problem.** Splitting `nums` into two subsets with equal sum is only possible if the total sum `S` is even — otherwise no integer split of `S` into two equal halves exists, so we can return `false` immediately. If `S` is even, the question becomes: "does some subset of `nums` sum to exactly `S / 2`?" If one such subset exists, the remaining elements automatically form the other half, since their sum is `S - S/2 = S/2` too. This reduces the problem to the classic **0/1 subset-sum** decision problem.

**Why this is a 0/1 knapsack variant.** Each number can either be included in the "target" subset or not — exactly the include/exclude choice of 0/1 knapsack, where "weight" and "value" are both just the number itself, and we only care about whether a given capacity (`target = S/2`) is exactly reachable.

**Building the DP.** Let `dp[s]` be `true` if some subset of the numbers processed *so far* sums to exactly `s`. Initialize `dp[0] = true` (the empty subset sums to 0) and all other `dp[s] = false`. For each number `num` in `nums`, for every achievable sum `s` we already know about, `s + num` becomes newly achievable. Implemented as a 1D array, this is:

```
for num in nums:
    for s from target down to num:
        dp[s] = dp[s] OR dp[s - num]
```

**Why iterate `s` from high to low.** We are reusing one 1D array across all numbers instead of allocating a fresh row per number (which a naive 2D knapsack table would do). If we updated `s` from low to high, `dp[s - num]` could already reflect the *current* number being counted twice (i.e., it would look like we can reuse the same coin/element more than once). Going from `target` down to `num` guarantees that when we read `dp[s - num]`, it still reflects only numbers processed in *previous* iterations — preserving the "use each element at most once" rule.

**Final answer.** After processing every number, `dp[target]` tells us whether a subset summing to exactly half the total exists.

**Complexity.** Let `n = nums.length` and `target = S / 2`. Time is `O(n * target)` — for each of the `n` numbers we scan up to `target` sums. With `n <= 200` and `nums[i] <= 100`, `target <= 10000`, so this is at most ~2,000,000 operations, comfortably fast. Space is `O(target)` using the 1D rolling array (the naive 2D table would cost `O(n * target)` space instead).

### C++ Code

```cpp
#include <vector>
#include <numeric>
using namespace std;

class Solution {
public:
    bool canPartition(vector<int>& nums) {
        int totalSum = accumulate(nums.begin(), nums.end(), 0);

        // An odd total can never be split into two equal integer halves.
        if (totalSum % 2 != 0) return false;

        int target = totalSum / 2;
        vector<bool> dp(target + 1, false);
        dp[0] = true; // the empty subset always sums to 0

        for (int num : nums) {
            if (num > target) continue; // this number alone can't fit in either half's target

            // Traverse right-to-left so each number is considered at most once per subset
            // (reading dp[s - num] before it gets updated for the current num).
            for (int s = target; s >= num; --s) {
                if (dp[s - num]) {
                    dp[s] = true;
                }
            }

            if (dp[target]) break; // early exit once the target sum is reachable
        }

        return dp[target];
    }
};
```

### 1. Computer Networks (Conceptual/Definition)

Describe what happens, step by step, when a browser needs to resolve a domain name like `www.example.com` into an IP address before it can open a connection. Mention the different resolvers/servers involved and what role caching plays.

**Answer:**

DNS resolution is a layered lookup that walks down the domain's hierarchy until an authoritative answer is found, with caching at nearly every step to avoid repeating work:

1. **Browser/OS cache check.** The browser first checks its own DNS cache, then the operating system's resolver cache (and, on many systems, a `hosts` file). If a non-expired record is found, resolution ends here immediately.
2. **Recursive resolver query.** If there's no local hit, the request goes to a **recursive resolver** (often run by the ISP or a public service like 8.8.8.8). This resolver's job is to do the full lookup on the client's behalf and cache the result for future queries from other clients.
3. **Root name server.** The recursive resolver (if it has nothing cached) asks a **root server**, which doesn't know the final IP but knows which **TLD (top-level domain) server** is responsible for `.com`, and returns a referral to it.
4. **TLD name server.** The resolver then asks the `.com` TLD server, which again doesn't have the final answer but knows which **authoritative name server** is responsible for `example.com`, and returns that referral.
5. **Authoritative name server.** The resolver finally asks `example.com`'s authoritative server, which holds the actual DNS records (A/AAAA, CNAME, etc.) and returns the IP address for `www.example.com`.
6. **Response and caching.** The recursive resolver returns the IP to the browser/OS, and caches the result itself for the record's TTL (time-to-live), so the next request — from this client or any other using the same resolver — can skip straight to step 2's cached answer without repeating steps 3-5.

**Why caching matters so much:** each uncached lookup requires multiple round trips across potentially different networks (root → TLD → authoritative), adding real latency before any actual application connection even begins. Because most domains are queried repeatedly by many clients, caching at the OS, resolver, and even intermediate levels means the expensive root-to-authoritative walk is a rare cold-start cost rather than something paid on every single request.

### 2. System Design Basics (Comparison)

Compare **round-robin** and **least-connections** as load-balancing strategies for distributing requests across a pool of backend servers. When does each one perform poorly?

**Answer:**

Both are algorithms a load balancer uses to pick which backend server should handle the next incoming request, but they use different information to decide:

| Aspect | Round-Robin | Least-Connections |
|---|---|---|
| **Decision basis** | Cycles through servers in fixed order, ignoring current load | Sends the request to whichever server currently has the fewest active connections |
| **State required** | Stateless (or just a pointer/counter) | Stateful — must track in-flight connection counts per server |
| **Best suited for** | Homogeneous servers with uniform, short-lived, similarly-sized requests | Heterogeneous load, or requests whose processing time varies significantly |
| **Overhead** | Very low — just increment and wrap a counter | Slightly higher — must read and update live connection counts on every request |

**When round-robin performs poorly:** if requests vary wildly in cost (e.g., one client's request triggers a huge report generation while another's is a trivial lookup), round-robin can keep sending new requests to a server that's still busy with a slow one, while a server that finished quickly sits idle until its turn comes back around. It also performs poorly if the backend servers have unequal capacity (e.g., a weaker server receives the same share of traffic as a powerful one) unless combined with weighting.

**When least-connections performs poorly:** it assumes connection count correlates with actual load, which breaks down when requests have very different costs per connection — a server could have few connections but each one is extremely CPU-heavy, making it look "underloaded" by connection count while it's actually saturated. It's also a poor fit when connections are long-lived but mostly idle (e.g., persistent WebSocket connections with little traffic), since a high connection count there doesn't mean high actual load, potentially causing the load balancer to avoid a server that has plenty of spare capacity.

In practice, many real systems improve on both with weighted variants or response-time-aware strategies, but the round-robin vs. least-connections trade-off is the right first question to ask: do you know enough about request cost variance to trust connection count as a load proxy, or is blind rotation actually safer?

### 3. Computer Architecture (Scenario/Applied)

A function runs an unpredictable data-dependent branch inside a tight loop that executes millions of times, for example `if (arr[i] > threshold) sum += arr[i];` where `arr` is unsorted random data. Profiling shows this loop runs noticeably slower than an equivalent branch-free version. Explain, in terms of CPU pipelining, why an unpredictable branch causes this slowdown, and why sorting `arr` first (even though sorting itself costs time) can make the loop faster overall.

**Answer:**

Modern CPUs use **pipelining**: while one instruction is executing, several others are already being fetched and decoded behind it, overlapped in different pipeline stages to keep throughput high. A conditional branch creates a problem for this pipeline because the CPU doesn't yet know which instruction comes *after* the branch (the "taken" path or the "not-taken" path) until the branch's condition is actually evaluated — but by then, several subsequent instructions have already needed to be fetched into the pipeline.

To avoid stalling the pipeline on every single branch, CPUs use a **branch predictor**: a hardware unit that guesses, based on the branch's recent history, which way it will go, and speculatively fetches and executes instructions down that predicted path *before* the actual condition is known.

- If the prediction is **correct**, the speculative work was useful — the pipeline never stalled, and the result is simply confirmed.
- If the prediction is **wrong** (a **misprediction**), every speculatively-executed instruction down the wrong path must be discarded, and the pipeline must be **flushed** and refilled starting from the correct path. This flush can cost on the order of 10-20 cycles on a deep pipeline — equivalent to many instructions' worth of wasted work, repeated every time the predictor guesses wrong.

**Why this loop is slow:** `arr[i] > threshold` on unsorted random data is essentially a coin flip each iteration with no learnable pattern, so the branch predictor (which relies on recent history correlating with future outcomes) performs close to as badly as random guessing — roughly a 50% misprediction rate. Each misprediction costs a pipeline flush, and with millions of iterations, these flush penalties dominate the loop's running time far more than the trivial comparison and addition themselves.

**Why sorting helps:** once `arr` is sorted, all the elements `<= threshold` come first, followed by all elements `> threshold`. The branch's outcome is now `false, false, ..., false, true, true, ..., true` — long runs of the same outcome. The branch predictor locks onto each run almost immediately and predicts correctly for the vast majority of iterations, with mispredictions now limited to roughly one single transition point rather than being spread unpredictably across the whole array. Even though sorting itself is `O(n log n)` extra work, the savings from eliminating millions of pipeline flushes in the loop can outweigh the sorting cost — this is a well-known example of how a CPU-pipeline-level concern (branch predictability) can justify an algorithmic change that has nothing to do with the loop's asymptotic complexity.
