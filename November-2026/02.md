## DSA

### Question: Minimum Cost to Make at Least One Valid Path in a Grid (Graphs — Hard)

You are given an `m x n` grid. Each cell `grid[i][j]` holds one of four signs that tells you which direction you can move **for free** if you are standing on that cell:

- `1` — points right, to `(i, j+1)`
- `2` — points left, to `(i, j-1)`
- `3` — points down, to `(i+1, j)`
- `4` — points up, to `(i-1, j)`

From any cell you may move to any of the (up to) 4 neighboring cells. If you move in the direction the current cell's sign points, it costs `0`. If you move in any other direction, it costs `1` (conceptually, you are "repainting" the sign to point the way you actually went).

You start at `(0, 0)` and want to reach `(m-1, n-1)`. Return the minimum total cost to do so. It is guaranteed a path always exists (you can always pay to redirect every sign).

**Input format:** a grid of integers, each in `{1, 2, 3, 4}`.

**Output format:** a single integer, the minimum cost.

**Examples:**

Example 1:
```
Input: grid = [[1,1,1,1],
               [2,2,2,2],
               [1,1,1,1],
               [2,2,2,2],
               [1,1,1,1]]
Output: 3
```

Example 2:
```
Input: grid = [[1,1,3],
               [3,2,2],
               [1,1,4]]
Output: 0
```

Example 3:
```
Input: grid = [[1,2],
               [4,3]]
Output: 1
```

**Constraints:**
- `1 <= m, n <= 100`
- `1 <= grid[i][j] <= 4`

### Step-by-Step Walkthrough

**Reframe it as shortest path.** Forget "signs" and think of it as a graph: every cell is a node, and from every cell there are up to 4 directed edges to its 4 grid-neighbors (if they exist). The edge that matches the cell's own sign has weight `0`; the other (up to 3) edges out of that cell have weight `1`. The question "minimum cost from `(0,0)` to `(m-1,n-1)`" is now exactly "shortest path in a weighted graph whose edge weights are only `0` or `1`."

**Why plain BFS doesn't work.** Unweighted BFS assumes every edge costs the same, but here some edges cost `0` and others cost `1` — a path with more hops can still be cheaper than a path with fewer hops if it uses more free edges. You need an algorithm that respects weights.

**Why full Dijkstra (with a priority queue) is overkill.** Dijkstra works fine here (and is a perfectly acceptable solution), but since every edge weight is either `0` or `1` — never anything else — there's a specialized, faster form of it called **0-1 BFS** that uses a plain deque instead of a heap, giving `O(V + E)` instead of `O(E log V)`.

**0-1 BFS mechanics.** Maintain a `dist` grid initialized to infinity except `dist[0][0] = 0`, and a deque of cells to process, seeded with `(0,0)`. Repeatedly pop a cell from the **front**. For each of its 4 directed edges to a neighbor:
- If the edge weight is `0` (it matches the cell's sign) and it improves the neighbor's distance, update it and push the neighbor to the **front** of the deque — it's just as "close" as the cell we popped, so it should be processed next, before any cost-1 edges we've queued.
- If the edge weight is `1` and it improves the neighbor's distance, update it and push the neighbor to the **back** — it's one step farther, so it should wait until everything currently at the same distance has been processed.

This keeps the deque's contents roughly non-decreasing in distance at all times (like a bucket queue with only two buckets), which is exactly why popping from the front always gives you a cell whose `dist` value, once finalized, is correct — the same invariant that makes plain BFS correct for unit weights, extended to two weight classes.

**Visited/finalization detail.** Because a cell can be pushed into the deque more than once before its shortest distance is confirmed (its distance might still improve after it was queued), track a `visited` array and skip processing a cell again once it's been finalized — this avoids redundant work but isn't required for correctness, only efficiency, since stale entries would simply fail every `dist[neighbor] > dist[cell] + cost` check and have no effect.

**Correctness intuition.** This is effectively Dijkstra specialized for a graph with only two distinct edge weights: instead of a general priority queue ordering by arbitrary distances, we only ever need to distinguish "same distance as what I'm currently processing" (front) from "one more than that" (back), so a deque suffices in place of a heap.

**Complexity.** Time: `O(m * n)` — each cell is finalized once, and each cell has at most 4 outgoing edges, so total edge relaxations are `O(4 * m * n) = O(m * n)`. Space: `O(m * n)` for the `dist` and `visited` grids plus the deque.

### C++ Code

```cpp
#include <vector>
#include <deque>
using namespace std;

int minCost(vector<vector<int>>& grid) {
    int m = grid.size(), n = grid[0].size();

    // dr[k], dc[k] is the move corresponding to sign (k+1): right, left, down, up.
    int dr[4] = {0, 0, 1, -1};
    int dc[4] = {1, -1, 0, 0};

    vector<vector<int>> dist(m, vector<int>(n, INT_MAX));
    vector<vector<bool>> visited(m, vector<bool>(n, false));
    deque<pair<int, int>> dq;

    dist[0][0] = 0;
    dq.push_front({0, 0});

    while (!dq.empty()) {
        auto [r, c] = dq.front();
        dq.pop_front();

        if (visited[r][c]) continue; // already finalized with a shorter/equal distance
        visited[r][c] = true;

        for (int k = 0; k < 4; ++k) {
            int nr = r + dr[k];
            int nc = c + dc[k];
            if (nr < 0 || nr >= m || nc < 0 || nc >= n) continue;

            // Moving in direction k is free only if it matches this cell's own sign.
            int cost = (grid[r][c] - 1 == k) ? 0 : 1;

            if (dist[r][c] + cost < dist[nr][nc]) {
                dist[nr][nc] = dist[r][c] + cost;
                if (cost == 0) {
                    dq.push_front({nr, nc}); // same distance bucket, process next
                } else {
                    dq.push_back({nr, nc});  // one distance bucket farther, process later
                }
            }
        }
    }

    return dist[m - 1][n - 1];
}
```

## CS Fundamentals

### 1. Operating Systems (Conceptual/Definition)

Explain the difference between a mutex and a semaphore. They're often used interchangeably in casual conversation, but they solve different problems — what is each actually for, and why can't a plain mutex replace a counting semaphore?

**Answer:**

**Mutex (mutual exclusion lock).** A mutex is a binary lock tied to the notion of ownership: at most one thread can hold it at a time, and critically, the thread that locks it is the one that must unlock it. Its entire purpose is protecting a critical section — a region of code that touches shared state that must not be modified by two threads concurrently (e.g., updating a shared counter or a shared data structure). It has exactly two states: locked/unlocked.

**Semaphore.** A semaphore is a counter-based signaling mechanism with two operations, traditionally called `wait` (or `acquire`, decrements the counter, blocking if it would go negative) and `signal` (or `release`, increments the counter, potentially waking a blocked waiter). A **counting semaphore** can have a count greater than 1, meaning up to `N` threads can proceed concurrently — this is used to limit concurrent access to a pool of `N` interchangeable resources (e.g., at most 5 threads may hold one of 5 database connections from a pool at a time). A **binary semaphore** (count capped at 1) looks superficially like a mutex, but has no ownership concept — any thread can call `signal` on it, even one that never called `wait`, because a semaphore is a general signaling primitive between threads, not an exclusive-access lock tied to a specific owner.

**Why a mutex can't replace a counting semaphore.** A mutex only ever allows 0 or 1 holders — there's no way to express "up to N threads may proceed simultaneously" with a binary lock; you'd need N separate mutexes and some way to pick a free one, which is just reinventing a counting semaphore badly. The core distinction is: a mutex answers "is this one resource currently in use by somebody, and specifically who owns it" (exclusion with ownership), while a semaphore answers "how many units of this resource are currently available" (counting/signaling, no ownership) — and a semaphore can also be used purely for signaling between threads (e.g., thread A does `signal` to wake thread B waiting on `wait`), a producer-consumer pattern a mutex alone cannot express since a mutex isn't meant to be unlocked by a different thread than the one that locked it.

### 2. DBMS (Comparison)

Compare a clustered index and a non-clustered index. Why can a table have only one clustered index but many non-clustered indexes, and why is a non-clustered index lookup typically a two-step process while a clustered index lookup isn't?

**Answer:**

**Clustered index.** A clustered index determines the **physical storage order** of the table's rows on disk — the table's actual data rows are stored sorted by the clustered index's key, inside the index's leaf nodes (in a B-tree, the leaf level literally *is* the table's data). Because the data can only be physically sorted one way at a time, a table can have **only one** clustered index (often, though not always, the primary key by default in systems like SQL Server or MySQL/InnoDB).

**Non-clustered index.** A non-clustered index is a separate structure from the table's physical row storage. Its leaf nodes store the indexed column's key values plus a pointer/reference back to the actual row — in a clustered table, that reference is typically the clustered index's key (the row's logical "address" via the clustered key), or in a heap table (no clustered index), a direct row/page identifier. A table can have many non-clustered indexes, one per query pattern you want to accelerate, since each is just an auxiliary lookup structure sitting alongside the table rather than dictating their physical order.

**Why clustered lookup is one step.** Searching a clustered index's B-tree to find a row's key takes you straight to the leaf node — and that leaf node *is* the full row's data. No further fetch needed.

**Why non-clustered lookup is typically two steps.** Searching a non-clustered index's B-tree gets you to a leaf node containing the key and a reference to the row — but not the row's other columns (unless the query only needs columns already present in the index itself, a scenario called a "covering index," which skips step two). So the engine then has to follow that reference back into the clustered index (or heap) to fetch the rest of the row's data — this second hop is often called a "bookmark lookup," and it's why a non-clustered index can satisfy a query by itself only when every requested column is part of the index, otherwise the engine pays the extra round-trip.

### 3. OOP (Scenario/Applied)

You have a base class `Shape` with a virtual `draw()` method and a non-virtual destructor. A derived class `Circle` adds its own dynamically-allocated member. Code elsewhere does `Shape* s = new Circle(); delete s;`. What goes wrong, and why does the fix (making the base destructor virtual) solve it?

**Answer:**

**What goes wrong.** When `delete s` runs and `s`'s static type is `Shape*`, the compiler decides which destructor to call based on whether `~Shape()` is virtual. Since it isn't, the call is resolved statically at compile time to `~Shape()` only — `~Circle()` is never invoked, even though the object's dynamic type is actually `Circle`. Any cleanup `~Circle()` would have done (e.g., freeing that dynamically-allocated member) never happens, causing a memory leak (and more generally, undefined behavior per the C++ standard when deleting through a base pointer with a non-virtual destructor when the dynamic type differs from the static type — in practice this most visibly manifests as the derived destructor being skipped).

**Why this doesn't happen with `draw()`.** `draw()` is declared virtual, so calls to it go through the vtable and correctly dispatch to `Circle::draw()` at runtime based on the object's actual dynamic type — this is ordinary runtime polymorphism working as intended. The destructor is the odd one out specifically because it wasn't marked virtual, so it alone falls back to static (compile-time) binding.

**Why marking `~Shape()` virtual fixes it.** Once the base destructor is virtual, destruction also goes through the vtable: `delete s` now looks up the actual dynamic type's destructor, calls `~Circle()` first (which cleans up Circle's own members), and `~Circle()`'s implicit epilogue then automatically calls `~Shape()` afterward (base destructors always run after derived ones, bottom-up, regardless of virtuality — virtuality only affects *which* destructor the `delete` expression initially dispatches to, not the base-after-derived ordering).

**The general rule.** Any class intended to be used polymorphically (i.e., any class with at least one virtual function, or any class ever deleted through a base pointer) should have a virtual destructor — this is such a common gotcha that most style guides state it as "if a class has any virtual functions, give it a virtual destructor" as a blanket rule, since the cost of making it virtual (one extra vtable entry) is negligible next to the cost of a silent resource leak.
