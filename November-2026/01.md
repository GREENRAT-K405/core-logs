## DSA

### Question: Multiply Strings (Strings — Medium)

Given two non-negative integers `num1` and `num2` represented as strings, return the product of `num1` and `num2`, also represented as a string.

You must **not** convert the inputs to integers directly or use a built-in big-integer type — the numbers may be far larger than what a 64-bit integer can hold.

**Input format:** two strings `num1`, `num2`, each containing only digits `0`–`9`, with no leading zeros unless the string is exactly `"0"`.

**Output format:** a single string representing the product, with no leading zeros (except the string `"0"` itself).

**Examples:**

Example 1:
```
Input: num1 = "2", num2 = "3"
Output: "6"
```

Example 2:
```
Input: num1 = "123", num2 = "456"
Output: "56088"
```

Example 3:
```
Input: num1 = "0", num2 = "52"
Output: "0"
```

**Constraints:**
- `1 <= num1.length, num2.length <= 200`
- `num1` and `num2` consist of digits only.
- Neither `num1` nor `num2` has leading zeros, except when the number itself is `0`.

### Step-by-Step Walkthrough

This is the "multiply on paper" algorithm, just done with array bookkeeping instead of pencil and paper.

**Why direct conversion doesn't work.** With strings up to 200 digits, the numbers can be astronomically larger than what fits in a 64-bit (or even 128-bit) integer, so parsing them into a native numeric type isn't an option — the problem is really asking you to re-implement multi-digit multiplication from scratch.

**The key observation.** If `num1` has `m` digits and `num2` has `n` digits, their product has at most `m + n` digits. So we can allocate a result buffer of exactly `m + n` integer slots up front and never worry about resizing.

**Where a single digit pair lands.** When you multiply the digit at index `i` of `num1` (from the left) by the digit at index `j` of `num2` (from the left), the digit-place value of that partial product starts at position `i + j + 1` in the result buffer (the "ones"-ish slot for that pair) and any carry from it spills into position `i + j`. This mirrors exactly what you do by hand: multiplying the units digit of one number by the units digit of the other produces a result landing in the units place, while multiplying further-left digits shifts the result further left.

**The algorithm:**
1. Allocate `result[0 .. m+n-1]`, initialized to 0.
2. For each digit `num1[i]` (iterating `i` from the last index to the first) and each digit `num2[j]` (same direction):
   - Compute `product = digit1 * digit2 + result[i+j+1]` (adding in whatever partial sum already sits there from a previous digit pair).
   - Store `product % 10` back into `result[i+j+1]`.
   - Add `product / 10` (the carry) into `result[i+j]` — it will get folded into that slot's own multiplication-and-carry step when we process it, or handled by the final carry if it overflows past 9 there too.
3. Walk the result array, skip any leading zero slots (there's at most one meaningful leading zero, from the `m+n` allocation being one slot larger than strictly necessary in most cases), and build the output string from the remaining digits.
4. Special-case `num1 == "0"` or `num2 == "0"` upfront and return `"0"` immediately, since the general algorithm would otherwise produce a string of all-zero digits that still needs trimming — simpler to just short-circuit.

**Why it works.** This is exactly long multiplication: every pair of digits contributes exactly one partial product to exactly one aligned position, and carries propagate left exactly as they would on paper. Because we accumulate directly into the shared `result` array rather than generating `n` separate shifted partial-product rows and adding them at the end, we avoid ever needing a separate "add two big numbers" step.

**Complexity.** Time: `O(m * n)` — every pair of digits is visited exactly once. Space: `O(m + n)` for the result buffer.

### C++ Code

```cpp
#include <string>
#include <vector>
using namespace std;

string multiply(string num1, string num2) {
    // Short-circuit the zero case to avoid dealing with trailing zero trimming.
    if (num1 == "0" || num2 == "0") return "0";

    int m = num1.size(), n = num2.size();
    vector<int> result(m + n, 0); // product has at most m + n digits

    for (int i = m - 1; i >= 0; --i) {
        int d1 = num1[i] - '0';
        for (int j = n - 1; j >= 0; --j) {
            int d2 = num2[j] - '0';
            // digits num1[i] and num2[j] contribute to positions i+j (carry) and i+j+1 (value)
            int sum = d1 * d2 + result[i + j + 1];
            result[i + j + 1] = sum % 10;
            result[i + j] += sum / 10;
        }
    }

    // Build the output string, skipping any leading zero slot.
    string res;
    size_t start = 0;
    while (start < result.size() - 1 && result[start] == 0) {
        ++start;
    }
    for (size_t k = start; k < result.size(); ++k) {
        res.push_back('0' + result[k]);
    }
    return res;
}
```

## CS Fundamentals

### 1. Computer Architecture (Scenario/Applied)

A process accesses a virtual address. The CPU's MMU checks the TLB first and it's a miss. Walk through what happens next, step by step, until the CPU finally has the data — including what happens if the page table says the page isn't in physical memory at all. Why does a TLB miss followed by a page fault cost orders of magnitude more time than a TLB hit?

**Answer:**

**Step 1 — TLB lookup (the fast path that just failed).** The Translation Lookaside Buffer is a small, fully-associative cache inside the MMU that stores recently-used virtual-page-to-physical-frame mappings. A hit resolves the address in roughly one clock cycle. Here, it misses, so the MMU can't translate the address immediately.

**Step 2 — Page table walk.** The MMU (or on some architectures, OS software via a trap) walks the page table structure for this process. Modern systems use multi-level page tables (e.g., a 4-level hierarchy on x86-64): the virtual address is split into index fields, and each level's entry points to the table (or frame) for the next level. Each level is a separate memory access, so a walk that misses all the way down can cost 3–4 extra memory round-trips just to find the mapping — this alone is already far slower than the 1-cycle TLB hit, since each access can be a full DRAM round trip (~100+ cycles) if it also misses the regular CPU cache.

**Step 3a — If the page table entry is valid (page is in RAM).** The walk ends with a valid physical frame number. The MMU completes the translation, the result is inserted into the TLB (evicting some existing entry to make room), and the instruction that triggered the access simply proceeds to use the physical address.

**Step 3b — If the page table entry says "not present" (page fault).** This means the page isn't currently backed by physical memory — it might never have been loaded (demand paging), or it was evicted/swapped out to disk. The MMU raises a page fault exception, trapping into the OS's page fault handler. The handler must: (1) determine this is a legitimate fault, not an illegal access (check against the process's memory map / VMAs); (2) find a free physical frame, evicting another page via the replacement policy (e.g., approximated LRU) if none is free; (3) issue a disk I/O to read the required page's contents from the backing store (swap space or the executable's file-backed mapping); (4) update the page table entry to point at the new frame and mark it present; (5) insert the new mapping into the TLB; (6) resume the faulting instruction, which now re-attempts the memory access from scratch — this time hitting the TLB.

**Why the cost gap is so large.** A TLB hit is ~1 cycle. A TLB miss resolved by a page table walk that hits RAM is maybe 10s–100s of cycles (several dependent memory accesses). But a page fault that must go to disk involves an OS trap (context switch overhead), scheduling another process while waiting (since disk I/O is enormously slow relative to the CPU), and an actual disk/SSD access — which, even on a fast SSD, is in the range of tens of thousands to millions of cycles, versus nanoseconds for a cache or TLB hit. That's roughly 5–6 orders of magnitude slower than the TLB-hit path, which is precisely why operating systems work so hard to minimize page faults (prefetching, working-set-aware replacement policies) and why thrashing (constant page faults because the working set doesn't fit in RAM) devastates performance.

### 2. OOP (Comparison)

Compare abstract classes and interfaces as two ways to define a contract that other classes must implement. What can an abstract class do that a plain interface cannot, and when would you reach for one over the other?

**Answer:**

Both let you define methods that implementing/subclassing types are obligated to provide, but they differ in what else they carry and how a class can combine them.

| | Abstract Class | Interface |
|---|---|---|
| Instance state (fields) | Yes — can hold real fields with values shared via inheritance | No instance fields (in most languages); only method signatures (plus constants, and default/static methods in languages like Java 8+) |
| Implementation | Can provide concrete method bodies alongside abstract ones | Traditionally none; some languages now allow default method bodies, but still no state to back them |
| Multiple inheritance | A class can extend only **one** abstract class in most mainstream OOP languages | A class can implement **many** interfaces |
| Constructors | Can have constructors, run during subclass construction | Cannot have constructors — there's no state to initialize |
| Relationship implied | "is-a" with shared lineage and shared implementation | "can-do" — a capability contract, no implied shared ancestry |

**What an abstract class gives you that an interface doesn't.** Shared, inherited implementation and state. If several related subclasses need the same field layout and the same non-trivial method bodies (not just the same method signatures), an abstract class lets you write that logic once in the base class and have every subclass inherit it for free — a pure interface (without default methods) can't share a single line of implementation.

**What an interface gives you that an abstract class doesn't.** The ability for one class to satisfy many unrelated contracts simultaneously. A class can't extend two abstract classes, but it can implement `Comparable`, `Serializable`, and `Runnable` all at once, because an interface imposes no constraint on what else the class already inherits from.

**When to choose which.** Reach for an abstract class when you have a genuine, narrow hierarchy of closely related types that should share real implementation and state — e.g., a `Shape` base class holding a `color` field and a concrete `describe()` method, with subclasses `Circle` and `Square` only needing to override `area()`. Reach for an interface when you're describing a capability that unrelated classes might all want to advertise — e.g., anything "comparable" or "serializable" — without forcing them into a shared ancestry they otherwise have no business sharing. In practice, most modern designs favor interfaces by default (composition/capability over rigid hierarchy) and use abstract classes only when there's real, non-trivial implementation worth sharing.

### 3. System Design Basics (Conceptual/Definition)

Define cache-aside, write-through, and write-back as caching strategies for a database-backed application. For each, say where a write goes first, and explain why write-back gives the best write latency but carries the highest risk of data loss.

**Answer:**

These three strategies differ in **when** the cache gets populated and **where a write is considered "done."**

**Cache-aside (lazy loading).** The application talks to the cache and the database separately. On a read: check the cache first; on a miss, read from the database and then populate the cache for next time. On a write: write directly to the database, and either invalidate the corresponding cache entry or update it afterward. The cache is only ever populated by reads (or explicit invalidation on write), never automatically kept in sync by the caching layer itself — the application owns that logic. If the app crashes right after writing to the database but before invalidating the cache, the cache can briefly serve stale data until it's evicted or explicitly refreshed.

**Write-through.** Every write goes to the cache **and** synchronously to the database as part of the same operation, before the write is considered complete. This keeps the cache always consistent with the database, at the cost of every write paying the full database write latency (the cache write doesn't save you anything on the write path — it only speeds up later reads). If the app or cache crashes right after this, there's no data loss, because the database write already completed as part of the same operation.

**Write-back (write-behind).** A write goes to the cache only, and is acknowledged as complete immediately — the database update is deferred and flushed asynchronously later (on a timer, or when the dirty entry is evicted). This makes writes extremely fast, since the caller never waits on the database. The risk: if the cache crashes (or the machine loses power) before that deferred flush happens, the write is lost entirely, because the database never received it and the cache's copy — the only place it existed — is gone. This is exactly the latency-vs-durability trade-off: write-back is fastest because it defers the expensive, durable write, but that same deferral is what creates a window where an acknowledged write can vanish.

**The underlying trade-off.** Cache-aside gives the application the most control but pushes consistency logic onto it. Write-through trades write latency for strong cache/database consistency and no data-loss window. Write-back trades that safety margin for the lowest possible write latency, which is why it's typically only used where either the data is non-critical, there's a replicated/durable write-ahead log backing the cache itself, or the business accepts a small loss window in exchange for throughput.
