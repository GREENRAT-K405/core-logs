### Question: Longest Palindromic Substring (Strings — Medium)

Given a string `s`, return the **longest palindromic substring** of `s`. A palindrome reads the same forwards and backwards. If there are multiple substrings of the same maximum length, you may return any one of them.

**Input format:** a string `s`.
**Output format:** a string — the longest contiguous substring of `s` that is a palindrome.

**Example 1:**
```
Input: s = "babad"
Output: "bab"
Explanation: "aba" is also a valid answer of the same length (3). Either is accepted.
```

**Example 2:**
```
Input: s = "cbbd"
Output: "bb"
Explanation: "bb" is the only palindromic substring of length 2; no longer palindrome exists.
```

**Example 3:**
```
Input: s = "a"
Output: "a"
Explanation: A single character is trivially a palindrome of length 1.
```

**Constraints:**
- `1 <= s.length <= 1000`
- `s` consists of digits and English letters.

### Step-by-Step Walkthrough

**Why brute force is too slow.** Checking every one of the `O(n^2)` substrings for the palindrome property (an `O(n)` check each) costs `O(n^3)` overall. With `n <= 1000` that's up to ~10^9 operations — too slow to rely on for the worst case, so we need a smarter structure.

**The center-expansion insight.** Every palindrome is symmetric around a center. That center is either:
- a single character, for an odd-length palindrome (e.g. `"aba"` is centered on the middle `b`), or
- the gap between two adjacent characters, for an even-length palindrome (e.g. `"bb"` is centered between the two `b`s).

A string of length `n` has exactly `2n - 1` such centers (`n` single-character centers plus `n - 1` between-character gaps). The key idea: instead of checking all `O(n^2)` substrings independently, check all `O(n)` *centers*, and for each one, greedily expand outward in both directions as long as the characters on either side keep matching. Expansion from a true palindrome's center will always reach that palindrome's full extent (and never further, since the first mismatch necessarily stops it), so this is guaranteed to find the actual longest palindrome, not an approximation.

**Algorithm.**
1. For every index `i` from `0` to `n - 1`, run `expandFromCenter(i, i)` to find the longest odd-length palindrome centered at `i`, and `expandFromCenter(i, i + 1)` to find the longest even-length palindrome centered between `i` and `i + 1`.
2. `expandFromCenter(left, right)` repeatedly moves `left` outward (decrementing) and `right` outward (incrementing) while both stay in bounds and `s[left] == s[right]`. When the loop stops, the palindrome's true boundaries are `(left + 1, right - 1)`, so its length is `right - left - 1`.
3. Track the maximum length seen across all `2n - 1` centers, and recover the starting index of that best palindrome to build the answer substring at the end (rather than slicing a new string on every expansion, which would waste time and memory).

**Why this is correct.** Any palindromic substring, by definition, has a well-defined center (single character or a gap). When we process that exact center, our expansion cannot stop before reaching that palindrome's actual boundaries, because by definition every character pair within it matches. So the longest palindrome overall is guaranteed to be found at the center-expansion step for its own center — we just need to check all `2n - 1` candidate centers to be sure we hit it.

**Complexity.**
- Time: `O(n)` centers, each expansion costs at most `O(n)` in the worst case (e.g. all characters identical), giving `O(n^2)` total — well within budget for `n <= 1000`.
- Space: `O(1)` auxiliary space (a DP table approach would use `O(n^2)` space for the same `O(n^2)` time, so center-expansion is strictly better on space).

### C++ Code

```cpp
#include <string>
#include <algorithm>
using namespace std;

class Solution {
public:
    // Expands outward from a center defined by (left, right) as long as the
    // characters match; returns the length of the palindrome found there.
    int expandFromCenter(const string& s, int left, int right) {
        while (left >= 0 && right < (int)s.size() && s[left] == s[right]) {
            left--;
            right++;
        }
        // (left, right) now sit one step past the palindrome's true edges,
        // so the palindrome itself spans (left + 1, right - 1).
        return right - left - 1;
    }

    string longestPalindrome(string s) {
        if (s.empty()) return "";

        int start = 0, maxLen = 1;

        for (int i = 0; i < (int)s.size(); i++) {
            int lenOdd = expandFromCenter(s, i, i);       // odd-length center at i
            int lenEven = expandFromCenter(s, i, i + 1);   // even-length center between i, i+1

            int len = max(lenOdd, lenEven);
            if (len > maxLen) {
                maxLen = len;
                // Recover the leftmost index of this palindrome from its
                // center i and its length.
                start = i - (len - 1) / 2;
            }
        }

        return s.substr(start, maxLen);
    }
};
```

Checking against the examples: `"babad"` finds a length-3 palindrome (`"bab"`, with `"aba"` tied and equally valid) and returns the first one encountered; `"cbbd"` finds `"bb"` as the unique longest; `"a"` returns `"a"` since the loop's single center trivially gives length 1. The even-center check (`i, i + 1`) naturally handles the case where `i + 1` is out of bounds — the bounds check inside `expandFromCenter` catches it immediately, so no separate edge-case handling is needed for the last index.

### 1. DBMS (Conceptual/Definition)

What does the **Isolation** property in ACID guarantee for a database transaction, and what concrete anomaly can still occur if a database runs at a weaker isolation level like "Read Committed" instead of "Serializable"? Give a short example.

**Answer:**

Isolation guarantees that concurrently executing transactions behave as if they ran one after another in some serial order, even though the database may actually be interleaving their operations for performance. The strongest isolation level, **Serializable**, enforces this fully: the end result is always equivalent to *some* serial ordering of the transactions, with no cross-transaction interference visible at all.

Weaker isolation levels trade some of that guarantee for better concurrency (less locking, fewer conflicts, higher throughput). **Read Committed** only guarantees that a transaction never sees *uncommitted* data from another transaction (no "dirty reads"), but it does not guarantee that repeated reads within the same transaction see consistent data.

Concrete anomaly — **non-repeatable read**: Transaction A reads a row (`balance = 100`). Before A finishes, Transaction B updates that same row (`balance = 200`) and commits. If A reads the row again, it now sees `200` — the value changed out from under it mid-transaction, even though A never modified it itself. Under Serializable isolation this couldn't happen, because the database would force an ordering where either all of A's work happens entirely before B's, or entirely after.

A related anomaly specific to range queries is the **phantom read**: Transaction A runs `SELECT COUNT(*) FROM orders WHERE amount > 100` twice within the same transaction. Between the two reads, Transaction B inserts a new matching row and commits. A's second count is higher than its first, even though A issued the identical query both times — a "phantom" row appeared. Read Committed does not prevent this; only stricter levels (Repeatable Read, with some engines, or Serializable) do.

The underlying tradeoff: higher isolation levels prevent more anomalies but require more locking or more aggressive conflict detection (e.g. via MVCC version checks), which reduces concurrency and throughput — so systems expose the isolation level as a tunable choice rather than always defaulting to the strictest one.

### 2. Computer Architecture (Comparison)

Compare the **write-through** and **write-back** cache policies: how does each handle a CPU write to a cached memory location, and what is the tradeoff between them?

**Answer:**

Both policies answer the same question: when the CPU writes to a memory address that is currently cached, when does main memory actually get updated?

**Write-through:** every write to a cache line is immediately propagated to main memory as well, synchronously (or via a write buffer that still guarantees it happens promptly). Cache and memory are kept consistent at essentially all times.
- Upside: simplicity — memory always reflects the latest value, so there's no risk of losing data if the system crashes, and cache coherence in multiprocessor systems is easier to reason about since memory is always authoritative.
- Downside: much higher memory traffic. Every single store instruction generates a memory write, even if the same cache line is overwritten many times in a row (e.g. a loop counter) — memory bandwidth is spent on writes that would otherwise be absorbed entirely by the cache.

**Write-back:** a write only updates the cache line itself, which is then marked **dirty** (via a dirty bit). The line is written back to main memory only later — when it is evicted from the cache to make room for something else, or during an explicit flush.
- Upside: far less memory traffic, since many writes to the same line over time collapse into a single eventual memory write when the line is evicted. This is the dominant policy in modern CPUs because write locality (repeatedly touching the same line) is extremely common.
- Downside: added complexity and risk. The cache must track dirty state per line. If the system loses power or crashes before a dirty line is flushed, that data is lost (which is why battery-backed or non-volatile caches matter in storage controllers). In multiprocessor systems, write-back also complicates **cache coherence**: other cores can't just read memory and trust it, since the "true" latest value might only exist dirty inside one core's cache — protocols like MESI exist specifically to track and resolve this.

The core tradeoff is **memory bandwidth and write latency versus consistency simplicity and crash safety**: write-through keeps memory as the single source of truth at the cost of traffic; write-back minimizes traffic at the cost of needing extra bookkeeping (dirty bits, coherence protocols, and flush-on-eviction logic) to make sure the "true" latest value is found and propagated correctly when it's needed.

### 3. Computer Networks (Scenario/Applied)

A client tries to open a TCP connection to a server, but the initial SYN packet is silently dropped by a flaky router along the path. Walk through what happens next from the client's perspective, and explain why TCP uses a **three-way handshake** rather than a simpler two-way one.

**Answer:**

**What happens after the dropped SYN:** TCP doesn't rely on the network to guarantee delivery, so the client protects itself with a retransmission timer. When the client sends the SYN, it starts a timer (the initial retransmission timeout, commonly around 1 second, implementation-dependent) and waits for a SYN-ACK. Since the SYN never arrived, no SYN-ACK comes back, and when the timer expires the client retransmits the SYN. If that also fails, TCP typically doubles the timeout each attempt (**exponential backoff**) and retries a bounded number of times (often 5-6 attempts across most OS defaults) before giving up and surfacing a connection-timeout error to the application. If the retransmitted SYN gets through, the handshake proceeds normally from there: server replies with SYN-ACK, client replies with ACK, and the connection is established — just a bit later than if the first packet had arrived cleanly.

**Why three-way, not two-way:** A connection handshake has to accomplish two things simultaneously: each side must (a) learn the other side's **initial sequence number** (ISN), which is how TCP later detects lost, duplicate, or reordered segments, and (b) get confirmation that the other side is actually ready and that *this specific* connection attempt was received (not a stale, delayed duplicate of an old one).

A two-way handshake (client sends SYN, server replies SYN-ACK, and the client is assumed connected without replying) fails on both counts:
- The server would never get confirmation that the client actually received its SYN-ACK and its proposed ISN. If that SYN-ACK is lost, the server would believe a connection exists while the client knows nothing was established — a half-open connection with no implicit way to clean itself up.
- It's also vulnerable to old, delayed duplicate SYNs floating around the network from a previous (already-closed) connection attempt. If the server simply trusted any SYN-ACK exchange as sufficient, a late-arriving stale SYN could trigger the server into allocating resources for a "connection" the client never actually asked to open now.

The third leg (`client -> ACK`) closes that gap: it's the client's explicit proof, acknowledging the server's chosen ISN, that the client did receive the SYN-ACK and still wants this connection *now*. Only after that ACK does the server consider the connection fully established. This is why TCP's state machine has an explicit "half-open" state after step two and only transitions to "established" after the third leg — the three-way handshake is the minimum number of messages needed for both sides to simultaneously confirm "I'm here, I got your sequence number, and this attempt is current," rather than just one side guessing the other is ready.
