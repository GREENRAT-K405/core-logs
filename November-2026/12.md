### Question: Split Array Largest Sum (Sorting/Searching — Hard)

Given an integer array `nums` and an integer `k`, split `nums` into `k` non-empty **contiguous** subarrays. Among all possible ways to split, minimize the **largest sum** of any individual subarray, and return that minimized value.

**Input format:** an array of non-negative integers `nums`, and an integer `k` (the number of subarrays to split into).
**Output format:** a single integer — the smallest possible value of the maximum subarray sum, over all valid splits into exactly `k` contiguous parts.

**Example 1:**
```
Input: nums = [7,2,5,10,8], k = 2
Output: 18
Explanation: Split as [7,2,5] and [10,8]. Sums are 14 and 18. The max is 18.
Any other split into 2 parts produces a larger maximum (e.g. [7,2,5,10] / [8] gives max 24).
```

**Example 2:**
```
Input: nums = [1,2,3,4,5], k = 2
Output: 9
Explanation: Split as [1,2,3] and [4,5]. Sums are 6 and 9. The max is 9, which is the smallest
achievable maximum.
```

**Example 3:**
```
Input: nums = [1,4,4], k = 3
Output: 4
Explanation: With k equal to the array length, each element is its own subarray: sums 1, 4, 4. Max is 4.
```

**Constraints:**
- `1 <= nums.length <= 1000`
- `0 <= nums[i] <= 10^6`
- `1 <= k <= min(50, nums.length)`

### Step-by-Step Walkthrough

**Reframing the problem.** Directly searching over all ways to place `k - 1` split points is exponential. Instead, notice the question is really: "what is the smallest value `limit` such that `nums` *can* be split into `k` or fewer contiguous pieces, none exceeding `limit`?" That reframing turns an optimization problem into a decision problem we can binary search on.

**Why the decision problem is monotonic.** Define `f(limit)` = the minimum number of contiguous pieces needed so that every piece's sum is `<= limit`, computed greedily (keep extending the current piece until adding the next element would exceed `limit`, then start a new piece). As `limit` increases, you never need *more* pieces — bigger allowed pieces can only merge smaller ones, never force a split. So `f` is monotonically non-increasing in `limit`. That monotonicity is exactly what makes binary search valid: we want the smallest `limit` with `f(limit) <= k`.

**Search bounds.**
- Lower bound `lo = max(nums)`: no subarray can have a sum smaller than the single largest element, since that element must live in some subarray.
- Upper bound `hi = sum(nums)`: putting everything in one subarray (k = 1) trivially satisfies any `k >= 1`.

**Binary search.** While `lo < hi`, compute `mid = lo + (hi - lo) / 2` and run the greedy piece-counter:
- If the number of pieces needed to respect `mid` is `<= k`, then `mid` is a *feasible* answer (we could even use fewer than k splits, or pad with empty-ish tiny splits since we're allowed up to k pieces) — try to shrink: `hi = mid`.
- Otherwise `mid` is too tight (would require more than `k` pieces) — raise the floor: `lo = mid + 1`.

The loop converges when `lo == hi`, which is the minimal feasible largest-sum.

**Greedy piece counter correctness.** For a *fixed* `limit`, the greedy "keep extending until you'd overflow" approach is provably optimal: it never finishes a piece sooner than necessary, so it uses the fewest possible pieces for that `limit`. This is the key subroutine the binary search leans on at each step.

**Complexity.**
- Time: the greedy counter is `O(n)` per check, and binary search runs `O(log(sum(nums) - max(nums)))` times, giving `O(n log(sum(nums)))` overall — with `sum(nums) <= 10^9`, that's at most ~30 iterations, each `O(n)`.
- Space: `O(1)` auxiliary space beyond the input array.

### C++ Code

```cpp
#include <vector>
#include <algorithm>
using namespace std;

class Solution {
public:
    // Minimum number of contiguous pieces needed so no piece's sum exceeds 'limit'.
    int countPieces(vector<int>& nums, long long limit) {
        int pieces = 1;
        long long currentSum = 0;
        for (int num : nums) {
            if (currentSum + num > limit) {
                // Current piece would overflow; close it and start a new one.
                pieces++;
                currentSum = num;
            } else {
                currentSum += num;
            }
        }
        return pieces;
    }

    int splitArray(vector<int>& nums, int k) {
        long long lo = 0, hi = 0;
        for (int num : nums) {
            lo = max(lo, (long long)num); // largest single element
            hi += num;                    // sum of everything
        }

        while (lo < hi) {
            long long mid = lo + (hi - lo) / 2;
            int piecesNeeded = countPieces(nums, mid);

            if (piecesNeeded <= k) {
                // 'mid' is an achievable cap; try for something smaller.
                hi = mid;
            } else {
                // 'mid' is too tight to fit in k pieces; raise the floor.
                lo = mid + 1;
            }
        }

        return static_cast<int>(lo);
    }
};
```

Checking against the examples: `[7,2,5,10,8], k=2` converges to `18`; `[1,2,3,4,5], k=2` converges to `9`; `[1,4,4], k=3` converges to `4` — matching the expected outputs above, and the `k == n` edge case (every element its own piece) falls out naturally since `lo` already equals `max(nums)` and the greedy counter never needs more than `n` pieces.

### 1. Computer Networks (Scenario/Applied)

Your company's main website serves the same product images, CSS, and JS bundles to users worldwide, and users far from your origin server complain about slow page loads. You're told "just put it behind a CDN." Explain mechanically what a CDN does to fix this, and describe one specific problem that appears once some of that site's content becomes personalized per-user (e.g. a "Hello, Alice" banner) rather than identical for everyone.

**Answer:**

A CDN (Content Delivery Network) is a geographically distributed set of proxy/edge servers that sits between users and your origin server. Mechanically, it fixes the latency problem in two ways:

1. **Shorter network path.** DNS (often via anycast or geo-DNS) routes a user's request to the edge server that's topologically/geographically nearest to them, instead of all the way to your origin. This cuts round-trip time, since latency is dominated by physical distance and number of network hops.
2. **Caching.** The first user near a given edge server triggers a cache miss — the edge fetches the asset from the origin once, stores it, and serves every subsequent nearby request directly from that cached copy (governed by `Cache-Control`/`Expires` headers and a TTL). This also offloads traffic from the origin, so it isn't a bottleneck under load, and reduces bandwidth cost since the origin only serves each asset once per edge location rather than once per user.

This works great for **static** content (images, CSS, JS, videos) because the same bytes are correct for every user.

The problem appears with **personalized/dynamic** content: a page with "Hello, Alice" can't simply be cached and replayed to the next visitor — "Bob" would see Alice's name. Mechanisms to handle this include:
- Caching only the static shell/assets at the edge, and fetching the personalized fragment from the origin via an API call or edge-side include, so the CDN still helps with the bulk of the payload.
- Edge computing/edge functions that run small amounts of personalization logic *at* the edge (e.g. reading a cookie) without a round trip to origin.
- Marking personalized responses `Cache-Control: private, no-store` (or similar) so the CDN never caches them and always proxies through to origin, which solves correctness but gives up the latency/offload benefit for that part of the response.

The underlying tension: caching only works where many users can safely share one response; as soon as a response is a function of *who is asking*, the CDN has to either split the response into cacheable/non-cacheable parts or bypass the cache entirely for that content.

### 2. OOP (Conceptual/Definition)

What is the "diamond problem" in object-oriented programming, and why does it specifically arise with multiple inheritance (a class inheriting from two or more classes that share a common ancestor)? Briefly contrast how a language that forbids multiple class inheritance (like Java, via single inheritance + interfaces) avoids it versus how a language that allows it (like C++) has to resolve it.

**Answer:**

The diamond problem occurs when a class `D` inherits from two classes `B` and `C`, both of which inherit from a common base class `A`. The inheritance graph looks like a diamond:

```
      A
     / \
    B   C
     \ /
      D
```

If `A` defines a method or a data member, and neither `B` nor `C` overrides it, then `D` has **two separate inherited paths** to the same member in `A`. The compiler/runtime faces an ambiguity: does `D` have one copy of `A`'s state (shared through both paths) or two independent copies (one via `B`, one via `C`)? And if `D` calls the inherited method, which path's version should run if `B` and `C` each overrode it differently? Both "which implementation wins" and "is there one `A` or two" are genuinely ambiguous without an explicit rule.

**Java's approach:** Java sidesteps the problem entirely by disallowing multiple inheritance of *classes* — a class can extend only one superclass. A class can, however, implement multiple *interfaces*. Since (traditionally) interfaces carried no state and no implementation, there was nothing to duplicate or disambiguate. Modern Java allows interfaces to have `default` methods, which reintroduces a milder version of the ambiguity (two interfaces providing conflicting default methods) — Java resolves *that* by forcing the implementing class to explicitly override the method and choose (or combine) a behavior; it's a compile error to leave it unresolved.

**C++'s approach:** C++ allows true multiple inheritance of classes, so it has to resolve the diamond directly. By default, `D` gets **two independent copies** of `A` (one through `B`, one through `C`), which avoids ambiguity about "whose data is this" but can be wasteful and surprising (modifying "the" `A` member through `B`'s path doesn't affect the copy reached through `C`'s path). To get a single shared copy, C++ requires `B` and `C` to inherit from `A` using the `virtual` keyword (`class B : virtual public A`), which tells the compiler to allocate exactly one shared `A` sub-object for `D`, resolved via a virtual base pointer. Method-call ambiguity (if both `B` and `C` override the same method) still has to be resolved explicitly by `D`, e.g. by overriding the method itself and choosing which parent's version to call.

The core lesson: multiple inheritance is powerful but forces a language to pick an explicit answer to "which ancestor's state/behavior wins," and language designers differ in whether they avoid the question (Java, via single class inheritance) or answer it with explicit tooling (C++, via virtual inheritance).

### 3. System Design Basics (Conceptual/Definition)

What problem does **consistent hashing** solve that a naive "hash the key mod N servers" scheme does not, in a system where servers (cache nodes, shards, etc.) are added or removed? Explain how consistent hashing achieves this.

**Answer:**

With naive hashing, you map a key to a server with something like `server = hash(key) % N`, where `N` is the current number of servers. This works while `N` is fixed, but the moment `N` changes — a server is added or removed — almost every key's `hash(key) % N` value changes too, because the modulus itself changed. In practice this means nearly the entire dataset has to be remapped and re-shuffled across servers (cache invalidation storm, or a huge data-migration event for a sharded store) just because one server joined or left. For a cache, that's catastrophic: a near-total cache miss wave hits the origin all at once right when the system was already being resized, often *because* of load problems.

**Consistent hashing** fixes this by decoupling "which server a key goes to" from the exact count of servers. The standard construction:

1. Hash both the servers and the keys onto the same fixed circular space (a "hash ring"), e.g. values from `0` to `2^32 - 1` arranged in a circle. Each server is placed at one or more points on the ring (hashing the server's ID/address).
2. To find which server owns a key, hash the key onto the ring and walk clockwise until you hit the first server point. That server owns the key.
3. When a server is **added**, it only takes ownership of the keys between itself and the next server counter-clockwise on the ring — it "steals" a contiguous arc of keys from exactly one neighbor, not from everyone.
4. When a server is **removed**, its arc of keys simply falls to the next server clockwise — again, only that one neighbor is affected.

So instead of remapping `O(all keys)` on a membership change, consistent hashing only remaps `O(keys owned by the one affected arc)` — roughly `1/N` of the keyspace on average, not all of it.

One refinement worth knowing: hashing each physical server to a single ring point can produce very uneven arcs (hot spots) if server hash values happen to cluster. The fix is **virtual nodes**: each physical server is hashed to many points on the ring (e.g. 100–200 "replicas"), which smooths out load distribution and makes the arc each server owns closer to a fair `1/N` share, while keeping the same "only affected neighbors move" property on membership changes. This is the same idea used by systems like Amazon's Dynamo and many distributed caches (e.g. consistent-hash-based client libraries for Memcached).
