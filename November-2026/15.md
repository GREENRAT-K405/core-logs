### Question: Longest Increasing Subsequence (Dynamic Programming — Medium)

**Problem Statement**

Given an integer array `nums`, return the length of the longest strictly increasing subsequence. A subsequence is derived by deleting zero or more elements without changing the order of the remaining elements; it does not need to be contiguous.

**Input/Output Format**

- Input: an integer array `nums`.
- Output: an integer, the length of the longest strictly increasing subsequence.

**Examples**

1. Input: `[10,9,2,5,3,7,101,18]` → Output: `4` (one valid subsequence is `[2,3,7,101]`)
2. Input: `[0,1,0,3,2,3]` → Output: `4` (one valid subsequence is `[0,1,2,3]`)
3. Input: `[7,7,7,7,7,7,7]` → Output: `1` (the sequence must be *strictly* increasing, so repeats don't extend it)

**Constraints**

- `1 <= nums.length <= 2500`
- `-10^4 <= nums[i] <= 10^4`
- Aim for better than O(n²) if possible.

### Step-by-Step Walkthrough

**The O(n²) DP first.** Define `dp[i]` as the length of the longest increasing subsequence that *ends exactly at index i*. For each `i`, look back at every `j < i`: if `nums[j] < nums[i]`, then `nums[i]` can extend whatever subsequence ends at `j`, giving a candidate length `dp[j] + 1`. Taking the best such candidate (or `1` if no earlier element is smaller) gives `dp[i] = 1 + max(dp[j] for j < i where nums[j] < nums[i])`. The answer is `max(dp)` over all `i`, because the longest subsequence overall must end somewhere. This is correct and easy to reason about, but it's O(n²) time — for `n = 2500` that's ~6.25M operations, fine here, but we can do asymptotically better.

**The key reframing for O(n log n).** Instead of tracking subsequences by where they *end* in the array, track them by *length*. Maintain an array `tails` where `tails[k]` holds the smallest possible tail value among all increasing subsequences of length `k + 1` found so far. Two facts make this work:

1. `tails` is always sorted. If a subsequence of length `k+2` exists with some tail value, you can always drop its last element to get a subsequence of length `k+1` with a strictly smaller tail — so the smallest tail for length `k+2` is never smaller than the smallest tail for length `k+1`.
2. For a new number `num`, the smaller we can keep a subsequence's tail at a given length, the more future numbers can extend it. So for each `num`, we want to place it at the *leftmost* position in `tails` where it can go.

So for each `num` in `nums`: binary search `tails` for the first position whose value is `>= num` (`lower_bound`).
- If no such position exists (`num` is bigger than every tail), `num` extends the longest subsequence found so far — append it, growing `tails`.
- Otherwise, `num` gives a strictly smaller tail for that subsequence length than what's currently stored — overwrite that position.

Crucially, `tails` after processing a prefix of the array is **not necessarily an actual subsequence that appears in `nums`** — it's a bookkeeping structure. What *is* guaranteed is that `tails.size()` always equals the length of the true longest increasing subsequence of the prefix processed so far, which is exactly what we return at the end.

**Why it's correct.** Each replacement in `tails` can only make an entry smaller or equal, never larger, which preserves invariant (1) and never destroys a potential extension that existed before. Each append corresponds to genuinely finding one more element than any previously known subsequence could use, so `tails.size()` tracks the true LIS length exactly.

**Complexity.**
- Time: O(n log n) — one binary search (O(log n)) per element of `nums` (O(n) elements).
- Space: O(n) for the `tails` array in the worst case (a fully sorted input).

### C++ Code

```cpp
#include <vector>
#include <algorithm>
using namespace std;

int lengthOfLIS(vector<int>& nums) {
    // tails[k] = smallest tail value among increasing subsequences of length k + 1
    vector<int> tails;

    for (int num : nums) {
        // Find the first position whose value is >= num.
        auto it = lower_bound(tails.begin(), tails.end(), num);

        if (it == tails.end()) {
            // num is bigger than every tail seen so far: it extends the
            // longest subsequence found to date.
            tails.push_back(num);
        } else {
            // num gives a smaller tail for this subsequence length,
            // which can only help future elements extend it.
            *it = num;
        }
    }

    return (int)tails.size();
}
```

Trace on `[0,1,0,3,2,3]`: `tails` evolves `[0]` → `[0,1]` → `[0,1]` (the second `0` replaces index 0 with itself) → `[0,1,3]` → `[0,1,2]` (the `2` replaces the `3`) → `[0,1,2,3]`. Final size `4`, matching the expected output.

### 1. Computer Networks (Conceptual/Definition)

What happens during a TLS handshake when a browser connects to an HTTPS website? Describe the main steps, and explain why the handshake uses asymmetric cryptography only briefly before switching to symmetric encryption for the rest of the connection.

**Answer:**

TLS (Transport Layer Security) runs on top of an already-established TCP connection and has two jobs before any application data flows: **authenticate the server** (so the browser knows it's really talking to the site it asked for) and **agree on a shared secret** that both sides can use to encrypt everything that follows. A simplified modern (TLS 1.3-style) handshake looks like:

1. **ClientHello.** The browser sends the TLS versions and cipher suites it supports, plus a random value and its half of an ephemeral key exchange (e.g., an elliptic-curve Diffie-Hellman public value).
2. **ServerHello + certificate.** The server picks a cipher suite, sends its own ephemeral key-exchange value, and sends its **digital certificate** — which contains the server's public key and is signed by a Certificate Authority (CA) the browser already trusts.
3. **Certificate verification.** The browser checks the certificate's signature chain up to a trusted root CA, checks the hostname matches, and checks it isn't expired or revoked. This is the authentication step — it proves the server holds the private key matching a certificate a trusted third party vouched for.
4. **Key derivation.** Both sides independently combine their own private ephemeral value with the other side's public ephemeral value (Diffie-Hellman) to arrive at the *same* shared secret, without ever transmitting that secret itself. This shared secret is then run through a key-derivation function to produce the actual **symmetric session keys**.
5. **Finished messages.** Both sides send a MAC over the handshake transcript so far, encrypted under the new session keys, proving they derived the same keys and that nobody tampered with the handshake in transit.
6. From this point on, all application data (the actual HTTP request/response) is encrypted using the fast **symmetric** cipher (e.g., AES-GCM or ChaCha20-Poly1305) with the derived session key.

**Why switch to symmetric encryption at all, instead of just using the server's public key for everything?** Asymmetric (public-key) cryptography is computationally expensive — operations like RSA or elliptic-curve math are orders of magnitude slower than symmetric ciphers, and that cost scales with every byte you'd encrypt. Public-key crypto is used only for the small, one-time job it's uniquely suited for: authenticating identity and bootstrapping a secret without ever sending that secret in the clear. Once both sides share that secret, symmetric encryption — which is extremely fast and well-suited to bulk data — takes over for the (potentially huge) volume of actual traffic. Using ephemeral key exchange (rather than encrypting the session key directly with the server's public key) is also what gives modern TLS **forward secrecy**: even if the server's long-term private key leaks later, past sessions can't be decrypted, because their session keys depended on ephemeral values that were never stored anywhere.

### 2. DBMS (Comparison)

Compare database normalization and denormalization. What specific problem does normalization solve, what does denormalization trade away to get back, and when would you deliberately denormalize a schema that's already in a higher normal form?

**Answer:**

**Normalization** is the process of organizing tables so that each piece of information is stored in exactly one place, following a sequence of rules (normal forms):
- **1NF** — each column holds a single atomic value, no repeating groups.
- **2NF** — (for tables with composite keys) every non-key column depends on the *whole* key, not just part of it.
- **3NF** — every non-key column depends only on the key, not on another non-key column (no "transitive" dependencies).

The problem normalization solves is **redundancy and the anomalies it causes**. If a customer's address is duplicated across every one of their orders, you get:
- *Update anomaly* — change the address, and you must remember to update it everywhere it's copied, or the copies drift out of sync.
- *Insertion anomaly* — you can't record a new customer until they place an order, if the customer's data only exists embedded inside order rows.
- *Deletion anomaly* — deleting a customer's last order accidentally deletes the only copy of their address too.

Normalizing fixes this by splitting data into separate tables (`customers`, `orders`) connected by foreign keys, so each fact lives in exactly one row.

**Denormalization** deliberately reverses this: it reintroduces redundancy — duplicating or precomputing data — in exchange for **read performance**. A fully normalized schema often needs several `JOIN`s to answer a common query (e.g., "show each order with the customer's name"), and joins get expensive as tables grow into the tens of millions of rows. Denormalizing might mean storing the customer's name directly on the `orders` row, or maintaining a precomputed summary table of totals, so a hot-path query can be answered by reading one table instead of joining several.

**When it's the right call:** when a system is heavily **read-dominated** and a specific query pattern is both frequent and expensive to join for — e.g., a dashboard that reads order summaries thousands of times a second, but orders are written far less often. The trade is explicit: you accept the *complexity and risk* of keeping duplicated data in sync (usually via application logic, triggers, or an async job) in return for avoiding repeated expensive joins on the critical read path. It's rarely the first move — most systems normalize first for correctness, then denormalize surgically, one query pattern at a time, once profiling actually shows the joins are the bottleneck.

### 3. OOP (Scenario/Applied)

A codebase has a `Rectangle` class with independent `setWidth(w)` and `setHeight(h)` methods. A developer adds a `Square` class that extends `Rectangle`, overriding both setters so that setting either dimension sets *both* (to keep it a square). Later, code written against the `Rectangle` type does:

```cpp
void resize(Rectangle& r) {
    r.setWidth(5);
    r.setHeight(4);
    assert(r.area() == 20); // fails when r is actually a Square
}
```

Why does passing a `Square` here break the program, which OOP design principle does this violate, and how would you redesign the class hierarchy to avoid it?

**Answer:**

This is the textbook violation of the **Liskov Substitution Principle (LSP)**, which states that if `S` is a subtype of `T`, objects of type `T` should be replaceable with objects of type `S` *without altering the correctness of the program*. `resize()` is written entirely in terms of `Rectangle`'s contract: "set the width, set the height, these are independent." A caller is entitled to assume that contract holds for *any* `Rectangle`, because that's the whole point of subtyping — it lets code depend on the base type without knowing or caring which concrete subtype it actually received.

`Square`'s overridden setters quietly change that contract: setting the width also changes the height as a side effect. So after `r.setWidth(5); r.setHeight(4);`, a true `Rectangle` would be 5×4 (area 20), but a `Square` ends up 4×4 (area 16) — the `assert` fails, and it fails *only* because of which concrete subtype got passed in, which is exactly the bug LSP is designed to rule out. The deeper issue: mathematically a square *is-a* rectangle, but that doesn't mean `Square` should be a *programming* subtype of `Rectangle` here, because `Rectangle`'s actual behavioral contract (independently mutable width and height) is something a square fundamentally cannot honor without breaking an invariant the base type promised.

**How to fix it**, in rough order of preference:

1. **Don't model the inheritance relationship at all.** Make `Rectangle` and `Square` independent classes, each implementing a common read-only `Shape` interface (e.g., `area()`), with no setter contract to violate. If shapes are immutable (construct a new one instead of mutating), the whole problem disappears — there's no `setWidth`/`setHeight` contract to break because there's no mutation.
2. **Use composition instead of inheritance.** A `Square` can *have a* `Rectangle` internally (or just store a single `side` field) and expose its own API, rather than *being a* `Rectangle` that has to honor `Rectangle`'s mutable setter contract.
3. **If mutation is required and the hierarchy must stay**, narrow the base type's contract so it no longer promises independent width/height mutation — e.g., expose only a constructor-time size and a `resize(width, height)` method that `Square` can legitimately override to mean "resize to a square of `max(width, height)`," documented as part of the contract rather than silently breaking an assumed one.

The general lesson: inheritance should model *behavioral* substitutability, not just real-world taxonomic "is-a" relationships. Whenever a subclass has to override a method to silently narrow or change what the base class promised, that's a strong signal the hierarchy itself is wrong, not just the override.
