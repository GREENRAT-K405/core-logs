## DSA

### Question: Vertical Order Traversal of a Binary Tree (Trees — Medium)

Given the `root` of a binary tree, return the **vertical order traversal** of its nodes' values — from top to bottom, column by column.

Assign each node a `(row, col)` coordinate: the root is at `(0, 0)`. For any node at `(row, col)`, its left child is at `(row + 1, col - 1)` and its right child is at `(row + 1, col + 1)`.

Group nodes by column, ordered from the leftmost column to the rightmost column. Within a column, nodes must be ordered by increasing row. If two or more nodes share the same `(row, col)`, order them by increasing value.

Return the result as a list of columns, each column being a list of values in the order described.

**Input format:** The binary tree, given level-order with `null` for missing children (e.g. `[3,9,20,null,null,15,7]`).
**Output format:** A list of lists of integers — one inner list per column, left to right.

**Example 1:**
```
Input:
        3
       / \
      9  20
         / \
        15  7

Output: [[9], [3, 15], [20], [7]]
```
Explanation: column -1 has only 9; column 0 has 3 (row 0) and 15 (row 2); column 1 has 20 (row 1); column 2 has 7 (row 2).

**Example 2:**
```
Input:
        1
       / \
      2   3
     /   /
    4   5

Output: [[4], [2], [1, 5], [3]]
```
Explanation: 1 is at (row 0, col 0). 2 is at (row 1, col -1), 4 is at (row 2, col -2). 3 is at (row 1, col 1), 5 is at (row 2, col 0). Column 0 holds 1 (row 0) and 5 (row 2), ordered by row.

**Example 3 (tie-break by value):**
```
Input:
        1
       / \
      2   3
       \  /
        4 5

Output: [[2], [1, 4, 5], [3]]
```
Explanation: 1 is at (0, 0). 2 is at (1, -1). 3 is at (1, 1). 4 (right child of 2) is at (2, 0). 5 (left child of 3) is at (2, 0) — same row and column as 4. Since they tie, they're ordered by value: 4 before 5. So column 0 is `[1, 4, 5]`.

**Constraints:**
- The number of nodes is in the range `[1, 1000]`.
- `0 <= Node.val <= 1000`

### Step-by-Step Walkthrough

**Approach.**
The core idea is to traverse the tree once, recording each node's `(column, row, value)`, then group and sort.

1. Do a BFS (or DFS) starting from the root at `(row = 0, col = 0)`.
2. For each visited node, push `(col, row, val)` onto a list. When moving to the left child, `col - 1`, `row + 1`; for the right child, `col + 1`, `row + 1`.
3. Once traversal is complete, sort the collected triples first by `col`, then by `row`, then by `val`. This single sort naturally produces: columns left-to-right, and within a column, top-to-bottom, with value as the tiebreaker for nodes that land on the exact same `(row, col)`.
4. Walk the sorted list and bucket values into output groups whenever the `col` changes, producing the final list of columns.

**Why it works.** The `(row, col)` labeling is exactly the rule given in the problem, so any node's position is fully determined by walking down from the root and applying the ±1 offsets. Because we need a global ordering across the *whole* tree (not a per-subtree ordering), it's easier to collect all `(col, row, val)` triples first and sort, rather than trying to merge column lists from left and right subtrees during a recursive DFS (which gets messy when left and right subtrees overlap in column range, as in Example 3).

BFS vs DFS for collection doesn't matter here — correctness comes entirely from the final sort key `(col, row, val)`, not from traversal order. BFS is used below for clarity.

**Complexity.**
- Time: `O(n log n)` — `O(n)` to visit every node and collect triples, `O(n log n)` to sort them.
- Space: `O(n)` to store the triples and the BFS queue.

### C++ Code

```cpp
#include <vector>
#include <queue>
#include <algorithm>
using namespace std;

struct TreeNode {
    int val;
    TreeNode *left;
    TreeNode *right;
    TreeNode(int x) : val(x), left(nullptr), right(nullptr) {}
};

class Solution {
public:
    vector<vector<int>> verticalTraversal(TreeNode* root) {
        // Each entry: (column, row, value)
        vector<tuple<int, int, int>> nodes;

        // BFS, tracking (node, row, col) so we visit level by level.
        queue<tuple<TreeNode*, int, int>> q;
        if (root) q.push({root, 0, 0});

        while (!q.empty()) {
            auto [node, row, col] = q.front();
            q.pop();
            nodes.push_back({col, row, node->val});

            if (node->left) q.push({node->left, row + 1, col - 1});
            if (node->right) q.push({node->right, row + 1, col + 1});
        }

        // Sort by column, then row, then value (tuple's default
        // lexicographic comparison does exactly this).
        sort(nodes.begin(), nodes.end());

        vector<vector<int>> result;
        int prevCol = INT_MIN;
        for (auto& [col, row, val] : nodes) {
            if (col != prevCol) {
                result.push_back({});
                prevCol = col;
            }
            result.back().push_back(val);
        }
        return result;
    }
};
```

### 1. Computer Networks (Conceptual)

What is the purpose of the TCP three-way handshake, and what would go wrong if a client and server started exchanging data without performing it?

**Answer:**

The three-way handshake (`SYN` → `SYN-ACK` → `ACK`) exists to let both sides of a TCP connection agree on and confirm two things before any application data flows: (1) that each side is actually reachable and willing to communicate, and (2) the **initial sequence numbers (ISNs)** each side will use to track bytes in the stream.

Step by step:
- The client sends `SYN` with its chosen ISN (`seq = x`), signaling "I want to open a connection, and I'll start counting my bytes from x."
- The server responds `SYN-ACK`, acknowledging the client's ISN (`ack = x+1`) and sending its own ISN (`seq = y`).
- The client responds `ACK` (`ack = y+1`), confirming it received the server's ISN.

After this exchange, both sides know: the other end is alive and listening, the starting sequence number to expect, and that packets exchanged so far did reach their destination.

If data exchange started without this handshake:
- Neither side could reliably distinguish a fresh connection's packets from a stray/duplicate packet from an old, already-closed connection — reused ports plus non-synchronized sequence numbers would make it impossible to detect out-of-order or duplicate data correctly.
- There would be no agreed sequence number baseline, so reassembling the byte stream in order and detecting lost segments (via acknowledgments) would break down.
- A server could not verify the client is actually reachable at the claimed source address before committing resources — this is also why the handshake, combined with SYN cookies, helps defend against certain spoofing-style floods (a half-open SYN flood being the classic abuse case the handshake is designed around, which is why servers track "half-open" connections and can rate-limit or drop them).

In short, the handshake is TCP's way of establishing a shared, synchronized starting point so the reliable, ordered, duplicate-free delivery guarantees TCP promises can actually hold.

### 2. Computer Architecture (Comparison)

Compare write-through and write-back cache policies: how does each handle a write to a cached memory location, and what are the trade-offs?

**Answer:**

Both policies answer the question: "When the CPU writes to data that's in the cache, when does main memory get updated?"

**Write-through:**
- Every write to the cache is immediately also written to main memory (or the next level down).
- Cache and memory are always consistent.
- Pros: simpler to implement, memory is never "behind," and it's trivially safe for other devices (e.g. DMA, other cores) reading memory directly, since memory is never stale.
- Cons: every write pays the latency of a memory access, even if the same line is written to repeatedly — this wastes bandwidth and hurts performance, especially in write-heavy workloads. A **write buffer** is often added to partially hide this latency by queuing writes, but it doesn't eliminate the extra memory traffic.

**Write-back:**
- Writes update only the cache line, which is marked **dirty**. The write is propagated to main memory only when that line is evicted (replaced) from the cache.
- Pros: multiple writes to the same line cost one memory write (at eviction) instead of one per write — much better performance for write-heavy or repeatedly-updated data, and less memory bus traffic overall.
- Cons: more complex to implement (needs a dirty bit per line, and eviction logic that writes dirty lines back before discarding them); memory is often stale relative to the cache, which matters a lot for cache coherence in multi-core systems (another core, or a DMA device, reading memory directly might see outdated data unless coherence protocols like MESI handle it).

**Trade-off summary:** write-through trades performance for simplicity and consistency; write-back trades some complexity (dirty bits, coherence protocols) for significantly better write performance by batching memory updates. Most modern CPU caches use write-back for exactly this reason — write-heavy code is common, and the coherence complexity is manageable with well-established protocols.

### 3. DBMS (Scenario/Applied)

A reporting query filters a 50-million-row `orders` table with `WHERE customer_id = ? AND order_date >= ?`, and it currently takes 40 seconds because it does a full table scan. The table already has a single-column index on `customer_id`. What would you check and change to speed this query up, and why?

**Answer:**

First, confirm the diagnosis rather than guessing: run `EXPLAIN` (or `EXPLAIN ANALYZE`) on the query. If it shows a full table scan (or even an index scan on `customer_id` alone followed by a large in-memory filter on `order_date`), that confirms the index isn't being used effectively for this query shape.

Why the existing single-column index on `customer_id` may not be helping enough: if a given `customer_id` still matches, say, thousands of rows, the database would use the index to find all of those rows, then still have to check `order_date` on each one individually — and if the optimizer estimates that's not much better than a full scan (e.g. the `customer_id` isn't selective), it may just scan the whole table instead.

The fix: create a **composite (compound) index on `(customer_id, order_date)`**, in that column order. This matters because:
- A B-tree composite index is sorted first by `customer_id`, then by `order_date` within each `customer_id`. That means once the engine locates the matching `customer_id` prefix, all matching `order_date >= ?` rows are already contiguous in the index — it can do a single efficient range scan instead of filtering row-by-row.
- Column order matters: `(customer_id, order_date)` supports this query well because the predicate uses equality on `customer_id` (the leading column) and a range on `order_date` (the second column). The reverse order, `(order_date, customer_id)`, would not help, since the leading column needs to support the equality filter to narrow things down first.
- If the query also only needs a few columns (e.g. `order_id`, `total_amount`), consider making it a **covering index** by including those columns, so the engine never has to go back to the full table row ("bookmark lookup") at all — it can answer entirely from the index.

Other things worth checking in this scenario: whether statistics on the table are stale (causing the optimizer to misjudge selectivity and pick a bad plan), whether the table is partitioned by date (which could let the engine skip irrelevant partitions entirely), and whether this query runs often enough to justify the extra write-side cost of maintaining a new index (every index speeds up reads but adds overhead to every `INSERT`/`UPDATE` on that table).
